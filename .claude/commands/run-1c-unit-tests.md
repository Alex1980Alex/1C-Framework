# Прогон YAxUnit unit-тестов для задачи 1С

Запусти YAxUnit unit-тесты задачи 1С через **`mcp-onec-test-runner`** и обнови `.run-state.json`
в папке задачи в формате, совместимом с BDD-треком (тот же массив `chain[]`), чтобы Stop-хук
`advance_test_done` авто-продвинул этап 4 пайплайна при всех `passed`.

## Задача от пользователя:
$ARGUMENTS

---

## Инструкция

### Входные данные

Из `$ARGUMENTS` извлеки:
1. **Путь к папке задачи** (или `src/bsl/exts/UnitTests/`) — для поиска тест-модулей
2. **Параметры (опционально):**
   - `--module <ИмяМодуля>` — запустить только один тест-модуль (`run_module_tests`)
   - `--all` — запустить все тесты расширения (`run_all_tests`)
   - `--fresh` — сбросить `chain[].type == "yaxunit"` записи в state и прогнать заново
   - `--dry-run` — только показать список найденных тест-модулей без запуска

**Если параметры не переданы** — определить по state:
- если есть записи `chain[].type == "yaxunit"` со `status != "passed"` → прогнать их
- если все уже `passed` → сообщить «все unit-тесты пройдены; --fresh для повтора»
- если записей нет → прогнать `run_all_tests` и добавить найденные модули в state

### Резолв путей

- **State file** (`.run-state.json`):
  - 1С-задача (есть `pipeline/<slug>/.pipeline-state.json`) → `<task_dir>/.run-state.json`
  - legacy/не-1С → `src/bsl/exts/UnitTests/.run-state.json`
- **Строка подключения:** `.env` → `ONEC_TEST_CONN`
  - Дефолт (prod-TestDB): `Srvr="KOMPUTER";Ref="TestDB"` — **может быть недоступен!**
  - Локальная рабочая БД: `Srvr="DESKTOP-TNU600C";Ref="ИБTransportManagementDevelop"`
  - При ошибке соединения → показать обе строки и попросить пользователя задать `ONEC_TEST_CONN` в `.env`

## Pipeline (5 этапов)

### Этап 1 — Получить конфигурацию раннера

```
mcp__mcp-onec-test-runner__get_configuration()
→ убедиться что раннер доступен и знает строку подключения
```

Если `get_configuration` упал или вернул ошибку подключения:
- Проверить `.env` → `ONEC_TEST_CONN`
- Напомнить пользователю: после правки `.env` нужен `/mcp reconnect` для перезагрузки раннера

### Этап 2 — Определить список тест-модулей

**Если `--module <Имя>`:** прогнать только этот модуль → перейти к Этапу 3.

**Если `--all` или нет параметров:** найти все модули задачи:
```
Glob("src/bsl/exts/UnitTests/CommonModules/*Тест/")
→ список имён директорий → имена модулей
```

Из `.run-state.json` отфильтровать:
- уже `passed` (пропустить, если нет `--fresh`)
- `failed` / `pending` / отсутствующие → включить в прогон

**Если `--dry-run`:** показать таблицу

| Модуль | Статус в state | Действие |
|---|---|---|
| `гкс_ОбъектТест` | `passed` | пропустить |
| `гкс_МодульТест` | `failed` | прогнать |
| `гкс_НовыйТест` | (нет) | прогнать |

Не запускать ничего, завершить.

### Этап 3 — Прогон тестов

**Один модуль:**
```
mcp__mcp-onec-test-runner__run_module_tests(moduleName="гкс_<ИмяОбъекта>Тест")
```

**Все тесты расширения:**
```
mcp__mcp-onec-test-runner__run_all_tests(full=true)
```

Для каждого вызова зафиксировать:
- `passed` / `failed` / `errors` — из ответа раннера
- `duration_s` — время исполнения
- для `failed` — извлечь текст ошибки / имя упавшей процедуры

### Этап 4 — Парсинг JUnit и обновление state

Раннер возвращает JUnit-совместимый результат. Для каждого тест-модуля сформировать
запись в `chain[]` формата:

```json
{
  "section": "unit_гкс_<ИмяОбъекта>Тест",
  "type": "yaxunit",
  "feature_file": null,
  "status": "passed",
  "started_at": "<ISO-timestamp>",
  "duration_s": 12,
  "passed": 3,
  "failed": 0,
  "errors": 0,
  "module": "гкс_<ИмяОбъекта>Тест",
  "attempts": 1,
  "pre_check": "ok",
  "post_check": "ok",
  "dependencies": [],
  "created_objects": []
}
```

Записать/обновить `.run-state.json`:
```json
{
  "task": "<TASK-ID>",
  "last_run": "<ISO-timestamp>",
  "chain": [
    { ...BDD-секции из предыдущего прогона... },
    { "section": "unit_гкс_<ИмяОбъекта>Тест", "type": "yaxunit", "status": "passed", ... }
  ]
}
```

**Правила слияния с существующим state:**
- BDD-записи (`type` отсутствует или `type == "bdd"`) — **не трогать**
- YAxUnit-записи (`type == "yaxunit"`) — перезаписать при `--fresh` или при ошибке, обновить при успехе
- Порядок в `chain[]`: BDD-секции сначала, YAxUnit-секции в конце (по алфавиту имени модуля)

**Stop-хук `advance_test_done`** читает `all(chain[].status == "passed")` — при выполнении условия
авто-продвигает этап 4 без правки хука. Для смешанного BDD+YAxUnit пайплайна это работает
корректно: BDD прошли (от `/run-1c-tests`) + YAxUnit прошли (от `/run-1c-unit-tests`) → все passed.

### Этап 5 — Диагностика падений и отчёт

**При `failed > 0`:**

1. Извлечь имя упавшей тест-процедуры из JUnit XML
2. Сопоставить с таблицей типовых ошибок:

| Симптом | Вероятная причина | Действие |
|---|---|---|
| `passed=0, errors=0` | Тест-модуль не задеплоен | Запустить деплой (`LoadConfigFromFiles + UpdateDBCfg`), повторить |
| `Метод не найден` | Опечатка в имени или не `Экспорт` | `/write-1c-unit-tests` → проверить сигнатуру |
| `ОжидаетЧто` провалил | Результат не совпал с ожидаемым | Прочитать метод, уточнить ожидание |
| Ошибка соединения | `ONEC_TEST_CONN` указывает на недоступный сервер | Проверить `.env`, `/mcp reconnect` |
| `Нет доступа` | Нужен привилегированный режим | В XML модуля установить `<Privileged>true</Privileged>` |

3. Предложить конкретный fix для каждого падения
4. Сохранить state с `"status": "failed"` и `"error": "<текст>"`

**Итоговый отчёт в чате:**

```
YAxUnit: <TASK-ID> (N модулей)
  [OK]   гкс_ДиректорияТранспортаТест   12s   (3 passed)
  [OK]   гкс_ВодительТест               8s    (2 passed)
  [FAIL] гкс_РасчётСуммыТест            ---   (1 failed: ТестДолжен_Рассчитать_ПриНуле)

BLOCKER at гкс_РасчётСуммыТест:
  Процедура: ТестДолжен_Рассчитать_ПриНуле
  Ошибка: ОжидаетЧто получило 0, ожидалось Неопределено
  Action: прочитать метод РассчитатьСумму, уточнить ожидание для нулевого входа
  Повтор: /run-1c-unit-tests <папка> --module гкс_РасчётСуммыТест

State: <task_dir>/.run-state.json обновлён
```

## Параметры команды

| Параметр | Назначение | Пример |
|---|---|---|
| `<путь>` (обязательный) | Путь к папке задачи или `src/bsl/exts/UnitTests/` | `configuration/260304_.../docs/` |
| `--module <Имя>` | Прогнать только один тест-модуль | `--module гкс_ДиректорияТранспортаТест` |
| `--all` | Прогнать все тесты расширения UnitTests | `--all` |
| `--fresh` | Сбросить YAxUnit-записи в state и прогнать заново | `--fresh` |
| `--dry-run` | Только список модулей и их статус без запуска | `--dry-run` |

### Типовые сценарии

**1. Первый прогон всех unit-тестов задачи:**
```
/run-1c-unit-tests configuration/260304_.../docs/
```

**2. Прогон одного упавшего модуля (отладка):**
```
/run-1c-unit-tests configuration/260304_.../docs/ --module гкс_РасчётСуммыТест
```

**3. Полный прогон расширения UnitTests:**
```
/run-1c-unit-tests src/bsl/exts/UnitTests/ --all
```

**4. Проверка состояния без запуска:**
```
/run-1c-unit-tests configuration/260304_.../docs/ --dry-run
```

## Кавеат: строка подключения раннера

`mcp-onec-test-runner` берёт строку подключения из переменной окружения `ONEC_TEST_CONN`
при старте MCP-процесса (не при каждом вызове).

Дефолт в конфиге (`Srvr="KOMPUTER";Ref="TestDB"`) указывает на CI/CD TestDB, которая
**может быть недоступна** в локальной разработке.

Для локальной работы:
1. В `.env` (корень репозитория) задать: `ONEC_TEST_CONN=Srvr="DESKTOP-TNU600C";Ref="ИБTransportManagementDevelop"`
2. Выполнить `/mcp reconnect` в Claude Code — это перезапустит mcp-onec-test-runner
   с новым значением переменной
3. Проверить: `mcp__mcp-onec-test-runner__get_configuration()` должен показать рабочую БД

## ВАЖНО

- **НЕ переписывай тест-модули.** Эта команда только ЗАПУСКАЕТ. Исправление тестов — через
  `/write-1c-unit-tests`.
- **Уважай BDD-секции в state** — не трогай `chain[]` записи без `type == "yaxunit"`.
- **Деплой — вне этой команды.** Если тесты не находятся (`passed=0`), значит расширение
  не задеплоено. Деплой выполняет `/write-1c-unit-tests` (Фаза 3, шаг 3.4).
- **`advance_test_done`** срабатывает только когда ALL секции в `chain[]` имеют `status == "passed"`,
  включая BDD-секции. Если BDD ещё не запускались — этап 4 не продвинется автоматически.
- **После правки `.env`** всегда нужен `/mcp reconnect` — раннер кеширует строку подключения.
