# Написание VA BDD тестов для задачи 1С

Напиши автоматизированные тесты Vanessa Automation (VA BDD) по готовому плану тестирования задачи, используя **skill `va-bdd-testing`**.

## Задача от пользователя:
$ARGUMENTS

---

## Инструкция

**Используй skill `va-bdd-testing`** — единый источник методологии написания VA BDD тестов
(откалиброванные step-паттерны, правила анализа форм, обработка диалогов, ARM workflow).

### Входные данные

Из `$ARGUMENTS` извлеки:
1. **Путь к TEST-PLAN-DETAILED.md** (или папке задачи с планом) — описание сценариев, матрица автоматизации, карта объектов конфигурации
2. **Путь к `src/`** — корень исходников конфигурации (для анализа форм и модулей)
3. Дополнительный контекст (конкретный сценарий, фаза, тег)

**Если передан путь к папке задачи**, найди внутри:
- `*TEST-PLAN*DETAILED*.md` — план тестирования (обязателен)
- `*ANALYSIS-REPORT*.md` — анализ задачи (для понимания точек модификации)
- `*ТЗ*.md` / `*TS*.md` — исходное ТЗ (для бизнес-контекста)

**Код задачи (`<TASK-ID>`)** извлеки из пути или имени файла (`PROJECT-1234`). Slug для
имён директорий — нижний регистр без дефиса (`PROJECT-1234` → `project1234`).

## ЗОЛОТОЕ ПРАВИЛО: всё проверяется на реальной базе и реальных данных

Команда предполагает наличие **живой TestDB** с реальной конфигурацией и тестовыми данными.
**Ни один факт о конфигурации не принимается на веру из документации или памяти** — каждое
утверждение (имя поля, тип, состав значений, поведение проведения, роль, наличие справочного
значения) подтверждается вызовом MCP к TestDB или исходникам через EDT-MCP.

**Обязательные проверки на реальной базе:**

| Что | Чем проверять | Когда |
|---|---|---|
| Метаданные объекта | `mcp__1c-mcp-crud__get_metadata`, `get_metadata_structure` | Фаза 1, перед анализом формы |
| Структура формы | `mcp__1c-mcp-crud__get_form_structure`, `mcp__edt-mcp__get_form_structure` | Фаза 1 |
| Наличие тестовых данных | `mcp__1c-mcp-crud__execute_query` (ТС, номенклатура, контрагенты, настройки) | Фаза 1 + перед каждым сценарием |
| Синтаксис SQL-запросов | `mcp__1c-mcp-crud__validate_query` (ДО исполнения) | Фазы 2 и 4 |
| Результат SQL на живых данных | `mcp__1c-mcp-crud__execute_query` | Фазы 2 и 4 |
| Исполняемость BSL-логики (без БД) | `mcp__bsl-debugger__bsl_execute` (OneScript runtime) | Фаза 2 (сомнения в алгоритме) |
| Имена методов/типов платформы | `mcp__bsl-platform-context__search` / `getMember` | Фаза 3 |
| API платформы | `mcp__bsl-platform-context__info` / `getMembers` / `getConstructors` | Фаза 3 |

**Если данных для сценария нет в TestDB** — фиксируй в отчёте «блокер: нужно создать X» и
либо создавай через `mcp__1c-mcp-crud__execute_code` (перед сценарием как Контекст), либо
помечай сценарий `@pending` с пояснением.

## Декомпозиция: разбей тесты на логические блоки

**Правило:** один логический блок = один объект конфигурации + все связанные с ним формы и бизнес-логика.

**Источники для декомпозиции:**
- Матрица автоматизации в `TEST-PLAN-DETAILED.md` (обычно группируется по точкам модификации)
- Точки модификации из `ANALYSIS-REPORT.md` (каждая точка = 1-2 объекта)
- Результат `mcp__1c-mcp-crud__get_metadata_tree` — реальная структура конфигурации

**Типовые логические блоки (обобщённо, без привязки к конкретному проекту):**

| Тип блока | Что внутри | Отдельный `.feature`? |
|---|---|---|
| `Документ.<Имя>` | Форма документа, ObjectModule (ОбработкаПроведения), движения регистров | Да — `NN_<doc>_create.feature` |
| `Обработка.<Имя>` (АРМ) | Форма с DynamicList, командами правой/верхней панели, фоновыми обработчиками | Да — `NN_<proc>_workflow.feature` |
| `Справочник.<Имя>` (сложный) | Форма со вкладками, подчинёнными формами, условной видимостью | Да — если задача его модифицирует |
| `РегистрСведений.<Имя>` | Механизм агрегации из других объектов — проверяется через состояние после цепочки действий | Верификационные шаги в блоке исходного объекта |
| `ОбщийМодуль.<Имя>` | Не тестируется напрямую через UI — только через объекты, которые его вызывают | Нет |

Для каждого логического блока — отдельный `.feature`-файл с осмысленным именем
(`NN_<object>_<aspect>.feature`, где `NN` задаёт порядок запуска: smoke → unit → workflow → regression).

## Для КАЖДОГО логического блока — 4 последовательные фазы

Фазы выполняются **строго по порядку**. Переход к следующей фазе возможен только после
выполнения **Definition of Done** предыдущей (см. критерии в конце каждой фазы).

### Фаза 1 — Анализ формы объекта (клиент + сервер)

**Цель:** получить точные имена всех элементов формы, типы полей, кастомные кнопки,
условия видимости и обязательности — **подтверждённые на реальной конфигурации**.

**MCP-инструменты:**
- `mcp__1c-mcp-crud__get_metadata` — реквизиты, типы, составы перечислений (ЖИВАЯ база)
- `mcp__1c-mcp-crud__get_form_structure` — структура формы (ЖИВАЯ база)
- `mcp__edt-mcp__get_form_structure` / `get_form_screenshot` — резервный источник (из исходников EDT)
- `mcp__edt-mcp__read_module_source` — модуль формы (Form.Module.bsl): обработчики команд,
  `ОбработкаПроверкиЗаполненияНаСервере`, `ПриОткрытии`, условная видимость, условная обязательность
- `Grep` по `Form.xml`:
  - `<Button name=` — имена всех кнопок
  - `(InputField|LabelField|RadioButtonField|CheckBoxField|SpinBox|ComboBox)` — типы
  - `<Table name=` — таблицы (в том числе DynamicList)
  - `AutoCommandBar` — наличие стандартной панели (для `ФормаПровестиИЗакрыть` и т.п.)

**Чеклист (из скилла `va-bdd-testing`, Stage 1):**
- [ ] Element name для каждой кнопки / поля / таблицы (**НЕ** display title!)
- [ ] Тип каждого поля (InputField/LabelField/RadioButtonField/CheckBoxField/…)
- [ ] Стандартные vs кастомные кнопки проведения
  (пример: `ФормаПровестиИЗакрыть` vs кастомная `Форма<Имя>ИЗакрытьДокумент`)
- [ ] `DataPath` ≠ element name (часто есть расхождение: element `Вес` → DataPath `Объект.ВесБрутто`)
- [ ] Условия видимости элементов (зависимости от флагов, переключателей, ролей)
- [ ] Условная обязательность в `ОбработкаПроверкиЗаполненияНаСервере` (может отличаться от FillChecking!)
- [ ] Модальные диалоги (`ПоказатьВопрос`, `ПоказатьВводЧисла`, кастомные формы)
- [ ] Навигационная ссылка для открытия формы (`e1cib/app/` для обработок, `e1cib/list/` для списков)

**Definition of Done (Фаза 1):**
- [ ] Таблица element names → тип → описание зафиксирована в комментарии будущего `.feature`-файла
- [ ] Все «как кликнуть X» и «как ввести Y» имеют конкретный ответ со ссылкой на Form.xml/EDT
- [ ] Все условия видимости и обязательности перечислены списком с цитатой из Form.Module.bsl
- [ ] `get_form_structure` выполнен на ЖИВОЙ TestDB — результат совпадает с EDT-источником
- [ ] Ни одной открытой неопределённости по форме

### Фаза 2 — Анализ объектной модели (максимальная глубина)

**Цель:** понять бизнес-логику до мельчайших деталей — что происходит при проведении,
какие движения создаются, какие состояния меняются, какие общие модули вызываются,
какие роли и права требуются — **с валидацией на TestDB**.

**MCP-инструменты:**
- `mcp__edt-mcp__read_module_source` — ObjectModule (`ОбработкаПроведения`,
  `ОбработкаПроверкиЗаполнения`), ManagerModule (`ТекстЗапроса*`, процедуры-геттеры)
- `mcp__bsl-semantic-search__bsl_search` — семантический поиск по 3900+ модулям
- `mcp__bsl-semantic-search__bsl_call_graph` — кто вызывает эту процедуру, глубина цепочки
- `mcp__bsl-semantic-search__bsl_impact_analysis` — что сломается при изменении
- `mcp__bsl-semantic-search__bsl_object_info` — структура объекта и связи
- `mcp__bsl-semantic-search__bsl_coding_context` — стиль окружающего кода
- `mcp__ast-grep-mcp__ast_grep` — точечный поиск паттернов BSL
- `mcp__1c-mcp-crud__execute_query` — прогнать запросы на TestDB, валидация на **реальных данных**
- `mcp__1c-mcp-crud__validate_query` — синтаксическая проверка запроса ДО исполнения
- `mcp__1c-mcp-crud__find_references_to_object` — найти ссылки на объект в базе
- `mcp__bsl-debugger__bsl_execute` — прогнать чистую логику на OneScript без подключения к БД
- `mcp-reasoner` со стратегиями `bsl_document_patterns` (10 уровней для документов),
  `bsl_subsystem_analysis` (12 уровней для подсистем), `bsl_architecture` (8 уровней)

**Что именно выяснить:**
- [ ] **Цепочка состояний** — какие значения перечислений возможны, через что переходят
  (state machine на бумаге)
- [ ] **Движения документа** — какие регистры пишет, в какой последовательности
  (ObjectModule.ОбработкаПроведения → общие модули проведения)
- [ ] **Триггеры набора записей** — что запускается при `ПриЗаписи` / `ПередЗаписью` наборов
  (влияет на обновление других объектов)
- [ ] **Управляющая логика формы** — условия «когда кнопка доступна», «когда поле обязательно»,
  «когда появляется диалог», «когда элемент виден»
- [ ] **Взаимодействие с другими объектами** — какие документы создаются из команд АРМ, какие
  предзаполнены, какие поля требуют ручного ввода
- [ ] **Роли и права** — требуется ли специфическая роль для кнопки/команды; проверить через
  `mcp__1c-mcp-crud__get_access_rights`
- [ ] **Асинхронные обработчики** — `ПодключитьОбработчикОжидания`, длительные операции
  (влияет на паузы в тестах)
- [ ] **Валидация на живых данных** — для каждого ключевого запроса логики запустить его на
  TestDB через `execute_query` и зафиксировать результат в отчёте

**Definition of Done (Фаза 2):**
- [ ] Карта state machine нарисована в Markdown (стрелки между состояниями + триггеры)
- [ ] Список движений документа с цитатами из кода (каждое — строка таблицы: регистр → что пишется → условие)
- [ ] Список асинхронных триггеров задокументирован (название обработчика, период, что делает)
- [ ] Матрица «действие → состояние → побочные эффекты» зафиксирована
- [ ] Все ключевые запросы прошли `validate_query` и исполнены на TestDB — результат приложен
- [ ] Роли/права для каждой кнопки подтверждены через `get_access_rights`
- [ ] Нет гипотез без подтверждения: либо код, либо SQL-результат, либо `bsl_execute`

### Фаза 3 — Дополнительное исследование (VA docs + API платформы + интернет)

**Цель:** найти откалиброванные паттерны для нестандартных сценариев, которых нет в скилле
`va-bdd-testing`, и подтвердить используемые API платформы 1С:8.3.27.

#### 3.1 API платформы 1С — `bsl-platform-context` (ОБЯЗАТЕЛЬНО для Фазы 2/4)

Используй `bsl-platform-context` для каждого использованного в тесте или проверочном запросе
типа/метода/свойства платформы:

- `mcp__bsl-platform-context__search` — общий поиск по API 8.3.27 (типы, методы, свойства,
  глобальные функции, менеджеры, константы)
- `mcp__bsl-platform-context__info` — краткая информация по найденному объекту
- `mcp__bsl-platform-context__getMember` — детали одного метода/свойства (сигнатура,
  параметры, возвращаемое значение, доступность на клиенте/сервере)
- `mcp__bsl-platform-context__getMembers` — все члены типа (полезно при работе с
  `ТаблицаЗначений`, `ДокументОбъект`, `НаборЗаписей`, `Запрос` и т.п.)
- `mcp__bsl-platform-context__getConstructors` — конструкторы типа (для создания объектов в
  `execute_code`)

**Когда обязательно обращаться к `bsl-platform-context`:**
- Используешь метод, в котором не уверен (`НайтиПоНаименованию` vs `НайтиПоКоду`, параметры порядка)
- Работаешь с контекстом клиент/сервер — нужно знать, доступен ли метод там, где ты его вызываешь
- Проверяешь поведение `ДокументОбъект.Записать()` / `Провести()` / параметры `РежимЗаписи`
- Разбираешь `ПолучитьФорму` / `ОткрытьФорму` — какие параметры передаёт форма
- Создаёшь объекты через `execute_code` — нужны конструкторы
- При сомнении «а это реально есть в 8.3.27?»

### Фаза 4 — Написание тестов

**Цель:** собрать `.feature`-файл из откалиброванных паттернов, с явным планом калибровки
неопределённых мест и **с валидацией тестовых данных на TestDB**.

**Правила (из скилла `va-bdd-testing`):**
- Используй **только откалиброванные паттерны** из секций 3.1–3.15 скилла. **НЕ ВЫДУМЫВАЙ**
  синтаксис шагов.
- Каждый неоткалиброванный момент — отмечай VERIFY-комментарием (`V1 pending — ...`) для
  последующего probe-прогона.
- Wildcard-паттерны для заголовков окон (`"*часть*"`), element names (не display titles).
- Паузы после асинхронных операций: проведение документа, поиск в справочнике, обновление формы.
- Cleanup в начале сценария: `И Я закрыл все окна клиентского приложения`.
- Один сценарий = одна смена состояния / одно бизнес-действие.
- Один логический блок = один `.feature`-файл (не смешивай сценарии разных объектов).

**Предзапись — проверка тестовых данных на TestDB:**

Перед тем как писать `.feature`, для каждого упоминаемого в сценариях объекта (ТС, номенклатура,
контрагент, справочное значение) **подтверди существование в TestDB** через
`mcp__1c-mcp-crud__execute_query`. Если объекта нет — либо найди замену, либо создай через
`execute_code` в блоке `Контекст:` / `Предусловие:`.

**Для каждого SQL-запроса верификации** (Stage 4 скилла):
1. `mcp__1c-mcp-crud__validate_query` — синтаксическая проверка
2. `mcp__1c-mcp-crud__execute_query` — исполнение на TestDB с фиксацией результата
3. Только после этого — вставка в шаги `Тогда`

**Структура вывода:**
```
features/<task-slug>/
    NN_<logical-block>.feature     # production сценарии
    probe_<aspect>.feature         # probe/калибровка (отдельно от production!)
```

Где `<task-slug>` = код задачи в нижнем регистре без дефисов (`PROJECT-1234` → `project1234`).

**В шапке каждого файла:**
```gherkin
# language: ru

# METADATA:
#   Task: <TASK-ID>
#   Logical block: <ТипОбъекта>.<Имя>
#   Configuration objects: {список полных имён метаданных}
#   TestDB data: {список реальных записей, которые используются}
#   Dependencies: {имена других feature-файлов, которые должны пройти первыми}
#
# CALIBRATION LOG:
#   V1  confirmed   Окно "*часть-заголовка*" — подтверждено probe 2026-XX-XX
#   V2  pending     Кнопка <Имя> — требует probe
#   V3  source      Инфостарт: https://... (паттерн для <control>)
```

**Definition of Done (Фаза 4):**
- [ ] `.feature`-файл создан в `features/<task-slug>/`

## ВАЖНО

- **НЕ запускай тесты** — эта команда только ПИШЕТ. Запуск — через `/run-1c-tests`
  (будет создан отдельно).
- **Сначала анализ, потом код** — Фазы 1-3 обязательны перед Фазой 4. Пропуск анализа =
  тесты не заработают с первого раза. Каждая фаза имеет Definition of Done — не переходи
  к следующей, пока текущая не закрыта.
- **Каждый логический блок — отдельный файл.** Не смешивай сценарии разных объектов
  конфигурации.
- **Только откалиброванные паттерны** из скилла `va-bdd-testing`. Новые паттерны из Фазы 3 —
  сначала в probe, потом в production.
- **Реальная база — источник истины.** Не принимай имена/типы/значения на веру из памяти
  или документации. Всегда перепроверяй через `mcp__1c-mcp-crud__*` и `mcp__bsl-platform-context__*`.
- **Для каждого SQL-запроса верификации** — `validate_query` → `execute_query` ДО вставки в шаги.
- **Тестовые данные** (ТС, номенклатура, контрагенты, справочные значения) — существование
  в TestDB обязательно подтверждается до написания сценария.
- **НЕ модифицируй** `TEST-PLAN-DETAILED.md` кроме секции статусов калибровки — остальной
  план задаёт требования.
- Веди калибровочный лог в комментариях feature-файла (V1, V2, … с датой, статусом и источником).
