# Написание VA BDD тестов для задачи 1С

Напиши автоматизированные тесты Vanessa Automation (VA BDD) по готовому плану тестирования задачи, используя **skill `va-bdd-testing`**.

## Задача от пользователя:
$ARGUMENTS

---

## Инструкция

**Используй skill `va-bdd-testing`** — единый источник методологии написания VA BDD тестов
(откалиброванные step-паттерны, правила анализа форм, обработка диалогов, ARM workflow).

### Входные данные

Из `$ARGUMENTS` извлеки:
1. **Путь к TEST-PLAN-DETAILED.md** (или папке задачи с планом) — описание сценариев, матрица автоматизации, карта объектов конфигурации
2. **Путь к `src/`** — корень исходников конфигурации (для анализа форм и модулей)
3. Дополнительный контекст (конкретный сценарий, фаза, тег)

**Если передан путь к папке задачи**, найди внутри:
- `*TEST-PLAN*DETAILED*.md` — план тестирования (обязателен)
- `*ANALYSIS-REPORT*.md` — анализ задачи (для понимания точек модификации)
- `*ТЗ*.md` / `*TS*.md` — исходное ТЗ (для бизнес-контекста)

**Код задачи (`<TASK-ID>`)** извлеки из пути или имени файла (`PROJECT-1234`). Slug для
имён директорий — нижний регистр без дефиса (`PROJECT-1234` → `project1234`).

## ЗОЛОТОЕ ПРАВИЛО: всё проверяется на реальной базе и реальных данных

Команда предполагает наличие **живой TestDB** с реальной конфигурацией и тестовыми данными.
**Ни один факт о конфигурации не принимается на веру из документации или памяти** — каждое
утверждение (имя поля, тип, состав значений, поведение проведения, роль, наличие справочного
значения) подтверждается вызовом MCP к TestDB или исходникам через EDT-MCP.

### Основной инструмент анализа — `1c-mcp-crud`

**`1c-mcp-crud` — primary MCP для анализа конфигурации.** Его функционала достаточно для
подавляющего большинства задач анализа: метаданные, формы, запросы на живых данных,
ссылки между объектами, права доступа, журнал регистрации, выполнение кода. Используй его
**по умолчанию** для всего, что можно прочитать из живой базы.

**Все инструменты `1c-mcp-crud` (используй в первую очередь):**

| Инструмент | Назначение | Когда |
|---|---|---|
| `get_metadata_tree` | Полное дерево метаданных конфигурации — все типы объектов | Начало Фазы 1 (декомпозиция) |
| `list_metadata_objects` | Список объектов одного типа (все документы, все регистры, …) | Начало Фазы 1 |
| `get_metadata` | Метаданные одного объекта (реквизиты, типы, составы) | Фаза 1 |
| `get_metadata_structure` | Расширенная структура (включая ТЧ, формы, команды) | Фаза 1 |
| `get_form_structure` | Структура формы: элементы, их имена, типы, DataPath | Фаза 1 |
| `get_access_rights` | Права доступа на объект, роли, RLS | Фаза 2 |
| `find_references_to_object` | Кто ссылается на этот объект в конфигурации | Фаза 2 |
| `get_link_of_object` / `get_object_by_link` | Работа с навигационными ссылками | Фазы 2 и 4 |
| `search_code` | Поиск по BSL-коду конфигурации | Фаза 2 |
| `get_bsl_syntax_help` | Справка по синтаксису BSL | Фаза 2/3 |
| `validate_query` | Синтаксическая проверка SQL-запроса ДО исполнения | Фазы 2 и 4 |
| `execute_query` | Выполнение SQL на живых данных TestDB | Фазы 1, 2, 4 |
| `execute_code` | Выполнение BSL на сервере 1С (создание тестовых данных, экспериментальная логика) | Фаза 4 (подготовка данных) |
| `get_event_log` | Журнал регистрации — для расследования проблем при прогоне | Debug |
| `post_document` | Программное проведение документа (если нужно для setup) | Фаза 4 (подготовка данных) |
| `mark_for_deletion` | Пометка на удаление (cleanup тестовых данных) | Teardown |
| `create_object` / `update_object` | Создание/обновление объектов (setup) | Фаза 4 (подготовка данных) |

## Декомпозиция: разбей тесты на логические блоки

**Правило:** один логический блок = один объект конфигурации + все связанные с ним формы и бизнес-логика.

**Обязательно пройти ВСЕ типы объектов из чеклиста ниже — но включать в тесты только те,
которые реально необходимы для тестирования задачи.** Чеклист — это фильтр «рассматривал
→ решение», а не требование писать тесты на каждый тип. Нельзя пропускать типы «молча»:
для каждого должен быть явный вердикт «нужен / не нужен / зависимость / pre-check».

### Шаг 1 — Получить полное дерево метаданных

```
mcp__1c-mcp-crud__get_metadata_tree    # полная структура конфигурации
```

Результат даёт все существующие в конфигурации типы объектов — это исходный список для
чеклиста ниже.

### Шаг 2 — Отфильтровать релевантные для задачи

Для каждого типа из дерева ответить на три вопроса:

1. **Упомянут ли этот тип в `ANALYSIS-REPORT.md` / `TEST-PLAN-DETAILED.md`?**
2. **Является ли зависимостью** от объектов из (1)?
   Проверить через `mcp__1c-mcp-crud__find_references_to_object` и
   `mcp__bsl-semantic-search__bsl_impact_analysis`.
3. **Влияет ли на среду теста** (роли, константы, регламентные задания)?

Если на все три — «нет», тип исключается из тестов с явной пометкой «не влияет».
Если хотя бы на один — «да», тип идёт в следующий шаг (в feature-файл, или в зависимость,
или в pre-check).

### Шаг 3 — Перечислить конкретные объекты отобранных типов

```
mcp__1c-mcp-crud__list_metadata_objects    # список всех объектов одного типа
```

Сопоставить со списком точек модификации из `ANALYSIS-REPORT.md` и сценариев
из `TEST-PLAN-DETAILED.md`. Для каждого отобранного объекта — решение по чеклисту
типов ниже (отдельный `.feature`, шаги верификации в соседнем блоке, зависимость, pre-check).

**Скрытые зависимости — не пропускать:** подписки на события, регламентные задания,
общие модули часто «ломают» тесты, хотя прямо в ТЗ не упоминаются. Для каждого объекта
из (1) обязательно проверить `find_references_to_object` на эти типы.

### Шаг 4 — Зафиксировать вердикт по каждому типу в отчёте

В итоговом отчёте команды (и в METADATA шапке feature-файлов) должна быть таблица:

| Тип объекта | Объект(ы) | Вердикт | Где учтён |
|---|---|---|---|
| `Документ.<Имя>` | конкретные имена | ✅ feature | `NN_<doc>.feature` |
| `Подписка.<Имя>` | конкретные имена | ⚠️ зависимость | проверяется косвенно через X |
| `Роль.<Имя>` | конкретные имена | 🔐 pre-check | `get_access_rights` |
| `Справочник.<Имя>` | — | ❌ не влияет | обоснование |

Это гарантирует, что ни один тип не пропущен молча.

### Полный перечень типов объектов конфигурации 1С — чеклист

Пройти по каждому типу и решить: нужен ли отдельный `.feature`, или это зависимость/setup/teardown.

| # | Тип объекта | Как тестируется | Отдельный `.feature`? |
|---|---|---|---|
| 1 | **`Константа.<Имя>`** | Через формы констант / код, читающий/пишущий | Редко (только если задача меняет поведение чтения) |
| 2 | **`Справочник.<Имя>`** (простой) | Форма элемента, форма списка, форма выбора | Если задача меняет форму/логику — да |

**Правило покрытия:**
1. **Все объекты из ANALYSIS-REPORT** → в feature-файлы (отдельные или как шаги/верификация)
2. **Все ПодпискиНаСобытие, связанные с объектами из (1)** → учитываются как скрытые зависимости
   (проверить через `find_references_to_object`)
3. **Все РегламентныеЗадания, связанные с объектами из (1)** → помечаются как `@manual_reglament`
4. **Все Роли, требуемые кнопками из (1)** → в pre-check через `get_access_rights`
5. **Константы, влияющие на поведение (1)** → в пре-check или в setup `execute_code`

### Источники для отбора релевантных объектов

- Матрица автоматизации в `TEST-PLAN-DETAILED.md`
- Точки модификации из `ANALYSIS-REPORT.md` (каждая точка = 1-2 объекта)
- `mcp__1c-mcp-crud__get_metadata_tree` — полная структура конфигурации
- `mcp__1c-mcp-crud__find_references_to_object` — скрытые зависимости (подписки, регламенты, модули)
- `mcp__bsl-semantic-search__bsl_impact_analysis` — обратное влияние при изменении

Для каждого отобранного логического блока — отдельный `.feature`-файл с осмысленным именем
(`NN_<object>_<aspect>.feature`, где `NN` задаёт порядок запуска: smoke → unit → workflow → regression).

## Для КАЖДОГО логического блока — 4 последовательные фазы

Фазы выполняются **строго по порядку**. Переход к следующей фазе возможен только после
выполнения **Definition of Done** предыдущей (см. критерии в конце каждой фазы).

---

### Фаза 1 — Анализ формы объекта (клиент + сервер)

**Цель:** получить точные имена всех элементов формы, типы полей, кастомные кнопки,
условия видимости и обязательности — **подтверждённые на реальной конфигурации**.

**MCP-инструменты:**
- `mcp__1c-mcp-crud__get_metadata` — реквизиты, типы, составы перечислений (ЖИВАЯ база)
- `mcp__1c-mcp-crud__get_form_structure` — структура формы (ЖИВАЯ база)
- `mcp__edt-mcp__get_form_structure` / `get_form_screenshot` — резервный источник (из исходников EDT)
- `mcp__edt-mcp__read_module_source` — модуль формы (Form.Module.bsl): обработчики команд,
  `ОбработкаПроверкиЗаполненияНаСервере`, `ПриОткрытии`, условная видимость, условная обязательность
- `Grep` по `Form.xml`:
  - `<Button name=` — имена всех кнопок
  - `(InputField|LabelField|RadioButtonField|CheckBoxField|SpinBox|ComboBox)` — типы
  - `<Table name=` — таблицы (в том числе DynamicList)
  - `AutoCommandBar` — наличие стандартной панели (для `ФормаПровестиИЗакрыть` и т.п.)

**Чеклист (из скилла `va-bdd-testing`, Stage 1):**
- [ ] Element name для каждой кнопки / поля / таблицы (**НЕ** display title!)
- [ ] Тип каждого поля (InputField/LabelField/RadioButtonField/CheckBoxField/…)
- [ ] Стандартные vs кастомные кнопки проведения
  (пример: `ФормаПровестиИЗакрыть` vs кастомная `Форма<Имя>ИЗакрытьДокумент`)
- [ ] `DataPath` ≠ element name (часто есть расхождение: element `Вес` → DataPath `Объект.ВесБрутто`)
- [ ] Условия видимости элементов (зависимости от флагов, переключателей, ролей)
- [ ] Условная обязательность в `ОбработкаПроверкиЗаполненияНаСервере` (может отличаться от FillChecking!)
- [ ] Модальные диалоги (`ПоказатьВопрос`, `ПоказатьВводЧисла`, кастомные формы)

**Предзапись — проверка тестовых данных на TestDB:**

`execute_code` в блоке `Контекст:` / `Предусловие:`.

**Для каждого SQL-запроса верификации** (Stage 4 скилла):
1. `mcp__1c-mcp-crud__validate_query` — синтаксическая проверка
2. `mcp__1c-mcp-crud__execute_query` — исполнение на TestDB с фиксацией результата

**Определения probes** лежат в `tools/vanessa/probes/*.yaml`. Чтобы добавить новый тип probe (например, `Document:` или `Accumulation:`) для другой задачи — создай YAML-файл с полями `tag`, `parser`, `checks` — Python-код править не нужно. Пример добавления нового probe:

```yaml
# tools/vanessa/probes/document.yaml
tag: Document
description: Document existence by number
enabled: true
parser:
  type: bracketed_list
  pattern: '^(?P<catalog>\S+)\[(?P<items>.+)\]$'
  item_separator: ","
  item_label: "{catalog}[{item}]"
checks:
  - name: exists
    always: true
    query: |
      ВЫБРАТЬ КОЛИЧЕСТВО(*) КАК Cnt ИЗ Документ.{catalog}
      ГДЕ Номер = &Name И НЕ ПометкаУдаления
    params: {Name: "{item}"}
    expect: field_positive
    expect_field: Cnt
    on_fail: "not found"
    on_pass_label: "found"
```
