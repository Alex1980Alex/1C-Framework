# Написание VA BDD тестов для задачи 1С

Напиши автоматизированные тесты Vanessa Automation (VA BDD) по готовому плану тестирования задачи, используя **skill `va-bdd-testing`**.

## Задача от пользователя:
$ARGUMENTS

---

## Инструкция

**Используй skill `va-bdd-testing`** — единый источник методологии написания VA BDD тестов
(откалиброванные step-паттерны, правила анализа форм, обработка диалогов, ARM workflow).

### Входные данные

Из `$ARGUMENTS` извлеки:
1. **Путь к TEST-PLAN-DETAILED.md** (или папке задачи с планом) — описание сценариев, матрица автоматизации, карта объектов конфигурации
2. **Путь к src/** — корень исходников конфигурации (для анализа форм и модулей)
3. Дополнительный контекст (конкретный сценарий, фаза, тег)

**Если передан путь к папке задачи**, найди внутри:
- `*TEST-PLAN*DETAILED*.md` — план тестирования (обязателен)
- `*ANALYSIS-REPORT*.md` — анализ задачи (для понимания точек модификации)
- `*ТЗ*.md` — исходное ТЗ (для бизнес-контекста)

---

## Декомпозиция: разбей тесты на логические блоки

**Правило:** один логический блок = один объект конфигурации + все связанные с ним формы и бизнес-логика.

Примеры логических блоков:
- `Документ.гкс_РегистрацияНаПЛК` — форма документа, ObjectModule (проведение), движения в РС состояний
- `Обработка.гкс_ПриемкаТранспорта` — АРМ-форма с DynamicList, тумблеры, кнопки правой панели
- `РегистрСведений.гкс_ЭлектронныеТабло` — как агрегируются данные из других объектов
- `Документ.гкс_Взвешивание` — модальный ввод веса, выбор оборудования

Для каждого логического блока — отдельный `.feature`-файл с осмысленным именем (`NN_<object>_<aspect>.feature`).

---

## Для КАЖДОГО логического блока — 4 последовательные фазы

### Фаза 1: Анализ формы объекта (клиент + сервер)

**Цель:** получить точные имена всех элементов формы, типы полей, кастомные кнопки, условия видимости.

**MCP-инструменты:**
- `mcp__edt-mcp__get_form_structure` / `get_form_screenshot` — структура управляемой формы
- `mcp__edt-mcp__read_module_source` — модуль формы (Form.Module.bsl): обработчики команд, `ОбработкаПроверкиЗаполненияНаСервере`, `ПриОткрытии`, условная видимость элементов
- `mcp__1c-mcp-crud__get_form_structure` / `get_metadata` — реквизиты и табличные части
- `Grep` по `Form.xml`: `<Button name=`, `(InputField|LabelField|RadioButtonField|CheckBoxField)`, `<Table name=`, `AutoCommandBar`

**Чеклист (из скилла `va-bdd-testing`, Stage 1):**
- [ ] Element name для каждой кнопки/поля/таблицы (НЕ display title!)
- [ ] Тип каждого поля (InputField/LabelField/RadioButtonField/CheckBoxField)
- [ ] Стандартные vs кастомные кнопки проведения (`ФормаПровестиИЗакрыть` vs `ФормаСформироватьНомерПробыИЗакрытьДокумент`)
- [ ] `DataPath` ≠ element name (пример: `Вес` → `Объект.ВесБрутто`)
- [ ] Условия видимости элементов (зависимости от флагов, тумблеров, ролей)
- [ ] Модальные диалоги (`ПоказатьВопрос`, `ПоказатьВводЧисла`, кастомные формы)
- [ ] Обязательные поля в `ОбработкаПроверкиЗаполнения` (могут отличаться от FillChecking!)

### Фаза 2: Анализ объектной модели (максимальная глубина)

**Цель:** понять бизнес-логику до мельчайших деталей — что происходит при проведении, какие движения создаются, какие состояния меняются, какие общие модули вызываются.

**MCP-инструменты:**
- `mcp__edt-mcp__read_module_source` — ObjectModule (`ОбработкаПроведения`), ManagerModule (процедуры получения данных, `ТекстЗапроса*`)
- `mcp__bsl-semantic-search__bsl_search` / `bsl_call_graph` / `bsl_impact_analysis` — кто вызывает эту процедуру, цепочка вызовов
- `mcp__bsl-semantic-search__bsl_object_info` — структура объекта и связи
- `mcp__ast-grep-mcp__ast_grep` — точечный поиск паттернов BSL
- `mcp__1c-mcp-crud__execute_query` — прогнать запросы на TestDB для проверки реальных данных

**Что именно выяснить:**
- [ ] **Цепочка состояний** — какие значения перечислений возможны, через что переходят (state machine)
- [ ] **Движения документа** — какие регистры пишет, в какой последовательности (ObjectModule.ОбработкаПроведения → общий модуль `гкс_ПроведениеДокументов`)
- [ ] **Триггеры** — что запускается при записи набора регистра (ПриЗаписи, ПередЗаписью)
- [ ] **Управляющая логика** — условия "когда кнопка доступна", "когда поле обязательно", "когда появляется диалог"
- [ ] **Взаимодействие с другими объектами** — какие документы создаются из АРМ-кнопок, какие предзаполнены, какие поля требуют ручного ввода
- [ ] **Роли и права** — требуется ли роль для кнопки/команды (пример: `ДоступенДиспетчер` для "На разгрузку")
- [ ] **Асинхронные обработчики** — `ПодключитьОбработчикОжидания` (влияет на паузы в тестах)

### Фаза 3: Дополнительное исследование (VA docs + интернет + github)

**Цель:** найти откалиброванные паттерны для нестандартных сценариев, которых нет в скилле `va-bdd-testing`.

**Источники:**
1. **Официальная документация VA:**
   - `WebFetch("https://pr-mex.github.io/vanessa-automation/dev/")` — главная страница методички
   - Поиск по разделам: шаги работы с формами, таблицами, диалогами, регламентами
2. **Инфостарт (infostart.ru):**
   - `WebSearch("vanessa automation шаг <control-type> infostart")`
   - `WebSearch("VA BDD 1С 8.3.27 <проблема>")`
3. **GitHub VA repo и похожие проекты:**
   - `WebSearch("site:github.com vanessa-automation <control-type> feature")`
   - `WebFetch("https://github.com/pr-mex/vanessa-automation")` — исходники шагов
   - Поиск реальных `.feature`-файлов в публичных 1С-проектах
4. **Локальный кеш документации (если есть):**
   - `mcp__pdf-vector-graph__search_documents` — индексированная документация 1С:8.3.27

**Когда обязательно лезть наружу:**
- Новый тип control, которого нет в секциях 3.1–3.15 скилла `va-bdd-testing`
- Шаг возвращает `"Не найдена процедура для шага"` при корректном (казалось бы) синтаксисе
- Работа с SpreadsheetDocumentField, ChartField, GanttChartField и другими нестандартными элементами
- Регламентные задания, фоновые задания, длительные операции
- Интеграция с внешними системами (RabbitMQ, REST, SOAP) — как VA их мокает/ждёт

**Что положить в калибровочный лог:**
Каждую найденную новую методику — как VERIFY-точку с источником (URL, дата).

### Фаза 4: Написание тестов

**Цель:** собрать `.feature`-файл из откалиброванных паттернов, с явным планом калибровки неопределённых мест.

**Правила (из скилла `va-bdd-testing`):**
- Используй **только откалиброванные паттерны** из секций 3.1–3.15 скилла. НЕ ВЫДУМЫВАЙ синтаксис шагов.
- Каждый неоткалиброванный момент — отмечай VERIFY-комментарием (`V1 pending — ...`) для последующего probe-прогона.
- Wildcard-паттерны для заголовков окон (`"*риемк*"`), element names (не display titles).
- Паузы после асинхронных операций: проведение документа, поиск в справочнике, обновление АРМ.
- Cleanup в начале сценария: `И Я закрыл все окна клиентского приложения`.
- Один сценарий = одна смена состояния / одно бизнес-действие.

**Структура вывода:**
```
features/<task-slug>/
    NN_<logical-block>.feature     # production сценарии
    probe_<aspect>.feature         # probe/калибровка (отдельно от production!)
```

Где `<task-slug>` = код задачи в нижнем регистре без дефисов (`GKSTCPLK-2256` → `gkstcplk2256`).

**В шапке каждого файла:**
```gherkin
# language: ru

# METADATA:
#   Task: GKSTCPLK-2256
#   Logical block: Документ.гкс_РегистрацияНаПЛК
#   Configuration objects: {список}
#   Dependencies: {00_smoke.feature, ...}
#
# CALIBRATION LOG:
#   V1  confirmed   Окно "*егистрация на ПЛК*"
#   V2  pending     Кнопка ВидПеревозки — требует probe
```

## Результат

- Набор `.feature`-файлов в `features/<task-slug>/` — по одному на логический блок
- `probe_*.feature` для неоткалиброванных моментов (если нужны)
- Обновлённая секция "Статус калибровки" в `TEST-PLAN-DETAILED.md` (таблица VERIFY-точек)
- Краткий отчёт в чате: сколько сценариев создано, сколько VERIFY-точек, что требует probe

## ВАЖНО

- **НЕ запускай тесты** — эта команда только ПИШЕТ. Запуск — через `/run-1c-tests` (будет создан отдельно).
- **Сначала анализ, потом код** — Фазы 1-3 обязательны перед Фазой 4. Пропуск анализа = тесты не заработают с первого раза.
- **Каждый логический блок — отдельный файл.** Не смешивай сценарии разных объектов конфигурации.
- **Используй только откалиброванные паттерны** из скилла `va-bdd-testing`. Новые паттерны из Фазы 3 — сначала в probe, потом в production.
- **Для каждого SQL-запроса проверки** (Stage 4 скилла) — запусти `mcp__1c-mcp-crud__validate_query` до вставки в шаги.
- **НЕ модифицируй** `TEST-PLAN-DETAILED.md` кроме секции статусов калибровки — остальной план задаёт требования.
- Веди калибровочный лог в комментариях feature-файла (V1, V2, ... с датой и статусом).
