## ЗОЛОТОЕ ПРАВИЛО: тестируем серверный код, а не UI

YAxUnit — это **unit-тесты серверной логики** (процедуры и функции общих модулей, модулей объектов,
модулей менеджера). **Ни один факт о тестируемой функции не принимается на веру** — каждый вызов,
параметр и возвращаемое значение подтверждается чтением исходника через `mcp__edt-mcp__read_method_source`
или `mcp__edt-mcp__read_module_source`. **Не пиши тест до того, как прочитал тестируемый метод целиком.**

### Основные инструменты анализа

| Инструмент | Назначение | Когда |
|---|---|---|
| `mcp__edt-mcp__list_projects` | Получить имя проекта EDT | Начало (обязательно) |
| `mcp__edt-mcp__list_modules` | Найти модули объекта конфигурации | Фаза 1 |
| `mcp__edt-mcp__get_module_structure` | Список методов модуля (имена, строки) | Фаза 1 |
| `mcp__edt-mcp__read_method_source` | Прочитать тело тестируемого метода | Фаза 1 |
| `mcp__edt-mcp__read_module_source` | Прочитать весь модуль (полный контекст) | Фаза 1 |
| `mcp__edt-mcp__get_metadata_details` | Реквизиты, типы, составы (для тест-данных) | Фаза 1 |
| `mcp__edt-mcp__write_module_source` | Записать тест-модуль в расширение UnitTests | Фаза 3 |
| `mcp__edt-mcp__get_project_errors` | Проверить ошибки EDT ПОСЛЕ записи | Фаза 3 |
| `mcp__1c-mcp-crud__execute_query` | Тестовые данные на живой базе | Фаза 1 / 4 |
| `mcp__1c-mcp-crud__execute_code` | Подготовка тест-данных (если нужно) | Фаза 4 |
| `mcp__bsl-platform-context__getMember` | API платформы 1С:8.3.27 (сигнатуры) | Фаза 2 |

## Декомпозиция: что тестировать

**Правило:** один тест-модуль = один общий модуль или один тип объекта конфигурации (модуль объекта /
модуль менеджера). Не смешивай логику разных модулей.

### Шаг 1 — Собрать точки модификации из ANALYSIS-REPORT

Из §4 ANALYSIS-REPORT выпиши все `[ADDED]`/`[MODIFIED]` точки (файл / метод / было→стало).
Именно эти методы подлежат unit-покрытию.

### Шаг 2 — Прочитать каждый тестируемый метод

Для каждой точки модификации:
```
mcp__edt-mcp__read_method_source(project, modulePath, methodName)
```
Зафиксировать: сигнатуру (параметры + возвращаемое значение), внутренние ветки (Если/ИначеЕсли),
возможные исключения, вызовы других методов.

### Шаг 3 — Определить кейсы (матрица покрытия)

Для каждого метода — таблица кейсов:

| Кейс | Тип | Входные данные | Ожидаемый результат |
|---|---|---|---|
| Штатный (happy path) | positive | нормальные значения | корректный выход |
| Граничный | boundary | 0, пустая строка, минимум/максимум | поведение на границе |
| Негативный | negative | некорректный тип / Неопределено / несуществующая ссылка | `.ВыбрасываетИсключение()` / Попытка / флаг |

**Минимум на метод:** 1 positive + 1 граничный или 1 negative.

### Шаг 4 — Зафиксировать вердикт (обязательно)

Для каждого метода из §4 ANALYSIS-REPORT:

| Метод / точка | Тест-модуль | Кейсы | Статус |
|---|---|---|---|
| `МодульМенеджера.ПолучитьДанные` | `гкс_ИмяОбъектаТест` | 3 (happy/boundary/negative) | будет создан |
| `МодульОбъекта.ПередЗаписью` | — | — | не тестируется (событие; см. BDD) |

## Для каждого тест-модуля — 6 последовательных фаз

### Фаза 1 — Анализ тестируемого кода

**Цель:** полностью понять тестируемый метод: входы, ветки, выходы, зависимости.

**Чеклист:**
- [ ] Прочитан полный текст тестируемого метода (`read_method_source`)
- [ ] Выписаны все параметры и типы
- [ ] Перечислены все Если/ИначеЕсли ветки (они = тест-кейсы)
- [ ] Идентифицированы внешние зависимости (вызовы других модулей → кандидаты для Мокито)
- [ ] Прочитаны смежные методы, если тестируемый их вызывает напрямую

**Definition of Done:** таблица «параметр → тип → значение в кейсах» составлена, все ветки
кода покрыты хотя бы одним кейсом в матрице.

---

### Фаза 2 — Дизайн тест-кейсов

**Цель:** спроектировать конкретные входные данные и ожидаемые результаты для каждого кейса.

**Источники данных:**
- `mcp__1c-mcp-crud__execute_query` — реальные UUID / коды / наименования из TestDB
- `mcp__edt-mcp__get_metadata_details` — допустимые значения типов, перечисления
- `mcp__bsl-platform-context__getMember` — сигнатуры платформенных вызовов внутри метода

**Правила:**
- **НЕ выдумывай** тест-данные. UUID объектов — из `execute_query`; перечисления — из `get_metadata_details`.
- Для кейсов «пустая ссылка» используй `Новый(ТипОбъекта).СсылкаНаПустойЭлемент()` (или `ПустаяСсылка()`).
- Мокирование зависимостей — когда внешний вызов имеет побочный эффект (запись в БД, HTTP) или
  затрудняет изоляцию теста — через `Мокито.Обучение(Модуль).Когда(...).Вернуть(...)` + `Мокито.Прогон()`
  (обвязка `&Вместо`+`МокитоПерехват` в расширении обязательна). DI параметром — предпочтительнее мока.

**Definition of Done:** для каждого кейса в матрице заполнены все три столбца: входные данные
(конкретные значения) / ожидаемый результат / способ проверки (ЮТест.ОжидаетЧто / `.ВыбрасываетИсключение()`).

---

### Фаза 3 — Написание тест-модуля

**Цель:** создать BSL-модуль в расширении `src/bsl/exts/UnitTests/` и задеплоить его.

#### Структура тест-модуля (обязательная)

```bsl
// Общий модуль: гкс_<ИмяОбъекта>Тест
// Свойства: Сервер=Да, Глобальный=Нет, Клиент=Нет, ВнешнееСоединение=Нет

#Область ОписаниеТестов

// Обязательная экспортная процедура — точка входа YAxUnit
Процедура ИсполняемыеСценарии() Экспорт
    ЮТТесты.ДобавитьСерверныйТест("ТестДолжен_<ИмяМетода>_ПриНормальныхДанных_ВернутьКорректноЗначение",
        "happy path: корректные данные");   // 2-й арг — человекочитаемое описание
    ЮТТесты.ДобавитьСерверныйТест("ТестДолжен_<ИмяМетода>_ПриПустойСсылке_ВернутьНеопределено",
        "граничный: пустая ссылка");
    // ... остальные тесты
КонецПроцедуры

#КонецОбласти

#Область Тесты

Процедура ТестДолжен_<ИмяМетода>_ПриНормальныхДанных_ВернутьКорректноЗначение() Экспорт
    // Arrange
    ВходнойПараметр = <конкретное значение>;

    // Act
    Результат = <ИмяМодуля>.<ИмяМетода>(ВходнойПараметр);

    // Assert
    ЮТест.ОжидаетЧто(Результат).Равно(<ОжидаемоеЗначение>);
КонецПроцедуры

Процедура ТестДолжен_<ИмяМетода>_ПриПустойСсылке_ВернутьНеопределено() Экспорт
    // Arrange
    ПустаяСсылка = Справочники.<ИмяСправочника>.ПустаяСсылка();

    // Act
    Результат = <ИмяМодуля>.<ИмяМетода>(ПустаяСсылка);

    // Assert
    ЮТест.ОжидаетЧто(Результат).Равно(Неопределено);
КонецПроцедуры

#КонецОбласти
```

#### Соглашения именования

| Что | Соглашение | Пример |
|---|---|---|
| Имя тест-модуля | `гкс_<ИмяОбъекта>Тест` | `гкс_ДиректорияТранспортаТест` |
| Имя тест-процедуры | `ТестДолжен_<Метод>_При<Условие>_<Результат>` | `ТестДолжен_ПолучитьВодителя_ПриПустойСсылке_ВернутьНеопределено` |
| Область кода | `#Область ОписаниеТестов` + `#Область Тесты` | обязательны обе |

#### Матчеры ЮТест (основные)

```bsl
ЮТест.ОжидаетЧто(Значение).Равно(Ожидаемое);
ЮТест.ОжидаетЧто(Значение).НеРавно(НеОжидаемое);
ЮТест.ОжидаетЧто(Значение).Заполнено();
ЮТест.ОжидаетЧто(Значение).НеЗаполнено();
ЮТест.ОжидаетЧто(Значение).ИмеетТип("Булево");
ЮТест.ОжидаетЧто(Значение).ИмеетТип("СправочникСсылка.<Имя>");
ЮТест.ОжидаетЧто(Коллекция).ИмеетДлину(N);
ЮТест.ОжидаетЧто(Коллекция).Содержит(Элемент);
// Проверка исключения (метода ОжидаетВыброс НЕ существует):
ЮТест.ОжидаетЧто(Объект).Метод("ИмяМетода").ВыбрасываетИсключение();
// или: прямой вызов в Попытке → ЮТест.ОжидаетЧто(Поймано, "ожидалось исключение").ЭтоИстина();
```

#### API Мокито (для изоляции зависимостей)

```bsl
// Мокирование метода общего модуля (обвязка &Вместо+МокитоПерехват в расширении ОБЯЗАТЕЛЬНА)
Мокито.Обучение(ОбщийМодуль)
    .Когда("МетодМодуля", Мокито.МассивПараметров(<Арг>))   // без параметров = любой вызов
    .Вернуть(<ЗначениеПодмены>);
Мокито.Прогон();   // ОБЯЗАТЕЛЬНО перед вызовом тестируемого кода
// Проверка: Мокито.Проверить(ОбщийМодуль).КоличествоВызовов("МетодМодуля").Равно(1);
```

#### Деплой тест-модуля

После записи BSL через `mcp__edt-mcp__write_module_source`:

1. **Проверка ошибок EDT:**
   ```
   mcp__edt-mcp__get_project_errors(projectName)
   → errors должно быть 0 (или только warning)
   ```

2. **Деплой расширения UnitTests:**
   ```bash
   # Загрузка расширения из исходников в конфигуратор:
   1cv8.exe DESIGNER /IBConnectionString "..." \
     /LoadConfigFromFiles "src/bsl/exts/UnitTests" -Extension UnitTests
   # Обновление расширения в БД:
   1cv8.exe DESIGNER /IBConnectionString "..." \
     /UpdateDBCfg -Extension UnitTests
   ```
   Строку подключения (`/IBConnectionString`) взять из `.env` → переменная `ONEC_TEST_CONN`
   (дефолт `Srvr="DESKTOP-TNU600C";Ref="ИБTransportManagementDevelop"`).

   ⚠ Деплой модифицирует live-инфобазу. Если в базе есть другие активные сессии —
   спросить пользователя перед выполнением.

3. **Запуск тестов через MCP (smoke-check):**
   ```
   mcp__mcp-onec-test-runner__run_module_tests(moduleName="гкс_<ИмяОбъекта>Тест")
   → ожидаем passed=N, failed=0, errors=0
   ```
   Полный прогон всего расширения — через `/run-1c-unit-tests`.

**Definition of Done (Фаза 3):**
- [ ] Тест-модуль создан в `src/bsl/exts/UnitTests/CommonModules/<Имя>Тест/`
  (BSL-файл + XML-метаданные модуля)
- [ ] `get_project_errors` = 0
- [ ] Расширение задеплоено (`LoadConfigFromFiles` + `UpdateDBCfg`)
- [ ] Smoke через `run_module_tests` — все тесты прошли (или падение диагностировано)

### Фаза 4 — Подписка на дискавери (подсистема `Модульные.<Content>`)

**Цель:** добавить новый тест-модуль в список тестов расширения, чтобы `run_all_tests`
его нашёл.

YAxUnit находит тест-модули ПО СОДЕРЖИМОМУ подсистемы `ЮТТ_ЮТПодключаемыеМодули → Модульные`
(сверено с движком `ЮТПодключаемыеМодулиСлужебный`). **Регистрация ОБЯЗАТЕЛЬНА** — добавь модуль в
`<Content>` подсистемы `Модульные` (через EDT: состав подсистемы, либо в XML):
```xml
<xr:Item xsi:type="xr:MDObjectRef">CommonModule.гкс_<ИмяОбъекта>Тест</xr:Item>
```
Без регистрации `run_all_tests` модуль НЕ увидит (ошибки не будет — молча пусто). Имя модуля
свободное (`ЮТТ` — префикс ПОДСИСТЕМЫ, не модулей); метода `ЮТТесты.ДобавитьМодуль` не существует.

---

### Фаза 5 — Прогон и верификация

**Цель:** убедиться что тесты реально работают.

```
mcp__mcp-onec-test-runner__run_module_tests(moduleName="гкс_<ИмяОбъекта>Тест")
```

Разбор падений:
- `passed=0` при 0 ошибок EDT → тест-модуль не подхвачен дискавери (проверь `ИсполняемыеСценарии`)
- Ошибка `Метод не найден` → опечатка в имени тестируемого метода или он не экспортный
- `ЮТест.ОжидаетЧто` не срабатывает → проверь, что результат не `Неопределено` (добавь
  промежуточный `ЮТест.ОжидаетЧто(Результат).НеРавно(Неопределено)` перед основным утверждением)

---

### Фаза 6 — Интеграция с пайплайном задачи

**Цель:** обновить state пайплайна и зафиксировать coverage.

1. Обновить `.run-state.json` в папке задачи (тот же файл, что у BDD-трека):
   ```json
   {
     "task": "<TASK-ID>",
     "chain": [
       { "section": "unit_<ИмяМодуля>", "status": "passed", "type": "yaxunit" }
     ]
   }
   ```
2. Добавить запись в IMPLEMENTATION-PROGRESS.md (раздел «Результаты тестирования»):
   ```
   YAxUnit unit-тесты: гкс_<ИмяОбъекта>Тест — N passed, 0 failed
   Покрыто методов: <список>
   ```

## Важные правила

- **YAxUnit = серверный unit-тест**, НЕ UI. Если требуется тест с открытием формы, диалогов
  или интерактивных операций — это BDD-трек (`/write-1c-tests` + `va-bdd-testing`).
- **Тест-модуль — только в расширении `UnitTests`**, не в основной конфигурации и не в
  других расширениях. Путь: `src/bsl/exts/UnitTests/CommonModules/<Имя>Тест/`.
- **Деплой до прогона.** `run_module_tests` работает против live-инфобазы. Без `UpdateDBCfg`
  расширения — тест-код невидим для платформы.
- **`get_project_errors` = 0 обязателен** после каждой записи тест-модуля. Красные ошибки EDT
  = тест не будет исполнен (платформа не скомпилирует расширение).
- **Не выдумывай API YAxUnit.** Источник истины: `src/bsl/exts/YAXUNIT/CommonModules/ЮТест.xml`,
  `ЮТУтверждения.xml`, `ЮТТесты.xml`, `Мокито.xml` — читай через `read_module_source`.
- **НЕ запускай полный прогон** — эта команда только ПИШЕТ и делает smoke одного модуля.
  Полный прогон — через `/run-1c-unit-tests`.

## Результат

- Набор BSL тест-модулей в `src/bsl/exts/UnitTests/CommonModules/` — по одному на логический блок
- Обновлённый `.run-state.json` в папке задачи (секция `unit_*`)
- Запись в IMPLEMENTATION-PROGRESS.md (раздел «Результаты тестирования»)
- Краткий отчёт в чате:
  - сколько методов покрыто
  - сколько тест-кейсов создано (positive / boundary / negative)
  - результат smoke-прогона (`run_module_tests`)
  - что не покрыто и почему (события формы → BDD, интерактивные операции → BDD)
