# ADR-035: Обязательное использование высоко-эффективных инструментов 1С-пайплайна — многоуровневый условный мандат

**Дата:** 2026-06-22
**Статус:** accepted (Фаза 1 — advisory — реализована 2026-06-22; Фаза 2 hard-промоут отложена до замера follow_rate/FP)
**Исследование:** контекст — [гл. 43.7 §«Необязательные инструменты с высоким выигрышем эффективности»](../../../docs/framework%20documentation/43_ПАЙПЛАЙН_1С/43.7_АНАЛИЗ_ВСЕЙ_КОНФИГУРАЦИИ.md) (без отдельного cache-профиля; основание — реальные прогоны 2026-06-21 + опыт)
**Связь:** расширяет обязательный минимум [43.4](../../../docs/framework%20documentation/43_ПАЙПЛАЙН_1С/43.4_СПРАВОЧНИК_ИНСТРУМЕНТОВ.md); enforcement-цель — [`onec-task-completion-stop.py`](../../../.claude/hooks/onec-task-completion-stop.py) (единый 1С task-completion gate); зеркалит лестницу advisory→hard из [ADR-018](018-mandatory-auto-pipeline-protocol.md) и tdd-guard ([ADR-015](015-testing-adopt-tddguard-optin-eval-playwright.md))

## Контекст

Гл. 43.7 разграничила **обязательный минимум** (43.4: память recall→capture · скилл-методика · внешний анализ · циклы `validate_query`→`execute_query`→`get_project_errors`; принуждается хуками) и **каталог применимости** (toolbox по необходимости). Анализ эффективности (43.7) выделил инструменты «не обязательны, но дают большой выигрыш при near-нулевой стоимости». Запрос (2026-06-22): **формализовать обязательное использование** этих инструментов отдельным ADR.

**Ключевое наблюдение:** часть «высокоэффективных» инструментов применима **не ко всем** задачам:
- `bsl_impact_analysis` ценен **перед правкой экспортного метода** (T2/рефактор), а не на «новом объекте с нуля»;
- `1c-debug-hmr` (live BP-trace) ценен на **runtime-логике** (≥3 ветвлений / bugfix-verify), требует живой инфобазы; память [[feedback-live-bp-trace-mandatory]] уже трактует его как де-факто обязательный;
- `get_form_screenshot` — только задачи **с формами**; SonarQube — **release-level**, не per-task; `bsl_dead_code` — аудит.
Поэтому **blanket «все всегда обязательны»** дал бы ложные блоки на неприменимых задачах (форменный тул на задаче без форм; сервис-зависимый тул при выключенном сервисе) и противоречил бы 43.4 «не все инструменты нужны в каждой задаче». [own, exp]

## Решение

Ввести **многоуровневый условный мандат** (а не плоский список «обязательно»). 4 уровня по оси _выигрыш × применимость × детектируемость гейтом_; принуждение — **поэтапное** (advisory → hard), graceful (block-once, opt-out, fail-safe — как `onec-task-completion-stop`/ADR-018). [own]

> **Определяющий принцип — контекст задачи.** Обязательность каждого инструмента **обусловлена контекстом**, а не глобальна: тип задачи (новый объект «с нуля» / T2-bugfix / `[REFACTOR]` / доработка / «с формами»), этап пайплайна, фактическая применимость и доступность сервиса. **Безусловного «всегда обязательно» нет ни на одном уровне.** Порядок гейта: сперва **определить контекст** (тип/этап задачи через `classify_1c_task`/`pipeline_1c_bridge`), затем требовать **только применимое** к этому контексту; при неопределённости контекста — **advisory, не блок** (инвариант безопасности: сомнение деградирует в подсказку, а не в ложный блок — зеркалит «сомнение → спросить» из [43.3](../../../docs/framework%20documentation/43_ПАЙПЛАЙН_1С/43.3_МАРШРУТИЗАЦИЯ_ХУКИ_ИНСТРУМЕНТИРОВАНИЕ.md)). [own]

| Уровень | Инструменты | Условие обязательности | Принуждение |
|---|---|---|---|
| **T1 — hard по типу задачи** | `bsl_impact_analysis` · `1c-debug-hmr` (live BP-trace) | impact — **перед правкой существующего экспортного метода** (T2 bugfix / `[REFACTOR]` / доработка); BP-trace — **runtime-логика ≥3 ветвлений / bugfix-verify** | gate-check (tool_use в транскрипте для edit-bearing задачи), block-once **после окна валидации** |
| **T2 — at-stage, дёшево+универсально** | `bsl_search` / `bsl_similar` | **на Планировании** — поиск эталона до дизайна (дополняет memory-recall) | gate-check (был ли поиск кода), block-once |
| **T3 — conditional, applies-when** | `bsl_call_graph` / `find_callers` (перед рефактором/удалением) · `get_form_screenshot` (задачи с формами) · `bsl_analyze_method` (изменённые методы) | по применимости к задаче | **advisory** (лог в `TOOL-USAGE-REPORT`, не блок) |
| **T4 — recommended / passive** | prework-воркеры · `pdf-vector-graph` RAG · `llm_complete` · `bsl_dead_code` · `tool_usage_report.py` · `bsl_lint`/`ast-grep` · SonarQube (выборочно `гкс_`, см. [ADR-033](033-sonar-remediation-stage.md)) | — | без гейта (surfacing/логирование/эффективность) |

**Принцип мандата:** «**использовать ИЛИ явно обосновать пропуск**» (не deadlock). Детект — по фактическим `tool_use` (не raw-text), как в существующем gate. Сервис-зависимые тулы (`1c-debug-hmr` — инфобаза; `bsl_impact_analysis` — индекс) при недоступности сервиса **деградируют в advisory** (нет блока), а не валят задачу. [own]

**Поэтапное принуждение (лестница, как ADR-018 / tdd-guard):**
1. **Фаза 1 (этот ADR, proposed):** документировать уровни в 43.7/43.4; добавить T1-T2 в чеклист `onec-task-completion-stop` как **info/advisory** (наряду с recall/capture/research); собрать follow_rate/FP за окно.
2. **Фаза 2 (после валидации):** промоут T1-T2 в **hard block-once** для edit-bearing 1С-задач; opt-out env (напр. `ONEC_TOOLGATE_DISABLE=1`). Условная детекция типа задачи (T2/рефактор/«с формами») — через `pipeline_1c_bridge` классификатор (best-effort; при неуверенности — advisory, не блок).

**Маппинг на этапы:** T2 (поиск эталона) — **1 Планирование**; T1 impact — **1-2** (перед дизайном правки) + **3** (перед записью); T1 BP-trace — **2** (Runtime Trace гипотез) + **3-4** (verify); T3 — по применимости; T4 — сквозь/по релизам.

## Последствия

### Положительные
- Меньше регрессий: impact-карта **до** правки экспортного метода («починил A — сломал B» отсекается на входе). [own]
- Runtime-логика проверяется на реальных данных (BP-trace), а не догадками — меньше циклов «угадал→переделал». [exp]
- Реюз эталонных реализаций (search) на старте → меньше «изобретений велосипеда». [own]
- Согласовано с существующей философией гейтов (graceful, block-once, opt-out) — без нового класса хуков. [own]
- Память [[feedback-live-bp-trace-mandatory]] получает формальную проводку (де-факто → де-юре с условием). [exp]

### Отрицательные / риски
- **Ложные блоки**, если сделать hard слишком рано или без условия применимости → строго: advisory-окно ПЕРЕД hard; сервис-down → деградация в advisory. [own]
- **Детекция типа задачи** (T2/рефактор/«с формами») эвристична — Фаза 2 риск FP; при неуверенности классификатора — advisory, не блок. [own]
- Доп. время на задачу (impact/BP-trace) — оправдано на edit-bearing/bugfix, избыточно на тривиальном новом коде → T1 только по типу задачи, не глобально. [own]
- Сервис-зависимость (`1c-debug-hmr` инфобаза, индекс для impact) — gate не должен требовать недоступное. [exp]

## Альтернативы (отклонены)
- **Blanket «все 13 инструментов hard-обязательны всегда»** — отклонён: форменные/release/сервис-зависимые тулы дают ложные блоки на неприменимых задачах; фрикция > выигрыша; противоречит 43.4 «бери только необходимое». [own]
- **Оставить всё advisory (только док 43.7, без проводки)** — отклонён частично: T1-T2 дают достаточный выигрыш по предотвращению регрессий, чтобы оправдать enforcement для edit-bearing задач. [own]
- **Hard-блок T1-T2 сразу (без advisory-окна)** — отклонён ПОКА: сначала измерить точность детекции/FP (лестница ADR-018/tdd-guard), потом промоут. [own]
- **Отдельный новый Stop-хук** — отклонён: переиспользуем `onec-task-completion-stop` (единый 1С gate) — без конкурирующих хуков (натяжение T3 из ADR-034). [own]
