# ADR-049: Debug-worker `mcp_ОтладкаВыполненияКода` — в расширении MCP_Сервер, не в основной конфигурации

**Дата:** 2026-07-08
**Статус:** accepted
**Исследование:** [`cache/autonomous-1c-debugging-2026.md`](../cache/autonomous-1c-debugging-2026.md), roadmap [`260708_ROADMAP_AUTONOMOUS_1C_DEBUGGING.md`](../../../../docs/roadmap/260708_ROADMAP_AUTONOMOUS_1C_DEBUGGING.md) (B1)

## Контекст

Roadmap 260708 B1 (persistent JOB-контекст) требует долгоживущий BSL debug-worker `ВыполнитьКодСУдержанием` — фоновое задание исполняет код и **держит контекст** (ожидание сигнала освобождения), пока debug-агент читает переменные/шагает. Это лечит корень P-1: rphost эфемерного JOB живёт **<100ms** (spawn→строка→quit до attach+BP), поэтому интерактивная отладка фоновых заданий сейчас невозможна.

Открытый вопрос §5.1: где размещать модуль — в основной конфигурации `ИБTransportManagementDevelop`/`SVETLY`/`MFM`, или только dev-ИБ? Прецедент: существующий `гкс_ОтладкаВыполненияКода` (Шаблон 6) был добавлен в **основную** конфигурацию (`Configuration.mdo`) — инвазивно к типовой.

## Решение

Модуль размещается в **расширении `MCP_Сервер`** (`external/1c_mcp/`, сабмодуль, префикс объектов `mcp_`) под именем **`mcp_ОтладкаВыполненияКода`** [own + exp].

Обоснование:
- **Не трогает типовую конфигурацию** [own] — отладочный инструментарий не должен жить в продуктовой конфе (риск случайного попадания в релиз, конфликты обновления типовой).
- **Существующий deploy-пайплайн** [exp, [[reference-1c-mcp-server-extension-deploy]]] — расширение уже деплоится через `DumpConfigToFiles → правка дампа → LoadConfigFromFiles + UpdateDBCfg -Extension "MCP_Сервер"`. Новый модуль — плюс один объект в дамп.
- **Естественная связка с триггером** [own] — B1-воркер вызывается из `1c-mcp-crud:execute_code`, который питается ЭТИМ ЖЕ расширением (`mcp_ИнструментЗапросыИКод`). Debug-worker и его триггер — в одном артефакте.
- **Скоуп деплоя = где установлено расширение** [own] — не нужно отдельно решать «в какие ИБ»: расширение уже присутствует в рабочих ИБ (питает 1c-mcp-crud). Deploy B1 = обновить расширение там же.

**Обязательный контракт деплоя (dump-live-first)** [exp, [[reference-1c-mcp-server-extension-deploy]]]: **НЕЛЬЗЯ** `LoadConfigFromFiles` устаревший репо-src `external/1c_mcp/src/1c_ext` поверх живого — репо-src отстаёт от живого расширения (однажды затёр `execute_code` → регрессия 2026-06-25). Только: (1) backup `.cfe`, (2) dump живого в файлы, (3) добавить `mcp_ОтладкаВыполненияКода` в ЭТОТ дамп, (4) LoadConfigFromFiles + UpdateDBCfg раздельно, (5) verify через `execute_code` рантайм, (6) ре-синхронизировать репо-src + commit в сабмодуле.

## Последствия

### Положительные
- Типовая конфигурация чистая; отладочный код изолирован в расширении.
- Один deploy-механизм; доступность = presence расширения (нет матрицы «ИБ × модуль»).
- Debug-worker рядом со своим триггером (`execute_code`).

### Отрицательные / риски
- **Расщепление debug-хелперов**: `гкс_ОтладкаВыполненияКода` (Шаблон 6) остаётся в основной конфе → два дома. **Митигация:** рекомендация консолидировать `гкс_ОтладкаВыполненияКода` → `mcp_` в расширении отдельной задачей (не блокирует B1).
- **Ловушка stale repo-src** — обязателен dump-live-first (см. контракт выше); нарушение = регрессия инструментов расширения.
- Права: расширение исполняет привилегированный код (`УстановитьПривилегированныйРежим`) — приемлемо для dev-инструмента, но не публиковать HTTP-триггер без auth.

## Альтернативы

1. **В основной конфигурации (как `гкс_ОтладкаВыполненияКода`)** — отклонено: инвазивно к типовой, риск релиза, конфликты обновления.
2. **Только dev-ИБ, standalone обработка** — отклонено: не переносится на SVETLY/MFM, нет единого deploy.
3. **Внешняя обработка (`.epf`)** — отклонено: фоновое задание не запускается из внешней обработки штатно; расширение даёт серверный общий модуль напрямую.
