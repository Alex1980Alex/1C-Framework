# ADR-051: Тяжёлый путь tool-observability (нативный OTel → Langfuse self-host + LLM-judge) — отложить за триггеры

- **Статус:** accepted
- **Дата:** 2026-07-18
- **Контекст-источник:** roadmap [260718 N-P3](../../../../docs/roadmap/260718_ROADMAP_TOOL_OBSERVABILITY_NEXT.md) (продолжение [260713](../../../../docs/roadmap/260713_ROADMAP_TOOL_OBSERVABILITY_AUDIT.md)); кеш [`tool-call-observability-effectiveness-2026.md`](../cache/tool-call-observability-effectiveness-2026.md), [`langfuse-llm-observability-2026`](../cache/).

## Контекст

Ядро контура «лог → анализ → вердикт → действие» над `data/hook-invocations.jsonl`
закрыто (260713 P0–P2 + 260718 N-P0..N-P2): корректность записи вылечена, error-детект
built-in честен (NB1 — непарный Pre), окно 14д реально покрывается, p95-FP убран,
probe + sink-регрессия сведены в вердикты, verdicts.jsonl получил читателя, per-call
лог у 5/10 MCP-серверов, разрез делегирования per-agent. Индустрия-консенсус (OTel
GenAI semconv, deepeval/MCP-Bench, Langfuse) описывает ДВА пути наблюдаемости:

- **лёгкий:** структурный JSONL + локальный SQL (DuckDB) с полями по `gen_ai.*` — это
  ровно наш путь (`audit_query.py` + `analyze_tool_health.py`, поля-алиасы P2.1);
- **тяжёлый:** нативная телеметрия → OTLP-коллектор → Langfuse/SigNoz self-host + LLM-judge
  (Argument Correctness / Task Completion) на сэмпле вызовов.

Вопрос ADR: поднимать ли тяжёлый путь сейчас.

## Решение

**Отложить тяжёлый путь; зафиксировать триггеры активации. Не поднимать инфраструктуру
(Docker Langfuse / OTLP-коллектор) в рамках 260718.**

Обоснования:

1. **Лёгкий путь закрывает текущую потребность.** После N-P0.1 success-метки честные
   (раньше LLM-judge поверх врущих меток был бы бессмыслен). Вердикты, эскалация,
   тренд, probe и per-agent разрез уже работают на JSONL+stdlib — без внешних сервисов.
2. **Тяжёлый путь — операционное решение, не код-правка.** Self-host Langfuse (Docker,
   постоянный процесс, БД, ретеншн) и OTLP-коллектор несут инфра-footprint и требуют
   оценки нагрузки/безопасности — это нельзя вкатывать «мимоходом» в код-сессии.
3. **Есть более дешёвый второй источник латентности, чем полный OTel.** Обнаружено
   (N-P2.3): платформа кладёт реальную длительность тула в `PostToolUse`-payload полем
   `duration_ms`. Захват этого поля даёт точную латентность без пэйринга и без OTLP —
   это следует сделать РАНЬШЕ тяжёлого пути (дешёвый выигрыш, отдельный small-change).

### Триггеры активации (пересмотреть ADR при выполнении ЛЮБОГО)

- **P3.1 (OTel → Langfuse)** — когда понадобится (а) кросс-сессионная корреляция трейсов
  за пределами локального JSONL, ИЛИ (б) независимый второй источник built-in-покрытия
  (нативные спаны `claude_code.tool` / `claude_code.mcp_server_connection` перекрывают
  наши слепые зоны без хуков), ИЛИ (в) внешнее требование к дашбордам/алертингу.
- **P3.2 (LLM-judge)** — только ПОСЛЕ N-P0.1 (выполнено) И когда rule-метрики P2 покажут
  потребность в семантической оценке (Argument Correctness / Task Completion), которую
  детерминированные правила не ловят. Реализация — на сэмпле 5–10% через `llm_complete`
  (z.ai, token-economy), не на потоке.

### Дешёвый предшественник (одобрен к реализации вне тяжёлого пути)

- **`duration_ms`-захват**: `tool-invocation-logger` / `mcp-invocation-logger` читают
  `PostToolUse.duration_ms` и кладут аддитивным полем; `pair_durations` предпочитает его
  паре, когда присутствует. Small-change, без инфраструктуры.

## Последствия

- Тяжёлый путь не реализуется в 260718; контур остаётся stdlib/JSONL + DuckDB-интерактив.
- Зафиксированы явные триггеры — возврат к вопросу не по «а не пора ли», а по событию.
- `duration_ms`-захват вынесен в backlog как next small-change (дешевле полного OTel).
- Реверс/пересмотр: при срабатывании триггера — новый ADR (OTel-топология, ретеншн,
  безопасность) со ссылкой на этот.
