# code-verify — универсальная верификация кода

## Обзор

Верификация кода после ЛЮБОГО изменения: баг фикс, рефакторинг, новая фича, Learning Loop. 3 уровня проверки (структурная → ревьюер-субагент → решение), 4 режима (knowledge-compliance, behavior-preservation, bug-fix-validation, quality-review). При FAIL — Ralph Wiggum Loop (макс 3 итерации).

---

## Быстрый справочник

| Режим | Когда | Что проверяет | Вход |
|-------|-------|---------------|------|
| `knowledge-compliance` | Learning Loop (FETCH→EXECUTE) | Код соответствует knowledge_block | knowledge_block + код + маркеры |
| `behavior-preservation` | Рефакторинг | Поведение не изменилось | оригинальный код + рефакторинг |
| `bug-fix-validation` | Баг фикс | Баг исправлен + нет регрессии | описание бага + фикс + тесты |
| `quality-review` | Новый код / общий | Безопасность, паттерны, производительность | код для ревью |

---

## Когда использовать

**ПОСЛЕ ЛЮБОГО ИЗМЕНЕНИЯ КОДА.** Единственное исключение: информационный вопрос без code output ("что такое RAG?").

| Ситуация | Режим |
|----------|-------|
| Learning Loop (FETCH → EXECUTE → **VERIFY**) | `knowledge-compliance` |
| Рефакторинг | `behavior-preservation` |
| Исправление бага | `bug-fix-validation` |
| Новый код / общий ревью | `quality-review` |
| Несколько ситуаций | Комбинировать: `bug-fix-validation` + `quality-review` |

---

## 3 уровня проверки

Уровни универсальны для всех 4 режимов. Различаются только промпты ревьюера.

### Уровень 1: Структурная проверка (оркестратор, бесплатно)

Оркестратор выполняет grep/read по результату — автоматическая проверка маркеров.

```
Для КАЖДОГО режима:
  1. Маркерные паттерны ПРИСУТСТВУЮТ?
     → grep по ожидаемым паттернам в коде
  2. Антипаттерны ОТСУТСТВУЮТ?
     → grep по запрещённым паттернам
  3. Mode-specific проверки:
     knowledge-compliance: Source: атрибуции присутствуют?
     behavior-preservation: публичный API не изменился?
     bug-fix-validation: баг-триггер покрыт тестом?
     quality-review: OWASP top-10 паттерны отсутствуют?

Результат: список проблем (может быть пустой)
```

### Уровень 2: Ревьюер-субагент (ОБЯЗАТЕЛЬНЫЙ)

Запуск субагента с mode-specific промптом (см. раздел "Шаблоны промптов").

```
Task(
  subagent_type="general-purpose",
  prompt="""
    # Роль
    Ты — code reviewer. Режим: {mode}.

    # Эталон
    {reference — зависит от режима}

    # Код для проверки
    {code}

    # Проблемы структурной проверки
    {issues из Уровня 1, если есть}

    # Инструкция
    {mode-specific инструкция — см. шаблоны ниже}

    # Формат ответа
    ## Результаты проверки
    | Элемент | Статус | Комментарий |
    |---------|--------|-------------|

    ## Вердикт
    PASS — код прошёл все проверки
    PARTIAL — частичные проблемы (перечислить)
    FAIL — критические проблемы (перечислить)

    ## Рекомендации (если FAIL/PARTIAL)
    Конкретные исправления.

    ## Маркер (ОБЯЗАТЕЛЬНО в последней строке output)
    Если PASS: [CODE-VERIFY-PASS]
    Если PARTIAL или FAIL: [CODE-VERIFY-FAIL]
  """
)
```

### Уровень 3: Решение оркестратора

```
Вердикт ревьюера:
  PASS    → продолжить workflow (CREATE в Learning Loop, commit и т.д.)
  PARTIAL → оркестратор исправляет конкретные проблемы → продолжить
  FAIL    → Ralph Wiggum Loop (итеративный retry, макс 3)
```

## 4 режима — шаблоны промптов ревьюера

### Режим 1: knowledge-compliance

**Когда:** Learning Loop (FETCH → EXECUTE → VERIFY). Проверяет что субагент использовал знания из FETCH, а не training данные.

```
# Шаблон промпта ревьюера (knowledge-compliance)

Task(
  subagent_type="general-purpose",
  prompt="""
    # Роль
    Ты — code reviewer. Проверь что код написан на основе
    предоставленных знаний, а не training данных агента.

    # Эталонные знания (из FETCH)
    {knowledge_block}

    # Код для проверки (из EXECUTE)
    {code}

    # Маркерные паттерны (должны присутствовать)
    {markers}

    # Проблемы структурной проверки
    {issues}

    # Инструкция
    Для КАЖДОЙ функции/класса в коде:
    1. Найди соответствующую секцию в эталонных знаниях
    2. Сравни: API, параметры, паттерны совпадают?
    3. Проверь атрибуцию (Source:) — корректна ли ссылка?
    4. Если функция НЕ из knowledge — ошибка или обоснованное дополнение?

    # Формат ответа
    ## Соответствие knowledge_block
    | Функция | Source указан | Соответствует knowledge | Комментарий |
    |---------|--------------|------------------------|-------------|

    ## Вердикт: PASS | PARTIAL | FAIL
    ## Рекомендации

    ## Маркер (ОБЯЗАТЕЛЬНО в последней строке output)
    Если PASS: [CODE-VERIFY-PASS]
    Если PARTIAL или FAIL: [CODE-VERIFY-FAIL]
  """
)
```

### Режим 2: behavior-preservation

**Когда:** Рефакторинг. Проверяет что поведение не изменилось.

```
# Шаблон промпта ревьюера (behavior-preservation)

Task(
  subagent_type="general-purpose",
  prompt="""
    # Роль
    Ты — code reviewer. Проверь что рефакторинг не изменил
    наблюдаемое поведение кода.

    # Оригинальный код (до рефакторинга)
    {original_code}

    # Новый код (после рефакторинга)
    {refactored_code}

    # Проблемы структурной проверки
    {issues}

    # Инструкция
    1. Публичный API сохранён? (функции, классы, параметры, возвращаемые типы)
    2. Side effects те же? (файловая система, БД, сеть, логирование)
    3. Обработка ошибок эквивалентна? (исключения, коды возврата)
    4. Граничные случаи обрабатываются так же?
    5. Импорты: ничего не потеряно, новое не конфликтует?

    ## Вердикт: PASS | PARTIAL | FAIL
    ## Рекомендации

    ## Маркер (ОБЯЗАТЕЛЬНО в последней строке output)
    Если PASS: [CODE-VERIFY-PASS]
    Если PARTIAL или FAIL: [CODE-VERIFY-FAIL]
  """
)
```

### Режим 3: bug-fix-validation

**Когда:** Баг фикс. Проверяет что баг исправлен и нет регрессии.

```
# Шаблон промпта ревьюера (bug-fix-validation)

Task(
  subagent_type="general-purpose",
  prompt="""
    # Роль
    Ты — code reviewer. Проверь что баг исправлен и фикс
    не создал регрессии.

    # Описание бага
    {bug_description}

    # Код до фикса
    {original_code}

    # Код после фикса
    {fixed_code}

    # Тесты (если есть)
    {test_code}

    # Проблемы структурной проверки
    {issues}

    # Инструкция
    1. Фикс адресует root cause, а не симптом?
    2. Баг-триггер покрыт тестом?
    3. Нет побочных изменений (unrelated changes)?
    4. Обработка граничных случаев не нарушена?
    5. Фикс минимален (не over-engineering)?

    ## Вердикт: PASS | PARTIAL | FAIL
    ## Рекомендации

    ## Маркер (ОБЯЗАТЕЛЬНО в последней строке output)
    Если PASS: [CODE-VERIFY-PASS]
    Если PARTIAL или FAIL: [CODE-VERIFY-FAIL]
  """
)
```

### Режим 4: quality-review

**Когда:** Новый код или общий ревью. Безопасность, паттерны, производительность.

```
# Шаблон промпта ревьюера (quality-review)

Task(
  subagent_type="general-purpose",
  prompt="""
    # Роль
    Ты — code reviewer. Проверь качество кода:
    безопасность, паттерны, производительность.

    # Код для проверки
    {code}

    # Контекст проекта
    Python 3.11+, async-first, Pydantic v2, provider pattern.
    Stores extend abstract base classes.

    # Проблемы структурной проверки
    {issues}

    # Инструкция
    ## Безопасность
    - SQL injection, command injection, XSS?
    - Секреты не захардкожены?
    - Input validation на системных границах?

    ## Паттерны проекта
    - Async-first (все I/O — async)?
    - Pydantic модели из schemas/?
    - Provider pattern (абстрактный base → конкретная реализация)?
    - Конфигурация через pydantic-settings?

    ## Производительность
    - N+1 запросы?
    - Блокирующие вызовы в async контексте?
    - Утечки ресурсов (файлы, соединения)?

    ## Читаемость
    - Именование понятное?
    - Функции ≤ 50 строк?
    - Комментарии только где логика неочевидна?

    ## Вердикт: PASS | PARTIAL | FAIL
    ## Рекомендации

    ## Маркер (ОБЯЗАТЕЛЬНО в последней строке output)
    Если PASS: [CODE-VERIFY-PASS]
    Если PARTIAL или FAIL: [CODE-VERIFY-FAIL]
  """
)
```

## Ralph Wiggum Loop — итеративный retry при FAIL

При FAIL ревьюера запускается Ralph Wiggum цикл — итеративный retry с фидбеком.

```
FAIL (ревьюер вернул список проблем)
  │
  ▼
Ralph Wiggum итерация N (макс 3):
  │
  │ Промпт = reference (эталон)
  │        + код предыдущей попытки
  │        + фидбек ревьюера (конкретные проблемы)
  │        + "Исправь ТОЛЬКО указанные проблемы"
  │
  ├─ FIX: исправить код по фидбеку
  │
  ├─ VERIFY: повторить 3 уровня
  │    ├─ PASS    → DONE
  │    ├─ PARTIAL → оркестратор фиксит → DONE
  │    └─ FAIL    → следующая итерация (N+1)
  │
  └─ После 3 неудачных итераций:
       → Объяснить почему не удаётся (не зацикливаться)
       → Продолжить с пометкой "requires manual review"
       → В антипаттерны: добавить проблемные места
```

**Принципы Ralph Wiggum в VERIFY:**
- Каждая итерация получает фидбек предыдущей (не начинает с нуля)
- После 3 неудач — объяснить причину, не зацикливаться
- Коммит по одному логическому изменению на итерацию
- Фидбек ревьюера = конкретные строки + секции reference

## Pipeline диаграмма

```
КОД ИЗМЕНЁН (Write/Edit)
  │
  ▼
Выбор режима:
  ├─ Learning Loop?        → knowledge-compliance
  ├─ Рефакторинг?          → behavior-preservation
  ├─ Баг фикс?             → bug-fix-validation
  └─ Новый код / общий?    → quality-review
  │
  ▼
УРОВЕНЬ 1: Структурная проверка (grep, 0 cost)
  │ ✓ Маркерные паттерны присутствуют
  │ ✓ Антипаттерны отсутствуют
  │ ✓ Mode-specific checks
  │
  ▼
УРОВЕНЬ 2: Ревьюер-субагент (1 subagent call)
  │ Task(general-purpose, prompt=mode-specific)
  │
  ▼
УРОВЕНЬ 3: Решение
  ├─ PASS    → ✅ Продолжить workflow
  ├─ PARTIAL → 🔧 Исправить → Продолжить
  └─ FAIL    → 🔄 Ralph Wiggum Loop (макс 3)
                  ├─ PASS → ✅ Done
                  └─ 3x FAIL → ⚠️ Manual review
```

## Антипаттерны

| Плохо | Почему | Как правильно |
|-------|--------|---------------|
| Пропустить VERIFY | Код может не соответствовать эталону | VERIFY после КАЖДОГО изменения кода |
| Не указать режим | Промпт ревьюера будет generic | Всегда выбирай конкретный режим |
| VERIFY без reference | Ревьюер не знает что проверять | Для knowledge-compliance — KB, для bug-fix — описание бага |
| Игнорировать PARTIAL | Накопление мелких проблем | PARTIAL = исправить конкретные проблемы |
| Зацикливаться на FAIL | Может быть системная проблема | Макс 3 итерации, потом manual review |
| VERIFY для вопросов | Нечего верифицировать | Только для code output |
| Запускать для docs/config | Нецелевое использование | Только для кода (.py, .ts, .js и т.д.) |
