# YAxUnit Unit-тесты для 1С

## Overview

Этот скилл кодирует методологию написания надёжных YAxUnit unit-тестов для серверной
бизнес-логики конфигураций 1С:Предприятие. Дистиллирован из практики работы с реальными
конфигурациями (платформа 8.3.27, YAxUnit 24.x).

Ключевой инсайт: **большинство падений unit-тестов вызваны неправильным именем метода,
неверным типом параметра или отсутствием деплоя расширения, а не логическими ошибками.**
Поэтому скилл делает упор на чтение исходника тестируемого метода ДО написания теста
и на обязательный деплой перед прогоном.

## Когда использовать этот скилл

- Написание новых тест-модулей для изменённых/добавленных серверных методов
- Проверка бизнес-логики: общие модули, модули объектов, модули менеджера
- Unit-покрытие после реализации задачи (Этап 6 `implement-1c-task` → `/write-1c-unit-tests`)
- Отладка упавших YAxUnit тестов (`Метод не найден`, `ОжидаетЧто` провалил проверку)
- Ревью тест-модулей на соответствие соглашениям YAxUnit

## YAxUnit ≠ BDD (ключевое разграничение)

| Аспект | YAxUnit (этот скилл) | VA BDD (va-bdd-testing) |
|---|---|---|
| **Что тестирует** | Серверные методы: логика, расчёты, движения | Пользовательский сценарий в UI |
| **Как запускается** | `run_module_tests` / `run_all_tests` через MCP | `run-bdd.ps1` + Vanessa Automation |
| **Тест-артефакт** | BSL-модуль в расширении `UnitTests` | `.feature`-файл Gherkin |
| **Нужен GUI** | Нет (серверный контекст) | Да (клиентское приложение) |
| **Изоляция** | Мокито для зависимостей | TestDB с реальными данными |
| **Когда использовать** | Формула / валидация / движение регистра | Форма / кнопка / диалог / ARM |

**Правило выбора:** если логику можно вызвать как `<Модуль>.<Метод>(Параметры)` на сервере
без открытия формы — YAxUnit. Если нужен UI — BDD.

## Обязательный 6-фазный workflow

**НИКОГДА не пиши тест-код до завершения Фаз 1 и 2.**

```
Фаза 1: АНАЛИЗ ТЕСТИРУЕМОГО КОДА
    read_method_source → сигнатура, ветки, зависимости
        |
Фаза 2: ДИЗАЙН КЕЙСОВ
    Матрица: positive + boundary + negative для каждой ветки
        |
Фаза 3: НАПИСАНИЕ ТЕСТ-МОДУЛЯ
    BSL: ИсполняемыеСценарии + тест-процедуры + деплой
        |
Фаза 4: ДИСКАВЕРИ
    Регистрация в реестре тест-модулей расширения
        |
Фаза 5: ПРОГОН И ВЕРИФИКАЦИЯ
    run_module_tests → разбор падений
        |
Фаза 6: ИНТЕГРАЦИЯ С ПАЙПЛАЙНОМ
    .run-state.json + IMPLEMENTATION-PROGRESS
```

## Фаза 1: Анализ тестируемого кода

### 1.1 Получить имя проекта EDT

```
mcp__edt-mcp__list_projects()
→ запомнить projectName (используется во всех последующих вызовах)
```

### 1.2 Найти модуль объекта

```
mcp__edt-mcp__list_modules(projectName, objectName="<ИмяОбъекта>")
→ список module_path для CommonModule/ObjectModule/ManagerModule
```

При расхождении Designer-пути и EDT-пути (ANALYSIS-REPORT пишет Designer-style
`CommonModules/<Имя>/Ext/Module.bsl`, EDT хранит по-другому) — использовать fallback:
перебрать возвращённые `module_path`, выбрать совпадающий по типу модуля.

### 1.3 Прочитать тестируемый метод

```
mcp__edt-mcp__read_method_source(projectName, modulePath, methodName)
```

**Обязательные вопросы после чтения:**
- Метод экспортный? (`Экспорт` в сигнатуре) — если нет, тест вызвать нельзя напрямую
- Какие параметры и их типы?
- Сколько ветвей `Если/ИначеЕсли/Иначе` — каждая = потенциальный кейс
- Есть ли вызовы внешних модулей с побочными эффектами? (→ кандидаты для Мокито)
- Какое возвращаемое значение в каждой ветке?

### 1.4 Прочитать зависимости (если нужны)

Если тестируемый метод вызывает другие методы текущего модуля — прочитать их тоже
(`read_method_source` для каждого), чтобы понять полный контракт.

### Definition of Done (Фаза 1)

- [ ] Метод прочитан целиком (`read_method_source`)
- [ ] Таблица «параметр → тип → допустимые значения» составлена
- [ ] Все ветки `Если/ИначеЕсли` перечислены
- [ ] Внешние зависимости с побочными эффектами идентифицированы
- [ ] Метод экспортный (или намечен workaround через вызывающий экспортный метод)

## Фаза 2: Дизайн кейсов

### Матрица покрытия (заполнять перед написанием кода)

| Кейс | Тип | Входные данные | Ожидаемый результат | Матчер |
|---|---|---|---|---|
| Штатный | positive | корректные значения | ожидаемый выход | `Равно` |
| Граничный | boundary | 0 / пустая строка / Неопределено | поведение на границе | `Равно` / `НеЗаполнено` |
| Негативный | negative | неверный тип / несуществующая ссылка | исключение / флаг | `ОжидаетВыброса` |

**Минимум на нетривиальный метод:** 1 positive + 1 граничный ИЛИ 1 negative.
**Тривиальный метод** (прямая возврат переменной, нет условий) — 1 positive достаточно.

### Источники тест-данных

```
mcp__1c-mcp-crud__execute_query("ВЫБРАТЬ ПЕРВЫЕ 1 Ссылка ИЗ Справочник.<Имя> ГДЕ НЕ ПометкаУдаления")
→ реальный UUID для positive кейса
```

```
mcp__edt-mcp__get_metadata_details(projectName, "<ИмяОбъекта>")
→ перечисления, допустимые типы реквизитов
```

```
mcp__bsl-platform-context__getMember("<Тип>", "<Метод>")
→ сигнатура платформенного метода, используемого внутри тестируемой функции
```

### Мокито — когда и зачем

Используй `Мокито` для изоляции:
- HTTP-запросы к внешним системам
- Запись в регистры / движения документов (побочный эффект)
- Методы, требующие живого пользователя / сессии
- Случайные / временные значения (`ТекущаяДата()`)

**НЕ мокируй:** платформенные типы (`ТаблицаЗначений`, `Запрос`), простые расчёты,
методы самого тестируемого модуля (тестируй их напрямую или создавай отдельный кейс).

## Фаза 3: Написание тест-модуля

### 3.1 Структура BSL-файла (канонический шаблон)

```bsl
#Область ОписаниеТестов

// Точка входа YAxUnit — ОБЯЗАТЕЛЬНАЯ экспортная процедура без параметров
Процедура ИсполняемыеСценарии() Экспорт
    ЮТТесты.ДобавитьСерверныйТест("ТестДолжен_ПолучитьВодителя_ПриКорректнойСсылке_ВернутьСтруктуру");
    ЮТТесты.ДобавитьСерверныйТест("ТестДолжен_ПолучитьВодителя_ПриПустойСсылке_ВернутьНеопределено");
    ЮТТесты.ДобавитьСерверныйТест("ТестДолжен_РассчитатьСумму_ПриНулевыхДанных_ВернутьНоль");
КонецПроцедуры

#КонецОбласти

#Область Тесты

// --- Позитивный кейс ---
Процедура ТестДолжен_ПолучитьВодителя_ПриКорректнойСсылке_ВернутьСтруктуру() Экспорт
    // Arrange — реальный UUID из TestDB (получен через execute_query)
    СсылкаНаТС = ТранспортныеСредства.НайтиПоКоду("ТС-0001");

    // Act
    Результат = гкс_ДиректорияТранспортаМенеджер.ПолучитьВодителя(СсылкаНаТС);

    // Assert
    ЮТест.ОжидаетЧто(Результат).Заполнено();
    ЮТест.ОжидаетЧто(Результат).ИмеетТип("Структура");
КонецПроцедуры

// --- Граничный кейс ---
Процедура ТестДолжен_ПолучитьВодителя_ПриПустойСсылке_ВернутьНеопределено() Экспорт
    // Arrange
    ПустаяСсылка = Справочники.гкс_ТранспортныеСредства.ПустаяСсылка();

    // Act
    Результат = гкс_ДиректорияТранспортаМенеджер.ПолучитьВодителя(ПустаяСсылка);

    // Assert
    ЮТест.ОжидаетЧто(Результат).Равно(Неопределено);
КонецПроцедуры

// --- Негативный кейс с Мокито ---
Процедура ТестДолжен_РассчитатьСумму_ПриОшибкеПодсчёта_ВыброситьИсключение() Экспорт
    // Arrange — мокируем внешний HTTP-вызов, который бросает исключение
    МокСервис = Мокито.Создать();
    Мокито.Обучить(МокСервис, "ПолучитьКурс", Мокито.Параметры().Любой())
        .ВыброситьИсключение("Сервис недоступен");

    // Act + Assert
    ЮТест.ОжидаетВыброс("Сервис недоступен");
    гкс_ВалютныйРасчётМодуль.РассчитатьСумму(МокСервис, 100);
КонецПроцедуры

#КонецОбласти
```

### 3.2 XML-метаданные модуля (обязательный файл)

При создании нового общего модуля в расширении — нужен XML-файл метаданных рядом с `.bsl`.
Шаблон (Server=true, Client=false, Global=false):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<MetaDataObject xmlns="http://v8.1c.ru/8.3/MDClasses"
    xmlns:v8="http://v8.1c.ru/8.1/data/core" version="2.20">
  <CommonModule uuid="<новый-UUID>">
    <Properties>
      <Name>гкс_<ИмяОбъекта>Тест</Name>
      <Synonym/>
      <Comment/>
      <Global>false</Global>
      <ClientManagedApplication>false</ClientManagedApplication>
      <Server>true</Server>
      <ExternalConnection>false</ExternalConnection>
      <ClientOrdinaryApplication>false</ClientOrdinaryApplication>
      <ServerCall>false</ServerCall>
      <Privileged>false</Privileged>
      <ReturnValuesReuse>DontUse</ReturnValuesReuse>
    </Properties>
  </CommonModule>
</MetaDataObject>
```

UUID генерируй через `python -c "import uuid; print(uuid.uuid4())"`.

### 3.3 Запись через EDT-MCP

```
mcp__edt-mcp__write_module_source(
    projectName,
    modulePath="UnitTests/CommonModules/гкс_<ИмяОбъекта>Тест/Module.bsl",
    content=<BSL-текст>
)
```

После каждой записи — обязательно:
```
mcp__edt-mcp__get_project_errors(projectName)
→ должно быть 0 errors
```

### 3.4 Деплой расширения

```bash
# Путь к платформе — стандартный для кластера
ONEC_CONN="Srvr=\"DESKTOP-TNU600C\";Ref=\"ИБTransportManagementDevelop\""

# Шаг 1: загрузить исходники расширения в конфигуратор
1cv8.exe DESIGNER /IBConnectionString "$ONEC_CONN" \
  /LoadConfigFromFiles "src/bsl/exts/UnitTests" -Extension UnitTests -Format Hierarchical

# Шаг 2: применить изменения к БД
1cv8.exe DESIGNER /IBConnectionString "$ONEC_CONN" \
  /UpdateDBCfg -Extension UnitTests
```

Строку подключения взять из `.env` → `ONEC_TEST_CONN`.
Если `.env` нет — дефолт: `Srvr="DESKTOP-TNU600C";Ref="ИБTransportManagementDevelop"`.

**Если в БД активные сессии** — спросить пользователя перед `UpdateDBCfg`.

## Фаза 4: Дискавери (регистрация в расширении)

YAxUnit находит тест-модули двумя способами:

**Автоматически** (предпочтительно): если в расширении настроен модуль сканирования
(`ЮТКонфигурация` или аналог), он ищет все модули с `ИсполняемыеСценарии()`.
Ничего дополнительно делать не нужно — тест подхватится после деплоя.

**Явная регистрация** (если авто-дискавери не работает): найди модуль регистрации
через `search_in_code(projectName, "ДобавитьМодуль")` и добавь туда имя нового модуля.

Проверка дискавери: `run_all_tests()` должен видеть новый модуль в списке.

## Фаза 5: Прогон и верификация

```
mcp__mcp-onec-test-runner__run_module_tests(moduleName="гкс_<ИмяОбъекта>Тест")
```

### Таблица типовых ошибок

| Симптом | Причина | Fix |
|---|---|---|
| `passed=0, errors=0` | Тест-модуль не задеплоен или `ИсполняемыеСценарии` не найдена | Проверить деплой; убедиться что процедура `Экспорт` |
| `Метод не найден: <Имя>` | Опечатка в имени или метод не `Экспорт` | Перечитать `read_method_source`, проверить `Экспорт` |
| `ОжидаетЧто` провалил | Реальный результат не совпал с ожидаемым | Добавить промежуточный `ЮТест.ОжидаетЧто(Результат).НеРавно(Неопределено)` перед основной проверкой |
| `Нет доступа к объекту` | Привилегированный режим нужен | Добавить `Привилегированный=Да` к тест-модулю (для тестов с записью данных) |
| `Не найден тип` | Модуль тестируемого объекта не в расширении UnitTests | Проверить `list_modules` — модуль должен быть виден из UnitTests |
| Ошибка компиляции EDT | Синтаксическая ошибка в BSL | `get_project_errors(projectName)` → исправить по сообщению |

## Фаза 6: Интеграция с пайплайном

### Обновление `.run-state.json`

Добавить запись в массив `chain` файла `.run-state.json` в папке задачи:

```json
{
  "section": "unit_гкс_<ИмяОбъекта>Тест",
  "type": "yaxunit",
  "status": "passed",
  "started_at": "<ISO-timestamp>",
  "duration_s": <секунды>,
  "passed": <N>,
  "failed": 0,
  "module": "гкс_<ИмяОбъекта>Тест"
}
```

Stop-хук `advance_test_done` читает `chain[].status` — при всех `passed` авто-продвигает
этап 4 пайплайна **без правки хука** (формат `chain[]` общий для BDD и YAxUnit).

### Запись в IMPLEMENTATION-PROGRESS.md

В раздел «Результаты тестирования» добавить:

```markdown
### YAxUnit unit-тесты

| Модуль | Passed | Failed | Методы |
|---|---|---|---|
| `гкс_<ИмяОбъекта>Тест` | N | 0 | `<Метод1>`, `<Метод2>` |

Запуск: `mcp__mcp-onec-test-runner__run_module_tests("гкс_<ИмяОбъекта>Тест")`
```

## API YAxUnit (справочник)

Источник истины — модули в `src/bsl/exts/YAXUNIT/CommonModules/`. При сомнении
читать через `mcp__edt-mcp__read_module_source`.

### ЮТТесты — регистрация тестов

```bsl
ЮТТесты.ДобавитьСерверныйТест("ИмяПроцедуры");          // серверный тест
ЮТТесты.ДобавитьКлиентскийТест("ИмяПроцедуры");         // клиентский тест (редко)
ЮТТесты.ДобавитьСерверныйТестСКонтекстом("Имя", Контекст); // тест с параметрами
```

### ЮТест — основные утверждения

```bsl
// Базовые проверки значения
ЮТест.ОжидаетЧто(Значение).Равно(Ожидаемое);
ЮТест.ОжидаетЧто(Значение).НеРавно(НеОжидаемое);
ЮТест.ОжидаетЧто(Значение).Больше(Порог);
ЮТест.ОжидаетЧто(Значение).БольшеИлиРавно(Порог);
ЮТест.ОжидаетЧто(Значение).Меньше(Порог);
ЮТест.ОжидаетЧто(Значение).МеньшеИлиРавно(Порог);

// Проверка заполненности
ЮТест.ОжидаетЧто(Значение).Заполнено();
ЮТест.ОжидаетЧто(Значение).НеЗаполнено();

// Проверка типа
ЮТест.ОжидаетЧто(Значение).ИмеетТип("Булево");
ЮТест.ОжидаетЧто(Значение).ИмеетТип("СправочникСсылка.Контрагенты");
ЮТест.ОжидаетЧто(Значение).ИмеетТип("Структура");
ЮТест.ОжидаетЧто(Значение).ИмеетТип("ТаблицаЗначений");

// Коллекции
ЮТест.ОжидаетЧто(Коллекция).ИмеетДлину(N);
ЮТест.ОжидаетЧто(Коллекция).НеПуста();
ЮТест.ОжидаетЧто(Коллекция).Содержит(Элемент);

// Исключения
ЮТест.ОжидаетВыброс("часть сообщения об ошибке");

// Сообщение при падении (опционально, для диагностики)
ЮТест.ОжидаетЧто(Результат, "Должен вернуть ненулевую сумму").Больше(0);
```

### ЮТУтверждения — расширенные проверки структур

```bsl
// Проверка структуры
ЮТУтверждения.ПроверитьТип(Значение, "Структура");
ЮТУтверждения.ПроверитьСвойство(Структура, "ИмяСвойства");
ЮТУтверждения.ПроверитьСвойствоТип(Структура, "ИмяСвойства", "Число");

// Проверка колонок ТаблицыЗначений
ЮТУтверждения.ПроверитьКолонку(ТЗ, "Сумма");
```

### Мокито — изоляция зависимостей

// Создание мока
Мок = Мокито.Создать();

Мокито.Обучить(Мок, "ИмяМетода", Мокито.Параметры().Любой())

Мокито.Проверить(Мок).ВызванМетод("ИмяМетода").КоличествоРаз(2);
Мокито.Проверить(Мок).НеВызванМетод("ИмяМетода");

## Антипаттерны (не делать)

| Антипаттерн | Почему плохо | Правильно |
|---|---|---|
| Писать тест до чтения исходника | Ошибка имени/сигнатуры → `Метод не найден` | Сначала `read_method_source` |
| Один тест проверяет несколько методов | Непонятно что упало; нарушает изоляцию | Одна процедура = одна проверка |
| Выдуманные UUID в тест-данных | Тест падает на чистой базе | `execute_query` для реальных UUID |
| Тест через `execute_code` (1c-mcp-crud) | Обходит расширение; нет YAxUnit-отчёта | `run_module_tests` через MCP |
| Тест UI-операций в YAxUnit | Серверный контекст не видит форму | Это BDD → `va-bdd-testing` |
| Запись в production-данные без rollback | Загрязнение БД | Мокито или явный teardown |
| Тест-модуль вне расширения `UnitTests` | YAxUnit не найдёт | Только в `src/bsl/exts/UnitTests/` |
| Пропустить деплой расширения | Тест работает со старым кодом | `LoadConfigFromFiles` + `UpdateDBCfg` перед прогоном |

## Соглашения расширения UnitTests

**Расположение:** `src/bsl/exts/UnitTests/CommonModules/`

**Именование модулей:**
- `гкс_<ИмяОбъектаКонфигурации>Тест` — тест конкретного объекта
- `гкс_<ИмяОбщегоМодуля>Тест` — тест общего модуля

**Свойства модуля:** `Сервер=Да`, `Глобальный=Нет`, `Клиент=Нет`
(исключение: `Привилегированный=Да` для тестов с записью данных).

**API источника истины:** `src/bsl/exts/YAXUNIT/CommonModules/`
- `ЮТест.xml` / BSL — основные матчеры
- `ЮТУтверждения.xml` / BSL — структурные проверки
- `ЮТТесты.xml` / BSL — регистрация тестов
- `Мокито.xml` / BSL — изоляция зависимостей
- `ЮТУтвержденияИБ.xml` / BSL — проверки данных ИБ (опционально)

При любом сомнении по API — читать через
`mcp__edt-mcp__read_module_source(projectName, "YAXUNIT/CommonModules/<Модуль>/Module.bsl")`.
