# YAxUnit Unit-тесты для 1С

## Overview

Этот скилл кодирует методологию написания надёжных YAxUnit unit-тестов для серверной
бизнес-логики конфигураций 1С:Предприятие. Дистиллирован из практики (платформа 8.3.27,
YAxUnit 24.x) и **сверен с вендоренным исходником** `src/bsl/exts/YAXUNIT/CommonModules/`.

Два ключевых инсайта:
1. **Большинство падений unit-тестов вызваны неправильным именем метода, неверным типом
   параметра или отсутствием деплоя/регистрации, а не логическими ошибками.** Поэтому упор — на
   чтение исходника тестируемого метода ДО написания теста и на обязательный деплой перед прогоном.
2. **API YAxUnit не выдумывают.** Матчеры и Мокито имеют точные имена; догадка = `Метод не найден`.
   Полный сверенный справочник — [references/api-reference.md](references/api-reference.md); при
   сомнении читать модуль через `mcp__edt-mcp__read_module_source`.

> ⚠ Ловушка имён: `ЮТест` (одна «Т») = утверждения/API; `ЮТТесты` (две «Т») = регистрация тестов.

## Когда использовать этот скилл

- Написание новых тест-модулей для изменённых/добавленных серверных методов
- Проверка бизнес-логики: общие модули, модули объектов, модули менеджера (в т.ч. `ОбработкаПроведения`/
  `ПередЗаписью` прямым вызовом + проверка движений через `ОжидаетЧтоТаблицаБазы`)
- Unit-покрытие после реализации задачи (Этап 6 `implement-1c-task` → `/write-1c-unit-tests`)
- Отладка упавших YAxUnit тестов (`Метод не найден`, провал матчера)
- Ревью тест-модулей на соответствие соглашениям YAxUnit

### рек.3 — когда YAxUnit-смоук applicable (advisory)

Гейт завершения 1С-задачи (`onec-task-completion-stop`) **рекомендует** (advisory `•`, НИКОГДА не блок)
прогнать YAxUnit-смоук, когда правлен/добавлен **экспортный серверный метод**
(`onec_change_scope.edits_exported_method`): экспортная поверхность = тестируемый инвариант,
POST-change комплемент impact-чека. Маршрут — **единственный** `mcp-onec-test-runner`
(`run_module_tests` затронутого модуля / `run_all_tests`), НЕ `edt/codepilot run_yaxunit_tests`-дубли,
НЕ BDD. Прогон пишет `.run-state.json` → авто-Этап-4; иначе — секция live-данных (ADR-050).

## YAxUnit ≠ BDD (ключевое разграничение)

| Аспект | YAxUnit (этот скилл) | VA BDD (va-bdd-testing) |
|---|---|---|
| **Что тестирует** | Серверные методы: логика, расчёты, движения | Пользовательский сценарий в UI |
| **Как запускается** | `run_module_tests` / `run_all_tests` через MCP | `run-bdd.ps1` + Vanessa Automation |
| **Тест-артефакт** | BSL-модуль в расширении `UnitTests` | `.feature`-файл Gherkin |
| **Нужен GUI** | Нет (серверный контекст) | Да (клиентское приложение) |
| **Изоляция** | `.ВТранзакции()` / `.УдалениеТестовыхДанных()` / Мокито | TestDB с реальными данными |
| **Когда использовать** | Формула / валидация / движение регистра | Форма / кнопка / диалог / ARM |

**Правило выбора:** если логику можно вызвать как `<Модуль>.<Метод>(Параметры)` на сервере
без открытия формы — YAxUnit. Если нужен UI — BDD.

## Обязательный 6-фазный workflow

**НИКОГДА не пиши тест-код до завершения Фаз 1 и 2.**

```
Фаза 1: АНАЛИЗ ТЕСТИРУЕМОГО КОДА     read_method_source → сигнатура, ветки, зависимости
Фаза 2: ДИЗАЙН КЕЙСОВ                Матрица: positive + boundary + negative на каждую ветку
Фаза 3: НАПИСАНИЕ ТЕСТ-МОДУЛЯ        BSL: ИсполняемыеСценарии + тест-процедуры + XML + деплой
Фаза 4: РЕГИСТРАЦИЯ (ДИСКАВЕРИ)      добавить модуль в подсистему Модульные (ОБЯЗАТЕЛЬНО)
Фаза 5: ПРОГОН И ВЕРИФИКАЦИЯ         run_module_tests → разбор падений
Фаза 6: ИНТЕГРАЦИЯ С ПАЙПЛАЙНОМ      .run-state.json + IMPLEMENTATION-PROGRESS
```

## Фаза 1: Анализ тестируемого кода

### 1.1 Получить имя проекта EDT
```
mcp__edt-mcp__list_projects()   → запомнить projectName (для всех последующих вызовов)
```

### 1.2 Найти модуль объекта
```
mcp__edt-mcp__list_modules(projectName, objectName="<ИмяОбъекта>")
→ module_path для CommonModule/ObjectModule/ManagerModule
```
При расхождении Designer-пути (`CommonModules/<Имя>/Ext/Module.bsl`) и EDT-пути — перебрать
возвращённые `module_path`, выбрать совпадающий по типу модуля.

### 1.3 Прочитать тестируемый метод
```
mcp__edt-mcp__read_method_source(projectName, modulePath, methodName)
```
**Обязательные вопросы после чтения:**
- Метод экспортный? (`Экспорт` в сигнатуре) — если нет, тест вызвать нельзя напрямую
- Какие параметры и их типы?
- Сколько ветвей `Если/ИначеЕсли/Иначе` — каждая = потенциальный кейс
- Есть ли вызовы внешних модулей с побочными эффектами? (→ кандидаты для DI/Мокито)
- Какое возвращаемое значение в каждой ветке?

### 1.4 Прочитать зависимости (если нужны)
Если тестируемый метод вызывает другие методы текущего модуля — прочитать их тоже, чтобы понять
полный контракт.

### Definition of Done (Фаза 1)
- [ ] Метод прочитан целиком (`read_method_source`)
- [ ] Таблица «параметр → тип → допустимые значения» составлена
- [ ] Все ветки `Если/ИначеЕсли` перечислены
- [ ] Внешние зависимости с побочными эффектами идентифицированы
- [ ] Метод экспортный (или намечен workaround через вызывающий экспортный метод)

## Фаза 2: Дизайн кейсов

### Матрица покрытия (заполнять перед написанием кода)

| Кейс | Тип | Входные данные | Ожидаемый результат | Матчер |
|---|---|---|---|---|
| Штатный | positive | корректные значения | ожидаемый выход | `.Равно()` |
| Граничный | boundary | 0 / пустая строка / Неопределено | поведение на границе | `.Равно()` / `.НеЗаполнено()` |
| Негативный | negative | неверный тип / несуществующая ссылка | исключение / флаг | `.ВыбрасываетИсключение()` / Попытка |

**Минимум на нетривиальный метод:** 1 positive + 1 граничный ИЛИ 1 negative.
**Тривиальный метод** (прямой возврат, нет условий) — 1 positive достаточно. Эталон границ: для
чётности проверяют `2, 1, 0, -1, -2` (ноль, отрицательные, граница).

### Источники тест-данных
```
mcp__1c-mcp-crud__execute_query("ВЫБРАТЬ ПЕРВЫЕ 1 Ссылка ИЗ Справочник.<Имя> ГДЕ НЕ ПометкаУдаления")
→ реальный UUID для positive кейса (НЕ выдумывать)
mcp__edt-mcp__get_metadata_details(projectName, "<ИмяОбъекта>")   → перечисления, типы реквизитов
mcp__bsl-platform-context__getMember("<Тип>", "<Метод>")          → сигнатура платформенного метода
```

### Изоляция зависимостей — DI предпочтительнее Мокито
- **Если зависимость передаётся ПАРАМЕТРОМ** вызывающего — подсунь тестовую реализацию (проще, без обвязки).
- **Мокито** — когда объект создаётся ВНУТРИ метода / для HTTP / записи в регистры / `ТекущаяДата()`.
  ⚠ Мокировать можно ТОЛЬКО метод конфигурации, обёрнутый в расширении `&Вместо` +
  `МокитоПерехват.АнализВызова` (не платформенный/расширения/внешней обработки). Готовые заглушки:
  `ЮТест.Данные().HTTPСервисЗапрос()` / `HTTPОтвет`. Детали — [references/api-reference.md](references/api-reference.md) §5.
- **НЕ мокируй:** платформенные типы (`ТаблицаЗначений`, `Запрос`), простые расчёты, методы самого
  тестируемого модуля (тестируй напрямую). Over-mocking → хрупкие тесты.

## Фаза 3: Написание тест-модуля

### 3.1 Структура BSL-файла (канонический шаблон, сверен с исходником)

```bsl
#Область СлужебныйПрограммныйИнтерфейс

// Точка входа YAxUnit — экспортная процедура без параметров.
// 2-й аргумент ДобавитьСерверныйТест — человекочитаемое описание (реальные тесты его дают).
Процедура ИсполняемыеСценарии() Экспорт
    ЮТТесты.ДобавитьСерверныйТест("ПолучитьВодителя_КорректнаяСсылка_Структура",
        "Водитель по корректной ссылке ТС возвращается структурой");
    ЮТТесты.ДобавитьСерверныйТест("ПолучитьВодителя_ПустаяСсылка_Неопределено",
        "Пустая ссылка ТС даёт Неопределено");
КонецПроцедуры

#КонецОбласти

#Область Тесты

// --- Позитивный кейс ---
Процедура ПолучитьВодителя_КорректнаяСсылка_Структура() Экспорт
    // Arrange — реальный UUID из TestDB (через execute_query)
    СсылкаНаТС = Справочники.гкс_ТранспортныеСредства.НайтиПоКоду("ТС-0001");
    // Act
    Результат = гкс_ДиректорияТранспортаМенеджер.ПолучитьВодителя(СсылкаНаТС);
    // Assert
    ЮТест.ОжидаетЧто(Результат, "должна вернуться структура").Заполнено();
    ЮТест.ОжидаетЧто(Результат).ИмеетТип("Структура");
КонецПроцедуры

// --- Граничный кейс ---
Процедура ПолучитьВодителя_ПустаяСсылка_Неопределено() Экспорт
    ПустаяСсылка = Справочники.гкс_ТранспортныеСредства.ПустаяСсылка();
    Результат = гкс_ДиректорияТранспортаМенеджер.ПолучитьВодителя(ПустаяСсылка);
    ЮТест.ОжидаетЧто(Результат).ЭтоНеопределено();
КонецПроцедуры

#КонецОбласти
```

**Негативный кейс (исключение) — `.ВыбрасываетИсключение()` или Попытка** (метода `ОжидаетВыброс` НЕТ):
```bsl
Процедура РассчитатьСумму_ОшибкаСервиса_Исключение() Экспорт
    Поймано = Ложь;
    Попытка
        гкс_ВалютныйРасчётМодуль.РассчитатьСумму(НедоступныйСервис, 100);
    Исключение
        Поймано = Истина;
    КонецПопытки;
    ЮТест.ОжидаетЧто(Поймано, "ожидалось исключение при недоступном сервисе").ЭтоИстина();
КонецПроцедуры
```

**Пропуск теста при отсутствии данных** — `ЮТест.Пропустить(...)` (НЕ ручной `ОжидаетЧто(Истина).Равно(Истина)`):
```bsl
Если ДанныеОтсутствуют Тогда
    ЮТест.Пропустить("В базе нет пользователя с заполненным EmailПользователя");
    Возврат;
КонецЕсли;
```

### 3.2 XML-метаданные модуля (обязательный файл рядом с `.bsl`)
`Server=true, Client=false, Global=false`:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<MetaDataObject xmlns="http://v8.1c.ru/8.3/MDClasses"
    xmlns:v8="http://v8.1c.ru/8.1/data/core" version="2.20">
  <CommonModule uuid="<новый-UUID>">
    <Properties>
      <Name>гкс_<ИмяОбъекта>Тест</Name>
      <Global>false</Global>
      <Server>true</Server>
      <ExternalConnection>false</ExternalConnection>
      <ClientManagedApplication>false</ClientManagedApplication>
      <ClientOrdinaryApplication>false</ClientOrdinaryApplication>
      <ServerCall>false</ServerCall>
      <Privileged>false</Privileged>
      <ReturnValuesReuse>DontUse</ReturnValuesReuse>
    </Properties>
  </CommonModule>
</MetaDataObject>
```
UUID — `python -c "import uuid; print(uuid.uuid4())"`.

### 3.3 Запись через EDT-MCP
```
mcp__edt-mcp__write_module_source(projectName,
    modulePath="UnitTests/CommonModules/гкс_<ИмяОбъекта>Тест/Module.bsl", content=<BSL>)
mcp__edt-mcp__get_project_errors(projectName)   → 0 errors обязательно
```

### 3.4 Деплой расширения (2 отдельных вызова Designer)
```bash
ONEC_CONN="Srvr=\"DESKTOP-TNU600C\";Ref=\"ИБTransportManagementDevelop\""   # из .env → ONEC_TEST_CONN
1cv8.exe DESIGNER /IBConnectionString "$ONEC_CONN" /LoadConfigFromFiles "src/bsl/exts/UnitTests" -Extension UnitTests
1cv8.exe DESIGNER /IBConnectionString "$ONEC_CONN" /UpdateDBCfg -Extension UnitTests
```
Версию платформы взять из установленной (локально 8.3.27.1936/2214). **Если активные сессии в БД —
спросить пользователя перед `UpdateDBCfg`.**

> 🔒 **После деплоя — СНЯТЬ безопасный режим расширения** (Конфигуратор → расширение → свойства).
> Иначе не работают перехваты Мокито, чтение `config.json` и `closeAfterTests` (при CLI-создании
> расширения дефолт = безопасный режим ВКЛ). См. [references/api-reference.md](references/api-reference.md) §9.

## Фаза 4: Регистрация в подсистеме `Модульные` (ОБЯЗАТЕЛЬНО)

YAxUnit находит тест-модули **по содержимому подсистемы** `ЮТТ_ЮТПодключаемыеМодули → Модульные`
(сверено с движком `ЮТПодключаемыеМодулиСлужебный`). Без регистрации `run_all_tests` модуль **не
увидит** — и ошибки не будет, просто пусто.

Добавить модуль в `<Content>` подсистемы `Модульные` (через EDT: состав подсистемы, либо в XML):
```xml
<!-- src/bsl/exts/UnitTests/Subsystems/ЮТТ_ЮТПодключаемыеМодули/Subsystems/Модульные.xml -->
<Content>
  <xr:Item xsi:type="xr:MDObjectRef">CommonModule.гкс_<ИмяОбъекта>Тест</xr:Item>
</Content>
```
Имя модуля — **любое** (`гкс_…Тест` работает; `ЮТТ` — префикс подсистемы, не модулей).
**Проверка:** после деплоя `run_all_tests()` должен видеть новый модуль в списке.

## Фаза 5: Прогон и верификация

```
mcp__mcp-onec-test-runner__run_module_tests(moduleName="гкс_<ИмяОбъекта>Тест")
```

### Таблица типовых ошибок

| Симптом | Причина | Fix |
|---|---|---|
| `passed=0, errors=0` | Модуль не задеплоен / не в подсистеме `Модульные` / нет `ИсполняемыеСценарии` | Проверить регистрацию (Фаза 4) + деплой; процедура `Экспорт` |
| `Метод не найден: <Имя>` | Опечатка в имени или метод не `Экспорт` | Перечитать `read_method_source`, проверить `Экспорт` |
| Матчер провалил | Реальный результат ≠ ожидаемый | Добавить промежуточный `.Заполнено()` перед основной проверкой; сверить данные |
| Мокито не подменяет | Метод не обёрнут `&Вместо`/нет `Мокито.Прогон()`/безопасный режим ВКЛ | Обвязка `&Вместо`+`МокитоПерехват`, `Прогон()` перед вызовом, снять безопасный режим |
| `Нет доступа к объекту` | Нужен привилегированный режим | `Привилегированный=Да` тест-модуля (для тестов с записью) |
| Ошибка компиляции EDT | Синтаксис BSL | `get_project_errors(projectName)` → исправить |

## Фаза 6: Интеграция с пайплайном

### Обновление `.run-state.json` (в папке задачи)
```json
{ "section": "unit_гкс_<ИмяОбъекта>Тест", "type": "yaxunit", "status": "passed",
  "duration_s": <секунды>, "passed": <N>, "failed": 0, "module": "гкс_<ИмяОбъекта>Тест" }
```
Stop-хук `advance_test_done` читает `chain[].status` — при всех `passed` авто-продвигает этап 4
(формат `chain[]` общий для BDD и YAxUnit).

### Запись в IMPLEMENTATION-PROGRESS.md → раздел «Тестирование на реальных данных» (ADR-050)
```markdown
### YAxUnit unit-тесты
| Модуль | Passed | Failed | Методы |
|---|---|---|---|
| `гкс_<ИмяОбъекта>Тест` | N | 0 | `<Метод1>`, `<Метод2>` |
Запуск: `mcp__mcp-onec-test-runner__run_module_tests("гкс_<ИмяОбъекта>Тест")`
```

## API-шпаргалка (частое; полный сверенный каталог → [references/api-reference.md](references/api-reference.md))

```bsl
// Регистрация: 2-й арг — описание; параметризация — .СПараметрами(...); наборы — ДобавитьТестовыйНабор
ЮТТесты.ДобавитьСерверныйТест("Имя", "Описание");

// Утверждения: ЮТест.ОжидаетЧто(Значение [, "Сообщение"]).<Матчер>()
ЮТест.ОжидаетЧто(Рез).Равно(Ожид);            ЮТест.ОжидаетЧто(Рез).НеРавно(X);
ЮТест.ОжидаетЧто(Рез).Больше(0);              ЮТест.ОжидаетЧто(Рез).Заполнено();  // .НеЗаполнено()
ЮТест.ОжидаетЧто(Флаг).ЭтоИстина();           ЮТест.ОжидаетЧто(Флаг).ЭтоЛожь();
ЮТест.ОжидаетЧто(Рез).ЭтоНеопределено();      ЮТест.ОжидаетЧто(Рез).ИмеетТип("Структура"); // Строка|Тип|ОписаниеТипов
ЮТест.ОжидаетЧто(Кол).ИмеетДлину(N);          ЮТест.ОжидаетЧто(Кол).Содержит(Эл);
ЮТест.ОжидаетЧто(Об).Свойство("Код").Равно("А001");
ЮТест.ОжидаетЧто(Об).Метод("Записать").ВыбрасываетИсключение();   // НЕ «ОжидаетВыброс»
ЮТест.ОжидаетЧтоТаблицаБазы("Справочник.Х").СодержитЗаписиСКодом("А001");  // движения/данные ИБ
ЮТест.Пропустить("причина");                  // штатный SKIP

// Мокито: Обучение → Прогон → (вызов) → Проверить (нужна обвязка &Вместо в расширении)
Мокито.Обучение(Модуль).Когда("Метод", Мокито.МассивПараметров(Арг)).Вернуть(Значение);
Мокито.Прогон();                              // ОБЯЗАТЕЛЬНО перед вызовом тестируемого кода
Мокито.Проверить(Модуль).КоличествоВызовов("Метод").Равно(1);
```
> ❌ Не существуют (галлюцинации): `ОжидаетВыброс`, `ДобавитьСерверныйТестСКонтекстом`, `Мокито.Создать`,
> `Мокито.Обучить`, `Мокито.Параметры()`, `.ВызванМетод`, `ЮТУтверждения.ПроверитьТип/ПроверитьКолонку`, `.НеПуста`.

## Антипаттерны (не делать)

| Антипаттерн | Почему плохо | Правильно |
|---|---|---|
| Писать тест до чтения исходника | Ошибка имени/сигнатуры → `Метод не найден` | Сначала `read_method_source` |
| Выдумывать API YAxUnit | `Метод не найден` на несуществующем матчере | Сверять с `references/` / исходником |
| Один тест проверяет несколько методов | Непонятно что упало; нарушает изоляцию | Одна зона ответственности на тест |
| Выдуманные UUID в тест-данных | Тест падает на чистой базе | `execute_query` для реальных UUID |
| Зависимость тестов от порядка | Флаки при смене порядка | Изоляция (`.ВТранзакции()` / teardown) |
| Over-mocking | Хрупкость: тест проверяет заглушки, не логику | Мокать минимум; предпочесть DI |
| Тест платформы, не логики | Проверяет то, что и так гарантирует 1С | Тестировать свою бизнес-логику |
| Только happy-path | Пропущены исключения и границы | Добавить boundary + negative кейсы |
| Флаки от случайных данных | То падает, то нет; не воспроизвести | Детерминированные данные в критичных кейсах |
| Тест через `execute_code` (1c-mcp-crud) | Обходит расширение; нет YAxUnit-отчёта | `run_module_tests` через MCP |
| Тест UI-операций в YAxUnit | Серверный контекст не видит форму | Это BDD → `va-bdd-testing` |
| Запись в production без rollback | Загрязнение БД | `.ВТранзакции()` / `.УдалениеТестовыхДанных()` / Мокито |
| Пропустить деплой/регистрацию | Тест работает со старым кодом / не найден | `LoadConfigFromFiles`+`UpdateDBCfg` + подсистема `Модульные` |

## Соглашения расширения UnitTests

**Расположение:** `src/bsl/exts/UnitTests/CommonModules/`

**Именование модулей:** проект использует `гкс_<ИмяОбъектаКонфигурации>Тест` / `гкс_<ИмяОбщегоМодуля>Тест`
(официальная схема YAxUnit — `ОМ_Объект`/`Спр_Объект_МО`; оба валидны — дискавери по подсистеме, не по имени).

**Свойства модуля:** `Сервер=Да`, `Глобальный=Нет`, `Клиент=Нет`, **не заимствованный**
(исключение: `Привилегированный=Да` для тестов с записью данных).

**Регистрация:** обязательна в подсистеме `ЮТТ_ЮТПодключаемыеМодули → Модульные` (Фаза 4).

**API источника истины** (`src/bsl/exts/YAXUNIT/CommonModules/`): `ЮТест` (утверждения/API),
`ЮТУтверждения` (матчеры), `ЮТУтвержденияИБ` (данные ИБ), `ЮТТесты` (регистрация), `Мокито` +
`МокитоОбучение`/`МокитоПроверки` (изоляция), `ЮТКонструкторВариантов` (data-driven). Полный
сверенный справочник + CI/покрытие (METR/vrunner/Coverage41C) — [references/api-reference.md](references/api-reference.md).
