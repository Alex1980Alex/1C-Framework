## 1. Общее описание

Функционал «Заблокированные ТС» реализует механизм усиленного контроля качества на приёмных лабораторно-контрольных комплексах (ПЛК). Суть: при получении неудовлетворительных результатов лабораторных анализов по одному ТС, система автоматически блокирует последующие ТС этого же поставщика/номенклатуры для принудительного прохождения дополнительных проверок перед разгрузкой.

**Архитектура**: Mediator-паттерн — единый серверный общий модуль `гкс_ВходнойКонтрольКачества` (~2 900 строк, 40+ методов) координирует всю бизнес-логику. РС `гкс_ЗаблокированныеРегистрацииУсиленныйКонтроль` выступает тонким CRUD-слоем с 3 экспортными методами в модуле менеджера.

**Функциональная опция**: `гкс_ИспользоватьУсиленныйКонтрольКачества` (хранение в константе). Управляет видимостью всех объектов подсистемы.

## 3. Принципы формирования записей (REQ-2) [VERIFIED: PASS]

### 3.1 Когда создаются записи

Записи в РС `гкс_ЗаблокированныеРегистрацииУсиленныйКонтроль` создаются **при проведении документа «Лабораторный анализ»** (`гкс_ЛабораторныйАнализ`), если результаты анализа показывают отклонение от допустимых значений показателей, определённых в настройках усиленного контроля.

### 3.2 Двухканальная запись

Реализована **двухканальная модель** создания записей (строки 252-278 модуля `гкс_ВходнойКонтрольКачества`):

1. **Канал «Первое ТС»** (`ДокументРегистрации`) — блокировка привязывается к конкретному документу регистрации на ПЛК.
2. **Канал «Группа ТС»** (`БлокирующаяГруппаТС`) — блокировка привязывается к группе ТС (справочник `гкс_ГруппыТС`), что позволяет блокировать все последующие ТС в группе поставщика.

### 3.3 Структура записи

Каждая запись фиксирует:
- **Что заблокировано**: `ДокументРегистрации` — регистрация ТС, которую нельзя направить на разгрузку
- **Чем заблокировано**: `БлокирующаяРегистрация` + `БлокирующаяГруппаТС` — источник блокировки
- **По какому показателю**: `Показатель` — конкретный показатель анализа
- **С каким состоянием**: `БлокирующееСостояниеКачества` — текущее состояние качества блокирующего ТС
- **Снята ли блокировка**: `Разблокировано` (Boolean)

### 3.4 Принцип Optimistic Read-Modify-Write

Метод `ОбновитьСостояниеБлокировки` реализует паттерн оптимистичного обновления:
1. Читает текущий набор записей по фильтру измерений
2. Модифицирует ресурсы (состояние, флаг разблокировки)
3. Записывает обратно

### 3.5 Пакетная предзагрузка

Метод `ЗаполнитьЗаблокированныеРегистрации` использует пакетную предзагрузку с дедупликацией через `Соответствие` для минимизации обращений к БД при массовых операциях (АРМ отображает список всех ТС).

## 4. Принципы проверок и валидаций (REQ-3) [VERIFIED: PASS]

### 4.1 Трёхуровневая система проверки блокировки

Метод `ПроверитьБлокировкуДляСозданияНнР` (проверка перед созданием «Направления на разгрузку») реализует **3 уровня**:

| Уровень | Результат | Действие |
|---------|-----------|----------|
| **Block** (Блокировка) | Есть активные незакрытые блокировки | Создание НнР запрещено. Пользователь видит ошибку. |
| **Warn** (Предупреждение) | Есть блокировки, но они допускают продолжение с подтверждением | Пользователю выводится предупреждение, может продолжить. |
| **OK** | Блокировок нет или все разблокированы (`Разблокировано = Истина`) | Создание НнР разрешено без ограничений. |

### 4.2 Проверки при проведении документов

1. **Лабораторный анализ (проведение)**: проверяется, попадают ли результаты анализа в диапазоны настроек усиленного контроля (`ЗначениеПоказателяМин`..`ЗначениеПоказателяМакс`). Если да — создаются/обновляются записи блокировки для всех ТС, подпадающих под правило.

2. **Направление на разгрузку (проведение)**: проверяется наличие активных блокировок для данной регистрации. При принятии качества — записи разблокируются (`Разблокировано = Истина`).

3. **Регистрация на ПЛК (проведение)**: проверяется, не попадает ли ТС под действующие правила усиленного контроля.

### 4.3 Валидация настроек

Настройки усиленного контроля (`гкс_НастройкиУсиленногоКонтроляКачества`) валидируются:
- Обязательность заполнения ключевых измерений (вид перевозки, точка маршрута, номенклатура, показатель)
- Корректность диапазона (Мин <= Макс)
- Непересечение периодов действия правил
- Корректность количества ТС (> 0)

| `ОбновитьСостояниеБлокировки` | Read-Modify-Write записей блокировки: читает набор записей по фильтру измерений, обновляет БлокирующееСостояниеКачества и/или Разблокировано, записывает | Проведение ЛА, проведение НнР |

### 6.3 Логика двухканальной записи (строки 252-278)


## 7. Интерактивная работа в АРМ гкс_ПриемкаТранспорта (REQ-6) [VERIFIED: PASS]

### 7.1 Общая характеристика АРМ

- **Обработка:** `гкс_ПриемкаТранспорта`
- **Синоним:** АРМ «Приёмки и отгрузки на ПЛК»
- **Основная форма:** ОсновнаяФорма

### 7.2 Feature Toggle — управление видимостью

Функциональная опция `гкс_ИспользоватьУсиленныйКонтрольКачества` управляет видимостью элементов интерфейса, связанных с усиленным контролем. При выключенной опции все связанные колонки, кнопки и индикаторы скрыты.

### 7.3 Сценарии взаимодействия пользователя

#### Сценарий 1: Просмотр списка ТС с блокировками
1. Пользователь открывает АРМ и видит список регистраций
2. Система вызывает `ЗаполнитьЗаблокированныеРегистрации` для пакетной загрузки статусов
3. Заблокированные ТС визуально выделены (индикатор/цвет)
4. Пользователь видит причину блокировки (показатель, блокирующее ТС)

#### Сценарий 2: Попытка направить заблокированное ТС на разгрузку
1. Пользователь выбирает ТС и инициирует создание НнР
2. Система вызывает `ПроверитьБлокировкуДляСозданияНнР`
3. При уровне **Block** — выводится ошибка, действие запрещено
4. При уровне **Warn** — выводится предупреждение с возможностью продолжить
5. При уровне **OK** — создание НнР происходит штатно

#### Сценарий 3: Разблокировка после принятия качества
1. Для блокирующего ТС проводится НнР с принятием качества
2. Система автоматически обновляет записи: `Разблокировано = Истина`
3. Ранее заблокированные ТС становятся доступны для направления на разгрузку

#### Сценарий 4: Приёмка без входного контроля
1. Пользователь с ролью `гкс_ПриемкаТранспортаБезВходногоКонтроля_ДобавлениеИзменение` может пропустить контроль
2. Создаётся запись в РС `гкс_ПриемкаТранспортаБезВходногоКонтроля`
3. ТС допускается к разгрузке без прохождения усиленного контроля
