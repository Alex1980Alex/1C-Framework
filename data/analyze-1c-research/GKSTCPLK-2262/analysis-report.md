## 1. Общее описание

Функционал «Заблокированные ТС» реализует механизм усиленного контроля качества на приёмных лабораторно-контрольных комплексах (ПЛК). Суть: при получении неудовлетворительных результатов лабораторных анализов по одному ТС, система автоматически блокирует последующие ТС этого же поставщика/номенклатуры для принудительного прохождения дополнительных проверок перед разгрузкой.

**Архитектура**: Mediator-паттерн — единый серверный общий модуль `гкс_ВходнойКонтрольКачества` (~2 900 строк, 40+ методов) координирует всю бизнес-логику. РС `гкс_ЗаблокированныеРегистрацииУсиленныйКонтроль` выступает тонким CRUD-слоем с 3 экспортными методами в модуле менеджера.

**Функциональная опция**: `гкс_ИспользоватьУсиленныйКонтрольКачества` (хранение в константе). Управляет видимостью всех объектов подсистемы.

### 2.8.5 Пять сценариев цепочки усиленного контроля (из проектной документации)

Ниже описаны 5 блоков-сценариев с привязкой к методам конфигурации.

#### Блок 1: Базовые сценарии (без правил УК)

**Сценарий 1.1: Пропуск входного контроля**
- Путь: Взвешивание → КачествоПринято
- Метод: `гкс_ПриемкаТранспорта.ЗаписатьРегистрПриемкиБезВходногоКонтроля()`
- Условие: ЖД перевозка + роль + ФО `гкс_ИспользоватьОтключениеВходногоКонтроляКачества`
- РС: `гкс_ПриемкаТранспортаБезВходногоКонтроля` (запись)

**Сценарий 1.2: Правило не подобралось для УК**
- Путь: ФНП → ЛА → стандартный процесс без блокировки
- Метод: `ЗарегистрироватьТранспортноеСредствоДляУсиленногоКонтроля()` → `ДанныеПоказателей.ПоказателиКонтроля` пуст → пропуск

**Сценарий 1.3: Правило "Каждое ТС"**
- Путь: ФНП ВК → Показатели УК (Единичный/Приемка) → ЛабАнализ.Выполнен
- Метод: `ЗаполнитьРегистрПоказателейУсиленногоКонтроляЛабАнализом()` → РС `гкс_ПоказателиУсиленногоКонтроляПоРегистрации`
- Результаты ЛА:
  - КачествоПринято → КачествоПринято → **Формирование НнР**
  - НеПринято → НеПринято (без блокировки, т.к. правило КаждоеТС не блокирует других)
  - РПП → РПП (ожидание)

#### Блок 2: Правило "Первое ТС" (тип `ПервоеТС`)

**Сценарий 2.1: Первое ТС поставщика**
- Путь: ФНП ВК → Показатели УК → ЛабАнализ.Выполнен
- Метод: `ЗарегистрироватьТранспортноеСредствоДляУсиленногоКонтроля()` → `ЭтоПервоеТС = Истина`
- РС: `гкс_ТранспортныеСредстваПоставщикаУсиленногоКонтроля` (ЭтоПервоеТС = Истина)
- Результаты ЛА:
  - КачествоПринято → КачествоПринято → **Формирование НнР** → разблокировка последующих ТС
  - **НеПринято** → НеПринято → `ОбработкаОтклоненияПоКачествуУсиленногоКонтроля()` → **Изменение правил на КаждоеТС** (строки 339-340: `УстановитьТипВНастройкахУсиленногоКонтроля(Правила, КаждоеТС)`)
  - РПП → РПП (ожидание)

**Сценарий 2.2: ТС до выполнения анализа первого ТС (ЗАБЛОКИРОВАНО)**
- Путь: ФНП ВК → ЛабАнализВК.Выполнен → **Заблокировано** (Блокирующая регистрация)
- Метод: `ЗаполнитьЗаблокированныеРегистрацииУсиленныйКонтроль()` → двухканальная запись (Канал 1: БлокирующаяРегистрация)
- РС: `гкс_ЗаблокированныеРегистрацииУсиленныйКонтроль` (Разблокировано = Ложь)
- Результаты ЛА собственного:
  - КачествоПринято → КачествоПринято + Заблокировано → **Не формируется НнР** (проверка `ПроверитьБлокировкуДляСозданияНнР`)
  - НеПринято → НеПринято + Заблокировано
  - РПП → РПП + Заблокировано

**Сценарий 2.3: Обработка заблокированных ТС при завершении ЛА первого ТС**
- Метод: `ОбновитьЗаблокированныеТСПриЗавершенииЛА()` (строки 1847-1899)
  - Сценарий A (КачествоПринято УК):
    - → Разблокировано = Истина
    - → **Формирование НнР**, Состояние регистрации = КачествоПринято
    - → Метод: `ЗаписатьСостоянияРегистрацииЗаблокированныхТС()` (строки 661-694)
    - Примечание: "ограничение — доработка с переходом на новый регистр По Фактическим пробам"
  - Сценарий B (НеПринято УК):
    - → Заблокировано остаётся
    - → Показатели УК (Единичный/Промежуточный/Композит)
  - Сценарий C (РПП УК):
    - → Заблокировано остаётся
    - → ДопАнализ ручной и/или Ручная приемка через НнР

**Сценарий 2.4: Ручная приемка через НнР**

**Сценарий 2.5: ЛабАнализУК заблокированных ТС**

#### Блок 5: Принципы отображения в АРМ

1. **В АРМ приемка выводятся** все ТС — заблокированные видны в общем списке
2. **Признак блокировки** — столбец "УК" с иконкой ⚠
3. **В Детали**: Таблица заблокированных ТС / Показатели + блокирующий статус + блокирующая регистрация и состояние
   - Метод: `ЗаполнитьИнформациюОБлокировке()` → `ПолучитьПричинуБлокировкиДляДеталей()` (строки 2761-2869)
4. **В Детали**: Таблица с показателями УК предыдущей группы
5. **Основной принцип**: Состояние регистрации меняется при ЛА (приемка). НнР формируется, если нет блокировки и Качество принято при приемке
6. **Результат** вычисляется по Лаб. Анализу Приемка по ТЧ + Обращение к предыдущей группе
7. **Открытый вопрос**: ??? Взаимодействие с кварион/табло (требует уточнения)

#### Ключевой механизм: Эскалация правил (НеПринято → КаждоеТС)

При отклонении качества (НеПринято) на Первом ТС или в Группе, метод `ОбработкаОтклоненияПоКачествуУсиленногоКонтроля()` (строки 299-342) выполняет:

1. Получает показатели с `ОтклонятьКачество = Истина`
2. Ищет правила типа `ПервоеТС` для документов регистрации ЛА
3. Ищет правила типа `ГруппыТС` через `Справочники.гкс_ГруппыТС.СоставГруппыПоРегистрации()`
4. **Меняет тип правила на `КаждоеТС`** через `УстановитьТипВНастройкахУсиленногоКонтроля()`
5. Устанавливает `ДатаОкончания` = ТекущаяДата + `гкс_СрокУстановкиПравилКаждоеТС` (константа, в днях)

Это значит: если первое ТС или группа не прошли контроль, ВСЕ последующие ТС этого поставщика/номенклатуры будут проверяться индивидуально в течение N дней.

#### Логика `ПроверитьБлокировкуДляСозданияНнР()` (строки 2424-2536)

```
Проверка: есть ли активные записи в РС ЗаблокированныеРегистрацииУК?
  │
  ├─ Нет записей → Результат.ЕстьБлокировка = Ложь → OK
  │
  ├─ Есть записи с КачествоНеПринято БЕЗ промежуточного композита:
  │   → ЕстьБлокировка = Истина
  │   → "ТС заблокировано. Качество не принято. Создание НнР запрещено."
  │   → СТОП (Block)
  │
  └─ Есть записи с КачествоНеПринято/РПП С промежуточным композитом:
      → ЕстьПредупреждение = Истина
      → "ТС заблокировано. Продолжить создание НнР?"
      → Вопрос Да/Нет (Warn)
```

Промежуточный композит определяется через `РС гкс_ПоказателиУсиленногоКонтроляПоРегистрации` с `НазначениеИспользования = ПромежуточныйКомпозит`.

### 2.8.6 Алгоритм полного цикла блокировки

```
  ЭТАП 1: РЕГИСТРАЦИЯ (гкс_РегистрацияНаПЛК.ОбработкаПроведения)
  ─────────────────────────────────────────────────────────────────
  1.1 Вызов ЗарегистрироватьТранспортноеСредствоДляУсиленногоКонтроля()
  1.2 Проверка: уже зарегистрировано? → пропустить
  1.3 Получить Контрагент + Номенклатура из регистрации
  1.4 Найти первое ТС поставщика за сутки (ПерваяРегистрацияТСПоставщика)
  1.5 Записать в РС ТранспортныеСредстваПоставщикаУК (ЭтоПервоеТС?)
  1.6 Найти настройки УК по комбинации реквизитов
  1.7 Записать показатели + правила в РС
  1.8 Если НЕ первое ТС → ИнициализироватьГруппуТС()
      → Справочники.гкс_ГруппыТС.ОпределитьРегистрациюВГруппу()
      → РС гкс_СоставГруппТранспорта (привязка к группе)

  ЭТАП 2: ЛАБОРАТОРНЫЙ АНАЛИЗ (гкс_ЛабораторныйАнализ.ОбработкаПроведения)
  ─────────────────────────────────────────────────────────────────
  2.1 Обновить показатели в РС ПоказателиУК
  2.2 Определить состояние качества (Принято/НеПринято)
  2.3 ЗаполнитьЗаблокированныеРегистрацииУсиленныйКонтроль():

  2.4 ОбновитьЗаблокированныеТСПриЗавершенииЛА():
      Сценарий A (Принято) → разблокировка: Разблокировано = Истина

         показатели для заблокированных ТС

  ЭТАП 3: ПРОВЕРКА В АРМ (кнопка "На разгрузку")
  ─────────────────────────────────────────────────────────────────
  3.1 ПроверитьБлокировкуДляСозданияНнР(Регистрация)
  3.2 Чтение РС ЗаблокированныеРегистрацииУК

  4.3 Заблокированные ТС становятся доступны для НнР
```

## 3. Принципы формирования записей (REQ-2) [VERIFIED: PASS]

### 3.1 Когда создаются записи

Записи в РС `гкс_ЗаблокированныеРегистрацииУсиленныйКонтроль` создаются **при проведении документа «Лабораторный анализ»** (`гкс_ЛабораторныйАнализ`), если результаты анализа показывают отклонение от допустимых значений показателей, определённых в настройках усиленного контроля.

### 3.2 Двухканальная запись

Реализована **двухканальная модель** создания записей (строки 252-278 модуля `гкс_ВходнойКонтрольКачества`):

1. **Канал «Первое ТС»** (`ДокументРегистрации`) — блокировка привязывается к конкретному документу регистрации на ПЛК.
2. **Канал «Группа ТС»** (`БлокирующаяГруппаТС`) — блокировка привязывается к группе ТС (справочник `гкс_ГруппыТС`), что позволяет блокировать все последующие ТС в группе поставщика.

### 3.3 Структура записи

Каждая запись фиксирует:
- **Что заблокировано**: `ДокументРегистрации` — регистрация ТС, которую нельзя направить на разгрузку
- **Чем заблокировано**: `БлокирующаяРегистрация` + `БлокирующаяГруппаТС` — источник блокировки
- **По какому показателю**: `Показатель` — конкретный показатель анализа
- **С каким состоянием**: `БлокирующееСостояниеКачества` — текущее состояние качества блокирующего ТС
- **Снята ли блокировка**: `Разблокировано` (Boolean)

### 3.4 Принцип Optimistic Read-Modify-Write

Метод `ОбновитьСостояниеБлокировки` реализует паттерн оптимистичного обновления:
1. Читает текущий набор записей по фильтру измерений
2. Модифицирует ресурсы (состояние, флаг разблокировки)
3. Записывает обратно

### 3.5 Пакетная предзагрузка

Метод `ЗаполнитьЗаблокированныеРегистрации` использует пакетную предзагрузку с дедупликацией через `Соответствие` для минимизации обращений к БД при массовых операциях (АРМ отображает список всех ТС).

## 4. Принципы проверок и валидаций (REQ-3) [VERIFIED: PASS]

### 4.1 Трёхуровневая система проверки блокировки

Метод `ПроверитьБлокировкуДляСозданияНнР` (проверка перед созданием «Направления на разгрузку») реализует **3 уровня**:

| Уровень | Результат | Действие |
|---------|-----------|----------|
| **Block** (Блокировка) | Есть активные незакрытые блокировки | Создание НнР запрещено. Пользователь видит ошибку. |
| **Warn** (Предупреждение) | Есть блокировки, но они допускают продолжение с подтверждением | Пользователю выводится предупреждение, может продолжить. |
| **OK** | Блокировок нет или все разблокированы (`Разблокировано = Истина`) | Создание НнР разрешено без ограничений. |

### 4.2 Проверки при проведении документов

1. **Лабораторный анализ (проведение)**: проверяется, попадают ли результаты анализа в диапазоны настроек усиленного контроля (`ЗначениеПоказателяМин`..`ЗначениеПоказателяМакс`). Если да — создаются/обновляются записи блокировки для всех ТС, подпадающих под правило.

2. **Направление на разгрузку (проведение)**: проверяется наличие активных блокировок для данной регистрации. При принятии качества — записи разблокируются (`Разблокировано = Истина`).

3. **Регистрация на ПЛК (проведение)**: проверяется, не попадает ли ТС под действующие правила усиленного контроля.

### 4.3 Валидация настроек

Настройки усиленного контроля (`гкс_НастройкиУсиленногоКонтроляКачества`) валидируются:
- Обязательность заполнения ключевых измерений (вид перевозки, точка маршрута, номенклатура, показатель)
- Корректность диапазона (Мин <= Макс)
- Непересечение периодов действия правил
- Корректность количества ТС (> 0)

## 7. АРМ гкс_ПриемкаТранспорта — центральный пульт управления (REQ-6) [VERIFIED: PASS]

### 7.1 Общая характеристика

- **Обработка:** `гкс_ПриемкаТранспорта` (АРМ "Приёмка и отгрузка на ПЛК")
- **ОсновнаяФорма:** 4002 строки, 199 методов, 7 дополнительных форм
- **Роль:** Единая точка входа для оператора ПЛК — весь жизненный цикл ТС от въезда до приёмки проходит через этот АРМ

### 7.2 Жизненный цикл ТС в АРМ (State Machine)

АРМ реализует **state machine с 13 состояниями**. Правая панель кнопок соответствует этапам процесса. Метод `ОбновитьКнопки` (строки 2280-2343) переключает доступность кнопок по текущему состоянию регистрации:

```
  КНОПКА АРМ              СОСТОЯНИЕ              БЛОКИРОВКА ВЛИЯЕТ?
  ─────────               ─────────              ──────────────────
  1. Редактировать        (любое)                Нет
  2. Въезд                Прибыл                 Нет
  3. Номер пробы          ГотовКОтборуПроб       Нет
  4. Принять пробы        ВзятыПробы             Нет
  5. Анализ               ПринятыПробы /         Нет (создание ЛА)
                          РезультатыПробПолучены  Но ЛА ТРИГГЕРИТ блокировку!
  6. На разгрузку         КачествоПринято /       ДА — КЛЮЧЕВАЯ ТОЧКА
                          КачествоНеПринято       Block/Warn/OK проверка
  7. Разгрузка            ВыгрузкаРазрешена      Нет (уже прошёл проверку)
  8. Отменить разрешение  ВыгрузкаРазрешена      Нет
  9. Выезд                Погружен/Выгружен      Нет
  10. Приемка             (финальное)             Нет
```

### 7.3 Точки влияния блокировки в жизненном цикле

#### Точка 1: Результаты анализа — ТРИГГЕР блокировки (этап 5 "Анализ")

Когда оператор создаёт и проводит `гкс_ЛабораторныйАнализ` из АРМ:
- Если результаты отклоняются от настроек усиленного контроля → создаются записи блокировки
- В колонке **"УК"** (усиленный контроль) появляется иконка ⚠ у заблокированных ТС
- Блокируется не только текущее ТС, но и все последующие ТС в группе поставщика

#### Точка 2: Направление на разгрузку — GATE (этап 6 "На разгрузку")

Метод `РедактироватьНаправлениеНаРазгрузку` (строки 374-413):

```
Пользователь нажимает "На разгрузку"
  │
  ├─ Одиночная регистрация:
  │     РезультатБлокировки = ПроверитьБлокировкуДляСозданияНнР()
  │       │
  │       ├─ ЕстьБлокировка = Истина → СТОП: сообщение, кнопка заблокирована
  │       ├─ ЕстьПредупреждение = Истина → Вопрос "Да/Нет"
  │       │     ├─ Да → ОткрытьФормуНаправленияНаРазгрузку()
  │       │     └─ Нет → отмена
  │       └─ Нет блокировок → ОткрытьФормуНаправленияНаРазгрузку()
  │
  └─ Групповая обработка:
        КонтрольВыбранныхПоСостоянию(ВалидныеСостояния) → проверка
        Форма "ГрупповоеНаправлениеНаРазгрузку"
```

#### Точка 3: Отображение причины блокировки (панель "Детали")

Регион `ИнформацияОБлокировке` (строки 3899-4001) — **программно** создаётся при `ПриСозданииНаСервере`:

- `СоздатьЭлементыБлокировкиНаСервере()` — создаёт группу, декорацию (красный текст), гиперссылку на блокирующий ЛА
- Управляется ФО `гкс_ИспользоватьЗаблокированныеТС` — если выключена, элементы не создаются
- `ЗаполнитьИнформациюОБлокировке(ДокументРегистрации)` — при выборе строки в таблице вызывает `гкс_ВходнойКонтрольКачества.ПолучитьПричинуБлокировкиДляДеталей()` и показывает:
  - Текст причины блокировки (красный цвет)
  - Гиперссылка на блокирующий `гкс_ЛабораторныйАнализ` (клик открывает документ)

#### Точка 4: Пропуск контроля качества

Кнопка `ПропуститьКонтрольКачества` (строки 838-873):
- Видимость: только ЖД перевозка + ФО `гкс_ИспользоватьОтключениеВходногоКонтроляКачества`
- Доступность: роль `гкс_ПриемкаТранспортаБезВходногоКонтроля_ДобавлениеИзменение`
- Только для состояния `ГотовКОтборуПроб`
- Создаёт запись в РС `гкс_ПриемкаТранспортаБезВходногоКонтроля` и НнР

#### Точка 5: Доступность кнопки "На разгрузку" по состоянию

Для состояния `КачествоНеПринято` (строки 2121-2141):
```
Элементы.РедактироватьНаправлениеНаРазгрузку.Доступность =
    ДоступностьКнопкиНаправлениеНаРазгрузку(Регистрация, СтруктураДоступов)
```
Вызывает `НаправлятьНаРазгрузкуРазрешение` на сервере — проверяет наличие блокировок.
