# MCP CLI: ленивое обнаружение инструментов, сокращающее расход токенов на 99%

## Суть проблемы

Стандартная интеграция MCP-серверов работает по принципу «загрузить всё и сразу»: при старте сессии агент подключается к каждому настроенному серверу, вызывает `tools/list` и вставляет **полное описание каждого инструмента** (название, описание, JSON-схема параметров) в системный промпт. Одно описание инструмента занимает в среднем **550–850 токенов**. При 60 инструментах это даёт ~47 000 токенов чистых метаданных ещё до того, как пользователь задал первый вопрос.

Реальные замеры подтверждают масштаб катастрофы:

- Разработчик Scott Spence обнаружил **81 986 токенов**, съеденных MCP-инструментами до начала работы — 41% от 200K контекстного окна Claude.
- Docker MCP Server (135 инструментов) потребляет **125 964 токена** — 63% контекста.
- Stripe API (500+ операций) просто не помещается в контекстное окно целиком.
- GitHub Copilot ввёл жёсткий лимит в 128 MCP-инструментов; Cursor ограничивает ~40.

Помимо прямого расхода токенов, исследования показывают, что **LLM чаще выбирает неправильный инструмент при увеличении числа вариантов**, растёт «галлюцинация» параметров, а из-за проблемы «потери внимания в середине» (lost in the middle) инструменты из центра длинного списка определений систематически игнорируются. Рекомендация практиков: не более **10–15 инструментов одновременно** для надёжной работы агента.

Ирония в том, что чем мощнее MCP-настройка, тем хуже работает агент.

## Что такое MCP CLI

**MCP CLI (`mcp-cli`)** — это лёгкая утилита командной строки, созданная **Филиппом Шмидом** (Philipp Schmid, Staff Engineer в Google DeepMind, ранее — Technical Lead в Hugging Face). Проект опубликован в январе 2026 года.

**Репозиторий:** [github.com/philschmid/mcp-cli](https://github.com/philschmid/mcp-cli)

- Язык: TypeScript на runtime Bun
- Компилируется в **единый кроссплатформенный бинарник**
- Лицензия: MIT
- ~**867 звёзд** на GitHub, 92 форка
- Текущая версия: **v0.3.0**

Ключевая идея: вместо загрузки всех определений инструментов в контекст агента при старте, mcp-cli предоставляет агенту три узкие CLI-команды, которые он вызывает **только по мере необходимости**.

## Как это работает: три шага вместо одного гигантского

### Старый подход (eager loading)

```
Агент запускается → Системный промпт получает 47 000 токенов описаний всех 60 инструментов
→ Каждый запрос к API дорожает → Место для рассуждений сокращается
```

### Новый подход MCP CLI (lazy loading)

Системный промпт агента содержит только инструкцию: «Если тебе нужен инструмент, используй утилиту mcp-cli для поиска и получения информации о нём» — это ~**400 токенов** вместо 47 000.

Три команды:

1. **`mcp-cli info`** — выводит список всех серверов и названий инструментов (без схем, без описаний). Это «оглавление» — стоит минимум токенов.

2. **`mcp-cli info <сервер> <инструмент>`** или **`mcp-cli grep "<паттерн>"`** — загружает полную JSON-схему конкретного инструмента или ищет по всем серверам по glob-паттерну. Агент получает только то, что ему реально нужно.

3. **`mcp-cli call <сервер> <инструмент> '{...}'`** — выполняет вызов инструмента с JSON-аргументами и возвращает результат.

### Пример рабочего процесса

Задача: «Проанализируй данные в файле report.csv»

| Шаг | Команда | Что получает агент |
|-----|---------|-------------------|
| 1. Поиск | `mcp-cli grep file` | Короткий список: `filesystem/read_file`, `filesystem/write_file` |
| 2. Схема | `mcp-cli info filesystem read_file` | JSON-схема: принимает `path: string`, возвращает содержимое файла |
| 3. Вызов | `mcp-cli call filesystem read_file '{"path":"report.csv"}'` | Содержимое файла |

Три маленьких точных шага вместо одного гигантского и слепого.

**Экономия: 99% сокращение** расхода токенов на MCP-метаданные (47 000 → 400).

## Архитектура и надёжность

### Пул соединений через lazy-spawn демон

При первом обращении к серверу mcp-cli запускает фоновый демон, который **держит соединение открытым 60 секунд** (настраивается через `MCP_DAEMON_TIMEOUT`). Последующие вызовы к тому же серверу переиспользуют это соединение, устраняя повторные задержки на запуск. Каждый MCP-сервер получает свой собственный демон.

### Worker pool

Для команд, затрагивающих все серверы (листинг, grep), используется **пул воркеров** с настраиваемым параллелизмом (по умолчанию 5, через `MCP_CONCURRENCY`). Это защита от ситуации, когда агент пытается запросить 100 инструментов одновременно.

### Экспоненциальный backoff

Сетевые ошибки (`ECONNREFUSED`, `ETIMEDOUT`, `ECONNRESET`) и HTTP-ошибки (502, 503, 504, 429) автоматически повторяются до 3 раз с нарастающей задержкой (1с → 2с → 4с). Невосстановимые ошибки (авторизация, валидация, конфигурация) немедленно завершаются с структурированным сообщением.

### Коды выхода

| Код | Значение |
|-----|---------|
| 0 | Успех |
| 1 | Ошибка клиента |
| 2 | Ошибка сервера |
| 3 | Ошибка сети |

### Конфигурация

Единый формат `mcp_servers.json`, совместимый с Claude Desktop, Gemini CLI и VS Code. Поддерживаются:

- **Локальные серверы** (stdio, запускаются как подпроцессы) — для файловой системы, локальных БД
- **Удалённые серверы** (HTTP/SSE) — для внешних API (Notion, GitHub, и т.д.)
- Подстановка переменных окружения `${VAR}`
- Цепочка резолюции: текущая директория → домашняя → `~/.config/mcp/`
- Фильтрация инструментов через `allowedTools` / `disabledTools` (поддержка glob-паттернов)

## Компромисс: задержка vs. экономия

Главный вопрос: не меняем ли мы проблему стоимости на проблему задержки?

### Аргументы «за» lazy loading

- Демон пула соединений устраняет повторную задержку на запуск сервера после первого обращения
- Ответы `tools/list` — это статические, кэшируемые данные; задержка измеряется миллисекундами
- Без lazy loading агент теряет ~25% эффективного пространства для рассуждений в 200K-окне
- Это приводит к более частой компрессии контекста, потере истории диалога и снижению качества анализа
- Точность выбора инструментов растёт: с 49% до 74% (данные Anthropic для Opus 4)

### Когда lazy loading НЕ нужен

- Простые агенты с 2–3 инструментами: статическая загрузка добавляет минимальный overhead
- Значение mcp-cli растёт с количеством серверов: становится существенным от ~20–30 инструментов и трансформирующим от 60+

## Альтернативные решения: что ещё есть на рынке

### Anthropic MCP Tool Search (встроен в Claude Code, январь 2026)

Активируется автоматически, когда определения инструментов превышают 10% контекста. Использует regex + BM25 поиск. Результат: **85% сокращение токенов** (77K → 8.7K), точность выбора инструментов: 49% → 74% на Opus 4. Самое простое решение для пользователей Claude Code, но привязано к платформе.

### Anthropic Code Execution approach

MCP-инструменты представляются как файловые API; агент пишет TypeScript для их вызова. Сокращение: **98.7%** (150K → 2K токенов). Требует sandbox-среду для выполнения кода.

### Speakeasy Dynamic Toolsets

Гибридный подход: прогрессивная + семантическая загрузка. Заявлено **96% среднее сокращение** токенов при 100% успешности задач на наборах до 400 инструментов.

### lazy-mcp (voicetreelab)

MCP-прокси, выставляющий два мета-инструмента: `get_tools_in_category` и `execute_tool`. Агент навигирует по иерархическому дереву доступных инструментов.

### Amp Agent Skills

Навыки (skills) + lazy loading. При старте агент видит только описания навыков; полные определения инструментов загружаются при активации навыка. chrome-devtools: с 26 инструментов (17K токенов) до 4 (1.5K токенов).

### Apify mcpc (январь 2026)

CLI-клиент с полной поддержкой OAuth 2.1, персистентными сессиями, прокси-sandboxing для enterprise.

### OpenMCP — tree partitioning схем

Борьба с раздутостью схем внутри отдельных инструментов: Stripe POST-операция (10K токенов) разбивается на раскрываемые сегменты.

### Предложения на уровне протокола

- **SEP-1576** (Huawei) — дедупликация схем через JSON `$ref`, адаптивный контроль опциональных полей, embedding-based matching для поиска инструментов
- **Discussion #532** — иерархическое управление инструментами: новые методы `tools/categories` и `tools/discover`

### Инфраструктурные решения

- **Docker MCP Catalog** — централизованное обнаружение инструментов
- **Microsoft mcp-gateway** — session-aware маршрутизация в Kubernetes
- **IBM ContextForge**, **Lunar.dev MCPX**, **Solo.io Agent Gateway** — enterprise-уровень

## Практическое руководство: когда что использовать

**Менее 15 инструментов** — проблема, возможно, не требует решения. Стандартная загрузка добавляет приемлемый overhead.

**15–60 инструментов, Claude Code** — встроенный MCP Tool Search (85% сокращение, нулевая настройка) может быть достаточен.

**15–60 инструментов, кросс-агентная совместимость** — mcp-cli заполняет эту нишу: единый бинарник, работает с любым агентом, имеющим доступ к shell.

**60+ инструментов, enterprise** — gateway-решения (ContextForge, Speakeasy, Docker MCP Catalog) предлагают более продвинутую маршрутизацию и governance.

## Будущее: от ленивого к предиктивному

Текущий подход mcp-cli решает проблему «библиотекаря, который таскает на себе все книги». Но теперь библиотекарь бегает к полке за каждой отдельной книгой. Следующий шаг — **предиктивная загрузка**:

- **Интеллектуальное кэширование** — кэширование схем часто используемых инструментов между вызовами (уже частично реализовано через демон)
- **Предварительная загрузка** — анализ контекста разговора для предсказания, какие инструменты понадобятся следующими
- **Построение цепочек вызовов** — оптимизация для многошаговых задач, где агенту нужно быстро скомбинировать десятки инструментов
- **Иерархическое управление** — на уровне протокола MCP, через предложения вроде SEP-1576

Более широкий тренд очевиден: паттерн «загрузить всё при старте», который доминировал при первоначальном внедрении MCP, систематически заменяется по всей экосистеме. Число инструментов, которые агент может эффективно использовать, ограничено не протоколом MCP, а **контекстным окном** — и любой серьёзный MCP-деплоймент рано или поздно придёт к необходимости lazy loading стратегии.
