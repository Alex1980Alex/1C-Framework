# Справочник по хукам (Hooks)

> Справочник по событиям хуков Claude Code, схеме конфигурации, форматам входных/выходных JSON-данных, кодам завершения, асинхронным хукам, промпт-хукам и хукам MCP-инструментов.

<Tip>
  Для краткого руководства с примерами см. [Автоматизация рабочих процессов с помощью хуков](/en/hooks-guide).
</Tip>

Хуки (hooks) — это пользовательские shell-команды или LLM-промпты, которые автоматически выполняются в определённых точках жизненного цикла Claude Code. Используйте этот справочник для поиска схем событий, параметров конфигурации, форматов входных/выходных JSON-данных и продвинутых возможностей, таких как асинхронные хуки и хуки MCP-инструментов. Если вы настраиваете хуки впервые, начните с [руководства](/en/hooks-guide).

## Жизненный цикл хуков

Хуки срабатывают в определённых точках во время сессии Claude Code. Когда событие срабатывает и matcher совпадает, Claude Code передаёт JSON-контекст о событии в ваш обработчик хука. Для командных хуков данные поступают через stdin. Ваш обработчик может затем проанализировать входные данные, выполнить действие и опционально вернуть решение. Некоторые события срабатывают один раз за сессию, тогда как другие срабатывают многократно внутри агентного цикла:

Таблица ниже описывает, когда срабатывает каждое событие. Раздел [События хуков](#события-хуков) содержит полную схему входных данных и параметры управления для каждого из них.

| Событие              | Когда срабатывает                                                    |
| :------------------- | :------------------------------------------------------------------- |
| `SessionStart`       | При начале или возобновлении сессии                                  |
| `UserPromptSubmit`   | При отправке промпта пользователем, до обработки Claude              |
| `PreToolUse`         | Перед выполнением вызова инструмента. Может заблокировать его        |
| `PermissionRequest`  | При появлении диалога запроса разрешений                             |
| `PostToolUse`        | После успешного выполнения вызова инструмента                        |
| `PostToolUseFailure` | После неудачного выполнения вызова инструмента                       |
| `Notification`       | При отправке уведомления Claude Code                                 |
| `SubagentStart`      | При порождении субагента                                             |
| `SubagentStop`       | При завершении субагента                                             |
| `Stop`               | Когда Claude завершает ответ                                         |
| `TeammateIdle`       | Когда участник [команды агентов](/en/agent-teams) собирается уйти в простой |
| `TaskCompleted`      | Когда задача помечается как выполненная                               |
| `PreCompact`         | Перед компактификацией контекста                                      |
| `SessionEnd`         | При завершении сессии                                                 |

### Как разрешается хук

Чтобы увидеть, как эти элементы работают вместе, рассмотрим хук `PreToolUse`, блокирующий деструктивные shell-команды. Хук запускает `block-rm.sh` перед каждым вызовом инструмента Bash:

```json  theme={null}
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/block-rm.sh"
          }
        ]
      }
    ]
  }
}
```

Скрипт читает JSON-входные данные из stdin, извлекает команду и возвращает `permissionDecision` со значением `"deny"`, если она содержит `rm -rf`:

```bash  theme={null}
#!/bin/bash
# .claude/hooks/block-rm.sh
COMMAND=$(jq -r '.tool_input.command')

if echo "$COMMAND" | grep -q 'rm -rf'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "Destructive command blocked by hook"
    }
  }'
else
  exit 0  # разрешить команду
fi
```

Допустим, Claude Code решает выполнить `Bash "rm -rf /tmp/build"`. Вот что происходит:

<Steps>
  <Step title="Событие срабатывает">
    Срабатывает событие `PreToolUse`. Claude Code отправляет входные данные инструмента в формате JSON на stdin хука:

    ```json  theme={null}
    { "tool_name": "Bash", "tool_input": { "command": "rm -rf /tmp/build" }, ... }
    ```
  </Step>

  <Step title="Проверка matcher">
    Matcher `"Bash"` совпадает с именем инструмента, поэтому `block-rm.sh` запускается. Если matcher опущен или указан `"*"`, хук выполняется при каждом возникновении события. Хуки пропускаются только когда matcher определён и не совпадает.
  </Step>

  <Step title="Обработчик хука выполняется">
    Скрипт извлекает `"rm -rf /tmp/build"` из входных данных и находит `rm -rf`, поэтому выводит решение в stdout:

    ```json  theme={null}
    {
      "hookSpecificOutput": {
        "hookEventName": "PreToolUse",
        "permissionDecision": "deny",
        "permissionDecisionReason": "Destructive command blocked by hook"
      }
    }
    ```

    Если бы команда была безопасной (например, `npm test`), скрипт выполнил бы `exit 0`, что сообщает Claude Code разрешить вызов инструмента без дополнительных действий.
  </Step>

  <Step title="Claude Code действует по результату">
    Claude Code читает JSON-решение, блокирует вызов инструмента и показывает Claude причину.
  </Step>
</Steps>

Раздел [Конфигурация](#конфигурация) ниже описывает полную схему, а каждый раздел [событий хуков](#события-хуков) документирует, какие входные данные получает ваша команда и какой вывод она может вернуть.

## Конфигурация

Хуки определяются в JSON-файлах настроек. Конфигурация имеет три уровня вложенности:

1. Выберите [событие хука](#события-хуков), на которое нужно реагировать, например `PreToolUse` или `Stop`
2. Добавьте [группу matcher](#паттерны-matcher) для фильтрации, когда хук срабатывает, например «только для инструмента Bash»
3. Определите один или несколько [обработчиков хуков](#поля-обработчика-хука) для выполнения при совпадении

См. [Как разрешается хук](#как-разрешается-хук) выше для полного пошагового разбора с аннотированным примером.

<Note>
  На этой странице используются конкретные термины для каждого уровня: **событие хука** для точки жизненного цикла, **группа matcher** для фильтра, и **обработчик хука** для shell-команды, промпта или агента, который выполняется. «Хук» сам по себе относится к общей функциональности.
</Note>

### Расположение хуков

Где вы определяете хук — определяет его область действия:

| Расположение                                               | Область действия              | Можно делиться                     |
| :--------------------------------------------------------- | :---------------------------- | :--------------------------------- |
| `~/.claude/settings.json`                                  | Все ваши проекты              | Нет, локально на вашей машине      |
| `.claude/settings.json`                                    | Один проект                   | Да, можно закоммитить в репозиторий |
| `.claude/settings.local.json`                              | Один проект                   | Нет, в gitignore                   |
| Managed policy settings                                    | Вся организация               | Да, управляется администратором    |
| [Plugin](/en/plugins) `hooks/hooks.json`                   | Когда плагин включён          | Да, в составе плагина              |
| [Skill](/en/skills) или [agent](/en/sub-agents) frontmatter | Пока компонент активен        | Да, определяется в файле компонента |

Подробнее о разрешении файлов настроек см. [настройки](/en/settings). Администраторы организаций могут использовать `allowManagedHooksOnly` для блокировки пользовательских, проектных и плагинных хуков. См. [Конфигурация хуков](/en/settings#hook-configuration).

### Паттерны matcher

Поле `matcher` — это строка регулярного выражения, фильтрующая, когда хуки срабатывают. Используйте `"*"`, `""` или полностью опустите `matcher`, чтобы совпадать со всеми случаями. Каждый тип события фильтрует по своему полю:

| Событие                                                                | Что фильтрует matcher         | Примеры значений matcher                                                       |
| :--------------------------------------------------------------------- | :---------------------------- | :----------------------------------------------------------------------------- |
| `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest` | имя инструмента               | `Bash`, `Edit\|Write`, `mcp__.*`                                               |
| `SessionStart`                                                         | способ запуска сессии          | `startup`, `resume`, `clear`, `compact`                                        |
| `SessionEnd`                                                           | причина завершения сессии      | `clear`, `logout`, `prompt_input_exit`, `bypass_permissions_disabled`, `other` |
| `Notification`                                                         | тип уведомления               | `permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`       |
| `SubagentStart`                                                        | тип агента                    | `Bash`, `Explore`, `Plan` или пользовательские имена агентов                   |
| `PreCompact`                                                           | что вызвало компактификацию   | `manual`, `auto`                                                               |
| `SubagentStop`                                                         | тип агента                    | те же значения, что и `SubagentStart`                                          |
| `UserPromptSubmit`, `Stop`, `TeammateIdle`, `TaskCompleted`            | matcher не поддерживается     | всегда срабатывает при каждом случае                                           |

Matcher — это регулярное выражение, поэтому `Edit|Write` совпадает с любым из инструментов, а `Notebook.*` совпадает с любым инструментом, начинающимся с Notebook. Matcher применяется к полю из [JSON-входных данных](#входные-и-выходные-данные-хуков), которые Claude Code отправляет вашему хуку через stdin. Для событий инструментов это поле `tool_name`. Каждый раздел [событий хуков](#события-хуков) перечисляет полный набор значений matcher и схему входных данных для этого события.

Этот пример запускает скрипт линтинга только когда Claude записывает или редактирует файл:

```json  theme={null}
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "/path/to/lint-check.sh"
          }
        ]
      }
    ]
  }
}
```

`UserPromptSubmit` и `Stop` не поддерживают matcher и всегда срабатывают при каждом случае. Если вы добавите поле `matcher` к этим событиям, оно будет молча проигнорировано.

#### Сопоставление MCP-инструментов

Инструменты [MCP](/en/mcp)-серверов отображаются как обычные инструменты в событиях (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`), поэтому вы можете фильтровать их так же, как и любое другое имя инструмента.

MCP-инструменты следуют паттерну именования `mcp__<server>__<tool>`, например:

* `mcp__memory__create_entities`: инструмент создания сущностей сервера Memory
* `mcp__filesystem__read_file`: инструмент чтения файлов сервера Filesystem
* `mcp__github__search_repositories`: инструмент поиска сервера GitHub

Используйте регулярные выражения для нацеливания на конкретные MCP-инструменты или группы:

* `mcp__memory__.*` — совпадает со всеми инструментами сервера `memory`
* `mcp__.*__write.*` — совпадает с любым инструментом, содержащим «write», от любого сервера

Этот пример логирует все операции сервера memory и валидирует операции записи от любого MCP-сервера:

```json  theme={null}
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "mcp__memory__.*",
        "hooks": [
          {
            "type": "command",
            "command": "echo 'Memory operation initiated' >> ~/mcp-operations.log"
          }
        ]
      },
      {
        "matcher": "mcp__.*__write.*",
        "hooks": [
          {
            "type": "command",
            "command": "/home/user/scripts/validate-mcp-write.py"
          }
        ]
      }
    ]
  }
}
```

### Поля обработчика хука

Каждый объект во внутреннем массиве `hooks` — это обработчик хука: shell-команда, LLM-промпт или агент, который выполняется при совпадении matcher. Существует три типа:

* **[Командные хуки](#поля-командного-хука)** (`type: "command"`): запускают shell-команду. Ваш скрипт получает [JSON-входные данные](#входные-и-выходные-данные-хуков) события через stdin и передаёт результаты обратно через коды завершения и stdout.
* **[Промпт-хуки](#поля-промпт-и-агент-хуков)** (`type: "prompt"`): отправляют промпт модели Claude для однократной оценки. Модель возвращает решение да/нет в формате JSON. См. [Промпт-хуки](#промпт-хуки).
* **[Агент-хуки](#поля-промпт-и-агент-хуков)** (`type: "agent"`): порождают субагента, который может использовать инструменты Read, Grep и Glob для проверки условий перед возвратом решения. См. [Агент-хуки](#агент-хуки).

#### Общие поля

Эти поля применяются ко всем типам хуков:

| Поле            | Обязательно | Описание                                                                                                                                          |
| :-------------- | :---------- | :------------------------------------------------------------------------------------------------------------------------------------------------ |
| `type`          | да          | `"command"`, `"prompt"` или `"agent"`                                                                                                             |
| `timeout`       | нет         | Секунды до отмены. По умолчанию: 600 для command, 30 для prompt, 60 для agent                                                                     |
| `statusMessage` | нет         | Пользовательское сообщение спиннера, отображаемое во время работы хука                                                                            |
| `once`          | нет         | Если `true`, выполняется только один раз за сессию, затем удаляется. Только для Skills, не для агентов. См. [Хуки в Skills и агентах](#хуки-в-skills-и-агентах) |

#### Поля командного хука

В дополнение к [общим полям](#общие-поля), командные хуки принимают следующие поля:

| Поле      | Обязательно | Описание                                                                                                            |
| :-------- | :---------- | :------------------------------------------------------------------------------------------------------------------ |
| `command` | да          | Shell-команда для выполнения                                                                                        |
| `async`   | нет         | Если `true`, выполняется в фоне без блокировки. См. [Запуск хуков в фоне](#запуск-хуков-в-фоне)                      |

#### Поля промпт- и агент-хуков

В дополнение к [общим полям](#общие-поля), промпт- и агент-хуки принимают следующие поля:

| Поле     | Обязательно | Описание                                                                             |
| :------- | :---------- | :----------------------------------------------------------------------------------- |
| `prompt` | да          | Текст промпта для отправки модели. Используйте `$ARGUMENTS` как плейсхолдер для JSON-данных хука |
| `model`  | нет         | Модель для оценки. По умолчанию — быстрая модель                                     |

Все совпадающие хуки выполняются параллельно, а идентичные обработчики автоматически дедуплицируются. Обработчики выполняются в текущей директории с окружением Claude Code. Переменная окружения `$CLAUDE_CODE_REMOTE` устанавливается в `"true"` в удалённых веб-окружениях и не устанавливается в локальном CLI.

### Ссылки на скрипты по пути

Используйте переменные окружения для ссылки на скрипты хуков относительно корня проекта или плагина, независимо от рабочей директории при запуске хука:

* `$CLAUDE_PROJECT_DIR`: корень проекта. Оборачивайте в кавычки для обработки путей с пробелами.
* `${CLAUDE_PLUGIN_ROOT}`: корневая директория плагина, для скриптов, упакованных с [плагином](/en/plugins).

    ```json  theme={null}

        "PostToolUse": [
          {
            "matcher": "Write|Edit",
            "hooks": [
              {
                "type": "command",
    ```

    ```json  theme={null}

      "description": "Automatic code formatting",

          {
            "matcher": "Write|Edit",
            "hooks": [
              {
                "type": "command",
                "command": "${CLAUDE_PLUGIN_ROOT}/scripts/format.sh",
                "timeout": 30
              }
            ]
          }
        ]
      }
    }
    ```

    См. [справочник компонентов плагинов](/en/plugins-reference#hooks) для подробностей о создании хуков плагинов.
  </Tab>

### Хуки в Skills и агентах

Помимо файлов настроек и плагинов, хуки могут быть определены непосредственно в [Skills](/en/skills) и [субагентах](/en/sub-agents) с использованием frontmatter. Эти хуки ограничены жизненным циклом компонента и выполняются только когда этот компонент активен.

Поддерживаются все события хуков. Для субагентов хуки `Stop` автоматически преобразуются в `SubagentStop`, так как именно это событие срабатывает при завершении субагента.

Хуки используют тот же формат конфигурации, что и хуки из файлов настроек, но ограничены временем жизни компонента и очищаются при его завершении.

Этот Skill определяет хук `PreToolUse`, запускающий скрипт проверки безопасности перед каждой командой `Bash`:

```yaml  theme={null}
---
name: secure-operations
description: Perform operations with security checks
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "./scripts/security-check.sh"
---
```

Агенты используют тот же формат в своём YAML frontmatter.

### Меню `/hooks`

Введите `/hooks` в Claude Code для открытия интерактивного менеджера хуков, где вы можете просматривать, добавлять и удалять хуки без прямого редактирования файлов настроек. Для пошагового руководства см. [Настройка первого хука](/en/hooks-guide#set-up-your-first-hook).

Каждый хук в меню помечен префиксом в скобках, указывающим его источник:

* `[User]`: из `~/.claude/settings.json`
* `[Project]`: из `.claude/settings.json`
* `[Local]`: из `.claude/settings.local.json`
* `[Plugin]`: из `hooks/hooks.json` плагина, только для чтения

### Отключение или удаление хуков

Чтобы удалить хук, удалите его запись из JSON-файла настроек или используйте меню `/hooks` и выберите хук для удаления.

Чтобы временно отключить все хуки без их удаления, установите `"disableAllHooks": true` в файле настроек или используйте переключатель в меню `/hooks`. Невозможно отключить отдельный хук, сохранив его в конфигурации.

Прямые правки хуков в файлах настроек не вступают в силу немедленно. Claude Code захватывает снимок хуков при запуске и использует его на протяжении всей сессии. Это предотвращает вступление в силу вредоносных или случайных модификаций хуков посреди сессии без вашей проверки. Если хуки были изменены извне, Claude Code предупредит вас и потребует проверки в меню `/hooks` перед применением изменений.

## Входные и выходные данные хуков

Хуки получают JSON-данные через stdin и передают результаты через коды завершения, stdout и stderr. Этот раздел описывает поля и поведение, общие для всех событий. Раздел каждого события в [Событиях хуков](#события-хуков) содержит его конкретную схему входных данных и параметры управления.

### Общие поля входных данных

Все события хуков получают эти поля через stdin в формате JSON, в дополнение к специфичным для события полям, документированным в каждом разделе [событий хуков](#события-хуков):

| Поле              | Описание                                                                                                                                       |
| :---------------- | :--------------------------------------------------------------------------------------------------------------------------------------------- |
| `session_id`      | Идентификатор текущей сессии                                                                                                                   |
| `transcript_path` | Путь к JSON-файлу диалога                                                                                                                      |
| `cwd`             | Текущая рабочая директория при вызове хука                                                                                                     |
| `permission_mode` | Текущий [режим разрешений](/en/permissions#permission-modes): `"default"`, `"plan"`, `"acceptEdits"`, `"dontAsk"` или `"bypassPermissions"`     |
| `hook_event_name` | Имя сработавшего события                                                                                                                       |

Например, хук `PreToolUse` для команды Bash получает следующее на stdin:

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/home/user/.claude/projects/.../transcript.jsonl",
  "cwd": "/home/user/my-project",
  "permission_mode": "default",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": {
    "command": "npm test"
  }
}
```

Поля `tool_name` и `tool_input` специфичны для события. Каждый раздел [событий хуков](#события-хуков) документирует дополнительные поля для данного события.

### Выходные данные через код завершения

Код завершения вашей команды хука сообщает Claude Code, должно ли действие продолжиться, быть заблокировано или проигнорировано.

**Exit 0** означает успех. Claude Code анализирует stdout на наличие [JSON-полей вывода](#json-вывод). JSON-вывод обрабатывается только при exit 0. Для большинства событий stdout отображается только в подробном режиме (`Ctrl+O`). Исключения — `UserPromptSubmit` и `SessionStart`, где stdout добавляется как контекст, который Claude может видеть и использовать.

**Exit 2** означает блокирующую ошибку. Claude Code игнорирует stdout и любой JSON в нём. Вместо этого текст stderr передаётся Claude как сообщение об ошибке. Эффект зависит от события: `PreToolUse` блокирует вызов инструмента, `UserPromptSubmit` отклоняет промпт и т.д. Полный список см. в [поведении exit code 2](#поведение-exit-code-2-по-событиям).

**Любой другой код завершения** — это неблокирующая ошибка. stderr отображается в подробном режиме (`Ctrl+O`), выполнение продолжается.

Например, скрипт хука, блокирующий опасные Bash-команды:

```bash  theme={null}
#!/bin/bash
# Читает JSON-входные данные из stdin, проверяет команду
command=$(jq -r '.tool_input.command' < /dev/stdin)

if [[ "$command" == rm* ]]; then
  echo "Blocked: rm commands are not allowed" >&2
  exit 2  # Блокирующая ошибка: вызов инструмента предотвращён
fi

exit 0  # Успех: вызов инструмента продолжается
```

#### Поведение exit code 2 по событиям

Exit code 2 — это способ хука сигнализировать «стоп, не делай этого». Эффект зависит от события, поскольку некоторые события представляют действия, которые можно заблокировать (например, вызов инструмента, который ещё не произошёл), а другие представляют вещи, которые уже случились или не могут быть предотвращены.

| Событие хука         | Может блокировать? | Что происходит при exit 2                                          |
| :------------------- | :----------------- | :----------------------------------------------------------------- |
| `PreToolUse`         | Да                 | Блокирует вызов инструмента                                        |
| `PermissionRequest`  | Да                 | Отклоняет разрешение                                               |
| `UserPromptSubmit`   | Да                 | Блокирует обработку промпта и стирает промпт                       |
| `Stop`               | Да                 | Предотвращает остановку Claude, продолжает диалог                   |
| `SubagentStop`       | Да                 | Предотвращает остановку субагента                                  |
| `TeammateIdle`       | Да                 | Предотвращает переход участника в простой (участник продолжает работу) |
| `TaskCompleted`      | Да                 | Предотвращает пометку задачи как выполненной                        |
| `PostToolUse`        | Нет                | Показывает stderr Claude (инструмент уже выполнился)               |
| `PostToolUseFailure` | Нет                | Показывает stderr Claude (инструмент уже завершился с ошибкой)     |
| `Notification`       | Нет                | Показывает stderr только пользователю                              |
| `SubagentStart`      | Нет                | Показывает stderr только пользователю                              |
| `SessionStart`       | Нет                | Показывает stderr только пользователю                              |
| `SessionEnd`         | Нет                | Показывает stderr только пользователю                              |
| `PreCompact`         | Нет                | Показывает stderr только пользователю                              |

### JSON-вывод

Коды завершения позволяют разрешить или заблокировать, но JSON-вывод даёт более тонкий контроль. Вместо завершения с кодом 2 для блокировки, завершите с кодом 0 и выведите JSON-объект в stdout. Claude Code читает определённые поля из этого JSON для управления поведением, включая [управление решением](#управление-решением) для блокировки, разрешения или эскалации пользователю.

<Note>
  Вы должны выбрать один подход на хук, а не оба: либо используйте только коды завершения для сигнализации, либо завершайте с кодом 0 и выводите JSON для структурированного управления. Claude Code обрабатывает JSON только при exit 0. При exit 2 любой JSON игнорируется.
</Note>

Stdout вашего хука должен содержать только JSON-объект. Если ваш профиль shell выводит текст при запуске, это может помешать разбору JSON. См. [Ошибка валидации JSON](/en/hooks-guide#json-validation-failed) в руководстве по устранению неполадок.

JSON-объект поддерживает три вида полей:

* **Универсальные поля**, такие как `continue`, работают для всех событий. Они перечислены в таблице ниже.
* **`decision` и `reason` верхнего уровня** используются некоторыми событиями для блокировки или предоставления обратной связи.
* **`hookSpecificOutput`** — вложенный объект для событий, требующих более богатого контроля. Требует поле `hookEventName`, установленное в имя события.

| Поле             | По умолчанию | Описание                                                                                                                          |
| :--------------- | :----------- | :-------------------------------------------------------------------------------------------------------------------------------- |
| `continue`       | `true`       | Если `false`, Claude полностью прекращает обработку после выполнения хука. Имеет приоритет над любыми специфичными для события полями |
| `stopReason`     | нет          | Сообщение, показываемое пользователю, когда `continue` равно `false`. Не показывается Claude                                       |
| `suppressOutput` | `false`      | Если `true`, скрывает stdout из вывода подробного режима                                                                           |
| `systemMessage`  | нет          | Предупреждающее сообщение, показываемое пользователю                                                                               |

Чтобы полностью остановить Claude независимо от типа события:

```json  theme={null}
{ "continue": false, "stopReason": "Build failed, fix errors before continuing" }
```

#### Управление решением

Не каждое событие поддерживает блокировку или управление поведением через JSON. События, которые поддерживают, используют различные наборы полей для выражения решения. Используйте эту таблицу как быстрый справочник перед написанием хука:

| События                                                               | Паттерн решения            | Ключевые поля                                                     |
| :-------------------------------------------------------------------- | :------------------------- | :---------------------------------------------------------------- |
| UserPromptSubmit, PostToolUse, PostToolUseFailure, Stop, SubagentStop | `decision` верхнего уровня | `decision: "block"`, `reason`                                     |
| TeammateIdle, TaskCompleted                                           | Только код завершения      | Exit code 2 блокирует действие, stderr передаётся как обратная связь |
| PreToolUse                                                            | `hookSpecificOutput`       | `permissionDecision` (allow/deny/ask), `permissionDecisionReason` |
| PermissionRequest                                                     | `hookSpecificOutput`       | `decision.behavior` (allow/deny)                                  |

Примеры каждого паттерна в действии:

<Tabs>
  <Tab title="Decision верхнего уровня">
    Используется `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure`, `Stop` и `SubagentStop`. Единственное значение — `"block"`. Чтобы разрешить действие, опустите `decision` из JSON или завершите с кодом 0 без JSON вообще:

    ```json  theme={null}
    {
      "decision": "block",
      "reason": "Test suite must pass before proceeding"
    }
    ```
  </Tab>

  <Tab title="PreToolUse">
    Использует `hookSpecificOutput` для более богатого управления: разрешить, отклонить или эскалировать пользователю. Вы также можете изменить входные данные инструмента перед выполнением или добавить дополнительный контекст для Claude. См. [Управление решением PreToolUse](#управление-решением-pretooluse) для полного набора опций.

    ```json  theme={null}
    {
      "hookSpecificOutput": {
        "hookEventName": "PreToolUse",
        "permissionDecision": "deny",
        "permissionDecisionReason": "Database writes are not allowed"
      }
    }
    ```
  </Tab>

  <Tab title="PermissionRequest">
    Использует `hookSpecificOutput` для разрешения или отклонения запроса разрешений от имени пользователя. При разрешении вы также можете изменить входные данные инструмента или применить правила разрешений, чтобы пользователю больше не показывался запрос. См. [Управление решением PermissionRequest](#управление-решением-permissionrequest) для полного набора опций.

    ```json  theme={null}
    {
      "hookSpecificOutput": {
        "hookEventName": "PermissionRequest",
        "decision": {
          "behavior": "allow",
          "updatedInput": {
            "command": "npm run lint"
          }
        }
      }
    }
    ```
  </Tab>
</Tabs>

Расширенные примеры, включая валидацию Bash-команд, фильтрацию промптов и скрипты автоматического одобрения, см. в [Что можно автоматизировать](/en/hooks-guide#what-you-can-automate) руководства и [эталонной реализации валидатора Bash-команд](https://github.com/anthropics/claude-code/blob/main/examples/hooks/bash_command_validator_example.py).

## События хуков

Каждое событие соответствует точке в жизненном цикле Claude Code, где могут выполняться хуки. Разделы ниже упорядочены в соответствии с жизненным циклом: от настройки сессии через агентный цикл до завершения сессии. Каждый раздел описывает, когда событие срабатывает, какие matcher оно поддерживает, какие JSON-входные данные получает и как управлять поведением через вывод.

### SessionStart

Выполняется при запуске новой сессии Claude Code или возобновлении существующей. Полезен для загрузки контекста разработки, такого как существующие задачи или недавние изменения в кодовой базе, или настройки переменных окружения. Для статического контекста, не требующего скрипта, используйте [CLAUDE.md](/en/memory).

SessionStart выполняется при каждой сессии, поэтому делайте эти хуки быстрыми.

Значение matcher соответствует способу инициации сессии:

| Matcher   | Когда срабатывает                      |
| :-------- | :------------------------------------- |
| `startup` | Новая сессия                           |
| `resume`  | `--resume`, `--continue` или `/resume` |
| `clear`   | `/clear`                               |
| `compact` | Автоматическая или ручная компактификация |

#### Входные данные SessionStart

В дополнение к [общим полям входных данных](#общие-поля-входных-данных), хуки SessionStart получают `source`, `model` и опционально `agent_type`. Поле `source` указывает, как была запущена сессия: `"startup"` для новых сессий, `"resume"` для возобновлённых, `"clear"` после `/clear` или `"compact"` после компактификации. Поле `model` содержит идентификатор модели. Если вы запускаете Claude Code с `claude --agent <name>`, поле `agent_type` содержит имя агента.

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "SessionStart",
  "source": "startup",
  "model": "claude-sonnet-4-5-20250929"
}
```

#### Управление решением SessionStart

Любой текст, который ваш скрипт хука выводит в stdout, добавляется как контекст для Claude. В дополнение к [полям JSON-вывода](#json-вывод), доступным для всех хуков, вы можете вернуть следующие специфичные для события поля:

| Поле                | Описание                                                                  |
| :------------------ | :------------------------------------------------------------------------ |
| `additionalContext` | Строка, добавляемая в контекст Claude. Значения от нескольких хуков объединяются |

```json  theme={null}
{
  "hookSpecificOutput": {
    "hookEventName": "SessionStart",
    "additionalContext": "My additional context here"
  }
}
```

#### Сохранение переменных окружения

Хуки SessionStart имеют доступ к переменной окружения `CLAUDE_ENV_FILE`, которая предоставляет путь к файлу, куда можно сохранять переменные окружения для последующих Bash-команд.

Для установки отдельных переменных окружения записывайте инструкции `export` в `CLAUDE_ENV_FILE`. Используйте добавление (`>>`) для сохранения переменных, установленных другими хуками:

```bash  theme={null}
#!/bin/bash

if [ -n "$CLAUDE_ENV_FILE" ]; then
  echo 'export NODE_ENV=production' >> "$CLAUDE_ENV_FILE"
  echo 'export DEBUG_LOG=true' >> "$CLAUDE_ENV_FILE"
  echo 'export PATH="$PATH:./node_modules/.bin"' >> "$CLAUDE_ENV_FILE"
fi

exit 0
```

Для захвата всех изменений окружения от команд настройки сравните экспортированные переменные до и после:

```bash  theme={null}
#!/bin/bash

ENV_BEFORE=$(export -p | sort)

# Запустите команды настройки, изменяющие окружение
source ~/.nvm/nvm.sh
nvm use 20

if [ -n "$CLAUDE_ENV_FILE" ]; then
  ENV_AFTER=$(export -p | sort)
  comm -13 <(echo "$ENV_BEFORE") <(echo "$ENV_AFTER") >> "$CLAUDE_ENV_FILE"
fi

exit 0
```

Любые переменные, записанные в этот файл, будут доступны во всех последующих Bash-командах, которые Claude Code выполняет во время сессии.

<Note>
  `CLAUDE_ENV_FILE` доступен для хуков SessionStart. Другие типы хуков не имеют доступа к этой переменной.
</Note>

### UserPromptSubmit

Выполняется когда пользователь отправляет промпт, до его обработки Claude. Это позволяет добавить дополнительный контекст на основе промпта/диалога, валидировать промпты или блокировать определённые типы промптов.

#### Входные данные UserPromptSubmit

В дополнение к [общим полям входных данных](#общие-поля-входных-данных), хуки UserPromptSubmit получают поле `prompt`, содержащее текст, отправленный пользователем.

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "UserPromptSubmit",
  "prompt": "Write a function to calculate the factorial of a number"
}
```

#### Управление решением UserPromptSubmit

Хуки `UserPromptSubmit` могут управлять тем, обрабатывается ли промпт пользователя, и добавлять контекст. Доступны все [поля JSON-вывода](#json-вывод).

Есть два способа добавить контекст в диалог при exit code 0:

* **Текст в stdout**: любой не-JSON текст, записанный в stdout, добавляется как контекст
* **JSON с `additionalContext`**: используйте формат JSON ниже для большего контроля. Поле `additionalContext` добавляется как контекст

Текст stdout отображается как вывод хука в транскрипте. Поле `additionalContext` добавляется более незаметно.

Для блокировки промпта верните JSON-объект с `decision`, установленным в `"block"`:

| Поле                | Описание                                                                                                      |
| :------------------ | :------------------------------------------------------------------------------------------------------------ |
| `decision`          | `"block"` предотвращает обработку промпта и стирает его из контекста. Опустите для продолжения обработки        |
| `reason`            | Показывается пользователю при `decision` равном `"block"`. Не добавляется в контекст                           |
| `additionalContext` | Строка, добавляемая в контекст Claude                                                                          |

```json  theme={null}
{
  "decision": "block",
  "reason": "Explanation for decision",
  "hookSpecificOutput": {
    "hookEventName": "UserPromptSubmit",
    "additionalContext": "My additional context here"
  }
}
```

<Note>
  Формат JSON не обязателен для простых случаев. Для добавления контекста можно просто вывести текст в stdout с exit code 0. Используйте JSON, когда нужно блокировать промпты или требуется более структурированное управление.
</Note>

### PreToolUse

Выполняется после того, как Claude создаёт параметры инструмента, и перед обработкой вызова инструмента. Фильтрует по имени инструмента: `Bash`, `Edit`, `Write`, `Read`, `Glob`, `Grep`, `Task`, `WebFetch`, `WebSearch` и любые [имена MCP-инструментов](#сопоставление-mcp-инструментов).

Используйте [управление решением PreToolUse](#управление-решением-pretooluse) для разрешения, отклонения или запроса подтверждения на использование инструмента.

#### Входные данные PreToolUse

В дополнение к [общим полям входных данных](#общие-поля-входных-данных), хуки PreToolUse получают `tool_name`, `tool_input` и `tool_use_id`. Поля `tool_input` зависят от инструмента:

##### Bash

Выполняет shell-команды.

| Поле                | Тип     | Пример             | Описание                                        |
| :------------------ | :------ | :----------------- | :---------------------------------------------- |
| `command`           | string  | `"npm test"`       | Shell-команда для выполнения                    |
| `description`       | string  | `"Run test suite"` | Опциональное описание того, что делает команда  |
| `timeout`           | number  | `120000`           | Опциональный таймаут в миллисекундах            |
| `run_in_background` | boolean | `false`            | Выполнять ли команду в фоне                     |

##### Write

Создаёт или перезаписывает файл.

| Поле        | Тип    | Пример                | Описание                             |
| :---------- | :----- | :-------------------- | :----------------------------------- |
| `file_path` | string | `"/path/to/file.txt"` | Абсолютный путь к файлу для записи   |
| `content`   | string | `"file content"`      | Содержимое для записи в файл         |

##### Edit

Заменяет строку в существующем файле.

| Поле          | Тип     | Пример                | Описание                              |
| :------------ | :------ | :-------------------- | :------------------------------------ |
| `file_path`   | string  | `"/path/to/file.txt"` | Абсолютный путь к файлу для редактирования |
| `old_string`  | string  | `"original text"`     | Текст для поиска и замены             |
| `new_string`  | string  | `"replacement text"`  | Текст замены                          |
| `replace_all` | boolean | `false`               | Заменять ли все вхождения             |

##### Read

Читает содержимое файла.

| Поле        | Тип    | Пример                | Описание                                     |
| :---------- | :----- | :-------------------- | :------------------------------------------- |
| `file_path` | string | `"/path/to/file.txt"` | Абсолютный путь к файлу для чтения           |
| `offset`    | number | `10`                  | Опциональный номер строки начала чтения      |

#### Управление решением PreToolUse

Хуки `PreToolUse` могут управлять тем, продолжается ли вызов инструмента. В отличие от других хуков, использующих поле `decision` верхнего уровня, PreToolUse возвращает своё решение внутри объекта `hookSpecificOutput`. Это даёт более богатое управление: три исхода (разрешить, отклонить или запросить) плюс возможность изменить входные данные инструмента перед выполнением.

| Поле                       | Описание                                                                                                                                          |
| :------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------ |
| `permissionDecision`       | `"allow"` обходит систему разрешений, `"deny"` предотвращает вызов инструмента, `"ask"` предлагает пользователю подтвердить                       |
| `permissionDecisionReason` | Для `"allow"` и `"ask"` показывается пользователю, но не Claude. Для `"deny"` показывается Claude                                                |
| `updatedInput`             | Изменяет параметры входных данных инструмента перед выполнением. Комбинируйте с `"allow"` для автоодобрения или `"ask"` для показа изменённых данных |
| `additionalContext`        | Строка, добавляемая в контекст Claude перед выполнением инструмента                                                                               |

```json  theme={null}
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow",
    "permissionDecisionReason": "My reason here",
    "updatedInput": {
      "field_to_modify": "new value"
    },
    "additionalContext": "Current environment: production. Proceed with caution."
  }
}
```

<Note>
  PreToolUse ранее использовал поля `decision` и `reason` верхнего уровня, но они устарели для этого события. Используйте `hookSpecificOutput.permissionDecision` и `hookSpecificOutput.permissionDecisionReason` вместо них. Устаревшие значения `"approve"` и `"block"` соответствуют `"allow"` и `"deny"`. Другие события, такие как PostToolUse и Stop, продолжают использовать `decision` и `reason` верхнего уровня как актуальный формат.
</Note>

### PermissionRequest

Выполняется, когда пользователю показывается диалог запроса разрешений. Используйте [управление решением PermissionRequest](#управление-решением-permissionrequest) для разрешения или отклонения от имени пользователя.

Фильтрует по имени инструмента, те же значения, что и PreToolUse.

#### Входные данные PermissionRequest

Хуки PermissionRequest получают поля `tool_name` и `tool_input`, как и хуки PreToolUse, но без `tool_use_id`. Опциональный массив `permission_suggestions` содержит варианты «всегда разрешать», которые пользователь обычно видит в диалоге разрешений. Различие в том, когда хук срабатывает: хуки PermissionRequest выполняются, когда диалог разрешений вот-вот будет показан пользователю, тогда как хуки PreToolUse выполняются перед вызовом инструмента независимо от статуса разрешений.

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "PermissionRequest",
  "tool_name": "Bash",
  "tool_input": {
    "command": "rm -rf node_modules",
    "description": "Remove node_modules directory"
  },
  "permission_suggestions": [
    { "type": "toolAlwaysAllow", "tool": "Bash" }
  ]
}
```

#### Управление решением PermissionRequest

Хуки `PermissionRequest` могут разрешить или отклонить запросы разрешений. В дополнение к [полям JSON-вывода](#json-вывод), доступным для всех хуков, ваш скрипт хука может вернуть объект `decision` с этими специфичными для события полями:

| Поле                 | Описание                                                                                                          |
| :------------------- | :---------------------------------------------------------------------------------------------------------------- |
| `behavior`           | `"allow"` предоставляет разрешение, `"deny"` отклоняет его                                                        |
| `updatedInput`       | Только для `"allow"`: изменяет параметры входных данных инструмента перед выполнением                              |
| `updatedPermissions` | Только для `"allow"`: применяет обновления правил разрешений, эквивалентно выбору пользователем варианта «всегда разрешать» |
| `message`            | Только для `"deny"`: сообщает Claude, почему разрешение было отклонено                                             |
| `interrupt`          | Только для `"deny"`: если `true`, останавливает Claude                                                            |

```json  theme={null}
{
  "hookSpecificOutput": {
    "hookEventName": "PermissionRequest",
    "decision": {
      "behavior": "allow",
      "updatedInput": {
        "command": "npm run lint"
      }
    }
  }
}
```

### PostToolUse

Выполняется сразу после успешного завершения инструмента.

Фильтрует по имени инструмента, те же значения, что и PreToolUse.

#### Входные данные PostToolUse

Хуки `PostToolUse` срабатывают после того, как инструмент уже успешно выполнился. Входные данные включают как `tool_input` (аргументы, отправленные инструменту), так и `tool_response` (результат, который он вернул). Точная схема обоих зависит от инструмента.

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "PostToolUse",
  "tool_name": "Write",
  "tool_input": {
    "file_path": "/path/to/file.txt",
    "content": "file content"
  },
  "tool_response": {
    "filePath": "/path/to/file.txt",
    "success": true
  },
  "tool_use_id": "toolu_01ABC123..."
}
```

#### Управление решением PostToolUse

Хуки `PostToolUse` могут предоставить обратную связь Claude после выполнения инструмента. В дополнение к [полям JSON-вывода](#json-вывод), доступным для всех хуков, ваш скрипт хука может вернуть следующие специфичные для события поля:

| Поле                   | Описание                                                                                   |
| :--------------------- | :----------------------------------------------------------------------------------------- |
| `decision`             | `"block"` уведомляет Claude с указанием `reason`. Опустите для продолжения                  |
| `reason`               | Объяснение, показываемое Claude при `decision` равном `"block"`                              |
| `additionalContext`    | Дополнительный контекст для рассмотрения Claude                                             |
| `updatedMCPToolOutput` | Только для [MCP-инструментов](#сопоставление-mcp-инструментов): заменяет вывод инструмента  |

```json  theme={null}
{
  "decision": "block",
  "reason": "Explanation for decision",
  "hookSpecificOutput": {
    "hookEventName": "PostToolUse",
    "additionalContext": "Additional information for Claude"
  }
}
```

### PostToolUseFailure

Выполняется при сбое выполнения инструмента. Это событие срабатывает для вызовов инструментов, которые выбрасывают ошибки или возвращают результаты сбоя. Используйте для логирования сбоев, отправки оповещений или предоставления корректирующей обратной связи Claude.

Фильтрует по имени инструмента, те же значения, что и PreToolUse.

#### Входные данные PostToolUseFailure

Хуки PostToolUseFailure получают те же поля `tool_name` и `tool_input`, что и PostToolUse, вместе с информацией об ошибке в полях верхнего уровня:

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "PostToolUseFailure",
  "tool_name": "Bash",
  "tool_input": {
    "command": "npm test",
    "description": "Run test suite"
  },
  "tool_use_id": "toolu_01ABC123...",
  "error": "Command exited with non-zero status code 1",
  "is_interrupt": false
}
```

| Поле           | Описание                                                                    |
| :------------- | :-------------------------------------------------------------------------- |
| `error`        | Строка, описывающая, что пошло не так                                       |
| `is_interrupt` | Опциональный boolean, указывающий, был ли сбой вызван прерыванием пользователя |

#### Управление решением PostToolUseFailure

Хуки `PostToolUseFailure` могут предоставить контекст Claude после сбоя инструмента. В дополнение к [полям JSON-вывода](#json-вывод), доступным для всех хуков, ваш скрипт хука может вернуть следующие специфичные для события поля:

| Поле                | Описание                                                         |
| :------------------ | :--------------------------------------------------------------- |
| `additionalContext` | Дополнительный контекст для Claude для рассмотрения вместе с ошибкой |

```json  theme={null}
{
  "hookSpecificOutput": {
    "hookEventName": "PostToolUseFailure",
    "additionalContext": "Additional information about the failure for Claude"
  }
}
```

### Notification

Выполняется, когда Claude Code отправляет уведомления. Фильтрует по типу уведомления: `permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`. Опустите matcher для запуска хуков для всех типов уведомлений.

Используйте отдельные matcher для запуска разных обработчиков в зависимости от типа уведомления. Эта конфигурация запускает скрипт оповещения о разрешениях, когда Claude нуждается в одобрении разрешения, и другое уведомление, когда Claude находится в простое:

```json  theme={null}
{
  "hooks": {
    "Notification": [
      {
        "matcher": "permission_prompt",
        "hooks": [
          {
            "type": "command",
            "command": "/path/to/permission-alert.sh"
          }
        ]
      },
      {
        "matcher": "idle_prompt",
        "hooks": [
          {
            "type": "command",
            "command": "/path/to/idle-notification.sh"
          }
        ]
      }
    ]
  }
}
```

#### Входные данные Notification

В дополнение к [общим полям входных данных](#общие-поля-входных-данных), хуки Notification получают `message` с текстом уведомления, опциональный `title` и `notification_type`, указывающий, какой тип сработал.

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "Notification",
  "message": "Claude needs your permission to use Bash",
  "title": "Permission needed",
  "notification_type": "permission_prompt"
}
```

Хуки Notification не могут блокировать или изменять уведомления. В дополнение к [полям JSON-вывода](#json-вывод), доступным для всех хуков, вы можете вернуть `additionalContext` для добавления контекста в диалог:

| Поле                | Описание                             |
| :------------------ | :----------------------------------- |
| `additionalContext` | Строка, добавляемая в контекст Claude |

### SubagentStart

Выполняется, когда субагент Claude Code порождается через инструмент Task. Поддерживает matcher для фильтрации по имени типа агента (встроенные агенты, такие как `Bash`, `Explore`, `Plan`, или пользовательские имена агентов из `.claude/agents/`).

#### Входные данные SubagentStart

В дополнение к [общим полям входных данных](#общие-поля-входных-данных), хуки SubagentStart получают `agent_id` с уникальным идентификатором субагента и `agent_type` с именем агента (встроенные агенты, такие как `"Bash"`, `"Explore"`, `"Plan"`, или пользовательские имена агентов).

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "SubagentStart",
  "agent_id": "agent-abc123",
  "agent_type": "Explore"
}
```

Хуки SubagentStart не могут блокировать создание субагента, но могут внедрить контекст в субагент. В дополнение к [полям JSON-вывода](#json-вывод), доступным для всех хуков, вы можете вернуть:

| Поле                | Описание                                   |
| :------------------ | :----------------------------------------- |
| `additionalContext` | Строка, добавляемая в контекст субагента    |

```json  theme={null}
{
  "hookSpecificOutput": {

    "additionalContext": "Follow security guidelines for this task"
  }
}
```

### SubagentStop

Выполняется, когда субагент Claude Code завершил ответ. Фильтрует по типу агента, те же значения, что и SubagentStart.

#### Входные данные SubagentStop

В дополнение к [общим полям входных данных](#общие-поля-входных-данных), хуки SubagentStop получают `stop_hook_active`, `agent_id`, `agent_type` и `agent_transcript_path`. Поле `agent_type` используется для фильтрации matcher. `transcript_path` — это транскрипт основной сессии, тогда как `agent_transcript_path` — собственный транскрипт субагента, хранящийся во вложенной папке `subagents/`.

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "~/.claude/projects/.../abc123.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "SubagentStop",
  "stop_hook_active": false,
  "agent_id": "def456",
  "agent_type": "Explore",
  "agent_transcript_path": "~/.claude/projects/.../abc123/subagents/agent-def456.jsonl"
}
```

Хуки SubagentStop используют тот же формат управления решением, что и [хуки Stop](#управление-решением-stop).

### Stop

Выполняется, когда основной агент Claude Code завершил ответ. Не выполняется, если остановка произошла из-за прерывания пользователем.

#### Входные данные Stop

В дополнение к [общим полям входных данных](#общие-поля-входных-данных), хуки Stop получают `stop_hook_active`. Это поле равно `true`, когда Claude Code уже продолжает работу в результате хука Stop. Проверяйте это значение или обрабатывайте транскрипт, чтобы предотвратить бесконечную работу Claude Code.

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "~/.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "Stop",
  "stop_hook_active": true
}
```

#### Управление решением Stop

Хуки `Stop` и `SubagentStop` могут управлять тем, продолжает ли Claude работу. В дополнение к [полям JSON-вывода](#json-вывод), доступным для всех хуков, ваш скрипт хука может вернуть следующие специфичные для события поля:

| Поле       | Описание                                                                     |
| :--------- | :--------------------------------------------------------------------------- |
| `decision` | `"block"` предотвращает остановку Claude. Опустите для разрешения остановки   |
| `reason`   | Обязательно при `decision` равном `"block"`. Сообщает Claude, почему он должен продолжить |

```json  theme={null}
{
  "decision": "block",
  "reason": "Must be provided when Claude is blocked from stopping"
}
```

### TeammateIdle

Выполняется, когда участник [команды агентов](/en/agent-teams) собирается уйти в простой после завершения своего хода. Используйте для обеспечения контрольных точек качества перед остановкой работы участника, таких как требование пройти проверку линтером или подтверждение существования выходных файлов.

Когда хук `TeammateIdle` завершается с кодом 2, участник получает сообщение stderr как обратную связь и продолжает работу вместо перехода в простой. Хуки TeammateIdle не поддерживают matcher и срабатывают при каждом случае.

#### Входные данные TeammateIdle

В дополнение к [общим полям входных данных](#общие-поля-входных-данных), хуки TeammateIdle получают `teammate_name` и `team_name`.

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "TeammateIdle",
  "teammate_name": "researcher",
  "team_name": "my-project"
}
```

| Поле            | Описание                                           |
| :-------------- | :------------------------------------------------- |
| `teammate_name` | Имя участника, который собирается уйти в простой   |
| `team_name`     | Имя команды                                         |

#### Управление решением TeammateIdle

Хуки TeammateIdle используют только коды завершения, а не JSON-управление решением. Этот пример проверяет существование артефакта сборки перед разрешением участнику уйти в простой:

```bash  theme={null}
#!/bin/bash

if [ ! -f "./dist/output.js" ]; then
  echo "Build artifact missing. Run the build before stopping." >&2
  exit 2
fi

exit 0
```

### TaskCompleted

Выполняется, когда задача помечается как выполненная. Это происходит в двух ситуациях: когда любой агент явно помечает задачу как выполненную через инструмент TaskUpdate, или когда участник [команды агентов](/en/agent-teams) завершает свой ход с незавершёнными задачами. Используйте для обеспечения критериев завершения, таких как прохождение тестов или проверок линтером, перед закрытием задачи.

Когда хук `TaskCompleted` завершается с кодом 2, задача не помечается как выполненная, и сообщение stderr передаётся модели как обратная связь. Хуки TaskCompleted не поддерживают matcher и срабатывают при каждом случае.

#### Входные данные TaskCompleted

В дополнение к [общим полям входных данных](#общие-поля-входных-данных), хуки TaskCompleted получают `task_id`, `task_subject` и опционально `task_description`, `teammate_name` и `team_name`.

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "TaskCompleted",
  "task_id": "task-001",
  "task_subject": "Implement user authentication",
  "task_description": "Add login and signup endpoints",
  "teammate_name": "implementer",
  "team_name": "my-project"
}
```

| Поле               | Описание                                                   |
| :----------------- | :--------------------------------------------------------- |
| `task_id`          | Идентификатор выполняемой задачи                            |
| `task_subject`     | Название задачи                                             |
| `task_description` | Подробное описание задачи. Может отсутствовать              |
| `teammate_name`    | Имя участника, завершающего задачу. Может отсутствовать     |
| `team_name`        | Имя команды. Может отсутствовать                            |

#### Управление решением TaskCompleted

Хуки TaskCompleted используют только коды завершения, а не JSON-управление решением. Этот пример запускает тесты и блокирует завершение задачи при их сбое:

```bash  theme={null}
#!/bin/bash
INPUT=$(cat)
TASK_SUBJECT=$(echo "$INPUT" | jq -r '.task_subject')

# Запуск набора тестов
if ! npm test 2>&1; then
  echo "Tests not passing. Fix failing tests before completing: $TASK_SUBJECT" >&2
  exit 2
fi

exit 0
```

### PreCompact

Выполняется перед тем, как Claude Code запустит операцию компактификации.

Значение matcher указывает, была ли компактификация запущена вручную или автоматически:

| Matcher  | Когда срабатывает                            |
| :------- | :------------------------------------------- |
| `manual` | `/compact`                                   |
| `auto`   | Авто-компактификация при заполнении контекстного окна |

#### Входные данные PreCompact

В дополнение к [общим полям входных данных](#общие-поля-входных-данных), хуки PreCompact получают `trigger` и `custom_instructions`. Для `manual` `custom_instructions` содержит то, что пользователь передал в `/compact`. Для `auto` `custom_instructions` пусто.

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "PreCompact",
  "trigger": "manual",
  "custom_instructions": ""
}
```

### SessionEnd

Выполняется при завершении сессии Claude Code. Полезен для задач очистки, логирования статистики сессии или сохранения состояния сессии. Поддерживает matcher для фильтрации по причине завершения.

Поле `reason` во входных данных хука указывает, почему сессия завершилась:

| Причина                       | Описание                                           |
| :---------------------------- | :------------------------------------------------- |
| `clear`                       | Сессия очищена командой `/clear`                   |
| `logout`                      | Пользователь вышел из системы                       |
| `prompt_input_exit`           | Пользователь вышел при отображении ввода промпта   |
| `bypass_permissions_disabled` | Режим обхода разрешений был отключён                |
| `other`                       | Другие причины выхода                               |

#### Входные данные SessionEnd

В дополнение к [общим полям входных данных](#общие-поля-входных-данных), хуки SessionEnd получают поле `reason`, указывающее, почему сессия завершилась. Все значения см. в [таблице причин](#sessionend) выше.

```json  theme={null}
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "SessionEnd",
  "reason": "other"
}
```

Хуки SessionEnd не имеют управления решением. Они не могут блокировать завершение сессии, но могут выполнять задачи очистки.

## Промпт-хуки

В дополнение к хукам Bash-команд (`type: "command"`), Claude Code поддерживает промпт-хуки (`type: "prompt"`), использующие LLM для оценки того, разрешить или заблокировать действие. Промпт-хуки работают со следующими событиями: `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop` и `TaskCompleted`. `TeammateIdle` не поддерживает промпт- и агент-хуки.

### Как работают промпт-хуки

Вместо выполнения Bash-команды промпт-хуки:

1. Отправляют входные данные хука и ваш промпт модели Claude, по умолчанию Haiku
2. LLM отвечает структурированным JSON, содержащим решение
3. Claude Code автоматически обрабатывает решение

### Конфигурация промпт-хуков

Установите `type` в `"prompt"` и предоставьте строку `prompt` вместо `command`. Используйте плейсхолдер `$ARGUMENTS` для вставки JSON-входных данных хука в текст промпта. Claude Code отправляет объединённый промпт и входные данные быстрой модели Claude, которая возвращает JSON-решение.

Этот хук `Stop` просит LLM оценить, выполнены ли все задачи, прежде чем разрешить Claude завершить работу:

```json  theme={null}
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "prompt",
            "prompt": "Evaluate if Claude should stop: $ARGUMENTS. Check if all tasks are complete."
          }
        ]
      }
    ]
  }
}
```

| Поле      | Обязательно | Описание                                                                                                                                                         |
| :-------- | :---------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`    | да          | Должно быть `"prompt"`                                                                                                                                           |
| `prompt`  | да          | Текст промпта для отправки LLM. Используйте `$ARGUMENTS` как плейсхолдер для JSON-входных данных хука. Если `$ARGUMENTS` отсутствует, JSON добавляется к промпту |
| `model`   | нет         | Модель для оценки. По умолчанию — быстрая модель                                                                                                                 |
| `timeout` | нет         | Таймаут в секундах. По умолчанию: 30                                                                                                                             |

### Схема ответа

LLM должен ответить JSON, содержащим:

```json  theme={null}
{
  "ok": true | false,
  "reason": "Explanation for the decision"
}
```

| Поле     | Описание                                                           |
| :------- | :----------------------------------------------------------------- |
| `ok`     | `true` разрешает действие, `false` предотвращает его               |
| `reason` | Обязательно при `ok` равном `false`. Объяснение, показываемое Claude |

### Пример: многокритериальный хук Stop

Этот хук `Stop` использует детальный промпт для проверки трёх условий перед разрешением Claude остановиться. Если `"ok"` равно `false`, Claude продолжает работу, используя предоставленную причину как следующую инструкцию. Хуки `SubagentStop` используют тот же формат для оценки, должен ли [субагент](/en/sub-agents) остановиться:

```json  theme={null}
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "prompt",
            "prompt": "You are evaluating whether Claude should stop working. Context: $ARGUMENTS\n\nAnalyze the conversation and determine if:\n1. All user-requested tasks are complete\n2. Any errors need to be addressed\n3. Follow-up work is needed\n\nRespond with JSON: {\"ok\": true} to allow stopping, or {\"ok\": false, \"reason\": \"your explanation\"} to continue working.",
            "timeout": 30
          }
        ]
      }
    ]
  }
}
```

## Агент-хуки

Агент-хуки (`type: "agent"`) подобны промпт-хукам, но с многоходовым доступом к инструментам. Вместо одного вызова LLM, агент-хук порождает субагента, который может читать файлы, искать код и проверять кодовую базу для верификации условий. Агент-хуки поддерживают те же события, что и промпт-хуки.

### Как работают агент-хуки

Когда агент-хук срабатывает:

1. Claude Code порождает субагента с вашим промптом и JSON-входными данными хука
2. Субагент может использовать инструменты Read, Grep и Glob для исследования
3. После до 50 ходов субагент возвращает структурированное решение `{ "ok": true/false }`
4. Claude Code обрабатывает решение так же, как промпт-хук

Агент-хуки полезны, когда верификация требует проверки реальных файлов или результатов тестов, а не только оценки входных данных хука.

### Конфигурация агент-хуков

Установите `type` в `"agent"` и предоставьте строку `prompt`. Поля конфигурации такие же, как у [промпт-хуков](#конфигурация-промпт-хуков), с более длительным таймаутом по умолчанию:

| Поле      | Обязательно | Описание                                                                             |
| :-------- | :---------- | :----------------------------------------------------------------------------------- |
| `type`    | да          | Должно быть `"agent"`                                                                |
| `prompt`  | да          | Промпт, описывающий, что нужно проверить. Используйте `$ARGUMENTS` как плейсхолдер   |
| `model`   | нет         | Модель для использования. По умолчанию — быстрая модель                               |
| `timeout` | нет         | Таймаут в секундах. По умолчанию: 60                                                  |

Схема ответа та же, что у промпт-хуков: `{ "ok": true }` для разрешения или `{ "ok": false, "reason": "..." }` для блокировки.

Этот хук `Stop` проверяет, что все юнит-тесты проходят, перед разрешением Claude завершить работу:

```json  theme={null}
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "agent",
            "prompt": "Verify that all unit tests pass. Run the test suite and check the results. $ARGUMENTS",
            "timeout": 120
          }
        ]
      }
    ]
  }
}
```

## Запуск хуков в фоне

По умолчанию хуки блокируют выполнение Claude до своего завершения. Для длительных задач, таких как деплой, наборы тестов или вызовы внешних API, установите `"async": true` для запуска хука в фоне, пока Claude продолжает работу. Асинхронные хуки не могут блокировать или управлять поведением Claude: поля ответа, такие как `decision`, `permissionDecision` и `continue`, не действуют, поскольку действие, которое они бы контролировали, уже завершилось.

### Настройка асинхронного хука

Добавьте `"async": true` в конфигурацию командного хука для запуска в фоне без блокировки Claude. Это поле доступно только для хуков `type: "command"`.

Этот хук запускает скрипт тестирования после каждого вызова инструмента `Write`. Claude продолжает работу немедленно, пока `run-tests.sh` выполняется до 120 секунд. Когда скрипт завершается, его вывод доставляется на следующем ходе диалога:

```json  theme={null}
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write",
        "hooks": [
          {
            "type": "command",
            "command": "/path/to/run-tests.sh",
            "async": true,
            "timeout": 120
          }
        ]
      }
    ]
  }
}
```

Поле `timeout` устанавливает максимальное время в секундах для фонового процесса. Если не указано, асинхронные хуки используют тот же 10-минутный таймаут по умолчанию, что и синхронные хуки.

### Как выполняются асинхронные хуки

Когда асинхронный хук срабатывает, Claude Code запускает процесс хука и немедленно продолжает, не дожидаясь его завершения. Хук получает те же JSON-входные данные через stdin, что и синхронный хук.

После завершения фонового процесса, если хук создал JSON-ответ с полем `systemMessage` или `additionalContext`, это содержимое доставляется Claude как контекст на следующем ходе диалога.

### Пример: запуск тестов после изменения файлов

Этот хук запускает набор тестов в фоне всякий раз, когда Claude записывает файл, затем сообщает результаты Claude по завершении тестов. Сохраните этот скрипт в `.claude/hooks/run-tests-async.sh` в вашем проекте и сделайте его исполняемым с `chmod +x`:

```bash  theme={null}
#!/bin/bash
# run-tests-async.sh

# Чтение входных данных хука из stdin
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

# Запуск тестов только для исходных файлов
if [[ "$FILE_PATH" != *.ts && "$FILE_PATH" != *.js ]]; then
  exit 0
fi

# Запуск тестов и отчёт через systemMessage
RESULT=$(npm test 2>&1)
EXIT_CODE=$?

if [ $EXIT_CODE -eq 0 ]; then
  echo "{\"systemMessage\": \"Tests passed after editing $FILE_PATH\"}"
else
  echo "{\"systemMessage\": \"Tests failed after editing $FILE_PATH: $RESULT\"}"
fi
```

Затем добавьте эту конфигурацию в `.claude/settings.json` в корне вашего проекта. Флаг `async: true` позволяет Claude продолжать работу, пока тесты выполняются:

```json  theme={null}
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/run-tests-async.sh",
            "async": true,
            "timeout": 300
          }
        ]
      }
    ]
  }
}
```

### Ограничения асинхронных хуков

Асинхронные хуки имеют несколько ограничений по сравнению с синхронными хуками:

* Только хуки `type: "command"` поддерживают `async`. Промпт-хуки не могут выполняться асинхронно.
* Асинхронные хуки не могут блокировать вызовы инструментов или возвращать решения. К моменту завершения хука инициирующее действие уже продолжилось.
* Вывод хука доставляется на следующем ходе диалога. Если сессия бездействует, ответ ждёт следующего взаимодействия пользователя.
* Каждое выполнение создаёт отдельный фоновый процесс. Дедупликация между множественными срабатываниями одного асинхронного хука не производится.

## Соображения безопасности

### Отказ от ответственности

Хуки выполняются с полными правами вашего системного пользователя.

<Warning>
  Хуки выполняют shell-команды с вашими полными пользовательскими правами. Они могут изменять, удалять или получать доступ к любым файлам, к которым имеет доступ ваша учётная запись. Проверяйте и тестируйте все команды хуков перед добавлением их в конфигурацию.
</Warning>

### Лучшие практики безопасности

Учитывайте эти практики при написании хуков:

* **Валидируйте и санируйте входные данные**: никогда не доверяйте входным данным слепо
* **Всегда экранируйте shell-переменные**: используйте `"$VAR"`, а не `$VAR`
* **Блокируйте обход путей**: проверяйте наличие `..` в путях файлов
* **Используйте абсолютные пути**: указывайте полные пути к скриптам, используя `"$CLAUDE_PROJECT_DIR"` для корня проекта
* **Пропускайте чувствительные файлы**: избегайте `.env`, `.git/`, ключей и т.д.

## Отладка хуков

Запустите `claude --debug` для просмотра деталей выполнения хуков, включая информацию о том, какие хуки совпали, их коды завершения и вывод. Переключите подробный режим с помощью `Ctrl+O` для просмотра прогресса хуков в транскрипте.

# Автоматизация рабочих процессов с помощью хуков

> Запускайте shell-команды автоматически, когда Claude Code редактирует файлы, завершает задачи или требует ввода. Форматируйте код, отправляйте уведомления, валидируйте команды и обеспечивайте соблюдение правил проекта.

Хуки (hooks) — это пользовательские shell-команды, которые выполняются в определённых точках жизненного цикла Claude Code. Они обеспечивают детерминированный контроль над поведением Claude Code, гарантируя, что определённые действия всегда происходят, вместо того чтобы полагаться на то, что LLM выберет их выполнить. Используйте хуки для обеспечения правил проекта, автоматизации рутинных задач и интеграции Claude Code с вашими существующими инструментами.

Для решений, требующих суждения, а не детерминированных правил, вы также можете использовать [промпт-хуки](#промпт-хуки) или [агент-хуки](#агент-хуки), которые используют модель Claude для оценки условий.

Для других способов расширения Claude Code см. [Skills](/en/skills) для предоставления Claude дополнительных инструкций и исполняемых команд, [субагенты](/en/sub-agents) для выполнения задач в изолированных контекстах и [плагины](/en/plugins) для упаковки расширений для совместного использования между проектами.

<Tip>
  Это руководство охватывает распространённые варианты использования и начало работы. Для полных схем событий, форматов JSON-вывода и продвинутых функций, таких как асинхронные хуки и хуки MCP-инструментов, см. [Справочник по хукам](#справочник-по-хукам-hooks).
</Tip>

## Настройка первого хука

Самый быстрый способ создать хук — через интерактивное меню `/hooks` в Claude Code. Это пошаговое руководство создаёт хук для уведомлений на рабочем столе, чтобы вы получали оповещение, когда Claude ожидает вашего ввода, вместо постоянного наблюдения за терминалом.

<Steps>
  <Step title="Откройте меню хуков">
    Введите `/hooks` в CLI Claude Code. Вы увидите список всех доступных событий хуков, а также опцию отключения всех хуков. Каждое событие соответствует точке в жизненном цикле Claude, где вы можете выполнять пользовательский код. Выберите `Notification` для создания хука, который срабатывает, когда Claude требует вашего внимания.
  </Step>

  <Step title="Настройте matcher">
    Меню показывает список matcher, которые фильтруют, когда хук срабатывает. Установите matcher в `*` для срабатывания на все типы уведомлений. Позже вы можете сузить его, изменив matcher на конкретное значение, например `permission_prompt` или `idle_prompt`.
  </Step>

  <Step title="Добавьте команду">
    Выберите `+ Add new hook...`. Меню запросит shell-команду для выполнения при срабатывании события. Хуки выполняют любую shell-команду, которую вы укажете, поэтому вы можете использовать встроенный инструмент уведомлений вашей платформы. Скопируйте команду для вашей ОС:

    <Tabs>
      <Tab title="macOS">
        Использует [`osascript`](https://ss64.com/mac/osascript.html) для запуска нативного уведомления macOS через AppleScript:

        ```
        osascript -e 'display notification "Claude Code needs your attention" with title "Claude Code"'
        ```
      </Tab>

      <Tab title="Linux">
        Использует `notify-send`, предустановленный на большинстве Linux-десктопов с демоном уведомлений:

        ```
        notify-send 'Claude Code' 'Claude Code needs your attention'
        ```
      </Tab>

      <Tab title="Windows (PowerShell)">
        Использует PowerShell для показа нативного окна сообщения через .NET Windows Forms:

        ```
        powershell.exe -Command "[System.Reflection.Assembly]::LoadWithPartialName('System.Windows.Forms'); [System.Windows.Forms.MessageBox]::Show('Claude Code needs your attention', 'Claude Code')"
        ```
      </Tab>
    </Tabs>
  </Step>

  <Step title="Выберите место хранения">
    Меню спрашивает, куда сохранить конфигурацию хука. Выберите `User settings` для сохранения в `~/.claude/settings.json`, что применит хук ко всем вашим проектам. Также можно выбрать `Project settings` для ограничения области действия текущим проектом. Все доступные области см. в [Расположение хуков](#расположение-хуков).
  </Step>

  <Step title="Протестируйте хук">
    Нажмите `Esc` для возврата в CLI. Попросите Claude сделать что-то, требующее разрешения, затем переключитесь с терминала. Вы должны получить уведомление на рабочем столе.
  </Step>
</Steps>

### Уведомления при ожидании ввода

Этот хук использует событие `Notification`, которое срабатывает, когда Claude ожидает ввода или разрешения. Каждая вкладка ниже использует нативную команду уведомлений платформы. ### Автоформатирование кода после редактирования

Автоматический запуск [Prettier](https://prettier.io/) для каждого файла, который Claude редактирует, для поддержания единообразного форматирования без ручного вмешательства.

Этот хук использует событие `PostToolUse` с matcher `Edit|Write`, поэтому он выполняется только после инструментов редактирования файлов. Команда извлекает путь к отредактированному файлу с помощью [`jq`](https://jqlang.github.io/jq/) и передаёт его Prettier. Добавьте это в `.claude/settings.json` в корне проекта:

```json  theme={null}
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

<Note>
  Примеры Bash на этой странице используют `jq` для разбора JSON. Установите его с помощью `brew install jq` (macOS), `apt-get install jq` (Debian/Ubuntu) или см. [загрузки `jq`](https://jqlang.github.io/jq/download/).
</Note>

### Блокировка редактирования защищённых файлов

Предотвратите модификацию Claude чувствительных файлов, таких как `.env`, `package-lock.json` или что-либо в `.git/`. Claude получает обратную связь, объясняющую, почему редактирование было заблокировано, чтобы он мог скорректировать свой подход.

Этот пример использует отдельный файл скрипта, который вызывает хук. Скрипт проверяет целевой путь файла по списку защищённых паттернов и завершается с кодом 2 для блокировки редактирования.

<Steps>
  <Step title="Создайте скрипт хука">
    Сохраните это в `.claude/hooks/protect-files.sh`:

    ```bash  theme={null}
    #!/bin/bash
    # protect-files.sh

    INPUT=$(cat)
    FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

    PROTECTED_PATTERNS=(".env" "package-lock.json" ".git/")

    for pattern in "${PROTECTED_PATTERNS[@]}"; do
      if [[ "$FILE_PATH" == *"$pattern"* ]]; then
        echo "Blocked: $FILE_PATH matches protected pattern '$pattern'" >&2
        exit 2
      fi
    done

    exit 0
    ```
  </Step>

  <Step title="Сделайте скрипт исполняемым (macOS/Linux)">
    Скрипты хуков должны быть исполняемыми для запуска Claude Code:

    ```bash  theme={null}
    chmod +x .claude/hooks/protect-files.sh
    ```
  </Step>

  <Step title="Зарегистрируйте хук">
    Добавьте хук `PreToolUse` в `.claude/settings.json`, который запускает скрипт перед любым вызовом инструмента `Edit` или `Write`:

    ```json  theme={null}
    {
      "hooks": {
        "PreToolUse": [
          {
            "matcher": "Edit|Write",
            "hooks": [
              {
                "type": "command",
                "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh"
              }
            ]
          }
        ]
      }
    }
    ```
  </Step>
</Steps>

### Повторное внедрение контекста после компактификации

Когда контекстное окно Claude заполняется, компактификация сжимает диалог для освобождения места. Это может привести к потере важных деталей. Используйте хук `SessionStart` с matcher `compact` для повторного внедрения критического контекста после каждой компактификации.

Любой текст, который ваша команда выводит в stdout, добавляется в контекст Claude. Этот пример напоминает Claude о соглашениях проекта и текущей работе. Добавьте это в `.claude/settings.json` в корне проекта:

```json  theme={null}
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "compact",
        "hooks": [
          {
            "type": "command",
            "command": "echo 'Reminder: use Bun, not npm. Run bun test before committing. Current sprint: auth refactor.'"
          }
        ]
      }
    ]
  }
}
```

Вы можете заменить `echo` любой командой, производящей динамический вывод, например `git log --oneline -5` для показа недавних коммитов. Для внедрения контекста при каждом старте сессии рассмотрите использование [CLAUDE.md](/en/memory). Для переменных окружения см. [`CLAUDE_ENV_FILE`](#сохранение-переменных-окружения) в справочнике.

## Как работают хуки

События хуков срабатывают в определённых точках жизненного цикла Claude Code. Когда событие срабатывает, все совпадающие хуки выполняются параллельно, а идентичные команды хуков автоматически дедуплицируются. Таблица ниже показывает каждое событие и когда оно срабатывает:

| Событие              | Когда срабатывает                                                    |
| :------------------- | :------------------------------------------------------------------- |
| `SessionStart`       | При начале или возобновлении сессии                                  |
| `UserPromptSubmit`   | При отправке промпта, до обработки Claude                            |
| `PreToolUse`         | Перед выполнением вызова инструмента. Может заблокировать            |
| `PermissionRequest`  | При появлении диалога разрешений                                     |
| `PostToolUse`        | После успешного выполнения инструмента                               |
| `PostToolUseFailure` | После неудачного выполнения инструмента                              |
| `Notification`       | При отправке уведомления Claude Code                                 |
| `SubagentStart`      | При порождении субагента                                             |
| `SubagentStop`       | При завершении субагента                                             |
| `Stop`               | Когда Claude завершает ответ                                         |
| `TeammateIdle`       | Когда участник [команды агентов](/en/agent-teams) собирается уйти в простой |
| `TaskCompleted`      | Когда задача помечается как выполненная                               |
| `PreCompact`         | Перед компактификацией контекста                                      |
| `SessionEnd`         | При завершении сессии                                                 |

Каждый хук имеет `type`, определяющий способ выполнения. Большинство хуков используют `"type": "command"`, выполняющий shell-команду. Два других варианта используют модель Claude для принятия решений: `"type": "prompt"` для однократной оценки и `"type": "agent"` для многоходовой верификации с доступом к инструментам. Подробнее см. [Промпт-хуки](#промпт-хуки) и [Агент-хуки](#агент-хуки).

### Чтение входных данных и возврат вывода

Хуки взаимодействуют с Claude Code через stdin, stdout, stderr и коды завершения. Когда событие срабатывает, Claude Code передаёт специфичные для события данные в формате JSON на stdin вашего скрипта. Ваш скрипт читает эти данные, выполняет работу и сообщает Claude Code о дальнейших действиях через код завершения.

#### Входные данные хука

Каждое событие включает общие поля, такие как `session_id` и `cwd`, но каждый тип события добавляет свои данные. Например, когда Claude запускает команду Bash, хук `PreToolUse` получает на stdin что-то подобное:

```json  theme={null}
{
  "session_id": "abc123",          // уникальный ID этой сессии
  "cwd": "/Users/sarah/myproject", // рабочая директория при срабатывании события
  "hook_event_name": "PreToolUse", // какое событие вызвало этот хук
  "tool_name": "Bash",             // инструмент, который Claude собирается использовать
  "tool_input": {                  // аргументы, переданные Claude инструменту
    "command": "npm test"          // для Bash это shell-команда
  }
}
```

Ваш скрипт может разобрать этот JSON и действовать на основе любого из этих полей. Хуки `UserPromptSubmit` получают текст `prompt`, хуки `SessionStart` получают `source` (startup, resume, compact) и т.д. Общие поля см. в [Общих полях входных данных](#общие-поля-входных-данных) справочника, а специфичные для события схемы — в разделе каждого события.

#### Выходные данные хука

Ваш скрипт сообщает Claude Code о дальнейших действиях, записывая в stdout или stderr и завершаясь с определённым кодом. Например, хук `PreToolUse`, желающий заблокировать команду:

```bash  theme={null}
#!/bin/bash
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command')

if echo "$COMMAND" | grep -q "drop table"; then
  echo "Blocked: dropping tables is not allowed" >&2  # stderr становится обратной связью Claude
  exit 2                                               # exit 2 = заблокировать действие
fi

exit 0  # exit 0 = разрешить продолжение
```

Код завершения определяет, что происходит дальше:

* **Exit 0**: действие продолжается. Для хуков `UserPromptSubmit` и `SessionStart` всё, что вы записали в stdout, добавляется в контекст Claude.
* **Exit 2**: действие блокируется. Запишите причину в stderr, и Claude получит её как обратную связь для корректировки.
* **Любой другой код завершения**: действие продолжается. stderr логируется, но не показывается Claude. Переключите подробный режим с помощью `Ctrl+O` для просмотра этих сообщений в транскрипте.

#### Структурированный JSON-вывод

Коды завершения дают два варианта: разрешить или заблокировать. Для большего контроля завершите с кодом 0 и выведите JSON-объект в stdout.

<Note>
  Используйте exit 2 для блокировки с сообщением stderr, или exit 0 с JSON для структурированного управления. Не смешивайте их: Claude Code игнорирует JSON при exit 2.
</Note>

Например, хук `PreToolUse` может отклонить вызов инструмента и сообщить Claude причину, или эскалировать его пользователю для одобрения:

```json  theme={null}
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Use rg instead of grep for better performance"
  }
}
```

Claude Code читает `permissionDecision` и отменяет вызов инструмента, затем передаёт `permissionDecisionReason` обратно Claude как обратную связь. Три варианта специфичны для `PreToolUse`:

* `"allow"`: продолжить без показа диалога разрешений
* `"deny"`: отменить вызов инструмента и отправить причину Claude
* `"ask"`: показать диалог разрешений пользователю как обычно

Другие события используют разные паттерны решений. Например, хуки `PostToolUse` и `Stop` используют поле `decision: "block"` верхнего уровня, а `PermissionRequest` использует `hookSpecificOutput.decision.behavior`. Полную разбивку по событиям см. в [таблице управления решением](#управление-решением) справочника.

Для хуков `UserPromptSubmit` используйте `additionalContext` для внедрения текста в контекст Claude. Промпт-хуки (`type: "prompt"`) обрабатывают вывод по-другому: см. [Промпт-хуки](#промпт-хуки).

### Фильтрация хуков с помощью matcher

Без matcher хук срабатывает при каждом возникновении своего события. Matcher позволяют сузить это. Например, если вы хотите запускать форматировщик только после редактирования файлов (не после каждого вызова инструмента), добавьте matcher к вашему хуку `PostToolUse`:

```json  theme={null}
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "prettier --write ..." }
        ]
      }
    ]
  }
}
```

Matcher `"Edit|Write"` — это паттерн регулярного выражения, совпадающий с именем инструмента. Хук срабатывает только когда Claude использует инструмент `Edit` или `Write`, а не при использовании `Bash`, `Read` или любого другого инструмента.

Каждый тип события фильтрует по определённому полю. Matcher поддерживают точные строки и паттерны регулярных выражений:

| Событие                                                                | Что фильтрует matcher         | Примеры значений matcher                                                       |
| :--------------------------------------------------------------------- | :---------------------------- | :----------------------------------------------------------------------------- |
| `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest` | имя инструмента               | `Bash`, `Edit\|Write`, `mcp__.*`                                               |
| `SessionStart`                                                         | способ запуска сессии          | `startup`, `resume`, `clear`, `compact`                                        |
| `SessionEnd`                                                           | причина завершения сессии      | `clear`, `logout`, `prompt_input_exit`, `bypass_permissions_disabled`, `other` |
| `Notification`                                                         | тип уведомления               | `permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`       |
| `SubagentStart`                                                        | тип агента                    | `Bash`, `Explore`, `Plan` или пользовательские имена агентов                   |
| `PreCompact`                                                           | что вызвало компактификацию   | `manual`, `auto`                                                               |
| `UserPromptSubmit`, `Stop`, `TeammateIdle`, `TaskCompleted`            | matcher не поддерживается     | всегда срабатывает при каждом случае                                           |
| `SubagentStop`                                                         | тип агента                    | те же значения, что и `SubagentStart`                                          |

Ещё несколько примеров с matcher для разных типов событий:

<Tabs>
  <Tab title="Логирование всех Bash-команд">
    Совпадение только с вызовами инструмента `Bash` и логирование каждой команды в файл. Событие `PostToolUse` срабатывает после завершения команды, поэтому `tool_input.command` содержит то, что было выполнено. Хук получает данные события в формате JSON на stdin, и `jq -r '.tool_input.command'` извлекает только строку команды, которая `>>` дописывает в файл лога:

    ```json  theme={null}
    {
      "hooks": {
        "PostToolUse": [
          {
            "matcher": "Bash",
            "hooks": [
              {
                "type": "command",
                "command": "jq -r '.tool_input.command' >> ~/.claude/command-log.txt"
              }
            ]
          }
        ]
      }
    }
    ```
  </Tab>

  <Tab title="Сопоставление MCP-инструментов">
    MCP-инструменты используют другое соглашение об именовании, чем встроенные инструменты: `mcp__<server>__<tool>`, где `<server>` — имя MCP-сервера, а `<tool>` — предоставляемый им инструмент. Например, `mcp__github__search_repositories` или `mcp__filesystem__read_file`. Используйте matcher с регулярным выражением для нацеливания на все инструменты конкретного сервера или совпадение между серверами с паттерном типа `mcp__.*__write.*`. Подробнее см. [Сопоставление MCP-инструментов](#сопоставление-mcp-инструментов) в справочнике.

    Команда ниже извлекает имя инструмента из JSON-входных данных хука с помощью `jq` и записывает в stderr, где оно отображается в подробном режиме (`Ctrl+O`):

    ```json  theme={null}
    {
      "hooks": {
        "PreToolUse": [
          {
            "matcher": "mcp__github__.*",
            "hooks": [
              {
                "type": "command",
                "command": "echo \"GitHub tool called: $(jq -r '.tool_name')\" >&2"
              }
            ]
          }
        ]
      }
    }
    ```
  </Tab>

  <Tab title="Очистка при завершении сессии">
    Событие `SessionEnd` поддерживает matcher по причине завершения сессии. Этот хук срабатывает только при `clear` (когда вы выполняете `/clear`), а не при нормальных выходах:

    ```json  theme={null}
    {
      "hooks": {
        "SessionEnd": [
          {
            "matcher": "clear",
            "hooks": [
              {
                "type": "command",
                "command": "rm -f /tmp/claude-scratch-*.txt"
              }
            ]
          }
        ]
      }
    }
    ```
  </Tab>
</Tabs>

Полный синтаксис matcher см. в [Справочнике по хукам](#паттерны-matcher).

### Расположение конфигурации хуков

Где вы добавляете хук — определяет его область действия:

| Расположение                                               | Область действия              | Можно делиться                     |
| :--------------------------------------------------------- | :---------------------------- | :--------------------------------- |
| `~/.claude/settings.json`                                  | Все ваши проекты              | Нет, локально на вашей машине      |
| `.claude/settings.json`                                    | Один проект                   | Да, можно закоммитить в репозиторий |
| `.claude/settings.local.json`                              | Один проект                   | Нет, в gitignore                   |
| Managed policy settings                                    | Вся организация               | Да, управляется администратором    |
| [Plugin](/en/plugins) `hooks/hooks.json`                   | Когда плагин включён          | Да, в составе плагина              |
| [Skill](/en/skills) или [agent](/en/sub-agents) frontmatter | Пока Skill или агент активен  | Да, определяется в файле компонента |

Вы также можете использовать [меню `/hooks`](#меню-hooks) в Claude Code для интерактивного добавления, удаления и просмотра хуков. Для отключения всех хуков сразу используйте переключатель внизу меню `/hooks` или установите `"disableAllHooks": true` в файле настроек.

Хуки, добавленные через меню `/hooks`, вступают в силу немедленно. Если вы редактируете файлы настроек напрямую во время работы Claude Code, изменения не вступят в силу до их проверки в меню `/hooks` или перезапуска сессии.

## Ограничения и устранение неполадок

### Ограничения

* Хуки взаимодействуют только через stdout, stderr и коды завершения. Они не могут запускать slash-команды или вызовы инструментов напрямую.
* Таймаут хука по умолчанию — 10 минут, настраиваемый для каждого хука полем `timeout` (в секундах).
* Хуки `PostToolUse` не могут отменить действия, так как инструмент уже выполнился.
* Хуки `PermissionRequest` не срабатывают в [неинтерактивном режиме](/en/headless) (`-p`). Используйте хуки `PreToolUse` для автоматизированных решений о разрешениях.
* Хуки `Stop` срабатывают каждый раз, когда Claude заканчивает ответ, а не только при завершении задачи. Они не срабатывают при прерываниях пользователем.

### Хук не срабатывает

Хук настроен, но никогда не выполняется.

* Запустите `/hooks` и убедитесь, что хук отображается под правильным событием
* Проверьте, что паттерн matcher точно совпадает с именем инструмента (matcher чувствительны к регистру)
* Убедитесь, что вы инициируете правильный тип события (например, `PreToolUse` срабатывает до выполнения инструмента, `PostToolUse` — после)
* Если используете хуки `PermissionRequest` в неинтерактивном режиме (`-p`), переключитесь на `PreToolUse`

### Ошибка хука в выводе

Вы видите сообщение типа «PreToolUse hook error: ...» в транскрипте.

* Ваш скрипт завершился с ненулевым кодом неожиданно. Протестируйте его вручную, передавая пример JSON:
  ```bash  theme={null}
  echo '{"tool_name":"Bash","tool_input":{"command":"ls"}}' | ./my-hook.sh
  echo $?  # Проверьте код завершения
  ```
* Если видите «command not found», используйте абсолютные пути или `$CLAUDE_PROJECT_DIR` для ссылки на скрипты
* Если видите «jq: command not found», установите `jq` или используйте Python/Node.js для разбора JSON
* Если скрипт вообще не запускается, сделайте его исполняемым: `chmod +x ./my-hook.sh`

### `/hooks` показывает, что хуки не настроены

Вы отредактировали файл настроек, но хуки не появляются в меню.

* Перезапустите сессию или откройте `/hooks` для перезагрузки. Хуки, добавленные через меню `/hooks`, вступают в силу немедленно, но ручные правки файлов требуют перезагрузки.
* Проверьте валидность JSON (висящие запятые и комментарии не допускаются)
* Убедитесь, что файл настроек находится в правильном месте: `.claude/settings.json` для проектных хуков, `~/.claude/settings.json` для глобальных хуков

### Хук Stop работает бесконечно

Claude продолжает работать в бесконечном цикле вместо остановки.

Ваш скрипт хука Stop должен проверять, инициировал ли он уже продолжение. Разберите поле `stop_hook_active` из JSON-входных данных и завершите раньше, если оно равно `true`:

```bash  theme={null}
#!/bin/bash
INPUT=$(cat)
if [ "$(echo "$INPUT" | jq -r '.stop_hook_active')" = "true" ]; then
  exit 0  # Разрешить Claude остановиться
fi
# ... остальная логика хука
```

### Ошибка валидации JSON

Claude Code показывает ошибку разбора JSON, хотя ваш скрипт хука выводит валидный JSON.

Когда Claude Code запускает хук, он порождает shell, который источает ваш профиль (`~/.zshrc` или `~/.bashrc`). Если ваш профиль содержит безусловные операторы `echo`, этот вывод предшествует JSON вашего хука:

```
Shell ready on arm64
{"decision": "block", "reason": "Not allowed"}
```

Claude Code пытается разобрать это как JSON и терпит неудачу. Для исправления оберните операторы echo в вашем профиле shell, чтобы они выполнялись только в интерактивных shell:

```bash  theme={null}
# В ~/.zshrc или ~/.bashrc
if [[ $- == *i* ]]; then
  echo "Shell ready"
fi
```

Переменная `$-` содержит флаги shell, и `i` означает интерактивный. Хуки выполняются в неинтерактивных shell, поэтому echo пропускается.

### Методы отладки

Переключите подробный режим с помощью `Ctrl+O` для просмотра вывода хуков в транскрипте, или запустите `claude --debug` для полных деталей выполнения, включая информацию о том, какие хуки совпали и их коды завершения.
