# Маршрутизатор

В архитектуре **маршрутизатора** этап маршрутизации классифицирует входные данные и направляет их к специализированным [агентам](/oss/python/langchain/agents). Это полезно, когда у вас есть различные **вертикали** — отдельные области знаний, каждая из которых требует своего собственного агента.

```тема русалки={null}
график LR
    A([Запрос]) --> B[Маршрутизатор]
    B --> C [Агент A]
    B --> D[Агент B]
    B --> E[Агент C]
    C --> F[Синтезировать]
    Д --> Ф
    Е --> Ф
    F --> G ([Общий ответ])
```

## Ключевые характеристики

* Маршрутизатор разбивает запрос на части
* Параллельно задействуется ноль или более специализированных агентов.
* Результаты синтезируются в согласованный ответ

## Когда использовать

Используйте шаблон маршрутизатора, когда у вас есть отдельные вертикали (разные области знаний, каждая из которых требует собственного агента), вам необходимо параллельно запрашивать данные из нескольких источников и вы хотите объединить результаты в единый ответ.

## Базовая реализация

Маршрутизатор классифицирует запрос и направляет его соответствующему агенту (агентам). Используйте [`Command`](/oss/python/langgraph/graph-api#command) для маршрутизации с одним агентом или [`Send`](/oss/python/langgraph/graph-api#send) для параллельной рассылки нескольким агентам.

<Вкладки>
  <Tab title="Единичный агент">
    Используйте команду `Command` для переадресации запроса к одному специализированному агенту:

    ```python theme={null}
    from langgraph.types import Command

    def classify_query(query: str) -> str:
        «Используйте LLM для классификации запроса и определения соответствующего агента».
        # Здесь логика классификации
        ...

    def route_query(state: State) -> Command:
        «Направление к соответствующему агенту на основе классификации запроса».
        active_agent = classify_query(state["query"])

        # Маршрутизация к выбранному агенту
        return Command(goto=active_agent)
    ```
  </Tab>

  <Tab title="Множественные агенты (параллельно)">
    Используйте команду `Send` для параллельной рассылки сообщений нескольким специализированным агентам:

    ```python theme={null}
    from typing import TypedDict
    from langgraph.types import Send

    class ClassificationResult(TypedDict):
        запрос: str
        агент: стр.

    def classify_query(query: str) -> list[ClassificationResult]:
        «Используйте LLM для классификации запросов и определения того, каких агентов следует вызвать».
        # Здесь логика классификации
        ...

    def route_query(state: State):
        «Направление к соответствующим агентам на основе классификации запроса».
        классификация = classify_query(state["query"])

        # Распределение между выбранными агентами параллельно
        возвращаться [
            Send(c["agent"], {"query": c["query"]})
            для c в классификациях
        ]
    ```
  </Tab>
</Вкладки>

## Без состояния против с состоянием

Два подхода:

* [**Маршрутизаторы без сохранения состояния**](#stateless) обрабатывают каждый запрос независимо
* [**Маршрутизаторы с сохранением состояния**](#stateful) сохраняют историю диалога между запросами

## Без статуса

Каждый запрос маршрутизируется независимо — память между вызовами не сохраняется. Для многоходовых диалогов см. [маршрутизаторы с сохранением состояния](#stateful).

<Совет>
  **Маршрутизатор против субагентов**: Оба подхода позволяют распределять задачи между несколькими агентами, но различаются способом принятия решений о маршрутизации:

  * **Маршрутизатор**: Специальный этап маршрутизации (часто это один вызов LLM или логика на основе правил), который классифицирует входные данные и распределяет их между агентами. Сам маршрутизатор обычно не хранит историю разговоров и не выполняет многоэтапную оркестрацию — это этап предварительной обработки.
  * **Субагенты**: Главный супервизор динамически решает, каких [субагентов](/oss/python/langchain/multi-agent/subagents) вызвать в рамках текущего диалога. Главный агент поддерживает контекст, может вызывать нескольких субагентов в разные ходы и координирует сложные многоэтапные рабочие процессы.

  Используйте **маршрутизатор**, если у вас есть четкие категории входных данных и вы хотите детерминированную или упрощенную классификацию. Используйте **супервизор**, если вам нужна гибкая, учитывающая контекст беседы организация работы, где LLM принимает решение о дальнейших действиях на основе изменяющегося контекста.
</Совет>

## Состояние

В диалогах, состоящих из нескольких этапов, необходимо сохранять контекст между вызовами.

### Оболочка инструмента

Простейший подход: обернуть маршрутизатор без сохранения состояния в инструмент, который может вызывать разговорный агент. Разговорный агент управляет памятью и контекстом; маршрутизатор остается без сохранения состояния. Это позволяет избежать сложностей, связанных с управлением историей разговора между несколькими параллельными агентами.

```python theme={null}
@инструмент
def search_docs(query: str) -> str:
    «Поиск по нескольким источникам документации».
    result = workflow.invoke({"query": query}) # [!code highlight]
    return result["final_answer"]

# Разговорный агент использует маршрутизатор в качестве инструмента
conversational_agent = create_agent(
    модель,
    инструменты=[search_docs],
    prompt="Вы — полезный помощник. Используйте search_docs для ответов на вопросы."
)
```

### Полное сохранение

Если вам необходимо, чтобы сам маршрутизатор сохранял состояние, используйте [persistence](/oss/python/langchain/short-term-memory) для хранения истории сообщений. При маршрутизации к агенту извлекайте предыдущие сообщения из состояния и выборочно включайте их в контекст агента — это инструмент для [контекстной инженерии](/oss/python/langchain/context-engineering).

<Предупреждение>
  **Маршрутизаторы с сохранением состояния требуют пользовательского управления историей.** Если маршрутизатор переключается между агентами в течение нескольких ходов, общение может казаться пользователям не плавным, когда агенты используют разные тона или подсказки. При параллельном вызове вам потребуется поддерживать историю на уровне маршрутизатора (входные данные и синтезированные выходные данные) и использовать эту историю в логике маршрутизации. Рассмотрите вместо этого [шаблон переадресации](/oss/python/langchain/multi-agent/handoffs) или [шаблон субагентов](/oss/python/langchain/multi-agent/subagents) — оба обеспечивают более понятную семантику для многоходовых разговоров.
</Предупреждение>
