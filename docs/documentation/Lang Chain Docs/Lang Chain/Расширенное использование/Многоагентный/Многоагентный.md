# Многоагентный

Многоагентные системы координируют специализированные компоненты для решения сложных задач. Однако не каждая сложная задача требует такого подхода — один агент с подходящими (иногда динамическими) инструментами и подсказками часто может достичь аналогичных результатов.

## Почему многоагентная архитектура?

Когда разработчики говорят, что им нужна "многоагентная система", они обычно имеют в виду одну или несколько из следующих возможностей:

* <Icon icon="brain" /> **Управление контекстом**: Предоставляйте специализированные знания, не перегружая контекстное окно модели. Если бы контекст был бесконечным, а задержка нулевой, вы могли бы сложить все знания в один запрос — но поскольку это не так, вам нужны шаблоны для выборочного отображения релевантной информации.
* <Icon icon="users" /> **Распределенная разработка**: Позволяет различным командам разрабатывать и поддерживать возможности независимо друг от друга, объединяя их в более крупную систему с четкими границами.
* <Icon icon="code-branch" /> **Параллелизация**: Создание специализированных рабочих процессов для подзадач и их параллельное выполнение для более быстрого достижения результатов.

Многоагентные модели особенно полезны, когда у одного агента слишком много инструментов, и он принимает неверные решения о том, какие из них использовать, когда задачи требуют специальных знаний с обширным контекстом (длинные подсказки и инструменты, специфичные для предметной области), или когда необходимо обеспечить последовательные ограничения, которые открывают возможности только после выполнения определенных условий.

<Совет>
  В основе проектирования многоагентных систем лежит **[контекстная инженерия](/oss/python/langchain/context-engineering)** — определение того, какую информацию видит каждый агент. Качество вашей системы зависит от обеспечения доступа каждого агента к необходимым для выполнения его задачи данным.
</Совет>

## Шаблоны

Вот основные шаблоны построения многоагентных систем, каждый из которых подходит для различных сценариев использования:

| Шаблон                                                                                    | Как это работает                                                                                                                                                                                                                                              |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [**Подагенты**](/oss/python/langchain/multi-agent/subagents)                              | Главный агент координирует действия подагентов как инструментов. Вся маршрутизация проходит через главного агента, который решает, когда и как вызывать каждого подагента.                                                                                    |
| [**Передача управления**](/oss/python/langchain/multi-agent/handoffs)                     | Поведение динамически изменяется в зависимости от состояния. Вызовы инструментов обновляют переменную состояния, которая запускает изменения маршрутизации или конфигурации, переключение агентов или корректировку инструментов и подсказок текущего агента. |
| [**Навыки**](/oss/python/langchain/multi-agent/skills)                                    | Специализированные подсказки и знания загружаются по запросу. Один агент сохраняет управление, загружая контекст из навыков по мере необходимости.                                                                                                            |
| [**Маршрутизатор**](/oss/python/langchain/multi-agent/router)                             | Этап маршрутизации классифицирует входные данные и направляет их одному или нескольким специализированным агентам. Результаты синтезируются в комбинированный ответ.                                                                                          |
| [**Пользовательский рабочий процесс**](/oss/python/langchain/multi-agent/custom-workflow) | Создавайте индивидуальные потоки выполнения с помощью [LangGraph](/oss/python/langgraph/overview), сочетая детерминированную логику и агентное поведение. Встраивайте другие шаблоны в качестве узлов в свой рабочий процесс.                                 |

### Выбор узора

Используйте эту таблицу, чтобы сопоставить ваши требования с подходящим шаблоном:

<div className="compact-first-col">
  | Шаблон                                                                 | Распределенная разработка | Параллелизация | Многошаговая обработка | Прямое взаимодействие с пользователем |
  | ---------------------------------------------------------------------- | :-----------------------: | :------------: | :--------------------: | :-----------------------------------: |
  | [**Субагенты**](/oss/python/langchain/multi-agent/subagents)           |           ⭐⭐⭐⭐⭐           |     ⭐⭐⭐⭐⭐      |         ⭐⭐⭐⭐⭐          |                   ⭐                   |
  | [**Передача прав**](/oss/python/langchain/multi-agent/handoffs)        |             —             |       —        |         ⭐⭐⭐⭐⭐          |                 ⭐⭐⭐⭐⭐                 |
  | [**Навыки**](/oss/python/langchain/multi-agent/skills)                 |           ⭐⭐⭐⭐⭐           |      ⭐⭐⭐       |         ⭐⭐⭐⭐⭐          |                 ⭐⭐⭐⭐⭐                 |
  | [**Маршрутизатор**](/oss/python/langchain/многоагентный/маршрутизатор) |            ⭐⭐⭐            |     ⭐⭐⭐⭐⭐      |           —            |                  ⭐⭐⭐                  |
</div>

* **Распределенная разработка**: Могут ли разные команды поддерживать компоненты независимо друг от друга?
* **Параллелизация**: Может ли несколько агентов выполнять задачи одновременно?
* **Многошаговый режим**: Поддерживает ли данный шаблон последовательный вызов нескольких субагентов?
* **Прямое взаимодействие с пользователем**: Могут ли субагенты напрямую общаться с пользователем?

<Совет>
  Вы можете комбинировать различные шаблоны! Например, архитектура **субагентов** может вызывать инструменты, которые запускают пользовательские рабочие процессы или агенты маршрутизатора. Субагенты даже могут использовать шаблон **навыков** для загрузки контекста по запросу. Возможности безграничны!
</Совет>

## Сравнение производительности

Различные шаблоны имеют разные характеристики производительности. Понимание этих компромиссов поможет вам выбрать правильный шаблон, соответствующий вашим требованиям к задержке и стоимости.

**Ключевые показатели:**

* **Вызовы модели**: Количество вызовов LLM. Большее количество вызовов = более высокая задержка (особенно при последовательном выполнении) и более высокие затраты на API на один запрос.
* **Обработано токенов**: Общее использование [контекстного окна](/oss/python/langchain/context-engineering) по всем вызовам. Больше токенов = более высокие затраты на обработку и потенциальные ограничения контекста.

### Повторный запрос

> **Первый ход:** "Купить кофе"
> **Переход 2:** "Снова купить кофе"

Пользователь повторяет тот же запрос в том же диалоге.

<div className="compact-first-col">
  | Шаблон                                                                 | Звонки на втором ходу | Всего (оба хода) | Наилучшее соответствие |
  | ---------------------------------------------------------------------- | :-------------------: | :--------------: | :--------------------: |
  | [**Субагенты**](/oss/python/langchain/multi-agent/subagents)           |           4           |        8         |                        |
  | [**Передача данных**](/oss/python/langchain/multi-agent/handoffs)      |           2           |        5         |           ✅            |
  | [**Навыки**](/oss/python/langchain/multi-agent/skills)                 |           2           |        5         |           ✅            |
  | [**Маршрутизатор**](/oss/python/langchain/многоагентный/маршрутизатор) |           3           |        6         |                        |
</div>

<Вкладки>
  <Tab title="Subagents">
    **4 звонка снова → всего 8**

    * Подагенты **по своей природе не имеют состояния** — каждый вызов выполняется по одному и тому же алгоритму.
    * Основной агент поддерживает контекст разговора, но подчиненные агенты каждый раз начинают заново.
    * Это обеспечивает сильную контекстную изоляцию, но повторяет весь процесс.
  </Tab>

  <Tab title="Handoffs">
    **2 звонка → всего 5**

    * Кофейный агент **все еще активен** с 1-го хода (состояние сохраняется)
    * Передача управления не требуется — агент напрямую звонит в инструмент `buy_coffee` (вызов 1)
    * Оператор отвечает пользователю (звонок 2)
    * **Экономит 1 звонок, пропуская переключение между звонками**
  </Tab>

  <Tab title="Навыки">
    **2 звонка → всего 5**

    * Контекст навыка **уже загружен** в историю разговора.
    * Нет необходимости перезагружать — агент напрямую вызывает инструмент `buy_coffee` (вызов 1)
    * Оператор отвечает пользователю (звонок 2)
    * **Экономит 1 звонок за счет повторного использования загруженного навыка**
  </Tab>

  <Tab title="Маршрутизатор">
    **3 звонка снова → всего 6**

    * Маршрутизаторы являются **без сохранения состояния** — каждый запрос требует вызова маршрутизации LLM.
    * Ход 2: Вызов маршрутизатора LLM (1) → Агент по продаже молока звонит, чтобы купить кофе (2) → Агент по продаже молока отвечает (3)
    * Может быть оптимизировано путем использования в качестве инструмента в агенте, сохраняющем состояние.
  </Tab>
</Вкладки>

**Ключевой вывод:** Шаблоны с сохранением состояния (передача запросов, навыки) позволяют сэкономить 40-50% вызовов на повторных запросах. Подагентные процессы поддерживают постоянную стоимость каждого запроса — такая архитектура без сохранения состояния обеспечивает сильную контекстную изоляцию, но за счет повторных вызовов модели.

    Маршрутизатор использует **LLM для маршрутизации**, а затем параллельно вызывает агентов. Аналогично субагентам, но с явным этапом маршрутизации. Всего: **9000 токенов**.

</Вкладки>

**Ключевой вывод:** Для задач, затрагивающих несколько доменов, наиболее эффективны шаблоны с параллельным выполнением (субъекты, маршрутизатор). Навыки требуют меньше вызовов, но потребляют много токенов из-за накопления контекста. Передача данных в этом случае неэффективна — она должна выполняться последовательно и не может использовать параллельный вызов инструментов для одновременного обращения к нескольким доменам.
