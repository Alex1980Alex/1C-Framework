# Субагенты

В архитектуре **субагентов** центральный главный [агент](/oss/python/langchain/agents) (часто называемый **супервизором**) координирует работу субагентов, вызывая их как [инструменты](/oss/python/langchain/tools). Главный агент решает, какого субагента вызвать, какие входные данные предоставить и как объединить результаты. Субагенты не имеют состояния — они не помнят прошлых взаимодействий, вся память о диалоге хранится главным агентом. Это обеспечивает [контекстную](/oss/python/langchain/context-engineering) изоляцию: каждый вызов субагента работает в чистом контекстном окне, предотвращая раздувание контекста в основном диалоге.

```тема русалки={null}
график LR
    A[Пользователь] --> B[Главный агент]
    B --> C [Субагент A]
    B --> D[Субагент B]
    B --> E[Субагент C]
    C --> B
    Д --> Б
    Е --> Б
    B --> F[Ответ пользователя]
```

## Ключевые характеристики

* Централизованное управление: вся маршрутизация проходит через главного агента.
* Отсутствие прямого взаимодействия с пользователем: Подавляющие агенты возвращают результаты основному агенту, а не пользователю (хотя вы можете использовать [прерывания](/oss/python/langgraph/human-in-the-loop#interrupt) внутри подагента, чтобы разрешить взаимодействие с пользователем).
* Субагенты через инструменты: Субагенты вызываются через инструменты
* Параллельное выполнение: главный агент может запускать несколько подчиненных агентов за один ход.

<Примечание>
  **Супервизор против маршрутизатора**: Агент-супервизор (в данном случае) отличается от [маршрутизатора](/oss/python/langchain/multi-agent/router). Супервизор — это полноценный агент, который поддерживает контекст разговора и динамически решает, каких субагентов вызывать в течение нескольких ходов. Маршрутизатор, как правило, представляет собой один этап классификации, который распределяет задачи между агентами, не поддерживая текущее состояние разговора.
</Примечание>

## Когда использовать

Используйте шаблон субагентов, если у вас несколько различных доменов (например, календарь, электронная почта, CRM, база данных), субагентам не нужно напрямую общаться с пользователями или вам нужно централизованное управление рабочим процессом. В более простых случаях с небольшим количеством инструментов используйте одного агента.

<Совет>
  **Необходимо взаимодействие с пользователем внутри подагента?** Хотя подагенты обычно возвращают результаты основному агенту, а не общаются напрямую с пользователями, вы можете использовать [прерывания](/oss/python/langgraph/human-in-the-loop#interrupt) внутри подагента, чтобы приостановить выполнение и собрать ввод пользователя. Это полезно, когда подагенту требуется уточнение или одобрение перед продолжением. Основной агент остается координатором, но подагент может собирать информацию от пользователя в процессе выполнения задачи.
</Совет>

## Базовая реализация

Основной механизм представляет собой субагента, выступающего в роли инструмента, который может вызывать главный агент:

```python theme={null}
from langchain.tools import tool
from langchain.agents import create_agent

# Создание субагента
subagent = create_agent(model="anthropic:claude-sonnet-4-20250514", tools=[...])

# Оберните его в инструмент
@tool("research", description="Исследовать тему и получить результаты")
def call_research_agent(query: str):
    result = subagent.invoke({"messages": [{"role": "user", "content": query}]})
    return result["messages"][-1].content

# Основной агент с субагентом в качестве инструмента
main_agent = create_agent(model="anthropic:claude-sonnet-4-20250514", tools=[call_research_agent])
```

## Синхронная и асинхронная обработка

Выполнение подчиненного агента может быть **синхронным** (блокирующим) или **асинхронным** (фоновым). Выбор зависит от того, нужен ли основному агенту результат для продолжения работы.

| Режим             | Поведение основного агента                            | Лучший для                                            | Компромисс                    |
| ----------------- | ----------------------------------------------------- | ----------------------------------------------------- | ----------------------------- |
| **Синхронизация** | Ожидает завершения работы субагента                   | Основной агент нуждается в результате для продолжения | Просто, но блокирует разговор |
| **Асинхронный**   | Продолжается, пока субагент работает в фоновом режиме | Независимые задачи, пользователю не нужно ждать       | Отзывчивый, но более сложный  |

<Совет>
  Не следует путать с `async`/`await` в Python. Здесь «async» означает, что основной агент запускает фоновую задачу (обычно в отдельном процессе или службе) и продолжает работу без блокировки.
</Совет>

### Синхронный (по умолчанию)

По умолчанию вызовы дочерних агентов выполняются **синхронно** — главный агент ожидает завершения каждого вызова дочернего агента, прежде чем продолжить. Используйте синхронный режим, если следующее действие главного агента зависит от результата вызова дочернего агента.

```тема русалки={null}
диаграмма последовательности
    участник Пользователь
    участник Главный агент
    участник исследования, субагент

    Пользователь->>Главный агент: "Какая погода в Токио?"
    Главный агент -> Исследовательский субагент: исследование («Погода в Токио»)
    Примечание от главного агента: Ожидание результата...
    Исследовательский субагент --> Главный агент: "В настоящее время 72°F, солнечно"
    Главный агент --> Пользователь: «В Токио 72°F и солнечно»
```

**Когда следует использовать синхронизацию:**

* Главному агенту необходим результат работы субагента для формулирования своего ответа.
* Задачи имеют зависимость порядка выполнения (например, получение данных → анализ → ответ).
* Сбои в работе субъагента должны блокировать ответ основного агента.

**Компромиссы:**

* Простая реализация — просто позвоните и подождите
* Пользователь не увидит ответа, пока все субагенты не завершат свою работу.
* Длительные задачи парализуют разговор

### Асинхронный

Используйте **асинхронное выполнение**, когда работа дочернего агента независима — главному агенту не нужен результат для продолжения общения с пользователем. Главный агент запускает фоновую задачу и остается отзывчивым.

```тема русалки={null}
диаграмма последовательности
    участник Пользователь
    участник Главный агент
    система трудоустройства участников
    участник, эксперт по проверке контрактов

    Пользователь->>Главный агент: "Просмотрите этот договор о слиянии и поглощении"
    Главный агент->>Система заданий: run_agent("legal_reviewer", task)
    Система заданий->>Проверка контрактов: Агент запуска
    Система заданий --> Главный агент: job_id: "job_123"
    Главный агент --> Пользователь: "Начата проверка (задание_123)"

    Примечание к проверке контрактов: Проверяю более 150 страниц...

    Пользователь -> Главный агент: "Какой статус?"
    Главный агент->>Система заданий: check_status(job_id)
    Система заданий --> Главный агент: "работает"
    Главный агент --> Пользователь: "Все еще изучаю контракт..."

    Примечание к проверке контракта: Проверка завершена.

    Пользователь -> Главный агент: "Это уже сделано?"
    Главный агент->>Система заданий: check_status(job_id)
    Система заданий --> Главный агент: "завершено"
    Главный агент -> Система заданий: get_result(job_id)
    Система заданий --> Главный агент: Анализ контрактов
    Главный агент --> Пользователь: "Проверка завершена: [результаты]"
```

**Когда следует использовать асинхронные операции:**

* Работа субагента независима от основного хода разговора.
* Пользователи должны иметь возможность продолжать общение в чате во время работы.
* Вы хотите запустить несколько независимых задач параллельно.

**Схема из трех инструментов:**

1. **Запуск задания**: Запускает фоновую задачу и возвращает идентификатор задания.
2. **Проверка статуса**: Возвращает текущее состояние (ожидание, выполнение, завершено, сбой)
3. **Получить результат**: Извлекает завершенный результат.

**Обработка завершения задания:** Когда задание завершается, ваше приложение должно уведомить пользователя. Один из подходов: отобразить уведомление, которое при нажатии отправляет сообщение типа «Проверьте задание_123 и подведите итоги».

## Шаблоны инструментов

Существует два основных способа представления субагентов в качестве инструментов:

| Шаблон                                                         | Лучший вариант для                                                    | Компромисс                                                  |
| -------------------------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------- |
| [**Инструмент на агента**](#инструмент-на-агента)              | Точный контроль ввода/вывода каждого субагента                        | Больше настроек, но больше возможностей для персонализации  |
| [**Единый инструмент диспетчеризации**](#single-dispatch-tool) | Много агентов, распределенные команды, соглашения вместо конфигурации | Более простая структура, меньше настроек для каждого агента |

### Инструмент на одного агента

```тема русалки={null}
график LR
    A[Пользователь] --> B[Главный агент]
    B --> C [Субагент A]
    B --> D[Субагент B]
    B --> E[Субагент C]
    C --> B
    Д --> Б
    Е --> Б
    B --> F[Ответ пользователя]
```

Ключевая идея заключается в том, чтобы представить подчиненных агентов в виде инструментов, которые главный агент может вызывать:

```python theme={null}
from langchain.tools import tool
from langchain.agents import create_agent

# Создать субагента
subagent = create_agent(model="...", tools=[...]) # [!code highlight]

# Оберните его в инструмент # [!подсветка кода]
@tool("subagent_name", description="subagent_description") # [!code highlight]
def call_subagent(query: str): # [!code highlight]
    result = subagent.invoke({"messages": [{"role": "user", "content": query}]})
    return result["messages"][-1].content

# Основной агент с субагентом в качестве инструмента # [!подсветка кода]
main_agent = create_agent(model="...", tools=[call_subagent]) # [!code highlight]
```

Главный агент запускает инструмент субагента, когда решает, что задача соответствует описанию субагента, получает результат и продолжает оркестровку. См. [Контекстная инженерия](#context-engineering) для более точного управления.

### Инструмент единой отправки

Альтернативный подход использует единый параметризованный инструмент для вызова временных субагентов для выполнения независимых задач. В отличие от подхода [инструмент на агента](#инструмент-на-агента), где каждый субагент представлен как отдельный инструмент, здесь используется подход, основанный на соглашениях, с одним инструментом для выполнения задачи: описание задачи передается субагенту в виде сообщения, а итоговое сообщение субагента возвращается в качестве результата работы инструмента.

Этот подход следует использовать, если вы хотите распределить разработку агентов между несколькими командами, необходимо изолировать сложные задачи в отдельные контекстные окна, нужен масштабируемый способ добавления новых агентов без изменения координатора или вы предпочитаете соглашения настройке. Этот подход жертвует гибкостью в проектировании контекста ради простоты в создании агентов и надежной изоляции контекста.

```тема русалки={null}
график LR
    A[Пользователь] --> B[Главный агент]
    B --> C{task<br/>agent_name, description}
    C -->|исследование| D[Исследовательский агент]
    C -->|писатель| E[Агент писателя]
    C -->|рецензент| F[Агент рецензента]
    Д --> С
    Е --> С
    Ф --> С
    C --> B
    B --> G[Ответ пользователя]
```

**Основные характеристики:**

* Инструмент для выполнения одной задачи: Один параметризованный инструмент, который может вызывать любой зарегистрированный субагент по имени.
* Вызов на основе соглашений: агент выбирается по имени, задача передается как сообщение, передаваемое человеком, итоговое сообщение возвращается в качестве результата работы инструмента.
* Распределение по командам: Разные команды могут разрабатывать и развертывать агентов независимо друг от друга.
* Обнаружение агентов: Подагентов можно обнаружить через системную подсказку (отображение списка доступных агентов) или через [постепенное раскрытие информации](/oss/python/langchain/multi-agent/skills-sql-assistant) (загрузка информации об агентах по запросу с помощью инструментов).

<Совет>
  Интересный аспект этого подхода заключается в том, что вспомогательные агенты могут обладать точно такими же возможностями, как и основной агент. В таких случаях вызов вспомогательного агента **на самом деле обусловлен необходимостью изоляции контекста**, что позволяет выполнять сложные многоэтапные задачи в изолированных контекстных окнах, не перегружая историю диалога основного агента. Вспомогательный агент выполняет свою работу автономно и возвращает только краткое резюме, поддерживая фокус и эффективность основного потока.
</Совет>

## Контекстная инженерия

Управляйте передачей контекстной информации между основным агентом и его подчиненными агентами:

| Категория                                          | Цель                                                                           | Воздействие                               |
| -------------------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------- |
| [**Спецификации субагентов**](#subagent-specs)     | Обеспечить вызов субагентов в нужное время                                     | Решения по маршрутизации основного агента |
| [**Входные данные субагента**](#subagent-inputs)   | Обеспечьте эффективную работу субагентами в оптимизированном контексте         | Производительность субагента              |
| [**Выходные данные субагента**](#subagent-outputs) | Обеспечить возможность супервизора действовать на основе результатов субагента | Производительность основного агента       |

См. также наше подробное руководство по [контекстной инженерии](/oss/python/langchain/context-engineering) для агентов.

### Технические характеристики субагента

Имена и описания, связанные с субагентами, являются основным способом, с помощью которого главный агент узнает, каких субагентов следует вызвать.
Это рычаги воздействия — выбирайте их внимательно.

* **Имя**: Так основной агент обращается к подчиненному агенту. Используйте понятное и ориентированное на действия обозначение (например, `research_agent`, `code_reviewer`).
* **Описание**: Что известно главному агенту о возможностях вспомогательного агента. Укажите конкретно, какие задачи он выполняет и когда его следует использовать.

В случае использования единого инструмента диспетчеризации (#single-dispatch-tool) главному агенту необходимо вызвать инструмент `task`, указав имя вызываемого субагента. Доступные инструменты могут быть предоставлены главному агенту одним из следующих способов:

* **Перечисление системных команд**: Отображение списка доступных агентов в системной подсказке.
* **Ограничение перечисления в инструменте диспетчеризации**: Для небольших списков агентов добавьте перечисление в поле `agent_name`.
* **Обнаружение на основе инструментов**: Для больших или динамических реестров агентов предоставьте отдельный инструмент (например, `list_agents` или `search_agents`), который возвращает доступных агентов.

### Входные данные суб-агента

Настройте контекст, который получает субагент для выполнения своей задачи. Добавьте входные данные, которые нецелесообразно собирать в статическом окне запроса — полную историю сообщений, предыдущие результаты или метаданные задачи — путем получения информации из состояния агента.

```python Subagent inputs example expandable theme={null}
from langchain.agents import AgentState
from langchain.tools import tool, ToolRuntime

class CustomState(AgentState):
    example_state_key: str

@инструмент(
    "subagent1_name",
    description="subagent1_description"
)
def call_subagent1(query: str, runtime: ToolRuntime[None, CustomState]):
    # Примените необходимую логику для преобразования сообщений в подходящие входные данные.
    subagent_input = some_logic(query, runtime.state["messages"])
    результат = subagent1.invoke({
        "messages": subagent_input,
        # При необходимости вы также можете передать сюда другие ключи состояния.
        # Обязательно укажите эти параметры как в основном, так и в подчиненном агенте.
        # схемы состояний.
        "example_state_key": runtime.state["example_state_key"]
    })
    return result["messages"][-1].content
```

### Выходы субагента

Настройте параметры обратной связи, которую получает главный агент, чтобы он мог принимать обоснованные решения. Две стратегии:

1. **Задайте подсказку суб-агенту**: Укажите точно, что должно быть возвращено. Распространенная ошибка заключается в том, что суб-агент выполняет вызовы инструментов или логические рассуждения, но не включает результаты в свое итоговое сообщение — напомните ему, что супервизор видит только конечный результат.
2. **Форматирование в коде**: скорректируйте или дополните ответ перед его возвратом. Например, передайте обратно определенные ключи состояния в дополнение к итоговому тексту, используя [`Команду`](/oss/python/langgraph/graph-api#command).

```python Subagent outputs example expandable theme={null}
from typing import Annotated
from langchain.agents import AgentState
from langchain.tools import InjectedToolCallId
from langgraph.types import Command


@инструмент(
    "subagent1_name",
    description="subagent1_description"
)
def call_subagent1(
    запрос: str,
    tool_call_id: Annotated[str, InjectedToolCallId],
) -> Команда:
    результат = subagent1.invoke({
        "сообщения": [{"роль": "пользователь", "контент": запрос}]
    })
    return Command(update={
        # Передаем дополнительное состояние от субагента
        "example_state_key": result["example_state_key"],
        "сообщения": [
            ToolMessage(
                content=result["messages"][-1].content,
                tool_call_id=tool_call_id
            )
        ]
    })
```
