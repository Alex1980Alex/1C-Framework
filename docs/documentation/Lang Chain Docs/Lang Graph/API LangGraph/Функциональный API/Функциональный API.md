# Обзор функционального API

**Функциональный API** позволяет добавить ключевые возможности LangGraph — [сохранение данных](/oss/python/langgraph/persistence), [память](/oss/python/langgraph/add-memory), [человек в цикле обработки](/oss/python/langgraph/interrupts) и [потоковая обработка](/oss/python/langgraph/streaming) — в ваши приложения с минимальными изменениями в существующем коде.

Он предназначен для интеграции этих функций в существующий код, который может использовать стандартные языковые примитивы для ветвления и управления потоком выполнения, такие как операторы `if`, циклы `for` и вызовы функций. В отличие от многих фреймворков для оркестрации данных, которые требуют реструктуризации кода в явный конвейер или направленный ациклический граф (DAG), функциональный API позволяет интегрировать эти возможности без навязывания жесткой модели выполнения.

Функциональный API использует два ключевых компонента:

* **`@entrypoint`** – Помечает функцию как отправную точку рабочего процесса, инкапсулируя логику и управляя потоком выполнения, включая обработку длительных задач и прерываний.
* **[`@task`](https://reference.langchain.com/python/langgraph/func/#langgraph.func.task)** – Представляет собой дискретную единицу работы, такую ​​как вызов API или этап обработки данных, которая может быть выполнена асинхронно в точке входа. Задачи возвращают объект, похожий на объект будущего, который можно ожидать или разрешить синхронно.

Это обеспечивает минимальную абстракцию для построения рабочих процессов с управлением состоянием и потоковой передачей данных.

<Совет>
  Для получения информации о том, как использовать функциональный API, см. [Использование функционального API](/oss/python/langgraph/use-functional-api).
</Совет>

## Функциональный API против Graph API

Для пользователей, предпочитающих более декларативный подход, API графов LangGraph позволяет определять рабочие процессы, используя парадигму графов. Оба API используют одну и ту же базовую среду выполнения, поэтому их можно использовать вместе в одном приложении.

Вот некоторые ключевые отличия:

* **Управление потоком выполнения**: Функциональный API не требует размышлений о структуре графа. Вы можете использовать стандартные конструкции Python для определения рабочих процессов. Это обычно сокращает объем необходимого кода.
* **Кратковременная память**: **GraphAPI** требует объявления [**состояния**](/oss/python/langgraph/graph-api#state) и может потребовать определения [**редукторов**](/oss/python/langgraph/graph-api#reducers) для управления обновлениями состояния графа. `@entrypoint` и `@tasks` не требуют явного управления состоянием, поскольку их состояние ограничено областью видимости функции и не используется совместно другими функциями.
* **Создание контрольных точек**: Оба API генерируют и используют контрольные точки. В **Graph API** новая контрольная точка генерируется после каждого [супершага](/oss/python/langgraph/graph-api). В **Функциональном API** при выполнении задач их результаты сохраняются в существующую контрольную точку, связанную с заданной точкой входа, вместо создания новой контрольной точки.
* **Визуализация**: API Graph позволяет легко визуализировать рабочий процесс в виде графа, что может быть полезно для отладки, понимания рабочего процесса и обмена информацией с другими. Функциональный API не поддерживает визуализацию, поскольку граф генерируется динамически во время выполнения.

## Пример

Ниже мы демонстрируем простое приложение, которое пишет эссе и прерывает выполнение запроса на проверку человеком.

```python theme={null}
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.func import entrypoint, task
from langgraph.types import interrupt

@задача
def write_essay(topic: str) -> str:
    «Напишите эссе на заданную тему».
    time.sleep(1) # Заполнитель для длительной задачи.
    return f"Эссе на тему: {тема}"

@entrypoint(checkpointer=InMemorySaver())
def workflow(topic: str) -> dict:
    «Простой алгоритм действий: пишется эссе, и запрашивается рецензия».
    essay = write_essay("cat").result()
    is_approved = interrupt({
        # Любая полезная нагрузка, сериализуемая в формате JSON, передается в прерывание в качестве аргумента.
        # На стороне клиента это будет отображаться как прерывание при потоковой передаче данных.
        # из рабочего процесса.
        "эссе": эссе, # Эссе, которое мы хотим проверить.
        # Мы можем добавить любую дополнительную информацию, которая нам потребуется.
        # Например, добавьте клавишу с названием "action" и некоторыми инструкциями.
        «действие»: «Пожалуйста, одобрите/отклоните эссе».
    })

    возвращаться {
        "эссе": эссе, # Эссе, которое было создано
        "is_approved": is_approved, # Ответ от HIL
    }
```

## Точка входа

Декоратор [`@entrypoint`](https://reference.langchain.com/python/langgraph/func/#langgraph.func.entrypoint) можно использовать для создания рабочего процесса из функции. Он инкапсулирует логику рабочего процесса и управляет потоком выполнения, включая обработку *длительных задач* и [прерываний](/oss/python/langgraph/interrupts).

### Определение

Точка входа определяется путем добавления к функции декоратора `@entrypoint`.

Функция **должна принимать один позиционный аргумент**, который служит входными данными для рабочего процесса. Если вам нужно передать несколько элементов данных, используйте словарь в качестве входного типа для первого аргумента.

Добавление `entrypoint` к функции создает экземпляр `Pregel` (https://reference.langchain.com/python/langgraph/pregel/#langgraph.pregel.Pregel.stream), который помогает управлять выполнением рабочего процесса (например, обрабатывает потоковую передачу, возобновление и контрольные точки).

Обычно для обеспечения сохранения данных и использования таких функций, как участие человека в процессе, рекомендуется передавать **контрольную точку** декоратору `@entrypoint`.

### Параметры инъекции

При объявлении точки входа вы можете запросить доступ к дополнительным параметрам, которые будут автоматически внедрены во время выполнения. К этим параметрам относятся:

| Параметр       | Описание                                                                                                                                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **предыдущая** | Получите доступ к состоянию, связанному с предыдущей контрольной точкой для данного потока. См. [кратковременная память](#кратковременная память).                                                                                   |
| **хранилище**  | Экземпляр \[BaseStore]\[langgraph.store.base.BaseStore]. Полезен для [долговременной памяти](/oss/python/langgraph/use-functional-api#long-term-memory).                                                                             |
| **writer**     | Используется для доступа к StreamWriter при работе с асинхронными операциями в Python < 3.11. См. [потоковая обработка с функциональным API для получения подробной информации](/oss/python/langgraph/use-functional-api#streaming). |
| **config**     | Для доступа к конфигурации во время выполнения. См. [RunnableConfig](https://python.langchain.com/docs/concepts/runnables/#runnableconfig) для получения дополнительной информации.                                                  |

<Предупреждение>
  Объявите параметры, указав соответствующее имя и тип.
</Предупреждение>

### Кратковременная память

Когда точка входа определяется с помощью контрольной точки, она сохраняет информацию между последовательными вызовами на одном и том же **идентификаторе потока** в [checkpoints](/oss/python/langgraph/persistence#checkpoints).

Это позволяет получить доступ к состоянию из предыдущего вызова, используя параметр `previous`.

По умолчанию параметр `previous` принимает значение, возвращаемое предыдущим вызовом.

```python theme={null}
@entrypoint(checkpointer=checkpointer)
def my_workflow(number: int, *, previous: Any = None) -> int:
    предыдущий = предыдущий или 0
    номер возврата + предыдущий

config = {
    "настраиваемый": {
        "thread_id": "some_thread_id"
    }
}

my_workflow.invoke(1, config) # 1 (предыдущее было None)
my_workflow.invoke(2, config) # 3 (предыдущее значение было 1 из предыдущего вызова)
```

#### `entrypoint.final`

`[`entrypoint.final`](https://reference.langchain.com/python/langgraph/func/#langgraph.func.entrypoint.final) — это специальный примитив, который может быть возвращен точкой входа и позволяет **разделить** значение, **сохраненное в контрольной точке**, от **возвращаемого значения точки входа**.

Первое значение — это возвращаемое значение точки входа, а второе — значение, которое будет сохранено в контрольной точке. Аннотация типа: `entrypoint.final[return_type, save_type]`.

```python theme={null}
@entrypoint(checkpointer=checkpointer)
def my_workflow(number: int, *, previous: Any = None) -> entrypoint.final[int, int]:
    предыдущий = предыдущий или 0
    # Эта функция вернет вызывающей стороне предыдущее значение, сохраняя
    # 2 * номер контрольной точки, которая будет использована при следующем вызове
    # для параметра `previous`.
    return entrypoint.final(value=previous, save=2 * number)

config = {
    "настраиваемый": {
        "thread_id": "1"
    }
}

my_workflow.invoke(3, config) # 0 (предыдущее значение было None)
my_workflow.invoke(1, config) # 6 (предыдущее значение было 3 * 2 из предыдущего вызова)
```

## Задача

Задача представляет собой отдельную единицу работы, например, вызов API или этап обработки данных. Она обладает двумя ключевыми характеристиками:

* **Асинхронное выполнение**: Задачи предназначены для асинхронного выполнения, что позволяет одновременно выполнять несколько операций без блокировки.
* **Сохранение контрольных точек**: Результаты выполнения задачи сохраняются в контрольной точке, что позволяет возобновить рабочий процесс с последнего сохраненного состояния. (Подробнее см. [persistence](/oss/python/langgraph/persistence)).

### Определение

Задачи определяются с помощью декоратора `@task`, который является оберткой для обычной функции Python.

```python theme={null}
from langgraph.func import task

@задача()
def slow_computation(input_value):
    # Имитация длительной операции
    ...
    вернуть результат
```

<Предупреждение>
  **Сериализация**
  Выходные данные задач должны быть сериализуемы в формате JSON для поддержки создания контрольных точек.
</Предупреждение>

### Исполнение

**Задачи** могут быть вызваны только из **точки входа**, другой **задачи** или [узла графа состояний](/oss/python/langgraph/graph-api#nodes).

Вызов задач *невозможен* напрямую из основного кода приложения.

При вызове **задачи** она *немедленно* возвращает объект Future. Future — это заполнитель для результата, который будет доступен позже.

Чтобы получить результат **задачи**, вы можете либо дождаться его синхронно (используя `result()`), либо дождаться его асинхронно (используя `await`).

<Вкладки>
  <Tab title="Синхронный вызов">
    ```python theme={null}
    @entrypoint(checkpointer=checkpointer)
    def my_workflow(some_input: int) -> int:
        future = slow_computation(some_input)
        return future.result() # Ожидание результата синхронно
    ```
  </Tab>

  <Tab title="Асинхронный вызов">
    ```python theme={null}
    @entrypoint(checkpointer=checkpointer)
    async def my_workflow(some_input: int) -> int:
        return await slow_computation(some_input) # Ожидание результата асинхронно
    ```
  </Tab>
</Вкладки>

## Когда использовать задачу

**Задачи** полезны в следующих ситуациях:

* **Создание контрольных точек**: Когда необходимо сохранить результат длительной операции в контрольную точку, чтобы не приходилось пересчитывать его при возобновлении рабочего процесса.
* **Участие человека**: Если вы создаете рабочий процесс, требующий вмешательства человека, вы ОБЯЗАТЕЛЬНО должны использовать **задачи** для инкапсуляции любой случайности (например, вызовов API), чтобы гарантировать корректное возобновление рабочего процесса. Подробнее см. раздел [детерминизм](#детерминизм).
* **Параллельное выполнение**: Для задач, интенсивно использующих ввод-вывод, **задачи** позволяют выполнять параллельное выполнение, обеспечивая одновременное выполнение нескольких операций без блокировки (например, вызов нескольких API).
* **Наблюдаемость**: Оборачивание операций в **задачи** позволяет отслеживать ход выполнения рабочего процесса и контролировать выполнение отдельных операций с помощью [LangSmith](https://docs.langchain.com/langsmith/home).
* **Повторяемая работа**: Когда необходимо повторно выполнить работу для обработки сбоев или несоответствий, **задачи** предоставляют способ инкапсулировать и управлять логикой повторных попыток.

## Сериализация

В LangGraph сериализация имеет два ключевых аспекта:

1. Входные и выходные данные `entrypoint` должны быть сериализуемыми в формате JSON.
2. Результаты выполнения задачи должны быть сериализуемыми в формате JSON.

Эти требования необходимы для обеспечения возможности создания контрольных точек и возобновления рабочего процесса. Используйте примитивы Python, такие как словари, списки, строки, числа и логические значения, чтобы гарантировать сериализуемость ваших входных и выходных данных.

Сериализация гарантирует надежное сохранение и восстановление состояния рабочего процесса, такого как результаты задач и промежуточные значения. Это крайне важно для обеспечения взаимодействия человека с системой, отказоустойчивости и параллельного выполнения.

Предоставление несериализуемых входных или выходных данных приведет к ошибке во время выполнения, если рабочий процесс настроен с использованием контрольной точки.

## Детерминизм

Для использования таких функций, как **участие человека в процессе выполнения**, любая случайность должна быть заключена внутри **задач**. Это гарантирует, что при остановке выполнения (например, при участии человека в процессе) и последующем возобновлении оно будет следовать той же *последовательности шагов*, даже если результаты **задач** не являются детерминированными.

LangGraph достигает такого поведения, сохраняя результаты **задачи** и [**подграфа**](/oss/python/langgraph/use-subgraphs) по мере их выполнения. Хорошо продуманный рабочий процесс гарантирует, что возобновление выполнения будет происходить в *той же последовательности шагов*, что позволит корректно получить ранее вычисленные результаты без необходимости их повторного выполнения. Это особенно полезно для длительно выполняющихся **задач** или **задач** с недетерминированными результатами, поскольку позволяет избежать повторения ранее выполненной работы и возобновить выполнение практически с того же места.

Хотя разные запуски рабочего процесса могут давать разные результаты, возобновление **конкретного** запуска всегда должно следовать одной и той же последовательности записанных шагов. Это позволяет LangGraph эффективно находить результаты **задач** и **подграфов**, которые были выполнены до прерывания графа, и избегать их повторного вычисления.

## Идемпотентность

Идемпотентность гарантирует, что многократное выполнение одной и той же операции даст одинаковый результат. Это помогает предотвратить дублирование вызовов API и избыточную обработку, если шаг выполняется повторно из-за сбоя. Всегда размещайте вызовы API внутри функций **задач** для создания контрольных точек и проектируйте их таким образом, чтобы они были идемпотентными в случае повторного выполнения. Повторное выполнение может произойти, если **задача** запускается, но не завершается успешно. В этом случае, если рабочий процесс возобновится, **задача** запустится снова. Используйте ключи идемпотентности или проверяйте существующие результаты, чтобы избежать дублирования.

## Распространенные ошибки

### Как справиться с побочными эффектами

Инкапсулируйте побочные эффекты (например, запись в файл, отправка электронного письма) в задачи, чтобы гарантировать, что они не будут выполняться несколько раз при возобновлении рабочего процесса.

<Вкладки>
  <Tab title="Неверно">
    В этом примере побочный эффект (запись в файл) непосредственно включен в рабочий процесс, поэтому он будет выполнен повторно при возобновлении рабочего процесса.

    ```python theme={null}
    @entrypoint(checkpointer=checkpointer)
    def my_workflow(inputs: dict) -> int:
        # Этот код будет выполнен повторно при возобновлении рабочего процесса.
        # Что, скорее всего, вам не нужно.
        with open("output.txt", "w") as f: # [!code highlight]
            f.write("Выполнен побочный эффект") # [!подсветка кода]
        значение = прерывание("вопрос")
        возвращаемое значение
    ```
  </Tab>

  <Tab title="Правильный ответ">
    В этом примере побочный эффект инкапсулирован в задачу, что обеспечивает согласованное выполнение при возобновлении работы.

    ```python theme={null}
    from langgraph.func import task

    @task # [!подсветка кода]
    def write_to_file(): # [!подсветка кода]
        with open("output.txt", "w") as f:
            f.write("Выполнен побочный эффект")

    @entrypoint(checkpointer=checkpointer)
    def my_workflow(inputs: dict) -> int:
        # Побочный эффект теперь заключен в задачу.
        write_to_file().result()
        значение = прерывание("вопрос")
        возвращаемое значение
    ```
  </Tab>
</Вкладки>

### Недетерминированный поток управления

Операции, которые могут давать разные результаты каждый раз (например, получение текущего времени или случайных чисел), следует инкапсулировать в задачи, чтобы гарантировать, что при возобновлении работы будет возвращен тот же результат.

* В задаче: Получить случайное число (5) → прервать → возобновить → (снова возвращает 5) → ...
* Не в задании: Получить случайное число (5) → прервать → возобновить → получить новое случайное число (7) → ...

Это особенно важно при использовании рабочих процессов с участием человека и множественными вызовами прерываний. LangGraph хранит список значений возобновления для каждой задачи/точки входа. При возникновении прерывания оно сопоставляется с соответствующим значением возобновления. Это сопоставление строго основано на индексе, поэтому порядок значений возобновления должен соответствовать порядку прерываний.

Если порядок выполнения не сохраняется при возобновлении работы, один из вызовов [`interrupt`](https://reference.langchain.com/python/langgraph/types/#langgraph.types.interrupt) может быть сопоставлен с неправильным значением `resume`, что приведет к некорректным результатам.

Пожалуйста, ознакомьтесь с разделом о детерминизме для получения более подробной информации.

<Вкладки>
  <Tab title="Неверно">
    В этом примере рабочий процесс использует текущее время для определения того, какую задачу следует выполнить. Это недетерминированный процесс, поскольку результат рабочего процесса зависит от времени его выполнения.

    ```python theme={null}
    from langgraph.func import entrypoint

    @entrypoint(checkpointer=checkpointer)
    def my_workflow(inputs: dict) -> int:
        t0 = inputs["t0"]
        t1 = time.time() # [!выделение кода]

        delta_t = t1 - t0

        если delta_t > 1:
            результат = slow_task(1).result()
            значение = прерывание("вопрос")
        еще:
            результат = slow_task(2).result()
            значение = прерывание("вопрос")

        возвращаться {
            "результат": результат,
            "значение": значение
        }
    ```
  </Tab>

  <Tab title="Правильный ответ">
    В этом примере рабочий процесс использует входные данные `t0` для определения того, какую задачу следует выполнить. Это детерминированный процесс, поскольку результат работы зависит только от входных данных.

    ```python theme={null}
    время импорта

    from langgraph.func import task

    @task # [!подсветка кода]
    def get_time() -> float: # [!подсветка кода]
        return time.time()

    @entrypoint(checkpointer=checkpointer)
    def my_workflow(inputs: dict) -> int:
        t0 = inputs["t0"]
        t1 = get_time().result() # [!выделение кода]

        delta_t = t1 - t0

        если delta_t > 1:
            результат = slow_task(1).result()
            значение = прерывание("вопрос")
        еще:
            результат = slow_task(2).result()
            значение = прерывание("вопрос")

        возвращаться {
            "результат": результат,
            "значение": значение
        }
    ```
  </Tab>
</Вкладки>
