# Упорство

LangGraph имеет встроенный слой сохранения состояния, реализованный с помощью контрольных точек. При компиляции графа с использованием контрольной точки, она сохраняет «контрольную точку» состояния графа на каждом шаге суперпоследовательности. Эти контрольные точки сохраняются в «потоке», к которому можно получить доступ после выполнения графа. Поскольку «потоки» позволяют получить доступ к состоянию графа после выполнения, открываются несколько мощных возможностей, включая участие человека, работу с памятью, перемещение во времени и отказоустойчивость. Ниже мы более подробно обсудим каждую из этих концепций.

## Темы

Поток — это уникальный идентификатор, присваиваемый каждой контрольной точке, сохраненной с помощью средства сохранения контрольных точек. Он содержит накопленное состояние последовательности [запусков](/langsmith/assistants#execution). При выполнении запуска [состояние](/oss/python/langgraph/graph-api#state) базового графа помощника будет сохранено в потоке.

При вызове графа с использованием контрольной точки необходимо **обязательно** указать `thread_id` в разделе `configurable` конфигурации:

```python theme={null}
{"configurable": {"thread_id": "1"}}
```

Текущее и историческое состояние потока можно получить. Для сохранения состояния поток необходимо создать до начала выполнения программы. API LangSmith предоставляет несколько конечных точек для создания и управления потоками и их состоянием. Дополнительную информацию см. в [справочнике по API](https://reference.langchain.com/python/langsmith/).

Контроллер контрольных точек использует `thread_id` в качестве первичного ключа для хранения и извлечения контрольных точек. Без него контроллер контрольных точек не сможет сохранить состояние или возобновить выполнение после прерывания, поскольку он использует `thread_id` для загрузки сохраненного состояния.

## Контрольные точки

Состояние потока в определенный момент времени называется контрольной точкой. Контрольная точка — это снимок состояния графа, сохраняемый на каждом супершаге, и представляется объектом `StateSnapshot` со следующими ключевыми свойствами:

* `config`: Конфигурация, связанная с этой контрольной точкой.
* `metadata`: Метаданные, связанные с этой контрольной точкой.
* `values`: Значения каналов состояния на данный момент времени.
* `next` Кортеж имен узлов, которые будут выполнены следующими в графе.
* `tasks`: кортеж объектов `PregelTask`, содержащих информацию о следующих задачах, которые будут выполнены. Если шаг уже был предпринят ранее, он будет включать информацию об ошибке. Если граф был прерван [динамически](/oss/python/langgraph/interrupts#pause-using-interrupt) внутри узла, задачи будут содержать дополнительные данные, связанные с прерываниями.

Контрольные точки сохраняются и могут быть использованы для восстановления состояния потока в более поздний момент времени.

Давайте посмотрим, какие контрольные точки сохраняются при вызове простого графа следующим образом:

```python theme={null}
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langchain_core.runnables import RunnableConfig
from typing import Annotated
from typing_extensions import TypedDict
из оператора импорт добавить

class State(TypedDict):
    foo: str
    bar: Annotated[list[str], add]

def node_a(state: State):
    return {"foo": "a", "bar": ["a"]}

def node_b(state: State):
    return {"foo": "b", "bar": ["b"]}


рабочий процесс = StateGraph(State)
workflow.add_node(node_a)
workflow.add_node(node_b)
workflow.add_edge(START, "node_a")
workflow.add_edge("node_a", "node_b")
workflow.add_edge("node_b", END)

checkpointer = InMemorySaver()
graph = workflow.compile(checkpointer=checkpointer)

config: RunnableConfig = {"configurable": {"thread_id": "1"}}
graph.invoke({"foo": "", "bar":[]}, config)
```

После построения графика мы ожидаем увидеть ровно 4 контрольные точки:

* Пустая контрольная точка с [`START`](https://reference.langchain.com/python/langgraph/constants/#langgraph.constants.START) в качестве следующего узла для выполнения.
* Контрольная точка с пользовательским вводом `{'foo': '', 'bar': []}` и `node_a` в качестве следующего узла для выполнения.
* Контрольная точка с выходными данными `node_a` `{'foo': 'a', 'bar': ['a']}` и `node_b` в качестве следующего узла для выполнения.
* Контрольная точка с выходными данными `node_b` `{'foo': 'b', 'bar': ['a', 'b']}` и без следующих узлов для выполнения.

Обратите внимание, что значения канала `bar` содержат выходные данные обоих узлов, поскольку у нас есть редуктор для канала `bar`.

### Получить состояние

При взаимодействии с сохраненным состоянием графа необходимо указать [идентификатор потока](#threads). Вы можете просмотреть *последнее* состояние графа, вызвав `graph.get_state(config)`. Это вернет объект `StateSnapshot`, соответствующий последней контрольной точке, связанной с идентификатором потока, указанным в конфигурации, или контрольной точке, связанной с идентификатором контрольной точки для потока, если таковой указан.

```python theme={null}
# получить последнюю версию состояния
config = {"configurable": {"thread_id": "1"}}
graph.get_state(config)

# Получить снимок состояния для конкретного checkpoint_id
config = {"configurable": {"thread_id": "1", "checkpoint_id": "1ef663ba-28fe-6528-8002-5a559208592c"}}
graph.get_state(config)
```

В нашем примере вывод команды `get_state` будет выглядеть следующим образом:

### Получить историю штата

Полную историю выполнения графа для заданного потока можно получить, вызвав метод [`graph.get_state_history(config)`](https://reference.langchain.com/python/langgraph/graphs/#langgraph.graph.state.CompiledStateGraph.get_state_history). Он вернет список объектов `StateSnapshot`, связанных с идентификатором потока, указанным в конфигурации. Важно отметить, что контрольные точки будут упорядочены хронологически, при этом самая последняя контрольная точка / `StateSnapshot` будет первой в списке.

```python theme={null}
config = {"configurable": {"thread_id": "1"}}
list(graph.get_state_history(config))
```

### Повтор

Также можно воспроизвести предыдущее выполнение графа. Если мы вызовем граф с идентификаторами потока (thread_id) и контрольной точки (checkpoint_id), то мы *воспроизведем* ранее выполненные шаги *до* контрольной точки, соответствующей этому идентификатору, и выполним только шаги *после* контрольной точки.

* `thread_id` — это идентификатор потока.
* `checkpoint_id` — это идентификатор, указывающий на конкретную контрольную точку в потоке.

Эти параметры необходимо передать при вызове графа в разделе `configurable` конфигурации:

```python theme={null}
config = {"configurable": {"thread_id": "1", "checkpoint_id": "0c62ca34-ac19-445d-bbb0-5b4984975b2a"}}
graph.invoke(None, config=config)
```

Важно отметить, что LangGraph знает, был ли конкретный шаг выполнен ранее. Если да, то LangGraph просто *повторяет* этот конкретный шаг в графе и не выполняет его повторно, а только для шагов *до* указанного `checkpoint_id`. Все шаги *после* `checkpoint_id` будут выполнены (т.е., будет создан новый форк), даже если они были выполнены ранее. Подробнее о воспроизведении см. в этом [руководстве по использованию time-travel](/oss/python/langgraph/use-time-travel).

### Обновление состояния

Помимо воспроизведения графа с определенных контрольных точек, мы также можем *редактировать* состояние графа. Мы делаем это с помощью метода [`update_state`](https://reference.langchain.com/python/langgraph/graphs/#langgraph.graph.state.CompiledStateGraph.update_state). Этот метод принимает три разных аргумента:

#### `config`

В конфигурационном файле должен содержаться `thread_id`, указывающий, какой поток нужно обновить. Если передан только `thread_id`, мы обновляем (или создаём форк) текущее состояние. При желании, если мы включим поле `checkpoint_id`, то создадим форк для выбранной контрольной точки.

#### `значения`

Это значения, которые будут использоваться для обновления состояния. Обратите внимание, что это обновление обрабатывается точно так же, как и любое обновление от узла. Это означает, что эти значения будут переданы функциям [редуктора](/oss/python/langgraph/graph-api#reducers), если они определены для некоторых каналов в состоянии графа. Это означает, что [`update_state`](https://reference.langchain.com/python/langgraph/graphs/#langgraph.graph.state.CompiledStateGraph.update_state) НЕ перезаписывает автоматически значения каналов для каждого канала, а только для каналов без редьюсеров. Давайте рассмотрим пример.

Предположим, вы определили состояние вашего графа с помощью следующей схемы (см. полный пример выше):

```python theme={null}
from typing import Annotated
from typing_extensions import TypedDict
из оператора импорт добавить

class State(TypedDict):
    foo: int
    bar: Annotated[list[str], add]
```

Предположим теперь, что текущее состояние графа следующее:

```
{"foo": 1, "bar": ["a"]}
```

Если вы обновите состояние, как показано ниже:

```python theme={null}
graph.update_state(config, {"foo": 2, "bar": ["b"]})
```

Тогда новое состояние графа будет следующим:

```
{"foo": 2, "bar": ["a", "b"]}
```

Ключ `foo` (канал) полностью изменяется (поскольку для этого канала не указан редуктор, поэтому [`update_state`](https://reference.langchain.com/python/langgraph/graphs/#langgraph.graph.state.CompiledStateGraph.update_state) перезаписывает его). Однако для ключа `bar` указан редуктор, поэтому к состоянию `bar` добавляется `"b"`.

#### `as_node`

Последний параметр, который вы можете указать по желанию при вызове [`update_state`](https://reference.langchain.com/python/langgraph/graphs/#langgraph.graph.state.CompiledStateGraph.update_state), — это `as_node`. Если вы его указали, обновление будет применено так, как если бы оно поступило от узла `as_node`. Если `as_node` не указан, он будет установлен на последний узел, обновивший состояние, если это не вызывает неоднозначности. Это важно, потому что следующие шаги выполнения зависят от последнего узла, предоставившего обновление, поэтому это можно использовать для управления тем, какой узел будет выполняться следующим. См. это [руководство по использованию time-travel, чтобы узнать больше о разветвлении состояния](/oss/python/langgraph/use-time-travel).

Схема состояния (state schema) определяет набор ключей, которые заполняются по мере выполнения графа. Как обсуждалось выше, состояние может быть записано контрольной точкой в ​​поток на каждом шаге графа, что обеспечивает сохранение состояния.

Но что, если нам нужно сохранить некоторую информацию *между ветками обсуждения*? Рассмотрим случай чат-бота, где мы хотим сохранить конкретную информацию о пользователе во *всех* чат-разговорах (например, ветках обсуждения) с этим пользователем!

Используя только контрольные точки, мы не можем обмениваться информацией между потоками. Это обуславливает необходимость интерфейса [`Store`](https://reference.langchain.com/python/langgraph/store/). В качестве примера мы можем определить `InMemoryStore` для хранения информации о пользователе между потоками. Мы просто компилируем наш граф с контрольной точкой, как и раньше, и с нашей новой переменной `in_memory_store`.

<Информация>
  **API LangGraph обрабатывает хранилища автоматически.**
  При использовании API LangGraph вам не нужно вручную реализовывать или настраивать хранилища. API автоматически обрабатывает всю инфраструктуру хранения данных.
</Info>

### Основные правила использования

Для начала давайте продемонстрируем это в отрыве от контекста, без использования LangGraph.

```python theme={null}
from langgraph.store.memory import InMemoryStore
in_memory_store = InMemoryStore()
```

Воспоминания обозначаются кортежем, который в данном конкретном примере будет выглядеть так: `(<user_id>, "memories")`. Пространство имен может иметь любую длину и представлять что угодно, не обязательно быть специфичным для пользователя.

```python theme={null}
user_id = "1"
namespace_for_memory = (user_id, "memories")
```

Для сохранения памяти в наше пространство имен в хранилище мы используем метод `store.put`. При этом мы указываем пространство имен, как определено выше, и пару ключ-значение для памяти: ключ — это просто уникальный идентификатор памяти (`memory_id`), а значение (словарь) — сама память.

```python theme={null}
memory_id = str(uuid.uuid4())
память = {"food_preference" : "Мне нравится пицца"}
in_memory_store.put(namespace_for_memory, memory_id, memory)
```

Мы можем считывать воспоминания из нашего пространства имен, используя метод `store.search`, который вернет все воспоминания для данного пользователя в виде списка. Самое последнее воспоминание будет последним в списке.

```python theme={null}
воспоминания = in_memory_store.search(namespace_for_memory)
воспоминания[-1].dict()
{'value': {'food_preference': 'Мне нравится пицца'},
 'key': '07e0caf4-1631-47b7-b15f-65515d4c1843',
 'пространство имен': ['1', 'воспоминания'],
 'created_at': '2024-10-02T17:22:31.590602+00:00',
 'updated_at': '2024-10-02T17:22:31.590605+00:00'}
```

Каждый тип памяти представляет собой класс Python ([`Item`](https://langchain-ai.github.io/langgraph/reference/store/#langgraph.store.base.Item)) с определенными атрибутами. Мы можем получить к нему доступ как к словарю, преобразовав его с помощью `.dict`, как показано выше.

Он обладает следующими характеристиками:

* `value`: Значение (само по себе словарь) этой памяти

* `key`: Уникальный ключ для этой области памяти в этом пространстве имен.

* `namespace`: Кортеж строк, пространство имен этого типа памяти.

  <Примечание>
    Хотя тип данных — `tuple[str, ...]`, при преобразовании в JSON он может быть сериализован как список (например, `['1', 'memories']`).
  </Примечание>

* `created_at`: Отметка времени создания этой памяти.

* `updated_at`: Метка времени обновления этой памяти.

### Семантический поиск

Помимо простого поиска, хранилище также поддерживает семантический поиск, позволяющий находить воспоминания на основе смысла, а не точных совпадений. Для этого настройте хранилище с использованием модели встраивания:

```python theme={null}
from langchain.embeddings import init_embeddings

хранилище = InMemoryStore(
    индекс={
        "embed": init_embeddings("openai:text-embedding-3-small"), # Поставщик встраивания
        "dims": 1536, # Размеры встраивания
        "fields": ["food_preference", "$"] # Поля для встраивания
    }
)
```

Теперь при поиске вы можете использовать запросы на естественном языке для нахождения релевантных воспоминаний:

```python theme={null}
# Найти воспоминания о предпочтениях в еде
# (Это можно сделать после добавления воспоминаний в хранилище)
воспоминания = store.search(
    namespace_for_memory,
    запрос="Что любит есть пользователь?",
    limit=3 # Возвращает 3 лучших матча
)
```

Вы можете управлять тем, какие части ваших воспоминаний будут встроены, настроив параметр `fields` или указав параметр `index` при сохранении воспоминаний:

```python theme={null}
# Хранилище с определенными полями для встраивания
store.put(
    namespace_for_memory,
    str(uuid.uuid4()),
    {
        "food_preference": "Я люблю итальянскую кухню",
        «Контекст»: «Обсуждение планов на ужин»
    },
    index=["food_preference"] # Встраивать только поле "food_preferences"
)

# Хранить без встраивания (доступ к данным по-прежнему возможен, но поиск по ним невозможен)
store.put(
    namespace_for_memory,
    str(uuid.uuid4()),
    {"system_info": "Последнее обновление: 01.01.2024"},
    index=False
)
```

### Использование в LangGraph

После этого мы используем `in_memory_store` из LangGraph. `in_memory_store` работает в тесной связи с контрольной точкой: контрольная точка сохраняет состояние в потоках, как обсуждалось выше, а `in_memory_store` позволяет нам хранить произвольную информацию для доступа *между* потоками. Мы компилируем граф с контрольной точкой и `in_memory_store` следующим образом.

```python theme={null}
from langgraph.checkpoint.memory import InMemorySaver

# Нам это нужно, потому что мы хотим включить возможность создания веток обсуждений (диалогов).
checkpointer = InMemorySaver()

# ... Определите граф ...

# Скомпилировать граф с использованием контрольной точки и сохранить его.
graph = graph.compile(checkpointer=checkpointer, store=in_memory_store)
```

Мы вызываем граф, используя `thread_id`, как и раньше, а также `user_id`, который мы будем использовать для присвоения имен нашим записям этому конкретному пользователю, как мы показали выше.

```python theme={null}
# Вызов графа
user_id = "1"
config = {"configurable": {"thread_id": "1", "user_id": user_id}}

# Для начала давайте просто поздороваемся с искусственным интеллектом
для обновления в graph.stream(
    {"messages": [{"role": "user", "content": "hi"}]}, config, stream_mode="updates"
):
    print(update)
```

Мы можем получить доступ к `in_memory_store` и `user_id` в *любом узле*, передав `store: BaseStore` и `config: RunnableConfig` в качестве аргументов узла. Вот как мы можем использовать семантический поиск в узле для поиска релевантных воспоминаний:

```python theme={null}
def update_memory(state: MessagesState, config: RunnableConfig, *, store: BaseStore):

    # Получаем идентификатор пользователя из конфигурации
    user_id = config["configurable"]["user_id"]

    # Пространство имен для памяти
    namespace = (user_id, "memories")

    # ... Проанализируйте разговор и создайте новое воспоминание

    # Создать новый идентификатор памяти
    memory_id = str(uuid.uuid4())

    # Мы создаём новое воспоминание
    store.put(namespace, memory_id, {"memory": memory})

```

Как мы показали выше, мы также можем получить доступ к хранилищу в любом узле и использовать метод `store.search` для получения воспоминаний. Напомним, что воспоминания возвращаются в виде списка объектов, которые можно преобразовать в словарь.

```python theme={null}
воспоминания[-1].dict()
{'value': {'food_preference': 'Мне нравится пицца'},
 'key': '07e0caf4-1631-47b7-b15f-65515d4c1843',
 'пространство имен': ['1', 'воспоминания'],
 'created_at': '2024-10-02T17:22:31.590602+00:00',
 'updated_at': '2024-10-02T17:22:31.590605+00:00'}
```

Мы можем получить доступ к этим воспоминаниям и использовать их в нашем моделировании.

## Библиотеки контрольных точек

В основе механизма контрольных точек лежат объекты контрольных точек, соответствующие интерфейсу [`BaseCheckpointSaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.base.BaseCheckpointSaver). LangGraph предоставляет несколько реализаций контрольных точек, все они реализованы в виде автономных устанавливаемых библиотек:

* `langgraph-checkpoint`: Базовый интерфейс для сохранения контрольных точек ([`BaseCheckpointSaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.base.BaseCheckpointSaver)) и интерфейса сериализации/десериализации ([`SerializerProtocol`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.serde.base.SerializerProtocol)). Включает реализацию контрольной точки в памяти ([`InMemorySaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.memory.InMemorySaver)) для экспериментов. LangGraph поставляется с включенным `langgraph-checkpoint`.
* `langgraph-checkpoint-sqlite`: Реализация средства проверки контрольных точек LangGraph, использующая базу данных SQLite ([`SqliteSaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.sqlite.SqliteSaver) / [`AsyncSqliteSaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.sqlite.aio.AsyncSqliteSaver)). Идеально подходит для экспериментов и локальных рабочих процессов. Требуется отдельная установка.
* `langgraph-checkpoint-postgres`: Усовершенствованный инструмент для создания контрольных точек, использующий базу данных Postgres ([`PostgresSaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.postgres.PostgresSaver) / [`AsyncPostgresSaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.postgres.aio.AsyncPostgresSaver)), используемый в LangSmith. Идеально подходит для использования в продакшене. Требуется отдельная установка.
* `langgraph-checkpoint-cosmosdb`: Реализация контрольной точки LangGraph, использующая Azure Cosmos DB (@\[`CosmosDBSaver`] / @\[`AsyncCosmosDBSaver`]). Идеально подходит для использования в производственной среде с Azure. Поддерживает как синхронные, так и асинхронные операции. Требуется отдельная установка.

### Интерфейс контрольных точек

Каждый контрольный указатель соответствует интерфейсу [`BaseCheckpointSaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.base.BaseCheckpointSaver) и реализует следующие методы:

* `.put` - Сохраняет контрольную точку с её конфигурацией и метаданными.
* `.put_writes` - Сохраняет промежуточные записи, связанные с контрольной точкой (т.е. [ожидающие записи](#pending-writes)).
* `.get_tuple` — Получает кортеж контрольных точек для заданной конфигурации (`thread_id` и `checkpoint_id`). Он используется для заполнения `StateSnapshot` в `graph.get_state()`.
* `.list` — Список контрольных точек, соответствующих заданной конфигурации и критериям фильтрации. Используется для заполнения истории состояний в `graph.get_state_history()`.

Если контрольная точка используется с асинхронным выполнением графа (т.е. выполнением графа с помощью `.ainvoke`, `.astream`, `.abatch`), будут использоваться асинхронные версии указанных выше методов (`.aput`, `.aput_writes`, `.aget_tuple`, `.alist`).

<Примечание>
  Для асинхронного запуска графа можно использовать [`InMemorySaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.memory.InMemorySaver) или асинхронные версии контрольных точек Sqlite/Postgres — [`AsyncSqliteSaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.sqlite.aio.AsyncSqliteSaver) / [`AsyncPostgresSaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.postgres.aio.AsyncPostgresSaver).
</Примечание>

### Сериализатор

Когда контрольные точки сохраняют состояние графа, им необходимо сериализовать значения каналов в этом состоянии. Это делается с помощью объектов сериализатора.

`langgraph_checkpoint` определяет [протокол](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.serde.base.SerializerProtocol) для реализации сериализаторов и предоставляет реализацию по умолчанию ([`JsonPlusSerializer`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.serde.jsonplus.JsonPlusSerializer)), которая обрабатывает широкий спектр типов, включая примитивы LangChain и LangGraph, даты и время, перечисления и многое другое.

#### Сериализация с помощью `pickle`

По умолчанию сериализатор [`JsonPlusSerializer`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.serde.jsonplus.JsonPlusSerializer) использует ormsgpack и JSON, что не подходит для всех типов объектов.

Если вы хотите использовать pickle для объектов, которые в настоящее время не поддерживаются нашим кодировщиком msgpack (например, датафреймы Pandas),
Вы можете использовать аргумент `pickle_fallback` класса [`JsonPlusSerializer`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.serde.jsonplus.JsonPlusSerializer):

```python theme={null}
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.checkpoint.serde.jsonplus import JsonPlusSerializer

# ... Определите граф ...
graph.compile(
    checkpointer=InMemorySaver(serde=JsonPlusSerializer(pickle_fallback=True))
)
```

#### Шифрование

Контрольные точки могут опционально шифровать все сохраняемое состояние. Чтобы включить эту функцию, передайте экземпляр [`EncryptedSerializer`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.serde.encrypted.EncryptedSerializer) в аргумент `serde` любой реализации [`BaseCheckpointSaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.base.BaseCheckpointSaver). Самый простой способ создать зашифрованный сериализатор — использовать [`from_pycryptodome_aes`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.serde.encrypted.EncryptedSerializer.from_pycryptodome_aes), который считывает ключ AES из переменной среды `LANGGRAPH_AES_KEY` (или принимает аргумент `key`):

```python theme={null}
импорт sqlite3

from langgraph.checkpoint.serde.encrypted import EncryptedSerializer
from langgraph.checkpoint.sqlite import SqliteSaver

serde = EncryptedSerializer.from_pycryptodome_aes() # считывает LANGGRAPH_AES_KEY
checkpointer = SqliteSaver(sqlite3.connect("checkpoint.db"), serde=serde)
```

```python theme={null}
from langgraph.checkpoint.serde.encrypted import EncryptedSerializer
from langgraph.checkpoint.postgres import PostgresSaver

serde = EncryptedSerializer.from_pycryptodome_aes()
checkpointer = PostgresSaver.from_conn_string("postgresql://...", serde=serde)
checkpointer.setup()
```

При работе с LangSmith шифрование автоматически включается, если присутствует `LANGGRAPH_AES_KEY`, поэтому вам нужно только указать переменную окружения. Другие схемы шифрования можно использовать, реализовав [`CipherProtocol`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.serde.base.CipherProtocol) и передав его в [`EncryptedSerializer`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.serde.encrypted.EncryptedSerializer).

## Возможности

### Человек в процессе

Во-первых, контрольные точки облегчают [рабочие процессы с участием человека](/oss/python/langgraph/interrupts), позволяя людям проверять, прерывать и утверждать шаги графа. Контрольные точки необходимы для таких рабочих процессов, поскольку человек должен иметь возможность просматривать состояние графа в любой момент времени, и граф должен возобновить выполнение после того, как человек внесет какие-либо изменения в его состояние. См. [руководства по использованию](/oss/python/langgraph/interrupts) для примеров.

### Память

Во-вторых, контрольные точки позволяют сохранять память между взаимодействиями. В случае повторных взаимодействий между людьми (например, в диалогах) любые последующие сообщения могут быть отправлены в этот поток, который сохранит память о предыдущих. См. [Добавление памяти](/oss/python/langgraph/add-memory) для получения информации о том, как добавлять и управлять памятью диалогов с помощью контрольных точек.

### Путешествие во времени

Во-третьих, контрольные точки позволяют совершать «путешествия во времени», давая пользователям возможность воспроизводить предыдущие выполнения графа для анализа и/или отладки конкретных шагов графа. Кроме того, контрольные точки позволяют создавать форки состояния графа в произвольных контрольных точках для исследования альтернативных траекторий.

### Отказоустойчивость

Наконец, контрольные точки также обеспечивают отказоустойчивость и восстановление после ошибок: если один или несколько узлов выходят из строя на данном супершаге, вы можете перезапустить граф с последнего успешного шага. Кроме того, когда узел графа выходит из строя в середине выполнения на данном супершаге, LangGraph сохраняет ожидающие записи контрольных точек со всех других узлов, которые успешно завершили выполнение на этом супершаге, так что при возобновлении выполнения графа с этого супершага нам не нужно повторно запускать успешно выполненные узлы.

#### Ожидающие записи

Кроме того, если узел графа выходит из строя в середине выполнения на определенном супершаге, LangGraph сохраняет ожидающие записи контрольных точек со всех других узлов, которые успешно завершили выполнение на этом супершаге, так что при возобновлении выполнения графа с этого супершага мы не запускаем повторно успешно работавшие узлы.
