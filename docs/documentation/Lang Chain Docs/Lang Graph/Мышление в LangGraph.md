# Мышление в LangGraph

> Узнайте, как мыслить о создании агентов с помощью LangGraph

При создании агента с помощью LangGraph вы сначала разбиваете его на отдельные этапы, называемые **узлами**. Затем вы описываете различные решения и переходы от каждого из ваших узлов. Наконец, вы соединяете узлы между собой посредством общего **состояния**, из которого каждый узел может считывать и в которое может записывать данные.

В этом пошаговом руководстве мы расскажем вам о процессе создания агента электронной почты для службы поддержки клиентов с помощью LangGraph.

## Начните с процесса, который вы хотите автоматизировать

Представьте, что вам нужно создать агента на основе искусственного интеллекта, который будет обрабатывать электронные письма службы поддержки клиентов. Ваша команда разработчиков предоставила вам следующие требования:

```txt theme={null}
Агент должен:

- Читать входящие электронные письма от клиентов
— Классифицируйте их по срочности и теме.
— Найдите необходимую документацию, чтобы получить ответы на свои вопросы.
- Составьте соответствующие ответы.
- Передавать сложные вопросы специалистам.
- Планируйте последующие встречи по мере необходимости.

Примеры сценариев обработки:

1. Простой вопрос о продукте: «Как мне сбросить пароль?»
2. Сообщение об ошибке: «Функция экспорта аварийно завершает работу при выборе формата PDF».
3. Срочная проблема с оплатой: «С меня дважды списали деньги за подписку!»
4. Запрос на добавление функции: «Можно ли добавить темный режим в мобильное приложение?»
5. Сложная техническая проблема: «Наша интеграция API периодически завершается с ошибкой 504».
```

Для реализации агента в LangGraph обычно выполняются одни и те же пять шагов.

## Шаг 1: Составьте план рабочего процесса в виде отдельных этапов

Начните с определения отдельных этапов вашего процесса. Каждый этап станет **узлом** (функцией, выполняющей одну конкретную задачу). Затем набросайте схему, показывающую, как эти этапы связаны друг с другом.

```тема русалки={null}
блок-схема TD
    A[НАЧАЛО] --> B[Прочитать письмо]
    B --> C [Классифицировать намерение]

    C -.-> D[Поиск документов]
    C -.-> E[Отслеживание ошибок]
    C -.-> F[Обзор человеческого поведения]

    Д --> Г [Черновик ответа]
    Е --> Г
    Ф --> Г

    Г -.-> Х[Обзор человеческих отношений]
    G -.-> I[Отправить ответ]

    H --> J[END]
    Я --> J[END]
```

Стрелками на этой диаграмме показаны возможные пути, но фактическое решение о том, какой путь выбрать, принимается внутри каждого узла.

Теперь, когда мы определили компоненты нашего рабочего процесса, давайте разберемся, что должен делать каждый узел:

* `Чтение электронного письма`: Извлечение и анализ содержимого электронного письма
* `Классификация намерений`: Используйте LLM для определения срочности и темы, а затем направьте запрос к соответствующему действию.
* `Поиск документов`: Запрос к базе знаний для получения необходимой информации.
* `Отслеживание ошибок`: Создание или обновление информации об ошибке в системе отслеживания.
* `Черновик ответа`: Сгенерируйте соответствующий ответ
* «Проверка человеком»: Передача запроса на утверждение или обработку оператором.
* `Отправить ответ`: отправить ответ по электронной почте

<Совет>
  Обратите внимание, что некоторые узлы принимают решения о дальнейшем перемещении («Классифицировать намерение», «Написать черновик ответа», «Проверить человеком»), в то время как другие всегда переходят к одному и тому же следующему шагу («Прочитать электронное письмо» всегда переходит к «Классифицировать намерение», «Поиск документа» всегда переходит к «Написать черновик ответа»).
</Совет>

## Шаг 3: Создайте свой штат

Состояние — это общая [память](/oss/python/concepts/memory), доступная всем узлам вашего агента. Представьте её как блокнот, который ваш агент использует для отслеживания всего, что он узнаёт и решает в процессе работы.

Для работы нашего почтового агента нам необходимо отслеживать:

* Исходное электронное письмо и информация об отправителе (восстановить их позже будет невозможно).
* Результаты классификации (необходимы для нескольких последующих узлов)
* Результаты поиска и данные о клиентах (повторная загрузка обходится дорого)
* Проект ответа (должен сохраняться на протяжении всего процесса рецензирования)
* Метаданные выполнения (для отладки и восстановления)

### Сохраняйте исходное состояние, форматируйте подсказки по запросу

<Совет>
  Ключевой принцип: в вашем состоянии должны храниться необработанные данные, а не отформатированный текст. Подсказки форматирования размещайте внутри узлов, когда это необходимо.
</Совет>

Это разделение означает:

* Разные узлы могут форматировать одни и те же данные по-разному в соответствии со своими потребностями.
* Вы можете изменять шаблоны подсказок, не изменяя схему состояния.
* Отладка стала понятнее – вы точно видите, какие данные получил каждый узел.
* Ваш агент может развиваться, не нарушая существующее состояние.

Давайте определим, что представляет собой наше государство:

```python theme={null}
from typing import TypedDict, Literal

# Определение структуры для классификации электронных писем
class EmailClassification(TypedDict):
    intent: Literal["question", "bug", "billing", "feature", "complex"]
    срочность: Буквальная ["низкая", "средняя", "высокая", "критическая"]
    тема: строка
    резюме: стр.

class EmailAgentState(TypedDict):
    # Необработанные данные электронной почты
    email_content: str
    sender_email: str
    email_id: str

    # Результат классификации
    Классификация: EmailClassification | Нет

    # Необработанные результаты поиска/API
    search_results: list[str] | None # Список фрагментов исходного документа
    customer_history: dict | None # Необработанные данные о клиентах из CRM

    # Сгенерированный контент
    draft_response: str | None
    сообщения: список[str] | Нет
```

Обратите внимание, что состояние содержит только необработанные данные — никаких шаблонов подсказок, никаких отформатированных строк, никаких инструкций. Результаты классификации хранятся в виде единого словаря, непосредственно из LLM.

## Шаг 4: Создайте свои узлы

Теперь мы реализуем каждый шаг как функцию. Узел в LangGraph — это просто функция Python, которая принимает текущее состояние и возвращает обновления к нему.

### Обрабатывайте ошибки надлежащим образом

Для обработки различных ошибок требуются разные стратегии:

| Тип ошибки                                                                       | Кто её исправляет        | Стратегия                                                         | Когда использовать                                               |
| -------------------------------------------------------------------------------- | ------------------------ | ----------------------------------------------------------------- | ---------------------------------------------------------------- |
| Временные ошибки (проблемы с сетью, ограничения скорости)                        | Система (автоматическая) | Политика повторных попыток                                        | Временные сбои, которые обычно устраняются при повторной попытке |
| Ошибки, восстанавливаемые LLM (сбои инструментов, проблемы с парсингом)          | LLM                      | Сохранять ошибку в состоянии и возвращаться к исходному состоянию | LLM может увидеть ошибку и скорректировать свой подход           |
| Ошибки, исправляемые пользователем (отсутствует информация, нечеткие инструкции) | Человек                  | Пауза с помощью `interrupt()`                                     | Требуется ввод данных пользователем для продолжения              |
| Непредвиденные ошибки                                                            | Разработчик              | Пусть они всплывут                                                | Неизвестные проблемы, требующие отладки                          |

### Реализация узлов нашего почтового агента

Мы реализуем каждый узел как простую функцию. Помните: узлы принимают состояние, выполняют работу и возвращают обновления.

<AccordionGroup>
  <Accordion title="Чтение и классификация узлов" icon="мозг">
    ```python theme={null}
    from typing import Literal
    from langgraph.graph import StateGraph, START, END
    from langgraph.types import interrupt, Command, RetryPolicy
    from langchain_openai import ChatOpenAI
    from langchain.messages import HumanMessage

    llm = ChatOpenAI(model="gpt-5-nano")

    def read_email(state: EmailAgentState) -> dict:
        «Извлечение и анализ содержимого электронных писем»
        # В рабочей среде это будет подключаться к вашей почтовой службе.
        возвращаться {
            "messages": [HumanMessage(content=f"Обработка электронного письма: {state['email_content']}")]
        }

    def classify_intent(state: EmailAgentState) -> Command[Literal["search_documentation", "human_review", "draft_response", "bug_tracking"]]:
        «Используйте LLM для классификации намерений и срочности электронных писем, а затем направляйте их соответствующим образом».

        # Создание структурированной LLM-функции, возвращающей словарь EmailClassification
        structured_llm = llm.with_structured_output(EmailClassification)

        # Форматирование приглашения ввода выполняется по запросу, а не сохраняется в состоянии.
        classification_prompt = f"""
        Проанализируйте это электронное письмо от клиента и классифицируйте его:

        Электронная почта: {state['email_content']}
        От: {state['sender_email']}

        Укажите классификацию, включающую цель, срочность, тему и краткое содержание.
        """

        # Получение структурированного ответа непосредственно в виде словаря
        классификация = structured_llm.invoke(classification_prompt)

        # Определение следующего узла на основе классификации
        если classification['intent'] == 'billing' или classification['urgency'] == 'critical':
            goto = "human_review"
        elif classification['intent'] in ['question', 'feature']:
            goto = "search_documentation"
        elif classification['intent'] == 'bug':
            goto = "bug_tracking"
        еще:
            goto = "draft_response"

        # Классификация магазина как единый словарь в состоянии
        return Command(
            обновление={"классификация": классификация},
            перейти = перейти к
        )
    ```

## Шаг 5: Соедините провода

Теперь соединим наши узлы в работающий граф. Поскольку наши узлы самостоятельно принимают решения о маршрутизации, нам потребуется лишь несколько важных ребер.

Чтобы включить прерывания с участием человека при использовании `interrupt()`, нам необходимо скомпилировать программу с контрольной точкой для сохранения состояния между запусками:

<Accordion title="Graph compilation code" icon="diagram-project" defaultOpen={true}>
  ```python theme={null}
  from langgraph.checkpoint.memory import MemorySaver
  from langgraph.types import RetryPolicy

  # Создание графика
  рабочий процесс = StateGraph(EmailAgentState)

  # Добавить узлы с соответствующей обработкой ошибок
  workflow.add_node("read_email", read_email)
  workflow.add_node("classify_intent", classify_intent)

  # Добавить политику повторных попыток для узлов, которые могут испытывать временные сбои.
  workflow.add_node(
      "поиск_документации",
      поиск_документации,
      retry_policy=RetryPolicy(max_attempts=3)
  )
  workflow.add_node("bug_tracking", bug_tracking)
  workflow.add_node("draft_response", draft_response)
  workflow.add_node("human_review", human_review)
  workflow.add_node("send_reply", send_reply)

  # Добавьте только необходимые ребра
  workflow.add_edge(START, "read_email")
  workflow.add_edge("read_email", "classify_intent")
  workflow.add_edge("send_reply", END)

  # Компиляция с контрольными точками для обеспечения сохранения данных; в случае запуска графа с Local_Server --> компилируйте без контрольных точек.
  память = MemorySaver()
  app = workflow.compile(checkpointer=memory)
  ```
</Аккордеон>

Структура графа минимальна, поскольку маршрутизация происходит внутри узлов через объекты [`Command`](https://reference.langchain.com/python/langgraph/types/#langgraph.types.Command). Каждый узел указывает, куда он может перейти, используя подсказки типов, например `Command[Literal["node1", "node2"]]`, что делает поток явным и отслеживаемым.

### Дополнительные соображения

<Accordion title="Компромиссы в гранулярности узлов" icon="sliders">
  <Информация>
    В этом разделе рассматриваются компромиссы при проектировании с учетом гранулярности узлов. Большинство приложений могут пропустить этот раздел и использовать описанные выше шаблоны.
  </Info>

  Возможно, вы задаетесь вопросом: почему бы не объединить `Чтение электронных писем` и `Классификация намерений` в один узел?

  Или зачем разделять поиск документов и ответы на черновики?

  Ответ кроется в компромиссе между устойчивостью и наблюдаемостью.

  **Вопрос отказоустойчивости:** Функция [устойчивого выполнения](/oss/python/langgraph/durable-execution) в LangGraph создает контрольные точки на границах узлов. Когда рабочий процесс возобновляется после прерывания или сбоя, он начинается с начала узла, где выполнение остановилось. Меньшие узлы означают более частые контрольные точки, что означает меньше работы, которую нужно повторить, если что-то пойдет не так. Если вы объедините несколько операций в один большой узел, сбой в конце будет означать повторное выполнение всего с начала этого узла.

  Почему мы выбрали именно такой подход к анализу поведения почтового агента:

  * **Изоляция внешних сервисов:** Поиск документов и отслеживание ошибок являются отдельными узлами, поскольку они обращаются к внешним API. Если служба поиска работает медленно или дает сбой, мы хотим изолировать это от вызовов LLM. Мы можем добавить политики повторных попыток к этим конкретным узлам, не затрагивая другие.

  * **Промежуточная видимость:** Наличие узла `Classify Intent` позволяет нам проверить, какое решение приняла система LLM перед принятием мер. Это ценно для отладки и мониторинга — вы можете точно видеть, когда и почему агент направляет запрос на проверку человеку.

  * **Различные режимы сбоев:** Для вызовов LLM, поиска в базе данных и отправки электронной почты используются разные стратегии повторных попыток. Отдельные узлы позволяют настраивать их независимо друг от друга.

  * **Повторное использование и тестирование:** Более мелкие узлы проще тестировать изолированно и повторно использовать в других рабочих процессах.

  Другой допустимый подход: можно объединить операции «Чтение электронного письма» и «Классификация намерения» в один узел. При этом вы потеряете возможность проверять исходный текст электронного письма перед классификацией и будете повторять обе операции при любой ошибке в этом узле. Для большинства приложений преимущества отдельных узлов в плане наблюдаемости и отладки оправдывают этот компромисс.

  Вопросы на уровне приложения: обсуждение кэширования на шаге 2 (следует ли кэшировать результаты поиска) — это решение на уровне приложения, а не функция фреймворка LangGraph. Вы реализуете кэширование внутри своих функций Node.js в зависимости от ваших конкретных требований — LangGraph не предписывает этого.

  Вопросы производительности: большее количество узлов не означает замедление выполнения. LangGraph по умолчанию записывает контрольные точки в фоновом режиме ([асинхронный режим обеспечения надежности](/oss/python/langgraph/durable-execution#durability-modes)), поэтому ваш граф продолжает работу, не дожидаясь завершения создания контрольных точек. Это означает, что вы получаете частые контрольные точки с минимальным влиянием на производительность. При необходимости вы можете настроить это поведение — использовать режим «exit» для создания контрольных точек только по завершении или режим «sync» для блокировки выполнения до тех пор, пока не будет создана каждая контрольная точка.
