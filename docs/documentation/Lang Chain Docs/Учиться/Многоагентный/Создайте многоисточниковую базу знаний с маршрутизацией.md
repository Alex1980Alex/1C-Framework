# Создание многоисточниковой базы знаний с маршрутизацией

## Обзор

Паттерн **маршрутизатора** — это [многоагентная](/oss/python/langchain/multi-agent) архитектура, в которой этап маршрутизации классифицирует входные данные и направляет их специализированным агентам, а результаты синтезируются в комбинированный ответ. Этот паттерн особенно эффективен, когда знания вашей организации хранятся в разных **вертикалях** — отдельных областях знаний, каждая из которых требует своего собственного агента со специализированными инструментами и подсказками.

В этом руководстве вы создадите маршрутизатор базы знаний из нескольких источников, который продемонстрирует эти преимущества на примере реалистичного корпоративного сценария. Система будет координировать работу трех специалистов:

* **Агент GitHub**, который осуществляет поиск в коде, по проблемам и запросам на слияние.
* **Агент Notion**, осуществляющий поиск во внутренней документации и вики-сайтах.
* **Агент Slack**, который осуществляет поиск по соответствующим веткам обсуждений и темам.

Когда пользователь задает вопрос: «Как аутентифицировать запросы к API?», маршрутизатор разбивает запрос на подвопросы, специфичные для источника, параллельно направляет их соответствующим агентам и синтезирует результаты в связный ответ.

```тема русалки={null}
график LR
    A([Запрос]) --> B[Классифицировать]
    B --> C[Агент GitHub]
    B --> D[Объектив понятия]
    B --> E[Агент Slack]
    C --> F[Синтезировать]
    Д --> Ф
    Е --> Ф
    F --> G ([Общий ответ])
```

### Зачем использовать роутер?

Схема расположения точек крепления маршрутизатора предоставляет ряд преимуществ:

* **Параллельное выполнение**: одновременный запрос к нескольким источникам, что снижает задержку по сравнению с последовательным подходом.
* **Специализированные агенты**: Для каждого направления разработаны специализированные инструменты и подсказки, оптимизированные для его области применения.
* **Выборочная маршрутизация**: Не каждый запрос требует каждого источника — маршрутизатор интеллектуально выбирает соответствующие вертикали.
* **Целевые подвопросы**: Каждый агент получает вопрос, адаптированный к его предметной области, что повышает качество результатов.
* **Чистый синтез**: Результаты из нескольких источников объединяются в единый, согласованный ответ.

## 1. Определите состояние

Сначала определим схемы состояний. Мы используем три типа:

* **`AgentInput`**: Простое состояние, передаваемое каждому субагенту (просто запрос)
* **`AgentOutput`**: Результат, возвращаемый каждым субагентом (имя источника + результат)
* **`RouterState`**: Основное состояние рабочего процесса, отслеживающее запрос, классификацию, результаты и окончательный ответ.

```python theme={null}
from typing import Annotated, Literal, TypedDict
импортный оператор


class AgentInput(TypedDict):
    «Простое входное состояние для каждого субагента».
    запрос: str


class AgentOutput(TypedDict):
    «Результаты работы каждого субагента».
    источник: str
    результат: строка


class Classification(TypedDict):
    «Единое решение по маршрутизации: какому агенту позвонить с каким запросом».
    источник: Literal["github", "notion", "slack"]
    запрос: str


class RouterState(TypedDict):
    запрос: str
    классификации: список[Классификация]
    Результаты: Annotated[list[AgentOutput], operator.add] # Редуктор собирает параллельные результаты
    окончательный_ответ: str
```

Поле `results` использует **редуктор** (`operator.add` в Python, функция конкатенации в JS) для сбора результатов параллельного выполнения агентов в единый список.

## 2. Определите инструменты для каждого направления

Создайте инструменты для каждой области знаний. В производственной системе они будут вызывать реальные API. В этом руководстве мы используем заглушки, которые возвращают фиктивные данные. Мы определяем 7 инструментов в 3 направлениях: GitHub (поиск кода, проблем, запросов на слияние), Notion (поиск документации, получение страницы) и Slack (поиск сообщений, получение ветки обсуждения).

```python expandable theme={null}
from langchain.tools import tool


@инструмент
def search_code(query: str, repo: str = "main") -> str:
    «Ищите код в репозиториях GitHub».
    return f"Найден код, соответствующий '{query}' в {repo}: промежуточное ПО аутентификации в src/auth.py"


@инструмент
def search_issues(query: str) -> str:
    «Поиск проблем и запросов на слияние в GitHub».
    "Найдено 3 проблемы, соответствующие '{query}': #142 (документация по аутентификации API), #89 (процесс OAuth), #203 (обновление токена)"


@инструмент
def search_prs(query: str) -> str:
    «Детали реализации можно найти в запросах на слияние (pull requests)».
    return f"PR #156 добавил аутентификацию JWT, PR #178 обновил области действия OAuth"


@инструмент
def search_notion(query: str) -> str:
    «Поиск документации в рабочем пространстве Notion».
    Возвращается "Найденная документация: 'Руководство по аутентификации API' — описывает процесс OAuth2, ключи API и токены JWT."


@инструмент
def get_page(page_id: str) -> str:
    «Получите доступ к конкретной странице Notion по ID».
    return f"Содержимое страницы: пошаговые инструкции по настройке аутентификации"


@инструмент
def search_slack(query: str) -> str:
    «Поиск сообщений и веток обсуждений в Slack».
    Возвращается сообщение "Обсуждение найдено в канале #engineering: 'Используйте токены Bearer для аутентификации API, см. документацию по процедуре обновления'"


@инструмент
def get_thread(thread_id: str) -> str:
    """Найти конкретную ветку обсуждений в Slack.""
    "В обсуждении рассматриваются лучшие практики ротации ключей API"
```

## 3. Создайте специализированных агентов

Создайте отдельного агента для каждой вертикали. Каждый агент будет иметь инструменты, специфичные для данной области, и подсказку, оптимизированную для соответствующего источника знаний. Все три агента следуют одному и тому же шаблону — различаются только инструменты и системная подсказка.

```python expandable theme={null}
from langchain.agents import create_agent
from langchain.chat_models import init_chat_model

модель = init_chat_model("openai:gpt-4.1")

github_agent = create_agent(
    модель,
    tools=[search_code, search_issues, search_prs],
    system_prompt=(
        «Вы — эксперт по GitHub. Отвечайте на вопросы о коде».
        "Ссылки на API и подробности реализации можно найти, выполнив поиск"
        «Репозитории, проблемы и запросы на слияние».
    ),
)

notion_agent = create_agent(
    модель,
    tools=[search_notion, get_page],
    system_prompt=(
        «Вы — эксперт по Notion. Ответьте на вопросы о внутренних процессах».
        «процессы, политики и документация команды путем поиска»
        «Рабочее пространство Notion в организации».
    ),
)

slack_agent = create_agent(
    модель,
    tools=[search_slack, get_thread],
    system_prompt=(
        «Вы — эксперт по Slack. Отвечайте на вопросы, используя поиск».
        «соответствующие темы и обсуждения, в которых участвовали члены команды»
        «Обмен знаниями и решениями».
    ),
)
```

## 4. Создайте рабочий процесс маршрутизатора

Теперь создадим рабочий процесс маршрутизатора, используя StateGraph. Рабочий процесс состоит из четырех основных шагов:

1. **Классификация**: Проанализируйте запрос и определите, каких агентов следует вызвать с какими подвопросами.
2. **Маршрут**: Параллельно распределите сообщение между выбранными агентами с помощью команды `Send`.
3. **Агенты запросов**: Каждый агент получает простой `AgentInput` и возвращает `AgentOutput`.
4. **Синтез**: Объедините полученные результаты в связный ответ.

```python theme={null}
from pydantic import BaseModel, Field
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send

router_llm = init_chat_model("openai:gpt-4.1-mini")


# Определение структурированной схемы выходных данных для классификатора
class ClassificationResult(BaseModel): # [!подсветка кода]
    «Результат классификации пользовательского запроса на подвопросы, специфичные для конкретного агента».
    классификация: список[Классификация] = Поле(
        description="Список агентов, которых следует вызвать для ответа на целевые подвопросы"
    )


def classify_query(state: RouterState) -> dict:
    «Классифицировать запрос и определить, каких агентов следует вызвать».
    structured_llm = router_llm.with_structured_output(ClassificationResult) # [!code highlight]

    результат = structured_llm.invoke([
        {
            "роль": "система",
            "содержание": """Проанализируйте этот запрос и определите, к каким базам знаний следует обратиться."
Для каждого соответствующего источника сгенерируйте целевой подвопрос, оптимизированный для этого источника.

Доступные источники:
- GitHub: код, ссылки на API, детали реализации, проблемы, запросы на слияние.
- концепция: Внутренняя документация, процессы, политики, командные вики.
- Slack: Командные обсуждения, неформальный обмен знаниями, недавние беседы

Возвращать ТОЛЬКО те источники, которые имеют отношение к запросу. Каждый источник должен содержать
Целенаправленный подвопрос, оптимизированный для конкретной области знаний.

Пример запроса "Как аутентифицировать запросы к API?":
- github: "Какой код аутентификации существует? Найдите информацию о промежуточном ПО аутентификации, обработке JWT."
- Замечание: "Какая документация по аутентификации существует? Ищите руководства по аутентификации через API."
(Время ожидания опущено, поскольку оно не имеет отношения к данному техническому вопросу)
        },
        {"role": "user", "content": state["query"]}
    ])

    return {"classifications": result.classifications}


def route_to_agents(state: RouterState) -> list[Send]:
    «Распределение информации между агентами осуществляется на основе классификации».
    возвращаться [
        Send(c["source"], {"query": c["query"]}) # [!code highlight]
        for c in state["classifications"]
    ]


def query_github(state: AgentInput) -> dict:
    """Запрос к агенту GitHub."""
    результат = github_agent.invoke({
        "messages": [{"role": "user", "content": state["query"]}] # [!code highlight]
    })
    return {"results": [{"source": "github", "result": result["messages"][-1].content}]}


def query_notion(state: AgentInput) -> dict:
    «Запросите информацию у агента Notion».
    результат = notion_agent.invoke({
        "messages": [{"role": "user", "content": state["query"]}] # [!code highlight]
    })
    return {"results": [{"source": "notion", "result": result["messages"][-1].content}]}


def query_slack(state: AgentInput) -> dict:
    """Запрос к агенту Slack.""
    результат = slack_agent.invoke({
        "messages": [{"role": "user", "content": state["query"]}] # [!code highlight]
    })
    return {"results": [{"source": "slack", "result": result["messages"][-1].content}]}


def synthesize_results(state: RouterState) -> dict:
    «Объедините результаты всех участников в единый, связный ответ».
    if not state["results"]:
        return {"final_answer": "Результаты не найдены ни в одном источнике знаний."}

    # Форматирование результатов для синтеза
    отформатированный = [
        f"**Из {r['source'].title()}:**\n{r['result']}"
        for r in state["results"]
    ]

    synthesis_response = router_llm.invoke([
        {
            "роль": "система",
            "content": f"""Обобщите эти результаты поиска, чтобы ответить на исходный вопрос: "{state['query']}"

- Объединение информации из нескольких источников без избыточности.
- Выделите наиболее актуальную и полезную информацию.
- Обратите внимание на любые расхождения между источниками.
— Ответ должен быть кратким и хорошо структурированным.
        },
        {"role": "user", "content": "\n\n".join(formatted)}
    ])

    return {"final_answer": synthesis_response.content}
```

## 5. Составьте рабочий процесс

Теперь соберите рабочий процесс, соединив узлы ребрами. Ключевым моментом является использование функции `add_conditional_edges` с функцией маршрутизации для обеспечения параллельного выполнения:

```python theme={null}
рабочий процесс = (
    StateGraph(RouterState)
    .add_node("classify", classify_query)
    .add_node("github", query_github)
    .add_node("notion", query_notion)
    .add_node("slack", query_slack)
    .add_node("synthesize", synthesize_results)
    .add_edge(START, "classify")
    .add_conditional_edges("classify", route_to_agents, ["github", "notion", "slack"])
    .add_edge("github", "synthesize")
    .add_edge("notion", "synthesize")
    .add_edge("slack", "synthesize")
    .add_edge("synthesize", END)
    .compile()
)
```

Вызов `add_conditional_edges` соединяет узел классификации с узлами агентов через функцию `route_to_agents`. Когда `route_to_agents` возвращает несколько объектов `Send`, эти узлы выполняются параллельно.

## 7. Понимание архитектуры

Рабочий процесс маршрутизатора следует четкой схеме:

### Этап классификации

Функция `classify_query` использует **структурированный вывод** для анализа запроса пользователя и определения того, каких агентов следует вызвать. Именно здесь находится интеллектуальная система маршрутизации:

* Использует модель Pydantic (Python) или схему Zod (JS) для обеспечения корректного вывода.
* Возвращает список объектов `Classification`, каждый из которых содержит `source` и целевой `query`.
* Включает только релевантные источники — нерелевантные просто опущены.

Этот структурированный подход более надежен, чем произвольный анализ JSON, и делает логику маршрутизации явной.

### Параллельное выполнение с отправкой

Функция `route_to_agents` сопоставляет классификации с объектами `Send`. Каждый объект `Send` указывает целевой узел и состояние для передачи:

```python theme={null}
# Классификации: [{"source": "github", "query": "..."}, {"source": "notion", "query": "..."}]
# Превращается в:
[Send("github", {"query": "..."}), Send("notion", {"query": "..."})]
# Оба агента работают одновременно, каждый получает только необходимый ему запрос.
```

Каждый узел агента получает простой `AgentInput`, содержащий только поле `query`, а не полное состояние маршрутизатора. Это делает интерфейс чистым и понятным.

### Сбор результатов с помощью редукторов

Результаты работы агентов передаются обратно в основное состояние через **редуктор**. Каждый агент возвращает:

```python theme={null}
{"results": [{"source": "github", "result": "..."}]}
```

Редуктор (`operator.add` в Python) объединяет эти списки, собирая все параллельные результаты в `state["results"]`.

### Фаза синтеза

После завершения работы всех агентов функция `synthesize_results` выполняет итерацию по собранным результатам:

* Ожидает завершения всех параллельных ветвей (LangGraph обрабатывает это автоматически)
* Ссылается на исходный запрос, чтобы убедиться, что ответ отвечает на вопрос пользователя.
* Объединяет информацию из всех источников без излишнего повторения.

<Примечание>
  **Частичные результаты**: В этом руководстве все выбранные агенты должны завершиться до начала синтеза. Для более сложных сценариев, где необходимо обрабатывать частичные результаты или тайм-ауты, см. [руководство по map-reduce](/oss/python/langchain/map-reduce).
</Примечание>

  ```python theme={null}
  """
  Пример маршрутизатора знаний из нескольких источников

  Этот пример демонстрирует схему маршрутизации для многоагентных систем.
  Маршрутизатор классифицирует запросы и направляет их параллельно специализированным агентам.
  и обобщает результаты в комбинированный ответ.
  """

  импортный оператор
  from typing import Annotated, Literal, TypedDict

  from langchain.agents import create_agent
  from langchain.chat_models import init_chat_model
  from langchain.tools import tool
  from langgraph.graph import StateGraph, START, END
  from langgraph.types import Send
  from pydantic import BaseModel, Field


  # Определения штатов
  class AgentInput(TypedDict):
      «Простое входное состояние для каждого субагента».
      запрос: str


  class AgentOutput(TypedDict):
      «Результаты работы каждого субагента».
      источник: str
      результат: строка


  class Classification(TypedDict):
      «Единое решение по маршрутизации: какому агенту позвонить с каким запросом».
      источник: Literal["github", "notion", "slack"]
      запрос: str


  class RouterState(TypedDict):
      запрос: str
      классификации: список[Классификация]
      Результаты: Аннотированные[список[AgentOutput], оператор.add]
      окончательный_ответ: str


  # Структурированная схема выходных данных для классификатора
  class ClassificationResult(BaseModel):
      «Результат классификации пользовательского запроса на подвопросы, специфичные для конкретного агента».
      классификация: список[Классификация] = Поле(
          description="Список агентов, которых следует вызвать для ответа на целевые подвопросы"
      )


  # Инструменты
  @инструмент
  def search_code(query: str, repo: str = "main") -> str:
      «Ищите код в репозиториях GitHub».
      return f"Найден код, соответствующий '{query}' в {repo}: промежуточное ПО аутентификации в src/auth.py"


  @инструмент
  def search_issues(query: str) -> str:
      «Поиск проблем и запросов на слияние в GitHub».
      "Найдено 3 проблемы, соответствующие '{query}': #142 (документация по аутентификации API), #89 (процесс OAuth), #203 (обновление токена)"


  @инструмент
  def search_prs(query: str) -> str:
      «Детали реализации можно найти в запросах на слияние (pull requests)».
      return f"PR #156 добавил аутентификацию JWT, PR #178 обновил области действия OAuth"


  @инструмент
  def search_notion(query: str) -> str:
      «Поиск документации в рабочем пространстве Notion».
      Возвращается "Найденная документация: 'Руководство по аутентификации API' — описывает процесс OAuth2, ключи API и токены JWT."


  @инструмент
  def get_page(page_id: str) -> str:
      «Получите доступ к конкретной странице Notion по ID».
      return f"Содержимое страницы: пошаговые инструкции по настройке аутентификации"


  @инструмент
  def search_slack(query: str) -> str:
      «Поиск сообщений и веток обсуждений в Slack».
      Возвращается сообщение "Обсуждение найдено в канале #engineering: 'Используйте токены Bearer для аутентификации API, см. документацию по процедуре обновления'"


  @инструмент
  def get_thread(thread_id: str) -> str:
      """Найти конкретную ветку обсуждений в Slack.""
      "В обсуждении рассматриваются лучшие практики ротации ключей API"


  # Модели и агенты
  модель = init_chat_model("openai:gpt-4.1")
  router_llm = init_chat_model("openai:gpt-4.1-mini")

  github_agent = create_agent(
      модель,
      tools=[search_code, search_issues, search_prs],
      system_prompt=(
          «Вы — эксперт по GitHub. Отвечайте на вопросы о коде».
          "Ссылки на API и подробности реализации можно найти, выполнив поиск"
          «Репозитории, проблемы и запросы на слияние».
      ),
  )

  notion_agent = create_agent(
      модель,
      tools=[search_notion, get_page],
      system_prompt=(
          «Вы — эксперт по Notion. Ответьте на вопросы о внутренних процессах».
          «процессы, политики и документация команды путем поиска»
          «Рабочее пространство Notion в организации».
      ),
  )

  slack_agent = create_agent(
      модель,
      tools=[search_slack, get_thread],
      system_prompt=(
          «Вы — эксперт по Slack. Отвечайте на вопросы, используя поиск».
          «соответствующие темы и обсуждения, в которых участвовали члены команды»
          «Обмен знаниями и решениями».
      ),
  )


  # Узлы рабочего процесса
  def classify_query(state: RouterState) -> dict:
      «Классифицировать запрос и определить, каких агентов следует вызвать».
      structured_llm = router_llm.with_structured_output(ClassificationResult)

      результат = structured_llm.invoke([
          {
              "роль": "система",
              "содержание": """Проанализируйте этот запрос и определите, к каким базам знаний следует обратиться."
  Для каждого соответствующего источника сгенерируйте целевой подвопрос, оптимизированный для этого источника.

  Доступные источники:
  - GitHub: код, ссылки на API, детали реализации, проблемы, запросы на слияние.
  - концепция: Внутренняя документация, процессы, политики, командные вики.
  - Slack: Командные обсуждения, неформальный обмен знаниями, недавние беседы

  "Возвращать ТОЛЬКО те источники, которые имеют отношение к запросу.""
          },
          {"role": "user", "content": state["query"]}
      ])

      return {"classifications": result.classifications}


  def route_to_agents(state: RouterState) -> list[Send]:
      «Распределение информации между агентами осуществляется на основе классификации».
      возвращаться [
          Send(c["source"], {"query": c["query"]})
          for c in state["classifications"]
      ]


  def query_github(state: AgentInput) -> dict:
      """Запрос к агенту GitHub."""
      результат = github_agent.invoke({
          "messages": [{"role": "user", "content": state["query"]}]
      })
      return {"results": [{"source": "github", "result": result["messages"][-1].content}]}


  def query_notion(state: AgentInput) -> dict:
      «Запросите информацию у агента Notion».
      результат = notion_agent.invoke({
          "messages": [{"role": "user", "content": state["query"]}]
      })
      return {"results": [{"source": "notion", "result": result["messages"][-1].content}]}


  def query_slack(state: AgentInput) -> dict:
      """Запрос к агенту Slack.""
      результат = slack_agent.invoke({
          "messages": [{"role": "user", "content": state["query"]}]
      })
      return {"results": [{"source": "slack", "result": result["messages"][-1].content}]}


  def synthesize_results(state: RouterState) -> dict:
      «Объедините результаты всех участников в единый, связный ответ».
      if not state["results"]:
          return {"final_answer": "Результаты не найдены ни в одном источнике знаний."}

      отформатированный = [
          f"**Из {r['source'].title()}:**\n{r['result']}"
          for r in state["results"]
      ]

      synthesis_response = router_llm.invoke([
          {
              "роль": "система",
              "content": f"""Обобщите эти результаты поиска, чтобы ответить на исходный вопрос: "{state['query']}"

  - Объединение информации из нескольких источников без избыточности.
  - Выделите наиболее актуальную и полезную информацию.
  - Обратите внимание на любые расхождения между источниками.
  — Ответ должен быть кратким и хорошо структурированным.
          },
          {"role": "user", "content": "\n\n".join(formatted)}
      ])

      return {"final_answer": synthesis_response.content}


  # Создание рабочего процесса
  рабочий процесс = (
      StateGraph(RouterState)
      .add_node("classify", classify_query)
      .add_node("github", query_github)
      .add_node("notion", query_notion)
      .add_node("slack", query_slack)
      .add_node("synthesize", synthesize_results)
      .add_edge(START, "classify")
      .add_conditional_edges("classify", route_to_agents, ["github", "notion", "slack"])
      .add_edge("github", "synthesize")
      .add_edge("notion", "synthesize")
      .add_edge("slack", "synthesize")
      .add_edge("synthesize", END)
      .compile()
  )


  если __name__ == "__main__":
      результат = workflow.invoke({
          "Запрос": "Как аутентифицировать запросы к API?"
      })

      print("Исходный запрос:", result["query"])
      print("\nКлассификации:")
      for c in result["classifications"]:
          print(f" {c['source']}: {c['query']}")
      print("\n" + "=" * 60 + "\n")
      print("Окончательный ответ:")
      print(result["final_answer"])
  ```

## 9. Расширенные возможности: Маршрутизаторы с сохранением состояния

Созданный нами маршрутизатор является **бессостоятельным** — каждый запрос обрабатывается независимо, без сохранения памяти между вызовами. Для многоходовых диалогов необходим **состоятельный** подход.

### Подход с использованием оболочек инструментов

Простейший способ добавить память для диалогов — это обернуть маршрутизатор без сохранения состояния в инструмент, который может вызывать агент диалога:

```python theme={null}
from langgraph.checkpoint.memory import InMemorySaver


@инструмент
def search_knowledge_base(query: str) -> str:
    «Поиск по нескольким источникам знаний (GitHub, Notion, Slack).»

    Используйте это для поиска информации о коде, документации или обсуждениях в команде.
    """
    результат = workflow.invoke({"query": query})
    return result["final_answer"]


conversational_agent = create_agent(
    модель,
    инструменты=[search_knowledge_base],
    system_prompt=(
        «Вы — отзывчивый помощник, который отвечает на вопросы о нашей организации».
        «Используйте инструмент search_knowledge_base, чтобы найти информацию по всему нашему коду».
        «документация и обсуждения в команде».
    ),
    checkpointer=InMemorySaver(),
)
```

Такой подход позволяет маршрутизатору оставаться без состояния, в то время как разговорный агент управляет памятью и контекстом. Пользователь может вести многоходовый диалог, и агент будет вызывать инструмент маршрутизатора по мере необходимости.

```python theme={null}
config = {"configurable": {"thread_id": "user-123"}}

результат = conversational_agent.invoke(
    {"messages": [{"role": "user", "content": "Как аутентифицировать запросы API?"}]},
    конфигурация
)
print(result["messages"][-1].content)

результат = conversational_agent.invoke(
    {"messages": [{"role": "user", "content": "Что насчет ограничения скорости для этих конечных точек?"}]},
    конфигурация
)
print(result["messages"][-1].content)
```

<Совет>
  В большинстве случаев рекомендуется использовать подход с оболочкой инструмента. Он обеспечивает четкое разделение: маршрутизатор обрабатывает запросы из нескольких источников, а диалоговый агент отвечает за контекст и память.
</Совет>

### Подход с полной сохранностью

Если вам необходимо, чтобы сам маршрутизатор сохранял состояние — например, для использования предыдущих результатов поиска при принятии решений о маршрутизации — используйте [persistence](/oss/python/langchain/short-term-memory) для хранения истории сообщений на уровне маршрутизатора.

<Предупреждение>
  **Маршрутизаторы с сохранением состояния усложняют процесс.** При маршрутизации к разным агентам в течение нескольких ходов разговоры могут казаться непоследовательными, если агенты используют разные интонации или подсказки. Вместо этого рассмотрите шаблон [handoffs pattern](/oss/python/langchain/multi-agent/handoffs) или [subagents pattern](/oss/python/langchain/multi-agent/subagents) — оба обеспечивают более понятную семантику для многоходовых разговоров с разными агентами.
</Предупреждение>

## 10. Ключевые выводы

Метод фрезерования наиболее эффективен при наличии следующих условий:

* **Различные вертикали**: Отдельные области знаний, каждая из которых требует специализированных инструментов и подсказок.
* **Потребности в параллельных запросах**: Вопросы, для которых полезно одновременно запрашивать информацию из нескольких источников.
* **Требования к синтезу**: Результаты, полученные из нескольких источников, необходимо объединить в связный ответ.

Данная модель состоит из трех фаз: **декомпозиция** (анализ запроса и генерация целевых подзапросов), **маршрутизация** (параллельное выполнение запросов) и **синтез** (объединение результатов).

<Совет>
  **Когда использовать схему маршрутизации**

  Используйте шаблон маршрутизации, когда у вас есть несколько независимых источников информации, необходимы параллельные запросы с низкой задержкой и требуется явный контроль над логикой маршрутизации.

  Для более простых случаев с динамическим выбором инструментов рассмотрите шаблон [subagents](/oss/python/langchain/multi-agent/subagents). Для рабочих процессов, где агентам необходимо последовательно взаимодействовать с пользователями, рассмотрите шаблон [handoffs](/oss/python/langchain/multi-agent/handoffs).
</Совет>
