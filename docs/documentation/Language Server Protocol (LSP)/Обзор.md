## 1. Что такое LSP

**Language Server Protocol (LSP)** — стандартизированный протокол взаимодействия между средой разработки (IDE/редактор) и языковым сервером через JSON-RPC 2.0.

### Проблема M × N

Без стандарта каждая комбинация "язык + редактор" требует отдельной реализации:

```
Языков (M):    Python, TypeScript, Rust, Java, BSL, ...
Редакторов (N): VS Code, Neovim, Sublime, Emacs, IntelliJ, ...

Без LSP: M × N реализаций (5 языков × 5 редакторов = 25 плагинов)
С LSP:   M + N реализаций (5 серверов + 5 клиентов = 10 компонентов)
```

### Решение: один сервер — все редакторы

```
┌──────────┐                          ┌──────────────────┐
│ VS Code  │──── JSON-RPC (stdio) ───►│                  │
├──────────┤                          │  Language Server  │
│ Neovim   │──── JSON-RPC (stdio) ───►│  (один процесс)  │
├──────────┤                          │                  │
│ Sublime  │──── JSON-RPC (TCP)  ───►│  Знает всё о      │
├──────────┤                          │  языке/формате   │
│ Emacs    │──── JSON-RPC (stdio) ───►│                  │
└──────────┘                          └──────────────────┘
   Клиенты                                  Сервер
```

**Ключевая идея**: Языковой сервер — отдельный процесс, который предоставляет "умные" функции (автодополнение, диагностика, навигация, рефакторинг) для конкретного языка или формата файлов.

### Кто создал

- **Автор**: Microsoft (2016)
- **Open-source**: [github.com/microsoft/language-server-protocol](https://github.com/microsoft/language-server-protocol)
- **Масштаб**: ~300 языковых серверов, ~50 редакторов с поддержкой LSP

## 2. Архитектура

### 2.1. Клиент-серверная модель

```
IDE (Клиент)                              Language Server
┌───────────────────┐    JSON-RPC 2.0    ┌───────────────────┐
│                   │                    │                   │
│  Отображение UI   │◄── Notification ──│  Анализ кода      │
│  Обработка ввода  │── Request ────────►│  Валидация        │
│  Рендеринг        │◄── Response ──────│  Навигация        │
│                   │                    │  Completion       │
└───────────────────┘                    └───────────────────┘
     Транспорт: stdio | TCP | WebSocket | Pipe
```

### 2.2. Три типа сообщений

| Тип | Поля | Ожидает ответ? | Пример |
|-----|------|:--------------:|--------|
| **Request** | `id`, `method`, `params` | Да | `textDocument/completion` |
| **Response** | `id`, `result` \| `error` | — | Список вариантов дополнения |
| **Notification** | `method`, `params` | Нет | `textDocument/didChange` |

### 2.3. Capability Negotiation

При подключении клиент и сервер обмениваются **capabilities** — объявлениями поддерживаемых функций:

```
Клиент: "Я поддерживаю: completion (snippets), hover (markdown), diagnostics (relatedInfo)"
Сервер: "Я предоставляю: completion (trigger: =, _), hover, diagnostics, documentSymbol"
```

Если сервер не объявил `hoverProvider` → клиент не будет отправлять `textDocument/hover`.

### 2.4. Жизненный цикл соединения

```
Client                          Server
  │                                │
  ├── initialize ─────────────────►│  Capability exchange
  │◄── InitializeResult ──────────┤
  ├── initialized ────────────────►│  Ready to work
  │                                │
  │  ══════ Рабочая сессия ══════ │
  │                                │
  ├── textDocument/didOpen ───────►│
  │◄── publishDiagnostics ────────┤
  ├── textDocument/completion ────►│
  │◄── CompletionList ────────────┤
  ├── textDocument/hover ─────────►│
  │◄── Hover ─────────────────────┤
  │                                │
  │  ═══════ Завершение ═════════ │
  │                                │
  ├── shutdown ───────────────────►│  Release resources
  │◄── null ──────────────────────┤
  ├── exit ───────────────────────►│  Process exits
  │                                │
```

### 2.5. Базовые типы данных

| Тип | Описание | Пример |
|-----|----------|--------|
| `DocumentUri` | URI документа (string) | `"file:///project/.env"` |
| `Position` | Позиция (0-based line:character) | `{ "line": 5, "character": 12 }` |
| `Range` | Диапазон (start→end) | `{ "start": {...}, "end": {...} }` |
| `Location` | URI + Range | `{ "uri": "file://...", "range": {...} }` |
| `TextEdit` | Редактирование (range + newText) | `{ "range": {...}, "newText": "hybrid" }` |

**Важно**: типы данных — *не зависят от языка программирования*. Нет AST, нет символов компилятора. Только URI, позиции и диапазоны.

## 3. Что нового в LSP 3.18 (vs 3.17)

| Фича | Метод | Описание |
|-------|-------|----------|
| **Inline Completions** | `textDocument/inlineCompletion` | Дополнения в стиле Copilot — серые предложения в строке |
| **Multi-Range Formatting** | `textDocument/rangesFormatting` | Форматирование нескольких диапазонов за один запрос |
| **Virtual Documents** | `workspace/textDocumentContent` | Получение содержимого по произвольной URI-схеме |
| **Folding Range Refresh** | `workspace/foldingRange/refresh` | Сервер просит клиент обновить folding |
| **Snippet TextEdit** | `SnippetTextEdit` | Template-based edits (табы, плейсхолдеры) |
| **MarkupContent in Diagnostics** | `textDocument/diagnostic` | Markdown в сообщениях диагностик |
| **Tooltips for Commands** | `Command.tooltip` | Подсказки для CodeLens команд |
| **Nullable activeParameter** | `SignatureHelp` | activeParameter может быть null |

Все новые features защищены capability flags — старые клиенты не ломаются.

## 5. MCP-LSP мосты (2024–2025)

Новая категория проектов — соединение **Model Context Protocol** (для LLM-агентов) и **Language Server Protocol** (для IDE).

| Проект | Направление | Описание |
|--------|-------------|----------|
| [Tritlo/lsp-mcp](https://github.com/Tritlo/lsp-mcp) | MCP → LSP | MCP-сервер обращается к LSP: hover, completion, codeAction, diagnostics |
| [Language-Server-MCP-Bridge](https://github.com/sehejjain/Language-Server-MCP-Bridge) | LSP → MCP | VS Code extension: LSP capabilities → MCP tools для GitHub Copilot |
| [jonrad/lsp-mcp](https://github.com/jonrad/lsp-mcp) | MCP → LSP | Node.js bridge, lazy start серверов |
| [bug-ops/mcpls](https://github.com/bug-ops/mcpls) | Bidirectional | Rust universal bridge, LSP 3.17 |
| [ktnyt/cclsp](https://github.com/ktnyt/cclsp) | MCP → LSP | Claude Code + LSP, robust position resolution |
| [oraios/serena](https://github.com/oraios/serena) | MCP + LSP | LSP abstraction для coding agents, **спонсируется VS Code team** |
| [axivo/mcp-lsp](https://github.com/axivo/mcp-lsp) | MCP → LSP | Multi-language: Go, Python, TypeScript, Terraform |

**Зачем нужны**: LLM-агенты получают доступ к compiler-accurate информации (типы, определения, ссылки) через LSP, вместо текстового поиска по файлам.

## 6. LSP vs MCP — сравнение протоколов

| Аспект | LSP | MCP |
|--------|-----|-----|
| **Назначение** | IDE ↔ Language Server | LLM Host ↔ Tool Server |
| **Клиент** | Редактор кода (VS Code, Neovim) | Claude, ChatGPT, Agent |
| **Сервер предоставляет** | Completion, Diagnostics, Navigation, Hover | Tools, Resources, Prompts |
| **Транспорт** | JSON-RPC (stdio / TCP / WebSocket) | JSON-RPC (stdio / SSE / HTTP) |
| **Capabilities** | Negotiated при initialize | Declared (tools/list, resources/list) |
| **Типы данных** | TextDocument, Position, Range | Tool, Resource, Prompt |
| **Вдохновение** | — | MCP вдохновлён LSP (JSON-RPC, capabilities) |
| **Синергия** | MCP-LSP мосты объединяют оба | LLM получает LSP intelligence через MCP |

**В проекте PDF Framework**: MCP-сервер (15 tools) **уже реализован**. LSP-сервер — следующий шаг для поддержки конфигурации в IDE.
