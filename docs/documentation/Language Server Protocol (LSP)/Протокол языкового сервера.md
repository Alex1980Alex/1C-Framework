# Протокол языкового сервера (Language Server Protocol)

## Что такое протокол языкового сервера?

Реализация поддержки таких функций, как автозаполнение, переход к определению или документация при наведении курсора мыши, для языка программирования — это значительная работа. Традиционно эту работу приходится повторять для каждого инструмента разработки, поскольку каждый из них предоставляет разные API для реализации одних и тех же функций.

Идея языкового сервера заключается в том, чтобы обеспечить встроенные в сервер специфические для каждого языка функции, позволяющие взаимодействовать с инструментами разработки по протоколу, обеспечивающему межпроцессное взаимодействие.

Идея протокола Language Server Protocol (LSP) заключается в стандартизации протокола взаимодействия инструментов и серверов, чтобы один и тот же языковой сервер можно было повторно использовать в нескольких инструментах разработки, а инструменты могли поддерживать языки с минимальными усилиями.

**LSP выгоден как поставщикам языковых решений, так и разработчикам инструментов!**

## Как это работает

Языковой сервер работает как отдельный процесс, и инструменты разработки взаимодействуют с ним, используя языковой протокол по JSON-RPC. Ниже приведен пример того, как инструмент и языковой сервер взаимодействуют во время обычной сессии редактирования:

### Процесс взаимодействия

1. **Пользователь открывает файл** (называемый документом) в инструменте:
   - Инструмент уведомляет языковой сервер об открытии документа (`textDocument/didOpen`)
   - С этого момента информация о содержимом документа хранится не в файловой системе, а в памяти инструмента
   - Содержимое синхронизируется между инструментом и языковым сервером

2. **Пользователь вносит изменения**:
   - Инструмент уведомляет сервер об изменении документа (`textDocument/didChange`)
   - Языковое представление документа обновляется языковым сервером
   - Языковой сервер анализирует информацию и уведомляет инструмент об обнаруженных ошибках и предупреждениях (`textDocument/publishDiagnostics`)

3. **Пользователь выполняет команду «Перейти к определению»** для символа в открытом документе:
   - Инструмент отправляет на сервер запрос `textDocument/definition` с двумя параметрами:
     - (1) URI документа
     - (2) позицию текста, с которой был инициирован запрос
   - Сервер отвечает URI документа и позицией определения символа внутри документа

4. **Пользователь закрывает документ** (файл):
   - Инструмент отправляет уведомление `textDocument/didClose`
   - Информирует языковой сервер о том, что документ больше не находится в памяти
   - Текущее содержимое теперь актуально в файловой системе

## Типы данных

Протокол взаимодействует с языковым сервером на уровне:
- **Ссылок на документы (URI)**
- **Позиций в документе**

Эти типы данных:
- Не зависят от языка программирования
- Применимы ко всем языкам программирования
- Не находятся на уровне доменной модели языка программирования

Типы данных не включают:
- Абстрактные синтаксические деревья
- Символы компилятора (разрешенные типы, пространства имен и т.д.)

**Преимущество**: Стандартизировать URI текстового документа или позицию курсора гораздо проще, чем стандартизировать абстрактное синтаксическое дерево и символы компилятора для разных языков программирования.

## Пример запроса: "Перейти к определению"

Данные, передаваемые между инструментом разработки и языковым сервером для запроса «Перейти к определению» в документе C++:

### Запрос

```json
{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "textDocument/definition",
    "params": {
        "textDocument": {
            "uri": "file:///p%3A/mseng/VSCode/Playgrounds/cpp/use.cpp"
        },
        "position": {
            "line": 3,
            "character": 12
        }
    }
}
```

### Ответ

```json
{
    "jsonrpc": "2.0",
    "id": 1,
    "result": {
        "uri": "file:///p%3A/mseng/VSCode/Playgrounds/cpp/provide.cpp",
        "range": {
            "start": {
                "line": 0,
                "character": 4
            },
            "end": {
                "line": 0,
                "character": 11
            }
        }
    }
}
```

## Работа с несколькими языками

Когда пользователь работает с разными языками программирования, инструмент разработки обычно запускает языковой сервер для каждого языка.

**Пример**: Сессия, в которой пользователь работает с файлами Java и SASS одновременно.

## Возможности (Capabilities)

Не каждый языковой сервер может поддерживать все функции, определенные протоколом. Поэтому LSP предоставляет **«возможности»**.

### Что такое возможности?

- Возможность группирует набор языковых функций
- Инструмент разработки и языковой сервер объявляют о поддерживаемых ими функциях, используя возможности

### Примеры

- Сервер объявляет, что он может обрабатывать запрос `textDocument/definition`
- Но может не обрабатывать запрос `workspace/symbol`
- Инструмент разработки объявляет о своей способности предоставлять уведомления о предстоящем сохранении перед сохранением документа
- Сервер может вычислить текстовые правки для форматирования отредактированного документа перед его сохранением

> **Важно**: Фактическая интеграция языкового сервера в конкретный инструмент не определяется протоколом языкового сервера и остается на усмотрение разработчиков инструмента.

## Библиотеки (SDK)

Для упрощения реализации языковых серверов и клиентов существуют библиотеки или SDK:

### SDK для инструментов разработки

- Предоставляют библиотеку для интеграции языковых серверов
- **Пример**: для JavaScript/TypeScript существует модуль npm для языкового клиента

### SDK для языковых серверов

- Существуют для различных языков программирования
- **Пример**: для реализации языкового сервера с использованием Node.js существует модуль npm language server
