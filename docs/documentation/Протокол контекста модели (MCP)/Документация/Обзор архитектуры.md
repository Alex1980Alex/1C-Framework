# Обзор архитектуры

В этом обзоре протокола контекста модели (MCP) обсуждаются его [область применения](#scope) и [основные концепции](#concepts-of-mcp), а также приводится [пример](#example), демонстрирующий каждую основную концепцию.

Поскольку SDK MCP абстрагируют многие аспекты, большинство разработчиков, вероятно, сочтут раздел [протокол уровня данных](#data-layer-protocol) наиболее полезным. В нем обсуждается, как серверы MCP могут предоставлять контекст для приложения искусственного интеллекта.

Для получения подробной информации о реализации, пожалуйста, обратитесь к документации для вашего [SDK, специфичного для вашего языка программирования](/docs/sdk).

## Объем

Протокол контекста модели включает в себя следующие проекты:

* [Спецификация MCP](https://modelcontextprotocol.io/specification/latest): Спецификация MCP, описывающая требования к реализации для клиентов и серверов.
* [MCP SDKs](/docs/sdk): SDK для различных языков программирования, реализующих MCP.
* **Инструменты разработки MCP**: Инструменты для разработки серверов и клиентов MCP, включая [инспектор MCP](https://github.com/modelcontextprotocol/inspector)
* [Эталонные реализации серверов MCP](https://github.com/modelcontextprotocol/servers): Эталонные реализации серверов MCP.

## Концепции MCP

### Участники

MCP использует клиент-серверную архитектуру, где хост MCP — приложение искусственного интеллекта, такое как [Claude Code](https://www.anthropic.com/claude-code) или [Claude Desktop](https://www.claude.ai/download) — устанавливает соединения с одним или несколькими серверами MCP. Хост MCP делает это, создавая один клиент MCP для каждого сервера MCP. Каждый клиент MCP поддерживает выделенное соединение со своим соответствующим сервером MCP.

Локальные MCP-серверы, использующие транспорт STDIO, обычно обслуживают одного MCP-клиента, тогда как удаленные MCP-серверы, использующие транспорт Streamable HTTP, обычно обслуживают множество MCP-клиентов.

Ключевыми участниками архитектуры MCP являются:

* **MCP Host**: приложение на основе искусственного интеллекта, которое координирует и управляет одним или несколькими клиентами MCP.
* **Клиент MCP**: Компонент, поддерживающий соединение с сервером MCP и получающий контекст от сервера MCP для использования хостом MCP.
* **Сервер MCP**: Программа, предоставляющая контекст клиентам MCP.

**Например**: Visual Studio Code выступает в роли хоста MCP. Когда Visual Studio Code устанавливает соединение с сервером MCP, например, с [сервером Sentry MCP](https://docs.sentry.io/product/sentry-mcp/), среда выполнения Visual Studio Code создает объект клиента MCP, который поддерживает соединение с сервером Sentry MCP.
Когда Visual Studio Code впоследствии подключается к другому серверу MCP, например, к [локальному серверу файловой системы](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem), среда выполнения Visual Studio Code создает дополнительный объект клиента MCP для поддержания этого соединения.

### Слои

MCP состоит из двух слоев:

* **Уровень данных**: Определяет протокол на основе JSON-RPC для взаимодействия клиента и сервера, включая управление жизненным циклом и основные примитивы, такие как инструменты, ресурсы, подсказки и уведомления.
* **Транспортный уровень**: Определяет механизмы и каналы связи, обеспечивающие обмен данными между клиентами и серверами, включая установление соединения, специфичное для данного транспортного уровня, формирование сообщений и авторизацию.

Концептуально слой данных — это внутренний слой, а транспортный слой — внешний слой.

#### Слой данных

Слой данных реализует протокол обмена данными на основе [JSON-RPC 2.0](https://www.jsonrpc.org/), который определяет структуру и семантику сообщений.
Этот слой включает в себя:

* **Управление жизненным циклом**: обеспечивает инициализацию соединения, согласование возможностей и завершение соединения между клиентами и серверами.
* **Функции сервера**: Позволяет серверам предоставлять основные функции, включая инструменты для действий ИИ, ресурсы для контекстных данных и подсказки для шаблонов взаимодействия от клиента и к клиенту.
* **Функции клиента**: Позволяет серверам запрашивать у клиента выборку данных из LLM хоста, получать ввод от пользователя и отправлять сообщения клиенту в журнал.
* **Вспомогательные функции**: Поддерживает дополнительные возможности, такие как уведомления об обновлениях в реальном времени и отслеживание хода выполнения длительных операций.

Транспортный уровень

Транспортный уровень управляет каналами связи и аутентификацией между клиентами и серверами. Он отвечает за установление соединения, формирование сообщений и безопасную связь между участниками MCP.

MCP поддерживает два механизма переноса:

* **Стандартная передача данных**: Использует стандартные потоки ввода/вывода для прямой связи между локальными процессами на одной машине, обеспечивая оптимальную производительность без сетевых накладных расходов.
* **Потоковая передача HTTP-сообщений**: Использует HTTP POST для передачи сообщений от клиента к серверу с дополнительными событиями, отправляемыми сервером (Server-Sent Events), для потоковой передачи. Эта передача обеспечивает удаленную связь с сервером и поддерживает стандартные методы аутентификации HTTP, включая токены bearer, ключи API и пользовательские заголовки. MCP рекомендует использовать OAuth для получения токенов аутентификации.

Транспортный уровень абстрагирует детали связи от уровня протокола, обеспечивая единый формат сообщений JSON-RPC 2.0 для всех транспортных механизмов.

### Протокол уровня данных

Ключевой частью MCP является определение схемы и семантики взаимодействия между клиентами и серверами MCP. Разработчики, вероятно, сочтут наиболее интересной часть MCP слой данных — в частности, набор [примитивов](#примитивов). Именно эта часть MCP определяет способы обмена контекстом между серверами MCP и клиентами MCP.

MCP использует [JSON-RPC 2.0](https://www.jsonrpc.org/) в качестве базового протокола RPC. Клиент и серверы отправляют друг другу запросы и отвечают соответствующим образом. Уведомления могут использоваться, когда ответ не требуется.

#### Управление жизненным циклом

MCP — это протокол с сохранением состояния, требующий управления жизненным циклом. Цель управления жизненным циклом — согласовать возможности клиента и сервера, такие как инструменты, ресурсы или подсказки. Подробную информацию можно найти в [спецификации](/specification/latest/basic/lifecycle), а [пример](#example) демонстрирует последовательность инициализации.

#### Примитивы

Примитивы MCP — это важнейшая концепция в рамках MCP. Они определяют, что клиенты и серверы могут предоставлять друг другу. Эти примитивы определяют типы контекстной информации, которая может передаваться приложениям ИИ, и диапазон действий, которые могут быть выполнены.

MCP определяет три основных примитива, которые могут быть доступны *серверам*:

* **Инструменты**: Исполняемые функции, которые приложения ИИ могут вызывать для выполнения действий (например, файловые операции, вызовы API, запросы к базам данных).
* **Ресурсы**: Источники данных, предоставляющие контекстную информацию для приложений ИИ (например, содержимое файлов, записи в базах данных, ответы API).
* **Подсказки**: Многоразовые шаблоны, помогающие структурировать взаимодействие с языковыми моделями (например, системные подсказки, примеры с небольшим количеством примеров).

Каждый примитивный тип имеет связанные с ним методы для обнаружения (`*/list`), извлечения (`*/get`) и, в некоторых случаях, выполнения (`tools/call`).
Клиенты MCP будут использовать методы `*/list` для поиска доступных примитивов. Например, клиент может сначала вывести список всех доступных инструментов (`tools/list`), а затем выполнить их. Такая конструкция позволяет динамически формировать списки.

В качестве конкретного примера рассмотрим MCP-сервер, предоставляющий контекст о базе данных. Он может отображать инструменты для запросов к базе данных, ресурс, содержащий схему базы данных, и приглашение к вводу кода, включающее несколько примеров взаимодействия с инструментами.

Более подробную информацию о серверных примитивах см. в разделе [концепции сервера](./server-concepts).

MCP также определяет примитивы, которые *клиенты* могут предоставлять. Эти примитивы позволяют разработчикам серверов MCP создавать более сложные интерактивные возможности.

* **Выборка**: Позволяет серверам запрашивать автодополнение языковой модели у клиентского приложения ИИ. Это полезно, когда разработчики серверов хотят получить доступ к языковой модели, но при этом оставаться независимыми от модели и не включать SDK языковой модели в свой сервер MCP. Они могут использовать метод `sampling/complete` для запроса автодополнения языковой модели у клиентского приложения ИИ.
* **Запрос дополнительной информации**: Позволяет серверам запрашивать дополнительную информацию у пользователей. Это полезно, когда разработчики серверов хотят получить больше информации от пользователя или запросить подтверждение действия. Они могут использовать метод `elicitation/request` для запроса дополнительной информации у пользователя.
* **Ведение журналов**: Позволяет серверам отправлять сообщения журналов клиентам в целях отладки и мониторинга.

Более подробную информацию о клиентских примитивах см. в разделе [client concepts](./client-concepts).

Помимо серверных и клиентских примитивов, протокол предлагает сквозные вспомогательные примитивы, которые расширяют возможности выполнения запросов:

* **Задачи (экспериментальные)**: Надежные оболочки выполнения, обеспечивающие отложенное получение результатов и отслеживание статуса запросов MCP (например, ресурсоемкие вычисления, автоматизация рабочих процессов, пакетная обработка, многоэтапные операции)

#### Уведомления

Протокол поддерживает уведомления в реальном времени, что позволяет осуществлять динамические обновления между серверами и клиентами. Например, когда изменяются доступные инструменты сервера — например, когда появляется новая функциональность или модифицируются существующие инструменты — сервер может отправлять уведомления об обновлении инструментов, чтобы информировать подключенных клиентов об этих изменениях. Уведомления отправляются в виде сообщений JSON-RPC 2.0 (без ожидания ответа) и позволяют серверам MCP предоставлять обновления в реальном времени подключенным клиентам.

    #### Понимание обмена инициализацией

    Процесс инициализации является ключевой частью управления жизненным циклом MCP и выполняет несколько важных функций:

    1. **Согласование версий протокола**: Поле `protocolVersion` (например, "2025-06-18") гарантирует, что и клиент, и сервер используют совместимые версии протокола. Это предотвращает ошибки связи, которые могут возникнуть при попытке взаимодействия разных версий. Если взаимосовместимая версия не согласована, соединение должно быть разорвано.

    2. **Обнаружение возможностей**: Объект `capabilities` позволяет каждой стороне указать, какие функции она поддерживает, включая то, какие [примитивы](#primitives) она может обрабатывать (инструменты, ресурсы, подсказки) и поддерживают ли они такие функции, как [уведомления](#notifications). Это обеспечивает эффективную коммуникацию, избегая неподдерживаемых операций.

    3. **Обмен идентификационными данными**: Объекты `clientInfo` и `serverInfo` предоставляют информацию об идентификации и версиях для целей отладки и обеспечения совместимости.

    В этом примере процесс согласования возможностей демонстрирует, как объявляются примитивы MCP:

    **Возможности клиента**:

    * `"elicitation": {}` - Клиент заявляет о своей способности работать с запросами взаимодействия с пользователем (может принимать вызовы методов `elicitation/create`).

    **Возможности сервера**:

    * `"tools": {"listChanged": true}` - Сервер поддерживает примитив инструментов И может отправлять уведомления `tools/list_changed` при изменении списка инструментов.
    * `"resources": {}` - Сервер также поддерживает примитив ресурсов (может обрабатывать методы `resources/list` и `resources/read`).

    После успешной инициализации клиент отправляет уведомление о готовности:

    ```json Notification theme={null}
    {
      "jsonrpc": "2.0",
      "метод": "уведомления/инициализированы"
    }
    ```

      ```json Tools List Response theme={null}
              «Описание»: «Получайте актуальную информацию о погоде для любого места в мире».
              "inputSchema": {
                "type": "object",
                "характеристики": {
                  "расположение": {
                    "type": "string",
                    "Описание": "Название города, адрес или координаты (широта, долгота)"
                  },
                  "единицы": {
                    "type": "string",
                    "enum": ["metric", "imperial", "kelvin"],
                    "Описание": "Единицы измерения температуры для использования в ответ",
                    "default": "metric"
                  }
                },
                "обязательно": ["местоположение"]
              }
            }
          ]
        }
      }
      ```
    </CodeGroup>

    #### Понимание запроса на поиск инструмента

    Запрос `tools/list` прост и не содержит параметров.

    #### Понимание реакции системы поиска инструментов

    В ответе содержится массив `tools`, предоставляющий исчерпывающие метаданные о каждом доступном инструменте. Такая структура на основе массивов позволяет серверам одновременно предоставлять доступ к нескольким инструментам, сохраняя при этом четкие границы между различными функциями.

    Каждый объект инструмента в ответе содержит несколько ключевых полей:

    * **`name`**: Уникальный идентификатор инструмента в пространстве имен сервера. Он служит первичным ключом для выполнения инструмента и должен соответствовать четкому шаблону именования (например, `calculator_arithmetic`, а не просто `calculate`).
    * **`title`**: Удобочитаемое отображаемое имя инструмента, которое клиенты могут показывать пользователям.
    * **Описание**: Подробное объяснение того, что делает этот инструмент и когда его использовать.
    * **`inputSchema`**: JSON-схема, определяющая ожидаемые входные параметры, обеспечивающая проверку типов и предоставляющая четкую документацию по обязательным и необязательным параметрам.

    #### Как это работает в приложениях ИИ

    Приложение на основе ИИ получает доступные инструменты со всех подключенных серверов MCP и объединяет их в единый реестр инструментов, к которому может получить доступ языковая модель. Это позволяет языковой модели понимать, какие действия она может выполнять, и автоматически генерировать соответствующие вызовы инструментов во время диалогов.

    ```python Псевдокод для инструмента поиска приложений ИИ theme={null}
    # Псевдокод с использованием шаблонов MCP Python SDK
    available_tools = []
    for session in app.mcp_server_sessions():
        tools_response = await session.list_tools()
        available_tools.extend(tools_response.tools)
    conversation.register_available_tools(available_tools)
    ```

  <Заголовок шага="Выполнение инструмента (примитивы)">
    Теперь клиент может запустить инструмент, используя метод `tools/call`. Это демонстрирует, как примитивы MCP используются на практике: после обнаружения доступных инструментов клиент может вызвать их с соответствующими аргументами.

    #### Понимание запроса на выполнение инструмента

    Запрос `tools/call` имеет структурированный формат, обеспечивающий типобезопасность и четкую связь между клиентом и сервером. Обратите внимание, что мы используем правильное имя инструмента из ответа на запрос обнаружения («weather_current»), а не упрощенное имя:

    <CodeGroup>
      ```json Tool Call Request theme={null}
      {
        "jsonrpc": "2.0",
        "id": 3,
        "метод": "инструменты/вызов",
        "параметры": {
          "name": "weather_current",
          "аргументы": {
            «Местоположение»: «Сан-Франциско»,
            "единицы": "имперский"
          }
        }
      }
      ```

      ```json Tool Call Response theme={null}
      {
        "jsonrpc": "2.0",
        "id": 3,
        "результат": {
          "содержание": [
            {
              "type": "text",
              "текст": "Текущая погода в Сан-Франциско: 68°F, переменная облачность, слабый западный ветер 8 миль в час. Влажность: 65%"
            }
          ]
        }
      }
      ```
    </CodeGroup>

    #### Ключевые элементы выполнения инструмента

    Структура запроса включает в себя несколько важных компонентов:

    1. **`name`**: Должно точно совпадать с названием инструмента из ответа на запрос обнаружения (`weather_current`). Это гарантирует, что сервер сможет правильно определить, какой инструмент следует запустить.

    2. **`аргументы`**: Содержит входные параметры, определенные в `inputSchema` инструмента. В этом примере:
       * `location`: "Сан-Франциско" (обязательный параметр)
       * `units`: "imperial" (необязательный параметр, по умолчанию "metric", если не указан)

    3. **Структура JSON-RPC**: Использует стандартный формат JSON-RPC 2.0 с уникальным `id` для сопоставления запроса и ответа.

    #### Анализ ответа на запрос выполнения инструмента

    Данный ответ демонстрирует гибкость контентной системы MCP:

    1. **Массив `content`**: Инструмент возвращает массив объектов контента, что позволяет создавать многоформатные ответы (текст, изображения, ресурсы и т. д.).

    2. **Типы контента**: Каждый объект контента имеет поле `type`. В этом примере `"type": "text"` обозначает текстовый контент, но MCP поддерживает различные типы контента для разных сценариев использования.

    3. **Структурированный вывод**: Ответ предоставляет полезную информацию, которую приложение ИИ может использовать в качестве контекста для взаимодействия с языковой моделью.

    Этот шаблон выполнения позволяет приложениям искусственного интеллекта динамически вызывать функциональность сервера и получать структурированные ответы, которые могут быть интегрированы в диалоги с языковыми моделями.

    #### Как это работает в приложениях ИИ

    Когда языковая модель решает использовать инструмент во время разговора, приложение ИИ перехватывает вызов инструмента, направляет его на соответствующий сервер MCP, выполняет его и возвращает результаты обратно в языковую модель в рамках процесса разговора. Это позволяет языковой модели получать доступ к данным в реальном времени и выполнять действия во внешнем мире.

    ```python theme={null}
    # Псевдокод для выполнения инструмента применения ИИ
    async def handle_tool_call(conversation, tool_name, arguments):
        session = app.find_mcp_session_for_tool(tool_name)
        result = await session.call_tool(tool_name, arguments)
        conversation.add_tool_result(result.content)
    ```

  <Заголовок шага="Обновления в реальном времени (Уведомления)">
    MCP поддерживает уведомления в реальном времени, позволяющие серверам информировать клиентов об изменениях без явного запроса. Это демонстрирует систему уведомлений — ключевую функцию, обеспечивающую синхронизацию и быстродействие соединений MCP.

    #### Понимание уведомлений об изменении списка инструментов

    Когда доступные серверу инструменты изменяются — например, когда появляется новая функциональность, существующие инструменты модифицируются или инструменты временно становятся недоступными — сервер может заблаговременно уведомлять подключенных клиентов:

    ```json Request theme={null}
    {
      "jsonrpc": "2.0",
      "метод": "уведомления/инструменты/список_измененных"
    }
    ```

    #### Основные особенности уведомлений MCP

    1. **Ответ не требуется**: Обратите внимание, что в уведомлении отсутствует поле `id`. Это соответствует семантике уведомлений JSON-RPC 2.0, согласно которой ответ не ожидается и не отправляется.

    2. **На основе возможностей**: Это уведомление отправляется только серверами, которые указали `"listChanged": true" в своих возможностях инструментов во время инициализации (как показано на шаге 1).

    3. **Событийно-ориентированный подход**: Сервер принимает решение о времени отправки уведомлений на основе изменений внутреннего состояния, что делает соединения MCP динамичными и быстродействующими.

    #### Ответ клиента на уведомления

    Получив это уведомление, клиент обычно реагирует, запрашивая обновленный список инструментов. Это создает цикл обновления, который поддерживает актуальность знаний клиента о доступных инструментах:

    ```json Request theme={null}
    {
      "jsonrpc": "2.0",
      "id": 4,
      "метод": "инструменты/список"
    }
    ```

    #### Почему уведомления важны

    Эта система оповещений имеет решающее значение по нескольким причинам:

    1. **Динамические среды**: Инструменты могут появляться и исчезать в зависимости от состояния сервера, внешних зависимостей или прав доступа пользователей.
    2. **Эффективность**: Клиентам не нужно отслеживать изменения; они получают уведомления о появлении обновлений.
    3. **Согласованность**: Гарантирует, что клиенты всегда имеют точную информацию о доступных возможностях сервера.
    4. **Сотрудничество в режиме реального времени**: Обеспечивает работу быстродействующих приложений искусственного интеллекта, способных адаптироваться к меняющимся условиям.

    Данная схема уведомлений распространяется не только на инструменты, но и на другие примитивы MCP, обеспечивая комплексную синхронизацию в реальном времени между клиентами и серверами.

    #### Как это работает в приложениях ИИ

    Когда приложение ИИ получает уведомление об изменении инструментов, оно немедленно обновляет свой реестр инструментов и обновляет доступные возможности LLM. Это гарантирует, что текущие диалоги всегда будут иметь доступ к самому актуальному набору инструментов, а LLM сможет динамически адаптироваться к новым функциям по мере их появления.

    ```python theme={null}
    # Псевдокод для обработки уведомлений от приложений ИИ
    async def handle_tools_changed_notification(session):
        tools_response = await session.list_tools()
        app.update_available_tools(session, tools_response.tools)
        if app.conversation.is_active():
            app.conversation.notify_llm_of_new_capabilities()
    ```
