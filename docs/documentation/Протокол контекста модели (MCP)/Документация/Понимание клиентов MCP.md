# Понимание клиентов MCP

Клиенты MCP создаются хост-приложениями для связи с конкретными серверами MCP. Хост-приложение, например Claude.ai или IDE, управляет общим пользовательским интерфейсом и координирует работу нескольких клиентов. Каждый клиент осуществляет одно прямое взаимодействие с одним сервером.

Важно понимать это различие: *хост* — это приложение, с которым взаимодействуют пользователи, а *клиенты* — это компоненты протокола, обеспечивающие подключение к серверу.

## Основные функции клиента

Помимо использования контекста, предоставляемого серверами, клиенты могут предоставлять серверам ряд функций. Эти функции клиентов позволяют разработчикам серверов создавать более сложные интерактивные интерфейсы.

| Функция               | Объяснение                                                                                                                                                                                                             | Пример                                                                                                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Выявление**         | Выявление позволяет операторам запрашивать у пользователей конкретную информацию во время взаимодействия, предоставляя структурированный способ сбора информации по запросу.                                           | Оператор, бронирующий поездку, может запросить у пользователя предпочтения относительно мест в самолете, типа номера или его контактного номера для завершения бронирования. |
| **Корневые каталоги** | Корневые каталоги позволяют клиентам указывать, на каких каталогах должны сосредоточиться серверы, передавая предполагаемый объем данных через механизм координации.                                                   | Серверу для бронирования поездок может быть предоставлен доступ к определенному каталогу, из которого он может считывать календарь пользователя.                             |
| **Выборка**           | Выборка позволяет серверам запрашивать завершение LLM через клиент, обеспечивая агентский рабочий процесс. Такой подход предоставляет клиенту полный контроль над правами доступа пользователей и мерами безопасности. | Сервер для бронирования поездок может отправить список рейсов в LLM и запросить у LLM выбор наилучшего рейса для пользователя.                                               |

### Выявление

Функция "запрос информации" позволяет серверам запрашивать у пользователей конкретную информацию во время взаимодействия, создавая более динамичные и оперативные рабочие процессы.

#### Обзор

Метод Elicitation предоставляет серверам структурированный способ сбора необходимой информации по запросу. Вместо того чтобы запрашивать всю информацию заранее или выдавать ошибку при ее отсутствии, серверы могут приостанавливать свою работу, чтобы запросить у пользователей конкретные входные данные. Это создает более гибкое взаимодействие, при котором серверы адаптируются к потребностям пользователей, а не следуют жестким шаблонам.

**Схема сбора информации:**

```тема русалки={null}
диаграмма последовательности
    участник Пользователь
    участник Клиент
    участник Сервер

    Примечание по сравнению серверной и клиентской частей: сервер инициирует запрос.
    Сервер->>Клиент: запрос/создание

    Примечание о взаимодействии клиента и пользователя: человеческое взаимодействие.
    Клиент->>Пользователь: Представить пользовательский интерфейс для запроса информации
    Пользователь-->>Клиент: Предоставьте запрашиваемую информацию

    Примечание по серверам и клиентам: Запрос выполнен.
    Клиент-->>Сервер: Возврат ответа пользователя

    Примечание от сервера: Продолжить обработку с новой информацией.
```

Данный алгоритм обеспечивает динамический сбор информации. Серверы могут запрашивать конкретные данные по мере необходимости, пользователи предоставляют информацию через соответствующий пользовательский интерфейс, а серверы продолжают обработку с учетом полученного контекста.

**Пример компонентов для сбора информации:**

```typescript theme={null}
{
  метод: "elicitation/requestInput",
  параметры: {
    Сообщение: "Пожалуйста, подтвердите данные бронирования вашего отдыха в Барселоне:".
    схема: {
      тип: "объект",
      характеристики: {
        confirmBooking: {
          тип: "логическое значение",
          Описание: "Подтвердите бронирование (перелет + отель = 3000 долларов)"
        },
        seatPreference: {
          тип: "строка",
          enum: ["window", "aisle", "no preference"],
          Описание: «Предпочтительный тип места для полетов»
        },
        roomType: {
          тип: "строка",
          enum: ["вид на море", "вид на город", "вид на сад"],
          Описание: "Предпочитаемый тип номера в отеле"
        },
        travelInsurance: {
          тип: "логическое значение",
          по умолчанию: false,
          Описание: "Добавить туристическую страховку (150 долларов)"
        }
      },
      обязательно: ["confirmBooking"]
    }
  }
}
```

#### Пример: Подтверждение бронирования отпуска

Сервер бронирования туристических услуг демонстрирует эффективность процесса получения подтверждения бронирования на заключительном этапе. После того, как пользователь выбрал идеальный туристический пакет в Барселону, серверу необходимо получить окончательное подтверждение и любые недостающие данные, прежде чем продолжить.

Сервер запрашивает подтверждение бронирования с помощью структурированного запроса, включающего краткое описание поездки (рейсы в Барселону с 15 по 22 июня, отель на берегу моря, общая сумма 3000 долларов США) и поля для указания любых дополнительных предпочтений, таких как выбор места, типа номера или вариантов туристической страховки.

По мере оформления бронирования сервер запрашивает контактную информацию, необходимую для завершения резервации. Он может запросить данные путешественника для бронирования авиабилетов, особые пожелания к отелю или контактную информацию на случай чрезвычайной ситуации.

#### Модель взаимодействия с пользователем

Взаимодействия в процессе опроса пользователей разработаны таким образом, чтобы быть ясными, контекстуальными и уважать автономию пользователя:

**Представление запроса**: Клиенты отображают запросы на получение информации с четким контекстом, указывающим, какой сервер запрашивает информацию, зачем она нужна и как будет использоваться. Сообщение запроса объясняет цель, а схема обеспечивает структуру и проверку.

**Варианты ответа**: Пользователи могут предоставить запрашиваемую информацию с помощью соответствующих элементов управления пользовательского интерфейса (текстовые поля, выпадающие списки, флажки), отказаться от предоставления информации с возможностью дополнительного пояснения или отменить всю операцию. Клиенты проверяют ответы на соответствие предоставленной схеме, прежде чем вернуть их на серверы.

**Вопросы конфиденциальности**: Elicitation никогда не запрашивает пароли или ключи API. Клиенты предупреждают о подозрительных запросах и позволяют пользователям проверять данные перед отправкой.

### Корни

Корневые каталоги определяют границы файловой системы для работы сервера, позволяя клиентам указывать, на каких каталогах сервер должен сосредоточиться.

#### Обзор

Корневые каталоги — это механизм, позволяющий клиентам передавать серверам границы доступа к файловой системе. Они представляют собой URI файлов, указывающие на каталоги, в которых могут работать серверы, помогая серверам понимать область доступа к файлам и папкам. Хотя корневые каталоги передают предполагаемые границы, они не обеспечивают соблюдение ограничений безопасности. Фактическая безопасность должна обеспечиваться на уровне операционной системы посредством разрешений файлов и/или песочницы.

**Структура корня:**

```json theme={null}
{
  "uri": "file:///Users/agent/travel-planning",
  "name": "Рабочее пространство для планирования поездок"
}
```

Корневые каталоги — это исключительно пути к файловой системе, и они всегда используют схему URI `file://`. Они помогают серверам понимать границы проектов, организацию рабочего пространства и доступные каталоги. Список корневых каталогов может динамически обновляться по мере работы пользователей с различными проектами или папками, при этом серверы получают уведомления через `roots/list_changed` при изменении границ.

#### Пример: Рабочая область планирования поездок

Туристическому агенту, работающему с несколькими клиентами одновременно, полезно использовать корневые каталоги для организации доступа к файловой системе. Рассмотрите возможность создания рабочего пространства с различными каталогами для разных аспектов планирования поездок.

Клиент предоставляет серверу планирования поездок корневые каталоги файловой системы:

* `file:///Users/agent/travel-planning` - Основное рабочее пространство, содержащее все файлы, касающиеся поездок.
* `file:///Users/agent/travel-templates` — Многоразовые шаблоны маршрутов и ресурсы
* `file:///Users/agent/client-documents` - Паспорта и проездные документы клиентов

Когда агент создает маршрут в Барселону, корректно работающие серверы соблюдают эти границы — обращаются к шаблонам, сохраняют новый маршрут и ссылаются на документы клиента в указанных корневых каталогах. Серверы обычно обращаются к файлам в корневых каталогах, используя относительные пути от корневых каталогов или инструменты поиска файлов, которые учитывают границы корневых каталогов.

Если агент открывает архивную папку, например, `file:///Users/agent/archive/2023-trips`, клиент обновляет список корневых файлов через `roots/list_changed`.

Полную реализацию сервера, учитывающего корневые каталоги, см. в репозитории [filesystem server](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem) в официальном репозитории серверов.

#### Философия дизайна

Корневые домены служат механизмом координации между клиентами и серверами, а не границей безопасности. Спецификация требует, чтобы серверы «ДОЛЖНЫ соблюдать границы корневых доменов», а не «ОБЯЗАНЫ обеспечивать» их соблюдение, поскольку серверы выполняют код, который клиент не может контролировать.

Корневые серверы работают наиболее эффективно, когда серверам доверяют или они проверены, пользователи понимают их консультативный характер, а цель состоит в предотвращении сбоев, а не в пресечении вредоносного поведения. Они превосходно справляются с определением контекста (указывая серверам, на чем следует сосредоточиться), предотвращением сбоев (помогая добросовестным серверам оставаться в рамках заданных границ) и организацией рабочих процессов (например, автоматическим управлением границами проекта).

#### Модель взаимодействия с пользователем

Как правило, управление корневыми директориями осуществляется автоматически приложениями хоста на основе действий пользователя, хотя некоторые приложения могут предоставлять возможность ручного управления корневыми директориями:

**Автоматическое определение корневого каталога**: Когда пользователи открывают папки, клиенты автоматически предоставляют к ним доступ в качестве корневого каталога. Открытие рабочей области для путешествий позволяет клиенту предоставить доступ к этому каталогу в качестве корневого, помогая серверам понять, какие маршруты и документы находятся в области действия текущей работы.

**Ручная настройка корневого каталога**: Опытные пользователи могут указывать корневые каталоги через конфигурацию. Например, добавить `/travel-templates` для многократно используемых ресурсов, исключив при этом каталоги с финансовыми записями.

### Отбор проб

Метод выборки позволяет серверам запрашивать автодополнение языковых моделей через клиент, обеспечивая поведение агентов при сохранении безопасности и контроля со стороны пользователя.

#### Обзор

Сэмплирование позволяет серверам выполнять задачи, зависящие от ИИ, без прямой интеграции с моделями ИИ или оплаты за них. Вместо этого серверы могут запросить у клиента, который уже имеет доступ к моделям ИИ, выполнение этих задач от их имени. Такой подход предоставляет клиенту полный контроль над правами доступа пользователей и мерами безопасности. Поскольку запросы на сэмплирование происходят в контексте других операций — например, инструмента, анализирующего данные, — и обрабатываются как отдельные вызовы моделей, они поддерживают четкие границы между различными контекстами, что позволяет более эффективно использовать контекстное окно.

**Процесс отбора проб:**

```тема русалки={null}
диаграмма последовательности
    участник LLM
    участник Пользователь
    участник Клиент
    участник Сервер

    Примечание по Server и Client: сервер инициирует выборку.
    Сервер->>Клиент: sampling/createMessage

    Примечание по поводу взаимодействия клиента и пользователя: проверка с участием человека.
    Клиент->>Пользователь: Предъявите запрос на утверждение.
    Пользователь-->>Клиент: Просмотр и утверждение/изменение

    Примечание по взаимодействию клиента и LLM с моделью.
    Клиент->>LLM: Переслать одобренный запрос
    LLM-->>Клиент: Формирование возврата

    Примечание по клиенту и пользователю: анализ ответа.
    Клиент->>Пользователь: Предъявите ответ для утверждения.
    Пользователь-->>Клиент: Просмотр и утверждение/изменение

    Примечание по серверам и клиентам: Запрос выполнен.
    Клиент-->>Сервер: Верните одобренный ответ.
```

Процесс обеспечивает безопасность за счет множества контрольных точек с участием человека. Пользователи просматривают и могут изменять как первоначальный запрос, так и сгенерированный ответ до того, как он будет отправлен на сервер.

**Пример параметров запроса:**

```typescript theme={null}
{
  сообщения: [
    {
      роль: "пользователь",
      Содержание: "Проанализируйте эти варианты перелета и порекомендуйте лучший выбор:\n" +
               «[47 рейсов с ценами, временем вылета, авиакомпаниями и пересадками]\n» +
               «Настройки пользователя: вылет утром, максимум 1 пересадка»
    }
  ],
  modelPreferences: {
    подсказки: [{
      имя: "claude-sonnet-4-20250514" // Рекомендуемая модель
    }],
    costPriority: 0.3, // Меньше внимания уделяется стоимости API
    speedPriority: 0.2, // Можно подождать тщательного анализа
    intelligencePriority: 0.9 // Требуется сложная оценка компромиссов
  },
  systemPrompt: "Вы — эксперт по путешествиям, помогающий пользователям находить лучшие авиабилеты в соответствии с их предпочтениями".
  maxTokens: 1500
}
```

#### Пример: Инструмент анализа полетов

Рассмотрим сервер бронирования поездок с инструментом под названием `findBestFlight`, который использует выборку для анализа доступных рейсов и рекомендует оптимальный вариант. Когда пользователь спрашивает: «Забронируйте мне лучший рейс в Барселону на следующий месяц», инструменту требуется помощь искусственного интеллекта для оценки сложных компромиссов.

Инструмент запрашивает API авиакомпаний и собирает 47 вариантов рейсов. Затем он запрашивает помощь ИИ для анализа этих вариантов: «Проанализируйте эти варианты рейсов и порекомендуйте лучший вариант: [47 рейсов с ценами, временем, авиакомпаниями и пересадками] Предпочтения пользователя: вылет утром, максимум 1 пересадка».

Клиент инициирует запрос на выборку, что позволяет ИИ оценить компромиссы — например, более дешевые ночные рейсы против удобных утренних вылетов. Инструмент использует этот анализ для представления трех лучших рекомендаций.

#### Модель взаимодействия с пользователем

Хотя это и не является обязательным требованием, выборочный контроль призван обеспечить участие человека в процессе. Пользователи могут осуществлять надзор с помощью нескольких механизмов:

**Контроль за подтверждением**: Запросы на выборку могут потребовать явного согласия пользователя. Клиенты могут указать, что сервер хочет проанализировать и почему. Пользователи могут одобрять, отклонять или изменять запросы.

**Функции прозрачности**: Клиенты могут отображать точный текст запроса, выбранную модель и ограничения по количеству токенов, что позволяет пользователям просматривать ответы ИИ перед тем, как вернуться на сервер.

**Параметры конфигурации**: Пользователи могут устанавливать предпочтения модели, настраивать автоматическое утверждение для доверенных операций или требовать утверждения для всего. Клиенты могут предоставлять возможности для удаления конфиденциальной информации.

**Вопросы безопасности**: И клиенты, и серверы должны надлежащим образом обрабатывать конфиденциальные данные во время выборки. Клиенты должны внедрить ограничение скорости запросов и проверять все содержимое сообщений. Конструкция с участием человека гарантирует, что инициированные сервером взаимодействия с ИИ не смогут поставить под угрозу безопасность или получить доступ к конфиденциальным данным без явного согласия пользователя.
