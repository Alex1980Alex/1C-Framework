## Введение

### Цель и сфера применения

Протокол контекстной модели (Model Context Protocol) обеспечивает возможности авторизации на транспортном уровне.
предоставление клиентам MCP возможности отправлять запросы к ограниченным серверам MCP от имени ресурса.
владельцы. Данная спецификация определяет поток авторизации для HTTP-транспортов.

### Требования протокола

Авторизация является **необязательной** для реализаций MCP. При поддержке:

* Реализации, использующие транспорт на основе HTTP, **ДОЛЖНЫ** соответствовать данной спецификации.
* Реализации, использующие транспорт STDIO, **НЕ ДОЛЖНЫ** соответствовать данной спецификации, и
  Вместо этого получите учетные данные из среды.
* Реализации, использующие альтернативные транспортные протоколы, **ОБЯЗАТЕЛЬНО** должны соответствовать установленным стандартам безопасности.
  практики в соответствии с их протоколом.

### Соответствие стандартам

Данный механизм авторизации основан на установленных спецификациях, перечисленных ниже, но

## Роли

Защищенный *MCP-сервер* выступает в роли [сервера ресурсов OAuth 2.1](https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-13.html#name-roles),
способный принимать и обрабатывать запросы на защищенные ресурсы с использованием токенов доступа.

Клиент MCP выступает в роли клиента OAuth 2.1 (https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-13.html#name-roles).
Выполнение запросов на защиту ресурсов от имени владельца ресурса.

Сервер авторизации отвечает за взаимодействие с пользователем (при необходимости) и выдачу токенов доступа для использования на сервере MCP.
Детали реализации сервера авторизации выходят за рамки данной спецификации. Он может размещаться на следующих серверах:
сервер ресурсов или отдельный объект. Раздел [Обнаружение сервера авторизации](#authorization-server-discovery)
Определяет, как сервер MCP сообщает клиенту местоположение соответствующего сервера авторизации.

   меры как для конфиденциальных, так и для государственных клиентов.

2. Серверы авторизации и клиенты MCP **ДОЛЖНЫ** поддерживать документы метаданных идентификатора клиента OAuth.

3. Серверы авторизации и клиенты MCP **МОГУТ** поддерживать динамическую регистрацию клиентов OAuth 2.0.
   Протокол ([RFC7591](https://datatracker.ietf.org/doc/html/rfc7591)).

4. Серверы MCP **ОБЯЗАТЕЛЬНО** должны поддерживать защищенные метаданные ресурсов OAuth 2.0 ([RFC9728](https://datatracker.ietf.org/doc/html/rfc9728)).
   Клиенты MCP **ОБЯЗАТЕЛЬНО** должны использовать защищенные метаданные ресурсов OAuth 2.0 для обнаружения серверов авторизации.

5. Серверы авторизации MCP **ОБЯЗАТЕЛЬНО** должны предоставлять как минимум один из следующих механизмов обнаружения:

   * Метаданные сервера авторизации OAuth 2.0 ([RFC8414](https://datatracker.ietf.org/doc/html/rfc8414))
   * [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html)

   Клиенты MCP **ОБЯЗАТЕЛЬНО** должны поддерживать оба механизма обнаружения для получения информации, необходимой для взаимодействия с сервером авторизации.

### Требования к обнаружению метаданных защищенных ресурсов

Серверы MCP **ОБЯЗАТЕЛЬНО** должны реализовывать один из следующих механизмов обнаружения для предоставления клиентам MCP информации о местоположении сервера авторизации:

1. **Заголовок WWW-Authenticate**: Включите URL-адрес метаданных ресурса в HTTP-заголовок `WWW-Authenticate` в поле `resource_metadata` при возврате ответов `401 Unauthorized`, как описано в [RFC9728 Раздел 5.1](https://datatracker.ietf.org/doc/html/rfc9728#name-www-authenticate-response).

2. **Известный URI**: Предоставлять метаданные по известному URI, как указано в [RFC9728](https://datatracker.ietf.org/doc/html/rfc9728). Это может быть один из следующих вариантов:
   * В пути к конечной точке MCP сервера: `https://example.com/public/mcp` может содержать метаданные по адресу `https://example.com/.well-known/oauth-protected-resource/public/mcp`
   * В корневом каталоге: `https://example.com/.well-known/oauth-protected-resource`

Клиенты MCP **ОБЯЗАТЕЛЬНО** должны поддерживать оба механизма обнаружения и использовать URL-адрес метаданных ресурса из проанализированных заголовков `WWW-Authenticate`, если он присутствует; в противном случае они **ОБЯЗАТЕЛЬНО** должны использовать обратное построение и запрос известных URI в порядке, указанном выше.

[Раздел 3 RFC 6750](https://datatracker.ietf.org/doc/html/rfc6750#section-3)
Это позволяет указать области действия, необходимые для доступа к ресурсу. Это обеспечивает клиентам немедленный доступ.

### Обнаружение метаданных сервера авторизации

Для обработки различных форматов URL-адресов эмитентов и обеспечения совместимости как со спецификациями метаданных сервера авторизации OAuth 2.0, так и со спецификациями обнаружения OpenID Connect 1.0, клиенты MCP **ОБЯЗАТЕЛЬНО** должны пытаться использовать несколько известных конечных точек при обнаружении метаданных сервера авторизации.

Метод обнаружения основан на [RFC8414 Раздел 3.1 «Запрос метаданных сервера авторизации»](https://datatracker.ietf.org/doc/html/rfc8414#section-3.1) для обнаружения метаданных сервера авторизации OAuth 2.0 и [RFC8414 Раздел 5 «Примечания по совместимости»](https://datatracker.ietf.org/doc/html/rfc8414#section-5) для обеспечения совместимости с OpenID Connect Discovery 1.0.

Для URL-адресов эмитентов, содержащих компоненты пути (например, `https://auth.example.com/tenant1`), клиенты **ОБЯЗАТЕЛЬНО** должны пытаться использовать конечные точки в следующем порядке приоритета:

1. Метаданные сервера авторизации OAuth 2.0 с добавлением пути: `https://auth.example.com/.well-known/oauth-authorization-server/tenant1`
2. Обнаружение OpenID Connect 1.0 с добавлением пути: `https://auth.example.com/.well-known/openid-configuration/tenant1`
3. Добавление пути OpenID Connect Discovery 1.0: `https://auth.example.com/tenant1/.well-known/openid-configuration`

Для URL-адресов эмитентов без компонентов пути (например, `https://auth.example.com`), клиенты **ОБЯЗАТЕЛЬНО** должны попытаться выполнить следующее:

1. Метаданные сервера авторизации OAuth 2.0: `https://auth.example.com/.well-known/oauth-authorization-server`
2. OpenID Connect Discovery 1.0: `https://auth.example.com/.well-known/openid-configuration`

## Подходы к регистрации клиентов

MCP поддерживает три механизма регистрации клиентов. Выберите подходящий для вас вариант:

* **Документы метаданных идентификатора клиента**: Когда между клиентом и сервером нет предварительной связи (наиболее распространенный случай)
* **Предварительная регистрация**: Если между клиентом и сервером уже установлены отношения.
* **Динамическая регистрация клиента**: Для обеспечения обратной совместимости или выполнения особых требований.

Клиенты, поддерживающие все варианты, **ДОЛЖНЫ** следовать следующему порядку приоритетов:

1. Используйте предварительно зарегистрированную информацию о клиенте для сервера, если она доступна клиенту.
2. Используйте документы метаданных идентификатора клиента, если сервер авторизации указывает, поддерживает ли он это (через `client_id_metadata_document_supported` в метаданных сервера авторизации OAuth).
3. Используйте динамическую регистрацию клиентов в качестве резервного варианта, если сервер авторизации поддерживает её (через `registration_endpoint` в метаданных сервера авторизации OAuth).
4. Предложите пользователю ввести информацию о клиенте, если другие варианты недоступны.

### Документы метаданных идентификатора клиента

Клиенты MCP и серверы авторизации **ДОЛЖНЫ** поддерживать документы метаданных идентификатора клиента OAuth, как указано в
[Документ с метаданными идентификатора клиента OAuth](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00).
Этот подход позволяет клиентам использовать URL-адреса HTTPS в качестве идентификаторов клиента, где URL-адрес указывает на документ JSON.
содержит метаданные клиента. Это решает распространенную проблему MCP, когда серверы и клиенты имеют
Отсутствуют какие-либо предшествующие отношения.

#### Требования к реализации

Внедрения MCP, поддерживающие документы метаданных идентификаторов клиентов, **ДОЛЖНЫ** соответствовать требованиям, указанным в
[Документ с метаданными идентификатора клиента OAuth](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00).
Ключевые требования включают в себя:

**Для клиентов MCP:**

* Клиенты **ОБЯЗАТЕЛЬНО** должны размещать свой документ с метаданными по адресу HTTPS в соответствии с требованиями RFC.
* URL-адрес `client_id` **ОБЯЗАТЕЛЬНО** должен использовать схему "https" и содержать компонент пути, например, `https://example.com/client.json`.
* Документ метаданных **ОБЯЗАТЕЛЬНО** должен содержать как минимум следующие свойства: `client_id`, `client_name`, `redirect_uris`
* Клиенты **ОБЯЗАТЕЛЬНО** должны убедиться, что значение `client_id` в метаданных точно соответствует URL-адресу документа.
* Клиенты **МОГУТ** использовать `private_key_jwt` для аутентификации клиента (например, для запросов к конечной точке токена) с соответствующей конфигурацией JWKS, как описано в [Разделе 6.2 документа «Метаданные идентификатора клиента»](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-00.html#section-6.2)

**Для серверов авторизации:**

* **СЛЕДУЕТ** получать документы с метаданными при обнаружении идентификаторов клиентов в формате URL.
* **ОБЯЗАТЕЛЬНО** необходимо проверить, что `client_id` полученного документа точно совпадает с URL-адресом.
* **СЛЕДУЕТ** кэшировать метаданные с учетом заголовков HTTP-кэша.
* **ОБЯЗАТЕЛЬНО** проверять URI перенаправления, указанные в запросе авторизации, на соответствие URI, указанным в документе метаданных.
* **ОБЯЗАТЕЛЬНО** необходимо проверить, что структура документа соответствует формату JSON и содержит обязательные поля.
* **СЛЕДУЕТ** соблюдать требования безопасности, изложенные в [Разделе 6 документа «Метаданные идентификатора клиента»](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-00.html#section-6)


## Стратегия выбора масштаба проекта

При реализации потоков авторизации клиенты MCP **ДОЛЖНЫ** следовать принципу минимальных привилегий, запрашивая
Только те области действия, которые необходимы для их предполагаемой деятельности. Во время первоначального подтверждения авторизации клиенты MCP
При выборе области применения следует придерживаться следующего порядка приоритетов:

1. **Используйте параметр `scope`** из начального заголовка `WWW-Authenticate` в ответе 401, если он предоставлен.
2. **Если параметр `scope` недоступен**, используйте все области действия, определенные в `scopes_supported` из документа метаданных защищенного ресурса, опуская параметр `scope`, если `scopes_supported` не определен.

Этот подход учитывает универсальный характер клиентов MCP, которым, как правило, не хватает знаний в конкретной предметной области для принятия обоснованных решений о выборе отдельных областей действия. Запрос всех доступных областей действия позволяет серверу авторизации и конечному пользователю определить соответствующие разрешения в процессе предоставления согласия.

Такой подход сводит к минимуму неудобства для пользователя, соблюдая при этом принцип минимальных привилегий.
Поле `scopes_supported` предназначено для отображения минимального набора необходимых областей видимости.
для базовой функциональности (см. [Минимизация области действия](/specification/2025-11-25/basic/security_best_practices#scope-minimization)),
с возможностью поэтапного запроса дополнительных областей действия на каждом этапе процесса авторизации.
описано в разделе [Обработка запросов на изменение объема работ](#scope-challenge-handling).

## Реализация параметров ресурсов

Клиенты MCP **ОБЯЗАТЕЛЬНО** должны реализовать индикаторы ресурсов для OAuth 2.0, как определено в [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html)
Чтобы явно указать целевой ресурс, для которого запрашивается токен. Параметр `resource`:

1. **ОБЯЗАТЕЛЬНО** должны быть включены как в запросы на авторизацию, так и в запросы на получение токена.
2. **ОБЯЗАТЕЛЬНО** необходимо указать MCP-сервер, с которым клиент намерен использовать токен.
3. **ОБЯЗАТЕЛЬНО** использовать канонический URI сервера MCP, как определено в [Разделе 2 RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html#name-access-token-request).

### URI канонического сервера

В целях настоящей спецификации канонический URI сервера MCP определяется как идентификатор ресурса, как указано в
[Раздел 2 RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html#section-2) и соответствует параметру `resource` в
[RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728).

Клиенты MCP **ДОЛЖНЫ** указывать максимально точный URI для сервера MCP, к которому они намереваются обратиться, следуя рекомендациям в [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707). Хотя каноническая форма использует компоненты схемы и хоста в нижнем регистре, реализации **ДОЛЖНЫ** принимать компоненты схемы и хоста в верхнем регистре для обеспечения надежности и совместимости.

Примеры допустимых канонических URI:

* `https://mcp.example.com/mcp`
* `https://mcp.example.com`
* `https://mcp.example.com:8443`
* `https://mcp.example.com/server/mcp` (когда компонент пути необходим для идентификации отдельного сервера MCP)

Примеры недействительных канонических URI:

* `mcp.example.com` (отсутствует схема)
* `https://mcp.example.com#fragment` (содержит фрагмент)

> **Примечание:** Хотя как `https://mcp.example.com/` (с завершающей косой чертой), так и `https://mcp.example.com` (без завершающей косой черты) технически являются допустимыми абсолютными URI согласно [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986), реализации **ДОЛЖНЫ** последовательно использовать форму без завершающей косой черты для лучшей совместимости, если только завершающая косая черта не имеет семантического значения для конкретного ресурса.

Например, при обращении к серверу MCP по адресу `https://mcp.example.com` запрос на авторизацию будет включать в себя следующее:

```
&resource=https%3A%2F%2Fmcp.example.com
```

Клиенты MCP **ОБЯЗАТЕЛЬНО** должны отправлять этот параметр независимо от того, поддерживают ли его серверы авторизации.

## Использование токена доступа

### Требования к токенам

Обработка токенов доступа при отправке запросов к серверам MCP **ДОЛЖНА** соответствовать требованиям, определенным в
[Раздел 5 OAuth 2.1 «Запросы ресурсов»](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-5).
Конкретно:

1. Клиент MCP **ОБЯЗАТЕЛЬНО** должен использовать поле заголовка запроса авторизации, определенное в
   [Раздел 5.1.1 OAuth 2.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-5.1.1):

```
Авторизация: Bearer <access-token>
```

Обратите внимание, что авторизация **ОБЯЗАТЕЛЬНО** должна быть включена в каждый HTTP-запрос от клиента к серверу.
даже если они являются частью одной и той же логической сессии.

2. Токены доступа **НЕ ДОЛЖНЫ** включаться в строку запроса URI.

Пример запроса:

```http theme={null}
GET /mcp HTTP/1.1
Хост: mcp.example.com
Авторизация: Предъявитель eyJhbGciOiJIUzI1NiIs...
```

### Обработка токенов

Серверы MCP, выступая в роли ресурсного сервера OAuth 2.1, **ОБЯЗАТЕЛЬНО** должны проверять токены доступа, как описано в
[Раздел 5.2 OAuth 2.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-5.2).
Серверы MCP **ОБЯЗАТЕЛЬНО** должны проверять, что токены доступа были выданы специально для них как для целевой аудитории.
согласно [разделу 2 RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html#section-2).
Если проверка не пройдена, серверы **ОБЯЗАНЫ** ответить в соответствии с
[Раздел 5.3 OAuth 2.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-5.3)
Требования к обработке ошибок. Недействительные или просроченные токены **ОБЯЗАТЕЛЬНО** должны получать HTTP-код 401.
ответ.

Клиенты MCP **НЕ ДОЛЖНЫ** отправлять на сервер MCP токены, отличные от тех, которые выданы сервером авторизации сервера MCP.

Серверы MCP **ОБЯЗАТЕЛЬНО** должны принимать только токены, действительные для использования с их серверами.
собственные ресурсы.

Серверы MCP **НЕ ДОЛЖНЫ** принимать или передавать какие-либо другие токены.

## Обработка ошибок

Серверы **ОБЯЗАТЕЛЬНО** должны возвращать соответствующие коды состояния HTTP для ошибок авторизации:

| Код состояния | Описание                   | Использование                                                 |
| ------------- | -------------------------- | ------------------------------------------------------------- |
| 401           | Несанкционированный доступ | Требуется авторизация или токен недействителен                |
| 403           | Запрещено                  | Недопустимые области действия или недостаточные права доступа |
| 400           | Неверный запрос            | Некорректный запрос на авторизацию                            |

### Обработка запросов на определение объема работ

В этом разделе рассматривается обработка ошибок недостаточной области видимости во время выполнения, когда
У клиента уже есть токен, но ему требуются дополнительные разрешения. Это приводит к ошибке.
Шаблоны обработки, определенные в [Разделе 5 OAuth 2.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-5)
и использует поля метаданных из [RFC 9728 (Защищенные метаданные ресурсов OAuth 2.0)](https://datatracker.ietf.org/doc/html/rfc9728).

#### Ошибки, связанные с недостаточной областью видимости во время выполнения

Когда клиент отправляет запрос с недостаточным токеном доступа
В случае возникновения проблем во время выполнения программы сервер **ДОЛЖЕН** отвечать следующим образом:

* Код состояния `HTTP 403 Forbidden` (согласно разделу 3.1 [RFC 6750](https://datatracker.ietf.org/doc/html/rfc6750#section-3.1))
* Заголовок `WWW-Authenticate` со схемой `Bearer` и дополнительными параметрами:
  * `error="insufficient_scope"` - указывает на конкретный тип ошибки авторизации
  * `scope="required_scope1 required_scope2"` - указывает минимальный объем данных, необходимый для операции.
  * `resource_metadata` — URI документа с метаданными защищенного ресурса (для обеспечения согласованности с ответами 401)
  * `error_description` (необязательно) — удобочитаемое описание ошибки

**Управление областью действия сервера**: При возникновении ошибок, связанных с недостаточной областью действия, серверы
**СЛЕДУЕТ** включать области действия, необходимые для удовлетворения текущего запроса, в поле `scope`.
параметр.

Серверы обладают гибкостью в определении того, какие области действия следует включать:

* **Минимальный подход**: Включите новые необходимые области действия для конкретной операции. Включите также любые существующие предоставленные области действия, если они необходимы, чтобы предотвратить потерю клиентами ранее предоставленных разрешений.
* **Рекомендуемый подход**: Включите как существующие соответствующие области действия, так и новые необходимые области действия, чтобы предотвратить потерю клиентами ранее предоставленных разрешений.
* **Расширенный подход**: Включите существующие области применения, вновь необходимые области применения и связанные области применения, которые обычно работают вместе.

Выбор зависит от оценки сервером влияния на пользовательский опыт и сложностей авторизации.

Серверы **ДОЛЖНЫ** придерживаться единой стратегии включения областей действия, чтобы обеспечить предсказуемое поведение для клиентов.

Серверы **ДОЛЖНЫ** учитывать влияние на пользовательский опыт при определении того, какие области действия следует включить в список.
в ответ на это, поскольку неправильно настроенные области действия могут потребовать частого взаимодействия с пользователем.

Пример ответа о недостаточном объеме данных:

```http theme={null}
HTTP/1.1 403 Запрещено
WWW-Authenticate: Bearer error="insufficient_scope",
                         scope="files:read files:write user:profile",
                         resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
                         error_description="Требуются дополнительные права на запись в файл"
```

#### Пошаговая процедура авторизации

В процессе первоначальной авторизации или во время выполнения клиенты будут получать ошибки, связанные с областью действия (`insufficient_scope`).
Клиенты **ДОЛЖНЫ** реагировать на эти ошибки, запрашивая новый токен доступа с расширенными правами доступа посредством поэтапной авторизации или обрабатывая ошибки другими подходящими способами.
Клиенты, действующие от имени пользователя, **ДОЛЖНЫ** попытаться пройти процедуру поэтапной авторизации. Клиенты, действующие от своего имени (клиенты с учетными данными клиента).
**МОЖЕТ** быть предпринята попытка пройти процедуру поэтапной авторизации или запрос может быть немедленно отменен.

Процесс выглядит следующим образом:

1. **Разобрать информацию об ошибке** из ответа сервера авторизации или заголовка `WWW-Authenticate`.
2. **Определите необходимые объемы работ** в соответствии с [Стратегией выбора объема работ](#scope-selection-strategy).
3. **Инициируйте (повторную) авторизацию** с заданным диапазоном полномочий.
4. **Повторите исходный запрос** с новыми данными авторизации не более нескольких раз и рассматривайте это как окончательную ошибку авторизации.

Клиентам **СЛЕДУЕТ** установить ограничения на количество повторных попыток и **СЛЕДУЕТ** отслеживать попытки обновления области действия, чтобы избежать
Повторные сбои при одной и той же комбинации ресурса и операции.

## Вопросы безопасности

Внедрение **ОБЯЗАТЕЛЬНО** должно соответствовать передовым методам обеспечения безопасности OAuth 2.1, изложенным в [Разделе 7 OAuth 2.1. «Вопросы безопасности»](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#name-security-considerations).

### Привязка и проверка аудитории токенов

[RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html) Индикаторы ресурсов обеспечивают критически важные преимущества в области безопасности, привязывая токены к их назначению.
**для аудиторий, поддерживающих данную возможность на сервере авторизации**. Для обеспечения текущего и будущего внедрения:

* Клиенты MCP **ОБЯЗАТЕЛЬНО** должны включать параметр `resource` в запросы авторизации и токенов, как указано в разделе [Реализация параметров ресурсов](#resource-parameter-implementation).
* Серверы MCP **ОБЯЗАТЕЛЬНО** должны проверять, что предоставленные им токены были выданы специально для их использования.

Документ [о лучших практиках безопасности](/specification/2025-11-25/basic/security_best_practices#token-passthrough)
В документе объясняется, почему проверка аудитории с помощью токена имеет решающее значение и почему передача токена через посредника категорически запрещена.

### Кража токенов

Злоумышленники, получившие токены, хранящиеся на стороне клиента, или токены, кэшированные или зарегистрированные на сервере, могут получить доступ к защищенным ресурсам.
Запросы, которые кажутся серверами ресурсов законными.

Клиенты и серверы **ОБЯЗАТЕЛЬНО** должны внедрить безопасное хранение токенов и следовать рекомендациям по использованию OAuth.
как указано в [OAuth 2.1, Раздел 7.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.1).

Серверы авторизации **ДОЛЖНЫ** выдавать кратковременные токены доступа, чтобы уменьшить последствия утечки токенов.
Для общедоступных клиентов серверы авторизации **ОБЯЗАТЕЛЬНО** должны обновлять токены обновления, как описано в [Раздел 4.3.1 OAuth 2.1 «Расширение конечной точки токена»](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-4.3.1).

### Безопасность связи

Реализации **ОБЯЗАТЕЛЬНО** должны соответствовать [разделу 1.5 OAuth 2.1 «Безопасность связи»](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-1.5).

Конкретно:

1. Все конечные точки сервера авторизации **ОБЯЗАТЕЛЬНО** должны обслуживаться по протоколу HTTPS.
2. Все URI перенаправления **ОБЯЗАТЕЛЬНО** должны быть либо `localhost`, либо использовать HTTPS.

### Защита с помощью кода авторизации

Злоумышленник, получивший доступ к коду авторизации, содержащемуся в ответе на запрос авторизации, может попытаться обменять этот код на токен доступа или иным образом использовать его.
(Более подробно описано в разделе 7.5 [OAuth 2.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.5))

Для решения этой проблемы клиенты MCP **ОБЯЗАТЕЛЬНО** должны реализовать PKCE в соответствии с [разделом 7.5.2 OAuth 2.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.5.2) и **ОБЯЗАТЕЛЬНО** должны проверить поддержку PKCE, прежде чем приступать к авторизации.
PKCE помогает предотвратить перехват и внедрение кодов авторизации, требуя от клиентов создания секретной пары «проверка-запрос», гарантируя, что только первоначальный запрашивающий может обменять код авторизации на токены.

Клиенты MCP **ОБЯЗАТЕЛЬНО** должны использовать метод проверки подлинности с помощью кода `S256`, если это технически возможно, как того требует [раздел 4.1.1 OAuth 2.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-4.1.1).

Поскольку спецификации OAuth 2.1 и PKCE не определяют механизм обнаружения клиентами поддержки PKCE, клиенты MCP **ОБЯЗАТЕЛЬНО** должны полагаться на метаданные сервера авторизации для проверки этой возможности:

* **Метаданные сервера авторизации OAuth 2.0**: Если параметр `code_challenge_methods_supported` отсутствует, сервер авторизации не поддерживает PKCE, и клиенты MCP **ОБЯЗАТЕЛЬНО** должны отказать в продолжении.

* **OpenID Connect Discovery 1.0**: Хотя в [метаданных поставщика OpenID](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderMetadata) не определено поле `code_challenge_methods_supported`, оно обычно включается поставщиками OpenID. Клиенты MCP **ОБЯЗАТЕЛЬНО** должны проверять наличие поля `code_challenge_methods_supported` в ответе метаданных поставщика. Если это поле отсутствует, клиенты MCP **ОБЯЗАТЕЛЬНО** должны отказать в продолжении.

Серверы авторизации, предоставляющие OpenID Connect Discovery 1.0, **ОБЯЗАТЕЛЬНО** должны включать `code_challenge_methods_supported` в свои метаданные для обеспечения совместимости с MCP.

### Открыть перенаправление

Злоумышленник может создавать вредоносные URI перенаправления, чтобы направлять пользователей на фишинговые сайты.

Клиенты MCP ОБЯЗАТЕЛЬНО должны иметь зарегистрированные URI перенаправления на сервере авторизации.

Серверы авторизации **ОБЯЗАТЕЛЬНО** должны проверять точность URI перенаправления на соответствие предварительно зарегистрированным значениям, чтобы предотвратить атаки с использованием перенаправления.

Клиенты MCP **ДОЛЖНЫ** использовать и проверять параметры состояния в потоке кода авторизации.
и отбросить все результаты, которые не соответствуют исходному состоянию или не совпадают с ним.

Серверы авторизации **ОБЯЗАТЕЛЬНО** должны принимать меры предосторожности для предотвращения перенаправления пользовательских агентов на ненадежные URI, следуя рекомендациям, изложенным в [разделе 7.12.2 OAuth 2.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.12.2)

Серверы авторизации **ДОЛЖНЫ** автоматически перенаправлять пользовательский агент только в том случае, если они доверяют URI перенаправления. Если URI не является надежным, сервер авторизации МОЖЕТ уведомить пользователя и рассчитывать на то, что пользователь примет правильное решение.

### Безопасность документа с метаданными идентификатора клиента

При внедрении документов метаданных идентификатора клиента серверы авторизации **ОБЯЗАТЕЛЬНО** должны учитывать последствия для безопасности.
Подробности см. в [Документе по метаданным идентификатора клиента OAuth, Раздел 6](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00#name-security-considerations).
К основным моментам, которые следует учитывать, относятся:

#### Защита от злоупотреблений сервером авторизации

Сервер авторизации принимает URL-адрес в качестве входных данных от неизвестного клиента и получает этот URL-адрес.
Злоумышленник может использовать это для того, чтобы заставить сервер авторизации отправлять запросы к произвольным URL-адресам.
например, запросы к частным административным конечным точкам, к которым имеет доступ сервер авторизации.

Серверы авторизации, получающие документы с метаданными, **должны** учитывать следующее:
Риски, связанные с подделкой запросов на стороне сервера (SSRF), описаны в [Документе по метаданным идентификатора клиента OAuth: атаки с подделкой запросов на стороне сервера (SSRF)](https://developer.mozilla.org/docs/Web/Security/Attacks/SSRF), как описано в [Документе по метаданным идентификатора клиента OAuth: атаки с подделкой запросов на стороне сервера (SSRF)](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00#name-server-side-request-forgery).

#### Риски, связанные с перенаправлением URI на Localhost

Документы метаданных идентификатора клиента сами по себе не могут предотвратить подмену URL-адреса `localhost`. Злоумышленник может выдать себя за любого клиента следующим образом:

1. Предоставление URL-адреса метаданных легитимного клиента в качестве его `client_id`.
2. Привязка к любому порту `localhost` и указание этого адреса в качестве redirect_uri.
3. Получение кода авторизации посредством перенаправления после подтверждения пользователем.

Сервер увидит метаданные легитимного клиента, а пользователь увидит имя легитимного клиента, что затруднит обнаружение атаки.

Серверы авторизации:

* **СЛЕДУЕТ** отображать дополнительные предупреждения для URI перенаправления, доступных только для `localhost`.
* **МОЖЕТ** потребоваться использование дополнительных механизмов подтверждения для повышения уровня безопасности.
* **ОБЯЗАТЕЛЬНО** необходимо четко отображать имя хоста URI перенаправления во время авторизации.

#### Политика доверия

Серверы авторизации **МОГУТ** применять политики доверия на основе доменов:

* Списки разрешенных доменов для доверенных серверов (для защищенных серверов)
* Принимайте любой HTTPS `client_id` (для открытых серверов)
* Проверка репутации неизвестных доменов
* Ограничения основаны на возрасте домена или проверке сертификата.
* Чтобы предотвратить фишинг, отображайте имена хостов CIMD и других связанных с клиентом файлов на видном месте.

Серверы сохраняют полный контроль над своими политиками доступа.

### Проблема растерянного заместителя

Злоумышленники могут использовать уязвимости серверов MCP, выступающих в качестве посредников для API третьих сторон, что приводит к [уязвимостям типа Confused Deputy](/specification/2025-11-25/basic/security_best_practices#confused-deputy-problem).
Используя украденные коды авторизации, они могут получить токены доступа без согласия пользователя.

Прокси-серверы MCP, использующие статические идентификаторы клиентов, **ОБЯЗАТЕЛЬНО** должны получать согласие пользователя для каждого динамически изменяемого идентификатора.
Перед переадресацией на серверы авторизации третьих лиц (что может потребовать дополнительного согласия) регистрируется клиент.

### Ограничение привилегий токена доступа

Злоумышленник может получить несанкционированный доступ или иным образом скомпрометировать сервер MCP, если сервер принимает токены, выданные для других ресурсов.

Данная уязвимость имеет два критически важных аспекта:

1. **Сбои проверки аудитории.** Когда сервер MCP не проверяет, что токены предназначались именно для него (например, с помощью утверждения об аудитории, как указано в [RFC9068](https://www.rfc-editor.org/rfc/rfc9068.html)), он может принять токены, первоначально выданные для других сервисов. Это нарушает фундаментальную границу безопасности OAuth, позволяя злоумышленникам повторно использовать легитимные токены в разных сервисах, а не в тех, для которых они предназначались.
2. **Передача токенов.** Если сервер MCP не только принимает токены с некорректной аудиторией, но и пересылает эти неизмененные токены нижестоящим сервисам, это потенциально может вызвать [проблему «запутанного заместителя»](#confused-deputy-problem), когда нижестоящий API может ошибочно доверять токену, как если бы он поступил с сервера MCP, или предполагать, что токен был проверен вышестоящим API. Дополнительные сведения см. в разделе [Передача токенов](/specification/2025-11-25/basic/security_best_practices#token-passthrough) руководства по лучшим практикам безопасности.

Серверы MCP **ОБЯЗАТЕЛЬНО** должны проверять токены доступа перед обработкой запроса, гарантируя, что токен доступа выдан специально для сервера MCP, и предпринимать все необходимые шаги для предотвращения возврата данных неавторизованным лицам.

Сервер MCP **ОБЯЗАТЕЛЬНО** должен следовать рекомендациям, изложенным в [OAuth 2.1 - Раздел 5.2](https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-13.html#section-5.2), для проверки входящих токенов.

Серверы MCP **ОБЯЗАТЕЛЬНО** должны принимать только токены, предназначенные специально для них самих, и **ОБЯЗАТЕЛЬНО** должны отклонять токены, которые не содержат их в утверждении о целевой аудитории или иным образом не подтверждают, что они являются предполагаемым получателем токена. Подробности см. в разделе [Рекомендации по обеспечению безопасности: передача токенов через серверы](/specification/2025-11-25/basic/security_best_practices#token-passthrough).

Если сервер MCP отправляет запросы к вышестоящим API, он может выступать в качестве клиента OAuth. Токен доступа, используемый в вышестоящем API, является отдельным токеном, выданным вышестоящим сервером авторизации. Сервер MCP **НЕ ДОЛЖЕН** передавать токен, полученный от клиента MCP.

Клиенты MCP **ОБЯЗАТЕЛЬНО** должны реализовать и использовать параметр `resource`, как определено в [RFC 8707 - Индикаторы ресурсов для OAuth 2.0](https://www.rfc-editor.org/rfc/rfc8707.html).
Необходимо явно указать целевой ресурс, для которого запрашивается токен. Это требование соответствует рекомендации, изложенной в...
[Раздел 7.4 RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728#section-7.4). Это гарантирует, что токены доступа привязаны к предназначенным для них ресурсам и
Не может быть использован не по назначению в разных сервисах.

## Расширения авторизации MCP

В основной протокол внесено несколько расширений, определяющих дополнительные механизмы авторизации. К таким расширениям относятся:

* **Необязательно** - Внедрение этих расширений возможно по желанию.
* **Аддитивные** расширения не изменяют и не нарушают основную функциональность протокола; они добавляют новые возможности, сохраняя при этом поведение основного протокола.
* **Компонуемость** — Расширения имеют модульную структуру и разработаны для совместной работы без конфликтов, что позволяет одновременно использовать несколько расширений в различных реализациях.
* **Версионирование осуществляется независимо** — Расширения следуют основному циклу версионирования MCP, но при необходимости могут использовать независимое версионирование.

Список поддерживаемых расширений можно найти в репозитории [MCP Authorization Extensions](https://github.com/modelcontextprotocol/ext-auth).
