# Архитектура

<div id="enable-section-numbers" />

Протокол контекстной модели (MCP) использует архитектуру клиент-хост-сервер, где каждый
Хост может запускать несколько экземпляров клиента. Такая архитектура позволяет пользователям интегрировать ИИ.
расширяемые возможности для различных приложений при сохранении четких границ безопасности и
Изолирование проблем. Созданный на основе JSON-RPC, MCP предоставляет протокол с сохранением состояния сеанса, ориентированный на...
об обмене контекстом и координации выборки между клиентами и серверами.

## Основные компоненты

```тема русалки={null}
график LR
    подграф "Процесс хоста приложения"
        H[Хост]
        C1[Клиент 1]
        C2[Клиент 2]
        C3[Клиент 3]
        H --> C1
        H --> C2
        H --> C3
    конец

    подграф "Локальная машина"
        S1[Сервер 1<br>Файлы и Git]
        S2[Сервер 2<br>База данных]
        R1[("Локальный<br>Ресурс A")]
        R2[("Локальный<br>Ресурс B")]

        C1 --> S1
        C2 --> S2
        S1 <--> R1
        S2 <--> R2
    конец

    подграф «Интернет»
        S3[Сервер 3<br>Внешние API]
        R3[("Удаленный<br>Ресурс C")]

        C3 --> S3
        S3 <--> R3
    конец
```

### Хозяин

Основной процесс выступает в роли контейнера и координатора:

* Создает и управляет несколькими экземплярами клиентских приложений.
* Управляет правами доступа и жизненным циклом клиентских подключений.
* Обеспечивает соблюдение политик безопасности и требований к согласию.
* Обрабатывает решения об авторизации пользователей
* Координирует интеграцию ИИ/LLM и отбор проб.
* Управляет агрегацией контекста между клиентами

### Клиенты

Каждый клиент создается хостом и поддерживает изолированное соединение с сервером:

* Устанавливает одну сессию с сохранением состояния для каждого сервера
* Обрабатывает согласование протоколов и обмен данными о возможностях.
* Перенаправляет сообщения протокола в обоих направлениях.
* Управляет подписками и уведомлениями
* Обеспечивает соблюдение границ безопасности между серверами.

Основное приложение создает и управляет множеством клиентов, причем каждый клиент имеет соотношение 1:1.
отношения с конкретным сервером.

### Серверы

Серверы предоставляют специализированный контекст и возможности:

* Предоставляйте доступ к ресурсам, инструментам и подсказкам с помощью примитивов MCP.
* Работать самостоятельно, сосредоточив свои обязанности на конкретных задачах.
* Запрос на отбор проб осуществляется через клиентский интерфейс.
* Необходимо соблюдать ограничения безопасности.
* Это могут быть локальные процессы или удаленные сервисы.

## Принципы проектирования

MCP построен на основе нескольких ключевых принципов проектирования, которые определяют его архитектуру и
выполнение:

1. **Создание серверов должно быть предельно простым.**
   * Приложения хоста выполняют сложные задачи оркестрации.
   * Серверы ориентированы на конкретные, четко определенные возможности.
   * Простые интерфейсы минимизируют накладные расходы на реализацию.
   * Четкое разделение обеспечивает поддерживаемость кода

2. **Серверы должны обладать высокой степенью компонуемости.**
   * Каждый сервер предоставляет выделенные функции изолированно.
   * Несколько серверов можно беспрепятственно объединять.
   * Общий протокол обеспечивает совместимость
   * Модульная конструкция обеспечивает расширяемость

3. **Серверы не должны иметь возможность читать весь разговор и "видеть" мысли других пользователей.
   серверы**
   * Серверы получают только необходимую контекстную информацию
   * Вся история переписки остается у организатора.
   * Каждое серверное соединение обеспечивает изоляцию
   * Взаимодействие между серверами контролируется хостом.
   * Процесс хоста обеспечивает соблюдение границ безопасности.

4. **Функции могут добавляться на серверы и клиенты постепенно.**
   * Основной протокол обеспечивает минимально необходимую функциональность.
   * Дополнительные возможности могут быть согласованы по мере необходимости.
   * Серверы и клиенты развиваются независимо друг от друга
   * Протокол разработан с учетом возможности дальнейшего расширения
   * Обратная совместимость сохранена

## Переговоры о возможностях

Протокол контекстной модели использует систему согласования на основе возможностей, в которой клиенты и
Серверы явно указывают поддерживаемые ими функции во время инициализации. Возможности
определить, какие функции и примитивы протокола доступны во время сеанса.

* Серверы объявляют о таких возможностях, как подписка на ресурсы, поддержка инструментов и запрос информации.
  шаблоны
* Клиенты заявляют о таких возможностях, как поддержка выборки и обработка уведомлений.
* Обе стороны должны уважать заявленные возможности на протяжении всего заседания.
* Дополнительные возможности могут быть согласованы путем расширения протокола.

```тема русалки={null}
диаграмма последовательности
    участник Ведущий
    участник Клиент
    участник Сервер

    Хост->>+Клиент: Инициализация клиента
    Клиент->>+Сервер: Инициализация сессии с указанием возможностей
    Сервер-->>Клиент: Ответьте, указав поддерживаемые возможности.

    Примечание относительно хоста/сервера: активная сессия с согласованными функциями.

    Цикл запросов клиентов
        Хост->>Клиент: Действие, инициированное пользователем или моделью.
        Клиент->>Сервер: Запрос (инструменты/ресурсы)
        Сервер-->>Клиент: Ответ
        Клиент-->>Хост: Обновить пользовательский интерфейс или ответить модели
    конец

    Цикл запросов к серверу
        Сервер->>Клиент: Запрос (выборка)
        Клиент->Хост: Переадресация на ИИ
        Хост-->>Клиент: Ответ ИИ
        Клиент-->>Сервер: Ответ
    конец

    цикл Уведомления
        Сервер--)Клиент: Обновление ресурсов
        Клиент--)Сервер: Изменения статуса
    конец

    Хост->>Клиент: Завершение
    Клиент->>-Сервер: Завершение сессии
    деактивировать сервер
```

Каждая из этих возможностей открывает доступ к определенным функциям протокола, которые можно использовать во время сеанса.
пример:

* Реализованные [функции сервера](/specification/2025-11-25/server) должны быть анонсированы в
  возможности сервера
* Для отправки уведомлений о подписке на ресурсы серверу необходимо объявить
  поддержка подписки
* Для вызова инструмента сервер должен объявить о возможностях инструмента.
* [Выборка](/specification/2025-11-25/client) требует от клиента указать поддержку в своем
  возможности

Такое согласование возможностей гарантирует, что клиенты и серверы будут иметь четкое понимание
Поддерживается функциональность при сохранении расширяемости протокола.
