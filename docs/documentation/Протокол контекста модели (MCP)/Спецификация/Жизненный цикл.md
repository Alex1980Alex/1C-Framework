## Этапы жизненного цикла

### Инициализация

Этап инициализации **ОБЯЗАТЕЛЬНО** должен быть первым взаимодействием между клиентом и сервером.
На этом этапе клиент и сервер:

* Обеспечить совместимость версий протокола
* Возможности обмена и ведения переговоров
* Предоставьте подробную информацию о реализации

Клиент **ОБЯЗАН** инициировать этот этап, отправив запрос `initialize`, содержащий:

* Поддерживаемая версия протокола
* Возможности клиента
* Информация о реализации для клиента

#### Согласование версий

В запросе `initialize` клиент **ОБЯЗАТЕЛЬНО** должен указать поддерживаемую им версию протокола.
Это **ДОЛЖНА** быть *последняя* версия, поддерживаемая клиентом.

Если сервер поддерживает запрошенную версию протокола, он **ОБЯЗАН** ответить тем же самым.
версия. В противном случае сервер **ОБЯЗАН** ответить другой версией протокола.
Поддерживается. Это **ДОЛЖНА** быть *последняя* версия, поддерживаемая сервером.

Если клиент не поддерживает версию, указанную в ответе сервера, он **должен** поддерживать.
отключить.

<Примечание>
  При использовании HTTP клиент **ОБЯЗАТЕЛЬНО** должен включать HTTP-заголовок `MCP-Protocol-Version: <protocol-version>` во всех последующих запросах к MCP.
  сервер.
  Подробности см. в разделе [Заголовок версии протокола в разделе Транспорты](/specification/2025-11-25/basic/transports#protocol-version-header).
</Примечание>

#### Переговоры о возможностях

Возможности клиента и сервера определяют, какие дополнительные функции протокола будут доступны.
доступно во время сессии.

Ключевые возможности включают в себя:

| Категория | Возможности         | Описание                                                                                                          |
| --------- | ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Клиент    | `roots`             | Возможность предоставления файловой системы [roots](/specification/2025-11-25/client/roots)                       |
| Клиент    | `выборка`           | Поддержка запросов LLM [выборка](/specification/2025-11-25/client/ampling)                                        |
| Клиент    | `elicitation`       | Поддержка запросов сервера [elicitation](/specification/2025-11-25/client/elicitation)                            |
| Клиент    | `tasks`             | Поддержка запросов клиента с расширением задач ([task-augmented](/specification/2025-11-25/basic/utilities/tasks) |
| Клиент    | `экспериментальный` | Описывает поддержку нестандартных экспериментальных функций                                                       |
| Сервер    | `prompts`           | Предлагает [шаблоны подсказок](/specification/2025-11-25/server/prompts)                                          |
| Сервер    | `resources`         | Предоставляет читаемые [ресурсы](/specification/2025-11-25/server/resources)                                      |
| Сервер    | `tools`             | Предоставляет вызываемые инструменты [tools](/specification/2025-11-25/server/tools)                              |
| Сервер    | `ведение журнала`   | Выдает структурированные [сообщения журнала](/specification/2025-11-25/server/utilities/logging)                  |
| Сервер    | `завершения`        | Поддерживает аргумент [автозавершение](/specification/2025-11-25/server/utilities/completion)                     |
| Сервер    | `tasks`             | Поддержка запросов к серверу с расширением [task-augmented](/specification/2025-11-25/basic/utilities/tasks)      |
| Сервер    | `экспериментальный` | Описывает поддержку нестандартных экспериментальных функций                                                       |

Объекты Capability могут описывать подвозможности, например:

* `listChanged`: Поддержка уведомлений об изменении списка (для подсказок, ресурсов и т. д.)
  инструменты)
* `subscribe`: Поддержка подписки на изменения отдельных элементов (только для ресурсов)

### Операция

В ходе работы клиент и сервер обмениваются сообщениями в соответствии с
возможности, достигнутые в результате переговоров.

Обе стороны **ОБЯЗАНЫ**:

* Соблюдайте согласованную версию протокола.
* Используйте только те возможности, которые были успешно согласованы.

### Неисправность

На этапе завершения работы одна из сторон (обычно клиент) корректно завершает протокол.
соединение. Конкретные сообщения для завершения работы не определены — вместо этого используется базовый транспорт.
Для сигнализации о завершении соединения следует использовать следующий механизм:

#### стдио

Для стандартного транспорта [stdio](/specification/2025-11-25/basic/transports) клиент **ДОЛЖЕН** инициировать
отключено:

1. Во-первых, закрываем входной поток для дочернего процесса (сервера).
2. Ожидание завершения работы сервера или отправка сигнала `SIGTERM`, если сервер не завершает работу.
   в разумные сроки
3. Отправка `SIGKILL`, если сервер не завершит работу в течение разумного времени после `SIGTERM`.

Сервер **МОЖЕТ** инициировать завершение работы, закрыв свой выходной поток для клиента и
выход.

#### HTTP

Для HTTP [транспортов](/specification/2025-11-25/basic/transports) завершение работы обозначается закрытием
связанные HTTP-соединения.

## Тайм-ауты

В реализациях **следует** устанавливать тайм-ауты для всех отправленных запросов, чтобы предотвратить зависание.
Проблемы с соединениями и исчерпание ресурсов. Когда запрос не получил подтверждения об успешном выполнении или об ошибке.
Если отправитель не отреагирует в течение установленного времени, он **ДОЛЖЕН** инициировать [отмену].
уведомление](/specification/2025-11-25/basic/utilities/cancellities) для этого запроса и прекратить ожидание
ответ.

SDK и другое промежуточное ПО **ДОЛЖНЫ** позволять настраивать эти тайм-ауты.
на основе запросов.

В некоторых реализациях **МОЖЕТ** быть выбрана опция сброса таймера ожидания при получении сигнала [прогресса].
уведомление](/specification/2025-11-25/basic/utilities/progress), соответствующее запросу, поскольку это
Это подразумевает, что работа действительно ведётся. Однако реализации **ДОЛЖНЫ** всегда
Установить максимальный тайм-аут, независимо от уведомлений о ходе выполнения, чтобы ограничить влияние
Некорректная работа клиента или сервера.

## Обработка ошибок

Внедрение **должно** быть готово к обработке следующих случаев ошибок:

* Несоответствие версий протокола
* Неспособность согласовать необходимые возможности
* Запрос [таймаутов](#таймаутов)

Пример ошибки инициализации:

```json theme={null}

  "jsonrpc": "2.0",
  "id": 1,

      "запрошено": "1.0.0"
    }
```
