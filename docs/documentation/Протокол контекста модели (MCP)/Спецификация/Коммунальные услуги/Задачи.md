# Задачи

<div id="enable-section-numbers" />

<Информация>**Ревизия протокола**: 2025-11-25</Информация>

<Примечание>
  Эти задачи были введены в версии спецификации MCP от 2025-11-25 и в настоящее время считаются **экспериментальными**.
  В будущих версиях протокола дизайн и поведение задач могут измениться.
</Примечание>

Протокол контекстной модели (MCP) позволяет запрашивающим сторонам — которые могут быть как клиентами, так и серверами, в зависимости от направления связи — дополнять свои запросы **задачами**. Задачи представляют собой устойчивые конечные автоматы, несущие информацию о базовом состоянии выполнения запроса, который они содержат, и предназначены для опроса запрашивающей стороны и отложенного получения результатов. Каждая задача однозначно идентифицируется с помощью сгенерированного получателем **идентификатора задачи**.

Задачи полезны для представления ресурсоемких вычислений и запросов на пакетную обработку, а также легко интегрируются с внешними API для управления заданиями.

## Определения

В задачах стороны выступают либо в роли «запрашивающих», либо в роли «получающих», определяемых следующим образом:

* **Запрашивающий:** Отправитель запроса, дополненного задачей. Это может быть клиент или сервер — любой из них может создавать задачи.
* **Получатель:** Получатель запроса, дополненного задачей, и сущность, выполняющая эту задачу. Это может быть клиент или сервер — любой из них может получать и выполнять задачи.

## Модель взаимодействия с пользователем

Задачи разработаны таким образом, чтобы их выполнял **запрашивающий** субъект: запрашивающие субъекты отвечают за дополнение запросов задачами и за получение результатов выполнения этих задач; в то же время получатели строго контролируют, какие запросы (если таковые имеются) поддерживают выполнение на основе задач, и управляют жизненными циклами этих задач.

Такой подход, ориентированный на инициатора запроса, обеспечивает детерминированную обработку ответов и позволяет использовать сложные схемы, такие как отправка параллельных запросов, для организации которых у инициатора запроса имеется достаточный контекст.

Реализации могут свободно предоставлять доступ к задачам через любой интерфейс, соответствующий их потребностям — сам протокол не предписывает какую-либо конкретную модель взаимодействия с пользователем.

## Возможности

Серверы и клиенты, поддерживающие запросы с расширением задач, **ОБЯЗАТЕЛЬНО** должны объявить о наличии возможности `tasks` во время инициализации. Возможность `tasks` структурирована по категориям запросов, при этом логические свойства указывают, какие конкретные типы запросов поддерживают расширение задач.

### Возможности сервера

Серверы заявляют, поддерживают ли они задачи, и если да, то какие запросы на стороне сервера могут быть дополнены задачами.

| Возможности                 | Описание                                                                       |
| --------------------------- | ------------------------------------------------------------------------------ |
| `tasks.list`                | Сервер поддерживает операцию `tasks/list`                                      |
| `tasks.cancel`              | Сервер поддерживает операцию `tasks/cancel`                                    |
| `tasks.requests.tools.call` | Сервер поддерживает запросы `tools/call` с расширением, соответствующим задаче |

```json theme={null}
{
  "возможности": {
    "задачи": {
      "список": {},
      "отмена": {},
      "запросы": {
        "инструменты": {
          "вызов": {}
        }
      }
    }
  }
}
```

### Возможности клиента

Клиенты указывают, поддерживают ли они задачи, и если да, то какие запросы на стороне клиента могут быть дополнены задачами.

| Возможности                             | Описание                                                                  |
| --------------------------------------- | ------------------------------------------------------------------------- |
| `tasks.list`                            | Клиент поддерживает операцию `tasks/list`                                 |
| `tasks.cancel`                          | Клиент поддерживает операцию `tasks/cancel`                               |
| `tasks.requests.sampling.createMessage` | Клиент поддерживает запросы `sampling/createMessage` с расширением задачи |
| `tasks.requests.elicitation.create`     | Клиент поддерживает запросы `elicitation/create` с расширением до задач   |

```json theme={null}
{
  "возможности": {
    "задачи": {
      "список": {},
      "отмена": {},
      "запросы": {
        "выборка": {
          "createMessage": {}
        },
        "вызывание": {
          "создавать": {}
        }
      }
    }
  }
}
```

### Переговоры о возможностях

На этапе инициализации обе стороны обмениваются своими возможностями по управлению задачами, чтобы определить, какие операции поддерживают выполнение задач. Запрашивающие стороны **СЛЕДУЕТ** дополнять запросы задачей только в том случае, если соответствующая возможность была заявлена ​​получателем.

Например, если возможности сервера включают `tasks.requests.tools.call: {}`, то клиенты могут дополнять запросы `tools/call` задачей. Если возможности клиента включают `tasks.requests.sampling.createMessage: {}`, то серверы могут дополнять запросы `sampling/createMessage` задачей.

Если параметр `capabilities.tasks` не определен, участник сети **НЕ ДОЛЖЕН** пытаться создавать задачи во время обработки запросов.

Набор возможностей в `capabilities.tasks.requests` является исчерпывающим. Если тип запроса отсутствует, он не поддерживает расширение задач.

Параметр `capabilities.tasks.list` определяет, поддерживается ли операция `tasks/list` соответствующей стороной.

Параметр `capabilities.tasks.cancel` определяет, поддерживается ли операция `tasks/cancel` стороной.

### Переговоры на уровне инструментов

Вызовы инструментов рассматриваются с особым вниманием в целях расширения функциональности задач. В результате выполнения команды `tools/list` инструменты объявляют о поддержке задач через `execution.taskSupport`, который, если присутствует, может иметь значение `"required"`, `"optional"` или `"forbidden"`.

Это следует рассматривать как дополнительный, более детальный слой, расширяющий существующие возможности, в соответствии со следующими правилами:

1. Если возможности сервера не включают `tasks.requests.tools.call`, то клиенты **НЕ ДОЛЖНЫ** пытаться использовать расширение задач на инструментах этого сервера, независимо от значения `execution.taskSupport`.
2. Если возможности сервера включают `tasks.requests.tools.call`, то клиенты учитывают значение `execution.taskSupport` и обрабатывают его соответствующим образом:
   1. Если `execution.taskSupport` отсутствует или `"forbidden"`, клиенты **НЕ ДОЛЖНЫ** пытаться запустить инструмент в качестве задачи. Серверы **ДОЛЖНЫ** возвращать ошибку `-32601` (Метод не найден), если клиент попытается это сделать. Это поведение по умолчанию.
   2. Если `execution.taskSupport` имеет значение `"optional"`, клиенты **МОГУТ** вызывать инструмент как задачу или как обычный запрос.
   3. Если `execution.taskSupport` имеет значение `"required"`, клиенты **ОБЯЗАТЕЛЬНО** должны вызывать инструмент как задачу. Серверы **ОБЯЗАТЕЛЬНО** должны возвращать ошибку `-32601` (Метод не найден), если клиент не пытается это сделать.

## Протокольные сообщения

### Создание задач

Запросы, дополненные функциональностью задачи, имеют двухфазную схему ответа, отличающуюся от обычных запросов:

* **Обычные запросы**: Сервер обрабатывает запрос и напрямую возвращает фактический результат операции.
* **Запросы с дополнениями к задаче**: Сервер принимает запрос и немедленно возвращает объект `CreateTaskResult`, содержащий данные задачи. Фактический результат операции становится доступен позже через `tasks/result` после завершения задачи.

Для создания задачи запрашивающие лица отправляют запрос, содержащий поле `task` в параметрах запроса. Запрашивающие лица **МОГУТ** указать значение `ttl`, определяющее желаемую продолжительность жизни задачи (в миллисекундах) с момента ее создания.

**Запрос:**

```json theme={null}
{
  "jsonrpc": "2.0",
  "id": 1,
  "метод": "инструменты/вызов",
  "параметры": {
    "name": "get_weather",
    "аргументы": {
      «город»: «Нью-Йорк»
    },
    "задача": {
      "ttl": 60000
    }
  }
}
```

**Ответ:**

```json theme={null}
{
  "jsonrpc": "2.0",
  "id": 1,
  "результат": {
    "задача": {
      "taskId": "786512e2-9e0d-44bd-8f29-789f320fe840",
      "статус": "работает",
      "statusMessage": "Операция выполняется."
      "createdAt": "2025-11-25T10:30:00Z",
      "lastUpdatedAt": "2025-11-25T10:40:00Z",
      "ttl": 60000,
      "pollInterval": 5000
    }
  }
}
```

Когда получатель принимает запрос с дополнениями к задаче, он возвращает объект [`CreateTaskResult`](/specification/2025-11-25/schema#createtaskresult), содержащий данные задачи. Ответ не включает фактический результат операции. Фактический результат (например, результат работы инструмента для `tools/call`) становится доступен только через `tasks/result` после завершения задачи.

<Примечание>
  Когда задача создается в ответ на запрос `tools/call`, хост-приложения могут захотеть вернуть управление модели на время выполнения задачи. Это позволяет модели продолжать обработку других запросов или выполнять дополнительную работу, ожидая завершения задачи.

  Для поддержки этого шаблона серверы могут указывать необязательный ключ `io.modelcontextprotocol/model-immediate-response` в поле `_meta` объекта `CreateTaskResult`. Значение этого ключа должно представлять собой строку, предназначенную для передачи в модель в качестве немедленного результата работы инструмента.
  Если сервер не предоставляет это поле, хост-приложение может использовать собственное предопределенное сообщение.

  Данные рекомендации не являются обязательными и представляют собой предварительную логику, предназначенную для учета конкретного сценария использования. В будущих версиях протокола это поведение может быть формализовано или изменено в рамках функции `CreateTaskResult`.
</Примечание>

### Получение заданий

<Примечание>
  В протоколе Streamable HTTP (SSE) клиенты **МОГУТ** отключиться от потока SSE, открытого сервером в ответ на запрос `tasks/get`, в любой момент времени.

  Хотя данное примечание не содержит предписаний относительно конкретного использования потоков SSE, все реализации **ДОЛЖНЫ** продолжать соответствовать существующей [спецификации потокового HTTP-транспорта](../transports#sending-messages-to-the-server).
</Примечание>

Заказчики проверяют завершение задачи, отправляя запросы [`tasks/get`](/specification/2025-11-25/schema#tasks%2Fget).
Заявители **ДОЛЖНЫ** соблюдать указанный в ответах параметр `pollInterval` при определении частоты опроса.

Запрашивающим сторонам **СЛЕДУЕТ** продолжать опрос до тех пор, пока задача не достигнет конечного состояния («завершено», «неудачно» или «отменено») или пока не будет достигнут статус [`input_required`](#input-required-status). Обратите внимание, что вызов `tasks/result` не означает, что запрашивающей стороне необходимо прекратить опрос — запрашивающим сторонам **СЛЕДУЕТ** продолжать опрашивать статус задачи через `tasks/get`, если они не ожидают завершения `tasks/result`.

**Запрос:**

```json theme={null}
{
  "jsonrpc": "2.0",
  "id": 3,
  "метод": "задачи/получить",
  "параметры": {
    "taskId": "786512e2-9e0d-44bd-8f29-789f320fe840"
  }
}
```

**Ответ:**

```json theme={null}
{
  "jsonrpc": "2.0",
  "id": 3,
  "результат": {
    "taskId": "786512e2-9e0d-44bd-8f29-789f320fe840",
    "статус": "работает",
    "statusMessage": "Операция выполняется."
    "createdAt": "2025-11-25T10:30:00Z",
    "lastUpdatedAt": "2025-11-25T10:40:00Z",
    "ttl": 30000,
    "pollInterval": 5000
  }
}
```

### Получение результатов задачи

<Примечание>
  В протоколе Streamable HTTP (SSE) клиенты **МОГУТ** отключиться от потока SSE, открытого сервером в ответ на запрос `tasks/result`, в любой момент времени.

  Хотя данное примечание не содержит предписаний относительно конкретного использования потоков SSE, все реализации **ДОЛЖНЫ** продолжать соответствовать существующей [спецификации потокового HTTP-транспорта](../transports#sending-messages-to-the-server).
</Примечание>

После завершения задачи результат операции извлекается через [`tasks/result`](/specification/2025-11-25/schema#tasks%2Fresult). Это отличается от первоначального ответа `CreateTaskResult`, который содержит только данные задачи. Структура результата соответствует исходному типу запроса (например, `CallToolResult` для `tools/call`).

Для получения результата выполненной задачи заказчики могут отправить запрос `tasks/result`:

В то время как `tasks/result` блокирует выполнение задачи до тех пор, пока она не достигнет конечного состояния, запрашивающие стороны могут продолжать опрос через `tasks/get` параллельно, если они не заблокированы в ожидании результата, например, если их предыдущий запрос `tasks/result` завершился неудачей или был отменен. Это позволяет запрашивающим сторонам отслеживать изменения статуса или отображать обновления хода выполнения задачи, даже после вызова `tasks/result`.

**Запрос:**

```json theme={null}
{
  "jsonrpc": "2.0",
  "id": 4,
  "метод": "задачи/результат",
  "параметры": {
    "taskId": "786512e2-9e0d-44bd-8f29-789f320fe840"
  }
}
```

**Ответ:**

```json theme={null}
{
  "jsonrpc": "2.0",
  "id": 4,
  "результат": {
    "содержание": [
      {
        "type": "text",
        "текст": "Текущая погода в Нью-Йорке:\nТемпература: 72°F\nУсловия: Переменная облачность"
      }
    ],
    "isError": false,
    "_мета": {
      "io.modelcontextprotocol/related-task": {
        "taskId": "786512e2-9e0d-44bd-8f29-789f320fe840"
      }
    }
  }
}
```

### Уведомление о статусе задачи

При изменении статуса задачи получатели **МОГУТ** отправить уведомление [`notifications/tasks/status`](/specification/2025-11-25/schema#notifications%2Ftasks%2Fstatus), чтобы сообщить инициатору об изменении. Это уведомление содержит полное состояние задачи.

**Уведомление:**

```json theme={null}
{
  "jsonrpc": "2.0",
  "метод": "уведомления/задачи/статус",
  "параметры": {
    "taskId": "786512e2-9e0d-44bd-8f29-789f320fe840",
    "статус": "завершено",
    "createdAt": "2025-11-25T10:30:00Z",
    "lastUpdatedAt": "2025-11-25T10:50:00Z",
    "ttl": 60000,
    "pollInterval": 5000
  }
}
```

Уведомление содержит полный объект [`Task`](/specification/2025-11-25/schema#task), включая обновленные `status` и `statusMessage` (если они присутствуют). Это позволяет запрашивающим сторонам получить доступ к полному состоянию задачи без выполнения дополнительного запроса `tasks/get`.

Заявители **НЕ ДОЛЖНЫ** полагаться на получение этих уведомлений, поскольку это необязательно. Получатели не обязаны отправлять уведомления о статусе и могут отправлять их только при определенных изменениях статуса. Заявители **СЛЕДУЕТ** продолжать опрашивать систему через `tasks/get`, чтобы убедиться, что они получают обновления статуса.

## Требования к поведению

Эти требования распространяются на все стороны, поддерживающие получение запросов, расширяющих функциональность задачи.

### Поддержка и выполнение задач

1. Получатели, которые не указывают возможности выполнения задачи для типа запроса, **ОБЯЗАНЫ** обрабатывать запросы этого типа обычным способом, игнорируя любые метаданные, расширяющие возможности задачи, если таковые имеются.
2. Получатели, объявляющие о возможности выполнения задачи для типа запроса, **МОГУТ** возвращать ошибку для запросов, не дополненных задачей, что потребует от запрашивающих использовать дополнение задачей.

### Требования к идентификатору задачи

1. Идентификаторы задач **ОБЯЗАТЕЛЬНО** должны быть строковыми значениями.
2. Идентификаторы задач **ОБЯЗАТЕЛЬНО** должны генерироваться получателем при создании задачи.
3. Идентификаторы задач **ОБЯЗАТЕЛЬНО** должны быть уникальными среди всех задач, контролируемых получателем.

### Жизненный цикл статуса задачи

1. Задачи **ОБЯЗАТЕЛЬНО** должны начинаться в статусе «в работе» при создании.
2. Получатели **ОБЯЗАТЕЛЬНО** должны передавать задачи только по следующим допустимым путям:
   1. Из состояния `working`: может перейти в состояния `input_required`, `completed`, `failed` или `cancelled`.
   2. Из состояния `input_required`: может перейти в состояния `working`, `completed`, `failed` или `cancelled`.
   3. Задачи со статусом «выполнено», «не выполнено» или «отменено» находятся в терминальном состоянии и **НЕ ДОЛЖНЫ** переходить в какой-либо другой статус.

**Диаграмма состояний задачи:**

```тема русалки={null}
stateDiagram-v2
    [*] --> работает

    рабочий --> требуется ввод
    рабочий --> терминал

    input_required --> работает
    input_required --> terminal

    терминал --> [*]

    обратите внимание на правую сторону терминала
        Терминальные состояния:
        • завершенный
        • неуспешный
        • отменено
    заключительная заметка
```

### Требуется ввод статуса

<Примечание>
  При использовании транспортного протокола Streamable HTTP (SSE) серверы часто закрывают потоки SSE после отправки ответного сообщения, что может привести к неоднозначности в отношении того, какой поток будет использоваться для последующих сообщений задачи.

  Серверы могут обрабатывать это, ставя сообщения в очередь для клиента, чтобы передавать связанные с задачей сообщения по побочным каналам вместе с другими ответами.

  Серверы обладают гибкостью в управлении потоками SSE во время опроса задач и получения результатов, и клиенты **ДОЛЖНЫ** ожидать доставки сообщений по любому потоку SSE, включая поток HTTP GET.
  Один из возможных подходов — поддержание потока SSE для `tasks/result` (см. примечания к статусу `input_required`).
  По возможности, серверам **НЕ СЛЕДУЕТ** переходить на поток SSE в ответ на запрос `tasks/get`, поскольку клиент указал, что желает получать результат путем опроса.

  Хотя данное примечание не содержит предписаний относительно конкретного использования потоков SSE, все реализации **ДОЛЖНЫ** продолжать соответствовать существующей [спецификации потокового HTTP-транспорта](../transports#sending-messages-to-the-server).
</Примечание>

1. Когда получатель задачи получает сообщения от инициатора запроса, необходимые для выполнения задачи, получатель **ДОЛЖЕН** перевести задачу в статус `input_required`.
2. Получатель **ОБЯЗАТЕЛЬНО** должен включить метаданные `io.modelcontextprotocol/related-task` в запрос, чтобы связать его с задачей.
3. Когда запрашивающая сторона сталкивается со статусом `input_required`, она **ДОЛЖНА** превентивно вызвать `tasks/result`.
4. Когда получатель получит все необходимые входные данные, задача **ДОЛЖНА** перейти из статуса `input_required` (обычно обратно в статус `working`).

### Управление временем жизни (TTL) и ресурсами

1. Получатели **ОБЯЗАТЕЛЬНО** должны включать в ответы на задания метку времени в формате `createdAt` [ISO 8601](https://datatracker.ietf.org/doc/html/rfc3339#section-5), чтобы указать, когда было создано задание.
2. Получатели **ОБЯЗАТЕЛЬНО** должны включать в ответы на задания метку времени в формате `lastUpdatedAt` [ISO 8601](https://datatracker.ietf.org/doc/html/rfc3339#section-5), чтобы указать, когда задание было обновлено в последний раз.
3. Приемники **МОГУТ** изменить запрошенную длительность `ttl`.
4. Получатели **ОБЯЗАТЕЛЬНО** должны указывать фактическую длительность `ttl` (или `null` для неограниченного времени) в ответах `tasks/get`.
5. После истечения времени жизни задачи (`ttl`), получатели **МОГУТ** удалить задачу и ее результаты, независимо от статуса задачи.
6. Получатели **МОГУТ** включать значение `pollInterval` (в миллисекундах) в ответы `tasks/get` для указания интервалов опроса. Запрашивающие стороны **ДОЛЖНЫ** учитывать это значение, если оно предоставлено.

### Получение результатов

1. Получатели, принимающие запрос с расширенными возможностями задачи, **ОБЯЗАТЕЛЬНО** должны возвращать в ответ объект `CreateTaskResult`. Этот результат **СЛЕДУЕТ** возвращать как можно скорее после принятия задачи.
2. Когда получатель получает запрос `tasks/result` для задачи, находящейся в конечном состоянии (`completed`, `failed` или `cancelled`), он **ОБЯЗАН** вернуть окончательный результат базового запроса, будь то успешный результат или ошибка JSON-RPC.
3. Когда получатель получает запрос `tasks/result` для задачи, находящейся в любом другом нетерминальном состоянии (`working` или `input_required`), он **ОБЯЗАН** блокировать ответ до тех пор, пока задача не достигнет терминального состояния.
4. Для задач, находящихся в терминальном состоянии, получатели **ОБЯЗАТЕЛЬНО** должны возвращать из `tasks/result` именно то, что вернул бы исходный запрос, будь то успешный результат или ошибка JSON-RPC.

### Связывание сообщений, относящихся к задаче

1. Все запросы, уведомления и ответы, связанные с задачей, **ОБЯЗАТЕЛЬНО** должны содержать ключ `io.modelcontextprotocol/related-task` в поле `_meta`, значение которого должно быть установлено в объект с `taskId`, соответствующим идентификатору связанной задачи.
   1. Например, запрос, от которого зависит вызов инструмента, дополненного задачей, **ДОЛЖЕН** иметь тот же идентификатор связанной задачи, что и задача этого вызова инструмента.
2. Для операций `tasks/get`, `tasks/result` и `tasks/cancel` параметр `taskId` в запросе **ДОЛЖЕН** использоваться в качестве источника достоверной информации для идентификации целевой задачи. Запрашивающие стороны **НЕ ДОЛЖНЫ** включать метаданные `io.modelcontextprotocol/related-task` в эти запросы, а получатели **ДОЛЖНЫ** игнорировать такие метаданные, если они присутствуют, в пользу параметра метода RPC.
   Аналогично, для операций `tasks/get`, `tasks/list` и `tasks/cancel` получателям **НЕ СЛЕДУЕТ** включать метаданные `io.modelcontextprotocol/related-task` в результирующие сообщения, поскольку `taskId` уже присутствует в структуре ответа.

### Уведомления о задачах

1. Получатели **МОГУТ** отправлять уведомления `notifications/tasks/status` при изменении статуса задачи.
2. Заявители **НЕ ДОЛЖНЫ** полагаться на получение уведомлений `notifications/tasks/status`, поскольку это необязательно.
3. При отправке уведомление `notifications/tasks/status` **НЕ ДОЛЖНО** включать метаданные `io.modelcontextprotocol/related-task`, поскольку идентификатор задачи уже присутствует в параметрах уведомления.

### Уведомления о ходе выполнения задачи

Запросы с расширенными возможностями поддерживают уведомления о ходе выполнения, как определено в спецификации [progress](./progress). Предоставленный в первоначальном запросе `progressToken` остается действительным на протяжении всего времени выполнения задачи.

### Список задач

1. Получателям **СЛЕДУЕТ** использовать постраничную навигацию с помощью курсора, чтобы ограничить количество задач, возвращаемых в одном ответе.
2. Получатели **ОБЯЗАТЕЛЬНО** должны включить `nextCursor` в ответ, если доступны дополнительные задачи.
3. Запрашивающие стороны **ОБЯЗАНЫ** рассматривать курсоры как непрозрачные токены и не пытаться их анализировать или изменять.
4. Если задача доступна для запроса через `tasks/get`, она **ОБЯЗАТЕЛЬНО** должна быть доступна для запроса через `tasks/list`.

### Отмена задачи

1. Получатели **ОБЯЗАНЫ** отклонять запросы на отмену задач, уже находящихся в терминальном состоянии («завершено», «не выполнено» или «отменено»), с кодом ошибки «-32602» (Недопустимые параметры).
2. После получения действительного запроса на отмену получатели **ДОЛЖНЫ** попытаться остановить выполнение задачи и **ОБЯЗАТЕЛЬНО** перевести задачу в статус «отменено» перед отправкой ответа.
3. После отмены задачи она **ОБЯЗАТЕЛЬНО** должна оставаться в статусе «отменено», даже если выполнение продолжается до конца или завершается с ошибкой.
4. Операция `tasks/cancel` не определяет поведение при удалении. Однако получатели **МОГУТ** удалять отмененные задачи по своему усмотрению в любое время, в том числе сразу после отмены или после истечения срока действия `ttl` задачи.
5. Заказчикам **НЕ СЛЕДУЕТ** полагаться на то, что отмененные задачи будут сохраняться в течение определенного периода времени, и им следует получить всю необходимую информацию перед отменой.

## Типы данных

### Задача

Задача представляет собой состояние выполнения запроса. Состояние задачи включает в себя:

* `taskId`: Уникальный идентификатор задачи
* `status`: Текущее состояние выполнения задачи
* `statusMessage`: Необязательное удобочитаемое сообщение, описывающее текущее состояние (может присутствовать для любого статуса, включая подробную информацию об ошибках для задач, завершившихся с ошибкой).
* `createdAt`: метка времени ISO 8601, когда была создана задача.
* `ttl`: Время в миллисекундах с момента создания задачи до ее удаления.
* `pollInterval`: Рекомендуемое время в миллисекундах между проверками состояния
* `lastUpdatedAt`: метка времени ISO 8601, когда в последний раз обновлялся статус задачи.

### Статус задачи

Задачи могут находиться в одном из следующих состояний:

* `working`: Запрос в данный момент обрабатывается.
* `input_required`: Получателю необходимы входные данные от запрашивающей стороны. Запрашивающая сторона должна вызвать `tasks/result` для получения запросов на ввод, даже если задача еще не достигла конечного состояния.
* `завершено`: Запрос успешно выполнен, результаты доступны.
* `failed`: Соответствующий запрос не был успешно завершен. В частности, для вызовов инструментов это включает случаи, когда для результата вызова инструмента параметр `isError` имеет значение true.
* `cancelled`: Запрос был отменен до завершения.

### Параметры задачи

При дополнении запроса выполнением задачи поле `task` включается в параметры запроса:

```json theme={null}
{
  "задача": {
    "ttl": 60000
  }
}
```

Поля:

* `ttl` (число, необязательно): Запрашиваемая продолжительность в миллисекундах, в течение которой задача будет сохранена с момента создания.

### Метаданные связанных задач

Все запросы, ответы и уведомления, связанные с задачей, **ОБЯЗАТЕЛЬНО** должны содержать ключ `io.modelcontextprotocol/related-task` в `_meta`:

```json theme={null}
{
  "io.modelcontextprotocol/related-task": {
    "taskId": "786512e2-9e0d-44bd-8f29-789f320fe840"
  }
}
```

Это позволяет связывать сообщения с исходной задачей на протяжении всего жизненного цикла запроса.

Для операций `tasks/get`, `tasks/list` и `tasks/cancel` запрашивающим и получающим **НЕ СЛЕДУЕТ** включать эти метаданные в свои сообщения, поскольку `taskId` уже присутствует в структуре сообщения.
Операция `tasks/result` **ОБЯЗАТЕЛЬНО** должна включать эти метаданные в свой ответ, поскольку сама структура результата не содержит идентификатора задачи.

## Обработка ошибок

В задачах используются два механизма сообщения об ошибках:

1. **Протокольные ошибки**: Стандартные ошибки JSON-RPC, связанные с проблемами на уровне протокола.
2. **Ошибки выполнения задачи**: Ошибки в выполнении базового запроса, отображаемые в статусе задачи.

### Ошибки протокола

Получатели **ОБЯЗАТЕЛЬНО** должны возвращать стандартные ошибки JSON-RPC для следующих случаев ошибок протокола:

* Недопустимый или несуществующий `taskId` в `tasks/get`, `tasks/result` или `tasks/cancel`: `-32602` (Недопустимые параметры)
* Недопустимый или несуществующий курсор в `tasks/list`: `-32602` (Недопустимые параметры)
* Попытка отменить задачу, уже находящуюся в терминальном состоянии: `-32602` (Недопустимые параметры)
* Внутренние ошибки: `-32603` (Внутренняя ошибка)

Кроме того, получатели **МОГУТ** возвращать следующие ошибки:

* Запрос, не требующий расширения задачи, если получателю требуется расширение задачи для данного типа запроса: `-32600` (Недействительный запрос)

Приёмники **ДОЛЖНЫ** предоставлять информативные сообщения об ошибках, описывающие причину ошибок.

**Пример: Требуется расширение функциональности задачи**

```json theme={null}
{
  "jsonrpc": "2.0",
  "id": 1,
  "ошибка": {
    "код": -32600,
    "message": "Требуется расширение задачи для обработки запросов на инструменты/вызовы"
  }
}
```

**Пример: Задача не найдена**

```json theme={null}
{
  "jsonrpc": "2.0",
  "id": 70,
  "ошибка": {
    "код": -32602,
    "message": "Не удалось получить задачу: Задача не найдена"
  }
}
```

**Пример: Срок выполнения задачи истек**

```json theme={null}
{
  "jsonrpc": "2.0",
  "id": 71,
  "ошибка": {
    "код": -32602,
    "message": "Не удалось получить задачу: Срок действия задачи истек"
  }
}
```

<Примечание>
  Получатели не обязаны хранить задачи неограниченно долго. В соответствии с требованиями, получатель должен возвращать ошибку, указывающую на невозможность найти задачу, если он удалил просроченную задачу.
</Примечание>

**Пример: Отмена задачи отклонена (уже завершена)**

```json theme={null}
{
  "jsonrpc": "2.0",
  "id": 74,
  "ошибка": {
    "код": -32602,
    "message": "Невозможно отменить задачу: уже находится в терминальном состоянии 'completed'"
  }
}
```

### Ошибки выполнения задачи

Если базовый запрос не завершается успешно, задача переходит в статус «failed». Это включает ошибки протокола JSON-RPC во время выполнения запроса или, в частности, вызовы инструментов, когда для результата инструмента параметр `isError` имеет значение true. Ответ `tasks/get` **ДОЛЖЕН** содержать поле `statusMessage` с диагностической информацией о сбое.

**Пример: Задача с ошибкой выполнения**

```json theme={null}
{
  "jsonrpc": "2.0",
  "id": 4,
  "результат": {
    "taskId": "786512e2-9e0d-44bd-8f29-789f820fe840",
    "статус": "сбой",
    "createdAt": "2025-11-25T10:30:00Z",
    "lastUpdatedAt": "2025-11-25T10:40:00Z",
    "ttl": 30000,
    "statusMessage": "Выполнение инструмента завершилось с ошибкой: превышен лимит запросов к API"
  }
}
```

Для задач, которые перекрывают запросы на вызов инструмента, если для результата выполнения инструмента параметр `isError` имеет значение `true`, задача должна перейти в статус `failed`.

Конечная точка `tasks/result` возвращает именно то, что вернул бы исходный запрос:

* Если исходный запрос привел к ошибке JSON-RPC, `tasks/result` **ОБЯЗАТЕЛЬНО** должен вернуть ту же ошибку JSON-RPC.
* Если запрос завершился ответом в формате JSON-RPC, `tasks/result` **ОБЯЗАТЕЛЬНО** должен вернуть успешный ответ в формате JSON-RPC, содержащий этот результат.

## Вопросы безопасности

### Изоляция задач и контроль доступа

Идентификаторы задач являются основным механизмом доступа к состоянию и результатам выполнения задач. Без надлежащего контроля доступа любая сторона, которая сможет угадать или получить идентификатор задачи, потенциально может получить доступ к конфиденциальной информации или манипулировать задачами, которые она не создавала.

При предоставлении контекста авторизации получатели **ОБЯЗАТЕЛЬНО** должны привязывать задачи к этому контексту.

Привязка контекста нецелесообразна для всех приложений. Некоторые MCP-серверы работают в средах без авторизации, например, в однопользовательских инструментах, или используют транспортные протоколы, не поддерживающие авторизацию.
В подобных ситуациях получатели **СЛЕДУЕТ** четко задокументировать это ограничение, поскольку результаты выполнения задачи могут быть доступны любому запрашивающему лицу, которое сможет угадать идентификатор задачи.
Если привязка контекста недоступна, получатели **ОБЯЗАТЕЛЬНО** должны генерировать криптографически защищенные идентификаторы задач с достаточной энтропией, чтобы предотвратить их угадывание, и должны рассмотреть возможность использования более коротких значений TTL для уменьшения окна уязвимости.

Если доступна привязка к контексту, получатели **ОБЯЗАНЫ** отклонять запросы `tasks/get`, `tasks/result` и `tasks/cancel` для задач, которые не относятся к тому же контексту авторизации, что и запрашивающий. Для запросов `tasks/list` получатели **ОБЯЗАНЫ** гарантировать, что возвращаемый список задач включает только задачи, связанные с контекстом авторизации запрашивающего.

Кроме того, получателям **СЛЕДУЕТ** внедрять ограничение скорости выполнения задач для предотвращения атак типа «отказ в обслуживании» и атак перечисления.

### Управление ресурсами

1. Приёмники **ДОЛЖНЫ**:
   1. Установить ограничения на количество одновременно выполняемых задач одним заказчиком.
   2. Установите максимальные значения времени жизни (ttl), чтобы предотвратить неограниченное удержание ресурсов.
   3. Оперативно удаляйте просроченные задачи, чтобы освободить ресурсы.
   4. Укажите максимально допустимую продолжительность `ttl`.
   5. Задокументируйте максимальное количество одновременно выполняемых задач на одного заказчика.
   6. Внедрить системы мониторинга и оповещения об использовании ресурсов.

### Аудит и ведение журналов

1. Приёмники **ДОЛЖНЫ**:
   1. Регистрируйте события создания, завершения и получения задач для целей аудита.
   2. Включайте контекст аутентификации в журналы, если он доступен.
   3. Отслеживайте подозрительные закономерности (например, большое количество неудачных запросов к задачам, чрезмерное количество опросов).
2. Заявители **должны**:
   1. Регистрируйте события жизненного цикла задач в целях отладки и аудита.
   2. Отслеживайте идентификаторы задач и связанные с ними операции.
