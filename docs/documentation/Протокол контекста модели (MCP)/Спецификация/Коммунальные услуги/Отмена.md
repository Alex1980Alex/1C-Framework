## Процесс отмены

Когда сторона хочет отменить обрабатываемый запрос, она отправляет сообщение `notifications/cancelled`.
уведомление, содержащее:

* Идентификатор запроса на отмену
* Необязательная строка с причиной, которую можно записать в журнал или отобразить.

```json theme={null}
{
  "jsonrpc": "2.0",
  "метод": "уведомления/отменено",
  "параметры": {
    "requestId": "123",
    Причина: «Пользователь запросил отмену»
  }
}
```

## Требования к поведению

1. Уведомления об отмене **ОБЯЗАТЕЛЬНО** должны содержать ссылки только на запросы, которые:
   * Ранее были выпущены в том же направлении
   * Предполагается, что работы еще не завершены.
2. Запрос `initialize` **НЕ ДОЛЖЕН** быть отменен клиентами.
3. Для запросов с расширением задач (./tasks) вместо уведомления `notifications/cancelled` **ОБЯЗАТЕЛЬНО** следует использовать запрос `tasks/cancel`. Задачи имеют собственный механизм отмены, который возвращает окончательное состояние задачи.
4. Получатели уведомлений об отмене **ДОЛЖНЫ**:
   * Остановить обработку отмененного запроса
   * Бесплатные сопутствующие ресурсы
   * Не отправлять ответ на отмененный запрос
5. Получатели **МОГУТ** игнорировать уведомления об отмене, если:
   * Указанный запрос неизвестен
   * Обработка завершена
   * Запрос отменить нельзя.
6. Отправитель уведомления об отмене **ДОЛЖЕН** игнорировать любой ответ на него.
   запрос, поступивший позже

## Примечания по реализации

* Обе стороны **ДОЛЖНЫ** регистрировать причины отмены для отладки.
* Пользовательский интерфейс приложения **ДОЛЖЕН** указывать на запрос об отмене.

## Обработка ошибок

Недействительные уведомления об отмене **СЛЕДУЕТ** игнорировать:

* Неизвестные идентификаторы запросов
* Уже выполненные запросы
* Некорректные уведомления

Это позволяет сохранить принцип "отправил и забыл" для уведомлений, одновременно допуская наличие расстояний между отправителями и получателями.
условия в асинхронной связи.
