## Сообщения

Все сообщения между клиентами и серверами MCP **ДОЛЖНЫ** соответствовать следующим правилам:
Спецификация [JSON-RPC 2.0](https://www.jsonrpc.org/specification). Протокол определяет
сообщения такого типа:

### Запросы

Запросы отправляются с клиента на сервер или наоборот для инициирования операции.

```typescript theme={null}
{
  jsonrpc: "2.0";
  id: строка | число;
  метод: строка;
  параметры?: {
    [ключ: строка]: неизвестно;
  };
}
```

* Запросы **ОБЯЗАТЕЛЬНО** должны содержать строковый или целочисленный идентификатор.
* В отличие от базового JSON-RPC, идентификатор **НЕ ДОЛЖЕН** быть `null`.
* Идентификатор запроса **НЕ ДОЛЖЕН** ранее использоваться запрашивающим лицом в рамках того же самого запроса.
  сессия.

### Ответы

В ответ на запросы отправляются сообщения, содержащие либо результат операции, либо ошибку.

#### Результаты ответов

[Ответы с результатами](/specification/2025-11-25/schema#jsonrpcresultresponse) отправляются после успешного завершения операции.

```typescript theme={null}
{
  jsonrpc: "2.0";
  id: строка | число;
  результат: {
    [ключ: строка]: неизвестно;
  }
}
```

* В результатах поиска **ОБЯЗАТЕЛЬНО** должен содержаться тот же идентификатор, что и в соответствующем запросе.
* В ответах на запрос "Результат" **ОБЯЗАТЕЛЬНО** должно быть поле `result`.
* Результат **МОЖЕТ** иметь любую структуру объекта JSON.

#### Ответы об ошибках

Сообщения об ошибках отправляются при сбое операции или возникновении ошибки.

```typescript theme={null}
{
  jsonrpc: "2.0";
  id?: строка | число;
  ошибка: {
    код: число;
    сообщение: строка;
    данные?: неизвестны;
  }
}
```

* Ответы об ошибках **ОБЯЗАТЕЛЬНО** должны содержать тот же идентификатор, что и соответствующий им запрос (за исключением случаев ошибок, когда идентификатор не удалось прочитать из-за некорректного формата запроса).
* Ответы об ошибках **ОБЯЗАТЕЛЬНО** должны содержать поле `error` с `code` и `message`.
* Коды ошибок **ОБЯЗАТЕЛЬНО** должны быть целыми числами.

### Уведомления

Уведомления отправляются с клиента на сервер или наоборот в виде одностороннего сообщения.
Получатель **НЕ ДОЛЖЕН** отправлять ответ.

```typescript theme={null}
{
  jsonrpc: "2.0";
  метод: строка;
  параметры?: {
    [ключ: строка]: неизвестно;
  };
}
```

* В уведомлениях **НЕ ДОЛЖНО** содержаться удостоверение личности.

## Использование JSON-схемы

Протокол контекста модели (MCP) использует JSON Schema для проверки данных на протяжении всего протокола. В этом разделе поясняется, как следует использовать JSON Schema в сообщениях MCP.

### Диалект схемы

MCP поддерживает JSON Schema со следующими правилами:

1. **Диалект по умолчанию**: Если схема не содержит поля `$schema`, по умолчанию используется [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/schema)
2. **Явное указание диалекта**: Схемы МОГУТ включать поле `$schema` для указания другого диалекта.
3. **Поддерживаемые диалекты**: Реализации ДОЛЖНЫ поддерживать как минимум диалекты 2020-12 и ДОЛЖНЫ документировать, какие дополнительные диалекты они поддерживают.
4. **Рекомендация**: Разработчикам РЕКОМЕНДУЕТСЯ использовать JSON Schema 2020-12.

### Пример использования

#### Диалект по умолчанию (2020-12):

```json theme={null}
{
  "type": "object",
  "характеристики": {
    "name": { "type": "string" },
    "возраст": { "тип": "целое число", "минимум": 0 }
  },
  "обязательно": ["имя"]
}
```

#### Явный диалект (проект-07):

```json theme={null}
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "характеристики": {
    "name": { "type": "string" },
    "возраст": { "тип": "целое число", "минимум": 0 }
  },
  "обязательно": ["имя"]
}
```

### Требования к реализации

* Клиенты и серверы **ОБЯЗАТЕЛЬНО** должны поддерживать JSON Schema 2020-12 для схем без явного поля `$schema`.
* Клиенты и серверы **ОБЯЗАНЫ** проверять схемы в соответствии с заявленным или используемым по умолчанию диалектом. Они **ОБЯЗАНЫ** корректно обрабатывать неподдерживаемые диалекты, возвращая соответствующую ошибку, указывающую на то, что диалект не поддерживается.
* Клиенты и серверы **ДОЛЖНЫ** документировать, какие диалекты схем они поддерживают.

### Проверка схемы

* Схемы **ОБЯЗАТЕЛЬНО** должны соответствовать заявленному или используемому по умолчанию диалекту.

## Общие поля

### `_meta`

Свойство/параметр `_meta` зарезервировано MCP для использования клиентами и серверами.
добавить дополнительные метаданные к своим взаимодействиям.

В соответствии с приведенными ниже правилами, MCP резервирует определенные ключевые имена для метаданных на уровне протокола;
В реализациях НЕ ДОЛЖНО делаться предположений о значениях этих ключей.

Кроме того, определения в [схеме](https://github.com/modelcontextprotocol/specification/blob/main/schema/2025-11-25/schema.ts)
могут быть зарезервированы определенные имена для метаданных, предназначенных для конкретных целей, как это указано в данных определениях.

**Формат имени ключа:** допустимые имена ключей `_meta` имеют два сегмента: необязательный **префикс** и **имя**.

**Префикс:**

* Если указано иное, ДОЛЖНО представлять собой последовательность меток, разделенных точками (`.`), за которыми следует косая черта (`/`).
  * Надписи ДОЛЖНЫ начинаться с буквы и заканчиваться буквой или цифрой; внутренние символы могут быть буквами, цифрами или дефисами (`-`).
  * В реализациях СЛЕДУЕТ использовать обратную DNS-нотацию (например, `com.example/` вместо `example.com/`).
* Любой префикс, где второй меткой является `modelcontextprotocol` или `mcp`, **зарезервирован** для использования в рамках MCP.
  * Например: `io.modelcontextprotocol/`, `dev.mcp/`, `org.modelcontextprotocol.api/` и `com.mcp.tools/` — все зарезервированы.
  * Однако, `com.example.mcp/` НЕ зарезервировано, поскольку второй меткой является `example`.

**Имя:**

* Если не пусто, должно начинаться и заканчиваться буквенно-цифровым символом (`[a-z0-9A-Z]`).
* Может содержать дефисы (`-`), подчеркивания (`_`), точки (`.`) и буквенно-цифровые символы между ними.

### `иконки`

Свойство `icons` предоставляет стандартизированный способ для серверов отображать визуальные идентификаторы своих ресурсов, инструментов, подсказок и реализаций. Иконки улучшают пользовательский интерфейс, предоставляя визуальный контекст и повышая доступность доступных функций.

Иконки представлены в виде массива объектов `Icon`, где каждая иконка включает в себя:

* `src`: URI, указывающий на ресурс значка (обязательно). Это может быть:
  * HTTP/HTTPS URL, указывающий на файл изображения
  * URI данных с данными изображения, закодированными в base64.
* `mimeType`: Необязательный MIME-тип, если тип сервера отсутствует или указан общий тип.
* `sizes`: Необязательный массив параметров размера (например, `["48x48"]`, `["any"]` для масштабируемых форматов, таких как SVG, или `["48x48", "96x96"]` для нескольких размеров)
* `theme`: Необязательный параметр темы (`light` или `dark`) для фона значка.

**Требуемая поддержка типов MIME:**

Клиенты, поддерживающие отображение значков, **ОБЯЗАТЕЛЬНО** должны поддерживать как минимум следующие MIME-типы:

* `image/png` — изображения в формате PNG (безопасные, универсальная совместимость)
* `image/jpeg` (и `image/jpg`) - изображения в формате JPEG (безопасная, универсальная совместимость)

Клиенты, поддерживающие отрисовку иконок, **ДОЛЖНЫ** также поддерживать:

* `image/svg+xml` — изображения SVG (масштабируемые, но требующие мер безопасности, как указано ниже)
* `image/webp` — изображения в формате WebP (современный, эффективный формат)

**Вопросы безопасности:**

Пользователи метаданных значков **ОБЯЗАНЫ** принимать соответствующие меры безопасности при работе со значками, чтобы предотвратить их компрометацию:

* Рассматривайте метаданные и байты значков как ненадежные входные данные и защищайтесь от сетевых рисков, рисков, связанных с конфиденциальностью, и рисков, связанных с некорректным анализом.
* Убедитесь, что URI значка использует протокол HTTPS или `data:`. Клиенты **ОБЯЗАТЕЛЬНО** должны отклонять URI значков, использующие небезопасные схемы и перенаправления, такие как `javascript:`, `file:`, `ftp:`, `ws:` или схемы URI локальных приложений.
  * Запретить изменение схемы и перенаправления на хосты с другим источником.
* Обеспечьте устойчивость к атакам, связанным с исчерпанием ресурсов из-за слишком больших изображений, больших размеров или чрезмерного количества кадров (например, в GIF-файлах).
  * Потребители **МОГУТ** устанавливать ограничения на размер изображений и контента.
* Получайте значки без учетных данных. Не отправляйте файлы cookie, заголовки `Authorization` или учетные данные клиента.
* Убедитесь, что URI значков имеют тот же источник, что и сервер. Это сводит к минимуму риск раскрытия данных или информации для отслеживания третьим лицам.
* Будьте осторожны при загрузке и отображении иконок, так как полезная нагрузка **МОЖЕТ** содержать исполняемый контент (например, SVG со встроенным JavaScript](https://www.w3.org/TR/SVG11/script.html) или расширенными возможностями](https://www.w3.org/TR/SVG11/extend.html)).
  * Пользователи **МОГУТ** запретить использование определенных типов файлов или иным образом очистить файлы значков перед отображением.
* Перед отображением проверяйте MIME-типы и содержимое файлов. Рассматривайте информацию о MIME-типах как рекомендацию. Определяйте тип содержимого с помощью магических байтов; отклоняйте при несоответствии или неизвестных типах.
  * Необходимо строго соблюдать список разрешенных типов изображений.

**Применение:**

Значки можно прикреплять к:

* `Реализация`: Визуальный идентификатор реализации сервера/клиента MCP.
* `Инструмент`: Визуальное представление функциональности инструмента.
* `Подсказка`: Значок для отображения рядом с шаблонами подсказок.
* `Ресурс`: Визуальный индикатор для различных типов ресурсов

Для поддержки различных контекстов отображения и разрешений можно предоставить несколько значков. Клиентам следует выбрать наиболее подходящий значок в соответствии со своими требованиями к пользовательскому интерфейсу.
