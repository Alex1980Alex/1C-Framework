## stdio

В транспорте **stdio**:

* Клиент запускает сервер MCP в качестве дочернего процесса.
* Сервер считывает сообщения JSON-RPC из стандартного ввода (`stdin`) и отправляет сообщения.
  в стандартный вывод (`stdout`).
* Сообщения представляют собой отдельные JSON-RPC запросы, уведомления или ответы.
* Сообщения разделяются символами новой строки и **НЕ ДОЛЖНЫ** содержать встроенные символы новой строки.
* Сервер **МОЖЕТ** записывать строки в кодировке UTF-8 в свой стандартный поток ошибок (`stderr`) для любых
  Для целей ведения журналов, включая информационные, отладочные и сообщения об ошибках.
* Клиент **МОЖЕТ** перехватывать, пересылать или игнорировать вывод `stderr` сервера.
  и **НЕ СЛЕДУЕТ** предполагать, что вывод `stderr` указывает на ошибки.
* Сервер **НЕ ДОЛЖЕН** записывать в свой `stdout` ничего, что не является допустимым сообщением MCP.
* Клиент **НЕ ДОЛЖЕН** записывать в стандартный ввод сервера ничего, что не является допустимым MCP.
  сообщение.

Сервер **ОБЯЗАТЕЛЬНО** должен предоставлять единый путь к конечной точке HTTP (далее именуемый...).

#### Предупреждение о безопасности

При реализации потокового HTTP-транспорта:

1. Серверы **ОБЯЗАТЕЛЬНО** должны проверять заголовок `Origin` во всех входящих соединениях, чтобы предотвратить атаки с использованием перепривязки DNS.
   * Если заголовок `Origin` присутствует и недействителен, серверы **ОБЯЗАТЕЛЬНО** должны ответить HTTP 403 Forbidden. HTTP-ответ
     Тело ответа **МОЖЕТ** представлять собой *ответ об ошибке* в формате JSON-RPC, не содержащий `id`.
2. При локальной работе серверы **ДОЛЖНЫ** привязываться только к localhost (127.0.0.1), а не ко всем сетевым интерфейсам (0.0.0.0).
3. Серверы **ДОЛЖНЫ** внедрить надлежащую аутентификацию для всех подключений.

Без этих мер защиты злоумышленники могли бы использовать перепривязку DNS для взаимодействия с локальными серверами MCP с удаленных веб-сайтов.

### Отправка сообщений на сервер

Каждое сообщение JSON-RPC, отправляемое клиентом, **ДОЛЖНО** представлять собой новый HTTP POST-запрос.
Конечная точка MCP.

1. Клиент **ОБЯЗАТЕЛЬНО** должен использовать HTTP POST для отправки сообщений JSON-RPC на конечную точку MCP.
2. Клиент **ОБЯЗАТЕЛЬНО** должен включить заголовок `Accept`, содержащий как `application/json`, так и
   В качестве поддерживаемых типов контента указаны `text/event-stream`.
3. Тело POST-запроса **ОБЯЗАТЕЛЬНО** должно представлять собой единый JSON-RPC *запрос*, *уведомление* или *ответ*.
4. Если входные данные представляют собой *ответ* или *уведомление* в формате JSON-RPC:
   * Если сервер принимает входные данные, он **ОБЯЗАН** вернуть HTTP-код состояния 202.
     Принято без тела.
   * Если сервер не может принять входные данные, он **ОБЯЗАН** вернуть код состояния ошибки HTTP.
     (например, 400 Bad Request). Тело HTTP-ответа **МОЖЕТ** содержать ошибку JSON-RPC.
     ответ*, не имеющий `id`.
5. Если входные данные представляют собой *запрос* в формате JSON-RPC, сервер **ОБЯЗАН** либо
   Возвращать `Content-Type: text/event-stream` для запуска потока SSE или
   `Content-Type: application/json` возвращает один JSON-объект. Клиент **ОБЯЗАТЕЛЬНО** должен
   подтверждают оба этих случая.
6. Если сервер инициирует поток SSE:
   * Сервер **ДОЛЖЕН** немедленно отправить событие SSE, состоящее из события
     Идентификатор и пустое поле `data` для подготовки клиента к повторному подключению.
     (используя этот идентификатор события в качестве `Last-Event-ID`).
   * После того, как сервер отправит клиенту событие SSE с идентификатором события,
     Сервер **МОЖЕТ** закрыть *соединение* (без завершения *потока SSE*).
     в любое время, чтобы избежать поддержания длительной связи. Клиент
     Затем **следует** "опросить" поток SSE, попытавшись переподключиться.
   * Если сервер закроет *соединение* до завершения *потока SSE*,
     Перед отправкой события SSE необходимо добавить стандартное поле [`retry`](https://html.spec.whatwg.org/multipage/server-sent-events.html#:~:text=field%20name%20is%20%22retry%22).
     Закрытие соединения. Клиент **ОБЯЗАН** учитывать поле `retry`.
     Ожидание заданного количества миллисекунд перед попыткой повторного подключения.
   * Поток SSE **ДОЛЖЕН** в конечном итоге включать *ответ* в формате JSON-RPC для
     JSON-RPC *запрос* отправляется в теле POST-запроса.
   * Сервер **МОЖЕТ** отправлять JSON-RPC *запросы* и *уведомления* перед отправкой
     JSON-RPC *ответ*. Эти сообщения **ДОЛЖНЫ** относиться к клиенту-отправителю.
     *запрос*.
   * Сервер **МОЖЕТ** прервать поток SSE, если [session](#session-management)
     истекает.
   *После отправки JSON-RPC *ответа* сервер **ДОЛЖЕН** завершить процесс.
     Поток SSE.
   * Разрыв соединения **МОЖЕТ** произойти в любое время (например, из-за проблем с сетью).
     Поэтому:
     * Разрыв соединения **НЕ СЛЕДУЕТ** интерпретировать как отмену клиентом своего запроса.
     * Для отмены клиенту **СЛЕДУЕТ** явно отправить уведомление MCP `CancelledNotification`.
     * Во избежание потери сообщений из-за разрыва соединения сервер **МОЖЕТ** передавать поток.
       [возобновляемый](#возобновляемость-и-повторная-доставка).

### Управление сессиями

«Сессия» MCP состоит из логически связанных взаимодействий между клиентом и
сервер, начиная с [фазы инициализации](/specification/2025-11-25/basic/lifecycle). Для поддержки
Серверы, желающие установить сессии с сохранением состояния:

1. Сервер, использующий протокол HTTP Streamable, **МОЖЕТ** присвоить идентификатор сессии по адресу
   время инициализации, путем включения его в заголовок `MCP-Session-Id` в HTTP-запросе.
   ответ, содержащий `InitializeResult`.
   * Идентификатор сессии **ДОЛЖЕН** быть уникальным во всем мире и криптографически защищенным (например,
     (безопасно сгенерированный UUID, JWT или криптографический хеш).
   * Идентификатор сессии **ОБЯЗАТЕЛЬНО** должен содержать только видимые символы ASCII (в диапазоне от 0x21 до
     0x7E).
   * Клиент **ОБЯЗАН** обрабатывать идентификатор сессии безопасным способом. Подробнее см. [Меры по предотвращению перехвата сессии](/specification/2025-11-25/basic/security_best_practices#session-hijacking).
2. Если сервер возвращает `MCP-Session-Id` во время инициализации, клиенты, использующие
   Транспорт Streamable HTTP ОБЯЗАТЕЛЬНО должен включать его в заголовок `MCP-Session-Id`.
   все их последующие HTTP-запросы.
   * Серверы, требующие идентификатор сессии, **ДОЛЖНЫ** отвечать на запросы без него.
     Заголовок `MCP-Session-Id` (кроме инициализации) приводит к ошибке HTTP 400 Bad Request.
3. Сервер **МОЖЕТ** завершить сессию в любое время, после чего он **ОБЯЗАН** ответить.
   к запросам, содержащим этот идентификатор сессии, с ошибкой HTTP 404 Not Found.
4. Когда клиент получает HTTP-код 404 в ответ на запрос, содержащий
   `MCP-Session-Id` — это **ОБЯЗАТЕЛЬНО** позволяет начать новую сессию, отправив новый `InitializeRequest`.
   без прикрепленного идентификатора сессии.
5. Клиенты, которым больше не нужна конкретная сессия (например, потому что пользователь уходит).
   Клиентское приложение должно отправить HTTP-запрос DELETE на конечную точку MCP с указанием
   Заголовок `MCP-Session-Id` используется для явного завершения сессии.
   * Сервер **МОЖЕТ** ответить на этот запрос кодом HTTP 405 Method Not Allowed.
     Это означает, что сервер не позволяет клиентам завершать сессии.

### Заголовок версии протокола

При использовании HTTP клиент **ОБЯЗАТЕЛЬНО** должен включать HTTP-заголовок `MCP-Protocol-Version: <protocol-version>` во всех последующих запросах к MCP.
сервер, позволяющий MCP-серверу отвечать в зависимости от версии протокола MCP.

Например: `MCP-Protocol-Version: 2025-11-25`

Версия протокола, отправленная клиентом, **ДОЛЖНА** соответствовать той, которая была согласована во время
инициализация](/specification/2025-11-25/basic/lifecycle#version-negotiation).

Для обеспечения обратной совместимости, если сервер *не* получает `MCP-Protocol-Version`
заголовок, и нет другого способа определить версию — например, полагаясь на заголовок.
Версия протокола согласовывается во время инициализации — сервер **ДОЛЖЕН** принять этот протокол.
версия `2025-03-26`.

Если сервер получает запрос с недопустимым или неподдерживаемым значением
`MCP-Protocol-Version`, он **ОБЯЗАТЕЛЬНО** должен ответить кодом `400 Bad Request`.
