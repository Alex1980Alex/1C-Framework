# 04.8 Dual-Vector BSL Search

> **Status (2026-04-30, Phase 8):** **Concept paper / research baseline.** Dual-vector layout (`content` + `module_path` named vectors) **НЕ применён** к Phase 8 production коллекциям — production retrieval `bsl_code_v4_late` (24 455 pts) использует **single-vector 4096d Qwen3** через TEI с Late Chunking pooling. Текущий код dual-vector pipeline присутствует, но bsl_code_v4 в Phase 8 пересоздана на 4096d single-vector. Потенциальный переход на named vectors `dense + bm25` с RRF fusion — [roadmap §32.3 Phase 9.3](../../roadmap/260426_ROADMAP_PHASE_8_QWEN3_EMBEDDING_REINDEX.md#323-phase-93--hybrid-sparsedense-2-4-часа). См. также [ADR-008 Late Chunking](../../../.claude/skills/architecture-research/adr/008-qwen3-late-chunking-for-bsl-retrieval.md).

## Обзор

Dual-Vector Search — стратегия поиска BSL кода, использующая два независимых векторных индекса для повышения релевантности результатов. В отличие от Hybrid Search (04.2), где BM25 и векторный поиск дополняют друг друга на уровне лексики и семантики, Dual-Vector разделяет **содержимое кода** и **структуру модуля** на отдельные векторные пространства, позволяя находить модули как по смыслу реализации, так и по семантике пути.

Стратегия особенно эффективна для запросов, содержащих названия модулей, типы объектов или иерархические пути конфигурации (например, "модуль менеджера справочника Контрагенты").

## Как работает

### Архитектура

DualVectorPipeline использует **пять последовательных этапов** для обработки запроса:

1. **BM25 Full-Text Search** — поиск по индексу SQLite FTS5 (~5 мс)
2. **Content Vector Search** — семантический поиск кода через вектор `content` (~50 мс)
3. **Module Path Vector Search** — поиск по пути модуля через вектор `module_path` (~50 мс)
4. **3-Way RRF Fusion** — объединение трёх рангированных списков через Reciprocal Rank Fusion
5. **Call Graph Boost** — переранжирование с учётом графа вызовов

### Названные векторы в Qdrant (концепт, не Phase 8)

В дизайне dual-vector коллекция `bsl_code_v4` содержала бы два независимых вектора размерностью **4096d Qwen3** (Phase 8) — изначально планировались **768d nomic** до миграции:

- **`content`** — эмбеддинг исходного текста модуля, захватывающий семантику реализации (алгоритмы, логика, назначение кода)
- **`module_path`** — эмбеддинг строкового пути модуля (например, "Документ.РеализацияТоваров.МодульОбъекта"), отражающий иерархию конфигурации и назначение модуля

Разделение позволило бы искать модули независимо — по содержимому ИЛИ по положению в иерархии конфигурации.

**В production (Phase 8):** `bsl_code_v4` и `bsl_code_v4_late` — **single-vector 4096d**, dual-vector layout не применён. Path-based reranking возможен через payload filter по `module_path`, не через отдельный vector space.

### Взвешенное слияние (RRF)

Три потока результатов объединяются через **Reciprocal Rank Fusion** с весами:

- **BM25:** 0.3 (точный лексический поиск по ключевым словам)
- **Content Vector:** 0.5 (основной семантический поиск кода)
- **Module Path Vector:** 0.2 (структурный поиск по пути)

**Критично:** веса должны суммироваться в 1.0. Перераспределение весов влияет на баланс между семантикой кода и структурой конфигурации.

### Call Graph Boost

После RRF применяется переранжирование на основе графа вызовов:

- Экспортируемые символы получают бонус 1.2x
- Символы с вызывающими процедурами добавляют бонус до 1.5x максимум
- Позволяет "поднять" часто используемые модули выше в результатах

## Использование

### Создание коллекции

```python
from src.bsl.semantic_search.services.dual_vector_search import create_dual_vector_collection

create_dual_vector_collection(qdrant_client, "bsl_code_v4_dual", vector_size=4096)
# NB: production bsl_code_v4 в Phase 8 — single-vector 4096d. Этот пример — для альтернативной коллекции при возврате к dual-vector экспериментам.
```

### Генерация эмбеддинга пути

```python
from src.bsl.semantic_search.services.dual_vector_search import generate_module_path_embedding

path_embedding = generate_module_path_embedding(embedder, "Документ.РеализацияТоваров.МодульОбъекта")
```

### Миграция с однозвекторной коллекции

```python
from src.bsl.semantic_search.services.dual_vector_search import migrate_collection

migrate_collection(
    qdrant_client,
    source_collection="bsl_code_v3",   # legacy E5 1024d (dropped 2026-04-30)
    target_collection="bsl_code_v4_dual",
    embedder=embedder,                 # должен быть Qwen3 4096d
    batch_size=100
)
```

### Поиск

```python
from src.bsl.semantic_search.services.dual_vector_search import DualVectorPipeline

pipeline = DualVectorPipeline(
    sqlite_db="cache/docs-mcp/hybrid_search.db",
    qdrant_client=qdrant_client,
    embedder=embedder,
    call_graph=call_graph,
    qdrant_collection="bsl_code_v4"
)

results = pipeline.search("модуль менеджера справочника Контрагенты", limit=10)
```

## Результаты

Dual-Vector Search улучшает **точность на +15-25%** по сравнению с однозвекторным поиском:

- Запрос "модуль менеджера справочника Контрагенты" находит точный модуль по пути, а не только семантически похожий код
- Структурные запросы разрешаются на этапе поиска, а не переранжирования
