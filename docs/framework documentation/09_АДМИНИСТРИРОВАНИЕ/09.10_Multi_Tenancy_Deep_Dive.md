# 09.10 Мультитенантность — Детали реализации и квоты

> Базовый обзор: [09.1 Мультитенантность](09.1_Мультитенантность.md). Этот файл — детали реализации (Phase 12 + Phase 60).

## Архитектура изоляции

Каждый тенант получает изолированные хранилища:

```
tenant "acme" → ChromaDB collection "tenant_acme"
              → NetworkX graph file  "data/tenants/graphs/acme.pkl"
              → SQLite metadata row  "data/tenants/tenants.db"

tenant "beta" → ChromaDB collection "tenant_beta"
              → ...
```

Изоляция полная: поиск по collection "tenant_acme" физически не видит данные "tenant_beta". Кэш (`dict[str, BaseVectorStore]`) хранит активные store-объекты в памяти; `asyncio.Lock` защищает одновременное создание.

## Sanitization tenant_id

Перед использованием как collection_name применяется sanitization:

```python
# Только [a-zA-Z0-9_], максимум 63 символа, обязательный префикс "tenant_"
tenant_id = "my-company.ru" → collection_name = "tenant_mycompanyru"
tenant_id = "АО Рога и Копыта" → collection_name = "tenant_"  # только ASCII
```

Правило: нестандартные символы удаляются, не заменяются. Проверяйте `collection_name` через `GET /tenants/{id}` перед использованием.

## Жизненный цикл тенанта

```
POST /tenants {"tenant_id": "acme"}
    → TenantVectorStoreManager.create_tenant("acme")
    → SQLite: INSERT INTO tenants (tenant_id, collection_name, created_at, ...)
    → ChromaDB: collection "tenant_acme" создаётся лениво при первом get_or_create_store()

POST /index + header X-Tenant-ID: acme
    → get_or_create_store("acme") → возвращает из кэша или создаёт ChromaDB collection
    → Документы индексируются ТОЛЬКО в collection "tenant_acme"

DELETE /tenants/acme
    → ChromaDB collection удаляется
    → SQLite: DELETE FROM tenants WHERE tenant_id = 'acme'
    → Кэш очищается
```

## Квоты (Phase 60)

Ограничения задаются через `TenantQuota`:

```python
class TenantQuota(BaseModel):
    max_documents: int | None = None      # None = безлимитно
    max_storage_mb: float | None = None
    max_queries_per_day: int | None = None
```

**REST API квот:**

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| `POST` | `/tenants/{id}/quota` | Задать квоту |
| `GET` | `/tenants/{id}/stats` | Текущее использование |

```bash
# Задать квоту
curl -X POST /tenants/acme/quota \
  -H "Content-Type: application/json" \
  -d '{"max_documents": 500, "max_storage_mb": 2048, "max_queries_per_day": 10000}'

# Проверить
curl /tenants/acme/stats
# → {"document_count": 142, "storage_bytes": 524288, "queries_today": 38}
```

При превышении квоты операция отклоняется с HTTP 429.

## JWT-интеграция

После Phase 12.3 tenant_id автоматически извлекается из JWT claim:

```python
# JWT payload: {"sub": "user123", "tenant_id": "acme", "role": "editor"}
# После decode → tenant_id = "acme" применяется ко всем операциям автоматически
```

Подробности: [09.2 Авторизация](09.2_Авторизация.md).

## Миграция single-tenant → multi-tenant

При переходе с одного тенанта на несколько:

1. Создать тенант для существующих данных: `POST /tenants {"tenant_id": "default"}`
2. Существующие документы уже в коллекции без tenant-prefix — **нужна переиндексация**:
   ```bash
   python -m src.cli.main index /data/docs/ --tenant-id default
   ```
3. Включить JWT auth: `AUTH__ENABLED=true` (см. 09.2)
4. Настроить маппинг пользователь → tenant в JWT-провайдере

> **Внимание:** lazy-init — collection создаётся при первой операции, не при create_tenant(). Если create_tenant() вернул OK, но get_or_create_store() ещё не вызывался, физической коллекции в ChromaDB нет.
