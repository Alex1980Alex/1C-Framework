# 13.5 Взаимодействие между слоями

> Хуки, скиллы и MCP-инструменты работают вместе через три канала коммуникации.
> Этот раздел показывает сквозные потоки данных на реальных примерах.

---

## Каналы коммуникации

```
Hook <──> Hook:     hook-todos.json (файл с file lock)
Hook  ──> Skill:    systemMessage ("используй skill X")
Skill ──> MCP:      tool call (search_documents, ask_question)
Hook  ──> MCP:      нет прямой связи (только через Skill)
```

### Hook ↔ Hook: hook-todos.json

Хуки общаются через файл `.claude/cache/hook-todos.json`. Один хук создаёт
задачу (`add_task`), другой проверяет её при Stop (`get_pending_tasks`).

```
knowledge-cache-reminder ──[add_task()]──→ hook-todos.json
factory-enforcer         ──[add_task()]──→     │
auto-git-save            ──[add_task()]──→     │
                                          [read on Stop]
                                               │
                                               ▼
                                        task-enforcer.py
                                          │         │
                                    pending?     no pending?
                                          │         │
                                    exit(2)      exit(0)
                                    BLOCK        ALLOW
```

Файл защищён file lock (`shared/hook_lock.py`) для безопасности
при параллельных вызовах. Atomic writes предотвращают corruption.

### Hook → Skill: systemMessage

Хук возвращает `systemMessage` с инструкцией для Claude. Claude читает
инструкцию и загружает указанный скилл через `Skill()` tool.

```
skill-router.py → stdout:
  {"continue": true, "systemMessage": "[SKILL-ROUTER] Загрузи skill tech-research"}
                                          │
                                          ▼
                                    Claude Code
                                          │ Skill('tech-research')
                                          ▼
                                    tech-research/SKILL.md загружен
```

Хук не загружает скилл напрямую — он только рекомендует. Решение о загрузке
принимает Claude.

### Skill → MCP: tool call

Скилл содержит инструкции, какие MCP-инструменты использовать. Claude
следует инструкциям и вызывает инструменты.

```
SKILL.md: "Фаза 1: поиск через search_documents(strategy=hybrid, k=10)"
                                          │
                                          ▼
                                    Claude Code
                                          │ MCP call
                                          ▼
                                    pdf-vector-graph.search_documents(
                                      query="...", strategy="hybrid", k=10
                                    )
```

## Пример 1: Research-поток (1С-вопрос)

```
USER: "что такое справочники в 1С?"
         │
         ▼
[КОГДА] skill-router.py (UserPromptSubmit)
         │ Layer A: keyword "1С" + "справочники"
         │ Layer B: fuzzy match "1c-doc-research"
         │ → systemMessage: "Загрузи skill 1c-doc-research"
         ▼
[КАК] Skill: 1c-doc-research
         │ Фаза 0: cache/_index.json → miss (темы нет)
         │ Фаза 1: MCP search_documents(query="справочники 1С") ──→ [ЧЕМ]
         │ Фаза 2: WebSearch(its.1c.ru, v8.1c.ru)
         │ Фаза 3: верификация терминологии
         │ Фаза 4: атрибуция [docs] [web]
         ▼
[КОГДА] knowledge-cache-reminder.py (PostToolUse:WebSearch)
         │ result содержит 1С-термины → score >= 2
         │ → add_task("Сохранить в кеш") → hook-todos.json
         │ → systemMessage: "Фаза 5: сохрани в кеш"
         ▼
[КАК] Skill: 1c-doc-research (Фаза 5)
         │ → Write cache/справочники.md
         │ → Update _index.json
         ▼
[КОГДА] task-enforcer.py (Stop)
         │ hook-todos.json: pending=0 (задача выполнена)
         │ → exit(0) ALLOW
         ▼
ОТВЕТ ПОЛЬЗОВАТЕЛЮ С АТРИБУЦИЕЙ
```

**Участники:** 3 хука + 1 скилл + 1 MCP tool + WebSearch.

## Пример 2: Фабрика (создание домена)

```
USER: "давай создадим новый домен для DevOps"
         │
         ▼
[КОГДА] decision-to-triad.py (UserPromptSubmit)
         │ keyword: "давай создадим" + "новый домен"
         │ → systemMessage: "Прогони через Фабрику (skill triad-factory)"
         ▼
[КАК] Skill: triad-factory
         │ ШАГ 1: КЛАССИФИКАЦИЯ
         │   Q1=Да (авто-роутинг) → Hook
         │   Q2=Да (5-фазный research) → Skill
         │   Q3=Да (WebSearch, MCP) → MCP
         │   Q4=Да (кеш знаний) → Cache
         │   Q5=Да (обязательно кешировать) → Enforcer
         │ ШАГ 2: ФОРМУЛА = Hook + Skill + MCP + Cache + Enforcer
         │ ШАГ 3: ГЕНЕРАЦИЯ
         │   → Write skills/devops-research/SKILL.md
         │   → Write skills/devops-research/cache/_index.json
         │   → Добавить TERMS в research-task-detector.py
         ▼
[КОГДА] factory-enforcer.py (PostToolUse:Write)
         │ Обнаружена запись в .claude/skills/ или .claude/hooks/
         │ → add_task("ШАГ 4: Зарегистрировать") → hook-todos.json
         │ → add_task("ШАГ 5: Верифицировать") → hook-todos.json
         ▼
[КАК] Claude выполняет ШАГ 4-5:
         │ ШАГ 4: Обновить skill-router-config.json, CLAUDE.md
         │ ШАГ 5: echo '{"prompt":"DevOps вопрос"}' | python detector.py
         ▼
[КОГДА] task-enforcer.py (Stop)
         │ hook-todos.json: pending=0
         │ → exit(0) ALLOW
         ▼
ДОМЕН ИНТЕГРИРОВАН
```

**Участники:** 3 хука + 1 скилл + Write/Edit tools.

## Пример 3: Auto-commit (stop enforcement)

```
Claude завершает работу
         │
         ▼
[КОГДА] git-commit-enforcer.py (Stop)
         │ git status --porcelain
         │ Фильтр: WATCHED_PATHS = [".claude/"]
         │ Статусы: M, A, D, R, C, U, T (не ??)
         │
         ├─ нет изменений → exit(0) ALLOW
         │
         └─ есть изменения → exit(2) BLOCK
            │ reason: "13 файлов в .claude/ не закоммичены"
            │ инструкция: git add + git commit
            ▼
[Claude] создаёт коммит
            ▼
[КОГДА] git-commit-enforcer.py (Stop, повтор)
            │ git status → чисто
            │ → exit(0) ALLOW
            ▼
СЕССИЯ ЗАВЕРШЕНА, ИЗМЕНЕНИЯ СОХРАНЕНЫ
```

**Участники:** 1 хук (повторный вызов при блокировке).

## Enforcement Loop

Общий паттерн принуждения через hook-todos.json:

```
[PostToolUse Hook]  ──add_task()──>  hook-todos.json
                                          │
                                     [Claude работает]
                                          │
                                     complete_task()
                                          │
[Stop Hook]         ──read──>        hook-todos.json
                                          │
                                    pending > 0?
                                    │          │
                                   YES        NO
                                    │          │
                                 exit(2)    exit(0)
                                 BLOCK      ALLOW
                                    │
                              Claude выполняет
                              задачу, повтор Stop
```

Этот паттерн используют:
- `knowledge-cache-reminder` → `task-enforcer` (сохранение в кеш)
- `factory-enforcer` → `task-enforcer` (ШАГ 4-5 Фабрики)
- `auto-git-save` → `task-enforcer` (коммит изменений)
- `docs-change-tracker` → `task-enforcer` (обновление документации)

## Почему три слоя, а не один MCP

| Возможность | Hook | Skill | MCP |
|-------------|:----:|:-----:|:---:|
| Event triggers (UserPromptSubmit) | + | — | — |
| Блокировка выхода (Stop) | + | — | — |
| Persistent cache | — | + | — |
| Tool execution | — | — | + |
| Domain knowledge | — | + | — |
| Workflow enforcement | + | — | — |

MCP — это **tools**. Hooks — это **events**. Skills — это **knowledge**.
Три разных механизма для трёх разных задач.

Если объединить в один MCP:
- Нельзя блокировать Stop (MCP — stateless tools, не events)
- Нельзя рекомендовать на каждый промпт (MCP не подписан на UserPromptSubmit)
- Нельзя хранить persistent cache (MCP — stateless)
- Timeout MCP произвольный, хуки — 3-5 сек (лёгкие, не тормозят UX)
