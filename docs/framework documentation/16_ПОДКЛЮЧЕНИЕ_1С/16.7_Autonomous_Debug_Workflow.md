## 16.7 Autonomous Debug Workflow — Claude как Debug UI через MCP

Раздел описывает **Scenario B**: полностью автономную отладку BSL-кода Claude'ом через MCP-сервер `1c-debug`, при сохранении открытого Конфигуратора как редактора кода. Применяется когда нужно автоматизировать regression-сценарии или дать Claude возможность ставить breakpoints, выполнять step-into / step-over, читать значения переменных без участия разработчика.

> **Связано:**
> - [16.6 EDT-MCP setup](16.6_EDT_MCP_setup.md) — базовая настройка debug agent.
> - [`1c-doc-research/cache/dbgs-rdbg-debug-server.md`](../../../.claude/skills/1c-doc-research/cache/dbgs-rdbg-debug-server.md) — protocol details, ограничения платформы.
> - [`scripts/start-onec-autonomous-debug.ps1`](../../../scripts/start-onec-autonomous-debug.ps1) — helper-скрипт (см. §16.7.5).

### 16.7.1 Hard constraint платформы

> **«It is impossible to simultaneously debug various debug items related to the same infobase»** — kb.1ci.com §32.2.2.

В терминах протокола RDBG: **только один Debug UI** на инфобазу может иметь full access (`registered`-статус). Все последующие клиенты получают `ibInDebug` (read-only observer).

Это **не баг и не настройка** — фундаментальное ограничение платформы 8.3.x. Нет способа сделать так, чтобы и Конфигуратор (с активным F5), и MCP одновременно владели Debug UI.

**Поэтому Scenario B = разделение ролей:**
- **Конфигуратор** = редактор кода (без активной debug-сессии)
- **MCP** = единственный Debug UI

### 16.7.2 Архитектура Scenario B

```
┌─────────────────────────────────────────────────────────────────┐
│  Конфигуратор (1cv8.exe, PID A)                                 │
│  ── редактор BSL                                                │
│  ── НЕ нажимать F5; если нажали — Shift+F5 (Stop Debugging)     │
└─────────────────────────────────────────────────────────────────┘
                                                                   
┌─────────────────────────────────────────────────────────────────┐
│  dbgs.exe (PID B) — HTTP RDBG debug server, listen :1550        │
│  ── persistent: hidden window или Windows service               │
└────────────┬────────────────────────────────┬───────────────────┘
             │ HTTP RDBG                      │ HTTP RDBG          
             ▼                                ▼                    
┌──────────────────────────┐    ┌────────────────────────────────┐ 
│  1cv8c.exe (PID C)       │    │  Claude Code (MCP client)      │ 
│  тонкий клиент,          │    │     ↓                          │ 
│  запущен с               │    │  mcp_debug_server.py (PID D)   │ 
│  /Debug /DebuggerURL     │    │  HTTP RDBG client wrapper      │ 
│  → debug TARGET          │    │  → primary Debug UI (registered)│ 
└──────────────────────────┘    └────────────────────────────────┘ 
```

Ключи:
- **`/Debug /DebuggerURL`** — клиент 1С:Предприятие при старте автоматически attach'ится к указанному debug server, регистрируясь как `ManagedClient` debug item. Не требует ручной настройки в `Сервис → Параметры → Отладка` на стороне клиента.
- **MCP-server** — единственный «полноправный» Debug UI; Claude через него управляет breakpoints / step / evaluation.
- **Конфигуратор** — наблюдатель файлов конфигурации; не attached к dbgs как Debug UI.

### 16.7.3 Setup пошагово (B1)

**Предусловия:**
- Платформа 8.3.10+ (HTTP RDBG protocol).
- 1С:Предприятие сервер запущен (если работаем со server-base).
- ИБ доступна: `localhost\<имя_базы>` пингуется.
- MCP-сервер `1c-debug` зарегистрирован в `.mcp.json` (см. §16.6).

**Шаги:**

1. **Закрыть лишние Debug UI.** Если Конфигуратор уже в debug-режиме (F5 нажат) — `Shift+F5`. Если EDT с активным debug — `Run → Terminate`. Иначе они забронируют Debug UI первыми.

2. **Запустить debug-окружение** одной командой:
   ```powershell
   .\scripts\start-onec-autonomous-debug.ps1 -InfobaseAlias "ИБTransportManagementDevelop"
   ```
   Скрипт:
   - Проверит наличие `dbgs.exe` (`C:\Program Files (x86)\1cv8\<version>\bin\dbgs.exe`)
   - Запустит `dbgs.exe -a localhost -p 1550` (если ещё не запущен) — в hidden window
   - Дождётся пока `:1550` начнёт слушать (max 5 секунд)
   - Запустит `1cv8c.exe ENTERPRISE /S "localhost\<база>" /Debug /DebuggerURL "http://localhost:1550"`

3. **В Claude Code** вызвать:
   ```
   mcp__1c-debug__debug_connect(infobase_alias="ИБTransportManagementDevelop")
   ```
   Ожидаемый ответ:
   ```json
   {
     "status": "connected",
     "attach": {
       "result": "registered",
       "fully_registered": true
     },
     "targets": [
       {
         "id": "<UUID>",
         "targetType": "ManagedClient",
         "userName": "<user>",
         "state": "Worked"
       }
     ]
   }
   ```

4. **Verify smoke-test:**
   ```
   mcp__1c-debug__debug_targets
   ```
   → `count: 1+`, target присутствует.

**С этого момента Claude может:**
- ставить breakpoints (`debug_set_breakpoint`)
- управлять выполнением (`debug_step` — Continue / StepInto / StepOver / StepOut)
- читать call stack (`debug_stack_trace`)
- читать локальные переменные (`debug_variables`)
- вычислять выражения (`debug_evaluate`)

### 16.7.4 Параметры запуска `1cv8c.exe` для отладки

| Ключ | Назначение |
|---|---|
| `ENTERPRISE` | режим 1С:Предприятие (тонкий клиент) |
| `/S "localhost\<база>"` | строка подключения к серверной базе |
| `/F "<путь>"` | альтернатива для файловой базы |
| `/Debug` | запуск в режиме отладки |
| `/DebuggerURL "http://host:port"` | URL debug server для авто-attach |
| `/N "<user>"` | имя пользователя (опц.) |
| `/P "<password>"` | пароль (опц.) |

⚠ **Базовые версии 1С:Предприятие НЕ поддерживают `/Debug` и `/DebuggerURL`.** Для них Scenario B не применим — используется только legacy-настройка через `Сервис → Параметры → Отладка` на стороне клиента.

### 16.7.5 Helper-скрипт `start-onec-autonomous-debug.ps1`

Файл: [`scripts/start-onec-autonomous-debug.ps1`](../../../scripts/start-onec-autonomous-debug.ps1)

**Параметры:**
| Параметр | По умолчанию | Назначение |
|---|---|---|
| `-InfobaseAlias` | `ИБTransportManagementDevelop` | имя ИБ в кластере |
| `-PlatformVersion` | `8.3.27.1936` | версия платформы 1С |
| `-DebugPort` | `1550` | порт debug server |
| `-UserName`, `-Password` | пусто | для авто-логина |
| `-NoLaunchClient` | `false` | не запускать `1cv8c.exe` (только `dbgs.exe`) |
| `-FileBase` | пусто | путь к файловой базе вместо `/S` |

**Примеры:**
```powershell
# Стандартный сценарий (server-base)
.\scripts\start-onec-autonomous-debug.ps1 -InfobaseAlias "ИБTransportManagementDevelop"

# С авто-логином
.\scripts\start-onec-autonomous-debug.ps1 `
    -InfobaseAlias "TestDB" `
    -UserName "Admin" `
    -Password "..."

# Только debug server (клиент пользователь запустит сам через ярлык)
.\scripts\start-onec-autonomous-debug.ps1 -NoLaunchClient

# Файловая база
.\scripts\start-onec-autonomous-debug.ps1 `
    -FileBase "D:\bases\TestFile" `
    -InfobaseAlias "TestFile"
```

### 16.7.6 Что делать если `result: ibInDebug`

**Симптом:** `debug_connect` вернул `fully_registered: false`, поле `existing_debug_ui` содержит UUID конкурирующего Debug UI.

**Диагностика:**
1. **Конфигуратор?** В Конфигураторе посмотреть статус-бар: если внизу строка «Отладка» / индикатор debug-сессии — нажать `Shift+F5`.
2. **EDT?** Если открыт — `Run → Terminate` для всех debug-сессий.
3. **Висящий клиент 1cv8c?** Если предыдущая сессия 1С:Предприятие зависла — закрыть процесс (`taskkill /F /IM 1cv8c.exe`).
4. **Висящий MCP-server?** Если `mcp_debug_server.py` процесс не отпустил Debug UI — restart Claude Code (или `mcp__1c-debug__debug_disconnect` сначала).

После закрытия конкурирующего UI повторить `mcp__1c-debug__debug_connect`.

**Verify ESTABLISHED-соединения:**
```powershell
netstat -ano | findstr :1550
```
Покажет какие процессы висят на debug server (PID можно сопоставить с `Get-Process -Id <PID>`).

### 16.7.7 Persistence — оставить debug server между сессиями

**Hidden process (рекомендую для dev):** скрипт уже стартует `dbgs.exe` через `Start-Process -WindowStyle Hidden` — окно не блокирует терминал. Минус — после reboot нужно запускать заново.

**Windows Service:** можно зарегистрировать `dbgs.exe --service` для persistent через reboot. Минус: **не поддерживает debug серверного кода** (rphost). Для client-only debug — OK.

**Команда регистрации службы (admin PowerShell):**
```powershell
$dbgs = "C:\Program Files (x86)\1cv8\8.3.27.1936\bin\dbgs.exe"
$args = "--service --addr=localhost --port=1550"
sc.exe create "1C-Debug-Server" binPath= "`"$dbgs`" $args" start= auto DisplayName= "1C:Enterprise Debug Server (autonomous)"
sc.exe start "1C-Debug-Server"
```

**Удаление:**
```powershell
sc.exe stop "1C-Debug-Server"
sc.exe delete "1C-Debug-Server"
```

### 16.7.8 Best practices

- ✅ **Один Debug UI = один владелец.** Перед `debug_connect` убедиться что Конфигуратор / EDT не держат debug-сессию.
- ✅ **Использовать `--addr=localhost`.** Не открывать debug server на внешний интерфейс — RDBG protocol без TLS, password-protected только опционально.
- ✅ **`/Debug` сразу при запуске клиента.** Это удобнее, чем настраивать клиент через `Сервис → Параметры → Отладка` после запуска.
- ✅ **Hidden window для dev**, **service для shared dev-stand'а**.
- ❌ **Не запускать dbgs.exe от имени `SYSTEM`** в dev — будут проблемы с правами на чтение конфигурации клиентом 1С:Предприятие.
- ❌ **Не делиться `dbgs.exe` между несколькими разработчиками** на одной машине — RDBG не имеет multi-tenancy, всё валится в один список targets.

### 16.7.9 Известные ограничения Scenario B

| Ограничение | Workaround |
|---|---|
| Серверный код (rphost) не отлаживается через `dbgs.exe --service` | Использовать hidden window или legacy `ragent.exe -debug` |
| Базовые версии 1С не поддерживают `/Debug` и `/DebuggerURL` | Workflow неприменим, использовать только Конфигуратор-как-Debug-UI |
| Если уже открыт EDT с активным debug — отнимает Debug UI | `Run → Terminate` в EDT перед `debug_connect` |
| ~~MCP `mcp_debug_server.py` не auto-attach'ит новые targets~~ — **закрыто 2026-05-09 (roadmap §13 P1.1)**: `_ping_loop` диспатчит `targetStarted` события и вызывает `attach_debug_targets` для каждого нового rphost / 1cv8c. Если `targetStarted` потерян (race window 0-2s) — `_ensure_target_attached` страхует на стороне eval/step tools. | — |
| Конфигуратор после ручного нажатия F5 race-condition'ит за Debug UI | Согласовать с разработчиком: либо MCP, либо Конфигуратор; не оба |
| Версии `<8.3.10` не имеют `dbgs.exe` (только TCP debug) | Обновить платформу или использовать legacy mode |

#### Post-BP-fire handshake (roadmap 260508, ✅ 2026-05-09)

`mcp_debug_server.py` v1.1 **автоматически отслеживает остановки** через event-loop в `_ping_loop` (yukon39 dispatch pattern). После срабатывания BP можно вызывать `debug_variables` / `debug_evaluate` / `debug_step` **без явного `target_id`** — wrapper подхватывает последний остановленный target из cache:

| До (v1.0) | После (v1.1) |
|---|---|
| `debug_variables(target_id="<UUID>")` обязательно | `debug_variables()` — auto-resolve через `last_stopped_target_id` |
| BP не fire'ит для rphost (новый target после `targetStarted` не attached) | `_ping_loop` ловит `targetStarted` → auto-attach |
| Stack pull через `getCallStack` после каждого BP (медленно) | Cache из `callStackFormed` push event → `debug_stack_trace()` instant |
| Race window 0-2s → RDBG 400 «target не зарегистрирован» | `_ensure_target_attached` idempotent guard в eval/step tools |

**Smoke-проверка инфраструктуры** (без сценария):
```bash
python scripts/smoke_test_debug_pipeline.py --probe-only --json
```
Ожидаемый exit_code:
- `0` — pipeline healthy (1С запущен + handshake OK)
- `1` — degraded (1С запущен, но что-то с handshake)
- `2` — 1С не запущена / dbgs.exe не listen :1550

**Полный цикл BP-fire** (требует ручного запуска сценария в 1С):
```bash
python scripts/smoke_test_debug_pipeline.py --full \
    --object-id <UUID документа из edt-mcp get_metadata_details> \
    --module-type ObjectModule --line 42 --wait-bp 30
```
