# 20.1 Обзор AutoResearch v2

AutoResearch v2 — система автономных итеративных улучшений кода с измеримыми метриками и многоканальной верификацией. Ключевое отличие от предыдущей версии заключается в переходе от монолитного агента к трёхагентной архитектуре, обеспечивающей разделение ответственности и независимую проверку результатов.

## Что нового в v2

Вторая версия системы представляет собой фундаментальную переработку архитектуры и рабочих процессов.

**Трёхагентный движок.** Вместо одного агента, который одновременно пишет и проверяет код, теперь используются три независимых процесса:
- **Executor** — выполняет изменение и коммитит его
- **Reviewer** — проверяет метрику и выносит вердикт
- **Comparator** — проводит слепое A/B сравнение каждые N итераций

Каждый агент запускается как отдельный вызов `claude -p` в headless mode, что обеспечивает изоляцию и воспроизводимость.

**Интерактивные команды.** Система поддерживает несколько режимов запуска:
- `/autoresearch` — стандартный запуск с текущими параметрами
- `/autoresearch:plan` — мастер создания рецепта с 5 воротами проверки (wizard 5 gates)
- `/autoresearch:security` — специализированный режим аудита безопасности по методологии STRIDE

**Eval система.** Добавлен скрипт `eval-autoresearch.py`, рассчитывающий F1-score и domain accuracy для объективной оценки качества изменений.

**Dashboard.** Мониторинг процесса через `autoresearch-dashboard.py` с двумя форматами вывода: ASCII CLI для терминала и JSON для интеграции с внешними системами.

**Custom idea directories.** Команда `/autoresearch:plan` позволяет указывать пользовательские директории с идеями для улучшений.

## Архитектура v2

Система построена вокруг принципа разделения ответственности между тремя независимыми агентами.

```
Пользователь → /autoresearch или autoresearch.ps1
                    │
    ┌───────────────┼───────────────┐
    ▼               ▼               ▼
 Executor       Reviewer        Comparator
 (claude -p)    (claude -p)     (claude -p)
 Пишет код      Проверяет       Слепое A/B
 Коммитит       Метрика→Verdict каждые 5 iter
    │               │               │
    └───────────────┼───────────────┘
                    ▼
         autoresearch.jsonl
         autoresearch.md
         autoresearch-results.tsv
```

Executor работает в режиме write — он имеет право изменять файлы и создавать коммиты. Reviewer работает в режиме read-only — он только анализирует результаты и выносит вердикт. Comparator активируется периодически для независимой оценки прогресса без знания о том, какое именно изменение было сделано.

Все результаты агрегируются в три файла: `autoresearch.jsonl` для машинной обработки, `autoresearch.md` как живой документ для чтения человеком, и `autoresearch-results.tsv` для табличного анализа.

## 7 принципов

Система следует строгим правилам, обеспечивающим воспроизводимость и измеримость улучшений.

1. **ONE change per iteration (атомарность).** Каждое изменение должно быть объяснимо в одном предложении. Это позволяет точно определить причину улучшения или регрессии.

2. **Measure BEFORE and AFTER.** Допускаются только числовые метрики. Формулировки "стало лучше" или "код чище" не являются метриками.

3. **REVERT on regression.** При ухудшении метрики изменение откатывается без исключений. Единственное исключение — вердикт FIX, когда Reviewer указывает на исправимую проблему.

4. **Never retry Dead Ends.** Тупиковые направления отслеживаются в `autoresearch.md` и не повторяются в последующих итерациях.

5. **Separation of concerns.** Executor не занимается тестированием собственного кода. Reviewer не пишет код. Это исключает конфликт интересов.

6. **Session persistence.** Файл `autoresearch.md` является живым документом, сохраняющим состояние между сессиями. При перезапуске система продолжает с прерванного места.

7. **Idea-to-Recipe.** Каждая идея преобразуется в уникальный рецепт, содержащий метрику, инструменты и область применения (scope).

## 10-фазный цикл

Каждая итерация проходит через 10 фаз, обеспечивающих систематический подход к улучшениям.

| Фаза | Действие | Кто |
|------|----------|-----|
| 1 | ANALYZE — глубокий анализ кодовой базы (только на 1-й итерации) | Opus |
| 2 | REVIEW — чтение контекста и истории предыдущих итераций | Executor |
| 3 | IDEATE — выбор гипотезы для проверки из пула идей | Executor |
| 4 | MODIFY — внесение одного атомарного изменения | Executor |
| 5 | COMMIT — создание git commit до верификации | Executor |
| 6 | VERIFY — измерение метрики и запуск тестов | Reviewer |
| 7 | DECIDE — вынесение вердикта: KEEP/REVERT/FIX/SKIP | Reviewer |
| 8 | COMPARE — слепое A/B сравнение (каждые 5 итераций) | Comparator |
| 9 | LOG — запись результатов в JSONL, TSV и markdown | Скрипт |
| 10 | REPEAT — переход к следующей итерации или остановка | Скрипт |

Фаза ANALYZE выполняется только один раз в начале сессии и использует модель Opus для глубокого понимания контекста. Последующие фазы могут использовать более быстрые модели.

## Стоп-условия

Система автоматически останавливается при выполнении одного из следующих условий:

- **Достигнут целевой порог.** Параметр `-Target` определяет целевое значение метрики. При его достижении процесс завершается успешно.
- **Плато.** Пять итераций подряд без улучшений метрики указывают на исчерпание доступных оптимизаций.
- **Превышен лимит итераций.** Параметр `-MaxIterations` ограничивает максимальное количество попыток.
- **Маркер AUTORESEARCH_DONE.** Агент может явно сигнализировать о завершении работы.
- **Критическая ошибка.** Если тесты сломаны и не восстанавливаются, процесс останавливается для ручного вмешательства.

## 8 доменов

Система поддерживает восемь доменов улучшений, каждый со своей метрикой и методом верификации.

| Домен | Метрика | Direction | Verify |
|-------|---------|-----------|--------|
| skills | F1 score | higher | eval-skill-router.py |
| skill-health | F1 + health | higher | eval-skill-router.py |
| python-quality | ruff errors | lower | ruff check src/ |
| hooks | accuracy | higher | eval-hooks.py |
| security | findings | lower (READ-ONLY) | bandit -r src/ |
| tests | coverage % | higher | pytest --cov |
| docs | documented % | higher | AST-based |
| bsl | errors | lower | bsl_analyze |

Домен security работает в режиме READ-ONLY — система может только выявлять проблемы, но не исправляет их автоматически во избежание внесения уязвимостей.

## Сравнение v1 vs v2

| Характеристика | v1 (глава 18) | v2 (эта глава) |
|---|---|---|
| Агенты | 1 — всё делает сам | 3 — Executor/Reviewer/Comparator |
| Объективность | Сам оценивает свой код | Reviewer независимо проверяет |
| A/B сравнение | Нет | Каждые N итераций |
| Custom рецепты | Нет | /autoresearch:plan wizard |
| Security audit | Нет | /autoresearch:security STRIDE |
| Eval | Нет | F1 + domain accuracy |
| Dashboard | Нет | CLI + JSON |

Переход на трёхагентную архитектуру устраняет фундаментальную проблему v1 — конфликт интересов, когда один агент одновременно создаёт и оценивает свою работу.
