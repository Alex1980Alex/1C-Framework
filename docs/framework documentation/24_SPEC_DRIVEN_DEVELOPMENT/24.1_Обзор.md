# 24.1 Spec Driven Development (SDD) — Обзор

> **Версия:** 1.0 | **Дата:** 2026-04-02 | **Статус:** ACTIVE

---

## Что такое Spec Driven Development

Spec Driven Development (SDD) — методология разработки, в которой **спецификация является единственным источником истины**, а код — расходным материалом. Разработчик пишет не код, а документ-спецификацию, настолько точный, что нейросеть генерирует весь код от первой до последней строки.

### Три уровня зрелости работы с AI

| Уровень | Подход | Ограничения |
|---------|--------|-------------|
| **Промтинг** | Формулирование запросов к AI | Полезно, но ограничено контекстным окном |
| **Memory Bank** | Файлы с описанием проекта в начале сессии | Даёт контекст, но теряется на 20+ итерациях |
| **SDD** | Разработка через спецификации | Наиболее мощный подход, контролирует контекст |

### Почему вайб-кодинг не работает в 1С

1. **Контекстное окно** — на проекте из 20-30 итераций нейросеть теряет нить рассуждений
2. **Код как конечный продукт** — архитектурная ошибка в 5000+ строках — задача на день поиска
3. **Практический пример** — нейросеть создала собственную систему резервирования с нуля вместо доработки существующей

> По данным GitClear (2020-2024), дублирование AI-генерированного кода выросло в ~4 раза, а доля рефакторинга упала с 25% до менее 10%.

## Пять принципов SDD для 1С

1. **Spec first** — сначала спецификация, потом код. Артефакты: proposal → specs → design → tasks
2. **Конкретность** — тип данных каждого реквизита, поведение при пустых полях, граничные условия
3. **Контекст** — нейросеть видит структуру конфигурации через MCP-серверы
4. **Правь спецификацию, а не код** — спецификация — единственный источник правды
5. **Инкрементальность** — одна задача, одна спецификация, один результат

---

## Три уровня SDD (Martin Fowler / Thoughtworks)

| Уровень | Описание | Применение |
|---------|----------|------------|
| **Spec-first** | Спецификация пишется первой, код — основной артефакт | Базовый уровень |
| **Spec-anchored** | Спецификация живёт рядом с кодом как якорь | Средний уровень |
| **Spec-as-source** | Спецификация — единственный источник, код одноразовый | Целевой уровень (Tessl) |

## Когда использовать SDD, а когда — нет

### Использовать SDD

- Доработка типовых конфигураций с 100+ объектами метаданных
- Командная разработка (единый процесс для всех)
- Задачи с несколькими модулями / регистрами / документами
- Критически важные бизнес-процессы (резервирование, расчёты)

### Достаточно прямого промпта

- Одиночная обработка / отчёт
- Рефакторинг одного модуля
- Исправление конкретной ошибки
- Прототипирование

### Правило маршрутизации

```
/analyze-1c-task-v2 → ANALYSIS-REPORT.md (с [ADDED]/[MODIFIED])
      ↓ тривиальная                    ↓ средняя/сложная
  implement-1c-task              /opsx:propose → /opsx:approve → /opsx:apply
                                                                      ↓
                                                          brownfield-validate
                                                                      ↓
                                                              /opsx:archive
```

| Сложность | Критерий | Маршрут |
|-----------|----------|---------|
| **Тривиальная** (LOW) | 1-2 точки модификации, 1 файл | `implement-1c-task` |
| **Средняя** (MEDIUM) | 3-5 точек, 2-3 файла | `/opsx:propose` → `...` → `/opsx:archive` |
| **Сложная** (HIGH) | 6+ точек, 4+ файла, SQL цепочки | `/opsx:propose` → `...` → `/opsx:archive` |
