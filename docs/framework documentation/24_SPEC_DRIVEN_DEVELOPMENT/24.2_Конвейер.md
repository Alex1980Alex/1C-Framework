# 24.2 Конвейер артефактов OpenSpec

> **Версия:** 1.0 | **Дата:** 2026-04-02 | **Статус:** ACTIVE

## Четыре артефакта изменения

OpenSpec использует 4-ступенчатый процесс (artifact-guided workflow). Каждая ступень — это файл Markdown с обязательной структурой. Переход между фазами возможен только при заполнении обязательных слотов.

### Ступень 1 — Proposal (Предложение)

**Назначение:** Описание задачи по-человечески: зачем, какую проблему решаем, что хотим получить.

**Формат:** `openspec/changes/{change-name}/proposal.md`

```markdown
## Problem
[Описание текущей проблемы]

## Solution
[Что предлагается сделать]

## Impact
[На какие объекты/процессы повлияет]
```

**Пример для 1С:**
> Добавить табличную часть "Прошлые места работы" в справочник "Сотрудники". Реквизиты: Организация, ДатаНачала, ДатаОкончания, Должность. Вывести на форму. Проверить что ДатаОкончания > ДатаНачала.

### Ступень 2 — Specs (Спецификации)

**Назначение:** Инженерная конкретика: типы данных, ограничения, поведение при граничных условиях.

**Формат:** `openspec/changes/{change-name}/specs/`

```markdown
## Metadata
| Реквизит | Тип | Обязательный | Описание |
|-----------|-----|--------------|----------|

## Constraints
- MUST: ДатаОкончания строго > ДатаНачала
- SHALL: Организация — СправочникСсылка.Организации

## Scenarios (Given/When/Then)
### Сценарий 1: Корректные данные
- Given: Заполнены все реквизиты
- When: Пользователь записывает элемент
- Then: Данные сохраняются без ошибок

### Сценарий 2: Некорректные даты
- Given: ДатаОкончания <= ДатаНачала
- When: Пользователь пытается записать
- Then: Выводится сообщение об ошибке
```

**Ключевые слова RFC 2119:** MUST (обязательно), SHALL (следует), SHOULD (рекомендуется), MAY (допускается).

### Ступень 3 — Design (Архитектура)

**Назначение:** Какие конкретно файлы будут затронуты. Здесь ловятся ошибки, которые при вайб-кодинге обнаружились бы через неделю.

**Формат:** `openspec/changes/{change-name}/design.md`

```markdown
## Files Changed
| Файл | Изменение | Маркер |
|------|-----------|--------|
| Сотрудники.xml | Добавлена табличная часть | [ADDED] |
| Module.bsl | Добавлена валидация дат | [ADDED] |
| Form.xml | Добавлены элементы формы | [ADDED] |

## Architecture
[Схема взаимодействия объектов]

## Risks
[Потенциальные проблемы и их минимизация]
```

### Ступень 4 — Tasks (Задачи)

**Назначение:** Чек-лист атомарных шагов для AI.

**Формат:** `openspec/changes/{change-name}/tasks.md`

```markdown
## Tasks
- [ ] Изменить Сотрудники.xml — добавить узел табличной части
- [ ] Добавить 4 реквизита в табличную часть
- [ ] Изменить Form.xml — добавить элементы на форму
- [ ] Написать обработчик валидации в Module.bsl
- [ ] Проверить XML-структуру
```

## Delta-Specs: маркеры ADDED/MODIFIED

Для доработки существующих конфигураций (brownfield) OpenSpec использует дельта-подход:

| Маркер | Значение | Пример |
|--------|----------|--------|
| `[ADDED]` | Новый код/объект | Новая функция, реквизит, элемент формы |
| `[MODIFIED]` | Изменение существующего | Правка SQL-запроса, изменение условия |

При архивации (фаза archive) дельта-спецификации мержатся в общую базу знаний проекта (`openspec/specs/`), поддерживая её актуальность без полного переписывания.

## Интеграция с analyze-1c-task-v2

Конвейер OpenSpec интегрирован с существующим skill `analyze-1c-task-v2`:

```
/analyze-1c-task-v2 → ANALYSIS-REPORT.md (с [ADDED]/[MODIFIED])
      ↓ тривиальная                    ↓ средняя/сложная
  implement-1c-task              /opsx:propose → /opsx:approve → /opsx:apply
                                                                      ↓
                                                          brownfield-validate
                                                                      ↓
                                                              /opsx:archive
```

**Связь артефактов:**
- `ANALYSIS-REPORT.md` (5-фазный анализ) → источник данных для `/opsx:propose`
- `proposal.md` ← секция "1. Описание задачи" из отчёта
- `specs/` ← секция "2. Объекты конфигурации" + "3. Детальный анализ"
- `design.md` ← секция "4. План изменений" с маркерами [ADDED]/[MODIFIED]
- `tasks.md` ← секция "5. Чек-лист верификации" как атомарные задачи
