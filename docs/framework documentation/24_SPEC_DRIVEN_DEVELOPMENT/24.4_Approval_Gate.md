# 24.4 Approval Gate — контроль человека над решениями AI

> **Версия:** 1.1 | **Дата:** 2026-04-14 | **Статус:** ACTIVE

---

## Проблема

Без Approval Gate AI переходит к написанию кода сразу после генерации плана. Для 1С это критично: ошибка в SQL-запросе или неверный объект метаданных может привести к день поиска и день исправления.

## Решение: Approval Gate

Approval Gate — обязательный шаг утверждения спецификации перед тем, как AI получит доступ к командам изменения конфигурации.

### Жизненный цикл изменения

```
draft → pending → approved → implementing → completed → archived
  │                   │
  │                   └── Только после approved можно:
  │                       - Запустить /opsx:apply
  │                       - Запустить implement-1c-task
  │                       - Изменять файлы конфигурации
  │
  └── pending: артефакты созданы, ждут ревью
```

---

## Реализация

### PreToolUse Hook (`approval-gate.py`) — 146 LoC

Блокирует выполнение skills `implement-1c-task`, `opsx:apply`, `openspec-apply-change`, `opsx-apply` без статуса `approved` в `.openspec.yaml`:

```python
# .claude/hooks/approval-gate.py
# Событие: PreToolUse:Skill
# Блокируемые skills: {implement-1c-task, opsx:apply, opsx-apply, openspec-apply-change}

def _read_approval_status(yaml_path) -> str | None:
    """Парсит approval.status из .openspec.yaml без pyyaml."""
    ...

def _read_profile(yaml_path) -> str:
    """NEW v1.1: Читает top-level profile field. Default '1c-bsl' для backward-compat."""
    ...

class ApprovalGate(BaseHook):
    def execute(self, inp):
        if inp.tool_name != "Skill": return None
        skill_name = inp.tool_input.get("skill", "")
        if skill_name not in _IMPLEMENTATION_SKILLS: return None

        unapproved = []
        for name, yaml_path in _get_active_changes():
            status = _read_approval_status(yaml_path)
            profile = _read_profile(yaml_path)  # NEW v1.1
            if status != "approved":
                unapproved.append((name, status or "pending", profile))

        if not unapproved: return None
        return HookOutput().block(f"APPROVAL GATE: ... [profile: {profile}] ...")
```

### Profile support (v1.1, добавлено 2026-04-14)

С v1.1 hook поддерживает **профили** — разные наборы правил для разных tech stacks:

| Profile | Применение | Файл конфигурации |
|---------|------------|-------------------|
| `1c-bsl` (default) | BSL changes (существующий) | `openspec/profiles/1c-bsl.yaml` (подразумевается) |
| `python-framework` | Python/LangChain/RAG changes | `openspec/profiles/python-framework.yaml` |

**Чтобы добавить новый profile:**
1. Создать `openspec/profiles/<name>.yaml` с rules для proposal/specs/design/tests
2. В `.openspec.yaml` нового change указать `profile: <name>`
3. Hook автоматически подхватит через `_read_profile()` — **код hook не меняется**

**Backward-compat:** existing BSL changes без поля `profile` получают default `1c-bsl` автоматически — не нужно ничего мигрировать.

### Block message (v1.1)

Сообщение о блокировке теперь включает profile:

```
APPROVAL GATE: Design must be approved before implementation.

Unapproved changes:
  - hermes-llm-wiki [profile: python-framework] (status: proposed)

To approve: /opsx:approve hermes-llm-wiki
To reject:  /opsx:approve hermes-llm-wiki --reject --comment "reason"

Review design.md and specs/ before approving.
Profile rules: openspec/profiles/<profile>.yaml
```

### `/opsx:approve` Skill

Ревью артефактов + approve/reject + обновление `.openspec.yaml`:

```
/opsx:approve → Claude показывает:
  1. proposal.md — суть задачи
  2. specs/ — метаданные и ограничения
  3. design.md — затрагиваемые файлы
  4. tasks.md — атомарные шаги

Пользователь подтверждает → статус → approved
Пользователь отклоняет → статус → rejected + комментарий
```

### `.openspec.yaml` — секция approval

```yaml
approval:
  status: approved        # draft | pending | approved | rejected
  reviewed_by: developer
  reviewed_at: 2026-04-02T14:30:00
  comment: "Архитектура корректна, можно реализовывать"
```

### ADR-041 R1: единый источник approval (2026-06-25)

Чтение OpenSpec-approval вынесено в общий модуль [`shared/approval_state.py`](../../../.claude/hooks/shared/approval_state.py)
— один ридер используют и `approval-gate.py` (DRY), и `gate_1c_implement` (G4 1С-пайплайна, гл.43). До R1 два гейта
читали РАЗНЫЕ сторы и расходились: `/opsx:approve` пишет `.openspec.yaml`, а G4 проверял только
`.pipeline-state.json` этап-2 → **ложный блок** `implement-1c-task` в SDD-потоке, хотя дизайн одобрен.

**Фикс (OR-семантика «дизайн одобрен?»):** G4 теперь honors OpenSpec-approval — implement проходит, если
дизайн одобрен в pipeline-state **ИЛИ** связанный OpenSpec change == `approved`
(`is_design_approved_via_openspec`, JIRA-gated → non-JIRA путь не затронут). Решения обоих гейтов пишутся в
единый decision-log через `gate_policy`. Behavior-preserving (code-verify PASS, 97 unit); детали —
[ADR-041](../../../.claude/skills/architecture-research/adr/041-sdd-pipeline-unification.md).

**R2 (мост state↔yaml, 2026-06-25):** `sync_approval` проецирует OpenSpec-approval → pipeline-state (этап 2 `approved`, `by="openspec-bridge"`) — сторы СХОДЯТСЯ, а не только OR-читаются. Односторонне (pipeline→OpenSpec не пишем: обошло бы human-review), идемпотентно, fail-open (SystemExit от `approve` перехвачен).

## Тестовые сценарии

| Сценарий | Ожидаемое поведение |
|----------|-------------------|
| status=pending + `implement-1c-task` | BLOCKED |
| status=approved + `implement-1c-task` | ALLOW |
| pipeline-state этап-2 НЕ approved, но OpenSpec change `approved` (R1) | ALLOW (G4 honors OpenSpec) |
| status=draft + `opsx:apply` | BLOCKED |
| status=approved + `opsx:apply` | ALLOW |
| Любой статус + `/opsx:explore` | ALLOW (не изменяет код) |
| Любой статус + `/opsx:propose` | ALLOW (создаёт артефакты) |

## Интеграция с openspec-mcp

При подключённом MCP-сервере `openspec-mcp`:
- Веб-дашборд показывает статус approval
- WebSocket уведомляет об изменении статуса
- Kanban-доска визуализирует pipeline
