См. также: [24.7 Hooks и CI](24.7_Автоматизация_hooks_и_CI.md), [24.8 CLI и инструменты](24.8_CLI_и_инструменты.md).

## Пример 1: end-to-end change GKSTCPLK-2507

Реальный change, прошедший весь workflow в sprint 2026-05-20: автоматическая установка вида допуска в РМ Приёмка/отгрузка по номенклатуре.

### Шаг 1: Анализ → ANALYSIS-REPORT

Команда:
```
/analyze-1c-task <путь-к-ТЗ>
```

Skill `analyze-1c-task-v2` выполняет 5 фаз (Требования → Объекты → Алгоритм → План → Верификация). На выходе — `ANALYSIS-REPORT.md` в папке задачи с:
- 5 точками модификации
- маркерами `[ADDED]`/`[MODIFIED]`
- секцией «11. Следующие шаги (SDD)» — рекомендация маршрута

В секции 11 указано: «Сложность средняя (1 ADDED метаданных + 3 MODIFIED) → рекомендуется SDD-маршрут».

### Шаг 2: Создание change

```
/opsx:propose gkstcplk-2507-auto-disallow-by-nomenclature
```

Skill `openspec-propose` вызывает `openspec_create_change(template=feature)`. Создаётся структура:

```
openspec/changes/gkstcplk-2507-auto-disallow-by-nomenclature/
├── proposal.md          (Summary + Motivation + Proposed Solution + Impact + Open Questions)
├── design.md            (Problem + Solution + Architecture + Open Architectural Questions)
├── tasks.md             (10 секций × 60 задач)
├── specs/
│   └── disallow-by-nomenclature-overlay/
│       └── spec.md      (## ADDED Requirements + 10 × ### Requirement + 25 × #### Scenario)
└── .openspec.yaml       (approval.status: pending)
```

### Шаг 3: Валидация после создания

```bash
openspec validate gkstcplk-2507-auto-disallow-by-nomenclature --json
# → {"valid": true, "issues": []}
```

CLI запускается, читает spec.md, парсит `## ADDED Requirements` headers и `### Requirement:` / `#### Scenario:` блоки. Если формат правильный → `valid: true`.

### Шаг 4: Approval (interactive)

```
/opsx:approve gkstcplk-2507-auto-disallow-by-nomenclature
```

Skill `opsx-approve`:
1. `openspec_critique_proposal` → score (9.8/10 в нашем случае)
2. Показывает Open Questions из proposal.md (historicity, синоним регистра)
3. User отвечает на вопросы → пишутся reviews
4. `openspec_approve_change` → `.openspec.yaml: approval.status = approved, reviewed_by = human, reviewed_at = <ISO>`

### Шаг 5: Apply

```
/opsx:apply gkstcplk-2507-auto-disallow-by-nomenclature
```

`approval-gate.py` (PreToolUse:Skill) проверяет статус — `approved` → пропускает. Skill `openspec-apply-change` → Skill `implement-1c-task v2.7` → 8-этапный pipeline:
1. Preflight (smoke-test MCP)
2. Analysis (read ANALYSIS-REPORT)
3. SQL validation (validate_query)
4. BSL edits (write_module_source)
5. Static analysis (bsl_analyze)
6. Cross-deps (find_references + BP-verification через 1c-debug-hmr)
7. Live testing (update_database + execute_query)
8. Documentation (IMPLEMENTATION-PROGRESS.md)

### Шаг 6: Post-apply hooks

После завершения сессии:
- `opsx-apply-postvalidate.py` → systemMessage «запусти `brownfield-validate`»
- `openspec-task-progress.py` → systemMessage с candidate-completed tasks по git diff

Claude следует подсказкам:
- `Skill('brownfield-validate')` → Gap + Design + Impl validation
- `mcp__openspec-mcp__openspec_batch_update_tasks` → пометить выполненные задачи

### Шаг 7: Archive

```
/opsx:archive gkstcplk-2507-auto-disallow-by-nomenclature
```

Skill `openspec-archive-change`: проверка completion → `mv` в `archive/YYYY-MM-DD-<name>` → `memory-orchestrator route_and_save`.

## Пример 2: Формат spec.md (валидный)

Минимальный валидный spec.md:

```markdown
# Spec: <capability-name>

**Change:** <change-id>

## ADDED Requirements

### Requirement: <название>

<RFC 2119 описание: MUST/SHOULD/MAY>

#### Scenario: <название сценария>

- **WHEN** <условие>
- **THEN** <результат>
```

Каждый `### Requirement:` **обязан** иметь хотя бы один `#### Scenario:` блок — иначе `openspec validate` падает с `No deltas found`.

## Пример 3: Типичные ошибки и фиксы

### Ошибка: `No delta sections found`

**Что видит CLI:**

```
[ERROR] mcp-http-service/spec.md
No delta sections found. Add headers such as "## ADDED Requirements" or move
non-delta notes outside specs/.
```

**Причина:** spec.md использует legacy формат `## ADDED` + `## Requirements` + `### REQ-N` вместо валидного `## ADDED Requirements` + `### Requirement:` + `#### Scenario:`.

**Фикс:** переписать заголовки + добавить Scenario для каждого Requirement.

### Ошибка: `Change must have at least one delta`

**Причина:** ни один spec в `specs/<cap>/spec.md` не парсится — нет валидных delta headers, либо нет `#### Scenario:` блоков.

**Фикс:** в каждом spec'е минимум один `## ADDED Requirements` (или `## MODIFIED Requirements`) + минимум один `### Requirement:` + минимум один `#### Scenario:` внутри Requirement.

### Ошибка: hook `openspec-change-coverage` warning без JIRA-токена

**Поведение:** info systemMessage при правке кода без JIRA в пути.

**Не баг, фича.** Hook молчит когда JIRA-токена нет (связь определить нельзя). Warning только когда есть `GKSTCPLK-NNNN` в пути и нет active change для этой JIRA.

### Ошибка: `validate_change` всегда `Invalid`

**Причина:** CLI `openspec` не установлен. MCP-tool под капотом вызывает CLI через shell — `execAsync` падает → `Invalid 0 errors`.

**Фикс:** `npm install -g openspec-extensions@1.3.4`.
