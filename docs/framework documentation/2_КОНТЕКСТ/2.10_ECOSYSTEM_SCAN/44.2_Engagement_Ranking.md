## Назначение

Переиспользуемый **stdlib-only** модуль чистых функций — ядро, заимствованное у `last30days-skill`
(ADR-039). Не event-хук (не регистрируется в settings.json) — библиотека, импортируемая потребителями
V1/V2. Три примитива.

## 1. `expand_queries(query, extra_terms=(), max_variants=4)`

Детерминированное **multi-query expansion** (без LLM/сети) для расширения recall.
Варианты: оригинал → lower → значимые токены (без RU/EN стоп-слов) → `query + extra_term`.
Дедуп с сохранением порядка, ограничено `max_variants`. Пустой запрос → `[]`.

```python
expand_queries("LangGraph multi-agent orchestration")
# → ["LangGraph multi-agent orchestration", "langgraph multi-agent orchestration",
#    "langgraph multi-agent orchestration"]  (дедуп схлопывает совпадения)
```

## 2. `blended_score` / `rank_items` — слияние relevance × engagement

Формула (ядро всего приёма):

```
blended = w_relevance · clamp(relevance, 0..1)  +  w_engagement · lognorm(engagement)
          где lognorm(e) = min(1, log1p(e) / log1p(engagement_cap))
дефолт: w_relevance = 0.7, w_engagement = 0.3, engagement_cap = 50
```

- **relevance** (0..1) — внешний сигнал совпадения (rapidfuzz/embeddings/token-overlap).
- **engagement** — сырой счётчик популярности (stars/upvotes/points). Лог-нормируется (насыщение),
  чтобы разрыв 5★ vs 5000★ не подавлял релевантность линейно.
- **Веса 0.7/0.3** — релевантность доминирует; популярность лишь «доводит» порядок.

```python
rank_items(items, relevance_key="relevance", engagement_key="engagement")
# → копии items, отсортированные по убыв. blended; балл записан в it["blended"]
# НЕ мутирует входные dict (работает на копиях)
```

## 3. `dedup_by_entity(items, entity_key, score_key="blended")`

Слить элементы с одинаковым ключом сущности (напр. нормализованный title/url/repo), оставив
**максимум** по `score_key`. `entity_key(item)` → хэшируемый ключ или `None` (None → уникален, не
схлопывается). Исключение в `entity_key` → элемент остаётся уникальным (try/except). Используется V2
для схлопывания одной новости, встреченной на нескольких платформах.

## API-сводка

| Функция | Вход | Выход |
|---|---|---|
| `expand_queries(q, extra_terms, max_variants)` | строка запроса | `list[str]` вариантов |
| `blended_score(relevance, engagement, *, w_relevance, w_engagement, engagement_cap)` | 2 числа | `float` 0..1 |
| `rank_items(items, *, relevance_key, engagement_key, score_key, ...)` | `list[dict]` | отсортированные копии + `blended` |
| `dedup_by_entity(items, entity_key, *, score_key)` | `list[dict]` + key-fn | дедуп, отсортировано по score |

## Решения дизайна

- **Чистота:** ноль IO/сети/глобального состояния → детерминизм + юнит-тесты без моков.
- **Относительная нормировка для кросс-источников:**
  потребитель нормирует engagement сам перед блендом. V2 делает **per-source min-max** в [0,1]
  (топ каждого источника = 1.0, `engagement_cap=1.0`): HN points / SO score / GitHub stars (10⁰–10⁵)
  конкурируют честно, без подавления звёздами. Глобальный `engagement_cap=max` — альтернатива,
  но топит малошкальные источники (выявлено live-проверкой, см. 44.4).
- **Анти-паттерн чистого engagement-ранкинга:** не сортируем по популярности в лоб — иначе вирусный,
  но нерелевантный контент всплывает первым. Блендинг с доминантой relevance этого избегает.
