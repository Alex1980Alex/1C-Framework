# 04.9 Matryoshka Embeddings — Storage/Latency Trade-off

> **Source:** roadmap [260509 §4.1](../../../roadmap/260509_ROADMAP_CONSOLIDATED_BACKLOG.md), closed 2026-05-16. Bench results in [`data/eval/matryoshka_report.json`](../../../../data/eval/matryoshka_report.json).

## Что такое Matryoshka Representation Learning (MRL)

Qwen3-Embedding-8B обучена с MRL loss — **первые N измерений вектора уже несут осмысленный сигнал**. Прямая truncation `vec[:N]` + L2-renormalize даёт workable embedding на меньшем dim **без переобучения**.

```
Native 4096d:    [v_0, v_1, ..., v_1023, v_1024, ..., v_4095]
MRL 1024 truncate: [v_0, v_1, ..., v_1023]                      (нужна L2-renormalize)
MRL  512 truncate: [v_0, v_1, ...,  v_511]                      (нужна L2-renormalize)
```

Cosine distance в Qdrant требует unit-normalized inputs. После truncation норма падает (`‖v‖ < 1`), поэтому **обязательная L2-renormalize** на client side. Без неё similarity scores дрейфуют — bug, который сложно поймать.

## Acceptance criterion (§4.1.3)

| delta_rel (vs 4096d baseline) | Recommendation |
|---|---|
| ≥ -5% (включая улучшение) | **MIGRATE** — production swap safe |
| -5% ≤ delta < -10% | **OPT_IN** — keep 4096d primary, MRL опционально |
| < -10% degradation | **REJECT** — close experiment |

Logic в [`scripts/matryoshka_bench.py`](../../../../scripts/matryoshka_bench.py) `compare_results()` — асимметричная (улучшение не блокирует migration; только degradation).

## Bench results (2026-05-16, pdf_documents 830 pts)

| Dim | recall@10 | p50 ms | p95 ms | delta_rel | latency speedup p95 | storage factor | Recommendation |
|---|---|---|---|---|---|---|---|
| 4096 (baseline) | 0.0563 | 20.6 | 29.2 | — | 1.0× | 1.0× | — |
| **1024 (MRL)** | **0.0563** | 19.5 | 26.5 | **+0.0%** | 1.1× | **4.0×** | **✅ MIGRATE** |
| 512 (MRL) | 0.0625 | 16.9 | 22.5 | +11.0% | 1.3× | 8.0× | MIGRATE (asymmetric — improvement noise at n=40) |

**Per-difficulty breakdown** (mean keyword_recall):

| Difficulty | 4096d | 1024d | 512d |
|---|---|---|---|
| easy | 0.1875 | 0.1875 | 0.1875 |
| medium | 0.0441 | 0.0441 | 0.0588 |
| hard | 0.0 | 0.0 | 0.0 |

## Interpretation

**Key finding**: 1024d MRL преобразование `pdf_documents` даёт **strictly identical retrieval** к 4096d baseline (delta=0.0% per query, identical per-difficulty). Это сильное эмпирическое подтверждение что Qwen3-Embedding-8B MRL-trained embeddings preserve full rank ordering в первых 1024 dims.

**Storage win unconditional**:
- `pdf_documents` 830 pts: 13 MB → 3.3 MB (-75%)
- `framework_code_v1` 21,242 pts: ~340 MB → ~85 MB (-75%)
- `bsl_code_v4_late` 37,694 pts (алиас → `_v3`, std pooling): ~600 MB → ~150 MB (-75%)

**Latency speedup модест** (1.1-1.3×) на dataset из 830 pts — HNSW graph traversal `O(log N)` доминирует над per-vector ops при таком N. На production-scale collections (24k+ pts) speedup ожидается ближе к 1.5-2×, не 4× как могло бы показаться из dim ratio.

**512d delta +11%** — статистический noise на baseline=0.056, n=40. CI на recall ~5% означает что результаты в пределах ±10% interchangeable. Cannot conclude 512d "лучше" 4096d.

## Caveats метода

1. **Keyword recall@10 вместо NDCG@10**: `golden_v1.expected_chunk_ids` empty pending §7.5 v2.0 grounding. Keyword recall — proxy метрика по `expected_keywords` (40/40 populated). Methodologically valid для A/B comparison, но absolute numbers не сопоставимы с production retrieval.
2. **Low baseline recall (0.056)**: `golden_v1` спроектирован против `framework_code_v1` keywords (Qwen3, FastAPI, MCP, RRF), а индексирован `pdf_documents` (1С Глава 5). Many queries don't have keyword hits in this corpus → keyword_recall approaches noise floor.
3. **n=40 queries**: confidence intervals широкие. Delta < 5% considered noise, > 10% considered signal.
4. **Single corpus tested**: production migration `framework_code_v1` SHOULD re-run bench with appropriate golden subset before swap.

## §4.1.7 BSL bench — REJECT verdict (2026-05-17)

После §7.5 v2.2 (golden_v1 +20 BSL queries, 15 grounded targeting bsl_code_v4_late) был запущен matryoshka_migrate.py на bsl_code_v4_late (тогда 54 800 pts × 4096d × Late Chunking pooling; **исторический снимок** — после Phase 5 alias-swap на std pooling `_v3` актуальный размер 37 694 pts). Результат:

| Dim | NDCG@10 | p95 ms | Delta vs 4096d | Verdict |
|---|---|---|---|---|
| 4096 (baseline) | **0.4659** | 372.1 | — | — |
| 1024 (MRL) | 0.3864 | 107.8 | **−17.1%** | ❌ **REJECT** |
| 512 (MRL) | 0.3363 | 109.5 | −27.8% | ❌ REJECT |

**Гипотезы почему BSL ≠ framework_code:**
1. **Late Chunking** — context-aware pooling распределяет document-level информацию по всем 4096 измерениям; truncate теряет critical signal сильнее, чем у std pooling.
2. **Symbol-level chunks** — каждый BSL chunk = одна процедура/функция с узкой семантикой; high-dim уникальность критичнее для disambiguation.
3. **Russian/BSL semantic density** — кириллические identifiers (`РегистрНакопления`, `ПолучитьСсылку`) пакуют семантический сигнал в верхние dims, которые отбрасываются.
4. **Lower baseline** — 0.466 vs framework 0.565; абсолютно меньшая degradation тут пропорционально хуже.

**Решение:** `bsl_code_v4_late` остаётся 4096d Qwen3 native. Staged коллекции `_mrl_1024` и `_mrl_512` удалены. Storage cost (~880 MB vs возможные 220 MB) оправдан +17% NDCG для production retrieval.

**Generalization:** Late-Chunking-pooled коллекции в этом фреймворке (тек. только `bsl_code_v4_late`) — не кандидаты на MRL truncation. Standard-pooling коллекции (`framework_code_v1`, `bsl_code_v4`, `pdf_documents`) — потенциально кандидаты, проверять по corpus.

## §4.1.8 PDF bench — MIGRATE verdict (2026-05-17, proactive growth swap)

После §7.5 v2.3 (golden_v1 +20 PDF queries, 16 grounded targeting pdf_documents) был запущен matryoshka_migrate.py на pdf_documents (830 pts × 4096d × std pooling). Результат **превзошёл baseline**:

| Dim | NDCG@10 | p95 ms | Delta vs 4096d | Verdict |
|---|---|---|---|---|
| 4096 (baseline) | 0.4042 | 110.2 | — | — |
| **1024 (MRL)** | **0.5120** | 111.0 | **+26.7%** | ✅ **MIGRATE** |
| 512 (MRL) | 0.4591 | 109.8 | +13.6% | ✅ MIGRATE |

**Сюрприз:** Truncate-to-1024d дал **выигрыш качества** на этом corpus, не просто паритет. Гипотезы:
1. **Curse of dimensionality** — 830 pts в 4096d → разреженное пространство; truncate до 1024d даёт denser similarity discrimination
2. **MRL training inductive bias** — Qwen3 обучен с MRL loss; первые 1024 dim concentrate наиболее discriminative signal
3. **n=18 statistical noise** — CI на 18 items шире; +27% включает удачные retrievals (но направление верное)

**Решение:** Swap выполнен через alias-pattern (тот же что §4.1.6). Storage 13.6 MB → 3.4 MB (-75%, на 830 pts), p95 latency 110 → 111 ms (нейтрально на маленькой коллекции). Backup `pdf_documents_4096_backup` сохранён.

**Patched indexer:** [`scripts/reindex_pdf_documents.py`](../../../../scripts/reindex_pdf_documents.py) использует helpers `resolve_collection_dim` / `maybe_truncate_vectors` / `resolve_physical_collection` из `framework_search.indexer` — автоматически детектит alias и truncate'ит на upsert.

**Pattern для будущих collections:**
1. Add 20+ targeted queries → golden_v1 (per-domain)
2. Ground через `ground_golden_v1.py --collection X` (5-7 мин)
3. Run `matryoshka_migrate.py --source X` (truncate + bench)
4. If MIGRATE → alias swap (1 мин)
5. Patch domain-specific indexer (1 файл, 3 line добавления + 1 import)

## §4.1.12 Scalar Quantization int8 для 3 REJECT-коллекций (2026-05-17)

Применён `quantization_config={"scalar": {"type": "int8", "quantile": 0.99, "always_ram": true}}` ко всем REJECT-коллекциям через `PATCH /collections/{name}` (non-destructive, Qdrant builds quantized index в background).

| Collection | float32 baseline | int8 + rescore (default) | int8 no-rescore |
|---|---|---|---|
| bsl_code_v4 (24 455 pts) | avg 91.9ms p95 176ms | **avg 24.9ms p95 30ms** | avg 16.9ms p95 27ms |
| bsl_code_v4_late (54 800 pts) | — | **avg 39.7ms p95 83ms** | — |
| graph_embeddings (36 590 pts) | — | **avg 28.8ms p95 31ms** | — |

**Recall@10 overlap (rescore vs quantized-only):** 10/10 — identical top-10. Score noise ~0.4%, полностью recovered через rescore.

### Что получено

- **3× speedup search latency** при zero quality loss
- **5× tighter p95** — стабильнее под нагрузкой
- **−75% RAM** для quantized vectors (int8 vs float32 в памяти)
- **Disk usage:** не изменён (float32 originals остаются для rescoring)

### Что НЕ получено

**Disk не уменьшился.** Qdrant SQ хранит quantized vectors дополнительно к float32 originals. Для real disk savings — destructive recreate без originals (−75% disk, но quality loss 3-5% + риск). PATCH approach выбран как safe path.

### Reversal

```bash

```

## §4.1.16 Init pitfall: alias-aware existence check (2026-05-19)

После MIGRATE-3 имена `pdf_documents`, `framework_code_v1`, `wiki_pages_v1` — alias'ы. `AsyncQdrantClient.get_collections()` возвращает **только физические** коллекции (`*_mrl_1024`), без aliases. Реализация `initialize()` в [`src/pdf_framework/vector_store/providers/qdrant.py`](../../../../src/pdf_framework/vector_store/providers/qdrant.py) ранее проверяла существование коллекции одним get_collections-обходом → для alias-имени получала `False` → пыталась `create_collection("pdf_documents")` → Qdrant отвечал `400 Bad Request: Alias with the same name already exists` → весь `Components.initialize()` падал, а MCP-сервер уходил в зомби.

Фикс — добавить `get_aliases()` lookup и проверять membership в объединении:

```python
collections = await self._client.get_collections()
collection_names = {c.name for c in collections.collections}
try:
    aliases = await self._client.get_aliases()
    alias_names = {a.alias_name for a in aliases.aliases}
except AttributeError:  # старые qdrant-client без get_aliases()
    alias_names = set()

exists = (
    self._collection_name in collection_names
    or self._collection_name in alias_names
)
if not exists:
    # ... create_collection(...)
```

`except` сужен до `AttributeError` — runtime ошибки (network/auth) должны падать, а не молча восстанавливаться через пустой alias set (иначе вернёмся к исходному 400-багу).

**Затрагиваемые именa** (после §4.1.6/8/10 в этом документе): `pdf_documents`, `framework_code_v1`, `wiki_pages_v1`. Для не-MRL коллекций (`bsl_code_v4`, `bsl_code_v4_late`, `graph_embeddings`, …) поведение прежнее — они физические, попадают в `collection_names` и так.
