### DBSF fusion — детали

- **DBSF (Distribution-Based Score Fusion)** требует **Qdrant ≥ 1.10**. Если build не поддерживает — код падает на **RRF** (Reciprocal Rank Fusion, k=60 по умолчанию Qdrant) автоматически (`try/except` вокруг `FusionQuery(DBSF)`).
- DBSF слияние = z-нормализация score каждого Prefetch-плеча, затем сумма. В отличие от RRF (вес 1/(k+rank), завязан только на ранг), DBSF учитывает **величину уверенности** плеча — плоское распределение BM25 на vocab-mismatch вносит меньший вклад.
- **Score-adaptive «бесплатно»:** явный query-adaptive classifier (выбор fusion/весов по типу запроса) **НЕ реализован** — помечен как «next» в roadmap. DBSF обеспечивает adaptive поведение без классификатора, поэтому приоритет низкий.

## Решение: native Qdrant hybrid (dense + sparse BM25, DBSF fusion)

### Layout

```
Named vectors:
  - dense:  4096d cosine  (Qwen3-Embedding-8B, Late Chunking std pooling)
Sparse vectors:
  - bm25:   IDF modifier  (FastEmbed Qdrant/bm25)
```

Один point хранит ОБА вектора. Sparse computed client-side из `payload.content`.

**Query path (production default, с 2026-06-20):** hybrid **DBSF fusion** — Prefetch dense (`using="dense"`) + Prefetch BM25 sparse (`using="bm25"`) → `FusionQuery(fusion=Fusion.DBSF)`. Оба плеча используются по умолчанию; цепочка fallback: DBSF недоступен (Qdrant < 1.10) → RRF; TEI down → BM25-only; FastEmbed/BM25 down → dense-only. Полный код — в разделе [Query path (production)](#query-path-production).

**Почему DBSF, а не RRF/BM25-alone:** DBSF (Distribution-Based Score Fusion) z-нормализует распределение score каждого плеча перед слиянием. На vocab-mismatch запросах BM25-плечо отдаёт плоские/низкие scores → после z-нормализации вносит меньший вклад автоматически. Это **score-adaptive поведение БЕЗ query-классификатора** — оно снимает проблему «failing arm», описанную в устаревшем разделе «Why RRF loses» (где мусорные dense-кандидаты из top-50 получали reciprocal-rank bonus и вытесняли точные BM25-хиты). DBSF строго доминирует RRF на обоих golden-сплитах (см. ниже).

> **Историческая заметка (SUPERSEDED 2026-06-20):** ранее дефолтом был pure BM25 (`client.query_points(query=SparseVector(...), using="bm25", ...)`), а RRF считался проигрышным, т.к. при мусорном dense top-50 его вес 1/(60+rank) вытеснял точные BM25-хиты. Переход на DBSF + здоровое dense-плечо сделали hybrid строго лучше BM25-alone.

### CamelCase нормализация (obligatory)

BSL identifiers — `ОбработкаПроведения`, `НоменклатураКонтрагент` — BM25 без preprocessing видит как один opaque token. Query `обработка проведения` тогда не матчит. Решение — split на index AND query:

```python
import re
_CAMELCASE_RE = re.compile(r"[А-ЯЁ][а-яё]*|[A-Z][a-z]*|[а-яё]+|[a-z]+|\d+")

def normalize_camelcase(text: str) -> str:
    parts = _CAMELCASE_RE.findall(text)
    return " ".join(parts).lower() if parts else text.lower()
```

Одинаковый regex в трёх местах (если расходятся — index/query desync ломает retrieval):
- [`scripts/migrate_bsl_to_hybrid.py`](../../../../scripts/migrate_bsl_to_hybrid.py)
- [`scripts/reindex_bsl_qwen3.py`](../../../../scripts/reindex_bsl_qwen3.py) `_normalize_camelcase_for_bm25`
- [`src/bsl/semantic_search/services/search.py`](../../../../src/bsl/semantic_search/services/search.py) `BSLSearchService._normalize_camelcase_for_bm25`

## Query path (production)

`src/bsl/semantic_search/services/search.py:_call_qdrant_search` (≈строки 439–614) auto-detects layout и при `hybrid` строит DBSF fusion с цепочкой graceful-fallback:

```python
layout = self._detect_collection_layout(collection_name)  # cached
if layout == "hybrid":
    bm25 = self._get_bm25_sparse()                  # FastEmbed Qdrant/bm25, lazy
    query_embedding = embed_tei(query, is_query=True)   # dense arm (TEI Qwen3)
    sparse_vec = SparseVector(...)                       # BM25 arm (CamelCase-normalized)
    prefetch_limit = max(limit, 50)

    if query_embedding and sparse_vec is not None:
        # both arms healthy -> DBSF fusion (RRF fallback if Qdrant < 1.10)
        prefetch = [
            qm.Prefetch(query=query_embedding, using="dense", limit=prefetch_limit, filter=filters),
            qm.Prefetch(query=sparse_vec,      using="bm25",  limit=prefetch_limit, filter=filters),
        ]
        try:
            client.query_points(collection_name, prefetch=prefetch,
                                query=qm.FusionQuery(fusion=qm.Fusion.DBSF), limit=limit)
        except Exception:                               # DBSF unavailable -> RRF
            client.query_points(collection_name, prefetch=prefetch,
                                query=qm.FusionQuery(fusion=qm.Fusion.RRF), limit=limit)
    elif sparse_vec is not None:                         # TEI down -> BM25-only
        client.query_points(collection_name, query=sparse_vec, using="bm25", limit=limit)
    elif query_embedding:                               # BM25/FastEmbed down -> dense-only
        client.query_points(collection_name, query=query_embedding, using="dense", limit=limit)
else:
    # Legacy single-vector dense query_points (non-migrated collections)
```

FastEmbed BM25 model lazy-init на первом hybrid-вызове (~2-3s, кэш в memory). Деградации:
- **TEI down** → BM25-only (прежний default-путь, всё ещё рабочий).
- **FastEmbed/BM25 down** → dense-only через `using="dense"`. Dense здоров (recall@10 lexical 0.72 / semantic 0.42) — это полноценный путь, а не аварийный.

**Latency:** дефолтный DBSF-путь требует TEI dense embed (~150-300ms) + BM25 sparse compute (FastEmbed CPU-only ~5ms). Экономия 150-300ms на TEI применима **только к BM25-only fallback** (TEI down) — не к дефолту. Дефолт жертвует latency ради +10pp (lexical) / +18pp (semantic) recall@10 (см. [Re-verification 2026-06-20](#re-verification-2026-06-20-итоговый-default)).

## Известные nuances

- **Per-corpus eval обязателен ПЕРЕД любым default switch.** Inversion test на `framework_code_v1` (`scripts/bench_framework_realistic_eval.py`, 67 queries из `data/eval/golden_v1.json`) на Python+MD корпусе показал **dense строго побеждает** (Recall@10 73.9% vs BM25 18.8% vs hybrid RRF 68.8%) — там запросы concept-level paraphrase. На BSL же (после ре-верификации 2026-06-20) дефолт — **hybrid DBSF**, а dense здоров. Вывод: режим fusion/плеча выбирается per-corpus по фактическому eval, а не по эвристике «Cyrillic ⇒ BM25» (последняя суперседнута).
- **Dense vectors остаются индексированными И участвуют в default-пути.** 37k × 4096d storage ~600MB RAM. `PATCH /collections/.../vectors {"dense": null}` **больше нельзя** — dense теперь часть дефолтного DBSF-плеча, не только fallback.
- **MCP server restart.** Long-running BSL MCP processes имеют кэшированный layout. После alias/collection swap нужен restart процесса MCP (Claude Code spawns per-session, так что новые сессии видят актуальный layout сразу).
