## Зачем эта глава

31.3 описывает **что запустить**. Эта глава отвечает на «**почему именно это** и **что НЕ делать**». Если бы 31.3 читали с понимаем, ошибок бы не было — но они повторяются (см. §6 «Типичные ошибки»), поэтому здесь собрана decision logic в одном месте.

## 1. Матрица backend × pooling × коллекция

| Backend | Pooling | Late Chunking | Где живёт | GPU при работе | Скорость | Когда выбирать |
|---|---|---|---|---|---|---|
| **`qwen3-st`** | last_token (через ST) | **✓ да** | in-process Python | ~16 GB FP16 | медленная (warmup ~30c + bucketed encode) | **Production full reindex** в `bsl_code_v4_late` |
| **`qwen3-tei`** | last_token (TEI built-in) | ✗ нет (TEI не поддерживает) | HTTP Docker `pdf-rag-tei:8080` | ~16 GB FP16 (постоянно) | быстрая (без warmup) | **Incremental** через git-commit hook, online queries (MCP search) |
| **`e5`** | mean | ✗ нет | in-process, CPU OK | 0 | средняя | legacy `bsl_code_v3` (DEPRECATED, drop pending) |

**Ключевое следствие:** `qwen3-st` и `qwen3-tei` оба используют ту же модель, но **результат отличается**:
- `qwen3-st late-chunking` → каждый chunk-вектор содержит контекст всего модуля (one forward pass + char-span mean-pool по hidden states)
- `qwen3-tei` → каждый chunk embedded независимо → теряет module-level контекст

**На BSL benchmark:** разница составляет **+64% recall@10** в пользу Late Chunking (Phase 8.12.9 A2-alt). Подробности: [arXiv:2409.04701](https://arxiv.org/abs/2409.04701).

## 2. GPU constraint (RTX 3090 / 4090 24GB)

| Сценарий | TEI Docker | qwen3-st | Итого VRAM | Работает? |
|---|---|---|---|---|
| Production queries (только TEI) | 16 GB | — | 16 GB | ✓ |
| Full reindex (только qwen3-st) | — | 16 GB | 16 GB | ✓ |
| Incremental + queries (только TEI) | 16 GB | — | 16 GB | ✓ |
| **Оба одновременно** | 16 GB | 16 GB | **32 GB** | ✗ **OOM на 24 GB GPU** |
| qwen3-st + `--enable-fa2` на ИБTransportManagementDevelop | — | 16 GB + buffers | >24 GB | ✗ **OOM** (memory `feedback_bsl_reindex_fallback`) |

**Правило:** перед full reindex через `qwen3-st` → `docker stop pdf-rag-tei`. После → `docker start pdf-rag-tei`.

### Конкретные команды

**Incremental (TEI остаётся up):**

```bash
python scripts/reindex_bsl_qwen3.py \
    --paths "<file1.bsl>" "<file2.bsl>" \
    --embedder qwen3-tei \
    --collection bsl_code_v4_late \
    --batch-size 32
```

**Full project reindex (требует stop TEI):**

```bash
docker stop pdf-rag-tei                                    # 1. FREE GPU
nvidia-smi --query-gpu=memory.used --format=csv            # 2. Verify <2 GB used

python scripts/reindex_bsl_qwen3.py \
    --project "<path-to-1c-project>" \
    --embedder qwen3-st \
    --pooling-mode late-chunking \
    --collection bsl_code_v4_late \
    --batch-size 50 \
    --buffer-size 512
    # БЕЗ --enable-fa2 для ИБTransportManagementDevelop (OOM)
    # Время: ~60-90 мин на 2000+ BSL файлов на RTX 3090

docker start pdf-rag-tei                                   # 3. Restore production
```

**Полная пересборка коллекции с нуля (только если payload schema изменилась):**

```bash
# WARNING: --recreate ДРОПАЕТ всю коллекцию (а не только текущий проект)!
# Запускать ТОЛЬКО при breaking changes в payload или модели.
python scripts/reindex_bsl_qwen3.py \
    --project "<path-to-1c-root>" \
    --embedder qwen3-st \
    --pooling-mode late-chunking \
    --collection bsl_code_v4_late \
    --recreate \
    --batch-size 50 --buffer-size 512
```

## 4. Альтернативные стратегии (опциональные флаги)

### 4.1 Dual-vector (`--dual-vector`)

Создаёт коллекцию с двумя named vectors: `content` + `module_path`. Позволяет искать **отдельно** по содержимому процедуры и по location в иерархии метаданных.

**Когда применять:** queries вида «процедура называется как-то про склад, в модуле объекта документа» — `module_path` vector ловит location-signal, `content` — semantic. Hybrid скоринг даёт ±10-15% precision@10 на типичных code-navigation queries.

**Сейчас в production:** нет (одиночный vector). См. [04.8 Dual Vector Search](../04_ПОИСК/04.8_Dual_Vector_Search.md) для активации.

### 4.2 FlashAttention 2 (`--enable-fa2`)

`qwen3-st` only. Заменяет O(n²) attention на ~линейную → ×1.5-2 throughput на long chunks. Требует:
- `pip install flash-attn` + CUDA 12.x toolkit + MSVC на Windows
- Left-padding (auto-applied) — correctness, не оптимизация: без left-padding FA2 + last-token pooling даёт garbage embeddings (`feedback_bsl_reindex_fallback` см. memory)

**Когда применять:** есть длинные модули и хватает VRAM. **НЕ применять** на `ИБTransportManagementDevelop/Конфигурация` — OOM на RTX 3090.

### 4.3 Bucketed batching (auto)

`qwen3-st` ВСЕГДА использует length-bucketed dynamic batching (Phase 8.10). Не управляется флагом — это про модель внутреннего batching'а.

Buckets (token_len → batch_size):
| Bucket | Token range | Batch size | Доля chunks (BSL) |
|---|---|---|---|
| S | ≤512 | 32 | 69% |
| M | ≤1024 | 16 | 19.5% |
| L | ≤2048 | 8 | 7.9% |
| XL | ≤4096 | 4 | 2.6% |
| XXL | >4096 | 1 | 0.7% (до 16854 tokens — translation dictionaries) |

Без bucketing'а padding до длинейшего в случайном batch'е раздувает wall-clock в 5-25× и рискует OOM.

### 4.4 Pooling mode (`--pooling-mode {standard,late-chunking}`)

`qwen3-st` only. Default = `standard` (каждый chunk independently). `late-chunking` — see §1.

**ВСЕГДА указывать `--pooling-mode late-chunking` для production `bsl_code_v4_late`** — иначе writes std pooling в production коллекцию и через год recall@10 падает с 0.567 до ~0.350.

## 5. Что лежит в коллекции — payload schema

Каждый point в `bsl_code_v4_late` соответствует **одной BSL процедуре/функции** (`chunk_type=symbol`), а НЕ скользящему окну символов. Реальный пример payload'а:

```json
{
  "chunk_id": "C__1С_Framework_ИБTransportManagementDevelop_..._Forms_ИзменениеДопускаТранспорта",
  "content": "// Object: DataProcessor.гкс_ПриемкаТранспорта\n// Module: Module (FormModule)\n// Region: ОбработчикиСобытийФормы\n&НаСервере\nПроцедура ПриСозданииНаСервере(...)\n\t...",
  "chunk_type": "symbol",
  "symbol_type": "Procedure",     // или "Function"
  "is_export": false,
  "module_path": "C:\\1С-Framework\\ИБTransportManagementDevelop\\...\\Module.bsl",
  "module_name": "Module",
  "module_type": "FormModule",    // FormModule|ObjectModule|ManagerModule|CommandModule|RecordSetModule
  "object_type": "DataProcessor",
  "object_name": "гкс_ПриемкаТранспорта",
  "name": "ПриСозданииНаСервере",
  "params": "Отказ, СтандартнаяОбработка",
  "signature": "Процедура ПриСозданииНаСервере(Отказ, СтандартнаяОбработка)",
  "region": "ОбработчикиСобытийФормы",
  "line_start": 5,
  "line_end": 15,
  "calls": [...],                 // до 20 references из call graph
  "caller_count": 0               // сколько мест в коде вызывают эту процедуру
}
```

**Префикс с context-комментариями** (`// Object: ...`, `// Module: ...`, `// Region: ...`) — это **обогащение** через `BSLContextEnricher` (см. `src/bsl/parser/context_enricher.py`). Embedding-модель «видит» эту локацию и группирует похожие по location процедуры ближе в векторном пространстве.

**`content` обрезается до 500 символов** в payload (для экономии Qdrant disk space), но **полный текст идёт в embedder**.

**`caller_count` + `calls[]`** заполняются из `cache/bsl_call_graph.db` если он есть на момент индексации. Поэтому build_call_graph рекомендуется **ДО** reindex.

## 6. Типичные ошибки

### Ошибка 1: Запустить `qwen3-tei` для full project reindex

**Симптом:** mixed-pooling коллекция (часть Late, часть std), gradual recall drop.

**Почему делается:** TEI быстрее, не требует stop/start dance, кажется что "тот же Qwen3 — какая разница".

**Правильно:** для full reindex (`--project`) → `qwen3-st` + `--pooling-mode late-chunking`. Для incremental (`--paths`) → `qwen3-tei` OK (mixed quality acceptable trade-off).

### Ошибка 2: Запустить `qwen3-st` БЕЗ остановки TEI

**Симптом:** CUDA OOM при `model.encode()` (две копии Qwen3-8B FP16 = 32 GB на 24 GB GPU).

**Правильно:** `docker stop pdf-rag-tei` → reindex → `docker start pdf-rag-tei`.

**Проверка:** `nvidia-smi --query-gpu=memory.used --format=csv` должен показать <2 GB перед qwen3-st запуском.

### Ошибка 3: Включить `--enable-fa2` на ИБTransportManagementDevelop

**Симптом:** CUDA OOM на длинных chunks (XXL bucket, >4096 tokens). FA2 уменьшает attention memory, но активации всё равно >24 GB на больших batch'ах.

**Правильно:** `--batch-size 50 --buffer-size 512 БЕЗ --enable-fa2` (см. memory `feedback_bsl_reindex_fallback`).

### Ошибка 4: Не делать `build_call_graph.py` перед reindex

**Симптом:** payload `calls` и `caller_count` остаются пустыми (или устаревшими).

**Правильно:** **сначала** `python scripts/build_call_graph.py --project <root> --db cache/bsl_call_graph.db` (16 секунд), **потом** reindex. Граф читается context enricher'ом.

### Ошибка 5: Применить Matryoshka truncation к BSL

**Симптом:** -12% до -20% recall@10 после MRL truncation 4096→1024d.

**Почему:** Cyrillic identifier-heavy content (имена процедур типа `гкс_ПолучитьДанныеЛабораторногоАнализа`) **не сжимается** MRL без потерь. Предиктор — content type, не pooling (memory `feedback_mrl_content_matters`).

**Правильно:** `bsl_code_v4_late` хранится в 4096d. SQ int8 quantization (3× speedup, zero quality loss с rescore) — да; MRL truncation — НЕТ. См. [04.9 Matryoshka §4.1.6-15](../04_ПОИСК/04.9_Matryoshka_Embeddings.md).

### Ошибка 6: Использовать `--recreate` для добавления проекта

**Симптом:** дроп всей коллекции `bsl_code_v4_late` (54 800 points всех конфигураций) при намерении добавить один проект.

**Правильно:** `--recreate` запрещён в `--paths` режиме. В `--project` режиме — использовать **только при breaking changes** в payload schema или embedder. Для добавления нового проекта — просто запустить `--project <new-root>` без `--recreate`, новые chunks доupsert'ятся.

### Ошибка 7: Игнорировать `--pooling-mode` для `qwen3-st`

**Симптом:** даже выбрав `qwen3-st`, без `--pooling-mode late-chunking` получаешь standard pooling (default).

**Правильно:** для `bsl_code_v4_late` обязательно `--pooling-mode late-chunking`. Это разделено на два флага, потому что `qwen3-st` может работать в **research-baseline режиме** (std pooling) для коллекции `bsl_code_v4` — но никогда для `_late`.

## 8. Альтернативные retrieval-стратегии (поверх индексации)

| Стратегия | Состояние в BSL | Где описано |
|---|---|---|
| Dense-only (текущая) | ✓ production | здесь, §1 |
| **Hybrid dense + BM25** | ✗ не активна для BSL (есть для PDF) | [04.2 Hybrid Search](../04_ПОИСК/04.2_Hybrid_Search.md) |
| Reranking (cross-encoder) | ✗ не активна для BSL | [04.6 Reranking](../04_ПОИСК/04.6_Фильтрация_и_Reranking.md) |
| HyDE (hypothetical doc) | ✗ не реализован | [04.7 Расширенный поиск](../04_ПОИСК/04.7_Расширенный_поиск.md) |
| GraphRAG (entity walk) | ✓ через `graph_embeddings` | [04.3 GraphRAG](../04_ПОИСК/04.3_GraphRAG.md) |
| Dual-vector | ✗ не активна для BSL | §4.1 + [04.8](../04_ПОИСК/04.8_Dual_Vector_Search.md) |

**Низковисящие фрукты для BSL retrieval улучшений:**
1. **Hybrid BM25** — BSL identifiers (`гкс_ПолучитьДанные...`) часто матчатся по подстроке. Может дать +10-20% recall на exact-name queries.
2. **Reranker** — топ-100 dense → bge-reranker-v2 → топ-10. Cost: +200ms на запрос. Может дать +5-15% NDCG.
3. **Dual-vector content+module_path** — см. §4.1.
