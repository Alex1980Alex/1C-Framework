## 1. Bug fix: «документ X не проводится для контрагента Y»

### Раньше (manual)
1. Спросить разработчика про среду (4-5 пингов туда-сюда)
2. Угадывать что не настроено
3. Поставить BP, попросить триггер
4. Если не сработало — снова угадывать

**Время:** 10-15 минут setup + долгий взаимный пересказ.

### Теперь
```
Step 1 — статус среды
  mcp__1c-debug__debug_health_check
  → ready=True, recommended_workflow="thin-client", elapsed_ms<1000

Step 2 — connect + BPs
  mcp__1c-debug__debug_connect(infobase_alias="ИБ...")
  mcp__1c-debug__debug_set_breakpoint(object_id="<doc-uuid>", line=141, module_type="ObjectModule")
  # ставим 3-5 BPs в подозрительных местах ОбработкаПроведения и связанных CommonModule
  # Fix #5: multi-BP aggregation — все попадут в один setBreakpoints workspace

Step 3 — попросить пользователя
  «Откройте документ X в окне 1С и нажмите Провести»

Step 4 — на каждом stop (последовательно через Continue)
  mcp__1c-debug__debug_stack_trace
  mcp__1c-debug__debug_variables
  mcp__1c-debug__debug_evaluate(expression="Контрагент.ИНН")
  mcp__1c-debug__debug_evaluate(expression="ЭтотОбъект.Состав.Количество()")
  mcp__1c-debug__debug_step(action="Continue")

Step 5 — финальный отчёт
  mcp__1c-debug__debug_session_summary(format="markdown")
  → копировать в комментарий бага
  mcp__1c-debug__debug_disconnect
```

**Артефакт в баге:** структурированный markdown с фактологией («BP1 fired @ line 141, params={Контрагент.ИНН='', Сумма=0}, root cause: пустой ИНН»).

**Время:** ~5 минут setup + готовый аудит-trail.

## 3. Performance hunting: «отчёт долго формируется»

```
Step 1 — baseline среды
  mcp__1c-debug__debug_health_check
  → проверить cluster_load probe (warn если rphost'ы под нагрузкой — debug может тормозить)

Step 2 — поставить BPs на ключевых "checkpoint"-местах
  BP1: начало процедуры формирования отчёта
  BP2: после загрузки исходных данных
  BP3: после агрегации
  BP4: после рендера

Step 3 — триггер пользователем (или через L2 scenario)

Step 4 — финальный summary
  mcp__1c-debug__debug_session_summary(format="json")
  → stop_events[].ts → раздельно: между BP1 и BP2 прошло X сек
  → видишь где именно тормозит
```

Можно автоматизировать через L2 + `pre_trigger_wait_sec=0` (минимум overhead) и сравнивать с baseline через `debug_session_diff`.

## 4. Regression hunt: «после моих правок что-то сломалось»

```bash
# 1. Baseline на чистой ветке
git checkout main
python scripts/autonomous_debug_test.py scripts/scenarios/critical_workflow.json
# скопировать session_id из output (Phase 5)
BASELINE_ID=<uuid>

# 2. Свои изменения
git checkout feature/my-changes
python scripts/autonomous_debug_test.py scripts/scenarios/critical_workflow.json
NEW_ID=<uuid>

# 3. Diff (через Claude Code MCP-tool)
mcp__1c-debug__debug_session_diff(
    prev_session_id="<BASELINE_ID>",
    curr_session_id="<NEW_ID>"
)
# → verdict=REGRESSION + точные deltas: bp_fire_count -1, eval_failures +2
```

**Use case:** даже если оба прогона "exit 0", разница в counters (например, новая ветка вызывает eval больше раз — потенциальная perf-регрессия) видна сразу.

## 5. Coverage-driven test design (P1.A + JOB-based)

Цель: узнать **какие строки BSL реально выполнились** при тестовом прогоне, и подтвердить покрытие критического пути. Используется вместе с JOB-based execution (Шаблон 6) для обхода RC2 warm-pool gap.

```
Step 1 — connect + register coverage lines
  mcp__1c-debug-hmr__debug_connect(infobase_alias="ИБTransport...", recycle_strategy="none")

  # Регистрируем линии интереса (UUID модуля + номера строк)
  mcp__1c-debug-hmr__debug_coverage_register(lines=[
    {object_id: "<CommonModule-UUID>", line: 157, module_type: "ManagerModule"},
    {object_id: "<CommonModule-UUID>", line: 159},
    {object_id: "<CommonModule-UUID>", line: 160},
    {object_id: "<OtherModule-UUID>", line: 3517, module_type: "CommonModule"},
    ...
  ])
  # → {registered_count: N, propertyID_resolved: true}
  # Зарегистрированные BPs работают как silent counters — halt не происходит

Step 2 — arm + JOB trigger
  mcp__1c-debug-hmr__debug_arm_next_rphost()
  # → arm выставлен для следующего JOB rphost

  mcp__1c-mcp-crud__execute_code("
    П = Новый Массив;
    П.Добавить(""<BSL вызывающий тестируемый путь>"");
    ФоновыеЗадания.Выполнить(""гкс_ОтладкаВыполненияКода.ВыполнитьКод"", П);
  ")
  # JOB спаунит новый rphost → auto-attach → coverage BPs fire → silent increment

Step 3 — ожидаем завершения JOB
  mcp__1c-debug-hmr__debug_ping  (2-3 итерации)
  # Если JOB завершился быстро — events могут быть пустыми, это нормально
  # Ждём ~2-5 сек пока ФоновоеЗадание = "Задание выполнено"

Step 4 — export coverage XML
  mcp__1c-debug-hmr__debug_coverage_export()
  # → {path: "data/debug_coverage/<session>.xml", coverage_pct: 66.7, lines_covered: 4, lines_total: 6}
  # XML совместим с SonarQube genericCoverage format:
  #   <lineToCover lineNumber="157" covered="true"/>
  #   <lineToCover lineNumber="159" covered="false"/>  ← эта ветка не выполнилась
```

**Интерпретация результата:**
- `covered="true"` → строка выполнилась в тестовом прогоне
- `covered="false"` → строка НЕ выполнилась → нужен дополнительный тест-сценарий для этой ветки
- `coverage_pct < 80%` → критический путь не полностью протестирован

**Важно:** если нужно покрыть несколько разных ветвлений — запустить `execute_code(JOB)` несколько раз с разными параметрами. Coverage counters накапливаются в рамках одной `debug_connect` сессии.

**Артефакт:** XML файл загружается в SonarQube/SonarCloud как `genericCoverage.xml` через `sonar.coverageReportPaths`. Также входит в `debug_session_summary(format="artifacts")` ZIP.

## 6. Integration debug по типам объектов

| Случай | Подход | Status |
|---|---|---|
| **Thin client** trigger (UI «Провести») | manual `debug_set_breakpoint` + user action | ✅ полностью работает (validated 2026-05-10) |
| **Background job / Регламентное задание** | set BP, scheduled job firing → wait_for_stop | ✅ работает (Server target type) |
| **HTTP service** (IIS path через 1c-mcp-crud) | L2 + `force_recycle: true` + `pre_trigger_wait_sec: 5` | ⚠️ timing race window — иногда BPs не fire даже после warm-up; см. 36.6 |
| **Web service** (SOAP) | то же что HTTP service | ⚠️ см. 36.6 |
| **Толстый клиент** | manual; либо `1cv8.exe /Execute` через subprocess | ✅ работает (ManagedClient/Server type) |
| **VA BDD тест** | run-bdd.ps1 → BSL execute → BP fires в processed code | см. [17.5 Команды Pipeline](../17_ТЕСТИРОВАНИЕ_1С/17.5_КОМАНДЫ_ПАЙПЛАЙНА.md) |

## 6. Сборный workflow для типичной dev-сессии

```
┌─ 09:00 — открыл задачу ───────────────────────────────────┐
│ mcp__1c-debug__debug_health_check                         │
│ → если warn'ы → mode=prepare с auto_prepare_available     │
│ → готов к debug за <1 минута                              │
└────────────────────────────────────────────────────────────┘
                         ↓
┌─ Bug fix iteration (5-10 min cycles) ─────────────────────┐
│ debug_connect → set_breakpoint(s) → user trigger          │
│ → stack/variables/evaluate → debug_step → fix BSL код    │
│ → repeat                                                  │
└────────────────────────────────────────────────────────────┘
                         ↓
┌─ Перед commit ────────────────────────────────────────────┐
│ debug_session_summary(format="markdown")                  │
│ → копировать в commit message                             │
│ debug_disconnect                                          │
└────────────────────────────────────────────────────────────┘
                         ↓
┌─ Перед PR review ─────────────────────────────────────────┐
│ python autonomous_debug_test.py scripts/scenarios/<task>.json │
│ → exit 0 = ready для review                              │
│ → markdown summary как PR description block              │
└────────────────────────────────────────────────────────────┘
                         ↓
┌─ Если ревьюер просит проверить regression ────────────────┐
│ debug_session_diff(prev_session_id=<baseline>)           │
│ → verdict + точные deltas в комментарии                  │
└────────────────────────────────────────────────────────────┘
```

## 7. Anti-patterns (что НЕ делать)

| Плохо | Почему | Как правильно |
|---|---|---|
| Пропустить L1 health_check «и так ясно что работает» | Pre-existing rphost'ы или missing flags ловятся ТОЛЬКО probe'ом | Всегда `debug_health_check` первым — это <1с |
| Установить много BPs одиночными вызовами без проверки `get_breakpoints` | До Fix #5 один BP перезаписывал другой; после — должны попадать в один cache entry per (module, prop) | После set'ов проверять `debug_get_breakpoints` — должен быть consolidated |
| Использовать `force_recycle_rphost=true` без необходимости | Убивает active sessions | Default `false`; включать ТОЛЬКО если L1 советует (recommended_workflow=force-recycle) |
| Запустить L2 без validates scenario JSON | Скрипт упадёт на середине, неясно почему | Schema validator теперь fail-fast (exit 9) — но проверь JSON сам в IDE |
| Игнорировать L3 summary | Без артефакта работа невидима — следующий dev / reviewer / future-вы не поймёт что было сделано | Markdown summary в каждый PR/commit с debug-сессией |
| Сравнивать sessions «на глаз» | Деградация может быть в counter'е, который человек не заметит | `debug_session_diff` — automated indicators |

## 7a. HTTP-service trigger flow с BP fire (roadmap 260511 §P0-§P0.5)

**Когда применять:** trigger BSL execution через `mcp__1c-mcp-crud__execute_code` — этот путь spawn'ит rphost как `JOB` target (не `Server`), а previous default filter `["Server", "ManagedClient"]` его пропускал → 0 BP fire (RC2 deep gap).

**Pre-condition:** roadmap 260511 P0-P0.5 batch applied (commits `9975fb8` + `3d91f1b`). Default `setAutoAttachSettings` filter теперь включает 8 target types (`Server, ManagedClient, HTTPService, WEBService, JOB, JobFileMode, COMConnector, OData`).

**Шаги:** см. полную последовательность в [roadmap 260511 §P0.5 verification](../../roadmap/260511_ROADMAP_1C_DEBUG_HMR_DEFICIENCIES_FROM_GKSTCPLK_2468.md) — кратко:

1. `debug_health_check` (видна `infobase_list` со списком valid IBs — §3.3)
2. `debug_connect(infobase_alias=<valid>, recycle_strategy="all_rphosts_of_cluster")` — gentle kill всех rphost'ов cluster'а, alias validated §3.1
3. `debug_set_breakpoint` на bottleneck
4. `mcp__1c-mcp-crud__execute_code` trigger → spawn'ит JOB target → wrapper auto-attach (`targetStarted`) → `_reapply_bp_workspace` пушит BPs ДО первой BSL операции
5. `debug_ping` — если 3 empty pings → auto-surface `no_fire_diagnostics` с RC1/RC2 suggestions (§3.6)
6. `debug_stack_trace` / `debug_variables` / `debug_evaluate` — inspect
7. `debug_step("Continue", target_id=...)` для КАЖДОГО stopped target (могут быть множественные JOB одновременно)
8. `debug_disconnect`

**Live E2E (2026-05-11, ИБTransportManagementDevelop):** 7 targets stopped (mix HTTPService + JOB), stack 10 frames captured, runtime confirmed `ТипЗнч(ДокументРегистрации) = Тип("ДокументСсылка.гкс_ФормированиеНомераПробы")`. См. cache entry [`rdbg-target-type-enum-and-bp-timing.md`](../../../.claude/skills/1c-doc-research/cache/rdbg-target-type-enum-and-bp-timing.md).

**Альтернатива через UI (Solution C, §3.5):** новый `debug_launch_thin_client(infobase_alias=..., wait_target_timeout_sec=15)` auto-flag'ает корректный `http://` protocol (closes RC3 — `tcp://` mismatch ранее). Затем `debug_wait_for_target` (§3.4) гарантирует sync attach перед `set_breakpoint`.

## 8. Bug fix через /implement-1c-task с BP-verification (Phase 1 roadmap 260510)

Полный pipeline-чеклист для типовой задачи `[MODIFIED]` точки модификации через 8-этапный
`implement-1c-task` с обязательной Live BP-verification на Этапе 5.x.

**Pre-condition:** есть готовый ANALYSIS-REPORT.md от `/analyze-1c-task` с `[MODIFIED]` точкой
(модуль + строка + действие). 1С infobase запущена, dbgs.exe на `:1550`, ragent с `-debug -http`.

**Шаги:**

1. **Запустить команду:** `/implement-1c-task <путь к ANALYSIS-REPORT>`
2. **Этап 0 Preflight** срабатывает автоматически (UserPromptSubmit hook `implement-1c-task-preflight.py`).
   Проверка systemMessage:
   - `Pipeline mode: Full` + `Debug environment: ready` → BP-verification доступна ✓
   - `Pipeline mode: Full (no-BP)` → debug-hmr недоступен, BP-verification SKIP (warning в IMPLEMENTATION-PROGRESS)
   - `Pipeline mode: Code-only / Read-only verify / Read-only research` → деградированный режим
3. **Этап 1-4** выполняются как обычно (Подготовка → Валидация запросов → BSL запись → Статанализ).
4. **Этап 5 Верификация** — в добавок к стандартным `find_references` + `get_project_errors`:
   - **Этап 5.x Live BP verification** (для КАЖДОЙ `[ADDED]`/`[MODIFIED]` точки):
     1. `mcp__1c-debug-hmr__debug_connect(infobase_alias=<ИБ>)` — если ещё не connected
     2. `debug_set_breakpoint(object_id=<UUID>, line=<MODIFIED_LINE>, module_type=<TYPE>)`
     3. `debug_get_breakpoints` — verify enabled=true
     4. Trigger через `mcp__1c-mcp-crud__execute_code` (минимальный harness, реалистичные данные)
     5. `debug_ping` — wait callStackFormed (max 3 iterations)
     6. `debug_stack_trace` — assert `frames[0].lineNo == MODIFIED_LINE`
     7. (опц.) `debug_variables` — state assertion
     8. `debug_step(action="Continue")` — release rphost (ОБЯЗАТЕЛЬНО даже на FAIL)
   - **Fallback при BP не fire'нул** (3 ping timeout'а):
     - a) `debug_break_on_next` + retry trigger
     - b) `debug_connect(force_recycle_rphost=True)` (Solution A — только dev-среда)
     - c) SKIP с обоснованием — pipeline блокируется перед Этапом 6
   - **Этап 5.y Regression diff** (опц., если есть baseline в IMPLEMENTATION-PROGRESS footer):
     - Прочитать `<!-- debug_session_id: <UUID> -->` из существующего файла
     - `debug_session_diff(prev_session_id=<UUID>, curr_session_id=<current>)`
     - Assert `verdict ∈ {NO_REGRESSION, IMPROVEMENT, NEUTRAL}` — если REGRESSION → блок на Этапе 6
5. **Этап 6 Тестирование** — `update_database` обязательно ДО live-вызовов; затем тест-план из ANALYSIS-REPORT.
6. **Этап 7 Документация** — IMPLEMENTATION-PROGRESS.md содержит:
   - `Pipeline mode: Full | Full (no-BP) | ...`
   - **BP verification** блок для каждой точки (Module, BP set ✓, Trigger, Stack hit lineNo, Variables, Step Continue ✓)
   - **Debug session** блок: `session_id`, `debug_session_summary(format="markdown")`, regression diff (если был baseline)
   - Footer `<!-- debug_session_id: <UUID> -->` для следующего прогона
7. **Этап 8 Git commit** — 3-уровневая структура (BSL submodule + docs submodule + main gitlink bump).

**Acceptance:** ВСЕ `[ADDED]`/`[MODIFIED]` точки покрыты BP-trace'ом (или обоснованно SKIP) + `debug_session_diff` не показывает REGRESSION + chекелист завершения (см. `implement-1c-task/SKILL.md`) PASS.

**Roadmap:** [260510 Phase 1](../../roadmap/260510_ROADMAP_DEBUG_HMR_INTEGRATION_INTO_1C_PIPELINE.md) §3.
