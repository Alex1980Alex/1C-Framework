# 36.7 HMR Subprocess Wrapper + Session Restoration

## Назначение

Hot-Module-Reload обёртка [`tools/bsl-debug-server/mcp_hmr_proc.py`](../../../tools/bsl-debug-server/mcp_hmr_proc.py) над основным MCP-сервером отладки. Решает три задачи одновременно:

1. **Live-reload без потери MCP-handshake'а** — при изменении исходников wrapper пересоздаёт inner subprocess и эмитит `notifications/{tools,resources,prompts}/list_changed`, не разрывая соединение с harness'ом.
2. **Persistent debug session** — `session_id` к RDBG переживает HMR-restart (`data/debug_sessions/.active.json` + `_get_client()` cold-start restore). Без этого первый же tool-call после reload'а получал бы `400 «UI+ часть отладки не зарегистрирована»`.
3. **Unified event dispatch** — `RDBGClient.ping()` теперь сам прокачивает события через `_handle_command` (раньше делал только background `_ping_loop` после своего `ping()`). Убирает race window, при котором manual `debug_ping` крал события у фонового loop'а и оставлял cache пустым.

> **MCP-сервер**: `1c-debug-hmr` (см. [`.mcp.json`](../../../.mcp.json) — параллельно plain-варианту `1c-debug`).
>
> **Связано:** [36.1 Обзор](36.1_Обзор.md), [36.6 Диагностика](36.6_Диагностика.md), [`feedback memory: 1c-debug MCP`](C:/Users/Tech.%20Boutique/.claude/projects/C--1--Framework/memory/reference_1c_debug_mcp.md)

## 1. Архитектура

```
┌─────────────────┐  stdio  ┌──────────────────────┐  stdio  ┌──────────────────────┐
│  Claude Code    │ ──────► │  mcp_hmr_proc.py     │ ──────► │  mcp_debug_server.py │
│  MCP harness    │ ◄────── │  (wrapper, watches)  │ ◄────── │  (RDBG client)       │
└─────────────────┘         └──────────┬───────────┘         └──────────────────────┘
                                       │ watchfiles
                                       ▼
                            ┌──────────────────────┐
                            │  source files:       │
                            │  mcp_debug_server.py │
                            │  bsl_locals.py       │
                            │  uuid_index.py       │
                            └──────────────────────┘
```

`mcp_hmr_proc.py` — асинхронный pipe-relay:

| Pump | Направление | Задачи |
|---|---|---|
| `up_pump` | `stdin` (client) → `child.stdin` | Кэширует `initialize` + `notifications/initialized` для replay при reload |
| `down_pump` | `child.stdout` → `stdout` (client) | Переживает respawn'ы — на EOF child'a проверяет, есть ли новый child |
| `watcher` | `watchfiles.awatch(*paths)` | На любое изменение → `_reload()` (kill child → spawn → replay handshake → emit list_changed) |

Все три pump'а защищены одним `_reload_lock` — пока reload идёт, up_pump блокирует запись, down_pump приостанавливает чтение, чтобы не получить race на `child.stdin/stdout`.

## 2. Reload-протокол

```
1. watchfiles детектирует изменение → wrapper logs "source change → reloading child"
2. async with _reload_lock:                        ← блокирует up/down pump'ы
3.   await _kill_child()                           ← SIGTERM, max 5s grace, потом kill
4.   await _spawn()                                ← новый subprocess с тем же entrypoint
5.   await _replay_initialize()                    ← пересылка cached initialize + notifications/initialized
        ─ child отвечает на initialize, но wrapper читает и ОТБРАСЫВАЕТ
        ─ harness уже считает себя initialized с прошлого hand­shake'а
6. await _emit_list_changed()                      ← три notifications: tools/resources/prompts list_changed
7. lock released                                   ← pump'ы продолжают работу
8. log "child reloaded"
```

**Trade-offs** (из docstring'а wrapper'а):
- In-flight requests во время reload теряются — клиент должен retry
- Live RDBG/debug session state в child'е теряется → восстанавливается из `.active.json`
- Reload latency = SIGTERM grace (≤5с) + spawn + replay initialize ≈ 1-3с

## 3. Persistent debug session (`.active.json`)

### Проблема

`RDBGClient` хранит in-memory state (session_id с RDBG, attached/registered флаги, BP cache, stop-state). После HMR-restart inner subprocess пересоздаётся → state теряется. RDBG, однако, **продолжает помнить** наш `dbgui` ~60с после последнего ping'а (GC grace). Если новый процесс генерит свежий `session_id` через `RDBGClient()`, RDBG отвечает `400 UI+ не зарегистрирована` — старый dbgui ещё жив, но новый id ему незнаком.

### Решение

**Persist** session-state на диск после успешного `attach()`:

```python
# tools/bsl-debug-server/mcp_debug_server.py:_persist_active_session
state = {
    "session_id": client.session_id,
    "debug_url": client.debug_url,
    "infobase_alias": client.infobase_alias,
    "persisted_at": time.time(),
}
# Атомарная запись через tmp + os.replace
os.makedirs(os.path.dirname(_ACTIVE_SESSION_PATH) or ".", exist_ok=True)
tmp = _ACTIVE_SESSION_PATH + ".tmp"
with open(tmp, "w", encoding="utf-8") as f:
    json.dump(state, f, ensure_ascii=False)
os.replace(tmp, _ACTIVE_SESSION_PATH)
```

**Restore** на cold-start `_get_client()`:

```python
def _get_client() -> RDBGClient:
    global _client
    if _client is None:
        state = _load_active_session()
        if state and state.get("session_id"):
            _client = RDBGClient(
                debug_url=state.get("debug_url", "http://localhost:1550"),
                infobase_alias=state.get("infobase_alias", "DefAlias"),
            )
            _client.session_id = state["session_id"]
            _client._attached = True
            _client._registered = True
            # Перезапускаем ping_loop (нормально стартует attach())
            try:
                loop = asyncio.get_running_loop()
                if _client._ping_task is None or _client._ping_task.done():
                    _client._ping_task = loop.create_task(_client._ping_loop())
            except RuntimeError:
                pass  # sync context (CLI) — ping_loop стартует лениво
        else:
            _client = RDBGClient()
    return _client
```

### Поведение по edge-cases

| Сценарий | Поведение |
|---|---|
| HMR-restart, RDBG помнит сессию | Instant continuation — 0 round-trip overhead, тот же `session_id` |
| HMR-restart, RDBG GC'нул сессию | Первый вызов 400 → existing UI+ recovery escalates → `detach + new attach + handshake` → новый `session_id` снова persist'ится через `attach()` → cost: 1 лишний round-trip |
| Graceful `debug_disconnect` | `detach()` чистит `.active.json` — disconnect ≠ HMR-restart |
| Crash без detach | Файл остаётся, escalation подхватит на следующем connect |

## 4. Unified event dispatch в `ping()`

### Проблема (root cause `debug_stack_trace` silent fail 2026-05-10)

Pre-fix `client.ping()` дренил RDBG-очередь, но **не вызывал** `_handle_command`. Только background `_ping_loop` обрабатывал события:

```python
# Pre-fix (НЕПРАВИЛЬНО):
async def ping(self):
    root = await self._post("pingDebugUIParams", body, include_dbgui_url=True)
    return _parse_response(root)   # ← raw events, cache НЕ заполняется

async def _ping_loop(self):
    while ...:
        commands = await self.ping()
        for cmd in commands:
            await self._handle_command(cmd)   # ← только здесь
```

Когда user вызывал manual `debug_ping` (MCP tool), тот:
1. Дренил RDBG queue (events возвращались)
2. **Крал** events у фонового `_ping_loop`'а
3. Cache (`_last_stack_by_target`, `_last_stopped_target_id`) оставался пустым

Следующий `debug_stack_trace` шёл HTTP-fallback path в `get_call_stack` (cache miss → `_ensure_target_attached + _post("getCallStack")`), где `httpx.HTTPStatusError` мог surface как opaque MCP error с пустым body.

### Фикс

`ping()` теперь dispatch'ит события сам:

```python
# Post-fix (mcp_debug_server.py:836-866):
async def ping(self) -> list[dict]:
    body = _build_request(_rdbg("idOfDebuggerUI", self.session_id))
    root = await self._post("pingDebugUIParams", body, include_dbgui_url=True)
    events = _parse_response(root)
    for ev in events:
        try:
            await self._handle_command(ev)
        except Exception as e:
            tag = ev.get("cmdID") or ev.get("_tag", "?")
            log.warning("ping dispatch failed for %s: %s", str(tag)[:40], e)
    return events
```

`_ping_loop` упрощён до делегата:

```python
async def _ping_loop(self) -> None:
    try:
        while self._attached and self._registered:
            await asyncio.sleep(2.0)
            try:
                await self.ping()      # dispatch внутри
            except Exception as e:
                log.debug("ping failed: %s", e)
    except asyncio.CancelledError:
        pass
```

### Эффект

| | До | После |
|---|---|---|
| Источник processing'а events | только `_ping_loop` | `ping()` сам, loop делегирует |
| Manual `debug_ping` populates cache | нет | **да** |
| Race window cache-miss | существовал | устранён |
| Per-event error isolation | была в `_ping_loop` | перенесена в `ping()`, ту же семантику |
| Double-processing risk | n/a (loop'у нечего было обрабатывать вне себя) | n/a (вызов один на event) |

### Тесты

`TestPingDispatch`:
- `test_populates_last_stopped_via_handle_command` — mock возвращает `callStackFormed`, `ping()` заполняет cache + возвращает events
- `test_continues_on_handler_exception` — первый event raise'ит, второй всё равно обрабатывается
- `test_empty_events_no_dispatch` — пустые events не падают, cache не мутируется

## 5. `debug_stack_trace` cache-first + error envelope

Defense-in-depth поверх root-cause фикса (commit предшествовал ему):

```python
@mcp.tool()
async def debug_stack_trace(target_id: str = "") -> str:
    try:
        client = _get_client()
        if not target_id:
            target_id = client.last_stopped_target_id or ""   # ← cache-first
            if not target_id:
                targets = await client.get_targets()           # ← fallback HTTP
                target_id = _find_stopped_target(targets) or ""
                if not target_id:
                    return json.dumps(
                        {"error": "No stopped targets", "targets": targets},
                        ensure_ascii=False, indent=2,
                    )
        stack = await client.get_call_stack(target_id)
        return json.dumps(
            {"target_id": target_id, "stack": stack, "depth": len(stack)},
            ensure_ascii=False, indent=2,
        )
    except Exception as e:
        log.exception("debug_stack_trace failed")
        return json.dumps(
            {"error": f"{type(e).__name__}: {e!r}", "target_id": target_id},
            ensure_ascii=False, indent=2,
        )
```

Два эффекта:
1. **Cache-first fallback** — `last_stopped_target_id` (заполнен через unified `ping()` dispatch) используется до HTTP roundtrip'а в `get_targets()`. Закрывает оставшийся race-window между двумя `await`'ами.
2. **Error envelope** — любое исключение surface'ится как `{"error": "<ExceptionType>: <repr>", "target_id": ...}` вместо opaque MCP-fail'а. `log.exception()` пишет full traceback в stderr.

Шаблон применяем и к остальным debug-tools'ам по мере необходимости (recommendation reviewer'a).

## 6. Когда использовать `1c-debug-hmr` vs `1c-debug`

| Ситуация | Сервер | Почему |
|---|---|---|
| Активная разработка `mcp_debug_server.py` | **`1c-debug-hmr`** | Edit → instant reload без потери session, без `/mcp reconnect` в Claude Code |
| Production-сценарии (CI, рутинная отладка) | `1c-debug` | Меньше движущихся частей, нет watchfiles overhead |
| Тестирование fix'ов wrapper'а live | **`1c-debug-hmr`** | Roundtrip "правка → проверка" — секунды, не минуты |
| Параллельная сессия Claude Code на той же базе | `1c-debug` | HMR-вариант имеет побочный watchfiles, может конфликтовать на NFS/network drives |

Tool prefix:
- `mcp__1c-debug__*` — plain
- `mcp__1c-debug-hmr__*` — HMR

**Альтернатива не рассматривается**: попытка использовать готовый `mcp-hmr 0.0.3.5` deadlock'ится на `tools/list` при проксировании FastMCP-target'а через in-memory transport (live-verified 2026-05-10 с fastmcp 2.14.7). Subprocess-isolation pattern в `mcp_hmr_proc.py` это обходит.

## 7. Известные ограничения

1. **Schema cache в harness'е** — Claude Code harness кеширует JSON-schema tools при initial handshake. `notifications/tools/list_changed` инвалидирует список tools (имена), но **не параметры schema**. Если в Python-сигнатуре MCP-tool добавлен новый параметр, harness его не увидит до полного `/mcp reconnect`. Workaround: пользователь делает `/mcp` reconnect после крупных изменений schema.
2. **Long Russian path / Cyrillic filenames** — `git stash --include-untracked` с длинным русским путём упирается в Windows MAX_PATH. Воркараунд: `git -c core.longpaths=true stash …`. Не блокирует HMR-flow но фейлит pre-LFS-migrate cleanup при наличии untracked русских директорий.
3. **`.active.json` без TTL** — проектное решение. Stale state file (через сутки или после reboot) даёт 1 лишний round-trip + escalation, после чего state перезаписывается с новым `session_id`. Введение TTL потребовало бы знать GC-окно RDBG (≈60с в норме, но зависит от условий).
4. **HMR убивает background ping_task** — при reload новый subprocess стартует с `_ping_task=None`. `_get_client()` восстанавливает task через `asyncio.get_running_loop().create_task(_ping_loop())`, но первая итерация loop'a происходит через `asyncio.sleep(2.0)` — окно ~2с до первого heartbeat'а к RDBG. Для 60с GC-окна некритично.
