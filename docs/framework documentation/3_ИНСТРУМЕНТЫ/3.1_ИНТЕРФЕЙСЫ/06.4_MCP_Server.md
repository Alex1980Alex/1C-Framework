# 06.4 MCP Server

## Обзор

MCP (Model Context Protocol) Server предоставляет 15 инструментов для интеграции с Claude Code и другими MCP-совместимыми клиентами.

## Запуск

```bash
# Запуск MCP сервера
python -m src.mcp_server.server
```

## 15 инструментов

| # | Инструмент | Описание |
|---|-----------|----------|
| 1 | `index_pdf` | Индексация PDF документа: загрузка, разбиение на чанки, embeddings, сохранение |
| 2 | `search_documents` | Поиск по проиндексированным документам (стратегии: vector, graph, hybrid, bm25, section_first, graphrag_local, graphrag_light) |
| 3 | `ask_question` | RAG question-answering — LLM-ответ на вопрос |
| 4 | `graph_query` | Запрос к графу знаний (сущности и связи) |
| 5 | `analyze` | Analytical RAG: многораундовый сбор доказательств со сравнительными таблицами |
| 6 | `research` | Deep research v2: plan-execute-verify с evidence graph и структурированными отчётами |
| 7 | `web_search` | Веб-поиск через Tavily/SerpAPI/DuckDuckGo (fallback при нехватке локальных данных) |
| 8 | `search_with_fallback` | Поиск по локальным документам, при низкой уверенности — дополнительно веб-поиск с fusion |
| 9 | `list_collections` | Список всех коллекций документов |
| 10 | `list_documents` | Список проиндексированных документов (читает `document_registry.db`; с D7-проводки 2026-06-12 реестр наполняется из любой точки входа — `Components` подключает его к `DocumentIndexer`, см. [34.1](../../2_КОНТЕКСТ/2.9_KNOWLEDGE_BASE/34.1_Обзор.md)) |
| 11 | `get_toc` | Получить оглавление проиндексированного документа |
| 12 | `get_stats` | Статистика по проиндексированным документам и графу знаний |
| 13 | `visual_search` | Поиск визуальных страниц (таблицы, графики, диаграммы) по текстовому описанию |
| 14 | `visual_hybrid_search` | Гибридный визуальный + текстовый поиск с RRF fusion |
| 15 | `plan_execute` | Plan-Execute агент: разбивает сложные запросы на шаги и выполняет их подходящими инструментами |

## Примеры использования

### Поиск

```
search_documents(
    query="конфигуратор",
    strategy="hybrid",
    k=5,
    language="ru"
)
```

### RAG ответ

```
ask_question(
    query="Что такое конфигуратор?",
    strategy="hybrid"
)
```

### Индексация

```
index_pdf(
    path="data/pdfs/document.pdf",
    graph=true,
    communities=true
)
```

```json
        }
    }

```

## Производительность холодного старта

`pdf-vector-graph` использует **lazy import** контейнера зависимостей `Components` ([src/mcp_server/server.py](../../../../src/mcp_server/server.py)) — тяжёлая цепочка LangChain загружается только при первом вызове tool'а, не на module import. Это нужно чтобы успеть ответить на JSON-RPC `initialize` до MCP handshake timeout клиента.

**Init pipeline (обновлено 2026-06-08, S1+S2 — decoupled init):** инициализация контейнера вынесена в единый фоновый `asyncio.Task` (`_do_init()`), а `_get_components()` ожидает его через `await asyncio.shield(task)`. Создание task'а — под `_init_lock` (микросекунды; await тяжёлой работы вне лока). Это закрывает два дефекта прежней схемы (init под `Lock` прямо в корутине запроса со сбросом `_components=None` при отмене):

1. **Death-spiral при таймауте.** Раньше отмена tool-call'а по клиентскому таймауту бросала `CancelledError` прямо в `initialize()` → весь прогресс терялся, `_components` оставался `None`, и КАЖДЫЙ следующий вызов перезапускал тяжёлый импорт с нуля. Теперь `shield` отвязывает init от жизненного цикла запроса: отмена вызывающего не убивает фоновый task — он продолжает работу и переиспользуется следующим вызовом. Рестарт init происходит **только** при реальной ошибке `initialize()` (детектируется `_init_task_failed()`: `done() && (cancelled() || exception())`), не при простой отмене. Успешный init кэширует `_components` для мгновенного reuse.
2. **Холодный первый вызов (warm-up).** `main()` запускает фоновый прогрев `asyncio.create_task(_warmup())` сразу на старте процесса — **до** `server.run` и как detached-task, поэтому JSON-RPC `initialize` handshake не блокируется, а тяжёлый импорт ML-стека идёт в idle-время после хендшейка. К первому реальному tool-call'у контейнер уже готов или почти готов. На shutdown warmup отменяется в `finally`.

Дополнительно у `pdf-vector-graph` в `.mcp.json` выставлен `"timeout": 600000` (10 мин, S3) — страховка на случай, если первый вызов всё же обгонит прогрев под пиковой contention.

> ⚠ Правки кода MCP-сервера подхватываются только после `/mcp reconnect` (запущенный stdio-процесс держит старый код).

| Метрика | Значение |
|---|---|
| Cold start handshake (после lazy import, 2026-05-19) | ~0.5 с |
| Cold start handshake (до lazy import) | ~24 с |
| Первый вызов tool'а (загрузка LangChain, изолированно) | +20-25 с однократно |
| Первый вызов под session-start contention (наблюдалось 2026-06-08, `mcp-pdf-vector-graph.log`) | до ~510 с (8.5 мин) — почти весь в импорте ДО `__init__` (сам `__init__` 0.54 с) |
| Последующие вызовы | штатные latencies |

> Именно contention-кейс (510 с импорта против ~60 с дефолтного клиентского таймаута) порождал `[Tool result missing due to internal error]` на тяжёлом `ask_question`: клиент отменял вызов, старый код терял прогресс → следующий вызов перезапускал импорт (death-spiral). Фикс S1+S2 (см. выше) + `timeout` (S3) устраняют это. Глубже — ленивая загрузка torch/transformers только в момент embedding-вызова (S4, отложено), чтобы лёгкие tools не тянули весь ML-стек.

### Если MCP-сервер показывает `✘ failed`

1. **Проверить cold start** — запустить вручную с `initialize` и замерить:
   ```powershell
   $start=Get-Date
   '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"probe","version":"1"}}}' | .venv\Scripts\python.exe -m src.mcp_server.server 2>$null | Out-Null
   "Cold start: $(((Get-Date)-$start).TotalSeconds) s"
   ```
   Ожидание: ~0.5-2 с.

2. **Поднять MCP handshake timeout** (страховка для других тяжёлых серверов):
   ```powershell
   [System.Environment]::SetEnvironmentVariable('MCP_TIMEOUT', '60000', 'User')
   ```
   Применяется после перезапуска Claude Code.

3. **Если cold start всё ещё медленный** — проверить eager imports в [server.py](../../../../src/mcp_server/server.py) (любой `from src.*` на верхнем уровне модуля, который тянет LangChain/Pydantic/embeddings, должен быть в `TYPE_CHECKING` блоке или внутри `_get_components()`).

4. **Persistent log сервера** — [`data/mcp-pdf-vector-graph.log`](../../../../data/mcp-pdf-vector-graph.log) (RotatingFileHandler, 2 MB × 3 backups, UTF-8). Пишется через именованный логгер `pdf-vector-graph` с `propagate=False` (не загрязняет root и stdio JSON-RPC канал). Тот же `file_handler` дополнительно прицеплен к **root logger** — это пропускает в файл записи внутренних модулей (`httpx`, `src.pdf_framework.*`, `pymorphy3.opencorpora_dict.wrapper` и т.д.), что позволяет видеть на каком конкретно под-этапе застрял `Components.initialize()`. К root прицеплен **только** file-handler (не stderr), чтобы не зашумлять Claude Code MCP-лог. Содержит: `MCP server pdf-vector-graph: starting stdio transport` при старте процесса, `Lazy-init Components: starting` / `Lazy-init Components: ready in Ns` вокруг первого tool-call'а, и внутреннюю трассировку между ними (`[QDRANT] Initialized`, `[BM25] Initialized`, `Loading dictionaries from …` и т.д.). При отсутствии стартовой строки в логе — процесс не запустился вовсе (проверить `tasklist | findstr python`); при отсутствии «ready in Ns» — сервер завис в `Components.initialize()`, последняя записанная внутренним модулем строка указывает на стадию-виновника.

### Granular Components timing (2026-05-19)

Чтобы локализовать стадию-виновника без догадок, [`src/api/dependencies/components.py`](../../../../src/api/dependencies/components.py) теперь инструментирован пошагово через локальный `_step()` helper в `__init__` и `_astep()` в `async initialize()`. Каждый блок выдаёт строку формата:

```
[Components] <step name>                  X.XXs (cum  Y.YYs)
[Components.init] <step name>             X.XXs (cum  Y.YYs)
```

`__init__` покрывает **16 unconditional + до 10 conditional подшагов** (всего 26 точек логирования; conditional gated на флаги `bm25_enabled`, `parent_child.enabled`, `light_rag.enabled`, `adaptive.routing_enabled`, `two_stage.enabled`, `optimization.enabled`, `external.web_search_enabled`, `hierarchical.summary_enabled`, `raptor.enabled`, `feedback.enabled`). Покрытые сущности: get_settings, get_loader, ProcessingPipeline, get_embedding_engine, get_vector_store, get_graph_store, ImageExtractor, SearchManager, ConversationMemory, + по одному `_step` на каждую Phase 30/38/7/8/3.3/34/32/37/36/40/18/19/22/30/13.2. `initialize()` покрывает 13 async-вызовов (vector_store, graph_store, parent_store, bm25_store, semantic_cache, version_manager, feedback_store, section_summary, collection_store, document_registry, research_session_store, query_tracker, audit_logger). Финальные строки — `[Components] __init__ DONE in X.XXs` и `[Components.init] DONE in X.XXs`.

Изолированный замер 2026-05-19 на холодном venv (вне MCP stdio): `__init__` 0.46 с, `initialize()` 0.67 с, общая Lazy-init фаза ≈ 1.1 с. Когда в production видишь "Lazy-init: starting" → "ready in" задержку >5 с — `grep "\[Components" data/mcp-pdf-vector-graph.log | tail -30` укажет конкретный подшаг с расхождением. Если ни один подшаг не выделяется аномально, а суммарное cum близко к 1 с — тормоз не в `Components`, а во внешнем contention (см. память `feedback_pdf_mcp_init_duration`: MCP cold-start storm при reconnect, disk I/O на параллельных venv-загрузках).

### Alias-aware Qdrant initialize (2026-05-19)

После Phase 8 MIGRATE-3 (см. [04.9 §4.1.6-15](../../2_КОНТЕКСТ/2.2_ПОИСК/04.9_Matryoshka_Embeddings.md)) `pdf_documents`, `framework_code_v1`, `wiki_pages_v1` существуют как **alias'ы** на физические `*_mrl_1024`. `QdrantVectorStore.initialize()` дополняет `get_collections()` обходом через `get_aliases()` и проверяет существование через union обоих set'ов — иначе alias-имя из конфига попадает в "не существует" ветку, вызывается `create_collection()` и Qdrant возвращает HTTP 400. Подробности с кодом — [04.9 §4.1.16](../../2_КОНТЕКСТ/2.2_ПОИСК/04.9_Matryoshka_Embeddings.md#41916-init-pitfall-alias-aware-existence-check-2026-05-19).
