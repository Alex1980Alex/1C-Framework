## 2. P0.A — Conditional + Hit-count BPs

**Что:** `debug_set_breakpoint` принимает 2 новых параметра:
- `condition: str` — BSL-выражение, RDBG-native (XML element `debugBreakpoints:condition`). RDBG не fires BP если условие false → 0 round-trip
- `hit_condition: str` — VS Code DAP syntax (`>N` / `>=N` / `<N` / `<=N` / `=N` / `%N`). Wrapper-level: counter в `_hit_conditions: dict[(oid,pid,line), str]`, на каждом BP fire — increment + check; если не satisfied → auto-Continue invisibly

**Архитектурное разделение:**
- `condition` = RDBG filter (быстро, server-side, обходит wrapper)
- `hit_condition` = wrapper filter (медленнее, но не требует RDBG XSD extension)

**Реализация:** [`bp_conditions.py`](../../../../tools/bsl-debug-server/bp_conditions.py) — `eval_hit_condition(cond, n)` + `auto_continue_if_unsatisfied(client, target_id, stack)`. `_aggregate_breakpoints` возвращает `dict[line, condition]` (раньше — `list[int]`) чтобы сохранять per-line condition при aggregation.

> **Re-apply gap закрыт (2026-06-04, review #2):** `_reapply_bp_workspace` (backstop при `targetStarted` / HMR-recovery, см. §5 P0.E и [36.7](36.7_HMR_Subprocess_Wrapper.md)) раньше собирал `bpInfo`-XML вручную **без** элемента `condition` → conditional BPs молча становились unconditional при каждом re-apply. Фикс: re-apply теперь идёт через общий `_build_bp_info_xml(line, condition)` (тот же helper, что `set_breakpoints`), поэтому кешированный condition сохраняется. Регресс: [`tests/test_reapply_condition.py`](../../../../tools/bsl-debug-server/tests/test_reapply_condition.py) (2 кейса — condition present / omitted).

**Пример:**
```
debug_set_breakpoint(
    object_id="e5dca369-...",
    line=497, module_type="CommonModule",
    condition="ДлинаСтроки > 5",  # RDBG filters
    hit_condition="%2"             # Wrapper makes visible only every 2nd hit
)
```

## 3. P0.B — Logpoints (tracepoints)

**Что:** Новый MCP tool `debug_set_logpoint(object_id, line, message_template, ...)`. На каждом BP fire:
1. Eval all `{expr}` placeholders в template via `client.eval_expression(expr, target_uuid, stack_level=0)` (в исходной реализации ошибочно `client.evaluate` — несуществующий метод, см. §3.1)
2. Render: `template.replace("{"+expr+"}", str(value))`
3. Write JSONL entry to `data/debug_logs/<session_id>.jsonl`
4. Auto-Continue (rphost не halt'ится user-visible)

**JSONL schema:**
```json
{
  "ts": "2026-05-11T18:23:45.678901",
  "target_id": "...",
  "object_id": "...", "property_id": "...", "line": 499,
  "template": "iter Счетчик={Счетчик} len={СтрДлина(Результат)}",
  "rendered": "iter Счетчик=3 len=3",
  "evaluated": {"Счетчик": "3", "СтрДлина(Результат)": "3"}
}
```

**Placeholder regex:** `\{([^{}]+)\}` skipping `{{escaped}}` (double-brace literal).

**SECURITY:** `{expr}` evaluates as **BSL expressions in running rphost** через `client.evaluate` — privileged operation. Не передавай untrusted templates.

**Реализация:** [`logpoints.py`](../../../../tools/bsl-debug-server/logpoints.py) — `extract_placeholders` + `fire_logpoint`. Wrapper integration: `_handle_command(callStackFormed)` calls `fire_logpoint` BEFORE hit_condition check (logpoints priority — they're tracepoints, never user-visible).

### 3.1 Live-hardening (2026-06-04) — впервые проверено на живой остановке

P0.B был tool-callable + register-verified ещё 2026-05-11, но **до 2026-06-04 ни разу не отрабатывал на реальном BP fire** (мешал HTTPService warm-pool gap §10). Первый live-прогон — через VA debug-attach ([17.2 §Debug-attached прогон](../../7_ПРОВЕРКА/7.4_ТЕСТИРОВАНИЕ_1С/17.2_НАСТРОЙКА_VA_BDD.md): запись из TestClient в серверный `RecordSetModule.ПриЗаписи`) — вскрыл 3 бага:

| # | Баг | Симптом в JSONL | Фикс |
|---|---|---|---|
| 1 | `client.evaluate` не существует (метод = `eval_expression`) | `rendered`/`evaluated` = `<eval-error: AttributeError>` на всех placeholder'ах | переименован вызов |
| 2 | eval **изнутри** ping-loop-обработчика → async-событие `exprEvaluated` некому доставить (re-entrancy deadlock) | `evaluated` = `[]` (пусто), значения не читаются | eval+log+Continue вынесены в отдельный `asyncio.create_task` (deferred); strong-ref в module-level `_active_tasks` set + `add_done_callback(_active_tasks.discard)` против GC (review #1) |
| 3 | `resultValueInfo` не декодировался в скаляр | сырой dict / base64 вместо значения | `_scalar()`: `valueString(_b64)` → `valueBoolean` (Истина/Ложь) → `valueDecimal` → `valueDate` → `pres(_b64)` → fallback |

**Почему нужна deferral'я (#2):** `fire_logpoint` зовётся внутри `_handle_command(callStackFormed)`, который сам крутится в ping-loop'е. Синхронный `await eval` там не получит ответ — `exprEvaluated` приходит следующим ping-событием, обработать которое некому (мы уже внутри обработчика). Вынос в `create_task` разрывает цикл: eval ждёт свой `exprEvaluated` в свежей корутине, а ping-loop продолжает крутиться и доставляет событие.

**Транзиентность halt'а:** остановка на BP записи РС живёт **~секунды** — async `debug_evaluate` из контекста Claude не успевает (round-trip ≈ окно halt'а). Logpoint вычисляет синхронно в окне halt'а **до** auto-Continue → транзиентность не мешает. Это делает logpoint **основным** (а не запасным) способом чтения переменных на короткоживущих серверных остановках. См. memory `feedback_register_bp_transient_logpoint`.

**Commits:** `6503fc9` (eval_expression + defer + `_scalar`), `dd7ce92` (GC strong-ref, review #1), мерж PR#1. **Тесты:** [`tests/test_logpoints.py`](../../../../tools/bsl-debug-server/tests/test_logpoints.py) — 9 (TestScalar ×7 + `test_fire_logpoint_defers_eval_and_continues` + `test_fire_logpoint_no_match`).

## 4. P0.C — Source mapping (FQN + file path)

**Что:** `debug_stack_trace` теперь обогащает каждый frame полем `resolved_source: {fqn, file_path, exists}`. Раньше user видел только UUIDs.

**Реализация:** `uuid_index.get_source_info(oid, pid) -> dict | None`:
- `_KIND_FQN`: `document` → `Документ`, `catalog` → `Справочник`, `commonmodule` → `ОбщийМодуль` (18 kinds)
- `_PROP_FQN`: `d1b64a2c-...` → `МодульМенеджера`, `a637f77f-...` → `МодульОбъекта`, `32e087ab-...` → `МодульФормы`, etc.
- Forms/Commands child UUIDs: `Документ.<parent>.Форма.<form-name>` / `Документ.<parent>.Команда.<cmd-name>`
- Guards: forms branch requires `property_id == FormModule UUID`, commands requires `CommandModule UUID` — mismatched returns `None`

**Live example (verified 2026-05-11):**
```json
{
  "lineNo": "16",
  "moduleID": {"objectID": "956571df-...", "propertyID": "9b7bbbae-..."},
  "resolved_source": {
    "fqn": "Configuration.Configuration",
    "file_path": null,
    "exists": false
  }
}
```

## 5. P0.D + P0.E — Cascade auto-Continue + BP-propagation drain

**Контекст:** `recycle_strategy="all_rphosts_of_ib"` (или просто spawn-on-attach) → каждый новый rphost halts at first BSL line (stop_on_next attach semantics). До P0.D эти cascade-halts оставались user-visible, blocking каждый последующий trigger.

**P0.D (фильтр):** [`system_stops.maybe_auto_continue_system_stop(client, target_id, stop_by_bp)`](../../../../tools/bsl-debug-server/system_stops.py):
- `stop_by_bp=True` → return False (keep visible, real BP)
- `_break_on_next_armed=True` → return False (user requested)
- Else → auto-Continue silently, return True (suppressed)

**P0.E (race fix):** между set_breakpoints и первым выполнением BSL есть гонка — dbgs.exe может не успеть push'нуть BP workspace к свежему rphost'у. Решение: пометить fresh-attached target в `_attached_pending` (после `_reapply_bp_workspace` в targetStarted handler); на первом halt'е для этого target — drain: re-apply BPs + `asyncio.sleep(0.15)` + Continue. Pattern из CDP `waitForDebuggerOnStart`.

**Session metrics gate:** `_stop_events`, `_bp_fire_count`, `_rphosts_seen`, `_bp_by_location` НЕ инкрементятся при `stop_suppressed = logpoint_fired or hit_condition_suppressed`. Метрики чистые от auto-Continue'd halts.

**Live verification (2026-05-11):**
- До P0.D: 9 targets застряли в `stopped_targets` после `all_rphosts_of_ib`, `execute_code` зависал
- После P0.D+E: `execute_code` возвращает `"aaa"` / `"bbbbbbb"` / `"cccccccccc"` чисто, `stopped_targets: []`

## 6. P0.F — Warm-pool arming (visible targets)

**MCP tool:** `debug_arm_warm_rphosts(target_types: list[str] = None) -> str`. Default filter: `["HTTPService", "JOB", "Server"]`. Pass `[]` to arm ALL targets без фильтра.

**Flow:**
1. `get_targets()` → list ALL rphost-like targets visible to dbgs (only attached to my session)
2. Filter by `target_types`
3. For each: `attach_debug_targets([id], attach=True)` + add to `_known_attached_targets` + `_attached_pending` (so P0.E drain applies on next halt)
4. Batch end: `_reapply_bp_workspace()` once

**Returns:** `{status, count, filter_types, armed_targets, bp_workspace_reapplied}` — explicit `reapplied_ok` flag tracks actual reapply outcome (not just len(armed)>0).

**Live verification:** 1 JOB target armed + BP workspace reapplied=true.

## 7. P0.G — Silent arm next rphost

**Контекст:** P0.F arms только targets visible через `getDbgAllTargetStates`. Pre-existing warm-pool rphost (alive до `debug_connect`) **invisible** этому query. Решение — `setBreakOnNextStatement` + silent drain.

**Flag:** `_break_on_next_silent_arm: bool = False` (one-shot). Устанавливается через `set_break_on_next_statement(silent=True)`.

**Silent-arm path в `system_stops.maybe_auto_continue_system_stop`:**
1. Detect `_break_on_next_silent_arm=True` AND `stop_by_bp=False`
2. Clear flag (one-shot)
3. `attach_debug_targets([target_id])` — grab the rphost
4. Add to `_known_attached_targets`
5. `_drain_bp_propagation` (reapply + sleep + Continue)
6. Return True (suppressed — no user-visible halt)

**MCP tool:** `debug_arm_next_rphost()` — single call: arms global trap + sets silent flag.

**Live verification (2026-05-11):** captured `callStackFormed` event with `suspendedByOther: true` for JOB target — wrapper silent-armed it через всю цепочку.

**Limitation:** `setBreakOnNextStatement` halts only rphosts already attached to my debug session (per yukon39 + RDBG XSD analysis). Pre-existing HTTPService warm-pool rphost remains invisible — see §10 ниже.

## 10. Known limit — HTTPService warm-pool BP fire

**Не закрывается** через RDBG protocol — это **vendor ceiling** платформы 8.3.27.

**Симптом:** функция, вызванная через `1c-mcp-crud:execute_code` (HTTP POST на `/hs/mcp/rpc`) попадает на warm-pool rphost. Этот rphost:
- Существовал до `debug_connect`
- НЕ зарегистрирован в моей debug session (`DBGUIExtCmdInfoStarted` event fires только на spawn)
- НЕ виден через `getDbgAllTargetStates`
- НЕ halt'ится через `setBreakOnNextStatement` (доставляется только attached targets)

**Confirmed sources:**
- RDBG XSD `debugRDBGRequestResponse.xsd` — 40+ команд analyzed, **NO attach-by-PID**
- [yukon39/bsl-debug-server](https://github.com/yukon39/bsl-debug-server) Java reference — same gap, not solved
- Конфигуратор / EDT "Подключиться к предмету отладки" dialog — uses same `RDBGSGetDbgTargets`, **NO PID-based attach option**
- [1c-dn forum, Vladimir Gurov (1С)](https://1c-dn.com/forum/forum1/topic2025/): «We plan to implement a more convenient way to debug HTTP services in next releases of EDT» — vendor acknowledges + promises future fix

**Workarounds** (документировано в [36.6 Диагностика](36.6_Диагностика.md)):

| Path | Autonomy | Side effect |
|---|---|---|
| `force_recycle_rphost=True` (snapshot) | ✅ автономно | kills pre-existing user sessions |
| `recycle_strategy="all_rphosts_of_ib"` | ✅ автономно | same + ragent respawn warm pool fast |
| `debug_launch_thin_client` + Solution C | ❌ UI участие | юзер нажимает в открытом клиенте |
| `iisreset` | ❌ admin | drops all IIS user sessions |
| **JOB-based execution** ✅ (реализовано 2026-05-12) | ✅ автономно | нет деструктивного эффекта — JOB rphost изолирован |

### §10.1 JOB-based execution — RC2 gap закрыт

**Реализация:** CommonModule `гкс_ОтладкаВыполненияКода` (server=true, `ВыполнитьКод(КодДляВыполнения) Экспорт`). Добавлен в конфигурацию ИБTransportManagementDevelop.

**Механизм:** `ФоновыеЗадания.Выполнить(...)` спаунит **новый** rphost → платформа посылает `DBGUIExtCmdInfoStarted` → wrapper auto-attach → BPs reapply → BP fire. Каждый вызов создаёт свежий JOB target, не затрагивает HTTP warm-pool rphosts.

**Workflow (Шаблон 6 в SKILL.md):**

```
1. debug_set_breakpoint(object_id=<UUID>, line=<N>)
2. debug_arm_next_rphost()          # arm для auto-attach JOB rphost
3. execute_code("
     П = Новый Массив;
     П.Добавить(""<BSL fragment>"");
     ФоновыеЗадания.Выполнить(""гкс_ОтладкаВыполненияКода.ВыполнитьКод"", П);
   ")                               # async — returns immediately
4. debug_ping → callStackFormed на JOB target
5. inspect / step
```

**Coverage через JOB:** `debug_coverage_register` → `debug_arm_next_rphost` → `execute_code(JOB)` → coverage BPs fire → `debug_coverage_export` → `covered=true`. Решает timing gap из live-верификации 2026-05-11 (coverage_pct=0 из-за HTTP arm drain).

| Tool | Что делает |
|---|---|
| `debug_calibrate_lines(object_id, line, module_type?, property_id?, radius=8)` | Silent-веер BP на `[line±radius]` (clamp radius 1..30, floor строки 1): каждая строка регистрируется через `bsl_coverage.register_line` → на fire hit+auto-Continue, видимых остановок нет. Один агрегированный `setBreakpoints`. Повторная калибровка того же object_id вычищает старый веер (нет утечки silent-BP). Состояние — `client._calibrations[object_id]` |
| `debug_calibrate_result(object_id?, clear=True, keep_bp_on_nearest=True)` | Возвращает `fired_lines` (hits>0), `nearest_fired`, `offset = nearest − requested` (сдвиг типовой для всего модуля). При `clear` снимает веер: coverage-ключи + BP-кэш + перепуш workspace (пустой кэш → явный пустой `bpWorkspace`-push, REPLACES-семантика); на nearest оставляет ОБЫЧНЫЙ BP (запись в кэше создаётся явно, если её нет — HMR-restart case) |

**Workflow:** `debug_calibrate_lines` → триггер JOB'ом (`ФоновыеЗадания.Выполнить` через execute_code; прямой HTTP-service вызов не ловится — §10) → `debug_ping` ×2-3 → `debug_calibrate_result` → остальные BP/logpoint модуля ставить с поправкой `offset`.

**Известные ограничения:** пользовательский BP внутри окна веера будет снят вместе с веером; строки, уже tracked через `debug_coverage_register`, при пересечении с веером засчитаются как fired по накопленным hits (stale-hit) и будут вычищены из coverage-трекера при `clear`.

**⚠ Окно останова эфемерного JOB ≈ 1–2 с** — платформа принудительно возобновляет halt server-контекста: `debug_variables`/`debug_evaluate` успевают сразу после ping со `stopByBP=true`, `debug_step(Step)` — нет; «Предмет отладки не зарегистрирован» = target уже завершился. Чтение переменных без гонки — logpoint (P0.B). Интерактивный step — только персистентный контекст (thin client / VA).
