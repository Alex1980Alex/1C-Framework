### Что закрылось и как

| Item | Реализация |
|------|-----------|
| **P0.1** Label-driven activation | `pr.task_meets_label_requirement()` — читает `metadata.labels` + `[label]` в subject. Backward-compat: пустой env = старое поведение |
| **P0.2** Conflict-aware push | `pr.push_branch_safe()` — детектит rejection hints, fetch, если remote-ancestor — retry, иначе skip с manual-review message |
| **P0.3** Detect existing PR | `pr.gh_pr_list_for_branch()` — OPEN PR → `gh_pr_comment`, иначе → `gh_pr_create` |
| **P0.4** Pre-commit as test | `DEFAULT_TEST_CMD = "pre-commit run --all-files"`, override через env |
| **P1.1** Email notifications | `shared/pr_notifier.py` — `send_email()` через `smtplib` + STARTTLS/SSL. Хук вызывает на created/merged/failed/checks_failed. Silent no-op если `AUTO_PR_SMTP_HOST`/`_NOTIFY_TO` не заданы |
| **P1.2** Queue-lite | `pr.gh_pr_wait_checks()` — poll `gh pr checks` каждые 15с до `success`/`failure`/timeout. Сделано как single-dev упрощение, не настоящий Mergify-queue |
| **P1.3** Auto-rebase | `pr.base_drift_status()` всегда показывает drift в systemMessage; `pr.auto_rebase_safe()` запускается только при `AUTO_PR_AUTO_REBASE=1`. На конфликте — abort + skip |
| **P1.4** Dry-run | Все проверки (label/scope/rebase-check/tests) выполняются, но push/PR/merge — нет; systemMessage показывает планируемые действия |
| **P1.5** Dashboard | `scripts/pr_automation_dashboard.py` — argparse `--days/--out/--json`, daily breakdown, top errors, stale PRs >7d. Output: stdout + `data/reports/pr_automation/_latest.md` + dated snapshot. Windows cp1251-safe (`stdout.reconfigure('utf-8')`) |
| **P2.1** Per-task SHA | Хук теперь обрабатывает `TaskUpdate(status=in_progress)`: пишет `start_sha` в state-file. На `completed` — scope = `start_sha..HEAD` если есть, иначе fallback на `base..HEAD`. Storage = JSON state (SQLite не введён — overkill для single-dev/~10 PR/день) |
| **P2.2** PR template | `.github/pull_request_template.md` — Summary / Test plan / Scope / Notes. Хук `--body` фолбэк совпадает по структуре |
| **P2.3** Reviewer assignment | `_resolve_reviewers()` — CODEOWNERS lookup через `pr.codeowners_for_paths()` (упрощённый gitignore-style matcher); fallback на `AUTO_PR_REVIEWERS` env |
| **P2.4** Orphan cleanup | `scripts/cleanup_orphan_branches.py` — dry-run default; local: ancestor + age≥30d; remote: PR MERGED/CLOSED. Запускать вручную или из cron, в settings.json как hook **не зарегистрирован** (намеренно — операторская задача, не каждое Stop) |
| **P2.5** Cross-PR deps | `blockedBy` task_ids читаются на `in_progress` (хранятся в state); на `completed` резолвятся в PR# через state.processed и `gh_pr_add_labels(["blocked-by:#N"])` |

### Что закрылось и как (P3)

| Item | Реализация | Статус |
|------|-----------|--------|
| **P3.1** GitHub App webhook receiver | FastAPI router `POST /webhooks/github` принимает `pull_request` + `check_suite` events, верифицирует HMAC SHA-256 подпись через `GITHUB_WEBHOOK_SECRET`, парсит payload, маппит `head.ref` `task/<id>-…` → task_id и пишет в **тот же state-file**, что и hook (`.claude/cache/post-task-push-pr-state.json`). Поля: `webhook_last_event`, `webhook_last_ts`, `merged_ts`, `merge_sha`, `check_suites[]` (capped 20). Wiring инструкция в docstring файла | **runnable** (router готов; оператор регистрирует в `src/api/app.py` через `app.include_router(github_webhooks.router)` + настраивает webhook в GitHub Settings) |
| **P3.2** Cherry-pick branch model | `cherry_pick_range_to_branch()` создаёт **temp git worktree** от `origin/<base>`, делает `git cherry-pick <start_sha>..<head_sha>` туда (working tree caller'а не трогается). На конфликте — `cherry-pick --abort` + worktree remove + branch delete + fallback на старую модель `git branch -f branch HEAD`. Hook логирует `mode=cherry-pick|head-ref` в systemMessage и в state-file | **runnable** (opt-in `AUTO_PR_CHERRY_PICK=1`) |
| **P3.3** Mergify migration | `.mergify.yml` template со 2 очередями (`default` требует approvals+CI, `hotfix` только CI), правилами enqueue для `head~=^task/` + label `auto-merge`, hotfix-lane по label `hotfix`, post-merge branch cleanup, auto-rebase при отставании от base. Совместим с hook'ом: при включении Mergify нужно выставить `AUTO_PR_AUTO_MERGE=0` чтобы избежать double-merge race. **Альтернатива (рекомендуется): GitHub native merge queue** — free, zero-infra. Включается в repo Settings → Branches → Branch protection rule → Require merge queue. Hook поддерживает через `AUTO_PR_MERGE_QUEUE=1` (опция в `gh_pr_merge(..., queue=True)` → `gh pr merge --merge-queue`). Self-hosted OSS альтернативы: Bulldozer (Palantir), Kodiak — обе deploy as GitHub Apps | **config-only** (Mergify SaaS); **runnable** (GitHub native queue via `AUTO_PR_MERGE_QUEUE=1`) |
| **P3.4** Post-merge CI auto-revert | `scripts/pr_check_post_merge.py` — итерирует merged PRs из state, для каждого через `gh pr view --json mergedAt,mergeCommit,baseRefName` + `gh run list --commit <sha>` определяет статус runs на merge-commit. На `failure` (с `--apply`) создаёт revert PR через temp worktree: `git revert -m 1 <merge_sha>` (с fallback на `git revert` без `-m` для squash commits), push в `auto-revert/<sha12>` branch, `gh pr create`. Записывает `post_merge_status` (success / failure / reverted / no_runs / pending) + `post_merge_revert_pr` в state — повторно не проверяет. Email-notify при revert | **runnable** (dry-run default; запускать вручную или из cron каждые 30мин) |

### P3.1 — что сделать оператору чтобы webhook receiver заработал

1. В [`src/api/app.py`](../../../src/api/app.py) добавить импорт + register:
   ```python
   from src.api.routes import github_webhooks
   ...
   app.include_router(github_webhooks.router)
   ```
2. Сгенерировать секрет (`openssl rand -hex 32`), положить в `.env`:
   ```
   GITHUB_WEBHOOK_SECRET=<тот же секрет, что в GitHub>
   ```
3. Запустить API: `uvicorn src.api.app:app --host 0.0.0.0 --port 8000`.
4. Экспонировать наружу: ngrok / Cloudflare Tunnel / прод-reverse-proxy.
5. В GitHub repo → **Settings → Webhooks → Add webhook**:
   - Payload URL: `https://<host>/webhooks/github`
   - Content type: `application/json`
   - Secret: тот же, что в `.env`
   - Events: `Pull requests`, `Check suites`

### Когда дёргать `pr_check_post_merge.py`

- Можно вручную после критичных merge'ей.
- Можно cron'ом каждые 30 минут (Windows Task Scheduler / Linux cron).
- Или из SessionStart hook'а с cooldown, но default — operator-driven, чтобы избежать неожиданных revert'ов посреди работы.

## P0 — quick wins (~8ч)

### P0.1 — Label-driven activation (~2ч)

**Проблема**: текущий `post-task-push-pr` срабатывает на каждый TaskUpdate(completed) если `AUTO_PR_ENABLED=1`. Pattern из Tier-1 best practices — gate на PR label, не на ENV master switch.

**Fix**: hook читает label из `tool_input` или task metadata (`task.labels.includes("auto-pr")`). Только при label fires.

**Эффект**: granular control per-task, не глобальный switch.

### P0.2 — Conflict-aware push (~2ч)

**Проблема**: если `task/<id>-<slug>` уже существует на remote с другими commits, `git push -u origin` fails. Hook эмитит `push failed`, но не пытается resolve.

**Fix**: detect "Updates were rejected" → fetch + check FF possible → если safe rebase ИЛИ skip с message "branch exists, manual review needed".

**Эффект**: меньше manual intervention при concurrent работе.

### P0.3 — Detect existing PR (reuse) (~2ч)

**Проблема**: при re-run task hook пытается create PR — fails если PR уже есть.

**Fix**: `gh pr list --head task/<id>-...` → если есть, добавить comment "updated to <new_sha>" вместо create.

**Эффект**: idempotency на PR layer, не только на state-file.

### P0.4 — Pre-commit gates как pre-push test (~2ч)

**Проблема**: `AUTO_PR_TEST_CMD` запускает pytest, но не lint/type checks. PR может попасть с code style issues, потом pre-commit fail на review-side.

**Fix**: дефолт `AUTO_PR_TEST_CMD` = `pre-commit run --all-files` (runs все gates). Pytest опц через отдельный env.

**Эффект**: PR гарантированно проходит pre-commit gates.

## P1 — production hardening (~15ч)

### P1.1 — Notification channel (~3ч)

Slack webhook / Telegram bot / email на:
- PR created
- PR auto-merged
- PR failed pre-push (с tail логов)
- FAIL verdict от code-verify

Pattern из Tier-3 best practices.

### P1.2 — Merge queue для batched merges (~6ч)

**Когда**: если parallel tasks merge в master с overlapping diffs. Сейчас single-developer — не критично.

**Fix**: использовать Mergify-style queue OR custom: после push, hook ждёт CI green + merges по очереди.

### P1.3 — Auto-rebase if branch is stale (~3ч)

Перед push: `git fetch origin && git rebase origin/$AUTO_PR_BASE`. Если конфликт → skip + warn.

### P1.4 — Dry-run mode (~2ч)

`AUTO_PR_DRY_RUN=1` — hook делает все checks + emit'ит planned actions, но НЕ push'ит и не create PR. Безопасный test.

### P1.5 — Audit log analysis dashboard (~4ч)

`data/hook-invocations.jsonl` → daily roll-up: успешные PR, failed pushes, push latency, time-to-merge. Mark по similar pattern как 38.5 auto-reports.

## P2 — workflow maturity (~20ч)

### P2.1 — Per-task scope detection (~6ч)

**Проблема**: текущий hook берёт **все commits since base** в task branch. Если в работе паралельно несколько таsks → mixing.

**Fix**: per-task SHA tracking (start_sha при TaskUpdate→in_progress, end_sha при completed). Cherry-pick range to new branch from master. Cleaner per-task diff.

**Pattern**: Graphite stacked PRs / Mergify partial merges.

### P2.2 — PR template (~2ч)

`.github/pull_request_template.md` — auto-filled headers (Task #, summary, test plan). Hook fills через `--body` flag.

### P2.3 — Reviewer assignment (~3ч)

`gh pr edit --add-reviewer @user` based на CODEOWNERS file. Auto-assigns правильного reviewer'а по `docs-change-enforcer` mapping.

### P2.4 — Auto-close orphan branches (~4ч)

Cron job: `git branch -r | grep task/` → если PR closed/merged → delete branch. Также удалять local untracked task/* refs старше 30 дней.

### P2.5 — Cross-PR dependency tracking (~5ч)

Если task X зависит от task Y → PR от X помечается blocked-by:Y. Mergify-style graph. Сейчас не нужно (single-developer).

## P3 — advanced (deferred)

### P3.1 — GitHub App integration

Migrate с `gh` CLI на GitHub App (Probot pattern). Pros: webhook-driven (не нужно polling), audit trail в GH UI. Cons: deployment overhead.

### P3.2 — Branch-per-task with cherry-pick

Вместо ref от current HEAD — cherry-pick task commits в фresh branch от master. Cleaner per-task PR diff. Но cherry-pick может fail на конфликте.

### P3.3 — Mergify migration

Если scale → multi-team, мигрировать на Mergify (merge queue + DSL). Pros: feature parity. Cons: paid SaaS.

### P3.4 — Auto-revert on post-merge CI fail

Если PR auto-merged но post-merge CI failed → automatic revert commit + reopened PR с failure context.
