# 43.1 Пайплайн 1С — обзор и 4-этапная парадигма

> **Глава о пайплайне разработки задач 1С** (анализ → реализация → тестирование). Само тестирование
> (VA BDD, `run-bdd.ps1`, `/write-1c-tests`, `/run-1c-tests`, Stage 4a) описано в
> [главе 17 «Тестирование 1С»](../17_ТЕСТИРОВАНИЕ_1С/17.5_КОМАНДЫ_ПАЙПЛАЙНА.md) — эта глава ссылается на
> неё как на этап 4. Этап 4 несёт **два трека**: BDD (`/write-1c-tests` + `/run-1c-tests`) и **YAxUnit
> unit** (`/write-1c-unit-tests` + `/run-1c-unit-tests`, скилл `yaxunit-unit-testing`,
> [гл. 17.6](../17_ТЕСТИРОВАНИЕ_1С/17.6_НАПИСАНИЕ_YAXUNIT_ТЕСТОВ.md)). Состояние на **2026-07-03**
> (синхронизация с кодом; роадмап
> [260614](../../roadmap/260614_ROADMAP_1C_COMMANDS_4STAGE_ALIGNMENT.md), ADR-017/018/019).
> Как пайплайн соотносится с **каталогом паттернов** и **оркестраторами** (слоистость каталог→пайплайн→оркестратор
> + резолв натяжений T1-T5) — отдельная глава [43.8 Слоистость](43.8_СЛОИСТОСТЬ_ПАТТЕРНЫ_ПАЙПЛАЙН_ОРКЕСТРАТОРЫ.md).

## Что это

Пайплайн работы с задачами 1С — **первоклассный экземпляр домен-агностичного 4-этапного пайплайна**
Планирование → Дизайн → Кодирование → Тестирование (ADR-017, ADR-018). Реализован **двумя режимами**
поверх одних и тех же богатых методик 1С:

- **Гейтованный** (с ревью): `/analyze-1c-task` → [пауза: ревью/правки `ANALYSIS-REPORT.md` + approve] →
  `/implement-1c-task` → `/write-1c-tests` → `/run-1c-tests`.
- **AUTO** (без паузы): `/run-1c-task <вход>` — один оркестратор: analyze → **авто-approve** → implement →
  test за проход.
- **Специализированный вход:** `/fix-sonar-task` (скилл `fix-sonar-task`, ADR-033) — оркестратор remediation
  дефектов SonarQube **через тот же пайплайн** (pull → триаж → `/analyze-1c-task` → `/implement-1c-task` →
  `/run-1c-tests` → re-scan); Sonar-issue никогда не фиксится ad-hoc вне пайплайна.

**Ключевой принцип B′ (ADR-019):** богатые методики 1С — `analyze-1c-task-v2` (5-фазный анализ + Runtime
Trace) и `implement-1c-task` (8-этапная реализация + Live BP-verification) — при приведении к парадигме
**НЕ менялись**. Вся проводка состояния вынесена в хуки (см. [43.3](43.3_МАРШРУТИЗАЦИЯ_ХУКИ_ИНСТРУМЕНТИРОВАНИЕ.md)).

## 4-этапное соответствие

Команды отображаются на generic-этапы, состояние ведётся в `pipeline/<slug>/.pipeline-state.json`
(+ указатель `pipeline/CURRENT`, helper [`shared/pipeline_state.py`](../../../.claude/hooks/shared/pipeline_state.py)).
> **Примечание (1С-задача):** для **1С-задачи** состояние переезжает в **папку задачи**
> (`configuration/.../docs/<task>/`) + реестр `pipeline/_1c_index.json` (relocate-on-artifact);
> generic-путь `pipeline/<slug>/` — для не-1С задач.

| Generic-этап | 1С-команда / методика | Артефакт | Проводка (хук) |
|---|---|---|---|
| **1. Планирование** | `/analyze-1c-task` Фазы 1-3 (+2.5 Trace) | `ANALYSIS-REPORT.md` | preflight авто-заводит pipeline-state (F-1); запись отчёта → этапы 1,2 done (F-1.5) |
| **2. Дизайн** | `/analyze-1c-task` Фазы 4-5 | `ANALYSIS-REPORT.md` | **approve-гейт** перед кодом (F-2) |
| **3. Кодирование** | `/implement-1c-task` | `IMPLEMENTATION-PROGRESS.md` | запись прогресса → этап 3 done (F-1.5) |
| **4. Тестирование** | BDD: `/write-1c-tests` + `/run-1c-tests` · YAxUnit: `/write-1c-unit-tests` + `/run-1c-unit-tests` ([гл. 17](../17_ТЕСТИРОВАНИЕ_1С/17.5_КОМАНДЫ_ПАЙПЛАЙНА.md), [17.6](../17_ТЕСТИРОВАНИЕ_1С/17.6_НАПИСАНИЕ_YAXUNIT_ТЕСТОВ.md)) | `.run-state.json` | все секции passed → этап 4 done (F-1.6) |

## Диаграмма потоков

```
                        задача (ТЗ-папка / JIRA / описание из чата)
                                        │
                   ┌────────────────────┴─────────────────────┐
                   │ из чата → маршрутизация (см. 43.3)         │
                   │ простая→AUTO · средняя→спросить · сложная→гейт
                   └────────────────────┬─────────────────────┘
          ┌──────────────────┐          │          ┌──────────────────────────┐
          │  ГЕЙТОВАННЫЙ      │          │          │   AUTO  (/run-1c-task)    │
          ├──────────────────┤          │          ├──────────────────────────┤
   /analyze-1c-task ──► ANALYSIS-REPORT.md          analyze ─► авто-approve ─►
          │  [ПАУЗА: ревью + approve — гейт G4]          implement ─► test
   /implement-1c-task ─► IMPLEMENTATION-PROGRESS.md  (без паузы на ревью 1-го этапа)
          │                                              │
   /write-1c-tests ─► features/<slug>/*.feature          (делегирует тем же методикам)
   /run-1c-tests   ─► .run-state.json (этап 4 done)
```

## Машина состояний

`pipeline_state.py` (stdlib CLI: `init | done | approve | status | gate`) ведёт
`pipeline/<slug>/.pipeline-state.json` — 4 этапа со статусами (`pending`/`done`) + флаг `approved` на
этапе 2. Slug = JIRA-код (стабилен между analyze и implement); fallback — ASCII-slug первой строки;
пусто/кириллица-без-JIRA → общий слот `1c-task`.

**Промежуток анализ → реализация = approval-гейт (G4).** В гейтованном режиме после `/analyze-1c-task` —
обязательная пауза: ревью и правки `ANALYSIS-REPORT.md`, затем одобрение дизайна
(`pipeline_state.py approve <slug>`). Реализация **хард-блокируется** хуком `pipeline-gate.py`, пока этап 2
не получит `approved`. Это сохраняет прежнюю модель «два этапа с промежутком для ревью», но делает гейт
принудительным. В AUTO-режиме оркестратор `/run-1c-task` ставит approve сам (без паузы).

**Гейт завершения (ADR-037).** При правке/добавлении `.bsl` завершение 1С-задачи **хард-блокируется**, пока
изменённый код не прогнан через SonarQube с чистой дельтой (0 BLOCKER/CRITICAL на изменённых строках) —
обязательная Sonar re-scan петля этапа 4/завершения. Детали — [43.5 Сквозная карта](43.5_СКВОЗНАЯ_КАРТА.md)
(петля завершения) и [43.7 Анализ всей конфигурации](43.7_АНАЛИЗ_ВСЕЙ_КОНФИГУРАЦИИ.md) (статанализ + ADR-033
remediation).
