# 43.5 Сквозная карта: чат → 1С-задача → этапы → завершение (полная цепочка)

> **Полный сквозной разрез жизненного цикла 1С-задачи — от первого сообщения в чате до закрытия
> обязательных петель на `Stop`.** Карта ведёт цепочку без разрывов:
> **§0 ВХОД** (чат → детект «это 1С?» → оценка сложности → выбор режима) → **§0.9 заведение состояния** →
> **§1–§4 4-этапная парадигма** (Планирование → Дизайн → Кодирование → Тестирование) →
> **§5 сквозные системы** → **§6 ЗАВЕРШЕНИЕ** (единый task-completion gate).
> Сводит воедино [43.1](43.1_ОБЗОР_И_ПАРАДИГМА.md) (парадигма), [43.2](43.2_КОМАНДЫ_И_РЕЖИМЫ.md) (команды),
> [43.3](43.3_МАРШРУТИЗАЦИЯ_ХУКИ_ИНСТРУМЕНТИРОВАНИЕ.md) (маршрутизация/хуки),
> [43.4](43.4_СПРАВОЧНИК_ИНСТРУМЕНТОВ.md) (инструменты), [43.6](43.6_АНАТОМИЯ_КОМАНД.md) (анатомия 3 слоёв).
> Каждое звено привязано к функции/хуку с `file:line`. Состояние на **2026-06-17** (механика — ADR-017/018/019,
> роадмап [260614](../../roadmap/260614_ROADMAP_1C_COMMANDS_4STAGE_ALIGNMENT.md)).

## §0. ВХОД: от сообщения в чате до выбора режима

«Нулевой этап» — всё, что происходит **до** первой команды пайплайна. Цель — из произвольного
чат-сообщения получить ответ на три вопроса: **(1) это вообще 1С-задача? (2) какой она сложности?
(3) каким режимом её вести?** Весь код — мост [`pipeline_1c_bridge.py`](../../../.claude/hooks/shared/pipeline_1c_bridge.py)
(best-effort: функции **никогда не кидают**); инъекцию рекомендации делает хук
[`onec-task-input.py`](../../../.claude/hooks/onec-task-input.py).

### 0.1 Триггер — три формы входа

Сообщение из чата приходит в одной из **трёх форм**. Две из них **самоописательны** и сразу знают, что
делать: `/слэш-команда` (опознаётся по ведущему `/`) и путь к существующей папке ТЗ (опознаётся обращением
к файловой системе). **Третья — свободный текст без слэша и без пути** («Доработать проведение документа…») —
самая частая и самая трудная: что это вообще, можно понять **только по содержимому**. Именно она — главный
предмет §0; для неё и существует детектор (§0.3) → оценщик сложности (§0.4) → маршрутизатор (§0.5).

| Форма входа | Что это | Куда уходит |
|---|---|---|
| **Свободный текст** (default) | сообщение без `/` и без пути («Доработать проведение…») | **полная цепочка** `onec-task-input` → `route_1c_task` (§0.2–0.5) |
| **Слэш-команда** | `/analyze-1c-task`, `/run-1c-task`, … | `onec-task-input` делает **early-return**; ведёт preflight команды (§0.9) |
| **Путь к папке ТЗ** | `configuration/<JIRA>/docs/<задача>/` (spec + скриншоты) | как аргумент `/run-1c-task` → `resolve_task_input` (kind=folder) |

> **Асимметрия обработки.** Формы 2–3 — короткий путь: для слэша `onec-task-input` сразу делает `return None`
> ([onec-task-input.py:32](../../../.claude/hooks/onec-task-input.py#L32)) — маршрут ведёт preflight команды;
> путь к папке разбирается уже внутри `/run-1c-task` (`resolve_task_input`, kind=folder). Полную цепочку
> «детект → сложность → режим» проходит **только свободный текст** — остальное в ней просто не нуждается.

### 0.2 Перехват: `onec-task-input.py` (UserPromptSubmit, advisory)

[`OnecTaskInput.execute`](../../../.claude/hooks/onec-task-input.py#L30) на каждое сообщение:

1. **Слэш-команда?** → `detect_slash_command(prompt)` истинно → `return None` (слэш-маршрут ведёт его
   собственный preflight, дублировать рекомендацию не нужно).
   *Простыми словами: вы сами начали с `/команды` — хук молчит и не вмешивается, дальше задачу ведёт preflight этой команды.*
2. Иначе зовёт `route_1c_task(prompt)` и по полю `flow` инъектит **рекомендацию** в `systemMessage`.
   Хук **advisory** — он ничего не блокирует, только подсказывает Claude маршрут. Финальное решение — за Claude.
   *Простыми словами: на обычное сообщение хук тихо прикидывает, не 1С-задача ли это, и если да — подсказывает Claude, каким режимом её вести; навязать ничего не может.*

### 0.3 Детект «это 1С-задача?» — `classify_1c_task`

**Вход — сырая строка сообщения; ни LLM, ни NLP.** Когда сообщение не слэш-команда и не путь к папке (§0.1),
единственный материал для решения — сам текст. [`classify_1c_task`](../../../.claude/hooks/shared/pipeline_1c_bridge.py#L245)
разбирает его **чистыми регэкспами** — детерминированно, < 1 мс, офлайн, воспроизводимо. Почему не моделью:
детект сидит в `UserPromptSubmit`-хуке с таймаутом 5 с на **каждое** сообщение чата — LLM-вызов здесь стоил бы
латентности и токенов на любой ввод (включая не-1С разговор). Цена выбора — словарь приходится **заземлять на
реальные формулировки**: он откалиброван на **~35 реальных ТЗ** `configuration/<JIRA>/docs/` (не выдуман;
[[project-1c-task-input-taxonomy]]), а не на догадку «как люди пишут про 1С». Возврат — `{is_1c, jira, ttype, ask, code}`.

**Формула детекта — четыре независимых пути к `is_1c=True`** (по порядку строк ниже = пути 1/2/3/4;
[pipeline_1c_bridge.py:260](../../../.claude/hooks/shared/pipeline_1c_bridge.py#L260)):

```
is_1c =  JIRA-код в тексте
      ∨  _1C_DEFINITIVE  (гкс_-префикс  ∨  путь configuration/)                  ← жёсткий маркер, без глагола
      ∨  _1C_CODE  (1С/BSL-синтаксис: Менеджер.Член · событие · КонецЕсли · ЕСТЬNULL …)  ← КОД, без глагола
      ∨  ( (_1C_SIGNAL доменный термин  ∨  _1C_STRONG CamelCase/объект.точка)  ∧  _TASK_VERB )
```

Логика **трёхуровневая по «силе» сигнала** (определяющие → код → по-смыслу-связкой):
- **Пути 1–2 — определяющие.** JIRA-код или жёсткий 1С-маркер (`гкс_`-префикс, путь `configuration/`) → 1С
  **сразу**, таск-глагол не требуется: «`GKSTCPLK-2182`» или «`гкс_НаправлениеНаРазгрузку`» — уже однозначно
  задача по конфигурации.
- **Путь 3 — наличие 1С-кода (ключевой признак).** Литеральный 1С/BSL-синтаксис в тексте — **самостоятельный
  сильный сигнал, таск-глагол НЕ требуется**: вызов менеджера (`Документы.X`, `РегистрыСведений.Y.СрезПоследних`),
  событийная сигнатура (`ПередЗаписью`, `ОбработкаПроведения`), закрывающее слово BSL (`КонецПроцедуры`), токен
  запроса (`ЕСТЬNULL`, `СГРУППИРОВАТЬ ПО`), БСП-вызов (`ОбщегоНазначения.`), конструктор (`Новый Структура`). Вставленный
  фрагмент кода ⇒ это 1С — и `confident_1c=True` (маршрут по сложности, не вопрос). Заземление: в реальных
  ТЗ/диалогах/отчётах код встречается массово (285 fenced-блоков в 46 файлах корпуса). Маркеры — `re.U` **без
  `re.I`** (синтаксис 1С в PascalCase; case-insensitive зашумил бы `конецесли`/`выбрать` в обычной речи).
- **Путь 4 — по смыслу, связкой.** Доменное слово (`_1C_SIGNAL`) **или** форменный маркер кода
  (`_1C_STRONG`) засчитывается **только в паре с таск-глаголом** (`_TASK_VERB`). Один термин без действия
  («покажи справочник контрагентов») — НЕ задача, а вопрос; нужна связка «термин + глагол»
  («**добавь** реквизит в **справочник**»).

**Дерево решения по сырому тексту** (порядок проверок = порядок короткого замыкания в коде):

```
                        сырой текст сообщения
                                 │
              есть [A-Z]{2,}-\d+ (JIRA)?  ──да──►  is_1c=TRUE        (путь 1; confident=TRUE)
                                 │ нет
          гкс_ ∨ configuration/  (_1C_DEFINITIVE)?  ──да──►  is_1c=TRUE   (путь 2; confident=TRUE)
                                 │ нет
   1С/BSL-КОД (_1C_CODE: Менеджер.Член · событие · КонецЕсли · ЕСТЬNULL · БСП-вызов)?  ──да──►  is_1c=TRUE  (путь 3; confident=TRUE)
                                 │ нет
      есть таск-глагол  (_TASK_VERB: доработ|исправ|добав|…)?  ──нет──►  is_1c=FALSE → flow=none (молчит)
                                 │ да
   термин (_1C_SIGNAL) ∨ CamelCase/объект.точка (_1C_STRONG)?  ──нет──►  is_1c=FALSE → none
                                 │ да
                           is_1c=TRUE  (путь 4)
                                 │
        был сильный маркер _1C_STRONG (гкс_ / configuration/ / объект.точка / CamelCase)?
                 ├─ да  ──►  confident_1c=TRUE   → маршрут по сложности (auto / ask_flow / gated, §0.5)
                 └─ нет ──►  confident_1c=FALSE  → flow=ask_1c (детект по слабому сигналу — СПРОСИ, §0.5)
```

> **Детект (`is_1c`) и уверенность (`confident_1c`) — разные вопросы из одной строки.** Путь 4 через «голый»
> доменный термин + глагол даёт `is_1c=True`, но `confident_1c=False`: система **не угадывает режим**, а
> спрашивает (§0.5, инвариант безопасности). А путь 3 (**наличие кода**) — сразу `confident_1c=True` (код = твёрдый
> признак 1С). Детект настроен на **высокий recall** (поймать и слабый намёк на 1С); уверенность решает,
> **что с пойманным делать** — прогон или вопрос.

|---|---|---|
| **`_1C_DEFINITIVE`** ([:230](../../../.claude/hooks/shared/pipeline_1c_bridge.py#L230)) | жёсткий маркер → 1С **без глагола** (путь 2) | `гкс_НаправлениеНаРазгрузку`, путь `configuration/260304…/` |

**Тонкости (почему высокий recall не превращается в шум):**
- **`\b`-границы против подстрок.** Термины с риском «утонуть» в чужом слове несут `\b`: `\bформ[аеуы]`
  (не `форм`), `\bдокумент`, `\bотч[её]т`, `\bрегистр`, `\bконстант`, `\bобмен`. Иначе «ин**форм**ация» ложно
  матчила бы `форм`, «доку**мента**ция» — `документ`. Аббревиатуры зажаты с обеих сторон: `\bАРМ`, `\bРМ\b`,
  `\bРС\b`, `\bРН\b` — чтобы «а**рс**енал»/«ка**рм**ан» не приняли за регистр сведений.
- **CamelCase-кириллица строго `re.U`, без `re.I`** ([:296](../../../.claude/hooks/shared/pipeline_1c_bridge.py#L296)).
  Класс `[а-яё][А-ЯЁ][а-яё]` ловит «горб» составного идентификатора (`ПриЗаписи`, `ТабличныйДокумент`). С `re.I`
  регистр игнорировался бы → класс схлопнулся бы в «любые три кириллические буквы подряд» → матчил бы **любое**
  русское слово, и детект стал бы бесполезен.
- **`is_1c=False` → хук молчит.** Ни один путь не сработал → `route_1c_task` отдаёт `flow=none`, и
  [`onec-task-input`](../../../.claude/hooks/onec-task-input.py#L38) делает `return None`: на не-1С-сообщениях
  (RAG/Python/обычный разговор) в чат не уходит **ни строки**. Ложно-положительное в худшем случае деградирует
  в `ask_1c` (вопрос), не в слепой прогон.

**Тип задачи `ttype`** (для prior-контекста и весов сложности):

| `ttype` | Условие в тексте | Смысл |
|---|---|---|
| **T3** | «не учт…» ∨ («тестирован…» ∧ «функционал») | «не учтено» / found-in-testing — **дельта** на прежнюю задачу |
| **T2** | «исправ…» ∧ «ошибк…» | bugfix |
| **T1** | иначе | новое / доработка |

`ask = (jira is None)` — 1С-задача из чата без JIRA-кода требует уточнения «новая / доработка» (протокол V.6, §0.7).

### 0.3.1 Пошаговый разбор: из строки → вердикт (3 трассы)

Та же тройка примеров, что в сводке §0.8, но **по шагам** — как реальный код ведёт сырую строку через
[`classify_1c_task`](../../../.claude/hooks/shared/pipeline_1c_bridge.py#L245) →
[`estimate_effort`](../../../.claude/hooks/shared/pipeline_1c_bridge.py#L355) →
[`route_1c_task`](../../../.claude/hooks/shared/pipeline_1c_bridge.py#L398).

**Трасса A — свободный текст с JIRA:** `GKSTCPLK-2182 Доработать создание Направления на разгрузку…`
1. `_JIRA.search` → `GKSTCPLK-2182` ⇒ путь 1 истинен → **`is_1c=True`** (глагол даже не проверяется — короткое замыкание `or`).
2. `ttype`: нет «не учт» / «исправ…ошибк» → **T1**; `ask = (jira is None) = False`.
3. `confident_1c = bool(jira) =` **`True`** ([:415](../../../.claude/hooks/shared/pipeline_1c_bridge.py#L415)).
4. `estimate_effort`: «доработать» ∈ `modify` (+2) · `ttype_T1` (+1) ⇒ `points = base(1)+2+1 =` **4** → банда **medium**.
5. `route` → confident ∧ medium → **`flow=ask_flow`** → хук спрашивает: AUTO (`/run-1c-task`) или гейт?

**Трасса B — свободный текст БЕЗ JIRA, слабый сигнал:** `Добавить реквизит в справочник контрагентов`
1. JIRA нет; `гкс_`/`configuration/` нет. Глагол «добав» ✓; термины «реквизит», «справочник» ∈ `_1C_SIGNAL` ✓ → путь 3 → **`is_1c=True`**.
2. `ttype=T1`; `ask=True` (нет JIRA).
3. `confident_1c`: JIRA нет; `_1C_STRONG`? «справочник контрагентов» — нет `гкс_`, нет объект.точка, нет CamelCase-горба → **False**.
4. `route` проверяет ¬confident **раньше** сложности: `points` считается (modify +2, T1 +1 = 4 → medium), но **не влияет** — выходит **`flow=ask_1c`**: подтвердить «1С ли», новая/доработка, V.6-папка.

**Трасса C — не-1С:** `Отрефактори search manager на httpx`
1. JIRA нет, `_1C_DEFINITIVE` нет. **`_1C_CODE`**? латиница `search manager`/`httpx` — ни одного 1С-синтаксис-маркера (нет `Менеджер.Член`/события/закрывающего слова). `_TASK_VERB`? «рефактор…» в списке **нет** → глагола нет. `_1C_SIGNAL`/`_1C_STRONG`? терминов и CamelCase-**кириллицы** нет.
2. Все четыре пути ложны → **`is_1c=False`** → **`flow=none`** → [`onec-task-input`](../../../.claude/hooks/onec-task-input.py#L38) `return None` (молчит). RAG-задача идёт своим путём, детектор не вмешивается.

**Трасса D — вставленный 1С-код БЕЗ глагола и БЕЗ `гкс_`** (суть правки 2026-06-17): `РегистрыСведений.СостоянияРегистрации.СрезПоследних(&Дата)`
1. JIRA нет, `гкс_`/`configuration/` нет, таск-глагола из словаря нет. Но **`_1C_CODE`** ловит вызов менеджера `РегистрыСведений.С…` (`Менеджер.Член`) **и** токен запроса `СрезПоследних` → путь 3 → **`is_1c=True`** (глагол НЕ требуется — наличие кода самодостаточно).
2. `code=True` ⇒ **`confident_1c=True`** → маршрут по сложности, не `ask_1c`. Это и есть исправление: фрагмент BSL без «таск-глагола» раньше промахивался (путь 4 требует глагол), теперь ловится путём 3.

> Трасса B — суть инварианта §0.5: доменный термин + глагол дают `is_1c=True`, но без сильного маркера система
> **спрашивает**, а не угадывает режим. Трасса C — обратная сторона: слово «рефакторинг» есть в словаре
> сложности `estimate_effort` (`cross`), но в `_TASK_VERB` глагола «рефактори» нет → путь 3 не активируется, и
> на чисто-английской формулировке детектор корректно молчит (детект и оценка сложности используют **разные**
> словари; gate — детект).

### 0.4 Оценка сложности — `estimate_effort`

[`estimate_effort`](../../../.claude/hooks/shared/pipeline_1c_bridge.py#L355) — **эвристика трудозатрат**
(грубый оценщик, НЕ замена ревью). Веса и пороги — в config
[`_EFFORT_CFG`](../../../.claude/hooks/shared/pipeline_1c_bridge.py#L330) (тюнятся **без правки кода**,
паттерн `a2_signals` из skill-router). Возврат `{complexity, points, signals}`.

| Группа сигналов | Вес | Примеры ключей |
|---|---|---|
| `light` (косметика) | **−2** | опечатк · текст сообщен · наименован · переименов · комментар · подсказк · заголовок · формулировк |
| `modify` | **+2** | доработать · добавить реквизит/колонк/поле/форм · новый реквизит · изменить алгоритм/запрос |
| `heavy_obj` | **+5** | новый/создать документ·справочник·регистр·отчёт·обработк · регистр накоплен/сведен/бухгалтер · план обмена/видов · бизнес-процесс |
| `cross` | **+3** | обмен данны · интеграц · RLS · права доступ · новую роль · подсистем · конвертац · миграц · рефакторинг |
| `multi` | **+2** | несколько · массов · по всем · пакетн · все документ |
| `folder` | **+2** | вход = готовая ТЗ-папка (`is_folder`) |
| `ttype_T1` / `ttype_T3` | **+1** | тип задачи |

**Расчёт:** `points = base(1) + Σ(modify, heavy_obj, cross, multi, folder, ttype)`; затем **банды**:

```
points ≤ 2  → simple        3 ≤ points ≤ 5  → medium        points ≥ 6  → complex
```

**`light` — только downgrade**, не counterweight: применяется лишь при `pos == 0` (нет позитивных
сигналов работы). Иначе имя-атрибута «Комментарий»/«Заголовок» в medium-задаче ложно занижало бы её в simple.

### 0.5 Маршрут — `route_1c_task` → `flow`

[`route_1c_task`](../../../.claude/hooks/shared/pipeline_1c_bridge.py#L398) объединяет детект (0.3) + сложность
(0.4) и выдаёт **режим**. Ключевой предохранитель — `confident_1c`:

```
confident_1c = bool(jira)  ∨  _1C_STRONG.search(prompt)      # есть JIRA ИЛИ сильный 1С-маркер
```

| `flow` | Условие | Рекомендация хука (инъекция в systemMessage) |
|---|---|---|
| **`none`** | не 1С (`is_1c=False`) | молчит (`return None`) |
| **`ask_1c`** | 1С, но `confident_1c=False` (слабый сигнал / нет JIRA, нет сильного маркера) | **ПОДТВЕРДИ:** это 1С? новая или доработка/багфикс? + V.6 (папка) |
| **`auto`** | confident ∧ `simple` | запусти **`/run-1c-task`** (AUTO: analyze→approve→implement→test без паузы) |
| **`ask_flow`** | confident ∧ `medium` | **СПРОСИ:** AUTO (`/run-1c-task`) или гейтованный (`/analyze`→ревью→`/implement`)? |
| **`gated`** | confident ∧ `complex` | гейтованный поток **`/analyze-1c-task`** → ревью ANALYSIS-REPORT → **`/implement-1c-task`** |

**Инвариант безопасности.** Матч без сильного маркера (`гкс_` / `configuration/` / объект.точка /
CamelCase / JIRA) → `confident_1c=False` → `ask_1c`, **не авто-маршрут**. Recall высокий, но ложные
срабатывания **деградируют в вопрос**, не в слепой прогон.

### 0.6 Решение за Claude, сомнение → спросить

> **Правило** (память [[feedback-1c-detection-judgment-mine]]): финальное решение «это 1С» и «каким
> потоком» — **за Claude**; хук = подсказка. При любом сомнении (1С/не-1С, AUTO/гейт) — **спросить
> пользователя**, не угадывать. Эвристика сложности — слабее правила пользователя (хвост-нота инъекции:
> «сомневаешься → СПРОСИ»). Задачи 1С живут в `C:\1С-Framework\configuration` (`<JIRA>/docs/<задача>`) —
> источник prior-контекста и заземление словаря детектора.

### 0.7 V.6 — таксономия входа и дизамбигуация

Вход 1С-задачи разнороден по **2 осям** (память [[project-1c-task-input-taxonomy]]):

- **Источник:** папка ТЗ (`configuration/<JIRA>/docs/` — spec + скриншоты + чат-диалог + история) **ИЛИ** чат.
- **Тип:** **T1** новое · **T2** bugfix · **T3** «не учтено» / found-in-testing.

Хук добавляет к рекомендации точечные V.6-ноты по `ttype`:
- **JIRA есть** → «собери ВСЕ артефакты папки (spec + скриншоты + чат-диалог + история), не один `*ТЗ*.md`».
- **T2** → «Планирование сжато (root-cause + точка фикса), Тестирование критично (регресс)».
- **T3** → «загрузи prior `ANALYSIS-REPORT` + реализацию родителя как контекст (**дельта, НЕ greenfield**);
  проверь prior-PR».
- **standalone из чата** → новая ТЗ-папка `configuration/<JIRA>/docs/<YYMMDD_slug>/` (provisional);
  доработка/T2/T3 → подпапка к родителю + prior-контекст.

### 0.8 Примеры сквозной классификации (как это решается)

| Чат-сообщение | `is_1c` / `ttype` | `confident` | `points` → банда | `flow` → действие |
|---|---|---|---|---|
| `GKSTCPLK-2182 Доработать создание Направления на разгрузку для заблокированных ТС` | ✓ / T1 | ✓ (JIRA) | modify+2, T1+1 = **4** → medium | **`ask_flow`** — спросить AUTO/гейт |
| `Создать новый регистр накопления гкс_УчётРазгрузки и провести документ` | ✓ / T1 | ✓ (`гкс_`) | heavy_obj+5, T1+1 = **7** → complex | **`gated`** — `/analyze`→ревью→`/implement` |
| `Добавить реквизит в справочник контрагентов` | ✓ / T1 | **✗** (нет JIRA/strong) | medium/4 (не влияет) | **`ask_1c`** — `confident_1c=✗` решает раньше сложности → подтвердить + V.6 |
| `Отрефактори search manager на httpx` | ✗ | — | — | **`none`** — молчит (не 1С) |

> Третий пример — суть инварианта 0.5: доменный термин («справочник») + глагол («добавить») дают `is_1c=True`,
> но без сильного маркера система **не угадывает режим**, а спрашивает.

### AUTO — `/run-1c-task` (оркестрация за один проход)

Оркестратор [`run-1c-task`](../../../.claude/skills/run-1c-task/SKILL.md) **делегирует** тем же методикам и
сам ставит approve — без паузы на ревью первого этапа:

```
1.   init pipeline (+ --task-dir для kind=folder)
1.5. recall (unified_search) + внешний анализ (WebSearch Infostart/GitHub)   ← иначе Stop-gate заблокирует
2.   методика analyze-1c-task-v2 (Фазы 1-5)            → ANALYSIS-REPORT.md (этапы 1,2)
2.4. Preflight полноты ТЗ (H6): неполно/противоречиво  → СТОП и вопрос (НЕ авто-approve)
2.5. pipeline_state approve <slug> --by auto           ← авто-approve (обход ревью, метка approved_by=auto)
3.   методика implement-1c-task (Этапы 0-8)            → IMPLEMENTATION-PROGRESS.md (этап 3)
4.   методика va-bdd-testing / /run-1c-tests           → .run-state.json (этап 4)
4.5. capture_pattern после verify PASS                 ← иначе Stop-gate заблокирует
W.   TOOL-RESULTS.json → tool_usage_report.py          → TOOL-USAGE-REPORT.md
```

**Хард-правило «AUTO ≠ игнор блокеров»:** критическая неоднозначность / противоречие в ТЗ / высокий риск на
любом этапе → **СТОП и вопрос пользователю** перед approve. AUTO экономит паузу на рутине, не отменяет
здравый смысл.

## §5. Сквозные системы (поперёк всех этапов)

Четыре системы работают на **каждом** этапе и **принудительны** через свой Stop-enforcer (все с opt-out + graceful):

| Система | Что делает на задаче | Логирование | Оценка эффективности | Enforcer (opt-out) |
|---|---|---|---|---|
| **Память (гл. 27)** | recall (`unified_search`/`search_patterns`) → apply (`apply_pattern`) → capture (`capture_pattern`/`route_and_save`/`.md`) | `hook-invocations` / транскрипт; `learned_patterns`, `skill-learning` pending | `tool-effectiveness` + confidence Beta(7,3) | `onec-task-completion-stop` (единый, `ONEC_TASK_GATE_DISABLE=1`) |
| **Система скиллов (гл. 11)** | каждый этап через профильный `Skill()` (analyze/implement/va-bdd/code-verify) | `skill-accuracy.jsonl`, `session-skills.json`, `skill-router.log` | `skill_system_acceptance.py`, `eval-skill-router.py`, `skill-quality-monitor` | `code-skill-enforcer` (Level A-F) |
| **Внешний анализ** | docs 8.3.27 (первоисточник) + **Infostart** + **GitHub best-practices** через `WebSearch`/`WebFetch` | `knowledge-cache` (`architecture-research/cache/`) после WebSearch | reuse кеша + атрибуция (1c-doc-research) | `onec-task-completion-stop` (тот же gate) |
| **Инструментирование (W)** | TOOL-PLAN → лог (`hook-invocations`) → оценка (`tool_usage_report.py`) → `TOOL-USAGE-REPORT.md` | `data/hook-invocations.jsonl` (`correlationid=run_id`) | `tool_usage_report.py` (err%/avg_ms ✓/⚠/✗) + `tool-effectiveness.jsonl` (`--rollup`) | — (отчёт; в AUTO — шаг оркестрации) |

Плюс **пайплайн-парадигма** сама принудительна: `pipeline-protocol-stop` (ADR-018) — см. §6.

## §6. ЗАВЕРШЕНИЕ: два Stop-гейта (выход цепочки)

На событии `Stop` (Claude хочет завершить ответ) срабатывают **два** hard-гейта **по порядку** — сначала
«была ли работа через пайплайн», затем «закрыты ли обязательные петли 1С-задачи».

### 6.1 `pipeline-protocol-stop` (ADR-018) — пайплайн использован?

[`pipeline-protocol-stop.py`](../../../.claude/hooks/pipeline-protocol-stop.py) блокирует завершение, если в
сессии **были правки** (Write/Edit), но **ни один** `pipeline/<slug>/.pipeline-state.json` не обновлён за сессию.

- **Сигнал «была правка»** — два независимых источника (ИЛИ): (a) `PreToolUse Write/Edit` в
  `hook-invocations.jsonl`; (b) [`_git_session_edit`](../../../.claude/hooks/pipeline-protocol-stop.py#L95) —
  незакоммиченный файл, изменённый за сессию (`git status` + `st_mtime ≥ старт сессии`); закрывает пробел
  инструментов без PreToolUse-матчера (MultiEdit/NotebookEdit).
- **Чистые вопросы без правок** → exempt (нет deadlock). Anti-deadlock: opt-out `PIPELINE_PROTOCOL_DISABLE=1`
  + graceful + выход всегда достижим (завести pipeline и завершить снова).

### 6.2 `onec-task-completion-stop` — единый task-completion gate 1С

[`onec-task-completion-stop.py`](../../../.claude/hooks/onec-task-completion-stop.py) — **ЕДИНЫЙ** gate
1С-задачи (консолидировал `memory-protocol-stop` + `research-protocol-stop` в один хук — убран 3-каскад).
Один проход по транскрипту ([`_collect_signals`](../../../.claude/hooks/onec-task-completion-stop.py#L164),
**фактические `tool_use`**, не raw-text) → консолидированный чеклист всех обязательных петель; блок **один раз**
со всеми `✗` сразу.

**Условие применимости gate** (иначе exempt):
- 1С-пайплайн **обновлён за эту сессию** (`title="1С-задача ("`, `updated_at ≥ старт`) — прямой сигнал; **или**
- **H5 межсессионная:** есть незавершённый 1С-пайплайн из прошлой сессии **И** в этой сессии была 1С-правка
  (`/configuration/` или `.bsl`/`.mdo`/`.os`).

**Критерии «1С-задача завершена корректно»:**

| Петля | Уровень | Детект (tool_use) |
|---|---|---|
| **ПАЙПЛАЙН** | ✓ показан | детектится по самому pipeline-state (раз задача распознана — пайплайн есть) |
| **RECALL** | **hard** | `mcp__memory-orchestrator__unified_search` / `mcp__vector-memory__search_patterns` / `list_patterns` |
| **CAPTURE** | **hard** | `mcp__skill-learning__capture_pattern`/`batch_capture` / `route_and_save` / `Write .md` в `/.claude/.../memory/*.md` |
| **RESEARCH** | **hard** | `WebSearch` / `WebFetch` (внешний анализ: Infostart + GitHub best-practices) |
| **SKILL** (1С-методика) | info | `Skill(analyze-1c-task-v2 / implement-1c-task / va-bdd-testing / run-1c-task / code-verify)` — уже принудит. на `Write` через `code-skill-enforcer` |

Проходит, если `recall ∧ capture ∧ research` истинны. На Stop пишется сводка
[`LOOPS.md`](../../../.claude/hooks/onec-task-completion-stop.py#L201) в папку задачи. Anti-deadlock: opt-out
`ONEC_TASK_GATE_DISABLE=1`; выход достижим (закрыть `✗`-петли и завершить снова); graceful (внутренняя
ошибка → allow).

> **Почему `research` остаётся by-design ослабленным:** засчитывается **любой** `WebSearch`/`WebFetch` —
> проверять релевантность к Infostart/GitHub нельзя без false-block (легитимный 1С-запрос находит Infostart
> без слова «infostart»). Симметрично `recall`.

## Машина состояний (жизненный цикл `.pipeline-state.json`)

```
slug  (JIRA-код → ASCII-slug первой строки → общий слот 1c-task)
  │ ensure_pipeline_1c / init   (title="1С-задача (<cmd>): <slug>")
  ▼
init → 4 этапа pending
  │  ── advance_for_artifact (ANALYSIS-REPORT, H7 ≥200 симв.) ──►  этапы 1,2 done
  │  ── approve (G4, этап 2; AUTO: --by auto) ─────────────────►  этап 2 approved
  │  ── advance_for_artifact (IMPLEMENTATION-PROGRESS) ────────►  этап 3 done
  │  ── advance_test_done (.run-state все passed) ─────────────►  этап 4 done
  ▼
current_stage = 5   (всё готово)
```

**Поля:** `task` (slug), `title`, `created_at`, `updated_at`, `current_stage` (1..5),
`stages[]={n, name, command, artifact, status (pending/done), completed_at}`; этап 2 дополнительно несёт
`{approved, approved_by, approved_at}`. **Где живёт:** 1С-задача — в **папке задачи**
(`configuration/.../docs/<task>/`), реестр slug→папка `pipeline/_1c_index.json`; generic — `pipeline/<slug>/`;
указатель активной — `pipeline/CURRENT`. Ядро —
[`pipeline_state.py`](../../../.claude/hooks/shared/pipeline_state.py) (CLI `init|done|approve|status|gate|resolve`).

## Оценка покрытия и пробелы (честно)

**Хорошо покрыто (✓):**
- **Вход/маршрутизация** — детект (definitive + термин/CamelCase + глагол) + сложность (банды) + инвариант
  «слабый сигнал → вопрос, не авто»; решение режима остаётся за Claude (хук advisory).
- **Анализ/Дизайн** — тройка live-данные (1c-mcp-crud) + код (edt-mcp) + семантика (bsl-semantic-search) +
  первоисточник-RAG (pdf-vector-graph) + опц. Runtime Trace; ревью закрыт approve-гейтом **G4**.
- **Кодирование** — write-path edt-mcp с обязательными циклами (Правило 5/6), статанализ, **Live BP-verification**.
- **Тестирование** — VA BDD + **Stage 4a** pre-check данных + retry/auto-fix + YAxUnit.
- **Завершение** — 2 Stop-гейта: пайплайн использован (ADR-018) + 4 обязательные петли (единый gate).

**Осталось by-design** (фикс = false-block / суть режима — обоснованно):
- **research-relevance** — засчитывается любой `WebSearch`/`WebFetch` (проверка релевантности → неизбежный
  false-block). Симметрично recall.
- **AUTO авто-approve (G4)** — смысл AUTO-режима; компенсируется хард-правилом «AUTO ≠ игнор блокеров» +
  меткой `approved_by=auto`.
- **apply_pattern** — нет tool-сигнала «применил паттерн»; recall+capture обязательны, apply — по релевантности.
- **route/advance best-effort** — классификатор сложности = эвристика; advance по имени файла + relocate —
  graceful best-effort (сомнение → вопрос).
- **W cross-task** — `tool-effectiveness.jsonl` отчётный; авто-петля обучения на нём — non-goal.

**Открытый пункт:**
- **Сквозной прогон `/run-1c-task`** — нужен 1 живой e2e-прогон (приёмка, не код; кодовые риски низкие).

**Инструментарий качества детектора (2026-06-17):** golden-set eval-харнесс
[`scripts/eval_1c_detector.py`](../../../scripts/eval_1c_detector.py) + [`data/1c-detector-ground-truth.json`](../../../data/1c-detector-ground-truth.json)

**калиброванный confidence-скор** (`classify_1c_task.confidence` ∈ {0.0·0.5·0.7·0.9·1.0}; `confident_1c =
confidence≥0.7`, behavior-preserving). Baseline: P=1.000 R=0.927 F1=0.962 (3 FN — descriptive bug-reports
без императивного глагола → recall-gap, цель semantic-fallback). Best practices (semantic-router, hybrid
