# 43.7 Анализ всей конфигурации — инструментарий массового аудита

> **Глава об инструментах анализа на уровне ВСЕЙ конфигурации 1С** (не одной задачи): вес объектов,
> качество кода, граф зависимостей, инвентарь и валидация метаданных, аудит форм/СКД/макетов.
> Питает **этап 1 (Планирование)** пайплайна ([43.1](43.1_ОБЗОР_И_ПАРАДИГМА.md)) — impact-анализ,
> поиск похожего, оценка масштаба — и операционные аудиты вне задач. Состояние на **2026-06-21**
> (ADR-030/031/032, гл. [28_1 Auto-Reports](../28_1_AUTO_REPORTS/), гл. [27 Память](../27_UNIFIED_MEMORY/27.1_Обзор.md)).

## Зачем отдельный слой

[43.4 Справочник инструментов](43.4_СПРАВОЧНИК_ИНСТРУМЕНТОВ.md) перечисляет инструменты **на задачу**.
Здесь — **массовый срез по всей конфигурации**: «какие объекты самые тяжёлые», «где код-смелы», «кто кого
вызывает», «что не валидно», «аудит всех форм/СКД». Это поддерживает Планирование (оценка масштаба,
impact) и регулярные операционные аудиты. Потребность **полностью закрыта существующими инструментами** —
отдельный Java-проект на `mdclasses` не нужен (см. §«Эффективность»).

## 5 слоёв инструментария (обзор)

| Слой | Инструмент | Готов | Что даёт на уровне всей конфигурации |
|---|---|:--:|---|
| 1. Качество кода (CI) | SonarQube BSL + BSL LS | ✅ | code smells / сложность / диагностики по всем `.bsl` |
| 2. Движок разбора метаданных | BSL Language Server (= `mdclasses` внутри) | ✅ | типизированный разбор MDO вкл. формы — **без Java-build** |
| 3. Граф кода | `build_call_graph.py` + `bsl-semantic-search` | ✅ | вызовы / импакт / dead-code / статистика по всем модулям |
| 4. Инвентарь + валидация метаданных | EDT-MCP | ✅ | состав объектов + маркеры валидации по всей конфигурации |
| 5. Поэлементный → массовый (offline) | `cc-1c-skills` (`*-info`) | ✅ | батч-аудит форм/СКД/метаданных по файлам, скриптуемо |

## 1. CI-аудит качества кода — SonarQube BSL

[`sonar-project.properties`](../../../sonar-project.properties) → плагин `sonar-bsl-plugin-community 1.18.1`,
сканирует всю `ИБTransportManagementDevelop/Конфигурация`. Источники добавляются **динамически** через
[`scripts/sonar_sources.py`](../../../scripts/sonar_sources.py) (ADR-021 G19 — новые `configuration/<JIRA>`
авто-подхватываются без правки конфига). Плагин гоняет **bsl-language-server встроенно** (Sensor BSL Core,
verified 2026-06-15) → массовый прогон диагностик/код-смелов по всей конфигурации. Рецепт локального прогона:
память `reference_bsl_sonar_scan_recipe`. Coverage отложен (ADR-020 BLOCKED).

## 2. BSL Language Server — это и есть наш «mdclasses» (без Java-build)

Рабочие JAR'ы в репо: [`tools/bsl-ls/bsl-language-server.jar`](../../../tools/bsl-ls/bsl-language-server.jar),
`tools/multilspy-fork/.../0.22.0/bsl-language-server.jar`, + интеграция Serena.
**Ключевой факт:** BSL LS внутри использует `io.github.1c-syntax:mdclasses` для разбора метаданных
(включая формы). То есть движок `mdclasses` **уже упакован и запускаем** через SonarQube/LSP — отдельный
Java-проект на `mdclasses` писать не нужно (см. §«Эффективность» и [ADR-032](../../../.claude/skills/architecture-research/adr/032-1c-ui-report-tooling-selection.md)).

## 3. Граф кода всей конфигурации

- [`scripts/build_call_graph.py`](../../../scripts/build_call_graph.py) → [`cache/bsl_call_graph.db`](../../../cache/bsl_call_graph.db)
  — **~33k символов / 80k вызовов / 2k модулей** + детектор «висячих» (dangling) вызовов.
- MCP `bsl-semantic-search`: `bsl_call_graph`, `bsl_dead_code`, `bsl_impact_analysis`, `bsl_stats`,
  `bsl_similar`; `bsl-code-search`: `find_callers` / `search_symbols` / `get_module_ast`.
- [`scripts/analyze_run.py --mode graph`](../../../scripts/analyze_run.py) (`--source sqlite|neo4j|qdrant_graph`)
  — авто-отчёт по графу (dangling/orphan), гл. [28_1 Auto-Reports](../28_1_AUTO_REPORTS/). Плюс Neo4j +
  Qdrant `graph_embeddings`.

## 4. Инвентаризация и валидация метаданных (EDT-MCP)

EDT-MCP (см. [skill `edt-mcp`](../../../.claude/skills/edt-mcp/SKILL.md)): `get_problem_summary` /
`get_markers` / `get_project_errors` (маркеры валидации по всей конфигурации), `scan_metadata_index`,
`get_metadata_objects`, `get_objects_by_tags` / `get_tags`. Даёт массовый срез «что есть + что валидно».
Целостность ссылок — `resync_to_disk` (детектор dangling-ссылок в `Configuration.mdo`).

## 5. Поэлементный анализ, который батчится в массовый (cc-1c-skills, offline)

Вендоренный [`external/cc-1c-skills`](../../../external/cc-1c-skills/VENDOR.md) (ADR-031): `form-info`,
`skd-info`, `meta-info`, `role-info`, `cf-info`, `subsystem-info` — per-object, но **скриптуемы**
(Python/PowerShell). `glob` всех `Form.form` → `form-info` в цикле = массовый аудит форм **без Java**.
⚠ паттерн «один процесс на объект» дорог на масштабе (см. §«Эффективность»).

## Виды «веса» объекта и чем считать

«Вес» неоднозначен — разные метрики закрываются разными слоями:

| Метрика «веса» | Чем считать |
|---|---|
| по коду (строки/байты BSL на объект) | прямой обход EDT-src (single-pass скрипт) |
| по сложности кода (cyclomatic, smells) | SonarQube BSL (слой 1) + BSL LS |
| по связности (вызовы / импакт / dead-code) | `bsl_call_graph.db` + `bsl-semantic-search` (слой 3) |
| по структуре метаданных (#реквизитов / ТЧ / форм / движений) | EDT-MCP `get_metadata_details` (батч) / `cc-1c-skills meta-info` / `mdclasses` (типиз. модель) |
| по проблемам (маркеры валидации на объект) | EDT-MCP `get_problem_summary` / `get_markers` (слой 4) |

## Эффективность: single-pass vs per-object (когда нужен mdclasses-напрямую)

Главная ось эффективности — **один проход с загрузкой модели в память** vs **обработка по объекту**
(subprocess/MCP на каждый), а НЕ «Java vs Python». Оценка на нашем конфиге (~2496 объектов):

| Подход | Модель | Время (оценка) |
|---|---|---|
| FS-скрипт (вес по коду) | 1 процесс, без парса XML | ~5–15 с (замерено) |
| single-pass Python по `.mdo` (lxml) | 1 процесс | ~20–60 с |
| `mdclasses` (Java) | 1 JVM-загрузка типиз. модели | ~10–60 с + build |
| SonarQube / BSL LS | 1 проход (внутри = `mdclasses`) | минуты, готовые метрики |
| `cc-1c-skills *-info` батч | **subprocess на каждый объект** | ~6–12 мин |
| EDT-MCP `get_metadata_details` батч | **MCP round-trip на каждый** + EDT | ~10–30 мин |

**Вывод (ADR-032):** `mdclasses` выигрывает в ~10–20× против per-object батчей, но **на нашем масштабе
ничьей с single-pass Python по `.mdo`** — выигрывает паттерн «один проход», не язык. Для метрик кода
SonarQube/BSL LS уже делают полный проход и **внутри = `mdclasses`**, поэтому свой Java-проект дублировал бы
имеющееся. `mdclasses`-напрямую оправдан **только** при регулярном CI-аудите **структуры метаданных** с
**множеством** запросов, где важны корректность типизации и масштаб (ERP 10k+ объектов).

## Когда что применять

| Задача | Инструмент |
|---|---|
| Вес/метрики кода по всей конфигурации | FS single-pass скрипт (мгновенно) + SonarQube (smells) |
| Качество/смелы/сложность в CI | SonarQube BSL (слой 1) |
| Impact/«кто вызывает»/dead-code | `bsl-semantic-search` + `bsl_call_graph.db` (слой 3) |
| Инвентарь + валидность объектов | EDT-MCP `scan_metadata_index` + `get_problem_summary` (слой 4) |
| Массовый аудит форм/СКД (структура) | `cc-1c-skills *-info` батч (слой 5) / EDT-MCP батч |
| Кастомные Java/CI-метрики структуры (масштаб ERP) | `mdclasses` (или его движок в BSL LS) — низкий приоритет |
