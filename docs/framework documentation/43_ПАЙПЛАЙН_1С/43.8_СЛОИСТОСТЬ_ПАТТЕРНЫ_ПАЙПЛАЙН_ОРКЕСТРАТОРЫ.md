# 43.8 Слоистость: каталог паттернов → пайплайн → оркестраторы (резолв T1-T5)

> **Архитектурный слой над главой 43.** Отвечает на вопрос «как пайплайн 1С соотносится с
> каталогом паттернов ([`PATTERNS.md`](../../architecture/PATTERNS.md)) и с оркестраторами
> (`/run-1c-task`, `/fix-sonar-task`)». Решение и роадмап резолва натяжений — [ADR-034](../../../.claude/skills/architecture-research/adr/034-pattern-pipeline-evolution-bestpractices.md);
> объективные факты-первоисточники (Temporal/LangGraph/OPA/SARIF/Anthropic-паттерны) —
> кеш [`pattern-pipeline-orchestration-2026.md`](../../../.claude/skills/architecture-research/cache/pattern-pipeline-orchestration-2026.md).
> Состояние на **2026-06-21** — T1-T5 закрыты (см. §4-5).

## 1. Главная модель — «алфавит → предложение → абзац»

«Система паттернов» и «система пайплайна» — **не два конкурирующих подхода**, а **разные ярусы одной стопки**.
Пайплайн 1С **сам собран из каталожных паттернов**; оркестраторы — ещё один слой паттернов **над** пайплайном.

```
Ярус 3 · МЕТА-ОРКЕСТРАТОР     /fix-sonar-task, /run-1c-task        ← дирижируют задачами
              ▲ использует (has-a)
Ярус 2 · ПОСТРОЙКА            Пайплайн 1С (гл. 43): 4 этапа + state + гейты + хуки   ← собран ИЗ паттернов
              ▲ инстанцирует (composed-of)
Ярус 1 · КАТАЛОГ КИРПИЧЕЙ     PATTERNS.md: Pipeline 1.10 · StateMachine 1.11 · GuardGate 2.6 · StopGate 2.9 …
```

| | Что это | Аналогия Lego |
|---|---|---|
| **Каталог паттернов** (PATTERNS.md) | **набор ТИПОВ кирпичей** — словарь переиспользуемых решений (не работающая система, а справочник) | коробка деталей |
| **Пайплайн 1С** (гл. 43) | готовая **постройка** из этих кирпичей — конкретный рабочий процесс | собранный корабль |
| **Оркестраторы** (`/fix-sonar-task`/`/run-1c-task`) | **новый этаж** над постройкой — паттерн, который её использует | надстройка на корабле |

**Вывод по парадигме:** конфликта подходов нет. Паттерны пассивны (словарь), пайплайн активен (композиция),
оркестратор — мета (дирижёр). Зависимость **ацикличная и однонаправленная: 3 → 2 → 1** (пайплайн не знает про
оркестраторы; паттерны не знают про пайплайн).

## 2. Композиция: из каких паттернов собран пайплайн

Пайплайн 1С буквально **инстанцирует ~9 каталожных паттернов**:

| Механизм гл. 43 | Паттерн каталога |
|---|---|
| 4 этапа Планирование→…→Тест | **1.10 Pipeline** |
| `.pipeline-state.json` + переходы этапов | **1.11 State Machine** |
| `route_1c_task` / `classify_1c_task` (детект 1С, сложность, режим) | **1.9 Router/Classifier** + **2.3 Config-Driven Routing** |
| `_1c_index.json` реестр задач | **1.5 Registry** |
| approval-гейт перед кодом (`pipeline-gate`) | **2.6 Guard Gate** |
| `pipeline-protocol-stop` / `onec-task-completion-stop` | **2.9 Stop Gate** |
| `hook-invocations` инструментирование | **2.12 Invocation Logger** + **2.5 Multi-Level Enforcement** |

`/fix-sonar-task` (PATTERN **2.14 Findings-to-Pipeline Remediation**) — ещё одна композиция: **Orchestrator над Pipeline**.

## 3. Правило сочетания (has-a, не is-a)

Связь паттерна и пайплайна — всегда **«содержит / использует»**, никогда «равны»:

- Пайплайн **СОДЕРЖИТ** паттерны (StateMachine/GuardGate…) — они его внутренние кирпичи (ярус 1 → внутри яруса 2).
- Оркестратор-паттерн **ИСПОЛЬЗУЕТ** пайплайн целиком — пайплайн для него одна крупная деталь (ярус 3 → над ярусом 2).

**Инвариант:** паттерн по отношению к пайплайну может быть либо **КОМПОНЕНТОМ** (внутри), либо **ПОТРЕБИТЕЛЕМ**
(сверху) — но **никогда «соседним кирпичом того же уровня»**. Один и тот же паттерн (например, State Machine)
выступает и материалом стены (внутри пайплайна), и — в другой роли — может надстраиваться сверху.

## 4. Натяжения на стыках (T1-T5) и статус резолва

При строгом разборе всплыли 5 натяжений. Все закрыты в рамках ADR-034 (R1-R8); реализация — §5.

| # | Натяжение | Риск | Резолв (реализован) |
|---|---|---|---|
| **T1** | Батч-оркестратор vs одиночный `CURRENT` (N кластеров = N пайплайнов, указатель один) | «текущий пайплайн» неоднозначен | **R1 child-workflow**: `/fix-sonar-task` гонит кластеры **строго последовательно**, один кластер = полный пайплайн-цикл со СВОИМ состоянием, «один CURRENT за раз» |
| **T2** | Сессионный Stop-gate vs per-кластерный паттерн | кластер №2..N «проезжает» без своего capture | **R2**: per-cluster completion-check (recall/capture для каждого кластера) + идемпотентность |
| **T3** | Два независимых Stop-Gate на одном `Stop` (`pipeline-protocol-stop` + `onec-task-completion-stop`) | ложный дедлок, конкуренция энфорсеров | **R3 gate-as-policy**: composable fail-closed `evaluate_gates` + decision-log; 3 гейта мигрированы; opt-in оркестратор даёт **один консолидированный вердикт** |
| **T4** | Инстанс в каталоге паттернов (2.14 → конкретный скилл) | размывание уровней абстракции | **R8**: 2.14 обобщён до «**Findings-to-Pipeline Remediation**», `/fix-sonar-task` = реализация |
| **T5** | Перегрузка слова «pipeline» (≥3 значения) | когнитивная путаница | **R8 глоссарий** в PATTERNS.md (1.10 / 2.13 / generic-4stage ADR-017 / 1С-пайплайн гл.43) |

**Где композиция изначально чистая** (не натяжения): DRY (оркестраторы делегируют, не дублируют методики);
ацикличная связность 3→2→1 (удаление паттерна не ломает пайплайн); единая философия принуждения (Guard/Stop-Gate);
согласованные мандаты (Sonar-remediation ⊂ «всё через пайплайн» ADR-018 — усиление, не спор).

## 5. Реализация (карта файлов)

### Gate-policy слой (T3) — [ADR-034](../../../.claude/skills/architecture-research/adr/034-pattern-pipeline-evolution-bestpractices.md) R3
- [`shared/gate_policy.py`](../../../.claude/hooks/shared/gate_policy.py) — `evaluate_gates(context, policies)` (fail-closed: любой deny/исключение → общий deny) + `log_decision` → `data/gate-decisions.jsonl` (decision-log/аудит, OPA-вдохновлено).
- [`shared/gate_policies.py`](../../../.claude/hooks/shared/gate_policies.py) — `build_context` (ОДИН проход, переиспует проверенные хелперы живых хуков через importlib) + чистые `pipeline_policy` / `onec_completion_policy`.
- [`gate-orchestrator-stop.py`](../../../.claude/hooks/gate-orchestrator-stop.py) — **opt-in** Stop-хук (`GATE_ORCHESTRATOR_ENABLE=1`, default OFF): заменяет 2 раздельных гейта одним `evaluate_gates`-проходом → один блок со всеми ✗. Старые `pipeline-protocol-stop`/`onec-task-completion-stop` при ON уступают (early-return). Активация — `settings.local.json` (gitignored). Откат — `=0`.
- Регресс: [`tests/unit/test_gate_policy.py`](../../../tests/unit/test_gate_policy.py) (4) + [`tests/unit/test_gate_policies.py`](../../../tests/unit/test_gate_policies.py) (6).

### Child-workflow + per-cluster (T1/T2) — R1/R2
- [`/fix-sonar-task` SKILL](../../../.claude/skills/fix-sonar-task/SKILL.md) Шаг 3: последовательный per-cluster пайплайн-цикл + per-cluster completion + идемпотентность.

### Сопутствующие улучшения findings→remediation (роадмап ADR-034)
- **R4 SARIF**: [`scripts/sonar_issues_pull.py`](../../../scripts/sonar_issues_pull.py) `--format sarif` (SARIF 2.1.0 — универсальный контракт находок).
- **R5 split детерминизм/judgment**: `remediation_class` (deterministic→трансформер / judgment→пайплайн).
- **R6 Clean-as-You-Code**: [`scripts/sonar_quality_gate_check.py`](../../../scripts/sonar_quality_gate_check.py) — hard QG-блокер только на новый код, opt-in `SONAR_QG_HARD=1`.
- **R7 evaluator-optimizer**: re-scan дельта + адверсариальный `code-verify` (Шаг 4 скилла).
- **R8 таксономия**: PATTERN 2.14 «Findings-to-Pipeline» + глоссарий «pipeline».

## 6. Как это работает в одном потоке

`/fix-sonar-task` ловит кластер багов → отдаёт в пайплайн:

```
/fix-sonar-task        ← ярус 3: ПАТТЕРН-оркестратор (Orchestrator + 2.14)
   └─ кладёт задачу на → Пайплайн 1С   ← ярус 2: ПОСТРОЙКА
        ├─ этап-машина  → State Machine   ← ярус 1: паттерн-кирпич (внутри)
        ├─ approval     → Guard Gate      ← ярус 1
        ├─ Stop-проверка→ Stop Gate (→ gate-orchestrator при ENABLE=1) ← ярус 1
        └─ реестр задач → Registry        ← ярус 1
```
