# 43.9.7 Отладка и runtime-трейс

> **Тип:** проверка поведения кода в исполнении — точки останова, стек, переменные, шаги. Глава каталога
> [43.9](43.9_ИНСТРУМЕНТЫ_ПО_ТИПАМ.md). Этапы: **2** (Runtime Trace гипотез, Фаза 2.5), **4** (BP-verify
> правок). Статический «анализ кода без исполнения» — в [43.9.9](43.9.9_СТАТАНАЛИЗ_И_КАЧЕСТВО.md).

## Назначение
Снять реальное поведение алгоритма на живых данных вместо догадок: где исполнение, какие значения, какая ветка
истинна. Режет циклы «угадал → переделал» на алгоритмах с ≥3 ветвлений и на bugfix.

## Инструменты

| Сервер | Ключевые функции | Тип | Подводный камень |
|---|---|---|---|
| **`1c-debug-hmr`** ⭐ | `debug_connect`/`debug_set_breakpoint`/`debug_set_logpoint`/`debug_ping`/`debug_stack_trace`/`debug_variables`/`debug_evaluate`/`debug_step`/`debug_arm_warm_rphosts`/`debug_session_diff` | live RDBG + **hot-reload** + persistent session (`.active.json`) | alias принимается «молча» → verify `rac infobase list` ([[feedback-1c-debug-hmr-alias-validation]]); HTTP-service spawn вне attach ([[feedback-1c-debug-hmr-recycle-scope]]) |
| **`1c-debug`** | те же `debug_*` | live RDBG (без HMR) | пере-attach при правке wrapper'а |
| **`bsl-debugger`** | `bsl_debug_*`, `bsl_execute` | OneScript, **статика** (без живой 1С) | не runtime живой ИБ — для чистой логики |
| **`edt-mcp`** | `debug_launch`/`set_breakpoint`/`wait_for_break`/`step`/`resume`/`evaluate_expression`/`get_variables`/`list_breakpoints`/`terminate_launch` | через EDT launch | поднимает клиент из EDT |

## Выбор среди альтернатив

- **Живой BP-trace 1С** → **`1c-debug-hmr`** (дефолт: переживает правки wrapper'а без потери сессии). Если HMR
  не нужен — `1c-debug`. Порт отладки 1550 — HTTP ([[feedback-1c-debug-url-protocol]]).
- **Отладка в связке с запуском из EDT** → edt `debug_launch` + `debug_*`.
- **Проверка чистой логики без живой 1С** → `bsl-debugger` (OneScript).
- Регистр/halt записи — через `debug_set_logpoint` (синхронный eval), а не BP ([[feedback-register-bp-transient-logpoint]]).

## Когда применять
Дизайн — Фаза 2.5 Runtime Trace (алгоритм с ≥3 runtime-ветвлений: `Тип(Параметр)`, режимы проведения,
`ПолучитьФункциональнуюОпцию`). Тестирование — BP-verify на каждой `[ADDED]`/`[MODIFIED]` точке + regression
diff. Для 1С-задач live BP-trace де-факто обязателен ([[feedback-live-bp-trace-mandatory]]).
