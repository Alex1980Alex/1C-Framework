# 43.2 Команды пайплайна 1С и режимы запуска

> Команды анализа и реализации. Команды тестирования (`/write-1c-tests`, `/run-1c-tests`) — в
> [главе 17](../../7_ПРОВЕРКА/7.4_ТЕСТИРОВАНИЕ_1С/17.5_КОМАНДЫ_ПАЙПЛАЙНА.md). Обзор парадигмы — [43.1](43.1_ОБЗОР_И_ПАРАДИГМА.md).

Каждая команда — тонкая обёртка, делегирующая всю методологию соответствующему skill.

## /analyze-1c-task — анализ задачи (этапы 1-2)

**Файл:** [.claude/commands/analyze-1c-task.md](../../../../.claude/commands/analyze-1c-task.md) ·
**Skill:** [`analyze-1c-task-v2`](../../../../.claude/skills/analyze-1c-task-v2/SKILL.md) (v4.5)

5-фазная методология → `ANALYSIS-REPORT.md`. В Фазу 2 встроен **Refactor gate**: маркер `[REFACTOR]` для
точек модификации, являющихся рефакторингом существующих символов (rename / replace body / safe delete);
для них фиксируются тип символа + ожидаемый backend из
[routing_matrix.yaml](../../../../src/bsl/semantic_search/refactor/routing_matrix.yaml).

**Фаза 2.5 Runtime Trace - ОБЯЗАТЕЛЬНА по умолчанию** (v4.5, ADR-050, мандат 2026-07-13): live BP-trace
через `1c-debug-hmr` проверяет аналитику **на реальных данных** ДО построения плана для КАЖДОЙ задачи с
исполняемым BSL-кодом. `--no-trace` - opt-out; `--trace` - форс для тривиальных алгоритмов; прежний
критерий «≥3 runtime-ветвлений» (`ТекущийПользователь()`, `ПолучитьФункциональнуюОпцию`, `Тип(Параметр)`)
задаёт теперь глубину step-трассировки, не факт запуска. Output: секция «Runtime Trace» (Entry / Stack /
Variables / Branch evaluation / **Discrepancies** static-vs-runtime) + обязательная глава
**§10 «Проверка на реальных данных»** (база, идентификаторы данных, сценарий, результаты; SKIP - только
`--no-trace` / нет исполняемого кода / debug env недоступен, причина фиксируется + `[STATIC-ASSUMPTION]`).
Присутствие §10 контролирует advisory-линтер `scripts/lint_1c_artifacts.py`.

4-этапная парадигма: запись `ANALYSIS-REPORT.md` авто-продвигает этапы 1 (Планирование) и 2 (Дизайн)
через хук `pipeline-1c-advance` (F-1.5). Далее — approve-гейт (см. «Режимы»).

## /implement-1c-task — реализация (этап 3)

**Файл:** [.claude/commands/implement-1c-task.md](../../../../.claude/commands/implement-1c-task.md) ·
**Skill:** [`implement-1c-task`](../../../../.claude/skills/implement-1c-task/SKILL.md) (v2.9)

8-этапный pipeline по готовому `ANALYSIS-REPORT.md`: **EDT-MCP + 1c-mcp-crud + bsl-debugger +
1c-debug-hmr**, обязательные циклы валидации (validate_query → execute_query → write; write →
get_project_errors). Этап 0 Preflight выбирает режим — 5 вариантов (Full / Full (no-BP) / Code-only /
Read-only verify / Read-only research).

- **Этап 3 Decision gate:** `[REFACTOR]`-точки идут через Этап 3R — rename через `bsl_rename_symbol`
  (единственный refactor-tool MCP `bsl-semantic-search`); замена тела метода / safe-delete — через обёртки
  скилла [`bsl-symbol-editing`](../../../../.claude/skills/bsl-symbol-editing/SKILL.md)
  (`read_method_source` → `write_module_source`, EDT-MCP); новый функционал — стандартный EDT-MCP путь.
- **Этап 4 статанализ:** `bsl_lint.py` (предпочтительный) + `bsl_analyze`.
- **Этап 5.x Live BP-verification:** для каждой `[ADDED]`/`[MODIFIED]` точки `debug_set_breakpoint` →
  trigger через `execute_code` → `debug_stack_trace` (assert `lineNo`) → `debug_step(Continue)`. Fallback:
  `break_on_next` → `force_recycle_rphost=True` (только dev). Этап 5.y Regression diff: `debug_session_diff`
  против baseline `<!-- debug_session_id: <UUID> -->` из footer'а IMPLEMENTATION-PROGRESS.md.
- **Этапы 5.x/6 - реальные данные (v2.9, ADR-050, мандат 2026-07-13):** BP-триггеры и тест-план
  исполняются на **реальных данных** живой базы (кандидаты - `execute_query`, параметры - функциями
  вызывающего, Шаблон 7 skill `1c-debug-hmr`; синтетика - только при пустой базе, с пометкой).
  IMPLEMENTATION-PROGRESS.md обязан содержать главу **«Тестирование на реальных данных»** - база,
  таблица данных (объект/идентификатор/дата/сценарий), инструменты, результаты PASS/FAIL; advisory-линт
  `lint_1c_artifacts` через `pipeline-1c-advance`.

**Хард-гейт (G4):** команда хард-блокируется хуком `pipeline-gate.py`, пока дизайн (этап 2) не `approved`
(см. «Режимы»). Запись `IMPLEMENTATION-PROGRESS.md` → этап 3 done (F-1.5).

## /run-1c-task — AUTO-оркестратор (без паузы)

**Файл:** [.claude/commands/run-1c-task.md](../../../../.claude/commands/run-1c-task.md) ·
**Skill:** [`run-1c-task`](../../../../.claude/skills/run-1c-task/SKILL.md)

Прогоняет задачу целиком в AUTO-режиме (analyze → **авто-approve** → implement → test) **без паузы** на
ревью первого этапа. **Делегирует** существующим методикам (`analyze-1c-task-v2`, `implement-1c-task`,
`va-bdd-testing`) и сам ставит `approve` — методики не дублируются и не меняются.

**Вход** (`$ARGUMENTS`) детектится `resolve_task_input` (см. [43.3](43.3_МАРШРУТИЗАЦИЯ_ХУКИ_ИНСТРУМЕНТИРОВАНИЕ.md)):
- **путь к ТЗ-папке** (`configuration/<JIRA>/docs/<задача>`) → kind=folder (источник = spec + скриншоты);
- **JIRA-код** (`GKSTCPLK-XXXX`) → kind=jira;
- **описание из чата** → kind=chat.

**Оркестрация (4 этапа):** init pipeline → методика analyze (Фазы 1-5) → `pipeline_state approve` (без
паузы) → методика implement (Этапы 0-8) → `/run-1c-tests` → TOOL-USAGE-отчёт (W).

**Хард-правило «AUTO ≠ игнор блокеров»:** критическая неоднозначность / противоречие в ТЗ / высокий риск на
любом этапе → **СТОП и вопрос пользователю** перед approve. AUTO экономит паузу на рутине, не отменяет
здравый смысл. Пайплайн dogfood-реализации: `pipeline/impl-1c-run-task/`.

**Bounded AUTO — лимит fix-итераций (P3.2, 2026-07-04):** авто-циклы «фикс → повторный гейт» ограничены.
[`shared/pipeline_state.py`](../../../../.claude/hooks/shared/pipeline_state.py) CLI:
`bump-attempt <slug> <stage>` инкрементирует счётчик попыток этапа и возвращает JSON
`{count, max, exceeded}` (лимит `ONEC_MAX_FIX_ITERATIONS`, default 4); при превышении —
`needs-human <slug> <причина>` фиксирует эскалацию (приоритет p0/p1/p2) и AUTO-прогон останавливается
с вопросом пользователю вместо бесконечного долбления гейта.

## Этап 4 — тесты: BDD + YAxUnit unit (два трека)

Этап 4 состоит из **двух параллельных треков** (оба пишут в общий `.run-state.json`, `advance_test_done`
продвигает этап при всех `passed`):

- **BDD (UI/сценарии)** — `/write-1c-tests` + `/run-1c-tests` (VA BDD, skill `va-bdd-testing`);
  подробно в [главе 17.5](../../7_ПРОВЕРКА/7.4_ТЕСТИРОВАНИЕ_1С/17.5_КОМАНДЫ_ПАЙПЛАЙНА.md).
- **YAxUnit unit (серверная логика)** — `/write-1c-unit-tests` (skill
  [`yaxunit-unit-testing`](../../../../.claude/skills/yaxunit-unit-testing/SKILL.md), пишет тест-модули в
  расширение `src/bsl/exts/UnitTests/`, деплой `LoadConfigFromFiles` + `UpdateDBCfg`) + `/run-1c-unit-tests`
  (прогон через `mcp-onec-test-runner` → JUnit → `chain[].type=yaxunit` → `advance_test_done`);
  методичка [гл. 17.6](../../7_ПРОВЕРКА/7.4_ТЕСТИРОВАНИЕ_1С/17.6_НАПИСАНИЕ_YAXUNIT_ТЕСТОВ.md). Unit-трек покрывает общие
  модули / модули объектов / модули менеджера; UI-логика — по-прежнему BDD.

> **Гейт завершения (ADR-037):** при правке/добавлении `.bsl` завершение 1С-задачи хард-блокируется, пока
> изменённый код не прогнан через SonarQube с чистой дельтой (0 BLOCKER/CRITICAL на изменённых строках) —
> обязательная Sonar re-scan петля. Детали — [43.5](43.5_СКВОЗНАЯ_КАРТА.md) (петля завершения) и
> [43.7](43.7_АНАЛИЗ_ВСЕЙ_КОНФИГУРАЦИИ.md) (статанализ + ADR-033 remediation).

## /fix-sonar-task — remediation дефектов SonarQube через пайплайн

**Файл:** [.claude/commands/fix-sonar-task.md](../../../../.claude/commands/fix-sonar-task.md) ·
**Skill:** [`fix-sonar-task`](../../../../.claude/skills/fix-sonar-task/SKILL.md)

Специализированный оркестратор входа в 1С-пайплайн (ADR-033): дефекты Sonar фиксятся **только через
пайплайн**, никогда ad-hoc. Паттерн: pull + триаж (`scripts/sonar_issues_pull.py`) → per-cluster
`/analyze-1c-task` (ANALYSIS-REPORT) → approve → `/implement-1c-task` → `/run-1c-tests` → re-scan
(`run-sonar-analysis.ps1` → BLOCKER=0). Вход — фильтр выгрузки (`--severities`, `--types`,
`--path-contains`) или пусто (дефолт BLOCKER+CRITICAL кастома).

## Режимы запуска: гейтованный vs AUTO

| Свойство | Гейтованный `/analyze` + `/implement` | AUTO `/run-1c-task` |
|---|---|---|
| Пауза на ревью ANALYSIS-REPORT | **да** (человек правит + approve) | **нет** (авто-approve) |
| Команд | 2 (+ тесты) | 1 (весь цикл) |
| Объём | analyze; затем отдельно implement + тесты | analyze → implement → test за проход |
| approve-гейт G4 | активен (хард-блок `/implement-1c-task`) | оркестратор сам ставит approve |
| Когда | сложная задача, нужен контроль анализа | простая / доверенная, готовая ТЗ-папка |
| Методики 1С | те же (analyze-1c-task-v2 / implement-1c-task) — НЕ дублируются |

**Промежуток анализ → реализация** (гейтованный режим) — это и есть точка ревью: после `/analyze-1c-task`
читаем `ANALYSIS-REPORT.md`, правим при необходимости, затем `pipeline_state.py approve <slug>`. Только
после approve `/implement-1c-task` разблокируется (G4). Какой режим выбрать при задаче из чата — рекомендует
классификатор сложности + маршрутизатор `route_1c_task` ([43.3](43.3_МАРШРУТИЗАЦИЯ_ХУКИ_ИНСТРУМЕНТИРОВАНИЕ.md)):
простая → AUTO, средняя → спросить, сложная → гейтованный. Технически `route_1c_task` возвращает одно из
**6 значений `flow`**: `none` (не 1С — молча), `ask_1c` (слабый 1С-сигнал — подтвердить), `auto` (простая →
`/run-1c-task`), `ask_flow` (средняя — «AUTO или гейт?»), `ask_action` (уверенный 1С без названного действия —
«что сделать?»), `gated` (сложная → `/analyze` + `/implement`). Финальное решение о маршруте — за Claude
(хук advisory), сомнение → спросить.
