## Маршрутизация задачи из чата

Когда 1С-задача приходит **из чата** (не slash-команда), хук
[`onec-task-input.py`](../../../../.claude/hooks/onec-task-input.py) (UserPromptSubmit) определяет 1С/не-1С,
оценивает сложность и **рекомендует режим** (`route_1c_task`):

```
Чат-промпт → route_1c_task():   flow ∈ {none, ask_1c, ask_action, auto, ask_flow, gated}
  ├─ не 1С                        → молчит            (flow=none)
  ├─ 1С, слабый сигнал / без JIRA  → ПОДТВЕРДИ + V.6    (flow=ask_1c)
  ├─ 1С уверенно, действие не названо → СПРОСИ «что сделать?»   (flow=ask_action)
  ├─ 1С, простая                   → /run-1c-task       (flow=auto)
  ├─ 1С, средней сложности         → СПРОСИ: AUTO/гейт   (flow=ask_flow)
  └─ 1С, сложная                   → /analyze → ревью → /implement (flow=gated)
```

Решение маршрута (2026-06-15): **простая→AUTO, средняя→спросить, сложная→гейт**; не-1С / сомнение →
спросить; уверенная 1С без названного действия → спросить «что сделать?» (`ask_action`, C1 2026-06-20).
Хук — **advisory** (инъектит рекомендацию в `systemMessage`, не блокирует).

## Детектор: `classify_1c_task`

**Многоуровневый** каскад (не «двухуровневый»); словарь **заземлён на ~35 реальных задач**
`configuration/<JIRA>/docs/` (не выдуман). Уровни сверху вниз; сильнейший сработавший задаёт `confidence`:

1. **JIRA-код** (`_find_jira`) → `confidence` **1.0** для allowlist-префикса (`GKSTCPLK`, env
   `ONEC_JIRA_PREFIXES`), **0.7** для прочих. **Denylist акронимов** (P0.3): `UTF`/`SHA`/`GPT`/`ISO`/…
   как `[A-Z]{2,}-\d+` больше НЕ считаются JIRA (иначе «UTF-8» ложно давало 1.0 + veto-иммунитет).
2. **Definitive-маркеры** (`_1C_DEFINITIVE`): `гкс_`-префикс, путь `configuration/` → 1С **даже без
   таск-глагола**, `confidence` **0.9**.
3. **Литеральный 1С/BSL-код** (`_1C_CODE`): `Менеджер.Член`, события (`ПередЗаписью`/`ОбработкаПроведения`),
   закрывающие (`КонецЕсли`/`КонецПроцедуры`), токены запроса (`ЕСТЬNULL`/`СГРУППИРОВАТЬ ПО`/`СрезПоследних`),
   БСП (`ОбщегоНазначения.`). Наличие кода = 1С **без таск-глагола**, `confidence` **0.9**
   (case-sensitive `re.U`, без `re.I` — иначе речь зашумила бы).
4. **Доменный термин ∪ CamelCase-объект + таск-глагол** → 1С (`confidence` **0.7** для `_1C_STRONG`,
   **0.5** для голого `_1C_SIGNAL`+глагол):
   - термины (`_1C_SIGNAL`): документ / справочник / регистр / обработка / отчёт / перечисление / константа /
     реквизит / проведение / печатн / форм / движени / подсистем / профил / механизм / обмен / предопредел /
     АРМ / РС / РН / план обмена / план видов / бизнес-процесс / функционал + бизнес-домен (разгрузк /
     приёмк / блокировк / проб / ПЛК / ТТН …);
   - CamelCase-объекты (`_1C_STRONG`): `НаправлениеНаРазгрузку`, `РегистрацияНаПЛК`, объект.точка;
   - глаголы (`_TASK_VERB`): доработать / исправить / добавить / создать / реализовать / настроить /
     заменить / обновить / убрать / устранить / сформировать / вернуть / учесть («не учтено» → T3) и др.
5. **Семантика** (мягкий слой ②): SetFit-гейт (ADR-025, opt-in) с откатом на TF-IDF — только на неуверенных
   входах; промоутит лишь в `ask_1c`, НЕ делает `confident_1c` (инвариант безопасности цел).
   > ⚠ **В ЭТОМ репозитории гейт ВКЛЮЧЁН:** `ONEC_SETFIT_ENABLE=1` задан в `.claude/settings.local.json`
   > (code-default = OFF; локально слой ② работает через SetFit, а не TF-IDF-откат). Проверено аудитом 2026-07-04.
6. **Veto не-1С тех-контекста** (`_NON_1C_CONTEXT`): FastAPI / pytest / эмбеддинг / docker / … перевешивают
   **слабый** сигнал. Veto-иммунны ТОЛЬКО строго-уверенные (`confidence ≥ 0.9` = JIRA-allowlist / код /
   `гкс_`·`configuration`); CamelCase-кириллица (0.7) — **ветируется** (C4).

`\b`-границы против ложных подстрок (информация⊃форм, документация⊃документ). CamelCase-регекс строго
`re.U` **без `re.I`** (иначе hump-класс `[а-яё][А-ЯЁ][а-яё]` матчил бы любые 3 кириллические буквы).

## Классификатор сложности: `estimate_effort`

Эвристика трудозатрат по keyword-сигналам, веса/пороги в config `_EFFORT_CFG` (тюнятся без правки кода):

| Группа | Вес | Примеры |
|---|---|---|
| `light` (косметика) | −2 | опечатка, текст сообщения, переименование, заголовок |
| `modify` | +2 | доработать, добавить реквизит/колонку/форму |
| `develop` | +2 | разработать, реализовать, печатн, механизм, функционал, новую форму |
| `heavy_obj` | +5 | новый документ/справочник/регистр/отчёт/обработка, регистр накопления |
| `cross` | +3 | обмен, интеграция, RLS, права доступа, подсистема, рефакторинг |
| `multi` | +2 | несколько, массово, по всем, пакетно |
| `folder` | +2 | вход = готовая ТЗ-папка |
| `ttype_T1` | +1 | тип задачи «новое» |
| `ttype_T3` | +1 | тип задачи «не учтено» / found-in-testing |

База = 1. Банды: **simple ≤2 · medium 3-5 · complex ≥6**. `light` — только **downgrade** чисто-косметической
задачи (применяется лишь при `pos==0`), НЕ counterweight: иначе имя реквизита «Комментарий»/«Заголовок» в
medium-задаче ложно занижало бы её в simple.

## Инвариант безопасности и правило

**Инвариант:** матч без сильного маркера (`гкс_` / `configuration/` / объект.точка / CamelCase /
литеральный BSL-код / JIRA-allowlist) → `confidence < 0.7` → `confident_1c=False` → `route` отдаёт
`ask_1c` (спросить), **не авто-маршрут**. Recall высокий, но ложные срабатывания **деградируют в вопрос**,
не в слепой прогон. **Важно** (уточнение к диаграмме): сильный маркер — в т.ч. вставленный BSL-фрагмент —
даёт `confidence ≥ 0.7` **даже без JIRA** ⇒ это уже `confident_1c` ⇒ маршрут по сложности (`auto`/…), а
НЕ `ask_1c`. То есть «без JIRA → всегда `ask_1c`» неверно: решает сила маркера, не наличие JIRA.

> **Правило** (память `feedback-1c-detection-judgment-mine`): финальное решение «это 1С» — **за Claude**
> (хук = подсказка); при любом сомнении (1С/не-1С, AUTO/гейт) — **спросить пользователя**, не угадывать.
> Задачи 1С живут в `C:\1С-Framework\configuration` (`<JIRA>/docs/<задача>`) — источник для доп. анализа
> перед доработкой (заземление словаря детектора, prior-контекст для T3).

## Инструментирование инструментов: жизненный цикл (W)

Раздел W роадмапа 260614: на протяжении задачи ведётся учёт, какие инструменты использовались на каждом
этапе, и оценивается их эффективность. Цикл из **4 шагов** — артефакт-план → лог при использовании →
оценка эффективности после → запись в артефакт:

```
1. ПЛАН              2. ЛОГ (авто)               3. ОЦЕНКА (авто)            4. ЗАПИСЬ В АРТЕФАКТ
TOOL-PLAN.md    →    hook-invocations.jsonl   →  tool_usage_report.py     →  TOOL-USAGE-REPORT.md
(инструменты         (каждый вызов:               (агрег по tool:             (+ data/tool-effectiveness.jsonl
 по этапам)           tool / outcome /             calls / errors / err% /     → cross-task --rollup →
                      elapsed_ms /                 avg_ms + вердикт ✓/⚠/✗)      корректировка плана,
                      correlationid=run_id)                                     сигнал в skill-learning)
```

### Шаг 1 — TOOL-PLAN.md (план, в начале/по ходу задачи)
Артефакт в папке задачи: таблица **«этап → инструменты → заметка качества»** — какие инструменты
планируются/использованы на Планировании / Дизайне / Кодировании / Тестировании. Ведётся оператором
(Claude): план + ручные заметки качества (✓ / ⚠ / ✗). **Полный перечень инструментов по этапам** (основа
для копирования в TOOL-PLAN + готовый шаблон) — [43.4 Справочник инструментов](43.4_СПРАВОЧНИК_ИНСТРУМЕНТОВ.md).

### Шаг 2 — лог при использовании (автоматически)
Каждый вызов инструмента авто-логируется в `data/hook-invocations.jsonl` (CloudEvents-конверт): `tool`,
`outcome`, `elapsed_ms`, **`correlationid = run_id`**, `session`. Механизм: MCP-вызовы логирует хук
[`mcp-invocation-logger.py`](../../../../.claude/hooks/mcp-invocation-logger.py) (matcher `mcp__.*`); нативные
тулы (Read/Write/Edit/Bash) — автоматически через `BaseHook.run()` (**P1.2, 2026-07-03:** `BaseHook.run()`
пробрасывает `run_id` через `shared.run_context.get_run_id` → `correlationid = run_id`, поэтому
`tool_usage_report --run-id` видит и нативные тулы; вне slash-команды `run_id` нет → прежний fallback на
`session`).
[`shared/invocation_logger.py`](../../../../.claude/hooks/shared/invocation_logger.py) — это **библиотека**
(`log_invocation`), а НЕ хук. **Отдельный лог не заводится** — переиспользуется существующий (раздел W: не
дублировать). Вручную ничего делать не нужно.

### Шаг 3 — оценка эффективности (автоматически, после использования)
[`scripts/tool_usage_report.py`](../../../../scripts/tool_usage_report.py) `--run-id <id>` (или `--session`)
читает лог по `correlationid==run_id`, агрегирует **по инструменту**: `calls`, `errors`
(`outcome=="error"` или поле `error`), `err%`, `avg_ms`. Вердикт качества **выводится автоматически из
err%**: `✗` при err% ≥ 30, `⚠` при err% > 0, `✓` при 0 — плюс слот `_заметка_` для ручной оценки глубже метрик.

### Шаг 4 — запись в артефакт
- **`TOOL-USAGE-REPORT.md`** в папке задачи — **группированный** отчёт: чеклист **обязательных петель**
  (✓/✗ Память / Скилы / Анализ конфигурации / Внешний анализ) + секции **по категориям** (`classify_tool`:
  memory / skills / config / research / impl / testing / infra), каждая привязана к **artifact/этапу**
  (config+research→ANALYSIS-REPORT, impl→IMPLEMENTATION-PROGRESS, testing→.run-state.json, память/скилы/infra→
  сквозные) + **блок на инструмент**: метрики (`calls/errors/err%/avg_ms/quality`) + **назначение** +
  **результат**. Метрики — из лога; **результат** курируется (лог его не содержит) в сайдкаре
  **`TOOL-RESULTS.json`** (`{tool: саммари-результата}`, авто-подхват из папки задачи или `--results <json>`).
  Путь отчёта резолвится через **реестр** (`--slug <slug>` → `pipeline_state.state_dir(slug)`) — единый источник,
  как `.pipeline-state.json`/`LOOPS.md` (все файлы задачи в одной папке). `--task-dir <D>` — явный override; без
  обоих — авто по текущему зарегистрированному 1С-пайплайну (`CURRENT`), иначе stdout.
- **`data/tool-effectiveness.jsonl`** (append, gitignored runtime store) — per-tool строки с ключом
  `run_id` для **cross-task** профиля. **Отчётный артефакт (H1, честно):** единственный потребитель —
  `tool_usage_report.py --rollup` (агрегат для ручной корректировки планов следующих задач); автоматического
  обучающего контура на нём НЕТ (skill-learning его не читает) — «замыкание на обучение» здесь не заявляется.

В AUTO-режиме `/run-1c-task` запуск отчёта (шаг 3-4) — часть оркестрации; в гейтованном — запускает оператор.

## Вход задачи: таксономия (V.6)

Вход 1С-задачи разнороден по 2 осям (память `project-1c-task-input-taxonomy`):

- **Источник:** папка ТЗ (`configuration/<JIRA>/docs/` — spec + скриншоты + чат-диалог + история) ИЛИ чат.
- **Тип:** **T1** новое / **T2** bugfix / **T3** «не учтено» / found-in-testing (дельта на прежнюю задачу —
  грузить prior-контекст + проверять prior-PR).

**Протокол дизамбигуации чат-входа (V.6)** инъектится `onec-task-input.py`: при 1С-задаче без явного типа —
авто-детект родителя; не нашёл / не сказано «доработка» → **обязательно спросить** new-vs-доработка (не
угадывать). Standalone из чата → новая ТЗ-папка `configuration/<JIRA>/docs/<YYMMDD_slug>/` (provisional);
доработка / T2 / T3 → подпапка к родителю + prior-контекст.
