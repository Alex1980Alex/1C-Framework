# 43.5 Сквозная карта: чат → 1С-задача → этапы → завершение (полная цепочка)

> **Полный сквозной разрез жизненного цикла 1С-задачи — от первого сообщения в чате до закрытия
> обязательных петель на `Stop`.** Карта ведёт цепочку без разрывов:
> **§0 ВХОД** (чат → детект «это 1С?» → оценка сложности → выбор режима) → **§0.9 заведение состояния** →
> **§0.10 stateless-детектор vs непрерывность задачи** (почему follow-up-промты не переключают алгоритм) →
> **§1–§4 4-этапная парадигма** (Планирование → Дизайн → Кодирование → Тестирование) →
> **§5 сквозные системы** → **§6 ЗАВЕРШЕНИЕ** (единый task-completion gate).
> Сводит воедино [43.1](43.1_ОБЗОР_И_ПАРАДИГМА.md) (парадигма), [43.2](43.2_КОМАНДЫ_И_РЕЖИМЫ.md) (команды),
> [43.3](43.3_МАРШРУТИЗАЦИЯ_ХУКИ_ИНСТРУМЕНТИРОВАНИЕ.md) (маршрутизация/хуки),
> [43.4](43.4_СПРАВОЧНИК_ИНСТРУМЕНТОВ.md) (инструменты), [43.6](43.6_АНАТОМИЯ_КОМАНД.md) (анатомия 3 слоёв).
> Каждое звено привязано к функции/хуку. Состояние на **2026-07-03** (синхронизировано с кодом: ADR-041
> SDD-мост, Д-1/P0.3 JIRA-denylist, P1.1/P1.3; механика — ADR-017/018/019/041,
> роадмап [260614](../../../roadmap/260614_ROADMAP_1C_COMMANDS_4STAGE_ALIGNMENT.md)).

## §0. ВХОД: от сообщения в чате до выбора режима

> 📂 **Поблочный разбор детектор-каскада** (схема + подробно + кратко + реальный пример на КАЖДЫЙ блок) —
> живёт в шести отдельных главах, ниже только обзорная навигация + факты, которых там нет.

«Нулевой этап» — всё, что происходит **до** первой команды пайплайна. Цель — из произвольного
чат-сообщения получить ответ на три вопроса: **(1) это вообще 1С-задача? (2) какой она сложности?
(3) каким режимом её вести?** Весь код — мост [`pipeline_1c_bridge.py`](../../../../.claude/hooks/shared/pipeline_1c_bridge.py)
(best-effort: функции **никогда не кидают**); инъекцию рекомендации делает хук
[`onec-task-input.py`](../../../../.claude/hooks/onec-task-input.py). Разбор ведётся **только для
свободного текста** без `/` и без пути к папке ТЗ — две другие формы входа самоописательны
(слэш-команда → её собственный preflight; путь к папке → аргумент `/run-1c-task`, §0.9).

### Каскад: 6 блоков

```
ВХОД → ① ПОИСК ПО ШАБЛОНАМ (regex) → РАЗВИЛКА (confidence ≥ 0.7?) → ② ДОСМОТР ПО СМЫСЛУ (SetFit/TF-IDF)
     → ③ ОЦЕНКА СЛОЖНОСТИ (estimate_effort) → РЕЖИМ (flow)
```

| Блок | Глава | Что делает (одна строка) |
|---|---|---|
| **ВХОД** | [43.5.1 ВХОД](43.5.1_ВХОД.md) | 3 формы входа; перехват `onec-task-input.py` (UserPromptSubmit, advisory, 5s) |
| **① ПОИСК ПО ШАБЛОНАМ** | [43.5.2](43.5.2_ПОИСК_ПО_ШАБЛОНАМ.md) | `classify_1c_task` — 4 regex-пути к `is_1c` (JIRA / `_1C_DEFINITIVE` / `_1C_CODE` / термин+глагол), <1мс офлайн |
| **РАЗВИЛКА** | [43.5.3](43.5.3_РАЗВИЛКА.md) | `confident_1c = confidence ≥ 0.7`? да → сразу к сложности; нет → семантический досмотр |
| **② ДОСМОТР ПО СМЫСЛУ** | [43.5.4](43.5.4_ДОСМОТР_ПО_СМЫСЛУ.md) | SetFit-гейт (opt-in, в этом репо ВКЛ) → откат TF-IDF; мягкий сигнал → максимум `ask_1c`; + veto НЕ-1С тех-контекста |
| **③ ОЦЕНКА СЛОЖНОСТИ** | [43.5.5](43.5.5_ОЦЕНКА_СЛОЖНОСТИ.md) | `estimate_effort` — веса сигналов → `points` → банда simple/medium/complex |
| **РЕЖИМ** | [43.5.6](43.5.6_РЕЖИМ.md) | `route_1c_task` → `flow ∈ {none, ask_1c, auto, ask_flow, ask_action, gated}` |

**Инвариант безопасности** (сквозной для всего каскада, [[feedback-1c-detection-judgment-mine]]): матч без
сильного маркера (`гкс_` / `configuration/` / объект.точка / CamelCase / JIRA) → `confident_1c=False` →
`ask_1c`, **не авто-маршрут**. Recall высокий, но ложные срабатывания **деградируют в вопрос**, не в слепой
прогон. Финальное решение «это 1С / каким потоком» — всегда **за Claude**; хук — только подсказка
(`systemMessage`), при сомнении — спросить пользователя.

### V.6 — таксономия входа и дизамбигуация (детали НЕ в 43.5.x, только здесь)

Вход 1С-задачи разнороден по **2 осям** (память [[project-1c-task-input-taxonomy]]):

- **Источник:** папка ТЗ (`configuration/<JIRA>/docs/` — spec + скриншоты + чат-диалог + история) **ИЛИ** чат.
- **Тип:** **T1** новое · **T2** bugfix · **T3** «не учтено» / found-in-testing.

Хук добавляет к рекомендации точечные V.6-ноты по `ttype`:
- **JIRA есть** → «собери ВСЕ артефакты папки (spec + скриншоты + чат-диалог + история), не один `*ТЗ*.md`».
- **T2** → «Планирование сжато (root-cause + точка фикса), Тестирование критично (регресс)».
- **T3** → «загрузи prior `ANALYSIS-REPORT` + реализацию родителя как контекст (**дельта, НЕ greenfield**);
  проверь prior-PR».
- **standalone из чата** → новая ТЗ-папка `configuration/<JIRA>/docs/<YYMMDD_slug>/` (provisional);
  доработка/T2/T3 → подпапка к родителю + prior-контекст.

> Полный пошаговый разбор трасс (строка → вердикт), словари сигналов, дерево решений и таблица примеров —
> в главах [43.5.1](43.5.1_ВХОД.md)–[43.5.6](43.5.6_РЕЖИМ.md) (реальный пример на каждый блок).

## §0.9 Заведение состояния пайплайна

После выбора режима (или сразу при слэш-команде) состояние задачи материализуется в
`pipeline/<slug>/.pipeline-state.json`. Это делает **preflight-хук** команды через
[`ensure_pipeline_1c`](../../../../.claude/hooks/shared/pipeline_1c_bridge.py) (ADR-019 F-1):

| Шаг | Функция / файл | Результат |
|---|---|---|
| **slug** | [`derive_slug` @ pipeline_1c_bridge.py](../../../../.claude/hooks/shared/pipeline_1c_bridge.py) | JIRA-код приоритетно (стабилен analyze↔implement); иначе ASCII-slug первой строки; пусто/кириллица-без-JIRA → общий слот `1c-task` |
| **slug активного 1С** | [`resolve_active_1c_slug` @ pipeline_1c_bridge.py](../../../../.claude/hooks/shared/pipeline_1c_bridge.py) | **C2/C3 (2026-06-20):** единый резолвер — JIRA-код в промпте → иначе указатель `CURRENT`, если это 1С-пайплайн. Так `/implement` цепляется к пайплайну `/analyze` для НЕ-JIRA задач; общий источник slug для G4 (`gate_1c_implement`) и `ensure_pipeline_1c` |
| **вход `/run-1c-task`** | [`resolve_task_input`](../../../../.claude/hooks/shared/pipeline_1c_bridge.py) | `{kind: folder\|jira\|chat, slug, folder}` — приоритет: существующая папка > JIRA > описание |
| **init** | `ensure_pipeline_1c` → `pipeline_state.init_task` | идемпотентно: 4 этапа `pending`; `title="1С-задача (<command>): <slug>"` — **единый маркер** [`is_1c_task_title`](../../../../.claude/hooks/shared/pipeline_1c_bridge.py) |
| **relocate-on-artifact** | `pipeline-1c-advance` при первом артефакте | состояние **переезжает в папку задачи** (`configuration/.../docs/<task>/`), чтобы state и артефакты жили рядом; реестр slug→папка — `pipeline/_1c_index.json` |

Маркер `title="1С-задача ("` критичен: по нему **все Stop-хуки** отличают реальную 1С-задачу от
framework-dev пайплайнов (и от «1С-задача из чата: …» — предикат строго `startswith("1С-задача (")`).

## §0.10 Stateless-детектор vs непрерывность задачи (почему follow-up-промты не переключают алгоритм)

> **Вопрос, который возникает естественно.** §0 показал: детект «это 1С?» висит на `UserPromptSubmit` и
> срабатывает на **каждом** сообщении (УРОВЕНЬ 1 хук-архитектуры). Но если задача уже идёт и мы обсуждаем её
> десятым сообщением — детектор ведь снова отрабатывает на **каждую** реплику. **Не сбивает ли это активный
> алгоритм задачи? Не происходит ли «переподключение» на маршрутизацию?** Ответ — нет, и не потому, что
> детект «умный», а потому, что детектор и алгоритм задачи — **два разных слоя**, и у детектора **нет
> полномочий что-либо переключать**.

### 0.10.1 Два слоя, которые нельзя путать

```
┌─ СЛОЙ 1 · ДЕТЕКТОР ВХОДА  (onec-task-input.py · УРОВЕНЬ 1 UserPromptSubmit) ──┐
│ • Stateless. Срабатывает на КАЖДОМ промте.                                  │
│ • Классифицирует ТОЛЬКО текст текущего промта, в изоляции.                  │
│ • НЕ знает, что «мы уже в задаче». НЕ читает .pipeline-state.json.          │
│ • Advisory: максимум инъектит подсказку в systemMessage.                    │
│   НЕ блокирует, НЕ переключает, НЕ переподключает. Власти switch'ить — НЕТ.  │
└──────────────────────────────────────────────────────────────────────────────┘
┌─ СЛОЙ 2 · НЕПРЕРЫВНОСТЬ ЗАДАЧИ  (state machine) ─────────────────────────────┐
│ • pipeline/<slug>/.pipeline-state.json  — этапы 1..4 + approve (§0.9)        │
│ • .run-state.json  — прогон тестов (этап 4)                                  │
│ • разговорный контекст Claude — «я веду эту задачу»                          │
│ • Keyed на ЗАДАЧУ (slug). Двигается ВПЕРЁД артефактами, НЕ                   │
│   переинициализируется новым промтом.                                        │
└──────────────────────────────────────────────────────────────────────────────┘
```

«Алгоритм выполнения задачи» живёт целиком в **Слое 2** (§0.9 + «Машина состояний» ниже). Детектор из Слоя 1
(каскад §0 / 43.5.1–43.5.6) его не касается — он лишь рекомендует **точку входа** на самом первом распознавании.

### 0.10.2 Почему повторный детект ≠ переключение

Детект действительно **перезапускается на каждом промте** (он stateless — [43.5.1](43.5.1_ВХОД.md)). Но «перезапуск проверки» ≠
«переключение алгоритма», по трём причинам:

1. **Детектору нечем переключать.** [`OnecTaskInput.execute`](../../../../.claude/hooks/onec-task-input.py)
   возвращает в лучшем случае `HookOutput().system_message(...)` — строку-совет. Он не вызывает слэш-команд, не
   трогает `.pipeline-state.json`, не прерывает. Контракт — `advisory`
   ([onec-task-input.py:12](../../../../.claude/hooks/onec-task-input.py)); как УРОВЕНЬ 1 он в принципе не умеет
   блокировать (только `additionalContext`).
2. **Состояние задачи не сбрасывается промтом.** `.pipeline-state.json` keyed на `slug` и двигается **только
   вперёд** артефактами ([`advance_for_artifact`](../../../../.claude/hooks/shared/pipeline_1c_bridge.py)), а не
   текстом реплики. Новое сообщение этапы не переинициализирует.
3. **Решение «продолжение / новое» — за Claude, не за хуком** ([[feedback-1c-detection-judgment-mine]]).
   Хук сознательно не пытается угадать «мы всё ещё в задаче?» — это отдано разговорному контексту Claude.

### 0.10.3 Что реально происходит на follow-up-промте активной задачи

| Follow-up внутри активной задачи | Слой 1 (детектор) | Слой 2 (алгоритм) |
|---|---|---|
| `/implement-1c-task`, `/run-1c-tests` | `return None` ([:32](../../../../.claude/hooks/onec-task-input.py)) — молчит | preflight команды двигает этап (§0.9) |
| «да, давай дальше» / «поправь имя реквизита» | переклассифицирует → `none`/слабый → молчит или слабый совет | этап на месте, Claude продолжает по контексту |
| «а добавь ещё проверку склада» (выглядит как новая под-задача) | может снова предложить маршрут ([43.5.6](43.5.6_РЕЖИМ.md)) | **судья — Claude:** дельта текущей задачи, а не рестарт |
| записан артефакт (`Write` `ANALYSIS-REPORT`/`IMPLEMENTATION-PROGRESS`) | — (это PostToolUse, не детектор) | [`pipeline-1c-advance`](../../../../.claude/hooks/pipeline-1c-advance.py) двигает этап **вперёд** |

### 0.10.4 Единственная реальная развилка

Так как детектор stateless, **если** follow-up сильно похож на **новую** 1С-задачу, хук снова кинет
рекомендацию маршрута ([43.5.6](43.5.6_РЕЖИМ.md)). Распознать «это продолжение текущей задачи vs новая задача» — **сознательно
отдано Claude** ([[feedback-1c-detection-judgment-mine]]), а не зашито в хук: дешевле и надёжнее переложить редкое суждение на контекст, чем
строить в stateless-хуке модель «активной сессии». Завершение при этом всё равно охраняет отдельный Stop-гейт
[`onec-task-completion-stop`](../../../../.claude/hooks/onec-task-completion-stop.py) (§6.2) — он смотрит на
pipeline-state и транскрипт, а **не** на повторный детект входа.

> **Суть.** Тот, кто срабатывает на каждый промт (детектор), не имеет права переключать; тот, кто ведёт
> алгоритм (state machine на `slug`), не слушает повторный детект. Поэтому «переподключения» нет **by design** —
> это разделение слоёв, а не сообразительность детекта.

### AUTO — `/run-1c-task` (оркестрация за один проход)

Оркестратор [`run-1c-task`](../../../../.claude/skills/run-1c-task/SKILL.md) **делегирует** тем же методикам и
сам ставит approve — без паузы на ревью первого этапа:

```
1.   init pipeline (+ --task-dir для kind=folder)
1.5. recall (unified_search) + внешний анализ (onec_search.py Infostart / ecosystem_scan.py GitHub)  ← иначе Stop-gate заблокирует
2.   методика analyze-1c-task-v2 (Фазы 1-5)            → ANALYSIS-REPORT.md (этапы 1,2)
2.4. Preflight полноты ТЗ (H6): неполно/противоречиво  → СТОП и вопрос (НЕ авто-approve)
2.5. pipeline_state approve <slug> --by auto           ← авто-approve (обход ревью, метка approved_by=auto)
3.   методика implement-1c-task (Этапы 0-8)            → IMPLEMENTATION-PROGRESS.md (этап 3)
4.   методика va-bdd-testing / /run-1c-tests           → .run-state.json (этап 4)
4.5. capture_pattern после verify PASS                 ← иначе Stop-gate заблокирует
W.   TOOL-RESULTS.json → tool_usage_report.py          → TOOL-USAGE-REPORT.md
```

**Хард-правило «AUTO ≠ игнор блокеров»:** критическая неоднозначность / противоречие в ТЗ / высокий риск на
любом этапе → **СТОП и вопрос пользователю** перед approve. AUTO экономит паузу на рутине, не отменяет
здравый смысл.

## §6. ЗАВЕРШЕНИЕ: два Stop-гейта (выход цепочки)

На событии `Stop` (Claude хочет завершить ответ) срабатывают **два** hard-гейта **по порядку** — сначала
«была ли работа через пайплайн», затем «закрыты ли обязательные петли 1С-задачи».

### 6.1 `pipeline-protocol-stop` (ADR-018) — пайплайн использован?

[`pipeline-protocol-stop.py`](../../../../.claude/hooks/pipeline-protocol-stop.py) блокирует завершение, если в
сессии **были правки** (Write/Edit), но **ни один** `pipeline/<slug>/.pipeline-state.json` не обновлён за сессию.

- **Сигнал «была правка»** — два независимых источника (ИЛИ): (a) `PreToolUse Write/Edit` в
  `hook-invocations.jsonl`; (b) [`_git_session_edit`](../../../../.claude/hooks/pipeline-protocol-stop.py) —
  незакоммиченный файл, изменённый за сессию (`git status` + `st_mtime ≥ старт сессии`); закрывает пробел
  инструментов без PreToolUse-матчера (MultiEdit/NotebookEdit).
- **Чистые вопросы без правок** → exempt (нет deadlock). Anti-deadlock: opt-out `PIPELINE_PROTOCOL_DISABLE=1`
  + graceful + выход всегда достижим (завести pipeline и завершить снова).

### 6.2 `onec-task-completion-stop` — единый task-completion gate 1С

[`onec-task-completion-stop.py`](../../../../.claude/hooks/onec-task-completion-stop.py) — **ЕДИНЫЙ** gate
1С-задачи (консолидировал `memory-protocol-stop` + `research-protocol-stop` в один хук — убран 3-каскад).
Один проход по транскрипту ([`_collect_signals`](../../../../.claude/hooks/onec-task-completion-stop.py),
**фактические `tool_use`**, не raw-text) → консолидированный чеклист всех обязательных петель; блок **один раз**
со всеми `✗` сразу.

**Условие применимости gate** (иначе exempt):
- 1С-пайплайн **обновлён за эту сессию** (`title="1С-задача ("`, `updated_at ≥ старт`) — прямой сигнал; **или**
- **H5 межсессионная:** есть незавершённый 1С-пайплайн из прошлой сессии **И** в этой сессии была 1С-правка
  (`/configuration/` или `.bsl`/`.mdo`/`.os`). P1.7 (2026-07-03): H5-кандидаты **age-bound** (env
  `ONEC_INCOMPLETE_MAX_AGE_DAYS`, default 14 — давно брошенный пайплайн не «оживает» на чужой сессии) +
  tie-break на самый свежий `updated_at`.

**Критерии «1С-задача завершена корректно»:**

| Петля | Уровень | Детект (tool_use) |
|---|---|---|
| **ПАЙПЛАЙН** | ✓ показан | детектится по самому pipeline-state (раз задача распознана — пайплайн есть) |
| **RECALL** | **hard** | `mcp__memory-orchestrator__unified_search` / `mcp__vector-memory__search_patterns` / `list_patterns` |
| **CAPTURE** | **hard** | `mcp__skill-learning__capture_pattern`/`batch_capture` / `route_and_save` / `Write .md` в `/.claude/.../memory/*.md` |
| **RESEARCH** | **hard** | `WebSearch`/`WebFetch` ИЛИ Bash-вызов `scripts/ecosystem_scan.py`/`onec_search.py`/`its_fetch.py`/`cc_docs_search.py` (P0.4 — канонический внешний анализ через скрипты тоже засчитывается, иначе следование энфорсеру ADR-039 не удовлетворяло бы петлю) |
| **SONAR** re-scan | **hard** (при `config_edit`) | изменённый/добавленный `.bsl` прогнан через SonarQube — дельта **0 BLOCKER/CRITICAL на изменённых строках** (`mode=changed-lines` с 2026-07-03: пересечение issue-строк с `git diff -w`; сервер-независимый CaYC — вырожденный new-code baseline детектится и не гейтит; issues per-file → project-wide fallback) ([ADR-037](../../../../.claude/skills/architecture-research/adr/037-mandatory-sonar-rescan-changed-1c-code.md); контракт `shared.sonar_rescan_state` [`changed_line_ranges`], verify `scripts/sonar_rescan_verify.py`); default-ON; Sonar-down→skip→ok; opt-out `ONEC_SONAR_GATE_DISABLE=1` |
| **SKILL** (1С-методика) | info | `Skill(analyze-1c-task-v2 / implement-1c-task / va-bdd-testing / run-1c-task / code-verify)` — уже принудит. на `Write` через `code-skill-enforcer` |
| **T1 impact / BP-trace** | advisory (ADR-035 Ф1, **не блок**) | `mcp__bsl-semantic-search__bsl_impact_analysis` (перед правкой экспортного метода) · `mcp__1c-debug`/`-hmr__*` BP-trace (содержательные `set_breakpoint`/`stack_trace`/`variables`/`evaluate`/`step`/`logpoint`, НЕ connection-проверки `ping`/`health`/`targets`) |
| **T2 reference-search** | advisory (ADR-035 Ф1, **не блок**) | `mcp__bsl-semantic-search__bsl_search`/`bsl_hybrid_search`/`bsl_similar` (поиск эталона на Планировании) |

Проходит, если `recall ∧ capture ∧ research` (и `sonar` re-scan при `config_edit`) истинны. На Stop пишется сводка
[`LOOPS.md`](../../../../.claude/hooks/onec-task-completion-stop.py) в папку задачи. Anti-deadlock: opt-out
`ONEC_TASK_GATE_DISABLE=1`; выход достижим (закрыть `✗`-петли и завершить снова); graceful (внутренняя
ошибка → allow).

> **Advisory-слой T1-T2 (ADR-035 Фаза 1, 2026-06-22):** high-leverage инструменты (T1 impact/BP-trace,
> T2 reference-search) сюрфейсятся **рекомендательно** — маркер `•` в чеклисте + строки в `LOOPS.md`, но
> **в блок-условие НЕ входят** (блок строго `recall ∧ capture ∧ research`; инвариант покрыт
> `tests/unit/test_onec_task_completion_stop.py`). На КАЖДОЙ 1С-задаче пишется событие presence в
> `.claude/cache/onec-toolgate-events.jsonl` → валидатор
> [`scripts/onec_toolgate_validation.py`](../../../../scripts/onec_toolgate_validation.py) (presence_rate,
> окно 2026-06-22→07-06) + SessionStart-баннер `onec-toolgate-validation-on-start` дают вердикт
> `promote-candidate`/`keep-advisory` для **Фазы 2** (условный промоут T1-T2 в hard по типу задачи — **только
> после окна + ручная проверка применимости**, presence ≠ безопасность hard / survivorship-bias). Полное
> решение — [ADR-035](../../../../.claude/skills/architecture-research/adr/035-mandatory-high-leverage-1c-tools.md).

> **Почему `research` остаётся by-design ослабленным:** засчитывается **любой** `WebSearch`/`WebFetch` —
> проверять релевантность к Infostart/GitHub нельзя без false-block (легитимный 1С-запрос находит Infostart
> без слова «infostart»). Симметрично `recall`.

## Машина состояний (жизненный цикл `.pipeline-state.json`)

```
slug  (JIRA-код → ASCII-slug первой строки → общий слот 1c-task)
  │ ensure_pipeline_1c / init   (title="1С-задача (<cmd>): <slug>")
  ▼
init → 4 этапа pending
  │  ── advance_for_artifact (ANALYSIS-REPORT, H7 ≥200 симв.) ──►  этапы 1,2 done
  │  ── approve (G4, этап 2; AUTO: --by auto) ─────────────────►  этап 2 approved
  │  ── advance_for_artifact (IMPLEMENTATION-PROGRESS) ────────►  этап 3 done
  │  ── advance_test_done (.run-state все passed) ─────────────►  этап 4 done
  ▼
current_stage = 5   (всё готово)
```

**Поля:** `task` (slug), `title`, `created_at`, `updated_at`, `current_stage` (1..5),
`stages[]={n, name, command, artifact, status (pending/done), completed_at}`; этап 2 дополнительно несёт
`{approved, approved_by, approved_at}`. **Где живёт:** 1С-задача — в **папке задачи**
(`configuration/.../docs/<task>/`), реестр slug→папка `pipeline/_1c_index.json`; generic — `pipeline/<slug>/`;
указатель активной — `pipeline/CURRENT`. Ядро —
[`pipeline_state.py`](../../../../.claude/hooks/shared/pipeline_state.py) (CLI `init|done|approve|status|gate|resolve`).

- **Вход/маршрутизация** — детект (definitive + термин/CamelCase + глагол) + сложность (банды) + инвариант
  «слабый сигнал → вопрос, не авто»; решение режима остаётся за Claude (хук advisory).
- **Анализ/Дизайн** — тройка live-данные (1c-mcp-crud) + код (edt-mcp) + семантика (bsl-semantic-search) +
  первоисточник-RAG (pdf-vector-graph) + опц. Runtime Trace; ревью закрыт approve-гейтом **G4**.
- **Кодирование** — write-path edt-mcp с обязательными циклами (Правило 5/6), статанализ, **Live BP-verification**.
- **Тестирование** — VA BDD + **Stage 4a** pre-check данных + retry/auto-fix + YAxUnit.
- **Завершение** — 2 Stop-гейта: пайплайн использован (ADR-018) + 4 обязательные петли (единый gate).

**Осталось by-design** (фикс = false-block / суть режима — обоснованно):
- **research-relevance** — засчитывается любой `WebSearch`/`WebFetch` (проверка релевантности → неизбежный
  false-block). Симметрично recall.
- **AUTO авто-approve (G4)** — смысл AUTO-режима; компенсируется хард-правилом «AUTO ≠ игнор блокеров» +
  меткой `approved_by=auto`.
- **apply_pattern** — нет tool-сигнала «применил паттерн»; recall+capture обязательны, apply — по релевантности.
- **route/advance best-effort** — классификатор сложности = эвристика; advance по имени файла + relocate —
  graceful best-effort (сомнение → вопрос).
- **W cross-task** — `tool-effectiveness.jsonl` отчётный; авто-петля обучения на нём — non-goal.

**Открытый пункт:**
- **Сквозной прогон `/run-1c-task`** — нужен 1 живой e2e-прогон (приёмка, не код; кодовые риски низкие).

**Инструментарий качества детектора (обновлено 2026-07-03):** golden-set eval-харнесс
[`scripts/eval_1c_detector.py`](../../../../scripts/eval_1c_detector.py) + [`data/1c-detector-ground-truth.json`](../../../../data/1c-detector-ground-truth.json)
(**248 примеров**: 1С-confident / 1С-weak / не-1С / adversarial) — `is_1c` P/R/F1 + route-confusion +
**калиброванный confidence-скор** (`classify_1c_task.confidence` ∈ {0.0·0.5·0.7·0.9·1.0}; `confident_1c =
confidence≥0.7`, behavior-preserving). **Исторический** regex-only baseline (замер на 64-GT): P=1.000 R=0.927
F1=0.962 (3 FN — descriptive bug-reports без императивного глагола → recall-gap). **Актуально:** интегрированный
каскад regex+SetFit на golden-set даёт `is_1c` F1 **0.88 → 0.97** / Recall **0.81 → 0.98** (SetFit поймал
22/25 hard-кейсов recall-gap; детали — [43.5.4](43.5.4_ДОСМОТР_ПО_СМЫСЛУ.md)). Best practices (semantic-router,
hybrid cascade) — [architecture-research/cache/intent-detection-routing-best-practices.md](../../../../.claude/skills/architecture-research/cache/intent-detection-routing-best-practices.md).
