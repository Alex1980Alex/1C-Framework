# 43.6 Анатомия команд пайплайна — 3 слоя (команда → скилл → хук)

> Главы [43.1](43.1_ОБЗОР_И_ПАРАДИГМА.md)–[43.5](43.5_СКВОЗНАЯ_КАРТА.md) описывают пайплайн на уровне
> **процесса** (этапы, режимы, инструменты). Эта глава — про **внутреннюю механику**: что физически
> происходит при вводе `/analyze-1c-task` и других команд пайплайна, и в каких файлах задана «схема
> работы». Состояние на **2026-07-03** (синхронизировано с кодом моста и Stop-хуков; предыдущий сквозной
> аудит — 2026-06-16, см. раздел ниже).

## Зачем этот разрез

Глава 43 (вся) — это **документация для человека**. Реальное поведение при вводе слэш-команды задают
**три слоя исполняемых файлов**, а не текст документации:

| Слой | Где живёт | Роль |
|---|---|---|
| **1 · Команда** | `.claude/commands/*.md` | точка входа: «песочница» инструментов + делегирование на скилл |
| **2 · Скилл-методика** | `.claude/skills/*/SKILL.md` | **реальный алгоритм** — фазы/этапы, permission scope, обязательные циклы |
| **3 · Хуки** | `.claude/hooks/*` | проводка состояния, гейты, Stop-enforce — работают «вокруг», невидимо для команды |

```
/analyze-1c-task <ТЗ>   (ввод пользователя)
   │
СЛОЙ 1 · КОМАНДА  .claude/commands/analyze-1c-task.md
   │   frontmatter (allowed-tools = чем можно) + тело «используй skill X» + парсинг $ARGUMENTS + формат артефакта
   ▼
СЛОЙ 2 · СКИЛЛ    .claude/skills/analyze-1c-task-v2/SKILL.md
   │   5 фаз + permission scope + обязательные циклы   ← ГЛАВНОЕ: пошаговая методика
   ▼
СЛОЙ 3 · ХУКИ     .claude/hooks/*   (срабатывают на событиях вокруг команды)
       UPS:        onec-task-input → pipeline-gate → pipeline-protocol → preflight (ensure_pipeline_1c)
       PostToolUse: pipeline-1c-advance (двигает этапы по артефакту)
       Stop:        pipeline-protocol-stop → onec-task-completion-stop
       состояние:   pipeline/<slug>/.pipeline-state.json  (для 1С — в папке задачи)
```

## Слой 1 — Команда (тонкая обёртка)

Файл команды = **YAML-frontmatter** + **markdown-тело**. Команда почти не содержит алгоритма — она
ограничивает набор инструментов и делегирует методике.

**Frontmatter:**
- `description` — одна фраза, показывается в `/help` и реестре команд;
- `allowed-tools` — whitelist-«песочница»: какими инструментами разрешено пользоваться в этой команде.

**Тело:**
- `$ARGUMENTS` — куда подставляется ввод пользователя;
- инструкция «используй skill `<имя>`» — точка делегирования на слой 2;
- парсинг входа (пути к ТЗ / `src/` / флаги) и заявленный формат артефакта.

| Команда (`.claude/commands/`) | `description` | `allowed-tools` | → скилл (слой 2) | Артефакт |
|---|---|---|---|---|
| [`analyze-1c-task.md`](../../../../.claude/commands/analyze-1c-task.md) | ✓ | **32** | `analyze-1c-task-v2` | `ANALYSIS-REPORT.md` |
| [`implement-1c-task.md`](../../../../.claude/commands/implement-1c-task.md) | ✓ | **69** | `implement-1c-task` | `IMPLEMENTATION-PROGRESS.md` + git commit |
| [`run-1c-task.md`](../../../../.claude/commands/run-1c-task.md) | ✓ | наследует (оркестратор) | `run-1c-task` | все артефакты + `TOOL-USAGE-REPORT.md` |
| [`write-1c-tests.md`](../../../../.claude/commands/write-1c-tests.md) | ✓ | наследует от скилла | `va-bdd-testing` | `features/<slug>/*.feature` |
| [`run-1c-tests.md`](../../../../.claude/commands/run-1c-tests.md) | ✓ | наследует от скилла | `va-bdd-testing` | `.run-state.json` + JUnit XML |

**Соглашения слоя 1:**
- `allowed-tools` отражает характер этапа: `/analyze-1c-task` — преимущественно read + один Write отчёта
  (32 tools); `/implement-1c-task` — write-heavy (69 tools, включая `write_module_source`, `update_database`,
  `Bash`, git).
- **Оркестратор и тест-команды намеренно не задают собственный `allowed-tools`** — они наследуют набор
  делегируемого скилла (`/run-1c-task` оркеструет три методики; `/write-1c-tests`/`/run-1c-tests` несут
  методику `va-bdd-testing`, у которой `allowed-tools` объявлен прямо в `SKILL.md`).
- **Имя команды ≠ имя скилла** (`/analyze-1c-task` → скилл `analyze-1c-task-v2`) — by design: одна методика
  может обслуживать несколько команд, версия методики растёт независимо от имени команды.

## Слой 2 — Скилл-методика (реальная схема работы)

Здесь лежит пошаговый алгоритм. Frontmatter скилла: `name`, `version`, `updated`, `commands:` (обратная
привязка к команде), `allowed-tools`/permission scope.

| Скилл (`.claude/skills/`) | Версия | Структура | Permission scope | Артефакт | `commands:` |
|---|---|---|---|---|---|
| [`analyze-1c-task-v2`](../../../../.claude/skills/analyze-1c-task-v2/SKILL.md) | 4.4.0 | 5 фаз + опц. Фаза 2.5 | read-only + единственный Write отчёта; `Edit`/`Bash`/`execute_code` запрещены | `ANALYSIS-REPORT.md` | `/analyze-1c-task` |
| [`implement-1c-task`](../../../../.claude/skills/implement-1c-task/SKILL.md) | 2.8.1 | Этапы 0–8 (+3R, 5.x, 5.y) | write-heavy (через `allowed-tools` команды) | `IMPLEMENTATION-PROGRESS.md` | `/implement-1c-task` |
| [`run-1c-task`](../../../../.claude/skills/run-1c-task/SKILL.md) | 1.0.0 | 4 этапа оркестрации (+2.4, 2.5, W) | делегирует; своего scope нет | `TOOL-USAGE-REPORT.md` (свой) + делегаты | `/run-1c-task` |
| [`va-bdd-testing`](../../../../.claude/skills/va-bdd-testing/SKILL.md) | 1.1.0 | Stages 1, 2, 3, 4 + обяз. Stage 4a | `Write`/`Edit` разрешены (пишет `.feature`); `allowed-tools` в SKILL.md | `.feature` + calibration log | `/write-1c-tests`, `/run-1c-tests` |

### Фазы `analyze-1c-task-v2` (Планирование + Дизайн)

1. **Требования** — разбор ТЗ, scope (что менять / что НЕ менять).
2. **Объекты** — проверка каждого через `get_metadata`, маркеры `[ADDED]`/`[MODIFIED]`/`[REFACTOR]` (Refactor gate v4.1).
3. **2.5 Runtime Trace** (опц., v4.2) — live BP-trace через `1c-debug-hmr` при ≥3 runtime-ветвлениях; флаг `--trace` или self-decision; иначе SKIP.
4. **Алгоритм** — поиск паттернов, логика решения с учётом discrepancies из 2.5.
5. **План модификаций** — пронумерованные точки (файл/строка/действие/код/зависимости).
6. **Верификация** — покрытие требований, побочные эффекты, тест-план.

**Обязательная секция отчёта «12. Оценка трудозатрат и пошаговый план» (Правило 4):** каждый `ANALYSIS-REPORT.md` завершается оценкой трудозатрат — пошаговый план (`Шаг | Действие | Точки/артефакты | Оценка`, время на каждый шаг выводится из порядка Фазы 4 + обязательные шаги ревью/TestDB/тесты/прогон) + итог отдельным параграфом (Минимум/Ожидаемо/С запасом в часах → идеальные дни, сложность, допущения, критический путь).

**Обязательная секция отчёта «13. Источники исследования» (Правило 5):** фиксировать данные внешнего поиска, включая отрицательные результаты. **Иерархия источников 1С (по типу вопроса):** (1) **эталон 8.3.27** → RAG `pdf-vector-graph`/`/search` (платформенные вопросы; RAG содержит только платформенную доку); (2) **ИТС** → skill `its-research`/`scripts/its_fetch.py` (полная: платформа+БСП+v8std; **первичный авторитетный источник для БСП/библиотечных тем и стандартов**, приоритетнее Infostart; **глубина обязательна** — несколько точных `site:`-запросов + fetch **дословной** главы/стандарта, ≥1 выдержка с атрибуцией, НЕ по заголовкам/описанию подсистемы; часть БСП-РР в дистрибутиве БСП → сверять с v8std + кодом). **Механизм:** глубокий разбор → **агент `its-researcher`** (parallel fan-out по db, бережёт контекст, аудируемо); точечная справка → inline `its_fetch.py`; (3) **Infostart** → `scripts/onec_search.py` (агент первым, `WebSearch` только fallback; приоритет 2); (4) **GitHub** → `scripts/ecosystem_scan.py` (ADR-039; эскалация 30 дн → `--days 3650`; для RU-1С часто структурно пуст). Маршрутизация: платформа → (1); БСП/стандарт → (2) ИТС первым; Infostart/GitHub — дополнение/проверка.

**Обязательная секция отчёта «14. Заполнение описания — Задача разработки» (Правило 6, v4.4 2026-07-08):** авто-заполняемый корпоративный Jira-шаблон задачи разработки (I.N.V.E.S.T.) — Предмет (Глагол → Существительное → Уточнение) / Описание (со слов инициатора) / Назначение / Требования (Список, Интерфейс, Функциональное описание, Критерии приемки, таблица Метаданных `Вид изменения | Вид объекта | Имя | Синоним | Назначение`, Ролевая модель) / Что сделать / Результат / Пояснения. Заполняется **автоматически** реальным содержимым отчёта по таблице маппинга в SKILL.md (напр. `[ADDED]`→добавлен, `[MODIFIED]`→изменен); инвариант — «Что сделать» = пошаговый план §12.1 с оценками часов + итог §12.2 (сумма >16 ч → декомпозиция на связанные задачи). Готово к копированию в Jira. Источник: [roadmap 260708](../../../roadmap/260708_Pаполнение%20описания%20Задача%20разработки/260708_Pаполнение%20описания%20Задача%20разработки.md).

Permission scope (Вариант C): read-only анализатор — единственный `Write` для `ANALYSIS-REPORT.md`;
`Edit`/`Bash`/`execute_code` запрещены по дизайну (анти-scope-creep). Правки кода фиксируются как точки
модификации и применяются через `/implement-1c-task`.

### Этапы `implement-1c-task` (Кодирование + Тестирование)

> Скилл покрывает **два этапа generic-парадигмы** (ADR-019 B′, метка frontmatter скилла): Этап 3
> «Кодирование» (внутр. этапы 0–3) **и** Этап 4 «Тестирование» (внутр. этапы 4–6 + делегирование
> `/write-1c-tests`/`/run-1c-tests`).

`0` Preflight (capability-матрица, **5 режимов**: Full / Full (no-BP) / Code-only / Read-only verify /
Read-only research) → `1` Подготовка →
`2` Валидация запросов → `3` BSL-изменения (+ `3R` рефакторинг) → `4` Статанализ (`bsl_lint.py`
предпочтительно, OneScript fallback) → `5` Верификация (+ `5.x` Live BP-verification каждой точки,
`5.y` regression diff) → `6` Тест на живых данных (обяз. `update_database`) → `7` Документация → `8` Git.

**Sonar (ADR-037, hard):** после BSL-правок — `scripts/run-sonar-analysis.ps1` → `python
scripts/sonar_rescan_verify.py` (mode `changed-lines`: 0 BLOCKER/CRITICAL на изменённых строках).
Stop-гейт `onec-task-completion-stop` блокирует завершение при непройденном re-scan (default-ON при
`config_edit`; opt-out `ONEC_SONAR_GATE_DISABLE=1`).

**Обязательные циклы (НИКОГДА не пропускать):**
- **Правило 6:** `validate_query` → `execute_query` (тест) → запись;
- **Правило 5:** `write_module_source` → `get_project_errors` → `read_method_source` (верификация);
- **Этап 5.x:** для каждой `[ADDED]`/`[MODIFIED]` точки — 8-шаговый BP-протокол; неполное покрытие
  блокирует переход на Этап 6 (или обоснованный SKIP в `IMPLEMENTATION-PROGRESS.md`).

### Структура `va-bdd-testing` (Тестирование)

Stage 1 (анализ Form.xml) → Stage 2 (документация VA) → Stage 3 (откалиброванные VA-паттерны) →
**Stage 4a (ОБЯЗ. pre-scenario TestDB check)** → Stage 4 (проверка БД после прогона). Правило:
никогда не писать шаги без завершённых Stage 1+2; на FAIL Stage 4a — BLOCKER (подготовка данных или СТОП).

## Слой 3 — Хуки (проводка состояния и принуждение)

Команда и скилл не знают про состояние пайплайна — его ведут хуки на событиях `UserPromptSubmit` (UPS),
`PostToolUse` и `Stop`.

| Хук (`.claude/hooks/`) | Событие | Что делает | Состояние (R/W) | Opt-out |
|---|---|---|---|---|
| [`onec-task-input.py`](../../../../.claude/hooks/onec-task-input.py) | UPS | Маршрут 1С-задачи из чата (`route_1c_task`, flow ∈ 6: `none` / `ask_1c` / `ask_action` / `auto` / `ask_flow` / `gated`) | — | (early-return) |
| [`onec-state-first-guard.py`](../../../../.claude/hooks/onec-state-first-guard.py) | PreToolUse `Write\|Edit` | ADR-026 state-first: 1С-правка (`.bsl`/`.mdo`/`.form` под `configuration/`) без активного 1С-pipeline-state → advisory-нудж (НИКОГДА не блок) | `.pipeline-state.json` (R) | `ONEC_STATE_FIRST_DISABLE=1` |
| [`pipeline-gate.py`](../../../../.claude/hooks/pipeline-gate.py) | UPS | Гейт `pl-*` / `/implement-1c-task`: hard-block или advisory | `.pipeline-state.json` (R) | `PIPELINE_GATE_DISABLE=1` |
| [`pipeline-protocol.py`](../../../../.claude/hooks/pipeline-protocol.py) | UPS | Инъекция обязательной инструкции вести работу через пайплайн (advisory) | — | `PIPELINE_PROTOCOL_DISABLE=1` |
| `analyze-1c-task-preflight.py` / `implement-1c-task-preflight.py` | UPS | Авто-заводят `pipeline/<slug>/` через `ensure_pipeline_1c` (F-1) | `.pipeline-state.json` (W) | — |
| [`pipeline-1c-advance.py`](../../../../.claude/hooks/pipeline-1c-advance.py) | PostToolUse `Write\|Edit` | Двигает этапы по артефакту (1,2 / 3 / 4); lint-нудж | `.pipeline-state.json` (R+W), `.run-state.json` (R) | `ARTIFACT_LINT_DISABLE=1` (только нудж) |
| [`pipeline-protocol-stop.py`](../../../../.claude/hooks/pipeline-protocol-stop.py) | Stop | Hard-block завершения, если были правки кода без проводки через пайплайн (ADR-018) | все `.pipeline-state.json` (R), `hook-invocations.jsonl` (R) | `PIPELINE_PROTOCOL_DISABLE=1` |
| [`onec-task-completion-stop.py`](../../../../.claude/hooks/onec-task-completion-stop.py) | Stop | ЕДИНЫЙ task-completion gate 1С: **hard** RECALL ∧ CAPTURE ∧ RESEARCH ∧ **SONAR** (при `config_edit`, ADR-037); SKILL — info; advisory-контур ADR-035/036 (`•`) | все `.pipeline-state.json` (R), транскрипт (R), Sonar-state (R), `LOOPS.md` + `onec-toolgate-events.jsonl` (W) | `ONEC_TASK_GATE_DISABLE=1` / `ONEC_SONAR_GATE_DISABLE=1` |

**Хелперы (`.claude/hooks/shared/`):**
- [`pipeline_state.py`](../../../../.claude/hooks/shared/pipeline_state.py) — ядро generic-пайплайна (ADR-017):
  CLI `init | done | approve | status | gate` + importable API (`gate_check`, `resolve_current`, `mark_done`,
  `approve`). Профили этапов: `STAGES` (generic) и `STAGES_1C` (1С: артефакты ANALYSIS-REPORT /
  IMPLEMENTATION-PROGRESS / `.run-state.json`).
- [`pipeline_1c_bridge.py`](../../../../.claude/hooks/shared/pipeline_1c_bridge.py) — мост 1С→state (ADR-019 B′,
  best-effort): `classify_1c_task`, `estimate_effort`, `route_1c_task`, `ensure_pipeline_1c`,
  `advance_for_artifact`, `gate_1c_implement` (G4), `advance_test_done`, `is_1c_task_title` (единый предикат),
  **`resolve_active_1c_slug`** (C2/C3: единая идентификация активного пайплайна — JIRA-код → иначе CURRENT-если-1С),
  `sync_approval` / `check_lineage` (ADR-041: проекция OpenSpec-approval → pipeline-state + advisory-чек lineage).

**Порядок исполнения (пайплайн-релевантные хуки), `.claude/settings.json`:**
- **UPS:** `onec-task-input` (первый блок) → `pipeline-gate` → `pipeline-protocol` → … → preflight
  `implement-1c-task` / `analyze-1c-task` (последними, timeout 30 — именно они зовут `ensure_pipeline_1c`).
- **PostToolUse `Write|Edit`:** `pipeline-1c-advance`.
- **Stop:** … → `pipeline-protocol-stop` (#12) → `onec-task-completion-stop` (#13) → … (сначала «была ли
  работа через пайплайн», затем «закрыты ли обязательные петли 1С-задачи»).

## Сквозная трассировка: `/analyze-1c-task` от ввода до артефакта

1. **Ввод** `/analyze-1c-task <ТЗ>`.
2. **UPS-хуки:** `onec-task-input` (для слэш-команды — early-return); `pipeline-gate` (analyze не гейтится);
   `pipeline-protocol` (инъекция инструкции); **`analyze-1c-task-preflight` → `ensure_pipeline_1c`** заводит
   `pipeline/<slug>/.pipeline-state.json` с `title="1С-задача (...)"`.
3. **Слой 1 (команда):** `allowed-tools` открывают 32 инструмента; тело активирует skill `analyze-1c-task-v2`.
4. **Слой 2 (скилл):** Фазы 1–5 → **`Write ANALYSIS-REPORT.md`** (единственный Write — read-only scope).
5. **PostToolUse:** `pipeline-1c-advance` → `advance_for_artifact` → этапы **1, 2 → done** (guard H7: артефакт
   ≥200 непробельных символов; иначе не продвигает).
6. **Approval-гейт G4:** `pipeline-gate` хард-блокирует `/implement-1c-task`, пока этап 2 (дизайн) не
   `approved` (`pipeline_state.py approve <slug>`). Поиск активного 1С-пайплайна — через **`resolve_active_1c_slug(prompt)`**:
   JIRA-код из промта → иначе `CURRENT`, если это 1С-задача. Тот же helper переиспользует `/implement`
   (`ensure_pipeline_1c`), поэтому гейт **надёжен и для НЕ-JIRA задач** (раньше `gate_1c_implement` искал
   `derive_slug(implement_prompt)` ≠ analyze-slug → молча no-op или ложный блок).
   **SDD-плечо (ADR-041):** одобрение дизайна через OpenSpec (`/opsx:approve` пишет `.openspec.yaml`)
   проецируется в pipeline-state (`sync_approval`) → гейт пропускает; `check_lineage` эмитит advisory
   `[LINEAGE-CHECK]` при дрейфе ANALYSIS-REPORT↔proposal/specs. **P1.3:** если активный 1С-пайплайн не
   найден — G4 эмитит advisory (не молчаливый no-op).
   В AUTO (`/run-1c-task`) approve ставит оркестратор сам (`--by auto`).
7. **Stop:** `pipeline-protocol-stop` проверяет, что пайплайн обновлён за сессию; `onec-task-completion-stop`
   проверяет петли RECALL / CAPTURE / RESEARCH / **SONAR** (при `config_edit`) + info-SKILL и пишет `LOOPS.md`.

## Жизненный цикл состояния

```
slug (JIRA-код → ASCII-slug первой строки → общий слот 1c-task)
   │ ensure_pipeline_1c / init
   ▼
init  → этапы pending  ──advance_for_artifact──►  этап 1,2 done (по ANALYSIS-REPORT)
   │                                              этап 3 done (по IMPLEMENTATION-PROGRESS)
   │ approve (G4, этап 2)                          этап 4 done (advance_test_done: .run-state все passed)
   ▼
current_stage = 5  (всё готово)
```

**Где живёт состояние:**
- **1С-задача** — `.pipeline-state.json` лежит **в папке задачи** (`configuration/.../docs/<task>/`); реестр
  slug→папка — `pipeline/_1c_index.json`.
- **Generic-задача** — `pipeline/<slug>/.pipeline-state.json`.
- Указатель активной задачи — `pipeline/CURRENT`.

**Поля `.pipeline-state.json`:** `task` (slug), `title`, `created_at`, `updated_at`, `current_stage` (1..5),
`stages[]` = `{n, name, command, artifact, status (pending/done), completed_at}`; этап 2 дополнительно несёт
`{approved, approved_by, approved_at}`. Маркер 1С-задачи — `title` начинается с `"1С-задача ("`
(единый предикат `is_1c_task_title`).

## Соглашения и инварианты

- **Команда — тонкая обёртка, алгоритм в скилле.** Менять методику = править `SKILL.md`, а не команду
  (ADR-019 B′: методики 1С при приведении к парадигме не переписывались).
- **Имя команды ≠ имя скилла** (by design).
- **1С-состояние — в папке задачи**, не в `pipeline/<slug>/` (чтобы артефакты и state жили рядом с ТЗ).
- **AUTO (`/run-1c-task`)** = analyze → авто-approve (`approved_by=auto`, audit-след) → implement → test;
  методики не дублируются — оркестратор делегирует.
- **Все хуки advisory + opt-out + graceful**, кроме hard-гейтов: approve-гейт (`pipeline-gate`, G4),
  `pipeline-protocol-stop` и `onec-task-completion-stop`. Последний несёт **несколько hard-подпроверок**
  (не одну): recall ∧ capture ∧ research **+ SONAR** (ADR-037, default-ON при `config_edit`) + опц.
  `ONEC_TOOLGATE_HARD` / `ONEC_TOOLGATE_DEBUG_HARD` — поэтому формула «3 hard-точки» неточна.
- **Оркестратор гейтов:** при `GATE_ORCHESTRATOR_ENABLE=1` (включён в `settings.local.json`) оба Stop-гейта
  **уступают** оркестратору [`gate-orchestrator-stop.py`](../../../../.claude/hooks/gate-orchestrator-stop.py)
  (early-return), дающему тот же вердикт одним проходом; решение+side-effects — single-source
  `onec-task-completion-stop.evaluate_completion` (паритет — [`tests/unit/test_gate_parity.py`](../../../../tests/unit/test_gate_parity.py)).

## Аудит консистентности слоёв

> Три слоя (команда / скилл / хуки) легко расходятся при независимых правках. Это **переиспользуемая
> процедура** проверки их согласованности: что сверять, что считается дефектом, а что нет. Применять при
> любой правке команды или скилла пайплайна.

### Что сверять (чеклист)

| Проверка | Дефект, если… |
|---|---|
| `allowed-tools` команды ↔ инструменты в теле скилла | скилл вызывает MCP-tool, которого нет в `allowed-tools` команды (окажется вне whitelist) |
| `version` / `updated` frontmatter скилла ↔ changelog/тело | frontmatter отстаёт от описанных в теле улучшений |
| `commands:` во frontmatter скилла | скилл не указывает обслуживаемую команду (связь держится только на имени/триггерах) |
| frontmatter команды (`description`) | команда без `description` (не видна в `/help`) |
| Имена MCP-серверов | прозаическое имя ≠ фактический неймспейс `mcp__<server>__*` (см. таблицу канонических имён) |
| **Якоря на живой код** (P2.7) | ссылка на `*.py`/хук с `#L<номер>` строки — **дефект**: номера дрейфуют при любой правке (ADR-041 сдвинул `pipeline_1c_bridge.py` на +190). Ссылаться на **файл + имя функции** без `#L` |
| **Штамп «Состояние на»** (P2.8) | дата в шапке файла отстаёт от последней правки содержимого (правили под новый ADR, дату не бампнули → штамп врёт о свежести) |
| **Покрытие свежих ADR** (P2.8) | ADR, задевший пайплайн (детектор/гейты/маршрутизация), не отражён в главе (grep по номеру ADR пуст) |

### Канонические имена MCP-серверов (по `.mcp.json`)

Главный источник рассинхрона — устаревшие/прозаические имена серверов. Эталон:

| Роль | Канонический MCP-сервер | Где живёт | Типичные инструменты |
|---|---|---|---|
| Данные/метаданные 1С | **`1c-mcp-crud`** (НЕ `1c-mcp-server`) | `external/1c_mcp/` | `execute_query`, `get_metadata`, `get_form_structure` |
| Статанализ BSL (OneScript) | **`bsl-debugger`** (НЕ `bsl-debug-server`) | `tools/bsl-debugger/` | `bsl_analyze`, `bsl_execute`, `bsl_debug_*` |
| Live-отладка RDBG | **`1c-debug`** (plain) / **`1c-debug-hmr`** (HMR) | `tools/bsl-debug-server/` | `debug_connect`, `debug_set_breakpoint`, `debug_stack_trace` |
| AST-поиск BSL | **`ast-grep-mcp`** | `tools/ast-grep-mcp/` (в профилях `.mcp/`) | `ast_grep` |

> ⚠ `bsl-debug-server` — это **каталог** (`tools/bsl-debug-server/`), где живут RDBG-серверы
> `1c-debug`/`1c-debug-hmr`, а **не** имя MCP-сервера. `mcp-reasoner` в конфигах **отсутствует** (фантом —
> не использовать).

### Как сверять

Три параллельных чтения исходников (не по памяти): (1) все `.claude/commands/*1c*.md`; (2) скиллы
`analyze-1c-task-v2`, `implement-1c-task`, `run-1c-task`, `va-bdd-testing`; (3) хуки пайплайна + регистрация
в `.claude/settings.json`.

### By-design — НЕ дефект (не «чинить»)

| Наблюдение | Почему так задумано |
|---|---|
| Имя команды ≠ имя скилла (`/analyze-1c-task` → `analyze-1c-task-v2`) | методика версионируется независимо; одна методика — несколько команд |
| `/run-1c-task`, `/write-1c-tests`, `/run-1c-tests` без `allowed-tools` | оркестратор и тест-команды **наследуют** инструменты делегируемого скилла (`va-bdd-testing` несёт свой `allowed-tools`) |
| Хардкод путей `D:\va-test\...` | реальное расположение VA-харнесса (память [[reference_va_debug_attach]]) — не баг среды |
| «4 основных MCP-сервера», хотя инструменты от 8 | «4 основных» (EDT-MCP, 1c-mcp-crud, bsl-debugger, 1c-debug-hmr) + вспомогательные — терминологическое сокращение |

### Инвариант поддержки

При правке команды/скилла — сверять три слоя по чеклисту выше; держать `version`/`commands:` во frontmatter
скилла актуальными; имена серверов — строго каноническими (таблица выше).

**Процедура при каждом ADR, задевающем пайплайн** (детектор `pipeline_1c_bridge`, гейты `onec-task-completion-stop`/`gate_policies`, маршрутизация — P2.8, чтобы 035/036/037/041 больше не проходили мимо главы):
1. Прогнать `grep -rl "<ADR-NNN>" docs/framework documentation/4_МЫШЛЕНИЕ/4.4_ПАЙПЛАЙН_1С/` — если пусто, глава не покрывает решение → дописать.
2. Бампнуть штамп «Состояние на …» в затронутых файлах (историческую дату решения — НЕ трогать, только sync-штамп).
3. Якоря на код — без `#L` (номера строк дрейфуют; ссылаться на файл + имя функции). Одноразовая зачистка выполнена P2.7 (roadmap 260703).

### Результат аудита 2026-06-16

Сквозной разбор 5 команд, 4 скиллов, 8 хуков + `settings.json`: найдено ~22 расхождения → **исправлено 14**
(10 первый заход + 4 после сверки с `.mcp.json`), **by-design 4**, **открытых 0**. История правок — коммиты
`d39f520d1`, `098f722c8`, `18d4a5103`.
