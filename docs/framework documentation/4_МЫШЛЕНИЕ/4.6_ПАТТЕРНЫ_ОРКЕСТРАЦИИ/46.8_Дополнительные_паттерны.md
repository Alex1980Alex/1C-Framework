## A. Расширения Fanout-And-Synthesize (→ [46.3](46.3_Fanout_And_Synthesize.md))

### A1. Multi-modal sweep
```
prompt ─┬─ агент: поиск ПО КОНТЕЙНЕРУ ─┐
        ├─ агент: поиск ПО СОДЕРЖИМОМУ ┼─ объединение (каждый слеп к остальным)
        └─ агент: поиск ПО СУЩНОСТИ ───┘
```
- **Когда:** один угол поиска не находит всё; нужна полнота охвата разными СПОСОБАМИ (не разными подтемами).
- **Реализация:** `parallel` субагентов, каждый со своей стратегией; дедуп результатов.
- **Workflow:** `parallel(MODES.map(m => () => agent(searchPrompt(m), {schema: HITS})))` → dedup.
- **Реальный пример:** `prework_dispatcher` (4 worker'а: architecture / similar-code / github-bp / stackoverflow — каждый свой способ); стратегии поиска `search_documents` (vector / bm25 / graph) под RRF.

### A2. Pipeline (без барьера)
```
item A: [s1]→[s2]→[s3]        (A в s3, пока B ещё в s1 — без синхронизации стадий)
item B:        [s1]→[s2]→[s3]
```
- **Когда:** многостадийная обработка элементов, стадии НЕ нужно синхронизировать (в отличие от барьера `parallel`). Wall-clock = самая медленная цепочка одного элемента, не сумма-по-стадиям.
- **Реализация:** Workflow `pipeline(items, stage1, stage2, ...)` — без барьера между стадиями.
- **Workflow:** `pipeline(files, f => review(f), r => parallel(r.findings.map(verify)))`.
- **Реальный пример:** software-паттерн `Pipeline` ([[pipeline]], `ProcessingPipeline: split→dedup→enrich`); 4-этапный `pipeline_state` (анализ→дизайн→код→тест).

## B. Расширения Adversarial Verification (→ [46.4](46.4_Adversarial_Verification.md))

### B1. Perspective-diverse verify
```
находка ─┬─ линза correctness ─┐
         ├─ линза security ─────┼─ агрегация вердиктов
         └─ линза repro ────────┘
```
- **Когда:** находка может провалиться РАЗНЫМИ способами → N **разных линз** ловят больше, чем N одинаковых рефьютеров.
- **Реализация:** разные промпты-проверки (не копии); агрегация.
- **Workflow:** `parallel(['correctness','security','repro'].map(l => () => agent(judge(l), {schema: VERDICT})))`.
- **Реальный пример:** `code-verify` — 4 режима-линзы (knowledge-compliance / behavior-preservation / bug-fix-validation / quality-review).

### B2. Completeness critic
```
результаты → [критик: «что упущено?»] → дыры → новый раунд работы
```
- **Когда:** убедиться, что охват полон (модальность не прогнана, claim не проверен, источник не прочитан).
- **Реализация:** финальный субагент-критик после основной работы → его находки = следующий раунд.
- **Workflow:** `const gaps = await agent('Что упущено в этом покрытии? ...', {schema: GAPS}); if (gaps) ...`.
- **Реальный пример:** `onec-task-completion-stop` (консолидированный чеклист recall/capture/research/sonar — критик полноты 1С-задачи); roadmap-audit «inventory перед execution».

### B3. Evaluator-optimizer
```
generate → [evaluate] ──не прошло──► refine ──┐
   ▲_________________________________________|   прошло → ■
```
- **Когда:** результат нужно довести до критерия через оценку+правку (не один проход).
- **Реализация:** петля «сгенерировал → оценил → уточнил» до прохождения порога.
- **Workflow:** `let r = gen(); while(!(await evaluate(r)).ok && n<3){ r = refine(r, feedback) }`.
- **Реальный пример:** `fix-sonar-task` (re-scan → adversarial code-verify → не сошлось → назад в implement, ADR-034 R7); Ralph-Wiggum в `code-verify`.

## C. Новый подход

### C1. Agent teams
```
lead-агент ──супервизит──┬─ peer-сессия 1 ─┐
                         ├─ peer-сессия 2 ─┼─ общий task-list
                         └─ peer-сессия 3 ─┘
```
- **Когда:** несколько **долгоживущих** параллельных сессий-исполнителей под управлением лид-агента; промежуточные результаты в общем task-list (не в контексте одного Claude). [code.claude.com/docs/en/workflows]
- **Отличие:** vs субагенты (рабочие на ход) — teams живут долго; vs Workflow (скрипт держит план) — здесь план держит лид-агент, ход за ходом.
- **CC-реализация:** `claude agents` (agent view), фоновые сессии-peers.
- **Реальный пример:** в нашем коде нет (CC-native фича); ближайший аналог — Opus-оркестратор + делегирование субагентам, но без долгоживущих peer-сессий.

## D. Варианты Loop Until Done (→ [46.7](46.7_Loop_Until_Done.md))

### D1. Loop-variants: dry / count / budget
```
loop-until-dry:    пока K раундов подряд не дают НОВОГО → стоп
loop-until-count:  пока накоплено < N → продолжать
loop-until-budget: пока budget.remaining() > порог → продолжать
```
- **Когда:** *dry* — открытый поиск неизвестного объёма (баги/находки); *count* — нужно ровно N; *budget* — масштаб под директиву `+Nk` токенов.
- **Реализация:** счётчик пустых раундов / накопитель / `budget.remaining()`; **обязателен термин-гард**.
- **Workflow:** `while(dry<2){ const fresh=...; if(!fresh.length){dry++;continue} dry=0; acc.push(...fresh) }`.
- **Реальный пример:** `code-verify` Ralph-Wiggum (count=3 итерации до PASS); Workflow loop-until-budget под `+Nk`.

## Связь с decision-tree (46.1)
- Нужен **полный охват разными способами** → A1 Multi-modal sweep (поверх Fanout 46.3).
- **Многостадийная обработка без синхронизации** → A2 Pipeline без барьера.
- **Разные режимы провала находки** → B1 Perspective-diverse (поверх Adversarial 46.4).
- **«Точно ли всё покрыто?»** → B2 Completeness critic.
- **Доводка до критерия петлёй** → B3 Evaluator-optimizer.
- **Долгоживущие параллельные исполнители** → C1 Agent teams.
- **Неизвестный объём / ровно N / под бюджет** → D1 Loop-variants (поверх Loop 46.7).
