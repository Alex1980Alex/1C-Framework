# 27.12.2 Блок «КООРДИНАЦИЯ» — Memory Orchestrator изнутри

> Зум на центральный блок мастер-схемы [27.12 §10](27.12_Memory_Systems_Map.md): внутреннее устройство 5 компонентов оркестратора (Router, Search, LinkRegistry, Propagation, MemCube) + адресная система UnifiedID — классы, контракты, точные константы из кода `src/memory/orchestrator/`. Обзорное описание оркестратора и его MCP-инструментов — [27.2 Оркестратор](27.2_Оркестратор.md); здесь — только «как оно устроено внутри». Все факты — из кода; расхождения с текстом 27.2/27.12 помечены ⚠.

```text
            ┌─────────────────────── КООРДИНАЦИЯ ───────────────────────┐
  write ───►│ Router (classify ≥0.6 → explicit → keyword → thresholds)  │
            │ Search (adapters ∥ → RRF k=60 → dedup → rerank → links)   │◄─── read
            │ LinkRegistry (SQLite link_registry.db, 8 типов, BFS)      │
            │ Propagation (BFS ≤3, time×dist decay, CircuitBreaker)     │
            │ MemCube (контейнер-мост: SQLite/Qdrant/JSONL/wiki-md)     │
            └──── адресация: UnifiedID {type}:{source}:{id} + IDRegistry┘
```

Каркас — класс `MemoryOrchestrator` ([memory_orchestrator.py](../../../../src/memory/orchestrator/memory_orchestrator.py)): `start()` собирает `LinkRegistry` (`data/link_registry.db`), `MemoryRouter`, `UnifiedSearchEngine` с 3 адаптерами, прогревает vector-memory (Qdrant + embedding), поднимает EventBus/EventStore и P4-сервисы. `OrchestratorConfig`: `search_timeout=5.0`, `enable_link_creation=True`, `LRUCache(max_size=256, ttl=3600s)`. `PropagationEngine` — **lazy-init** при первом `propagate_update`. Сам оркестратор данных не хранит — только `_save_to_target()`-делегаты в подсистемы (4-я цель `wiki` пишет черновик `docs/wiki/drafts/<slug>.md` через `MemCube.to_wiki_page()`).

## 1. Router — MemoryRouter + ContentClassifier

[memory_router.py](../../../../src/memory/orchestrator/memory_router.py). 4-фазный конвейер `route(content, metadata) → RoutingDecision{targets, confidences, method, reasoning, classification}`. Контент длиннее `max_content_length=10000` обрезается до `truncate_length=2000`.

**Фаза 0 — ContentClassifier (Memori-pattern, regex middleware).** 5 групп сигналов (`_FACT/_PREFERENCE/_RULE/_SKILL/_CODE_SIGNALS`), каждое совпадение даёт `+0.3 × кол-во матчей`, metadata-hint `content_type` — `+1.0`. `confidence = min(score/3.0, 1.0)` (3+ сигнала = 1.0). Если `confidence ≥ 0.6` — роутинг завершён по `CONTENT_TYPE_TARGETS`: FACT/PREFERENCE/OBSERVATION → `memory-ai`, RULE/CODE → `vector-memory`, SKILL → `skill-learning`, WIKI → `wiki`. Без сигналов — `OBSERVATION, confidence=0.3`.

**Фаза 1 — детерминированные правила** (`_phase1_rule_classification`):

| Правило | Источник | Confidence |
|---|---|---|
| `EXPLICIT_KEYWORDS` (4 категории: patterns/facts/code/skills) | подстрока в lower-контенте | **1.0** |
| `INTENT_PATTERNS` (11 фраз: «запомнить это», «promote to wiki», …) | подстрока | **0.95** |
| `CODE_PATTERNS` (```` ```bsl/python ````, `Функция \w+(`, `def \w+(`, …) | regex | **0.85** → vector-memory |
| `CONFIG_PATTERNS` (`.json/.yaml/.xml/.toml`, `settings.json`) | regex | **0.7** → vector-memory |

**Фаза 2 — keyword scoring**: `raw = match_count/len(keywords)` по `CATEGORY_KEYWORDS`, веса категорий `patterns=1.5`, `facts=1.2`, `skills=1.3`; баллы суммируются per-target.

**Фаза 3 — выбор 1–3 целей по порогам** (`_phase3_select_targets`): top-score `≥0.8` → 1 цель; 2-й `≥0.5` → 2 цели; 3-й `≥0.3` → 3 цели; иначе fallback на top-1. Финальный fallback всего роутера — `memory-ai` с conf 0.3. Каждое решение пишется в `memory-routing.log` (§27 D1.1, opt-out `MEMORY_ROUTING_LOG_DISABLE=1`). При multi-store save оркестратор связывает сущности цепочкой `SESSION_CONTEXT, strength=0.7`.

`RoutingStats` считает попадания per-метод (`auto_classify/explicit/intent/type_detection/keyword_scoring/fallback`, single/multi-target) — видно в `get_system_stats().router`.

## 2. Search — UnifiedSearchEngine

[unified_search.py](../../../../src/memory/orchestrator/unified_search.py). Pipeline: **parallel dispatch → (filter by memory_type) → RRF-fusion → min_score → dedup → rerank → link-enrich → limit**.

**Адаптеры** (`BaseSearchAdapter`: `search(query, limit)` + `source_name()`), регистрируются в `start()` оркестратора:

| Адаптер | Backend | Скоринг raw_score |
|---|---|---|
| `AiMemorySearchAdapter` | SQLite `memory_ai.db` | токены ≥3 симв., OR-LIKE по content+tags, fetch `max(limit×3, 30)`, rerank `0.5·match_ratio + 0.5·importance` |
| `VectorMemorySearchAdapter` | Qdrant `learned_patterns` | `similarity × pattern.confidence`, фильтр `confidence ≥ min_confidence` (default 0.3) |
| `SkillLearningSearchAdapter` | JSONL `patterns.jsonl` | keyword-overlap `|q∩doc| / |q|` |

**Тайминги:** per-adapter `asyncio.wait_for(timeout_ms=5000)`, плюс **hard ceiling `×1.5` (7.5s)** через `asyncio.timeout` на всю фазу gather — защита от деградации event loop в длинной MCP-сессии (баг 2026-04-23); недобежавшие задачи отменяются с `SourceError(error="hard_timeout")`.

**Fusion — `RRFMerger`**: `score(d) = Σ_S weight_S/(k + rank_S(d))`, `k=60`, rank с 1 (`enumerate`+1). Нормализация к [0,1] делением на `max_rrf = Σ weight/(k+1)`; финал `final_score = 0.6·RRF_norm + 0.4·boost`, где boost = `ScoreNormalizer` (свежесть <24h **×1.2**, <7d **×1.1**; `raw_score>0.8` **×1.15**, cap 1.0). ⚠ `rrf_source_weights` по умолчанию `None` → все источники weight 1.0 (таблица весов в 27.2 — пример, не дефолт кода). При `rrf_enabled=False` — плоский merge + ScoreNormalizer.

**Пост-обработка:** `min_score=0.3` filter → `Deduplicator` (MD5 от `content.strip().lower()`, дубликаты схлопываются в `duplicate_sources`) → `Reranker` (diversity: ≤3 результата с одного источника в топ-10) → `LinkEnricher` (`get_all_links(min_strength=0.5)` → `linked_entities` in/out). Каждый поиск трейсится в `memory-read.log` (per-arm hits, latency, **текст запроса не логируется** — только `query_len`).

## 3. LinkRegistry — граф связей

[link_registry.py](../../../../src/memory/orchestrator/link_registry.py). SQLite `data/link_registry.db`, `SCHEMA_VERSION=1`, таблицы `entity_links` / `link_history` (audit-trail create/update/delete) / `link_stats` (per-entity счётчики) / `schema_info`; 7 индексов.

**LinkType — 8 типов** (`based_on`/`graph_node` ретированы 2026-06-12, ADR-L1 260612 — 0 рёбер за всю историю): `supports`, `contradicts`, `extends`, `derives_from`, `session_context`, `promoted_to`, `superseded_by`, `mirrors`. Enum продублирован CHECK-constraint'ом в схеме.

**`EntityLink`** — инварианты в `__post_init__`: `0.0 ≤ strength ≤ 1.0`, запрет self-link, обязательные source/target; поля `bidirectional`, `expires_at` (TTL → `cleanup_expired()`). `create_link` отклоняет дубликат тройки `(source_id, target_id, link_type)` (`ValueError`); `create_links_batch` молча пропускает `IntegrityError`.

**BFS-обход `get_related_entities`**: дефолты `min_strength=0.5`, `max_depth=2`, `direction="both"`; накапливает `total_strength = Π strength` по пути и сортирует по `effective_strength = total_strength × 0.9^(depth−1)`. `find_path(source, target, max_depth=5)` — кратчайший путь по исходящим связям. Также: `export()`/`import_links()`, `vacuum()`, `get_registry_stats()` (total/by_type/avg_strength — попадает в `health_check`).

## 4. Propagation — PropagationEngine

[propagation_engine.py](../../../../src/memory/orchestrator/propagation_engine.py), v2.0. Event-driven BFS-каскад confidence по графу LinkRegistry.

**`PropagationConfig` — лимиты и затухание** (формулы актуализированы и в 27.2, и здесь — линейный `time_decay`, экспонента `distance_decay`, `max_entities_per_event=10`, инверсии знака для `contradicts` в коде нет; как в коде и в 27.12 §6):

| Параметр | Значение | Смысл |
|---|---|---|
| `max_depth` | **3** | глубина BFS |
| `max_entities_per_event` | **10** | узлов на одно событие |
| `min_delta_threshold` | **0.001** | отсечка микро-дельт |
| time decay | `max(0.5, 1 − days/365)` | по возрасту **связи** |
| distance decay | `max(0.3, 0.5^depth)` | экспонента по глубине |
| `event_queue_size` / workers | 1000 / 2 | фоновая обработка |
| circuit breaker | 5 fail → OPEN, reset 60s | анти-лавина |

Итог: `delta = base_delta × link_strength × time_decay × dist_decay`; знак задаётся аргументом `success`, инверсии для `contradicts` в коде **нет**. Каждый «срез» лимитом инкрементит `cascades_prevented`.

**Маршрут события:** `propagate()` → дедуп и background-очередь существуют в движке, но **оркестратор создаёт его в sync-режиме без дедупа** (`PropagationConfig(enable_background_processing=False, enable_event_deduplication=False)`, post-review 260609 P2.3): MCP-вызов await'ит реальный результат, повторная пропагация того же entity не глотается. Обработка — синхронно под CircuitBreaker. Обход — **только исходящие** `get_links_from()`; ⚠ наборы `FORWARD/REVERSE_PROPAGATION_LINKS` объявлены и экспортируются, но в текущем `_process_propagation` для фильтрации не используются. Получатели гейтятся `RECEIVER_TYPES = {(vector-memory, semantic), (memory-ai, episodic)}`; `STATIC_TYPES` (legacy `1c-docs-rag`/`conv-memory`) и неизвестные типы — не трогаются. `_apply_update` честный (P2.3): сущность засчитывается в `entities_updated` **только** если handler вернул `True` (реальная мутация); без handler'а — `False`. Vector-handler после `set_payload` бампит §24 epoch. Результат трейсится в `memory-propagation.log`.

> Автономный cascade-on-apply внутри vector-memory (depth-1, same-store) — отдельный механизм, см. [27.12 §10.2](27.12_Memory_Systems_Map.md).

## 5. MemCube — единый контейнер

[memcube.py](../../../../src/memory/orchestrator/memcube.py), MemOS-pattern. Один dataclass `MemoryCube`, который проходит весь конвейер classify → route → store → search и сериализуется в формат любой подсистемы.

Ключевые поля: identity (`cube_id` UUIDv4, `content`, `content_type` — enum **7** значений `fact/preference/rule/skill/code/observation/wiki`, `memory_type`, `source`, `title`); **`content_hash = sha256(content)[:16]`** — авто-вычисляется в `__post_init__` (канонический модуль `content_hash.py`), это cross-store join-ключ §26; scoring (`confidence=0.7`, `importance=0.5` дефолты); Engram-секции `what/why/where/learned`; temporal (`created/updated/expires_at`, `version`, `touch()` бампает версию, `is_expired()` — TTL). ⚠ Полей `quality_score`/`access_count`/`last_accessed` из таблицы 27.2 в коде нет.

**4 проекции (мост между форматами):** `to_ai_memory_row()` → SQLite-строка `important_messages` (category = content_type); `to_vector_memory_payload()` → Qdrant payload (`pattern_id`, `decay_rate=0.05`, `application_count=0`); `to_skill_learning_record()` → JSONL; `to_wiki_page()` ↔ `from_wiki_page()` — Markdown с YAML-frontmatter (`unified_id`, `content_hash`, confidence/importance/version) и секциями `## What/Why/Where/Learned/Content` (round-trip парсер).

## 6. UnifiedID + IDRegistry — адресная система

[unified_id.py](../../../../src/memory/orchestrator/unified_id.py). Формат: **`{memory_type}:{source}:{identifier}`** (`episodic:memory-ai:550e8400-…`). `identifier` валидируется regex `^[a-zA-Z0-9_:\-]+$`; `parse()` — `split(":", 2)`.

- **MemoryType (6):** `episodic · semantic · learning · docs · wiki · graph`.
- **SourceServer (7):** `memory-ai · vector-memory · skill-learning · pdf-docs · orchestrator · obsidian-vault · lightrag`; у каждого — дефолтный `memory_type` (property-маппинг).
- Фабрики: `generate()` (UUIDv4), `from_original()`, `from_path()` — детерминированный `sha256(project:path)[:16]` для docs/wiki; convenience `create_episodic_id / create_semantic_id / create_doc_id / create_wiki_id / create_graph_id`.

**`IDRegistry`** — in-memory двунаправленный маппинг `unified↔original` (`register` бросает `ValueError` при попытке ремапа, `resolve`, `lookup`, идемпотентный `get_or_create`, `batch_register`, `export/import_state`, `stats()` by_type/by_source). Глобальный синглтон `get_registry()`; MCP-обёртка — `memory_id_management` (`tools/id_management.py`, UUIDv7-операции).

## 8. Типичные сбои и диагностика

Весь блок построен **fail-soft**: отказ одного компонента деградирует ответ, но не роняет операцию.

- **Источник поиска упал/завис** → `SourceError{source, error, duration_ms}` в `sources_failed` ответа `unified_search`; `error="timeout"` — per-adapter 5s, `"hard_timeout"` — общий ceiling 7.5s (остальные задачи отменяются). Vector-adapter глотает исключение Qdrant/TEI → `[]` + `WARNING "Vector memory search failed"` в stderr-лог.
- **Каскад заблокирован** → `PropagationResult.reason`: `"circuit_breaker_open"` (5 подряд ошибок → OPEN на 60s; смотреть `memory_circuit_status`, сбрасывать `memory_circuit_reset`), `"invalid_entity_id"` (не парсится UnifiedID). `"duplicate_event"` / `"queued_for_background_processing"` через MCP-путь больше не встречаются (sync-режим без дедупа, post-review P2.3) — только у standalone-движка с дефолтным config. Высокий `cascades_prevented` = сработали лимиты depth/entities/threshold. `entities_updated` содержит только реально мутированные узлы (handler вернул `True`); пустой список при живых связях = handler не нашёл сущность в store.
- **Запись не сохранилась** → `_save_to_target` возвращает `None` (ERROR в лог), сущность просто выпадает из `saved_entities`; `route_and_save` всё равно вернёт `success: true` — проверять `entity_count` и `memory-routing.log`. Дубликат связи → `ValueError "Link already exists"`.
- **Здоровье блока** → `health_check`: `degraded` (часть компонентов unhealthy / есть OPEN-circuit'ы), `unhealthy` (все). `get_system_stats()` — request_counts, router-stats, propagation-stats, link-registry totals.
- **Логи-sink'и блока** (метаданные-only, без тел; общий обзор observability — §27): `memory-routing.log`, `memory-read.log`, `memory-propagation.log`, snapshot `memory-metrics.jsonl` на `stop()`; audit-буфер flush'ится на `stop()` (иначе CREATE/LINK/PROPAGATE не доезжают до `audit.jsonl`).
- **Stale-код MCP-сервера**: правки `src/memory/orchestrator/*` требуют `/mcp reconnect` — запущенный stdio-процесс держит старый код.
