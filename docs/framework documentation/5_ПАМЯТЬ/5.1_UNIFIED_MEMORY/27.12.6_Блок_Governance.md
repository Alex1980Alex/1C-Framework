# 27.12.6 Блок «GOVERNANCE» — жизненный цикл и защита памяти

> Детализация блока **«GOVERNANCE (поверх всего)»** мастер-схемы Unified Memory System ([27.12 §10](27.12_Memory_Systems_Map.md)). Governance — это сервисы, которые не хранят контент, а управляют его **жизненным циклом** (TTL, версии, забывание) и **защищают** систему (предохранитель, аудит, метрики). Математика §22 confidence — в [27.9](27.9_Confidence_Lifecycle.md); здесь — её место в общей системе. Все факты — из кода.

```text
  GOVERNANCE поверх всего:  TTL · Versioning · ForgetGate(archive/decay/delete)
                            · CircuitBreaker · Audit · Metrics · §22 confidence
```

Два «этажа» governance, не путать:

1. **Оркестраторные P4-сервисы** — универсальные, entity-agnostic, инициализируются в `MemoryOrchestrator.start()` ([memory_orchestrator.py](../../../../src/memory/orchestrator/memory_orchestrator.py)), персистентность в `data/services/` (`audit.jsonl`, `versions.jsonl`, `ttl.jsonl`). Экспонируются как 13 MCP-инструментов P4-группы.
2. **Vector-memory-специфичный §22 confidence** + его операционализация — maintenance ForgetGate (§26 P4) поверх `learned_patterns`. Работает напрямую с Qdrant-payload'ами, единый источник политики — [confidence.py](../../../../src/memory/vector_memory/confidence.py).

## 1. TTL Service — срок жизни записи

**Класс:** `TTLService` — [ttl_service.py](../../../../src/memory/ai_memory/services/ttl_service.py). **Персистентность:** JSONL (append при `register`, полный rewrite после `cleanup`/`extend`/`record_access`); оркестратор создаёт его на `data/services/ttl.jsonl`.

Политики (`TTLPolicy` → секунды, `_POLICY_DURATIONS`):

| Policy | Секунды | Срок |
|---|---|---|
| `NEVER` | `None` | вечно (`expires_at=None`) |
| `SHORT` | 3600 | 1 час |
| `MEDIUM` | 86400 | 24 часа |
| `LONG` (default) | 604800 | 7 дней |
| `EXTENDED` | 2592000 | 30 дней |
| `CUSTOM` | `ttl_seconds` (fallback 604800) | произвольно |

- `TTLEntry`: `entity_id`, `expires_at`, `access_count`, `last_accessed_at`, `extended_count`. `extend_ttl(seconds)` продлевает от текущего `expires_at` (или от now).
- **Фоновая очистка:** `start_cleanup_task()` — `asyncio`-цикл с интервалом `auto_cleanup_interval_seconds=3600` (`enable_auto_cleanup=True` по умолчанию); останавливается в `orchestrator.stop()`.
- ⚠ Семантика: `is_expired()` для **незарегистрированной** сущности возвращает `True` («unknown = expired»).

**MCP:** `memory_ttl_set` (register/политика), `memory_ttl_check` (срок/остаток), `memory_ttl_cleanup` (немедленный sweep, возвращает removed entity_ids).

## 2. Versioning — история версий, rollback, diff

**Класс:** `VersioningService` — [versioning_service.py](../../../../src/memory/ai_memory/services/versioning_service.py). **Персистентность:** append-only JSONL `data/services/versions.jsonl` + lazy in-memory cache per entity; thread-safe через `asyncio.Lock`.

- `EntityVersion`: монотонный `version` (=`len(existing)+1`), полный `content`-снапшот, `change_type` (`ChangeType`: `create`/`update`/`delete`/`rollback`), `created_by`, `change_summary`, `metadata`.
- **Rollback — недеструктивный:** `rollback_to_version(entity_id, N)` не переписывает историю, а создаёт **новую** версию с контентом версии N, `change_type=ROLLBACK` и `metadata={"rollback_from", "rollback_to"}`.
- **Diff:** `compare_versions` — per-key сравнение двух content-словарей, каждое изменение классифицируется `added`/`removed`/`modified`.
- Лимит `max_versions_per_entity=100` (`auto_cleanup=True`). ⚠ **Расхождение код/ожидание:** `_cleanup_old_versions` прунит только in-memory cache — JSONL-файл append-only и **не** переписывается, старые версии остаются на диске (вернутся в cache при холодном `_load_versions`).

**MCP:** `memory_version_history`, `memory_version_rollback`, `memory_version_compare`.

## 3. Audit — журнал всех операций

**Класс:** `AuditService` — [audit_service.py](../../../../src/memory/ai_memory/services/audit_service.py). **Персистентность:** append-only JSONL; default в коде `data/audit/audit.jsonl`, но оркестратор передаёт `data/services/audit.jsonl` — фактический файл второй.

- `AuditAction` (12): `create`/`read`/`update`/`delete`/`search`/`link`/`propagate`/`merge`/`rollback`/`export`/`config_change`/`health_check`.
- `AuditLogEntry`: action, `resource_type`/`resource_id`, `session_id`, `old_value`/`new_value`, `success`, `error_message`, `duration_ms`, `metadata`.
- **Буферизация:** in-memory buffer (`max_buffer_size=1000`) + **немедленный** persist для деструктивных действий (`DELETE`, `ROLLBACK`, `CONFIG_CHANGE`). Auto-flush при заполнении идёт через `_flush_buffer_unlocked()` — lock уже удержан в `log()`, повторный захват non-reentrant `asyncio.Lock` давал deadlock ровно на `max_buffer_size` (§27 P0 D0.3 hardening). Дополнительный flush — в `orchestrator.stop()` (иначе буферизованные CREATE/LINK/PROPAGATE не доезжали до диска).
- `cleanup()` — retention `retention_days=90` (rewrite файла).

**MCP:** `memory_audit_log` (query с фильтрами resource/session/action/время), `memory_audit_stats` (total/error_rate/by_action/by_resource).

## 4. CircuitBreaker — предохранитель от лавины

**Класс:** `CircuitBreaker` + `CircuitBreakerRegistry` — [circuit_breaker.py](../../../../src/memory/infrastructure/circuit_breaker.py). In-memory (без Redis/файлов — состояние сбрасывается с процессом).

```text
CLOSED ──(failure_count ≥ 5)──► OPEN ──(elapsed ≥ 60s, lazy в property state)──► HALF_OPEN
  ▲                                ▲                                                │
  └──(2 consecutive successes)─────┴───────────────(probe failed)───────────────────┘
```

`CircuitBreakerConfig`: `failure_threshold=5`, `success_threshold=2`, `reset_timeout=60.0` s, `half_open_max_probes=1`. Успех в CLOSED сбрасывает `failure_count`; вызов при OPEN → `CircuitBreakerError` + `total_rejected` (неawait'нутая корутина закрывается против ResourceWarning).

- **Главный потребитель:** `PropagationEngine` — breaker `"propagation_engine"` ([propagation_engine.py](../../../../src/memory/orchestrator/propagation_engine.py)) с порогами из `PropagationConfig`; защищает каскад доверия от самовозбуждения (см. [27.12 §6](27.12_Memory_Systems_Map.md)).
- **Observability (§27 P1 D1.4):** реальные переходы состояний пишутся fail-soft через `write_trace` в `memory-circuit.log` (`circuit`, `old→new`, `failure_count`, `last_error`); opt-out `MEMORY_CIRCUIT_LOG_DISABLE=1`.

**MCP:** `memory_circuit_status` (snapshot по имени или все из registry), `memory_circuit_reset` (форс-CLOSED).

## 5. Metrics — счётчики/латентности

**Класс:** `MetricsCollector` — [metrics.py](../../../../src/memory/infrastructure/metrics.py). In-memory, thread-safe (`threading.Lock`), **глобальный синглтон** `get_metrics_collector()` — его и берёт оркестратор. Без Prometheus.

- Три примитива: `counter(name, delta)`, `gauge(name, value)`, `observe_duration(name, sec)`; `timer(name)` — context-manager (`MetricsTimer`), авто-инкремент `{op}_calls` на входе и `{op}_errors` при исключении.
- `get_all()` → `{counters, gauges, durations:{count,total,average}, uptime_seconds}`.
- ⚠ Не персистентен: cross-process метрики (например, ingestion §26) дублируются в JSONL-логи именно потому, что синглтон не переживает границу процессов ([ingest_metrics.py](../../../../src/memory/orchestrator/ingest_metrics.py)).

**MCP:** `memory_metrics` (snapshot, `reset=true` обнуляет).

## 6. ForgetGate — два разных механизма забывания

### 6.1 Общий 4-стратегийный (`ForgetGateService`)

**Класс:** `ForgetGateService` — [forgetgate_service.py](../../../../src/memory/vector_memory/services/forgetgate_service.py). Storage-agnostic: оценивает `ForgetCandidate`-список, решения применяются через callback `apply_fn` — сам в Qdrant не ходит.

- **Стратегии** (`ForgetStrategy`): `confidence_decay` (экспонента `conf·e^(−decay_rate·age_days)`), `access_based` (штраф до 50% за простой > `access_decay_days`, буст ×1.1 при `access_count>10`), `surprise_based` (IDF по тегам через `SurpriseCalculator`; «рутина» при surprise < `routine_threshold` → ×0.8), `composite` (default; веса: confidence `1−0.3−0.2=0.5`, access `0.3`, surprise `0.2`).
- **Действия** (`ForgetAction`) по итоговому confidence (`_decide_action`): `< 0.05` → **DELETE**, `< 0.1` → **ARCHIVE**, `< 0.3` → **DECAY**, иначе **KEEP** (пороги — `delete_threshold=0.05`, `min_confidence=0.1`, hardcoded 0.3).
- `ForgetGateConfig`: `decay_rate=0.05`, `access_decay_days=30`, `batch_size=100`, `dry_run=False` (в классе; см. ниже).

**MCP `memory_forget`** ([memory_orchestrator.py](../../../../src/memory/orchestrator/memory_orchestrator.py)): `dry_run=True` **по умолчанию**, кандидаты передаются явно вызывающим (без `candidates` оценивается пустой список — авто-sweep store'ов инструмент **не делает**); возвращает stats + до 50 decisions. ⚠ Расхождение со схемой [27.12 §8](27.12_Memory_Systems_Map.md): стрелка «ForgetGate → vector-memory `expired_at`» в коде реализована **не** этим сервисом, а maintenance-вариантом ниже.

### 6.2 Maintenance-вариант §26 P4 (`plan_forget`)

**Модуль:** [forget_gate.py](../../../../src/memory/maintenance/forget_gate.py) (D4.2) — чистая I/O-free функция `plan_forget(points)` над Qdrant-scroll'ом `learned_patterns`. **Переиспользует §22 `should_archive`** из [confidence.py](../../../../src/memory/vector_memory/confidence.py) — политика архивации single-sourced:

- **fail-breach:** effective confidence < `fail_floor=0.40` — для ВСЕХ типов, включая invariant;
- **staleness:** idle > `staleness_days=180` (anchor = `last_applied` → `created_at`, бухгалтерские timestamps намеренно исключены) AND eff < `staleness_conf=0.75` AND не invariant (`architectural-principle`/`bsl-pattern`).

Результат — `ForgetPlan{archive, keep, already_archived, invariant_protected}` (последний показывает, кого invariant-exemption спас от staleness — bound виден в отчёте). Единственное действие — **ARCHIVE** (`set_payload {expired_at}`, invalidate-not-delete; revive — через `apply`, §22 P3).

**Когда какой:** общий `ForgetGateService` — универсальный движок для ad-hoc оценки произвольных сущностей через MCP (4 стратегии, 4 действия, включая DELETE); maintenance `plan_forget` — единственный **автономно работающий** в production путь забывания (bounded-growth `learned_patterns`, только archive, политика = §22).

## 7. §22 confidence — governance внутри vector-memory

§22 ([27.9](27.9_Confidence_Lifecycle.md)) — частный случай governance, встроенный per-pattern прямо в store: Beta(7,3)-posterior над time-decayed счётчиками `succ`/`fail` выполняет роль и TTL (decay к prior 0.70 при простое), и ForgetGate (`should_archive` → `expired_at`), и «versioning доверия» (lifecycle-лог `confidence-lifecycle.log`). Константы из кода: `PRIOR_SUCCESS=7.0`, `PRIOR_FAILURE=3.0` (prior mean 0.70), `DEFAULT_DECAY_RATE=0.05`, `COUNT_FLOOR=1e-6`, `STABILITY_K=0.3` (FSRS-lite `rate/(1+0.3·ln(1+n))` — established-паттерны затухают медленнее). Отличие от P4-сервисов: lazy decay-on-read (`payload_effective_confidence`) — без фонового sweep'а; raise/decay/forget/revive — см. таблицу в 27.9, математику здесь не дублируем. `apply_to_payload` при любом apply снимает `expired_at` (revive-on-apply) — обратный ход к maintenance-архивации §6.2.

### 7.1 WikiDecayService — второй, более старый decay-путь того же поля

**Класс:** `WikiDecayService` — [wiki_decay.py](../../../../src/memory/librarian/wiki_decay.py). Применяет **линейный** time-decay к `confidence` точек `learned_patterns`: `days_idle = (now − last_applied|updated_at|created_at).days`; `decay = decay_rate · (days_idle / 30.0)` (месячная каденция); `new_conf = max(min_confidence, old_conf − decay)`. `DEFAULT_DECAY_RATE=0.05` per 30 дней ([wiki_decay.py:29](../../../../src/memory/librarian/wiki_decay.py#L29)); `decay_rate` читается per-point из payload с тем же дефолтом ([wiki_decay.py:86](../../../../src/memory/librarian/wiki_decay.py#L86)). Вызывается только вручную из CLI [export_graph_to_wiki.py:332](../../../../scripts/export_graph_to_wiki.py#L332) (`cmd_decay_confidence` → `decay_all(dry_run)`) — **не** в maintenance-каденсе §8.

⚠ **Честно про пересечение:** WikiDecayService и §22 (7 выше) оба пишут `confidence` в тех же точках `learned_patterns`, но разными формулами (линейная vs Beta-count экспоненциальная) и с разной моделью «последнего касания» (`decay_applied_at`/`last_applied`/`updated_at`/`created_at` здесь vs `last_decay_at` там). Это НЕ единый канонический механизм — они сосуществуют в коде. Судя по коду, §22/`confidence.py` — актуальный lazy on-read/apply-путь, включённый в hot-path (`apply_pattern`); WikiDecayService — отдельный ручной CLI-sweep, не подключённый ни к какому автоматическому расписанию. Какой из них «главнее» при одновременном использовании (порядок применения, взаимный overwrite) в коде не определено — это открытый риск, а не задокументированный дизайн.

## 8. Maintenance cadence (§26 P4 D4.1) — оркестровка governance по расписанию

**Stop-хук** [memory-maintenance-cadence.py](../../../../.claude/hooks/memory-maintenance-cadence.py): раз в **N различных сессий** (default 10) детачит subprocess `scripts/memory_maintenance.py`. Cold-start — seed состояния без запуска; state `.claude/cache/memory-maintenance-cadence-state.json` (`pending_sessions` cap 200); stdout/stderr → `data/reports/memory/_maintenance.log`; никогда не блокирует Stop.

| Env | Default | Назначение |
|---|---|---|
| `MEMORY_MAINTENANCE_DISABLE=1` | — | полный opt-out хука |
| `MEMORY_MAINTENANCE_EVERY=N` | 10 | период в сессиях |
| `MEMORY_MAINTENANCE_APPLY=1` | — (dry-run) | разрешить запись |
| `MEMORY_MAINTENANCE_LOG_DISABLE=1` | — | отключить trace `memory-maintenance-runs.jsonl` |

**CLI** [memory_maintenance.py](../../../../scripts/memory_maintenance.py) — последовательность из 4 job'ов (каждый fail-soft, opt-out `--skip reflect,sync,promote,forget`; subprocess-таймаут 600 s):

```text
reflect  scripts/reflect_memory.py            episodic→semantic консолидация   [subprocess, --apply]
sync     scripts/cross_store_sync.py          MIRRORS-links + конфликты        [subprocess, --apply]
promote  export_graph_to_wiki promote-patterns learned→wiki drafts             [apply-only: skip в dry-run]
forget   plan_forget → set_payload(expired_at) ForgetGate-bound (D4.2)         [inline]
```

**DRY-RUN по умолчанию:** без `--apply` sub-jobs планируют, `promote` скипается, `forget` только классифицирует. С `--apply` архивация дополнительно: пишет `log_event("forget", source="memory_maintenance")` в `confidence-lifecycle.log` и делает `epoch.bump()` (иначе surfacing-cache §24 остаётся stale — §27 P0 D0.2). Финал — **D4.3 dashboard** ([dashboard.py](../../../../src/memory/maintenance/dashboard.py), чистый агрегатор): store sizes (Qdrant count / SQLite rows / JSONL lines / wiki drafts), `cross_store_dup_rate`, ingest/dup rates из `memory-ingestion.log`, forget-summary, link stats → `data/reports/memory/memory_maintenance_<stamp>.{md,json}` + одна summary-строка/run в `memory-maintenance-runs.jsonl`.

## 10. Типичные сбои и диагностика

- **MCP-сервер отдаёт старое governance-поведение** — persistent stdio-процесс держит код до `/mcp reconnect` ([[feedback-mcp-stale-code-reconnect]]); детектор «новый код» — событие `server_start` в `confidence-lifecycle.log`.
- **Cadence «не срабатывает»** — проверить `.claude/cache/memory-maintenance-cadence-state.json`: cold-start только seed'ит; нужно ≥ `MEMORY_MAINTENANCE_EVERY` **различных** session_id. Лог запуска — `data/reports/memory/_maintenance.log`.
- **ForgetGate «ничего не архивирует»** — норма на свежем корпусе: `should_archive` требует eff<0.40 ИЛИ 180+ дней простоя; `invariant_protected` в dashboard показывает, кого спас exemption. После apply-архивации без видимого эффекта в surfacing — проверить, был ли `epoch.bump()` (без него cache stale до 5 мин).
- **Audit-записи пропадают** — буферизованные не-деструктивные события доезжают до диска только при flush (full buffer / `orchestrator.stop()`); упавший процесс теряет хвост буфера. Деструктивные (DELETE/ROLLBACK/CONFIG_CHANGE) — всегда на диске.
- **Circuit застрял в OPEN** — переход в HALF_OPEN ленивый (вычисляется в property `state` при следующем обращении); форс — `memory_circuit_reset`. История инцидентов — `memory-circuit.log`.
- **Versioning-файл растёт** — by design: JSONL append-only, `max_versions` прунит только cache (см. §2).
- **Метрики «обнулились»** — `MetricsCollector` in-memory: каждый процесс (hook vs MCP-сервер) видит свой синглтон; cross-process истина — JSONL-sinks (§27 observability).
