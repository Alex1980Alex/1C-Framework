### 2026-06-05 — Surfacing TEI-import fix (найден сквозной проверкой §27)

- `memory-first-hook` логировал `tei=down` со `ModuleNotFoundError: shared.semantic_search` на 100% вызовов — dense-плечи всегда пусты. Причина — **namespace-collision**: `src/shared/` (реальный пакет) затенял собственный `.claude/hooks/shared/` хука при `sys.path.insert(0, src_path)` (ради `memory.*`) → первый `import shared` привязывался к `src/shared` (без `semantic_search.py`/`pattern_reinforce.py`) на весь процесс. Фикс — `append` вместо `insert(0)` на 2 точках (hooks-dir остаётся на `sys.path[0]`); после — `tei=ok`, плечи `{skill,pattern_dense,pattern_lexical}` populated, hybrid восстановлен. Правило: в хуках, импортирующих и `shared.*` (hooks-local) и `memory.*` (src), добавлять `src` через **`append`**, НЕ `insert(0)` ([[feedback-hook-src-shared-collision]]).    `on_present(item, pid)`; идемпотентен (`create_link` бросает на дубль, `make_link_fn`
   глотает). Второй потребитель (`harvest`) параметр не передаёт — контракт цел.

Плюс: дефолты были **захардкожены в argparse** поверх констант модуля, а каденс идёт через
CLI → правка `reflection.py` была no-op (`_build_parser` + дефолты из модуля); `harvester="reflection"`
(без него записи reflect неотличимы от чужих и критерий записи не построить); per-job
`_job_apply` + `MEMORY_MAINTENANCE_APPLY_<JOB>` — общий флаг раздал бы запись сразу 5 джобам,
включая production `wiki_pages_v1`/`skill_library`. ⚠ покрывает только `SUBPROCESS_JOBS`,
для 5 инлайн-джобов — молчаливый no-op (fail-closed + docstring).

**Попутно — латентный баг с рождения:** fallback-импорт в `reflection.py` (`# pragma: no cover`)
не регистрировал модуль в `sys.modules` до `exec_module`, а `@dataclass` в `pattern_harvest`
читает `sys.modules[cls.__module__]` во время исполнения тела класса → `None.__dict__`.
Ветка никогда не исполнялась, поэтому и не падала. `read_episodes` теперь фильтрует
`archived_at`: `min_cluster=2` **активировал** латентный конфликт с forget-gate (архивный
контент дистиллировался бы в свежий паттерн 0.70 с вечными рёбрами на архивные id).

### Критерий 5 заменён (⚠ при сравнении с историей)

`reflection>=1` (рёбра, созданные **в окне**) — **неудовлетворим по построению**: reflection
идемпотентен и отработал 2026-06-11, за день до открытия окна. Он не «проспал» баг — честно
горел красным, но не отличал «сломано» от «нечего делать». Замена:

| Критерий | Что ловит |
|---|---|
| `reflection_reachable` — `clusters_triggered>0` через реальный `reflect(dry_run=True)` | мёртвый триггер (до фикса дал бы 0 → FAIL) |
| `reflection_wrote` — ingest-события `harvester=reflection` **за 30д** | возврат в dry-run (флаг живёт в gitignored `settings.local.json`) |

Вариант «рёбер всего ≥1» отвергнут — был бы зелёным все 5 недель при мёртвом триггере.
Окно у критерия 6 **удовлетворимо**, вопреки логике критерия 5: apply-прогон над уже
собранным корпусом уходит в `skipped_dup` и эмитит `dup`-событие на хеш, то есть каждый
прогон даёт ≥1 событие. Аргумент идемпотентности сюда **не переносится** — это поймал
второй ревьюер. Ср. вакуумно-истинный `archive_ran` — тот же класс дефекта, зеркально.

### Верификация

Два адверсариальных ревью (PARTIAL → FAIL → фиксы). Второй снял первую редакцию замены:
она **не наблюдала путь записи вообще** (оба критерия зелёные при reflect в вечном dry-run),
и поймал вакуумный тест (`save_to_sqlite` застаблен → `assert "dup" not in []` проходил
тривиально), непокрытую строку проводки `apply = _job_apply(name, apply)`, и баннер каденса,
писавший «dry-run» пока reflect мутировал прод.

**Системная находка:** CI собирает строго по маркерам (`-m "unit and not slow"` /
`-m "integration or e2e"`), а `tests/integration/test_memory_p5_session_save.py` маркера не
имел → слом контракта `already_saved` оставил 5 красных тестов при зелёном CI. Маркер
проставлен; **ещё 27 файлов в `tests/integration/` без маркера в CI не гоняются** — открытый долг.

**2376 unit** + 28 integration + **саботаж-харнесс 14/14** (харнесс поймал сам себя:
устаревший якорь → `[SKIP-BROKEN] harness is lying`). Первые тесты на
`memory_ai_acceptance.py` — [`tests/unit/test_memory_ai_acceptance.py`](../../../../tests/unit/test_memory_ai_acceptance.py),
включая `test_each_criterion_can_fail` (ни один критерий не может быть структурно
нефальсифицируемым). Пайплайн — `pipeline/fix-memory-ai-zero-criteria/`.
Память: [[reference-acceptance-criteria-idempotent-jobs]], [[reference-cadence-dry-run-silent-noop]].

## 2026-07-25 — Event-driven синки ≠ регрессия наблюдаемости

Детектор freshness (§27 P4) держал в постоянном алерте три синка под формулировкой
«these sinks were logging and went silent». Терялось не наблюдение, а **посылка**: у
`propagation` / `circuit` / `links` нет планового писателя — они пишут ТОЛЬКО по событию.

Доказательства (замер по живым логам):

| Синк | Последняя запись | Что это за дата |
|---|---|---|
| `propagation` | 2026-06-11 (1046 ч) | сессия внедрения honest-failure контракта |
| `circuit` | 2026-07-17 (203 ч) | сессия payload hardening P1 |
| `links` | 2026-07-17 (181 ч) | сессия link-aware дедупа |

То есть последние записи совпадают с сессиями, где эти синки и **реализовали** —
органического трафика у них не было никогда. Сверх того:

- `propagate_update` не имеет продакшн-вызывающих: только диспетч MCP-тула оркестратора
  ([`memory_orchestrator.py`](../../../../src/memory/orchestrator/memory_orchestrator.py)),
  ни один хук его не зовёт;
- единственная hook-side точка `create_link` ([`shared/reflection.py`](../../../../.claude/hooks/shared/reflection.py))
  лежит в модуле, который **не импортирует ни один хук**;
- `circuit` пишется только на переходе breaker'а — для него молчание прямо означает
  «ни один breaker не сработал», то есть хорошую новость.

Тот же класс, что закрыли §26 Q1 ADR по коллекциям `experience`/`conversation`:
0-writer синк выводят из наблюдения либо ретирят, а не алертят на него вечно.

**Реализация.** `EVENT_DRIVEN_SOURCES` в [`event_envelope.py`](../../../../src/memory/infrastructure/event_envelope.py)
— рядом с `CACHE_LOGS`, единственным source of truth для expected-set (добавление синка
туда проводит его и в DuckDB-слой, и в детектор). `analyze_freshness` переводит такой синк
в статус **`quiet`** вместо `stale`, из-за чего он выпадает из `report["regressions"]`, а с
ним — из маркера `[REGRESSION]` и обоих потребителей: баннера
[`memory-maintenance-cadence`](../../../../.claude/hooks/memory-maintenance-cadence.py) (P1.4)
и `infra_alerts` в tool-health ([`analyze_tool_health.stale_sinks`](../../../../scripts/analyze_tool_health.py), N-P1.1).
В отчёте статус виден и объяснён нотой — синк не спрятан, а переклассифицирован.

Было `8 fresh · 3 stale (regressions) · 0 cold` → стало
`8 fresh · 0 stale · 3 quiet (event-driven) · 0 cold`; `stale_sinks()` отдаёт `[]`.

Регресс — 2 теста в [`test_memory_observability.py`](../../../../tests/unit/test_memory_observability.py)
на обе стороны инварианта: три event-driven синка при 1000 ч молчания дают `quiet` и пустые
`regressions`; синк с плановым писателем (`surfacing`) при том же молчании по-прежнему
`stale` и попадает в `regressions`. 2688 unit зелёные.

⚠ **Диагностика, если синк молчит:** сперва определить, event-driven он или плановый.
Для плановых (`lifecycle`/`surfacing`/`ingestion`/`metrics`/`maintenance`) молчание —
реальный сигнал. Для event-driven надо смотреть, происходило ли само событие, а не когда
последний раз писали в лог.
