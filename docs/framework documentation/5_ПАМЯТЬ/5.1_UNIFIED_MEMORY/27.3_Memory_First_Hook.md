# 27.3 Memory-First Hook — автоконтекст памяти

> **Migration note (Phase 9.1, 2026-04-30, commit `ac91c4b7`):** Layer 2 переключён с **Ollama nomic-embed-text 768d** на **TEI Qwen3-Embedding-8B 4096d**. До 2026-04-30 hook имел silent dim mismatch (hook embedding 768d vs collections 1024d) — Qdrant возвращал 0 результатов, fallback на token overlap через `learned_patterns` маскировал проблему. Теперь все 3 коллекции (`skill_library`, `experience_embeddings`, `conversation_memory`) — **4096d**, embed cold ~600ms vs Ollama ~2s. Подробности: [31.5 Миграция и итоги § Lessons learned #2](../../2_КОНТЕКСТ/2.8_QWEN3_RETRIEVAL_PRODUCTION/31.5_Миграция_и_итоги.md).

## Проблема

MCP-серверы памяти (memory-ai, vector-memory, skill-learning) — это инструменты, которые Claude вызывает **по своему решению**. Нет гарантии, что перед ответом он проверит память проекта. Результат: повторные объяснения, потеря контекста, игнорирование ранее принятых решений.

## Решение

Фаза **P0.5** добавляет `UserPromptSubmit` hook, который перехватывает каждый промпт пользователя и автоматически ищет релевантные записи в памяти **до** начала ответа. Найденный контекст печатается в `stdout` (Claude Code инжектирует plain-text stdout UserPromptSubmit-хуков в контекст модели), и Claude получает его до генерации.

> **Fix 2026-04-05:** раньше использовался `systemMessage` — это *user-facing warning*, Claude его не видит. Реальная reach rate была ~55%. После перехода на `print(stdout)` — 100%. См. [архитектурный кеш](../../../../.claude/skills/architecture-research/cache/userpromptsubmit-hook-output-formats.md).

**Эволюция:**
- **P0.5 (2026-04-04):** single-layer `.md` поиск с Russian stemming
- **P5.2 (2026-04-05):** 3-layer federated recall (SQLite + Qdrant + `.md`) с RRF merge
- **P5.2 v3 (2026-04-09, legacy — superseded by Phase 9.1 below):** Layer 2 → semantic search (Ollama nomic-embed-text 768d + 3 Qdrant коллекции). IPv4 fix. Companion hook `session-context-enforcer.py`
- **Phase 9.1 (2026-04-30, commit `ac91c4b7`):** Layer 2 alignment — Ollama nomic 768d → TEI Qwen3-Embedding-8B 4096d. Все 3 коллекции пересозданы на 4096d. Silent dim mismatch (768d query vs 1024d collections) устранён
- **§24 (2026-05-31, ADR-D6):** `learned_patterns` всплывают **семантически** (добавлены в `SEMANTIC_COLLECTIONS`) + **confidence-gating** (§22 `effective_confidence`) + **hybrid RRF** (dense ⊕ always-on lexical arm, lexical 0.7/dense 0.3 для BSL) + execution-cache + epoch-invalidation + surfacing trace-log. Token-overlap из «fallback» стал **постоянным lexical-плечом** (не только TEI-down). Подробности: [27.10 Memory Surfacing Quality](27.10_Memory_Surfacing_Quality.md)

**Файл:** [`.claude/hooks/memory-first-hook.py`](../../../../.claude/hooks/memory-first-hook.py)
**Событие:** `UserPromptSubmit`
**Тесты:** 29 PASS (`tests/integration/test_memory_first_hook.py`)

## Алгоритм scoring

### Layer 3 (.md) — весовая модель токенов

| Поле `.md` | Вес | Обоснование |
|---|---|---|
| `name` (YAML frontmatter `name`) | ×3 | Самый сильный сигнал |
| `description` (YAML frontmatter `description`) | ×2 | Краткая характеристика |
| body (содержимое файла) | ×1 | Дополнительный контекст |

Формула layer-score (.md):

```
score = 0.7 × query_coverage + 0.3 × memory_density
threshold = 0.3
```

### Layer 1 (SQLite) и Layer 2 (Qdrant) — token overlap

```
score = |overlap| / |query_tokens|
+ 0.2 если какой-то query_token присутствует в tags (SQLite)
threshold = 0.3
```

### RRF merge (Reciprocal Rank Fusion)

```
fused_score(item) = Σ_layer [ weight_layer × 1 / (k + rank_layer) ]   k=60

дедуп: sha1(content[:200])[:16] — если hash совпадает, RRF scores суммируются
```

Результаты сортируются по `fused_score DESC`, возвращаются top-5 (`MAX_RESULTS`).

### Логика

1. Токенизация промпта (lowercase, split по не-буквенным символам)
2. Стемминг каждого токена кириллицы (см. Russian Stemming ниже)
3. Для каждой памяти: токенизация + стемминг полей name/description/body
4. Подсчёт пересечения стеммов с весами по полям
5. Вычисление coverage и density, комбинация в `score`
6. Отсечение по threshold, сортировка по убыванию score
7. Топ-5 печатается в stdout (plain text, Claude Code инжектирует его в контекст)

## Russian Stemming (v1.1)

Лёгкий суффиксный стриппер без морфологии (не pymorphy3 — для скорости). Работает только с кириллицей, минимальная длина стема — 3 символа.

### Таблица правил

37 суффиксов обрабатываются в порядке убывания длины (16×3-char → 13×2-char → 8×1-char):

| Длина | Суффиксы |
|---|---|
| 3-char | ами, ями, ова, ева, его, ого, ему, ому, ыми, ими, ыми |
| 2-char | ам, ям, ом, ем, ей, ий, ый, ой, ая, яя, ое, ие, ые, ую, юю, ов |
| 1-char | а, я, о, е, у, ю, ы, и, ь |

### Примеры

| Словоформа | Стем | Удалённый суффикс |
|---|---|---|
| агенты | агент | -ы |
| агентов | агент | -ов |
| агентам | агент | -ам |
| агентами | агент | -ами |
| документации | документаци | -и |
| документацию | документаци | -ю |
| конфигурации | конфигураци | -и |
| хуков | хук | -ов |
| настройка | настройк | -а |

### Ограничения

- Английские токены не стеммируются (работают хорошо и так)
- Минимальная длина стема — 3 символа (защита от избыточного обрезания)
- Обрабатывается только кириллица
- Без морфологии: "конфигурация" → "конфигураци" (не идеально, но достаточно)
- Транслитерация cyr↔lat не выполняется

## Оптимизации

| Параметр | Значение | Назначение |
|---|---|---|
| Min prompt length | 20 символов | Пропуск приветствий и коротких команд |
| Cooldown | 30 секунд | Файл `cache/memory-first-cooldown.json` |
| Timeout | **10 секунд** (budget `TOTAL_BUDGET=3s`; hook-timeout поднят 5→10 в `settings.json` 2026-06-30 — avg ~3.6s / max ~4.7s упирались в 5s-лимит) | TEI embed + мультиколлекционный Qdrant RRF + lexical arms |
| Score threshold | 0.3 | Отсечение низкорелевантного шума |
| Skip patterns | `/command`, однословные | Служебные запросы |
| Embedding model | Qwen3-Embedding-8B (4096d, Phase 9.1) | TEI Docker `pdf-rag-tei` localhost:8080 |
| Embed timeout | 1.5 секунды (TEI cold ~600ms) | Fallback на token overlap если TEI недоступен |

### TEI keep-alive (2026-06-30)

Cold-start TEI (~385 мс против ~36 мс warm) добавлял джиттер каждому UPS-прогону. SessionStart-хук
[`tei-warmup-on-start.py`](../../../../.claude/hooks/tei-warmup-on-start.py) детачем спавнит
[`scripts/tei_keepalive.py`](../../../../scripts/tei_keepalive.py) — single-instance keep-alive демон:
heartbeat-lock `.claude/cache/tei-keepalive.lock`, пинг `POST localhost:8080/embed` каждые 240 с,
bounded 6 ч. Opt-out `TEI_KEEPALIVE_DISABLE=1`, тюнинг `TEI_KEEPALIVE_INTERVAL`/`_DURATION`.
Демон защищён от случайного kill хуком `process-guard.py` (см. [09.7](../../7_ПРОВЕРКА/7.2_АДМИНИСТРИРОВАНИЕ/09.7_Система_хуков.md)).

### Graceful degradation

При любой ошибке hook возвращает `{"continue": true}` и логирует в `cache/hooks-error.log`. Пользователь не видит сбоев, Claude продолжает работу без контекста памяти.

## Инструменты для прямого запроса (в обход хука)

Если нужно обойти hook (debugging, exploratory) — отдельные MCP-инструменты, независимые от внутренней (прямой DB/Qdrant-client) реализации хука ([`.mcp.json`](../../../../.mcp.json)):

```python
# Layer 1-эквивалент
mcp__memory-ai__search_messages(query="...", limit=10)
mcp__memory-ai__get_important_messages(limit=5)

# Layer 2-эквивалент
mcp__vector-memory__search_patterns(query="...", limit=20)
mcp__vector-memory__get_pattern(pattern_id="...")

# Wiki (через obsidian-mcp, когда server running)
mcp__obsidian-mcp__obsidian_simple_search(query="...")
mcp__obsidian-mcp__obsidian_complex_search(filters=...)

# Multi-collection (НЕ вызывается хуком — отдельный путь через оркестратор)
mcp__memory-orchestrator__unified_search(query="...", targets=["wiki","graph","patterns"])
mcp__memory-orchestrator__get_related(unified_id="...", depth=2)
```

## Antipatterns

| Плохо | Почему | Как правильно |
|---|---|---|
| Полагаться на semantic поиск по wiki внутри memory-first-hook | `search_wiki()` (`.claude/hooks/memory-first-hook.py:761`) — stub, всегда `[]` | Для wiki-поиска использовать `mcp__obsidian-mcp__*` или `unified_search` напрямую |
| Игнорировать Layer 4 wiki weight (0.20) как «мёртвый груз» в тюнинге RRF | Вес зарезервирован под будущую реализацию — легитимная noop-константа, не баг | При тюнинге весов учитывать, что Layer 4 сейчас 0 вклада — эффективно распределяет relative влияние оставшихся 3 слоёв |
| Ожидать параллельный (`asyncio.gather`) fetch слоёв | Хук синхронный (`BaseHook`), вызовы `search_sqlite`/`search_qdrant`/`search_md`/`search_wiki` последовательные | Профилировать через per-stage trace-log в `.claude/cache/memory-first-surfacing.log` |
| RRF k=10 вместо 60 | Слишком жёсткий cutoff long-tail | `SURFACE_RRF_K = 60` (industry default, well-tested) |

## Companion: session-context-enforcer (v3)

Дополнительный `UserPromptSubmit` hook, работающий в паре с `memory-first-hook`. Два режима:

| Режим | Триггер | Действие | Cooldown |
|---|---|---|---|
| **A: Session query** | "предыдущая сессия", "что было", "previous session" | systemMessage: "MCP memory-orchestrator first, git second" | Нет |
| **B: Task prompt** | "сделай", "создай", "реализуй", "implement", "fix" и др. | systemMessage: "проверь unified_search на связанные работы" | 5 минут |

**Файл:** `.claude/hooks/session-context-enforcer.py`

**Архитектура «90/10» (ClawMem-паттерн):**
- `memory-first-hook` автоматически инжектит 90% контекста через semantic search (hook → Qdrant → stdout)
- `session-context-enforcer` инструктирует Claude вызвать MCP memory-orchestrator для оставшихся 10% (сложные запросы, кросс-системный поиск)
