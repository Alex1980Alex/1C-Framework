# 32.2 Архитектура

Wiki Knowledge Layer состоит из **5 сервисных классов** в одном модуле [`src/pdf_framework/indexing/wiki_exporter.py`](../../../../src/pdf_framework/indexing/wiki_exporter.py) + **внешний адаптер** `MemoryCube` для serialization/deserialization. Все сервисы independent — могут использоваться по отдельности или комбинированно. Координация — через общий `WikiExportConfig` и event bus.

### Сервисы

#### 1. `WikiExporter` ([wiki_exporter.py:158](../../../../src/pdf_framework/indexing/wiki_exporter.py#L158))

**Назначение:** Graph entity → markdown файл. Базовая операция для всех остальных сервисов.

**Публичные методы:**

| Метод | Что делает |
|---|---|
| `export_entity(entity_id) → Path \| None` | Экспорт одной entity. Возвращает путь к файлу или `None` если entity не найдена. Idempotent (сравнивает hash frontmatter + body, пропускает неизменённые). |
| `export_all() → ExportResult` | Batch экспорт всех entities из graph_store. Поддерживает `batch_size` и `dry_run`. |
| `_sanitize_filename(name) → str` | Канонизация slug: lowercase, kebab-case, без consecutive hyphens, max 80 chars. |

**Алгоритм `export_entity`:**

```
1. graph_store.get_entity(entity_id) → Entity | None
   ├─ если None → return None
   └─ если found → продолжаем

2. graph_store.get_neighbors(entity_id, depth=1) → SubGraph
   → собираем list[Relation] (limit max_relations_per_page)

3. Build frontmatter (YAML):
   unified_id, status: active, confidence, tags (from entity),
   related: [[<sanitized-target>]] для каждой Relation,
   created_at, updated_at, source_pdf (from properties)

4. Build body (markdown):
   # <name>
   ## Properties (table из entity.properties)
   ## Source chunks (top source_chunk_limit chunks)
   ## Connections (related entities с relation_type)

5. Compute SHA1 над frontmatter + body
   ├─ если file exists AND existing hash == new hash → skip (idempotent)
   └─ иначе write_text(encoding="utf-8")

6. return Path(file)
```

#### 2. `ForwardSyncService` ([wiki_exporter.py:333](../../../../src/pdf_framework/indexing/wiki_exporter.py#L333))

**Назначение:** Catch-up sync по timestamp. Не event-driven — используется при start-up или после простоев когда события могли быть пропущены.

**Публичные методы:**

| Метод | Что делает |
|---|---|
| `sync_entity(entity_id) → Path \| None` | Sync одной entity (обёртка над `WikiExporter.export_entity` с retry-friendly интерфейсом) |
| `sync_since(timestamp) → ExportResult` | Все entities у которых `updated_at >= timestamp` |

Используется как backend для `IncrementalWikiSync._sync_with_retry`.

#### 3. `IncrementalWikiSync` ([wiki_exporter.py:432](../../../../src/pdf_framework/indexing/wiki_exporter.py#L432))

**Назначение:** Event-driven sync. Подписывается на EventBus, обрабатывает `graph.*` события асинхронно. Включает DLQ для persistent failures, metrics для observability, exponential backoff retry.

**Публичные методы:**

| Метод | Что делает |
|---|---|
| `start()` | Подписывается на EventBus topic `graph.*` через `_listen_loop()` (async task). Активирует обработку очереди. |
| `stop()` | Cancel'ит listener task, ждёт завершения in-flight events. |
| `handle_event(event: GraphChangeEvent)` | Внешняя точка входа: dispatcher по `event_type`. Можно дёргать вручную помимо EventBus. |

**Внутренние:**

- `_sync_with_retry(entity_id)` — `tenacity.AsyncRetrying` с `_BACKOFF_DELAYS` schedule + `stop_after_attempt`. После исчерпания → DLQ entry + metric `wiki_sync_failures_total`.
- `_delete_wiki_page(entity_id)` — удаление файла при `ENTITY_DELETED` событии.
- `_should_sync(event)` — фильтр noisy events (`change_type=="embedding_only"` skip'аются).
- `_write_failed_event(entity_id, reason)` — append JSONL в `data/wiki_sync_dlq.jsonl`.

**Retry policy** (Phase 6.5, см. roadmap §3.7):

```python
async for attempt in AsyncRetrying(
    stop=stop_after_attempt(self._max_retries),
    wait=wait_chain(*[wait_fixed(d) for d in self._BACKOFF_DELAYS]),
    retry=retry_if_exception_type(Exception),
    reraise=True,
    before_sleep=lambda state: logger.warning(...),
):
    with attempt:
        await self._forward_sync.sync_entity(entity_id)
```

`_BACKOFF_DELAYS = [1, 2, 5, 10, 30]` (секунды) — exponential growth, плато на 30s. После 5 неудач → DLQ.

#### 4. `ReverseSyncService` ([wiki_exporter.py:597](../../../../src/pdf_framework/indexing/wiki_exporter.py#L597))

**Назначение:** Markdown → Graph. Watchdog observer на `docs/wiki/entities/`. Edit'ы в файлах распознаются через `on_modified`/`on_created`/`on_deleted`, парсятся (YAML frontmatter + regex `[[link]]`), и трансформируются в `add_relation` calls на graph_store.

**Публичные методы:**

| Метод | Что делает |
|---|---|
| `start_watching()` | Spawn `watchdog.observers.Observer` на `wiki_dir`, регистрирует `WikiHandler(FileSystemEventHandler)`. Recursive=False (только prefix dir). |
| `stop_watching()` | `observer.stop()` + `observer.join(timeout=5)` |
| `handle_page_change(change: WikiPageChange)` | Внешняя точка входа (testable). Для `change_type=="deleted"` — no-op. Для остальных — извлекает links → `Relation` объекты → `graph_store.add_relation(...)`. |

**Внутренние:**

- `_parse_wiki_page(path) → WikiPageChange` — `yaml.safe_load` frontmatter + regex `\[\[([^\]|]+)(?:\|[^\]]+)?\]\]` для links. Invalid YAML → `WikiParseError`.
- `_on_file_event(path, change_type)` — debounce (`debounce_s=2.0` default), parse, dispatch на `handle_page_change`.
- `_last_processed: dict[str, float]` — per-path mtime cache для debounce.

#### 5. `WikiSearchIndexer` ([wiki_exporter.py:753](../../../../src/pdf_framework/indexing/wiki_exporter.py#L753))

**Назначение:** Индексация wiki-страниц через инжектируемый `hybrid_search` (duck-typed `Any`) объект, вызываемый как `HybridSearchService` (BM25 + dense через TEI Qwen3) в `scripts/export_graph_to_wiki.py cmd_index_search`.

**Публичные методы:**

| Метод | Что делает |
|---|---|
| `index_all_pages() → int` | Glob по `wiki_dir/*.md`, вызывает `index_page` на каждый файл, ловит исключения per-file. Возвращает счётчик успешно обработанных (без учёта пустых страниц). |
| `index_page(path) → None` | Index одной страницы (для incremental updates). Возвращает `None` — success/failure не сигнализируется вызывающему, только через exception + `logger.warning`. |
| `remove_page(entity_id) → None` | Снимает документ с индекса через `hybrid_search.remove_document(entity_id)`. |
| `_extract_searchable_text(page_path) → str` | Strips YAML frontmatter, resolves `[[target\|display]]` и `[[target]]` → plain text. Метода `_extract_metadata` в текущем коде нет — metadata строится inline в `index_page`. |

Используется в `LightRAGStrategy.search()` через `HybridSearchService` — wiki-страницы возвращаются как `wiki_page_paths` в `SearchResponse.metadata` параллельно с обычными chunk-результатами.

## Адаптер: `MemoryCube`

[`src/memory/orchestrator/memcube.py`](../../../../src/memory/orchestrator/memcube.py) — унифицированный data class из chapter 27, используется как точка serialization между L2 и L3:

```python
@dataclass
class MemoryCube:
    content: str
    content_type: ContentType   # CODE / WIKI / EPISODIC / SKILL
    memory_type: MemoryType      # EPISODIC / SEMANTIC / WIKI
    source: SourceServer
    title: str | None
    confidence: float
    tags: list[str]
    what: str | None
    importance: float = 0.5
    # ... + metadata, timestamps, unified_id

    def to_wiki_page(self, status: str | None = None) -> str:
        """Render as YAML frontmatter + markdown body."""

    @classmethod
    def from_wiki_page(cls, content: str) -> MemoryCube:
        """Parse YAML frontmatter + body → MemoryCube."""
```

Round-trip контракт: `MemoryCube == MemoryCube.from_wiki_page(cube.to_wiki_page())` — обеспечивает безопасную миграцию L2 ↔ L3 (используется в `WikiPromoter._create_draft` и в `ReverseSyncService` при future migration scenarios).

## EventBus integration (Phase 6.5)

Сервис `IncrementalWikiSync` подписывается на topic `graph.*` через [`src/memory/infrastructure/event_bus.py`](../../../../src/memory/infrastructure/event_bus.py). События генерируются `IncrementalGraphUpdater` при изменении графа:

| Event type | Когда генерируется | Action в wiki sync |
|---|---|---|
| `graph.entity.created` | `add_entity()` | `_sync_with_retry(entity_id)` → новый файл |
| `graph.entity.updated` | `update_entity()` | `_sync_with_retry(entity_id)` → перезапись (idempotent skip если hash совпал) |
| `graph.entity.deleted` | `delete_entity()` | `_delete_wiki_page(entity_id)` → unlink файла |
| `graph.relation.added` | `add_relation()` | `_sync_with_retry()` для обоих affected entities (frontmatter `related` обновляется) |
| `graph.relation.removed` | `delete_relation()` | то же, что added |
| `graph.community.merged` | community detection re-run | sync всех affected entities (могут поменяться `community_id` поля) |

EventBus реализован как async pub/sub в памяти процесса. WikiPromoter тоже опционально публикует свои события (`wiki.draft.created`) — но потребителей пока нет.

## Конкурентность

- `WikiExporter._lock: asyncio.Lock` — защищает запись на диск (DLQ append + frontmatter write идут под одним lock'ом, чтобы избежать torn writes).
- `IncrementalWikiSync._listen_loop()` — single async task, обрабатывает события sequentially (не параллельно) чтобы упростить retry semantics и DLQ ordering.
- `ReverseSyncService._last_processed` — in-memory dict, не thread-safe; watchdog observer работает в одном thread'е, async-tasks планируются через `loop.create_task` — конкурентного доступа к dict нет.
- Multi-process scenario: pipeline предполагает single-writer per `output_dir`. Если 2 процесса параллельно запустят `export-all` — конфликт через filesystem (последняя запись win'ит). Hardening через filesystem lock — future enhancement.
