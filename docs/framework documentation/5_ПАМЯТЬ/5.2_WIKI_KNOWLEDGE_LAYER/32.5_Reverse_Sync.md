# 32.5 Reverse Sync — Wiki → Graph

Reverse sync — это направление **docs/wiki/entities/*.md → GraphStore**: edit'ы в markdown файлах (например, через Obsidian, VS Code, или прямое редактирование) автоматически отражаются в knowledge graph. Реализован через `ReverseSyncService` с watchdog observer на файловой системе.

L3 = canonical = wiki — это **система записи** для high-confidence knowledge. Edits в файлах являются authoritative и должны распространиться обратно в граф.

## Архитектура

```
User edit docs/wiki/entities/<id>.md
        │
        ▼ (filesystem event)
┌──────────────────────────────────────────┐
│ watchdog Observer                         │
│   schedule(WikiHandler, wiki_dir,         │
│            recursive=False)               │
└──────────────┬───────────────────────────┘
               │
               ▼
┌──────────────────────────────────────────┐
│ WikiHandler(FileSystemEventHandler)       │
│   on_modified  → schedule async task      │
│   on_created   → schedule async task      │
│   on_deleted   → schedule async task      │
└──────────────┬───────────────────────────┘
               │ loop.create_task(...)
               ▼
┌──────────────────────────────────────────┐
│ ReverseSyncService._on_file_event(path,   │
│                                  type)    │
│   1. Debounce check                       │
│   2. Parse (frontmatter + links)          │
│   3. Dispatch to handle_page_change       │
└──────────────┬───────────────────────────┘
               │
               ▼
┌──────────────────────────────────────────┐
│ handle_page_change(change: WikiPageChange)│
│   For each new link in change.added_links:│
│     graph_store.add_relation(Relation(...))│
└──────────────────────────────────────────┘
```

## Lifecycle

### Start watching

```python
await reverse_sync.start_watching()
```

Внутри:

```python
from watchdog.events import FileSystemEventHandler
from watchdog.observers import Observer

service = self

class WikiHandler(FileSystemEventHandler):
    def on_modified(self, event):
        if event.src_path.endswith(".md"):
            try:
                loop = asyncio.get_event_loop()
                loop.create_task(service._on_file_event(event.src_path, "modified"))
            except RuntimeError:    # no running loop
                pass

    def on_created(self, event):    # idem с "created"
        ...

    def on_deleted(self, event):    # idem с "deleted"
        ...

self._observer = Observer()
self._observer.schedule(WikiHandler(), str(self._wiki_dir), recursive=False)
self._observer.start()
```

**Ограничения watchdog:**
- `recursive=False` — следим только за prefix dir (`docs/wiki/entities/`), не за поддиректориями. Drafts/, archive/, patterns/ — отдельные observers (или не нужны для reverse sync).
- На Windows используется `ReadDirectoryChangesW` (native). На Linux — `inotify`. На macOS — `FSEvents`. Для Docker volumes inotify может не работать; fallback: polling observer (см. watchdog docs).
- Watchdog Observer runs в отдельном thread'е. `loop.create_task` диспатчит обратно в asyncio event loop того треда, в котором был старт.

### Stop watching

```python
await reverse_sync.stop_watching()
```

```python
async def stop_watching(self) -> None:
    if self._observer:
        self._observer.stop()
        self._observer.join(timeout=5)
        logger.info("[REV-SYNC] Stopped watching")
```

Join timeout — защита от висящего observer thread'a.

## Debounce

Watchdog часто эмитит **дубли** событий: при сохранении файла из текстового редактора может прийти 2-3 `on_modified` подряд (depend on save strategy редактора). Plus после `created` обычно следует `modified` от того же редактирования.

`ReverseSyncService` использует **per-path debounce** через `_last_processed: dict[str, float]`:

```python
async def _on_file_event(self, path: str, change_type: str) -> None:
    now = time.monotonic()
    last = self._last_processed.get(path, 0)
    if now - last < self._debounce_s:                  # default 2.0s
        return
    self._last_processed[path] = now
    # ... continue processing
```

Default `debounce_s = 2.0` — компромисс между responsiveness и noise filtering. Тесты используют `debounce_s=0.0` для синхронной верификации.

## Парсинг wiki-страницы

```python
def _parse_wiki_page(self, path: Path) -> WikiPageChange:
    content = path.read_text(encoding="utf-8")
    entity_id = path.stem                              # "e1.md" → "e1"

    fm_match = re.match(r"^---\n(.*?)\n---", content, re.DOTALL)
    frontmatter: dict = {}
    body = content

    if fm_match:
        import yaml
        try:
            frontmatter = yaml.safe_load(fm_match.group(1)) or {}
        except Exception as exc:
            raise WikiParseError(f"Invalid frontmatter in {path}: {exc}") from exc
        body = content[fm_match.end():]

    links = re.findall(r"\[\[([^\]|]+)(?:\|[^\]]+)?\]\]", body)

    return WikiPageChange(
        entity_id=entity_id,
        page_path=path,
        change_type="modified",                        # каллер может override
        frontmatter=frontmatter,
        added_links=links,
    )
```

### Edge cases

| Случай | Поведение |
|---|---|
| Файл без frontmatter | `frontmatter = {}`, `body = content` целиком |
| Frontmatter с invalid YAML (`{key: : :}`) | `yaml.safe_load` бросает → `WikiParseError` (caught в `_on_file_event`) |
| Frontmatter не закрытый (`---` без второго `---`) | `re.match` не сработает → `fm_match = None` → frontmatter пустой, body = весь content |
| Wiki-link с pipe display (`[[target\|Display]]`) | Capture group 1 = `target`, display отбрасывается |
| Wiki-link с whitespace внутри (`[[ target ]]`) | regex `[^\]|]+` захватит весь stripped, но spaces могут поломать downstream `add_relation` — рекомендация: avoid whitespace в links |
| Self-link (page links to itself) | Создаётся `add_relation("e1", "e1", "related_to")` — graph store должен это обрабатывать (NetworkX: `add_edge("e1","e1")` создаёт self-loop) |

## Dispatch к graph_store

```python
async def handle_page_change(self, change: WikiPageChange) -> None:
    if change.change_type == "deleted":
        logger.info("[REV-SYNC] Wiki page deleted: %s", change.entity_id)
        return                                          # no-op for deletes

    new_relations = self._links_to_relations(change.added_links, change.entity_id)
    for rel_data in new_relations:
        try:
            relation = Relation(
                id=f"wiki:{change.entity_id}:{rel_data['target']}",
                source_entity_id=change.entity_id,
                target_entity_id=rel_data["target"],
                relation_type="related_to",
                properties={"source": "wiki_edit"},
            )
            await self._graph_store.add_relation(relation)
            logger.info("[REV-SYNC] Added relation: %s → %s",
                        change.entity_id, rel_data["target"])
        except Exception as exc:
            logger.warning("[REV-SYNC] Failed to add relation: %s", exc)
```

### Что НЕ делает reverse sync (пока)

| Operation | Текущее поведение | Roadmap |
|---|---|---|
| Удаление страницы → удаление entity из графа | Просто log, никаких graph mutations | Сложно: page может быть removed случайно, или archived; graph mutation должна требовать confirmation |
| Removed links → remove_relation | Не отслеживается (только `added_links`) | Требует diff'а между prev и new versions страницы; нужен content-addressable cache (например, sha1 → last_links per path) |
| Frontmatter changes → entity properties update | Игнорируется | Future enhancement: e.g., изменение `confidence` в frontmatter → update entity.confidence |
| Renamed wiki-link target | Создаст relation на новый target, старая не удалится | Trade-off acceptable пока — manual cleanup через `verify` CLI |

### Relation type

Все relations созданные через reverse sync имеют `relation_type="related_to"` (generic). Если нужны типизированные relations (`uses`, `extends`, `implements`) — frontmatter должен содержать typed links (e.g., через `relations` array вместо `[[link]]` syntax). Это потребует расширения parsing logic — future enhancement.

`properties={"source": "wiki_edit"}` маркирует относя что они пришли из wiki, а не из NLP extraction. Графовые алгоритмы могут фильтровать или приоритизировать по source.

## Troubleshooting

| Симптом | Причина | Действие |
|---|---|---|
| Watchdog не подхватывает изменения | Observer не запущен, или wiki_dir не существует | Проверить `start_watching()` log; убедиться что `wiki_dir.exists()` |
| Изменения подхватываются с задержкой 5-30s | Filesystem на Docker volume через VirtualBox/HyperV — inotify не работает | Использовать polling observer: `watchdog.observers.polling.PollingObserver` с `timeout=1` |
| `add_relation` падает с "Entity not found" | Target в `[[target]]` ссылается на несуществующий entity | Создавать relation всё равно как orphan, или логировать warning — текущее поведение |
| Reverse sync обрабатывает свои собственные writes (loop) | Forward sync `WikiExporter.export_entity` тригерит filesystem event → reverse sync парсит → add_relation → graph change → forward sync... | **Известная проблема:** detect через debounce (часто помогает) или через "write source" flag в file content metadata. Не closed; в production обычно работает через debounce + idempotency forward sync'а |
| Файл в `archive/` или `drafts/` подхватывается reverse-sync'ом | `recursive=False` отключен или wiki_dir указывает на root | Убедиться что `wiki_dir = Path("docs/wiki/entities")` (не `docs/wiki`) |
