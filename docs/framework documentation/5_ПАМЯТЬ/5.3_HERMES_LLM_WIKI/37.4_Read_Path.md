> При каждом UserPromptSubmit `memory-first-hook.py` **синхронно, последовательно** (без async/await — один Python-процесс на промпт) ищет в L1/L2/L3(stub)/L4 и сливает результаты через RRF. L0 не читается напрямую (raw layer для re-indexing only).

## Pipeline целиком

```
User → "найди как работает hybrid search"
           │
           ▼
.claude/hooks/memory-first-hook.py (UserPromptSubmit, sync BaseHook)
           │
           ├─[sequential]─►  L1 (sqlite): search_sqlite(query_tokens)
           │                  прямой SQL SELECT по data/memory_ai.db
           │                  → episodic context (важные сообщения, token-overlap)
           │
           ├─[sequential]─►  L2 (qdrant): search_qdrant(query_tokens, prompt)
           │                  TEI dense embed + lexical scroll, напрямую через
           │                  qdrant_client (без MCP) по skill_library +
           │                  learned_patterns, гибридный RRF внутри слоя
           │
           ├─[sequential]─►  L3 (wiki): search_wiki(query_tokens)
           │                  **STUB — всегда возвращает []** (полная реализация
           │                  token-overlap по docs/wiki/drafts/ отложена)
           │
           ├─[sequential]─►  L4 (md): search_md(query_tokens)
           │                  weighted token-overlap по персональным .md файлам
           │                  (MEMORY_DIR — ~/.claude/projects/<project>/memory/*.md)
           │
           ▼
RRF fusion (k=60, LAYER_WEIGHTS: sqlite=0.30, qdrant=0.35, wiki=0.20, md=0.15)
           │
           ▼
top-MAX_RESULTS (5) items → инъекция через stdout (не systemMessage/hookSpecificOutput)
           │
           ▼
Claude получает обогащённый prompt и отвечает
```

## memory-first-hook.py — детально

[`.claude/hooks/memory-first-hook.py`](../../../../.claude/hooks/memory-first-hook.py) — UserPromptSubmit hook, регистрируется в [`.claude/settings.json`](../../../../.claude/settings.json) с **timeout 10s** (не 30s). Внутри хука мягкий soft-budget `TOTAL_BUDGET = 3.0s` на сами поиски (по слоям: `SQLITE_TIMEOUT=0.2s`, `QDRANT_TIMEOUT=2.0s`, `MD_TIMEOUT=0.5s`, `WIKI_TIMEOUT=0.2s`) — превышение бюджета не убивает хук, просто следующие слои пропускаются (`if time.monotonic() < deadline`).

### Логика hook'а (реальный код, упрощённо)

```python
# .claude/hooks/memory-first-hook.py (упрощённо, без async — класс BaseHook)

LAYER_WEIGHTS = {"sqlite": 0.30, "qdrant": 0.35, "md": 0.15, "wiki": 0.20}
MAX_RESULTS = 5
SURFACE_RRF_K = 60


class MemoryFirstHook(BaseHook):
    def execute(self, inp: HookInput) -> HookOutput | None:
        prompt = inp.prompt
        query_tokens = set(tokenize(prompt))

        # Последовательные вызовы — НЕ asyncio.gather, обычные Python-функции
        sqlite_results = search_sqlite(query_tokens, limit=10)
        qdrant_results = search_qdrant(query_tokens, limit=10, prompt=prompt)
        md_results = search_md(query_tokens, limit=10)
        wiki_results = search_wiki(query_tokens, limit=10)  # stub → []

        merged = rrf_merge(
            {
                "sqlite": sqlite_results,
                "qdrant": qdrant_results,
                "md": md_results,
                "wiki": wiki_results,
            },
            LAYER_WEIGHTS,
        )[:MAX_RESULTS]

        if not merged:
            return None

        # stdout, НЕ HookOutput.system_message()/hookSpecificOutput —
        # для UserPromptSubmit stdout читается Claude как context напрямую.
        _emit_stdout(format_federated_context(merged))
        return None


def rrf_merge(layers: dict[str, list], weights: dict[str, float], k: int = 60) -> list:
    scores: dict[str, dict] = {}
    for source, items in layers.items():
        w = weights.get(source, 0.0)
        for rank, item in enumerate(items, start=1):
            chash = hashlib.sha1(item["content"].encode("utf-8", "replace")).hexdigest()[:16]
            rrf = w * (1.0 / (k + rank))
            if chash in scores:
                scores[chash]["fused_score"] += rrf
            else:
                scores[chash] = {"item": item, "fused_score": rrf}
    merged = [{**e["item"], "fused_score": e["fused_score"]} for e in scores.values()]
    merged.sort(key=lambda x: -x["fused_score"])
    return merged
```

### L3 search_wiki() — честно, это stub

Реальный код (`memory-first-hook.py`):

```python
def search_wiki(query_tokens: set, limit: int = 10) -> list:
    """Layer 4 wiki search — stub returning [] (full impl deferred).

    Called from RRF merge in execute(); empty result means layer 'wiki' simply
    contributes nothing to the merge, other layers (sqlite/qdrant/md) still work.
    """
    return []
```

Слой участвует в RRF-формуле с весом `LAYER_WEIGHTS["wiki"] = 0.20`, но **никогда не возвращает хиты** — токен-оверлап по `docs/wiki/drafts/` и опциональный semantic через `wiki_pages_v1` (описанные в более ранних версиях этого документа) в текущем коде не реализованы. Graceful degradation: пустой L3 просто не добавляет ничего к fusion, остальные 3 слоя (sqlite/qdrant/md) работают штатно.

## Graceful degradation

Каждая `search_*` функция **сама** оборачивает свою логику в `try/except` и возвращает `[]` при любой ошибке (Qdrant down, SQLite locked, TEI недоступен) — никакого `asyncio.gather(..., return_exceptions=True)` в коде нет, это обычные последовательные вызовы с fail-soft внутри каждой функции:
- RRF просто не получает вклад от упавшего слоя (его вес эффективно перераспределяется на остальные)
- Hook возвращает результаты из доступных слоёв

**Полная failure mode** (все 4 слоя вернули `[]`) — hook не эмитит ничего (`return None`), Claude работает без обогащения (прочая context-машинерия — CLAUDE.md, MEMORY.md — продолжает работать).

## Latency budget

| Слой | Soft-budget в коде | Backend |
|---|---|---|
| L1 sqlite | `SQLITE_TIMEOUT = 0.2s` | Прямой `sqlite3` SELECT по `data/memory_ai.db` |
| L2 qdrant | `QDRANT_TIMEOUT = 2.0s` | TEI embed (warm ~80ms) + `qdrant_client` по 2 коллекциям + lexical arms |
| L3 wiki | `WIKI_TIMEOUT = 0.2s` (не используется — stub instant `[]`) | — |
| L4 md | `MD_TIMEOUT = 0.5s` | Filesystem scan `MEMORY_DIR/*.md` |
| **Soft total** | `TOTAL_BUDGET = 3.0s` | Превышение не убивает hook, просто следующий слой пропускается |
| **Hard hook timeout** | **10s** (`.claude/settings.json`) | Claude Code SIGKILL при превышении |

## RRF weights — обоснование

| Layer | Weight (`LAYER_WEIGHTS`) | Почему |
|---|---|---|
| **sqlite (L1 episodic)** | 0.30 | Recent context критичен (что user обсуждал в этой сессии). Volatile, но точный |
| **qdrant (L2 patterns)** | **0.35** | Доминирующий — это место где живут learned facts + skills, confidence-weighted, наиболее accurate |
| **wiki (L3 canonical)** | 0.20 | Задуман как narrow high-precision canonical layer; **в текущем коде — stub, вклад = 0 хитов** (см. выше) |
| **md (L4 user notes)** | 0.15 | Персональные `.md` заметки (`MEMORY_DIR`), narrow, cross-session preferences |

Веса — константа `LAYER_WEIGHTS` в `.claude/hooks/memory-first-hook.py` (не env-tunable; §25 self-tuning грузит альтернативные *другие* константы из `data/memory/surfacing_tuning.json` — `MIN_SURFACE_CONF`/`CONF_FLOOR`/`SURFACE_RRF_K`/веса внутри qdrant-слоя, но не `LAYER_WEIGHTS` верхнего уровня).

## Tools для запроса напрямую

Если нужно обойти hook (debugging, exploratory) — это отдельные MCP-инструменты, независимые от внутренней (прямой DB/Qdrant-client) реализации хука:

```python
# L1-эквивалент
mcp__memory-ai__search_messages(query="...", limit=10)
mcp__memory-ai__get_important_messages(limit=5)

# L2-эквивалент
mcp__vector-memory__search_patterns(query="...", limit=20)
mcp__vector-memory__get_pattern(pattern_id="...")

# Wiki (через obsidian-mcp, когда server running)
mcp__obsidian-mcp__obsidian_simple_search(query="...")
mcp__obsidian-mcp__obsidian_complex_search(filters=...)

# Multi-collection (НЕ вызывается хуком — отдельный путь через оркестратор)
mcp__memory-orchestrator__unified_search(query="...", targets=["wiki","graph","patterns"])
mcp__memory-orchestrator__get_related(unified_id="...", depth=2)
```

## Antipatterns

| Плохо | Почему | Как правильно |
|---|---|---|
| Полагаться на semantic поиск по wiki внутри memory-first-hook | `search_wiki()` — stub, всегда `[]` | Для wiki-поиска использовать `mcp__obsidian-mcp__*` или `unified_search` напрямую |
| Игнорировать L3 wiki weight (0.20) как "мёртвый груз" в тюнинге RRF | Вес зарезервирован под будущую реализацию — легитимная noop-константа, не баг | При тюнинге весов учитывать, что L3 сейчас 0 вклада — эффективно распределяет relative влияние оставшихся 3 слоёв |
| Ожидать параллельный (`asyncio.gather`) fetch слоёв | Хук синхронный, `BaseHook`, вызовы последовательные | Профилировать через `_trace_time()` записи в `.claude/cache/memory-first-surfacing.log` (per-stage ms) |
| RRF k=10 вместо 60 | Слишком жёсткий cutoff long-tail | `SURFACE_RRF_K = 60` (industry default, well-tested) |
