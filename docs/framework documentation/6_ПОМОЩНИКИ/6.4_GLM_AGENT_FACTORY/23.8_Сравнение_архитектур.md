# 23.8 Сравнение архитектур Plan A / B / C

> Технический анализ трех подходов маршрутизации Agent() вызовов на GLM-5.1.

---

## План А: Hook-based Interception

**Механизм:** PreToolUse хук с matcher `"Task"` перехватывает `Agent()` вызовы, возвращает `continue:false` + результат.

| Аспект | Оценка |
|--------|--------|
| Прозрачность | Максимальная (0 изменений в Claude) |
| Надежность | 75% отказов в production |
| Поддержка subagents | Нет (не наследуются) |
| Латентность | 0ms (нет extra процесса) |

### Критические баги

1. **#26923** --- `exit 2` не блокирует Task matcher --> ложные срабатывания
2. **#39814** --- `updatedInput` игнорируется для Agent --> потеря параметров
3. **#21460** --- хуки не наследуются subagents --> обработка только root level

**Статус: ОТКЛОНЕН** --- кумулятивная вероятность production отказов 75%.

---

## План Б: MCP Server

**Механизм:** Выделенный MCP сервер с 6 tools: `analyze`, `review`, `generate`, `research`, `architect`, `write`.

| Аспект | Оценка |
|--------|--------|
| Прозрачность | Partial (требует явного вызова) |
| Надежность | 10/10 (нет внешних зависимостей) |
| Поддержка subagents | Полная (standard MCP) |
| Латентность | +10--50ms (local IPC) |

### Преимущества

- Стабильная архитектура (нет зависимостей от hook багов)
- Явная семантика (Claude выбирает какой tool использовать)
- Контроль над injection файлового контента
- Поддержка streaming responses

### Ограничения

- Требует обучения Claude использовать новые tools (через CLAUDE.md)
- Невозможна "прозрачная" маршрутизация
- Decision logic в Claude для BSL vs universal code

**Статус: РЕАЛИЗОВАН** (production-ready)

---

## План В: HTTP Proxy

**Механизм:** Прозрачный reverse proxy через `ANTHROPIC_BASE_URL`, перехватывает ВСЕ API вызовы на transport layer.

**Базирование:** ccproxy (192 stars, Python, active development).

| Аспект | Оценка |
|--------|--------|
| Прозрачность | Максимальная (transport level) |
| Надежность | 9/10 (API versioning risk) |
| Поддержка subagents | Автоматическая (все calls перехватываются) |
| Латентность | +30--100ms per call |

### Преимущества

- Полная прозрачность --- Claude не знает о proxy
- Automatic subagent routing --- все nested Agent() автоматически роутятся
- Auto-disable logic --- fallback на Anthropic при GLM недоступности
- Streaming support --- полная поддержка SSE

### Риски

- Версионирование API --- Anthropic API shape изменения требуют обновления proxy
- Extra latency --- каждый call +30--100ms
- Debugging complexity --- трассировка проходит через proxy

**Статус: РЕАЛИЗОВАН** (production-ready)

| Надежность | 25% | 100% | 90% |
| Subagents | Нет | Да | Да (auto) |
| Латентность | 0ms | 10--50ms | 30--100ms |
| Сложность | Средняя | Средняя | Высокая |
| Зависимости | 3 бага | Нет | API versioning |
| Production-ready | Нет | Да | Да |

## Финальное решение

**Гибридный подход --- Plan B + Plan C:**

1. **Plan B (MCP)** --- primary production path. Явный routing через `mcp__glm-agent__*` tools.
2. **Plan C (HTTP Proxy)** --- для прозрачного перехвата Agent() и subagents.
3. **Plan A** --- отклонен из-за зависимости от 3 нерешенных hook багов.
