# 42.4 Failure Caching + Analysis

Multi-layer кэш и анализ ошибок CI через [`scripts/ci_failure_cache.py`](../../../../scripts/ci_failure_cache.py).

**Phase 1 normalization (2026-05-26):** `_normalize_for_hash()` strips ISO timestamps, slash dates `2026/05/25 HH:MM:SS`, `<job_NNN>` IDs, `run_id=N`/`id=N` markers, collapses whitespace перед hash. Без этого каждый recurring fail с unique timestamp → unique hash → auto-issue threshold (3) **никогда не достигался**. После normalization: 40 unique → 10 unique hashes на retro-clean (см. [`scripts/ci_failure_normalize.py`](../../../../scripts/ci_failure_normalize.py) для in-place rehash).

## Pipeline

```
FAILURE event (Monitor) → ci_failure_cache.py:
  1. gh run view --log-failed → fetch raw log
  2. extract_first_error() → first meaningful error line (skip runner noise)
  3. SHA256[:16] hash → dedup key
  4. JSONL append → .claude/cache/ci-failures.jsonl
  5. TEI embed (Qwen3, 4096d) → MRL truncate → 1024d
  6. Qdrant upsert → ci_failures collection
  7. Qdrant search top-3 similar past failures (score >= 0.7)
  8. Count occurrences of same hash:
     - if >= 3 AND no existing issue → gh issue create
     - tag in .claude/cache/ci-failure-issues.json
```

## Storage layers

| Layer | Path | What | Retention |
|---|---|---|---|
| JSONL log | `.claude/cache/ci-failures.jsonl` | Все failures с metadata | Unlimited (append-only) |
| Issue tags | `.claude/cache/ci-failure-issues.json` | hash → issue URL mapping | Persistent (manual cleanup) |
| Qdrant `ci_failures` | localhost:6333 collection | 1024d Qwen3 embeddings + payload | Survives до collection delete |
| GitHub Issues | Labels `ci-failure,automated` | Auto-created на 3+ recurrences | Manual close |

> ⚠️ **Prerequisite для auto-issue creation:** labels `ci-failure` и `automated` должны существовать в repo. Без них `gh issue create --label ci-failure,automated` silently fails (returns rc != 0), `_maybe_create_issue` возвращает None. **Setup:** `gh label create ci-failure --color "B60205"` + `gh label create automated --color "0075CA"`. Известный gap (наблюдался 2026-05-26 — hash `ecfa34d07afd0009` достиг 3 occurrences, issue не создался).

## Monitor integration

Monitor `bkozphbx9` (CI watcher + auto-cache):
- На каждый FAILURE event парсит `PR#N\tjob_name\ttitle`
- Если новый (не в prev) → вызывает `ci_failure_cache.py --pr N --job <name>`
- Emit в чат: `FAIL PR#N job=<name> title="..." occ=<count>[ issue_url=...]`
- `occ=1` = новая ошибка, `occ>=3` = recurring + issue URL

## SessionStart auto-catchup (added 2026-05-25)

Monitor session-bound — умирает между Claude сессиями. Чтобы failures из off-hours не терялись, hook [`ci-catchup-on-start.py`](../../../../.claude/hooks/ci-catchup-on-start.py) (SessionStart event) при каждом старте сессии спавнит detached subprocess `python scripts/ci_failure_cache.py --catchup 20`.

```
SessionStart event
  ↓
ci-catchup-on-start.py (hook, ≤5s, advisory)
  ↓
Popen detached (CREATE_NEW_PROCESS_GROUP on Windows)
  ↓
python scripts/ci_failure_cache.py --catchup 20
  ↓ (in background, ≤30s)
gh run list --status failure --limit 20
  ↓ filter out run_ids already в .claude/cache/ci-failures.jsonl
  ↓ для каждого нового run → fetch_failure_log → _process_failure → append + embed + upsert
  ↓
{processed, skipped, errors[]} → DEVNULL (background mode)
```

Env vars:
- `CI_CATCHUP_DISABLE=1` — skip hook completely
- `CI_CATCHUP_LIMIT=N` — override default 20 (use 50+ если сессии редко стартуют)

Manual invocation:

```bash
# Idempotent — повторный вызов не дублирует записи
python scripts/ci_failure_cache.py --catchup 30
# → {"processed": 27, "skipped": 3, "errors": []}
```

**Gap coverage:** этот механизм закрывает off-session window между Monitor stops (TaskStop / session end) и next session start. Не purports быть 24/7 — true server-side auto требует GitHub `workflow_run.completed` webhook (deferred, отдельный roadmap).

## Generic Event Hashing (`--log-event`)

Beyond CI failures, the same cache infrastructure supports hashing arbitrary events. Use cases:

| Event type | Source | Why hash |
|---|---|---|
| `notification` | `gh api notifications` (live polled by Monitor every 60s) | Dedup repeat notifications, detect spam patterns |
| `pr-review` | `gh pr view N --comments` | Track duplicate review concerns across PRs |
| `workflow-event` | `gh run list` start/cancel | Detect job lifecycle anomalies (cancel storms) |
| `other` | Anything | Universal escape hatch |

**API:**

```bash
python scripts/ci_failure_cache.py --log-event <TYPE> --key <ID> --content <TEXT>
```

Schema (vs CI-failure rows):

| Field | CI failure entry | Generic event entry |
|---|---|---|
| `event_type` | (absent) | `notification`/`pr-review`/`workflow-event`/`other` |
| `key` | (absent) | Identifier (`thread-id`, `PR#N`, `run_id`, etc.) |
| `run_id` / `pr` / `sha` / `job` / `url` / `error_first_line` | populated | (absent) |
| `content_preview` | (absent) | First 300 chars of content |
| `error_hash` | sha256 of normalized error_line | sha256 of normalized content |
| `ts` | populated | populated |

**Threshold-aware (NOT for generic events):** `log_event()` НЕ вызывает `_maybe_create_issue` — generic events не создают auto-issues, regardless от occurrence count. Для recurrence detection generic events — используй `--search QUERY` (matches both `error_first_line` и `content_preview`) или query JSONL напрямую через `python -c "import json; ..."`. Auto-issue creation для generic event типа — deferred (отдельный roadmap item, требует label conventions per event_type).

**Validation:** `event_type` whitelist в `VALID_EVENT_TYPES = {"notification", "pr-review", "workflow-event", "other"}`. Invalid тип → `ValueError` → friendly stderr message + exit 2 в CLI mode. Защищает от typos типа `"notifications"` vs `"notification"` фрагментирующих cache.

## Pre-merge Review Enforcement (Hook)

[`.claude/hooks/pre-merge-review-check.py`](../../../../.claude/hooks/pre-merge-review-check.py) — **PreToolUse:Bash blocking hook**. Intercepts `gh pr merge N ...` commands, fetches PR review comments + reviews via `gh api`, parses gemini-code-assist severity markers (`![high]` / `![medium]` / explicit `Severity: HIGH/MEDIUM`), blocks merge с exit 2 если есть unresolved HIGH/MEDIUM findings.

**Output sample:**

```
[PRE-MERGE-REVIEW] PR #61 has unresolved bot reviews:
  HIGH: 1  MEDIUM: 2

Samples:
  - HIGH gemini-code-assist[bot] scripts/ci_digest.py: ![high] Переменная `e` загружается...
  - MEDIUM gemini-code-assist[bot] scripts/ci_failure_cache.py: ...

Action: review and apply fixes BEFORE merge. Override with env GH_MERGE_REVIEW_OVERRIDE=1 if intentional.
```

**Override:** `GH_MERGE_REVIEW_OVERRIDE=1` в Bash command env — для случаев когда user явно подтверждает merge despite findings (e.g. "мержи без fix-ов").

**Enforces protocol:** [memory `feedback_pre_merge_review_protocol`](file:///C:/Users/Tech.%20Boutique/.claude/projects/C--1--Framework/memory/feedback_pre_merge_review_protocol.md) — saved 2026-05-26 после case'а где PR #61 был merged без чтения 3 gemini comments (1 HIGH real regression). Hook гарантирует что pattern не повторится без явного override.

**Monitor integration:** Comprehensive watcher (см. [42.3](42.3_Запуск_и_примеры.md)) поллит `gh api notifications` каждые 60s (3-й iter из 20s loop), emit `[notif]` lines, и invoke `--log-event notification` для каждой новой строки. Auto-cache даёт persistent state без duplicate emit'ов через `comm -13` delta detection.
