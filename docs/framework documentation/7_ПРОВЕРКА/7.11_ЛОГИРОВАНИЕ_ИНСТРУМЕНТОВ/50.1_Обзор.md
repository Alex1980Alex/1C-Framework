# 50.1 Логирование инструментов и Tool Observability — Обзор

Замкнутый контур наблюдаемости за вызовами инструментов (built-in Read/Bash/Edit/… и MCP-серверов): **лог → анализ → вердикт → действие**. Каждый вызов инструмента фиксируется структурной строкой, аналитический слой считает метрики и выносит вердикт о здоровье инструмента, а баннеры/авто-задачи превращают вердикт в действие.

## Зачем

Без этого контура нельзя ответить на вопросы: какие инструменты стабильно падают, какие тормозят, где Claude зацикливается на повторных вызовах, какой MCP-сервер деградировал. Раньше вызовы инструментов были видны только как побочный эффект случайно сматчившихся энфорсеров (один Bash → N строк `category="hook"` от разных хуков), латентность нативных тулов не мерилась вообще, а ошибки built-in-инструментов терялись. Контур делает наблюдаемость **честной и однозначной**: одна каноническая строка на вызов, реальная латентность, честный сигнал провала.

## Два пути наблюдаемости

Индустрия-консенсус 2026 (OTel GenAI, deepeval/MCP-Bench, Langfuse) описывает два уровня — реализованы оба:

| Путь | Что | Инфраструктура | Когда |
|---|---|---|---|
| **Лёгкий** (default) | Структурный JSONL `data/hook-invocations.jsonl` + stdlib-анализ (`analyze_tool_health.py`) + DuckDB-интерактив (`audit_query.py`) | нет (файлы + Python) | всегда |
| **Тяжёлый** (opt-in) | Нативный OpenTelemetry Claude Code → otel-collector → cross-check + Langfuse self-host + LLM-judge | Docker (коллектор, Langfuse) | по требованию |

Лёгкий путь самодостаточен: вердикты, эскалация, тренд, probe и разрез делегирования работают на JSONL+stdlib без внешних сервисов. Тяжёлый путь добавляет независимый второй источник (нативные `success`/`duration_ms` от платформы) для **сверки честности** лёгкого + дашборды. См. [50.4 OTel / Cross-check / Langfuse](50.4_OTel_Cross_check_Langfuse.md).

## Контур «лог → анализ → вердикт → действие»

```
Вызов инструмента (built-in / mcp__)
  │  PreToolUse + PostToolUse
  ▼
[ЛОГ]  канонические логгеры → data/hook-invocations.jsonl
  │    (одна строка на вызов: tool_call / mcp_call; CloudEvents-конверт;
  │     tool_call_id, duration_ms, args_hash, success, gen_ai.* алиасы)
  ▼
[АНАЛИЗ]  analyze_tool_health.py (окно 14д, stdlib)
  │    tool_effectiveness: completion_stats (непарный Pre = провал),
  │    tool_durations (прямой duration_ms), percentile, retry/abandonment
  ▼
[ВЕРДИКТ]  broken / degraded / ineffective / unused / healthy (§6.1)
  │    + ratchet-baseline, тренд из verdicts.jsonl, infra-join (probe + sinks)
  ▼
[ДЕЙСТВИЕ]  data/reports/tools/_latest.{md,json} + verdicts.jsonl
       SessionStart-баннер (сюрфейс alerts) + broken → авто-задача диагностики
       (авто-фикса кода НЕТ — контур только диагностирует)
```

## Ключевые честные сигналы (почему метрики не врут)

- **Провал built-in = непарный Pre.** Платформа НЕ шлёт `PostToolUse` на неуспешный built-in вызов (Bash non-zero exit, Edit «строка не найдена», Read miss — эмпирика). Значит error-rate из Post ≡ 0 структурно, а честный провал = `PreToolUse` без парного `PostToolUse` (`completion_stats`). См. [50.3](50.3_Анализ_вердикты_действия.md).
- **Реальная латентность из `duration_ms`.** Платформа кладёт настоящую длительность тула в `PostToolUse`-payload полем `duration_ms` — точнее пэйринга Pre→Post (пара врала до ~10 секунд). Поле `elapsed_ms` = время работы ХУКА (~20мс), НЕ инструмента.
- **p95-деградация отключена у content-variable тулов** (Bash/Grep/execute_code — длительность определяется содержимым вызова, не здоровьем) + пол 500мс — устранена «FP-фабрика».
- **Payload = недоверенный вход.** И hook-payload, и OTLP-атрибуты коэрсятся при чтении (реальный Claude Code кодирует `success`/`duration_ms` как строки `"false"`/`"3879"` — наивный парсинг тихо ломает детекцию).
