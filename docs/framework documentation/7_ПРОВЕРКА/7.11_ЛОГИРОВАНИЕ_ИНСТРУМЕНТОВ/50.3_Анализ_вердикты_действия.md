# 50.3 Анализ, вердикты, действия

Аналитический слой над `data/hook-invocations.jsonl`: за окно (14д по умолчанию) считает per-tool метрики, выносит вердикт о здоровье, сводит инфра-сигналы и превращает вердикт в действие (баннер + авто-задача).

## Rule-слой метрик — `tool_effectiveness.py`

Единый stdlib-модуль ([`scripts/tool_effectiveness.py`](../../../../scripts/tool_effectiveness.py)), из которого потребители (`analyze_tool_health`, `tool_usage_report`) берут метрики:

| Функция | Метрика |
|---|---|
| `completion_stats(pres, posts, now)` | **честный сигнал незавершения**: непарный `PreToolUse` старше grace (120с) = провал. Корень: платформа НЕ шлёт Post на неуспешный built-in → error-rate из Post ≡ 0; единственный честный провал = Pre без Post. Гард-блоки (`enforcer exit 2`) сюда не попадают (преемптят логгер). |
| `tool_durations(pres, posts)` | длительность вызовов, **предпочитая прямой `duration_ms`** (H-P0.1) паре Pre→Post. На данных без поля идентична `pair_durations` (behavior-preserving). |
| `pair_durations(pres, posts)` | латентность из пары Pre→Post (join по `tool_call_id`, иначе FIFO; tz-guard). |
| `percentile(values, q)` | p50/p95 без numpy. |
| `effectiveness_from_posts(posts)` | `repeats` (повтор того же `args_hash` = retry) + `abandonment` (последняя попытка — ошибка). |
| `step_efficiency(calls, repeats)` | доля избыточных вызовов ∈ [0,1]. |
| `rollup_by_server(tools_stats)` | per-server агрегат: success-rate, error-rate, step-efficiency, брошенные тулы. |

## Вердикты (§6.1) — `analyze_tool_health.py`

[`scripts/analyze_tool_health.py`](../../../../scripts/analyze_tool_health.py) (stdlib-only, detached-safe) за окно выносит per-tool вердикт:

| Вердикт | Условие | Значок |
|---|---|---|
| `broken` | success-rate < 50% (или MCP-сервер down ≥2д) | 🔴 |
| `degraded` | error-rate выше baseline, ЛИБО genuine-latency p95 > 2× baseline | 🟠 |
| `known-issue` | тул со сломом по ИЗВЕСТНОЙ внешней причине (реестр `known_issues.json`) — подавлен, НЕ эскалируется (ADR-055) | 🔕 |
| `ineffective` | abandonment (не восстановились после ошибки) | 🟡 |
| `unused` | 0 вызовов за окно (кандидат на отключение) | ⚪ |
| `healthy` | всё в норме | 🟢 |
| `info` | несюрфейсящийся инфра-сигнал (opt-in Langfuse down) | ℹ️ |

Важные защиты от ложных вердиктов:

- **p95-деградация ОТКЛЮЧЕНА у content-variable тулов** (Bash/Grep/execute_code/Read/Skill/Task* — длительность от содержимого вызова, не здоровья) + пол абсолюта 500мс. Устранена «FP-фабрика» (6 живых degraded были p95-FP → 0).
- **`repeats` НЕ движет вердикт** — идемпотентный поллинг (ping/targets) = healthy, был FP.
- **`DEGRADED_MIN_CALLS=3`** — не красить degraded по calls=1/er=100%.
- **Ratchet-baseline** (`baseline.json`, паттерн mypy-baseline): baseline = лучший (min) p95/error-rate per-tool; ухудшение НЕ пишется. Выход из «degraded навсегда» — `--reset-baseline`.
- **`window_incomplete`** флаг: если ротация срезала хвост окна — вердикты помечаются как посчитанные по усечённым данным.
- **TTL-prune 30д** для `unused` (`last_seen`) — unused не вечен.

### Как читать `broken` у MCP-тула (эмпирика диагностики 2026-07-25)

`broken` считается по непарным `PreToolUse`, а **семантика непарности у MCP-серверов различается** — она
зависит от того, КАК сервер сообщает об ошибке. Проверено прямым экспериментом (по одному заведомо
ошибочному вызову на сервер + сверка `tool_call_id` в логе):

| Форма ошибки сервера | Что видит платформа | Запись в логе | Следствие для метрик |
|---|---|---|---|
| **Протокольная ошибка MCP** (`isError` / JSON-RPC error) — так делает `edt-mcp` | вызов неуспешен | Post **не приходит** → непарный Pre | попадает в success-rate честно |
| **Текст ошибки в теле успешного ответа** — так делает `1c-mcp-crud` (`«Ошибка выполнения инструмента …»` + стек BSL) | вызов успешен | пара Pre→Post, `success=True` | ⚠ **слепая зона**: app-level ошибки в error-rate НЕ видны |

Отсюда — методика разбора `broken` (вместо «инструмент сломан» по умолчанию):

1. **Проверить живость сервера** дешёвым тулом (`get_edt_version`, `list_metadata_objects`) — вердикт часто
   стоит на данных прошлых дней, а сервер давно ожил.
2. **Воспроизвести вызов** с корректными аргументами. Если отработал — сломан был не инструмент.
3. **Посмотреть парность в логе** по `tool_call_id` и сравнить с фоном: типичная доля непарных Pre по MCP —
   **≈7%** (замер 1047 Pre). Тул сильно выше фона = аномалия, около фона = шум малой выборки
   (`MIN_CALLS_FOR_BROKEN=5` — двух неудач хватает, чтобы уронить тул в `broken`).
4. **Развести три причины непарного Pre**: (а) реальный отказ инструмента, (б) **ошибка вызывающего**
   (неверный FQN/имя объекта/свойство — валидация сервера отклонила вызов), (в) транспорт: недоступность
   или таймаут (dev-инфобазы 1С флапают, см. `probe_mcp_health.py`).

Живые примеры этого разбора: `mcp__edt-mcp__modify_metadata` (4/5 непарных = ошибки вызывающего, FQN/свойство
наугад — лечится `get_metadata_details(assignable=true)` перед правкой, антипаттерн в skill `edt-mcp`);
`mcp__1c-mcp-crud-kat__get_metadata_structure` (6/8 непарных при том, что ошибки этого сервера приходят
PAIRED ⇒ причина транспортная, а не аргументная; тул отвечает штатно).

**Разбор 14 degraded той же методикой (2026-07-25) — три исхода:**

| Исход | Инструменты | Что сделано |
|---|---|---|
| Известная внешняя причина → `known-issue` | `update_database` (43% непарных на 46 вызовов: MCP-таймаут 60с при **асинхронном** завершении — EDT дописывает обновление после отвала клиента, результат проверяется повторным вызовом `stateAfter=UPDATED`), `search_in_code` (p95 11.4с by design — live-скан workspace вместо индекса) | записи в `known_issues.json` с `review_by` (ADR-055) |
| Непарность не означает провал → в код | `AskUserQuestion` (5/24 = 21% непарных, 0 ошибок: пользователь не ответил / прервал диалог) | добавлен в `ASYNC_UNPAIRED_UNRELIABLE` рядом с `Agent`/`Task` |
| Шум малой выборки / около фона | `apply_form_recipe` 3/5, `inspect_form_layout` 2/6, `mutate_form_model` 2/8, `get_edt_version` 1/5, `list_projects` 4/23, `llm_complete` 4/29, `edt_validate_request` 2/17, `PowerShell` 28/409, `Write` 48/3886, `unified_search`/`list_metadata_objects` 0 | действий нет — вердикт самоочистится на свежем окне |

## Known-issues слой — «xfail для инструментов» (ADR-055)

Тул, сломанный по ИЗВЕСТНОЙ (часто внешней/апстрим) причине, иначе плодил бы mandatory-задачу каждые 72ч, а метрика не самоочищалась бы (whack-a-mole). Реестр [`data/reports/tools/known_issues.json`](../../../../data/reports/tools/known_issues.json) `{tool: {reason, ref, review_by}}` → overlay `_apply_known_issues` (после `apply_infra_to_tools`) меняет вердикт `broken/degraded/ineffective` → **`known-issue`** (🔕). Такой тул виден в отчёте/баннере с причиной+ref, но баннерный escalation-фильтр `(broken, degraded)` его НЕ подхватывает → задача не заводится.

Форма best-practice (Alertmanager silences + pytest `xfail(strict)` → xpass; кеш `architecture-research/cache/tool-alert-suppression-known-issues-2026.md`):

- **`review_by` обязателен** — `_review_expired`: истёкшая/отсутствующая/непарсимая дата → подавление НЕ действует (fail-closed, нет вечного молчаливого mute; истёкший тул снова `broken` → эскалируется).
- **xpass-детект** — если known-issue тул снова `healthy`, ставится `recovered_known_issue` + баннер сюрфейсит «возможно починен, сними suppression».
- **Sidecar** `known_issues[]` / `recovered_known_issues[]` для баннера.
- **Слой 2 (реальный фикс отложен):** actionable-подзадачи в roadmap-секции NEXT + `review_by`-авто-resurface + локальный SessionStart-хук [`known-issue-saturday-nudge-on-start.py`](../../../../.claude/hooks/known-issue-saturday-nudge-on-start.py) (по субботам напоминает про не-истёкшие known-issue, once/day, opt-out `KNOWN_ISSUE_NUDGE_DISABLE=1`).

Живой кейс: `mcp__codepilot1c__qa_run`/`qa_generate` (корень W13 — апстрим `getThickClientInfo` + `infra_error`-при-успехе; фикс внешний). Fail-soft: нет config → поведение прежнее.

## Decision layer — свод сигналов в вердикты (§6, NB4)

Три параллельных потока сведены в единый отчёт, а не три баннера:

- **`mcp_down_deps`** — MCP-сервер down ≥2 дня подряд (по `data/mcp-health.jsonl`) → `broken` для его инструментов (карта affects).
- **`stale_sinks`** — замолчавшие memory-синки (`[REGRESSION]`-маркер observability-отчёта) → `degraded` для инструментов memory-серверов.
- Сводятся в `infra_alerts` (`gather_infra_alerts`) + override активных тулов (`apply_infra_to_tools`, только `broken`).

**Читатель истории вердиктов** — [`scripts/tool_verdict_history.py`](../../../../scripts/tool_verdict_history.py) (раньше `verdicts.jsonl` был write-only): повтор `broken` того же тула за 30д → приоритет p1 + метка `repeat`; healed-детект (broken→healthy = вылечено; broken→known-issue = подавлено, НЕ вылечено — ADR-055); тренд-секция в `_latest.md`.

## Проактивный health-probe зависимостей — `probe_mcp_health.py`

[`scripts/probe_mcp_health.py`](../../../../scripts/probe_mcp_health.py) пробит не сами MCP-tools (их зовёт клиент, серверы тяжёлые), а их **зависимости**: Qdrant (`/healthz`), TEI (`/embed`), memory-ai / bsl-code-search (SQLite ro), skill-learning (RW-каталог), 5-6× 1c-mcp-crud (HTTP reachability, severity=degraded — dev-инфобазы флапают), Langfuse (severity=info, только при `.env.otel`). Результат → `data/mcp-health.jsonl` + сайдкар `_mcp_health.json`. SessionStart-хук [`mcp-health-probe-on-start.py`](../../../../.claude/hooks/mcp-health-probe-on-start.py) (баннер только при down, opt-out `MCP_HEALTH_PROBE_DISABLE=1`).

## Действие

- **Отчёты**: `data/reports/tools/_latest.md` (человекочитаемый) + `_latest.json` (сайдкар для баннера) + `verdicts.jsonl` (история) + `baseline.json` (ratchet). Секции: alerts, инфраструктура, эффективность per-server, делегирование per-agent, OTel cross-check ([50.4](50.4_OTel_Cross_check_Langfuse.md)), тренд, все инструменты. `data/reports/tools/*` gitignored.
- **Stop-хук** [`tool-health-analyzer-stop.py`](../../../../.claude/hooks/tool-health-analyzer-stop.py) — detached-прогон анализатора (cooldown 24ч, паттерн post-indexing-analyzer). Opt-out `TOOL_HEALTH_ANALYZER_DISABLE=1`.
- **SessionStart-баннер** [`tool-health-banner-on-start.py`](../../../../.claude/hooks/tool-health-banner-on-start.py) — сюрфейсит alerts; `broken` → авто-задача диагностики через `task_master` (дедуп 72ч, эскалация до 336ч); `degraded` — за человеком; **`known-issue` НЕ эскалируется** (строка `🔕 подавлено`), а `recovered_known_issue` даёт строку «сними suppression» (ADR-055); молчит при healthy. Opt-out `TOOL_HEALTH_BANNER_DISABLE=1`. **Авто-фикса кода НЕТ** — контур только диагностирует. Отдельный SessionStart-хук [`known-issue-saturday-nudge-on-start.py`](../../../../.claude/hooks/known-issue-saturday-nudge-on-start.py) по субботам напоминает про отложенные known-issue фиксы.

## Разрез делегирования (per-agent)

Поле `agent_id` (платформа шлёт с 2026-07) даёт разрез: сколько вызовов/ошибок в субагентах vs основной сессии (`(main)`). В отчёте секция «Делегирование» — провалы делегирования (напр. Agent 20% error-rate) стали видны.
