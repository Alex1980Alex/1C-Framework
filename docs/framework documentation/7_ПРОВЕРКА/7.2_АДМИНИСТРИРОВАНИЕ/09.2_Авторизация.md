# 09.2 Авторизация (JWT + RBAC)

## Обзор

Система авторизации на базе JWT токенов с ролевым доступом (RBAC).

## Роли

| Роль | Права |
|------|-------|
| **viewer** | Поиск, чтение документов |
| **editor** | viewer + индексация, удаление документов |
| **admin** | editor + управление тенантами, пользователями, настройками |

## Генерация JWT токенов

```bash
# Токен для admin
pdf-framework auth token --tenant company-a --role admin

# Токен для viewer
pdf-framework auth token --tenant company-a --role viewer

# Токен для editor
pdf-framework auth token --tenant company-a --role editor
```

## Использование токена

```bash
# API запрос с JWT
curl -X POST http://localhost:8000/search/ \
    -H "Authorization: Bearer <jwt-token>" \
    -H "Content-Type: application/json" \
    -d '{"query": "конфигуратор"}'
```

## Настройка

```env
AUTH__ENABLED=true
AUTH__JWT_SECRET=your-secret-key-min-32-chars-long
AUTH__JWT_EXPIRATION_HOURS=24
```

## Отключение авторизации

Для разработки можно отключить:

```env
AUTH__ENABLED=false
```

## OAuth2 для MCP серверов

Для многопользовательского доступа к MCP серверам поддерживается **OAuth2 2.1 + PKCE**. Реализация вынесена из BSL MCP в reusable shared-модуль + готовая FastAPI обвязка для любого HTTP MCP-сервера + audit infrastructure; backward-compat BSL-обёртка и её хост `src/bsl/mcp_server` ретированы 2026-07-24 ([ADR-056](../../../../.claude/skills/architecture-research/adr/056-retire-src-bsl-mcp-server.md)). (Перенесено из архивной главы 37.7 Hermes-хроники, R2 260705.)

### Архитектура

```
src/shared/mcp_oauth/                          ← Generic core
├── models.py              (AuthCodeData, AccessTokenData, RefreshTokenData)
├── service.py              (OAuth2Service — PKCE S256, refresh rotation, RFC 9728 PRM)
├── store.py                (OAuth2Store ABC + InMemoryBackend + cleanup task)
├── audit.py                (AuditedOAuth2Service + OAuthAuditEvent — 5 event types)
└── fastapi/
    ├── routes.py            (build_oauth_router — /authorize /token /.well-known/*)
    └── dependencies.py      (require_oauth FastAPI Depends)
```

### Активация

```env
MCP_AUTH_MODE=oauth2
MCP_ACCESS_TOKEN_TTL=3600        # 1 час
MCP_REFRESH_TOKEN_TTL=1209600    # 14 дней
MCP_CODE_TTL=120                 # 2 минуты
```

Альтернативные env-имена (`pdf-vector-graph` в `.mcp.json` → `env`): `MCP_OAUTH_ENABLED` (default `false` — без флага сервер работает без авторизации), `MCP_OAUTH_PUBLIC_URL`, `MCP_OAUTH_CODE_TTL`, `MCP_OAUTH_ACCESS_TTL`, `MCP_OAUTH_REFRESH_TTL`.

### Времена жизни токенов

| Тип | TTL | Назначение |
|-----|-----|------------|
| Access Token | 3600 сек | Доступ к MCP ресурсам |
| Refresh Token | 14 дней | Обновление access token |
| Authorization Code | 120 сек | Обмен на access token (PKCE) |

### Generic OAuth2Service ([`service.py`](../../../../src/shared/mcp_oauth/service.py), 165 LoC)

```python
class OAuth2Service:
    """Generic OAuth 2.1 service with PKCE."""

    def __init__(self, store: OAuth2Store, code_ttl=600, access_ttl=3600, refresh_ttl=86400): ...
    def generate_prm_document(self, public_url: str) -> dict: ...       # RFC 9728 PRM
    async def generate_authorization_code(self, client_id, redirect_uri, code_challenge, user_data=None) -> str: ...
    @staticmethod
    def validate_pkce(code_verifier: str, code_challenge: str) -> bool: ...  # RFC 7636 S256
    async def exchange_code_for_tokens(self, code, redirect_uri, code_verifier) -> tuple | None: ...
    async def refresh_tokens(self, refresh_token) -> tuple | None: ...  # single-use + rotation counter
    async def validate_access_token(self, token) -> dict | None: ...
```

Store ([`store.py`](../../../../src/shared/mcp_oauth/store.py), 157 LoC) — `OAuth2StoreBackend` ABC + `InMemoryBackend` (single-process) + `OAuth2Store` wrapper с `start_cleanup()`/`stop_cleanup()`. Готов к extension: `SQLiteBackend`/`RedisBackend` — drop-in.

### BSL legacy wrapper (ретирован)

Адаптер `src/bsl/mcp_server/auth/oauth2.py` (78 LoC), паковавший `(login, password)` в generic `user_data: dict`, удалён вместе со всем модулем `src/bsl/mcp_server` 2026-07-24 ([ADR-056](../../../../.claude/skills/architecture-research/adr/056-retire-src-bsl-mcp-server.md)): модуль был неиспользуемым vendored-близнецом upstream `vladimir-kharin/1c_mcp`, продакшн-доступ к 1С идёт через сабмодуль `external/1c_mcp`. Новый код использует `src.shared.mcp_oauth` напрямую; BSL-паттерн воспроизводится через `user_data={"login": ..., "password": ...}`.

### FastAPI reusable router

[`src/shared/mcp_oauth/fastapi/`](../../../../src/shared/mcp_oauth/fastapi/) — `build_oauth_router()` собирает `/.well-known/oauth-protected-resource` (RFC 9728), `/.well-known/oauth-authorization-server` (RFC 8414), `/authorize` (PKCE S256 mandatory, plain отклоняется), `/token` (authorization_code + refresh_token grants). Подключение одной строкой:

```python
app.include_router(build_oauth_router())
```

`require_oauth` ([`dependencies.py`](../../../../src/shared/mcp_oauth/fastapi/dependencies.py)) — Bearer-валидация с feature-flag bypass через `app.state.oauth_enabled`.

**Безопасность `_public_url`:** `x-forwarded-proto`/`x-forwarded-host` доверяются безусловно — деплоить строго за reverse proxy, который strips эти заголовки на входе (nginx `proxy_set_header`, Envoy `request_headers_to_remove`), иначе клиент может подделать `issuer` в PRM/ASM метаданных. В паре с `TrustedHostMiddleware`.

### Audit infrastructure

[`src/shared/mcp_oauth/audit.py`](../../../../src/shared/mcp_oauth/audit.py) — `AuditedOAuth2Service` (sync sink contract, emit-failures глотаются, audit никогда не блокирует auth) эмитит `OAuthAuditEvent` (5 типов: `code_issued`, `token_exchanged`, `token_refreshed`, `token_validated`, `token_rejected`). Payload содержит только `client_id`/`event_type`/`success`/generic `failure_reason` — **никогда** значения `access_token`/`refresh_token`/`code`/`code_verifier`/`code_challenge` (verified by reviewer, mitigates oracle attacks).

### RFC compliance

| RFC | Реализация |
|---|---|
| **RFC 7636** PKCE | ✅ S256 mandatory |
| **RFC 9728** PRM | ✅ `/.well-known/oauth-protected-resource` |
| **RFC 8414** ASM | ✅ `/.well-known/oauth-authorization-server` |
| **RFC 6750** Bearer | ✅ `WWW-Authenticate` header on 401 |
| **RFC 8707** Resource Indicators | ❌ TODO |
| **RFC 7591** Dynamic Client Registration | ❌ TODO |

### stdio vs HTTP transport

[`src/mcp_server/server.py`](../../../../src/mcp_server/server.py) — **stdio-only transport**. OAuth применяется только к HTTP/SSE MCP, не к stdio (local IPC). Когда потребуется HTTP-transport для pdf-vector-graph — подключение через `build_oauth_router()` + настройка `app.state.oauth_service`/`app.state.oauth_enabled`.

### Antipatterns

| Плохо | Почему | Как правильно |
|---|---|---|
| Использовать BSL wrapper для нового кода | Sync-shaped legacy API, login/password coupling | Импортировать напрямую из `src.shared.mcp_oauth` с `user_data: dict` |
| Trust `x-forwarded-*` без proxy | Client может spoof `issuer` в PRM/ASM | Deploy за reverse proxy, который strips inbound headers + adds outbound |
| Hardcode `MCP_OAUTH_ENABLED=true` в `.mcp.json` | Все окружения forced enabled, нет feature-flag rollout | Keep `false` default, override через shell env в конкретных деплоях |
| Subclass `OAuth2Service` для custom user_data | Лучше пакуй в `user_data: dict` (generic) | Subclass только если меняется flow (например `AuditedOAuth2Service`) |
| Игнорировать refresh rotation | Refresh tokens single-use, новый refresh приходит вместе с access | Всегда сохраняй новый refresh после каждого `refresh_tokens()` |

Подробное руководство: `docs/guides/OAUTH2_ACTIVATION.md`, setup + curl/httpx примеры + troubleshooting: [`docs/wiki/auth/oauth-setup.md`](../../../../docs/wiki/auth/oauth-setup.md).

## IDOR-защита (multi-tenant security)

> Roadmap 260509 §2.3 — closed 2026-05-09.

Все REST-эндпоинты, принимающие `tenant_id` от пользователя (path / query / body), обязаны вызывать общий guard `assert_tenant_access(path_tenant_id, current_tenant, role)` из [`src/api/auth/dependencies.py`](../../../../src/api/auth/dependencies.py). Guard разрешает доступ только если:

- роль = `admin` (тогда любой `tenant_id` разрешён) **или**
- `path_tenant_id == current_tenant` (тенант из JWT совпадает с переданным)

Иначе — `HTTPException 403 "access to other tenant denied"`.

**Где применяется:**

| Эндпоинт | Файл | Параметр tenant_id |
|---|---|---|
| `POST /tenants` (CRUD) | [`tenants.py`](../../../../src/api/routes/tenants.py) | path / admin-only через `require_admin` |
| `GET /tenants/{id}` + `/stats` + `/usage` | [`tenants.py`](../../../../src/api/routes/tenants.py) | path / `_assert_tenant_access` (legacy in-file) |
| `POST /documents/index-async` | [`documents.py`](../../../../src/api/routes/documents.py) | query `tenant_id="default"` / `assert_tenant_access` |
| `POST /jobs/enqueue` | [`jobs.py`](../../../../src/api/routes/jobs.py) | body `request.tenant_id` / `assert_tenant_access` |
| `POST /graph/incremental-update` | [`graph.py`](../../../../src/api/routes/graph.py) | query `tenant_id="default"` / `assert_tenant_access` |

**Тесты:** [`tests/unit/api/test_tenants_idor.py`](../../../../tests/unit/api/test_tenants_idor.py) — 13 тестов (9 unit для guard'а + 4 wiring smoke-tests на присутствие вызова в источнике).

**Чек-лист при добавлении нового эндпоинта с `tenant_id`:**

1. Добавить параметры зависимостей: `_current_tenant: str = Depends(get_current_tenant), _role: str = Depends(get_current_role)`.
2. Первой строкой тела вызвать `assert_tenant_access(tenant_id, _current_tenant, _role)`.
3. Добавить в `tests/unit/api/test_tenants_idor.py::TestIDORGuardWiring` соответствующий путь файла в parametrize-список.
4. Документация — добавить строку в таблицу выше.

**Регрессия:** `assert_tenant_access(...)` обязан вызываться **до** любых I/O операций (Qdrant, Neo4j, ARQ enqueue) — иначе non-admin может вызвать дорогую операцию и получить 403 только в конце.

## Политика ротации JWT secret (roadmap 260509 §2.3.5)

`AUTH__JWT_SECRET` — основной shared-secret для подписи JWT (HS256). Утечка эквивалентна полной компрометации всех существующих токенов до их естественного истечения.

**Триггеры ротации:**

| Триггер | Срочность | Действие |
|---|---|---|
| Регулярная | **каждые 90 дней** | Запланировано через cron / календарь оператора |
| Подозрение утечки | **немедленно** | Rotate + аудит логов |
| Уход сотрудника с production-доступом | **в течение 24 ч** | Rotate + revoke его user-token'ы |
| Coverage gate (pip-audit CVSS ≥ 7.0 на `pyjwt`) | **в течение 7 дней** | Update lib → rotate secret |

**Процедура:**

1. Сгенерировать новый secret: `python -c "import secrets; print(secrets.token_urlsafe(64))"` (минимум 64 байта entropy, не короче чем существующий).
2. Записать в secret store (Vault / GitHub Secrets / Docker secrets), **не коммитить** в репо.
3. Update `AUTH__JWT_SECRET` в production env, перезапустить API:
   - **Все существующие токены становятся невалидны** — клиенты получают 401 и должны re-login.
   - **Grace period отсутствует** (HS256 не поддерживает rolling keys без расширения header'а с `kid`).
   - Max downtime для активных пользователей = время на re-login (обычно секунды).
4. После rotation: проверить через `curl -H "Authorization: Bearer <old_token>" /tenants/me` → должно вернуть 401.
5. Обновить дату последней ротации в operations log (рекомендуется per-deployment файл `data/secrets-rotation.log`).

**Что НЕ делать:**

- ❌ **Снижать `AUTH__JWT_EXPIRATION_HOURS=24`** до < 1ч в попытке «частой ротации» — нагружает auth flow без security wins (rotation secret'а покрывает тот же угол атаки).
- ❌ **Хранить старые secret'ы для verify-only режима** — кодовая база поддерживает только один active secret; multi-key rotation потребует переписывания `JWTHandler.decode_token` через JWKS (вне scope).
- ❌ **Использовать тот же `AUTH__JWT_SECRET` между dev/staging/prod** — каждое окружение должно иметь свой secret для isolation.

**Aux: `pip-audit` scan** (job `security-audit`, [`.github/workflows/ci.yml:355-377`](../../../../.github/workflows/ci.yml#L355)) ловит CVE в `pyjwt`/`cryptography`/смежных deps. Запускается **только вручную** через `workflow_dispatch` — расписания `schedule:`/cron в `ci.yml` **нет**; job гейтирован `if: github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'`, но триггер `schedule` в workflow не объявлен, поэтому по расписанию не срабатывает. `--strict` mode, `continue-on-error: true` (advisory — fix CVSS ≥ 7.0 в течение 7 дней per выше).
