# 17.5 Команды тестирования 1С — VA BDD (написание и прогон)

> Эта глава — про **этап 4 (Тестирование)** пайплайна 1С: написание и прогон VA BDD тестов. Полный пайплайн
> (анализ → реализация → тестирование, 4-этапная парадигма, режимы запуска, маршрутизация, хуки проводки)
> описан в отдельной [главе 43 «Пайплайн 1С»](../../4_МЫШЛЕНИЕ/4.4_ПАЙПЛАЙН_1С/43.1_ОБЗОР_И_ПАРАДИГМА.md).

## Обзор

Две slash-команды покрывают этап тестирования задачи 1С — написание `.feature`-файлов и их
секционно-цепочный прогон с возобновлением:

```
/write-1c-tests <TEST-PLAN>            → features/<task-slug>/NN_*.feature
    ↓
/run-1c-tests <features/<task-slug>/>  → .run-state.json + JUnit XML
    ↓ (на FAIL секции)
/write-1c-tests --section <X>          → точечная калибровка
    ↓
/run-1c-tests --from <X>               → возобновление с упавшей секции
```

Обе команды делегируют методологию скиллу `va-bdd-testing` (v1.1). Входной артефакт —
`TEST-PLAN-DETAILED.md` (от этапа анализа, см. [главу 43](../../4_МЫШЛЕНИЕ/4.4_ПАЙПЛАЙН_1С/43.2_КОМАНДЫ_И_РЕЖИМЫ.md)). В
4-этапной парадигме зелёный `.run-state.json` (все секции passed) закрывает этап 4 — хук
`pipeline-1c-advance` (F-1.6).

## /write-1c-tests — написание VA BDD тестов

**Файл команды:** [.claude/commands/write-1c-tests.md](../../../../.claude/commands/write-1c-tests.md)
**Используемый skill:** `va-bdd-testing` (v1.1)

**Назначение:** По готовому плану тестирования задачи сгенерировать `.feature`-файлы для Vanessa
Automation с откалиброванными step-паттернами.

**Вход** (`$ARGUMENTS`):
- Путь к `TEST-PLAN-DETAILED.md` или папке задачи с планом
- Опциональные: конкретный сценарий, фаза, тег

**Декомпозиция задачи на логические блоки.** Один логический блок = один объект конфигурации +
все связанные с ним формы и бизнес-логика = один `.feature`-файл. Источники для декомпозиции:
матрица автоматизации в TEST-PLAN, точки модификации из ANALYSIS-REPORT, дерево метаданных от
`mcp__1c-mcp-crud__get_metadata_tree`.

**Чеклист типов объектов конфигурации 1С (27 типов).** Команда требует пройти **все типы
объектов из чеклиста**, но включать в тесты только те, которые реально необходимы для
тестирования задачи. Для каждого типа выдаётся явный вердикт: `✅ feature` / `⚠️ зависимость` /
`🔐 pre-check` / `❌ не влияет`. Это гарантирует, что ни один тип не был пропущен молча
(важно для скрытых зависимостей: подписки на события, регламентные задания, роли, константы).

**4 обязательные фазы на КАЖДЫЙ логический блок.** Переход к следующей фазе возможен только
после выполнения Definition of Done предыдущей:

1. **Анализ формы (клиент + сервер).** Получить точные element names, типы полей, кастомные кнопки,
   условия видимости. Инструменты: `mcp__1c-mcp-crud__get_form_structure`/`get_metadata`,
   `mcp__edt-mcp__read_module_source` (Form.Module), Grep по `Form.xml`.
2. **Анализ объектной модели (максимальная глубина).** State machine состояний, движения регистров,
   триггеры, роли, асинхронные обработчики. Инструменты: EDT-MCP, `bsl-semantic-search` (call graph,
   impact analysis, object info), `ast-grep-mcp`, `mcp__1c-mcp-crud__execute_query` для валидации
   на живых данных, `mcp-reasoner` (10-12 уровней для сложной бизнес-логики).
3. **Дополнительное исследование.** API платформы через `mcp__bsl-platform-context__search`/
   `getMember`/`getMembers`/`getConstructors`, официальная документация VA
   (https://pr-mex.github.io/vanessa-automation/dev/), Инфостарт, GitHub.
4. **Написание тестов.** Собрать `.feature`-файл из откалиброванных паттернов скилла
   `va-bdd-testing`, с VERIFY-комментариями для неоткалиброванных мест. Перед записью каждого
   упоминаемого объекта (ТС, номенклатура, контрагент) — проверить наличие в TestDB через
   `execute_query`, при отсутствии — создать через `execute_code` в блоке `Контекст:` или
   пометить сценарий `@pending`.

**Основной инструмент анализа:** `1c-mcp-crud` — primary MCP с достаточным функционалом для
большинства задач (16 tools: get_metadata_tree, list_metadata_objects, get_form_structure,
execute_query, validate_query, execute_code, find_references_to_object, get_access_rights,
get_event_log и др.). Дополнительные MCP используются, только когда `1c-mcp-crud` не хватает.

**Выход:**
```
features/<task-slug>/
    NN_<logical-block>.feature     # production сценарии
    probe_<aspect>.feature         # probe/калибровка отдельно
```
Плюс обновление секции «Статус калибровки» в `TEST-PLAN-DETAILED.md` и отчёт в чате.

## /run-1c-tests — цепочный прогон VA BDD тестов

**Файл команды:** [.claude/commands/run-1c-tests.md](../../../../.claude/commands/run-1c-tests.md)
**Используемый skill:** `va-bdd-testing` (v1.1)

**Назначение:** Запустить feature-файлы задачи с секционно-цепочным исполнением: при сбое —
возобновление с упавшей секции без повторного прогона пройденных.

**Модель цепочки.** Секция = один `.feature`-файл = один логический блок. Цепочка = упорядоченная
последовательность секций с зависимостями, извлечёнными из `METADATA → Dependencies:` в шапке
`.feature`-файлов. Топологическая сортировка → порядок исполнения.

**State file** `features/<task-slug>/.run-state.json` хранит статус каждой секции (passed/failed/
pending/invalidated), продолжительность, попытки, созданные объекты (UUID + тип + маркер), последний
шаг ошибки. При запуске без параметров команда находит первую секцию со `status ≠ passed` и
продолжает цепочку с неё.

**Переиспользование артефактов.** Каждая секция в `Тогда` может создавать объекты (документы,
записи регистров), идентифицируемые уникальным маркером в тестовых данных. Post-check после
успешной секции извлекает UUID через `execute_query` и сохраняет в state. Следующие секции получают
эти артефакты как контекст.

**Pipeline (7 этапов на каждую секцию):**

1. **Загрузка и маршрутизация** — прочитать state, построить граф зависимостей, определить
   секции к прогону.
2. **Pre-check (Stage 4a).** Проверка тестовых данных через `execute_query`, проверка артефактов
   предыдущих секций (не пропали ли из БД), проверка ролей. При FAIL — НЕ запускать VA.
3. **Подготовка окружения.** `execute_code` для инициализации контекста из артефактов предыдущих
   секций (параметры сеанса, предзаполненные ссылки).
4. **Запуск VA** пофайлово (НЕ batch — VA зависает при batch-прогоне):
   ```
   powershell -File tools\vanessa\run-bdd.ps1 -Feature "<slug>/<section>.feature" -RunId "<id>"
   ```
5. **Post-check.** Парсинг JUnit XML, SQL-верификация созданных документов/записей регистров,
   извлечение UUID новых артефактов.
6. **Обработка FAIL.** STOP-цепочка, диагностика через таблицу Common Error Messages из скилла
   `va-bdd-testing`, фиксация `last_error_step` в state. Команда НЕ правит feature — это работа
   пользователя или `/write-1c-tests`.
7. **Обновление state + отчёт.** Красивая таблица OK/FAIL/SKIP с рекомендациями для resume.

**Параметры:**

| Параметр | Назначение |
|---|---|
| `<путь>` | Путь к TEST-PLAN / features-директории |
| `--section <NAME>` | Запустить только одну секцию |
| `--from <NAME>` | Запустить с указанной секции и далее |
| `--fresh` | Сбросить state и прогнать с нуля |
| `--dry-run` | Только pre-check всех секций без запуска VA |
| `--timeout <SEC>` | Таймаут на секцию (по умолчанию 120) |
| `--verbose` | Подробный вывод checks |

**После 3 неудачных попыток** на одной секции — предупреждение пользователю о необходимости
углублённой калибровки через `/write-1c-tests --section <X>`.

## Stage 4a — Pre-scenario TestDB Data Check (обязательный)

**Добавлено в скилл `va-bdd-testing` v1.1** (2026-04-11). Защищает от сценариев, которые падают
посередине из-за отсутствия тестовых данных в TestDB.

**Почему это критично.** В реальной калибровке задачи GKSTCPLK-2256 **4 из 6 падений** были
вызваны отсутствием тестовых данных, а не логикой тестов. VA тратит 120–200 секунд на сценарий
перед падением с сообщением вроде «Х985ХМ36RUS не найден в ЭлектронныеТабло» или «М012ВР не найден
в справочнике ТС». Pre-check ловит это за 5–20 секунд до запуска VA.

**Что проверяется** (8-пунктовый чеклист на каждый сценарий):

1. Все ТС существуют в `Справочник.ТранспортныеСредства`
2. Все ТС имеют `ЭтоСправочникПЛК = Истина` (если форма фильтрует по этому)
3. Все ТС «свежие» (без активных регистраций) ИЛИ сценарий терпит stale-состояние
4. Все каталожные элементы (номенклатура, контрагенты, организации, склады, ямы разгрузки) существуют
5. Все точки маршрута существуют
6. Требуемые настройки регистров сведений (табло, параметры) существуют
7. Пользователь теста имеет все роли для кнопок/команд из сценария
8. Значения перечислений, используемые в верификационных запросах, существуют

**5 готовых query templates** в скилле `va-bdd-testing`:

- Проверка существования элемента справочника (generic)
- Fresh transport (нет активных регистраций) — с JOIN на `гкс_СостоянияРегистрации.СрезПоследних`
- Проверка настройки регистра сведений
- Проверка ролей через `mcp__1c-mcp-crud__get_access_rights`
- Проверка значения перечисления

**Что делать при FAIL pre-check** (2 варианта):

1. **Создать недостающие данные** через `mcp__1c-mcp-crud__execute_code` в блоке `Контекст:`
   сценария — предпочтительно для предсказуемого setup.
2. **Пометить сценарий `@pending`** — когда создание данных нетривиально. Сценарии с тегом
   `@pending` **пропускаются** командой `/run-1c-tests` до разблокировки.

**Бюджет времени:**

| Подход | Время на FAIL сценария |
|---|---|
| Без pre-check | 120–200с (VA timeout + teardown) |
| Pre-check через `execute_query` | 0.5–2с на запрос |
| Pre-check для всего сценария (~10 элементов) | 5–20с суммарно |

Экономия **~95%** времени на падениях типа «нет данных».

## Изменения в run-bdd.ps1

Скрипт-runner получил 2 новых опциональных параметра для интеграции с `/run-1c-tests`.
**Обратно совместимо** — существующие вызовы без новых параметров работают как раньше.

### -OutputJson \<path\>

Абсолютный путь для записи структурированного результата в формате JSON. Когда задан, скрипт в
конце прогона пишет файл со следующими полями:

| Поле | Тип | Описание |
|---|---|---|
| `feature` | string | Relative path feature-файла |
| `run_id` | string | Уникальный идентификатор прогона (если задан `-RunId`) |
| `started_at` / `finished_at` | ISO-8601 | Временные метки |
| `duration_s` | float | Длительность в секундах |
| `exit_code` | int | 0 = pass, 1 = fail |
| `build_status` | string | Содержимое `BuildStatus.log` |
| `junit_xml` | string | Путь к скопированному JUnit XML |
| `va_log` | string | Путь к скопированному `va-out.txt` |
| `process_pid` | int | PID главного процесса 1С |
| `last_step` | string | Последний выполненный VA-шаг (best-effort extraction) |
| `timeout_sec` | int | Значение `-TimeoutSec` |

`last_step` извлекается из `va-out.txt` через ASCII-безопасный regex `^\s*\p{IsCyrillic}+\s+`
(матчит строки, начинающиеся с кириллического keyword — И / Когда / Тогда / Допустим / Если),
без encoding-ловушек при обработке UTF-8 без BOM.

### -RunId \<string\>

Уникальный идентификатор прогона для изоляции артефактов. Когда задан:
- JUnit XML копируется в `build/reports/runs/<RunId>/`
- `va-out.txt` копируется в `build/reports/runs/<RunId>/va-out.txt`
- `result.json` автоматически записывается в `build/reports/runs/<RunId>/result.json`, если
  `-OutputJson` не задан явно

Это позволяет держать историю прогонов и параллельно анализировать несколько сессий.

### Retry с экспоненциальным backoff

5 новых параметров для автоматического повтора при транзиентных ошибках VA:

| Параметр | По умолчанию | Описание |
|---|---|---|
| `-MaxRetries` | 1 | Макс. попыток (1 = без retry). Для `/run-1c-tests` рекомендуется 3 |
| `-BackoffBaseSec` | 5 | Базовая задержка перед первым retry |
| `-BackoffMultiplier` | 3.0 | Множитель задержки: 5s, 15s, 45s |
| `-BackoffMaxSec` | 60 | Потолок задержки |
| `-JitterPct` | 30 | Случайный разброс +/-% к задержке |

**Классификация ошибок.** Функция `Test-TransientError` анализирует VA лог и BuildStatus:

- **Транзиентные** (retry): `Не найдено окно`, `TestClient не отвечает`, `Таймаут ожидания`,
  `Поле не доступно`, crash без VA log
- **Логические** (no retry): `Не найдена процедура для шага`, `Кнопка не найдена`,
  `Неверный тип навигационной ссылки`, `Поле формы не существует`

Когда `-OutputJson` задан, результат дополняется полями retry:

| Поле | Тип | Описание |
|---|---|---|
| `total_attempts` | int | Общее число попыток |
| `retried` | bool | `true` если было хотя бы одно retry |
| `error_category` | string | `none` / `transient` / `logical` |
| `attempts` | array | Массив объектов `{attempt, started_at, duration_s, exit_code, error_category, last_step}` |

**Обратно совместимо** — без `-MaxRetries` (или с `-MaxRetries 1`) поведение идентично
предыдущей версии.

### Auto-fix типовых ошибок (Этап 6.5)

Каталог ошибок: `tools/vanessa/error-catalog.yaml` — 6 типов с алгоритмами auto-fix.
Управляется параметром `--fix-mode` команды `/run-1c-tests`:

| Режим | Поведение |
|---|---|
| `suggest` (default) | Показать предлагаемый fix, не применять |
| `auto` | Применить fix + retry автоматически |
| `off` | Только диагностика |

**Типы ошибок и алгоритмы:**

| ID | Ошибка | Auto-fixable | MCP lookup |
|---|---|---|---|
| `button_not_found` | Кнопка не найдена | Да (80%) | `get_form_structure` → fuzzy match |
| `field_not_found` | Поле формы не существует | Да (75%) | `get_form_structure` + DataPath check |
| `window_not_found` | Не найдено окно | Да (70%) | Проверка nav prefix + wildcards |
| `row_not_found` | Строка не найдена | Да (65%) | Column type → `первой строке` |
| `wrong_nav_link` | Неверный тип ссылки | Да (90%) | Тип объекта → app/list |
| `step_not_found` | Процедура для шага | **Нет** | Только suggest (VA docs search) |

**Ограничения:** макс 3 итерации auto-fix на секцию, откат fix при повторном FAIL.

### Пример использования из /run-1c-tests

```powershell
# Для каждой секции цепочки
$runId = "$taskSlug-$(Get-Date -Format 'yyyyMMdd-HHmmss')"
powershell -File tools\vanessa\run-bdd.ps1 `
    -Feature "gkstcplk2256/06_arm_workflow.feature" `
    -RunId $runId `
    -TimeoutSec 300 `
    -MaxRetries 3

# Прочитать структурированный результат
$result = Get-Content "build\reports\runs\$runId\result.json" | ConvertFrom-Json
if ($result.exit_code -eq 0) {
    # Обновить .run-state.json, пометить секцию passed
} else {
    # STOP-цепочка, вывести last_step для диагностики
}
```

## Цикл отладки секции

Когда секция падает:

```
/run-1c-tests → FAIL @ <section>
    ↓
Анализ ошибки (скилл va-bdd-testing → Common Error Messages)
    ↓
Исправление <section>.feature вручную ИЛИ через /write-1c-tests --section <section>
    ↓
/run-1c-tests --from <section>      # state знает, что предыдущие прошли
    ↓
Повторный прогон только <section> и далее
```

State сохраняет `attempts` — счётчик попыток. После **3 неудач** — STOP с рекомендацией
углублённой probe-калибровки.
