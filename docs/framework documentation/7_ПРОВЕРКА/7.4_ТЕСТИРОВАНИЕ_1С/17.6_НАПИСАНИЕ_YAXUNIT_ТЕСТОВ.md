# 17.6 Написание YAxUnit-тестов для 1С

> **Тип:** модульное тестирование серверной бизнес-логики. Этап: **4 Тестирование**. Полный
> пайплайн 1С — [глава 43](../../4_МЫШЛЕНИЕ/4.4_ПАЙПЛАЙН_1С/43.1_ОБЗОР_И_ПАРАДИГМА.md).
> Инструменты этапа 4 — [43.9.8 Тестирование](../../4_МЫШЛЕНИЕ/4.4_ПАЙПЛАЙН_1С/43.9.8_ТЕСТИРОВАНИЕ.md).

---

## 1. Когда YAxUnit, а когда BDD (Vanessa Automation)

| Критерий | YAxUnit | VA BDD |
|----------|---------|--------|
| **объект проверки** | Функции/процедуры общих модулей, API экспортные методы | Сценарии пользователя, межмодульные взаимодействия, UI-автоматизация |
| **контекст исполнения** | Серверный код только; in-process, без GUI | Серверный + клиентский код; требует запущенного 1C; GUI-сценарии эмулируют пользователя |
| **скорость** | Быстро (мсек на тест) | Медленно (сек–минуты на сценарий, зависит от GUI-операций) |
| **воспроизводимость** | Высокая; изолированные unit-тесты | Средняя; зависит от консистентности тестового стенда |
| **зависимость от данных** | Низкая; работает с моками, фикстурами в памяти | Высокая; требует TestDB, изоляция сценариев через откаты |
| **типичная задача** | Проверить корректность бизнес-логики функции; граничные случаи | Проверить end-to-end рабочий процесс; перепроведение документов; формирование отчёта |

**Практическое правило:** YAxUnit для быстрой feedback-лупа (часть code review), VA BDD для регрессионного набора (перед deployом). Запуск YAxUnit — через `python scripts/run_1c_unit_tests.py` (итоговый runner: `mcp-onec-test-runner`, **НЕ** `run-bdd.ps1`). Если тест требует GUI, документооборота или слепых откатов данных — это VA BDD, не YAxUnit.

## 2. Структура тест-модуля

## Директорийная структура

```
src/bsl/exts/UnitTests/
├── .externaldata
│   ├── Metadata/
│   │   └── ConfigDumpInfo.xml
│   ├── Catalogs/
│   ├── Documents/
│   └── ...
├── Documents/
│   ├── Ext/
│   │   ├── Module.bsl (если нужно расширение)
│   │   └── ...
│   └── ...
├── CommonModules/
│   ├── гкс_ПримерУнитТестов_Сервер.bsl
│   ├── гкс_ТестыАльтернативнойЛогики_Сервер.bsl
│   └── ...
└── Configuration.bsl
```

**Правило:** тест-модули — это **CommonModule** с атрибутом `Server = true` и **НЕ видимые извне** (атрибут `Visible = false` опционален, но рекомендуется).

## Полная анатомия тест-модуля

```bsl
// гкс_ПримерУнитТестов_Сервер.bsl — Общий модуль
// Атрибуты: Server = True

#Область СлужебныйПрограммныйИнтерфейс

Процедура ИсполняемыеСценарии() Экспорт
    ЮТТесты.ДобавитьСерверныйТест("ЭтоСсылка_Строка_Ложь",
        "ЭтоСсылка(Строка) = Ложь");
    ЮТТесты.ДобавитьСерверныйТест("ЭтоСсылка_Справочник_Истина",
        "ЭтоСсылка(Справочник) = Истина");
    ЮТТесты.ДобавитьСерверныйТест("ФолдСейф_PushPop_Согласованность",
        "FoldState persist/restore coherency");
КонецПроцедуры

#КонецОбласти

#Область Тесты

Процедура ЭтоСсылка_Строка_Ложь() Экспорт
    ЮТест.ОжидаетЧто(гкс_ОбщегоНазначения.ЭтоСсылка(Тип("Строка")),
        "Строка не является ссылкой")
        .ЭтоЛожь();
КонецПроцедуры

Процедура ЭтоСсылка_Справочник_Истина() Экспорт
    ТипСпр = Новый ОписаниеТипов("СправочникСсылка.Партнеры");
    ЮТест.ОжидаетЧто(гкс_ОбщегоНазначения.ЭтоСсылка(ТипСпр),
        "Справочник.Партнеры — ссылочный тип")
        .ЭтоИстина();
КонецПроцедуры

Процедура ФолдСейф_PushPop_Согласованность() Экспорт
    // Фикстура
    Сост1 = гкс_МояЛогика.СохранитьСостояние();
    Сост2 = гкс_МояЛогика.СохранитьСостояние();

    // Act
    гкс_МояЛогика.ВосстановитьСостояние(Сост1);
    РезультатВосстановления = гкс_МояЛогика.ПолучитьТекущееСостояние();

    // Assert
    ЮТест.ОжидаетЧто(РезультатВосстановления).ЭтоОбъект(Сост1);
    ЮТест.ОжидаетЧто(Сост1 <> Сост2).ЭтоИстина();
КонецПроцедуры

#КонецОбласти
```

## Критические правила

1. **Имя в ДобавитьСерверныйТест ДОЛЖНО точно совпадать с именем процедуры.** Если написали `"ЭтоСсылка_Строка_Ложь"`, процедура обязана называться `Процедура ЭтоСсылка_Строка_Ложь() Экспорт`. Несовпадение → тест не запустится (runner не найдёт процедуру).

2. **Все процедуры тестов обязаны иметь модификатор `Экспорт`.** Без него модуль их не видит.

3. **`ИсполняемыеСценарии()` — единственная точка входа** для YAxUnit. Это процедура, которую вызывает runner (`yaxunit`); она регистрирует все тесты через `ЮТТесты.Добавить…()`. Другие процедуры в этой области не вызываются напрямую.

## Соглашение об именовании (Naming Convention)

```
<ЧтоПроверяется>_<Условие>_<ОжидаемыйРезультат>
```

Примеры:
- `ЭтоСсылка_Строка_Ложь` — проверяем `ЭтоСсылка()`, условие входа — `Строка`, ожидание — `Ложь`.
- `РасчетНДС_ТавераАНулеваяСтавка_НДСНеНачисляется` — проверяем расчёт НДС, таверная категория партнёра, НДС не начисляется.
- `ИмпортДокументов_ПостмаркетОшибка_ОшибкаПерехвачена` — импорт, ошибка от постмаркета, исключение обработано корректно.

**Цель:** по названию теста сразу ясны (1) что проверяется, (2) при каких условиях, (3) какой результат ожидается. Облегчает навигацию при падении тестов.

## 3. Assert-API: ЮТест.ОжидаетЧто(...).Матчер()

Основной паттерн для утверждений в YAxUnit:

```
ЮТест.ОжидаетЧто(<ФактическоеЗначение> [, <Сообщение>]).<Матчер>()
```

где `<ФактическоеЗначение>` — значение для проверки, опциональное `<Сообщение>` — текст ошибки при неудаче, а `<Матчер>()` — один из встроенных методов сравнения из модуля **ЮТУтверждения**.

| Матчер | Назначение | Пример |
|--------|-----------|--------|
| `.Равно(<Ожидаемое>)` | Проверка равенства значений | `ЮТест.ОжидаетЧто(Результат).Равно(42)` |
| `.НеРавно(<Ожидаемое>)` | Проверка неравенства | `ЮТест.ОжидаетЧто(Статус).НеРавно("Ошибка")` |
| `.Больше(<Ожидаемое>)` | Проверка «больше» | `ЮТест.ОжидаетЧто(Количество).Больше(0)` |
| `.БольшеИлиРавно(<Ожидаемое>)` | Проверка «≥» | `ЮТест.ОжидаетЧто(Сумма).БольшеИлиРавно(100)` |
| `.Меньше(<Ожидаемое>)` | Проверка «меньше» | `ЮТест.ОжидаетЧто(Остаток).Меньше(50)` |
| `.МеньшеИлиРавно(<Ожидаемое>)` | Проверка «≤» | `ЮТест.ОжидаетЧто(Дни).МеньшеИлиРавно(365)` |
| `.ЭтоИстина()` | Проверка истинности логического значения | `ЮТест.ОжидаетЧто(ФлагАктивен).ЭтоИстина()` |
| `.ЭтоЛожь()` | Проверка ложности | `ЮТест.ОжидаетЧто(ФлагОтключен).ЭтоЛожь()` |
| `.ЭтоНеопределено()` | Проверка неопределённого значения | `ЮТест.ОжидаетЧто(Результат).ЭтоНеопределено()` |
| `.ИмеетТип(<Тип>)` | Проверка типа значения | `ЮТест.ОжидаетЧто(Объект).ИмеетТип(Тип("СправочникСсылка.Номенклатура"))` |
| `.Содержит(<Элемент>)` | Проверка наличия элемента в массиве/строке | `ЮТест.ОжидаетЧто(Массив).Содержит("Найденный")` |
| `.СодержитСтрокуПоШаблону(<Шаблон>)` | Проверка совпадения по шаблону (RegEx) | `ЮТест.ОжидаетЧто(Сообщение).СодержитСтрокуПоШаблону("Ошибка \d+")` |
| `.ВСписке(<Список>)` | Проверка принадлежности списку | `ЮТест.ОжидаетЧто(Статус).ВСписке(Новый Массив("Черновик", "Опубликовано"))` |
| `.Заполнено()` | Проверка заполненности значения | `ЮТест.ОжидаетЧто(Наименование).Заполнено()` |
| `.ИмеетДлину(<Длина>)` | Проверка точной длины строки/массива | `ЮТест.ОжидаетЧто(Коллекция).ИмеетДлину(3)` |
| `.ИмеетДлинуБольше(<Длина>)` | Проверка длины > N | `ЮТест.ОжидаетЧто(Строка).ИмеетДлинуБольше(10)` |
| `.ИмеетДлинуМеньше(<Длина>)` | Проверка длины < N | `ЮТест.ОжидаетЧто(Код).ИмеетДлинуМеньше(20)` |
| `.Свойство(<ИмяСвойства>)` | Переход в режим проверки свойства объекта | `ЮТест.ОжидаетЧто(МойОбъект, "Объект должен иметь код").Свойство("Код").Равно("А001")` |
| `.Метод(<ИмяМетода>, [<Параметры>])` | Проверка вызова метода и результата | `ЮТест.ОжидаетЧто(МойОбъект).Метод("Записать", ЮТМетоды.МассивПараметров(РежимЗаписи.Запись)).ВыбрасываетИсключение()` |
| `.ВыбрасываетИсключение([<ТипИсключения>])` | Проверка возбуждения исключения | `ЮТест.ОжидаетЧто(МойОбъект, "Без прав — ошибка").Метод("Записать").ВыбрасываетИсключение()` |

**Примеры использования:**

```bsl
// Проверка свойства объекта
ЮТест.ОжидаетЧто(МойОбъект, "Объект должен иметь код").Свойство("Код").Равно("А001");

// Проверка выброса исключения при вызове метода
ЮТест.ОжидаетЧто(МойОбъект, "Без прав — ошибка")
    .Метод("Записать", ЮТМетоды.МассивПараметров(РежимЗаписи.Запись))
    .ВыбрасываетИсключение();
```

**БД-утверждения:**

Для проверки содержимого таблиц БД используются специализированные утверждения:

```bsl
// Проверка записей таблицы ИБ (движения регистров / данные справочников):
ЮТест.ОжидаетЧтоТаблицаБазы("Справочник.Номенклатура")
    .СодержитЗаписи(ЮТест.Предикат(Новый Структура("Код, Наименование", "А001", "Товар")));
// Удобные варианты: .СодержитЗаписиСКодом("А001") / .СодержитЗаписиСНаименованием("Товар") / .СодержитТолькоОднуЗапись(...)
```

## 4. Изоляция данных и моки

### Транзакции и очистка тестовых данных

YAxUnit поддерживает два основных механизма для работы с данными:

**`.ВТранзакции()`** — метод выполняет тест в контексте транзакции с автоматическим откатом при завершении:

```bsl
ДобавитьСерверныйТест("ТестМодульБизнесЛогики")
    .ВТранзакции();   // тест выполнится в транзакции с авто-откатом (ТОЛЬКО серверный тест)

Процедура ТестДополнениеОстатков() Экспорт
    // Изменения в БД откатываются автоматически после теста
    ДокументСсылка = ЮТест.Данные().СоздатьДокумент(Документы.ПоступлениеОстатков,
        Новый Структура("РежимЗаписи", РежимЗаписиДокумента.Проведение));

    ЮТест.ОжидаетЧто(ДокументСсылка.Проведен).ЭтоИстина();
КонецПроцедуры
```

**`.УдалениеТестовыхДанных()`** — явная очистка данных после каждого теста (альтернатива транзакциям):

```bsl
ДобавитьСерверныйТест("ТестМодульДляОчистки")
    .УдалениеТестовыхДанных();   // удаляет объекты, созданные через ЮТест.Данные() (НЕ откат изменений)

Процедура ТестСозданиеНоменклатуры() Экспорт
    // Созданные элементы будут удалены после теста
    Номенклатура = ЮТест.Данные().СоздатьЭлемент(Справочники.Номенклатура, "Тестовый товар");

    ЮТест.ОжидаетЧто(Номенклатура).Заполнено();
КонецПроцедуры
```

### Фабрики для создания тестовых данных

Встроенная фабрика **`ЮТест.Данные()`** создаёт элементы конфигурации:

```bsl
// Создание справочника
Номенклатура = ЮТест.Данные().СоздатьЭлемент(Справочники.Номенклатура, "Товар А",
    Новый Структура("Артикул", "ART-001"));

// Создание документа
Документ = ЮТест.Данные().СоздатьДокумент(Документы.ПоступлениеОстатков,
    Новый Структура("Номер, Дата", "00001", ТекущаяДата()));
```

### Мокирование методов

Модуль **Мокито** позволяет подменять методы модулей для управления их поведением:

**Обучение мока (подстановка значения):**

```bsl
Процедура ТестПолучениеДанныхИзВнешнейСистемы() Экспорт
    ТестовыеДанные = Новый Массив;
    ТестовыеДанные.Добавить(Новая Структура("Код, Наименование", "А001", "Товар"));

    // Обвязка &Вместо("ПолучитьДанныеИзСистемы") + МокитоПерехват в расширении ОБЯЗАТЕЛЬНА
    Мокито.Обучение(МойМодуль)
        .Когда("ПолучитьДанныеИзСистемы")   // без параметров = любой вызов
        .Вернуть(ТестовыеДанные);
    Мокито.Прогон();   // ОБЯЗАТЕЛЬНО: режим прогона перед вызовом тестируемого кода

    // Тестируемый код теперь получит подменённые данные
    Результат = ОсновнойМодуль.ОбработатьДанные();

    ЮТест.ОжидаетЧто(Результат).ИмеетДлину(1);
КонецПроцедуры
```

**Проверка вызовов мока:**

```bsl
Процедура ТестПроверкаВызоваМетода() Экспорт
    Мокито.Обучение(МойМодуль).Когда("СохранитьДанные").Вернуть(Истина);
    Мокито.Прогон();

    // Выполняем тестируемый код
    ОсновнойМодуль.ВыполнитьОперацию();

    // Проверяем, что метод был вызван ровно один раз
    Мокито.Проверить(МойМодуль).КоличествоВызовов("СохранитьДанные").Равно(1);

    // Проверяем с конкретными параметрами
    Мокито.Проверить(МойМодуль)
        .КоличествоВызовов("СохранитьДанные",
            Мокито.МассивПараметров(Новый Структура("Ключ, Значение", "ID", 42)))
        .Равно(1);
КонецПроцедуры
```

**Когда использовать моки:**

- **Подменить внешние сервисы** — WebЗапросы, REST-API, 1С-информационные сервисы
- **Контролировать побочные эффекты** — запись в БД, отправку писем, логирование
- **Ускорить тесты** — избежать дорогостоящих операций (импорт данных, вычисления)
- **Изолировать зависимости** — тестировать методы отдельно от окружения
- **Проверить кооперацию** — убедиться, что модуль вызывает зависимость с правильными параметрами

## 5. Регистрация тест-модуля (дискавери)

YAxUnit автоматически обнаруживает тест-модули **только** через подсистему `ЮТТ_ЮТПодключаемыеМодули` и специальный объект `Модульные`. Без регистрации модуль не будет найден и выполнен.

### Трёхэтапная процедура регистрации

**Шаг 1: Создание общего модуля**

Создайте новый **незаимствованный** общий модуль (CommonModule). Имя модуля — ЛЮБОЕ: `ЮТТ` это префикс ПОДСИСТЕМЫ, а НЕ модулей (в этом проекте тест-модули называются `гкс_<Объект>Тест`; официальная схема YAxUnit — `ОМ_Объект` / `Спр_Объект_МО`):

- Имя модуля свободное; ключевое — зарегистрировать его в подсистеме `Модульные` (Шаг 2)
- Установите флаг **«Сервер»** (или «Сервер и клиент», если требуется)
- Добавьте экспортные процедуры тестов (например, `ТестДополнение()`, `ТестУвеличение()`)

**Шаг 2: Добавление модуля в Модульные.xml**

Откройте объект `Модульные` (подсистема `ЮТТ_ЮТПодключаемыеМодули`) и отредактируйте его XML. Найдите элемент `<Content>` и добавьте новую запись:

```xml
<Content>
  <xr:Item xsi:type="xr:MDObjectRef">CommonModule.ЮТТМойПроект</xr:Item>
  <xr:Item xsi:type="xr:MDObjectRef">CommonModule.ЮТТПроверкиКонфигурации</xr:Item>
</Content>
```

**Шаг 3: Обновление Configuration.xml**

Откройте файл `Configuration.xml` и добавьте ссылку на новый модуль в секцию `<ChildObjects>`:

```xml
<ChildObjects>
  <!-- Существующие записи -->
  <Subsystem>ЮТТ_ЮТПодключаемыеМодули</Subsystem>
  <!-- ... другие объекты ... -->
</ChildObjects>
```

### Без регистрации модуль не найден

Если пропустить любой из трёх шагов:

- YAxUnit **не обнаружит** тестовый модуль
- Тесты **не будут выполнены**
- В журнале запусков не появится никакого сообщения об ошибке

**Проверка регистрации:**

Проверка: после деплоя расширения запустите `run_all_tests` — модуль должен появиться в списке.

## 6. Деплой расширения UnitTests

Деплой выполняется **двумя отдельными вызовами** Designer (8.3.27.1936). Нельзя объединить в один вызов.

```powershell
# Шаг 1: загрузить файлы расширения в конфигуратор
```

## 7. Прогон тестов через mcp-onec-test-runner

| Инструмент | Команда | Назначение |
|---|---|---|
| `mcp-onec-test-runner` | `run_module_tests(moduleName="ЮТТПримерТест")` | Прогон одного конкретного модуля |
| `mcp-onec-test-runner` | `run_all_tests(full=true)` | Прогон всех зарегистрированных тест-модулей |
| `edt-mcp` | `run_yaxunit_tests(...)` | Прогон из EDT с поддержкой отладки |

Результаты сохраняются в `build/reports/` в формате **JUnit XML**.

> **ПРЕДУПРЕЖДЕНИЕ — подключение к TestDB.** `mcp-onec-test-runner` берёт строку
> подключения из gitignored-файла `.env` (переменная `ONEC_TEST_CONN`). Значение по умолчанию:
> `Srvr="KOMPUTER";Ref="TestDB"` — хост `KOMPUTER` **может быть недоступен** в локальной среде.
> Для локального прогона исправить `.env`:
> ```
> ONEC_TEST_CONN=Srvr="DESKTOP-TNU600C";Ref="ИБTransportManagementDevelop"
> ```
> После правки `.env` выполнить `/mcp reconnect`.

### Headless-исполнение тонкого клиента (предусловия, проверено live 2026-06-26)

Раннер запускает `1cv8c.exe ENTERPRISE … /C "RunUnitTests=<config.json>"`. Чтобы прогон
**не «сел в простой»**, обязательны три условия:

1. **БЕЗ `/TESTMANAGER`** в ключах запуска — это режим менеджера UI-тестов: клиент ждёт
   подключения тест-клиента и не исполняет `RunUnitTests`. В launcher
   `scripts/onec_test_runner_launch.py` → `tools.enterprise.additional-launch-keys`
   должно быть `["/DisableStartupDialogs", "/DisableStartupMessages"]`.
2. **`/DisableStartupDialogs` + `/DisableStartupMessages`** — иначе стартовый диалог БСП
   (первый запуск / обновление ИБ) блокирует управление до `&После("ПриНачалеРаботыСистемы")`.
3. **Безопасный режим расширения YAXUNIT — ВЫКЛЮЧЕН.** Иначе чтение `config.json` запрещено
   (`ЮТПараметрыЗапускаСлужебный`: «Расширение подключено в безопасном режиме»), параметры
   молча сбрасываются в дефолт и прогон не идёт. Снять: Конфигуратор → расширение →
   свойства → «Безопасный режим». При CLI-создании расширения (`LoadConfigFromFiles
   -Extension`) дефолт = безопасный режим ВКЛ → требует ручного/авто-снятия.

`config.json` должен нести `closeAfterTests: true` и `showReport: false` — иначе по окончании
прогона открывается форма отчёта и клиент висит. Голый `RunUnitTests=true` (без файла-конфига)
ставит `showReport=Истина, closeAfterTests=Ложь` → зависание; всегда передавать путь к файлу.

## 8. Honest-критерий «тест готов»

> **Тест, который не падает при поломке проверяемой функции, — не тест.**

| Проверка | Как убедиться |
| :--- | :--- |
| **Assert не тавтология** | Временно передать заведомо неверный аргумент или закомментировать `Возврат` в функции — тест должен упасть |
| **Assert не no-op** | Убрать вызов матчера (`.ЭтоЛожь()`) — должна быть ошибка компиляции или явное падение при запуске |
| **Имя метода совпадает посимвольно** | Сравнить строку первого аргумента `ДобавитьСерверныйТест("ИМЯ", ...)` с именем объявленной процедуры — разница в одном символе = тест не запустится |
| **Модуль зарегистрирован** | Проверить наличие `<xr:Item ...>CommonModule.ЮТТМойМодуль</xr:Item>` в `Модульные.xml` раздела `<Content>` |
| **Тест изолирован** | После прогона убедиться, что данные в базе не изменились (транзакция откатилась) или удалены (`.УдалениеТестовыхДанных()`) |

## 9. Связь с пайплайном (рек.3), CI-раннеры и покрытие

### рек.3 — YAxUnit-смоук как advisory-петля (2026-07-19)

Гейт завершения 1С-задачи (`onec-task-completion-stop`) **рекомендует** (advisory `•`, НИКОГДА не
блокирует) прогнать YAxUnit-смоук, когда правлен/добавлен **экспортный серверный метод** (детектор
`onec_change_scope.edits_exported_method`; с 2026-07-19 — двуязычные ключевые слова по грамматике
bsl-parser, async-префикс `Асинх`, session-scoped сужение по `.bsl`-путям сессии против грязного
work-tree, кап 50 файлов): экспортная поверхность = тестируемый инвариант, POST-change
комплемент impact-чека («кто сломается»). Маршрут — **единственный** `mcp-onec-test-runner`
(`run_module_tests` затронутого модуля / `run_all_tests`), НЕ `edt/codepilot run_yaxunit_tests`-дубли,
НЕ BDD. Прогон пишет `.run-state.json` → авто-Этап-4 (`advance_test_done`); иначе — секция live-данных
(ADR-050). Метрика — `onec_toolgate_validation.yaxunit_rate_on_applicable` (честный знаменатель = задачи
с правкой экспортного метода).

> **`ЮТДымовыеТесты` ≠ рек.3-«смоук».** Встроенный YAxUnit-`ДымовыеТесты` — тяжёлый ФУНКЦИОНАЛЬНЫЙ
> smoke по ВСЕЙ конфе (открыть все формы / провести все документы / права); реализация — отдельное
> незрелое расширение [alexandr-yang/yaxunit-smoke](https://github.com/alexandr-yang/yaxunit-smoke)
> («not for production»). Компиляция/метаданные — ТРЕТИЙ путь (syntax check `check_syntax_designer_modules`/
> `check_syntax_edt`). рек.3-«смоук» = быстрый unit-прогон ЗАТРОНУТОГО модуля, ни то, ни другое.

### Безопасный режим ломает и Мокито

Помимо чтения `config.json` (§7), включённый безопасный режим расширения **ломает перехваты Мокито**
(`МокитоПерехват`/`&Вместо` требуют привилегированных операций) → мок молча не подменяет. После деплоя
расширения снять и «Безопасный режим», и «Защиту от опасных действий».
