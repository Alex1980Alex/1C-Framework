# Проверка Git и документации

Пакет работает с Python 3.11+ и Git без pipeline-каталога и клиентских хуков оснастки. Установка и доверие к новой копии требуют отдельной приёмки.
В командах `<package>` — абсолютный путь проверенной распаковки, `<target>` — абсолютный путь проверяемого Git-репозитория; пути с пробелами заключайте в кавычки.

Сборка из доверенного дерева: `python -I -B scripts/git_docs_package.py build --source "<source>" --output "<external>/git-docs.zip" --source-base <full-SHA>`.
Исходный каталог и новый выходной ZIP задавайте абсолютными путями; ZIP должен находиться вне исходного дерева. Рядом создаётся `git-docs.zip.manifest.json`.
`source_base` сообщает происхождение, а не одобрение. Получите ожидаемый SHA256 манифеста по независимому доверенному каналу; пересчитанный SHA скачанного рядом манифеста сам по себе доверия не даёт.
До распаковки проверьте архив уже доверенной копией проверяющего кода:
`python -I -B "<trusted-checker>/scripts/git_docs_package.py" verify --archive "<external>/git-docs.zip" --trusted-manifest "<external>/git-docs.zip.manifest.json" --expected-manifest-sha256 <independently-trusted-SHA256>`.
После PASS распакуйте в новый каталог, сохраняя структуру путей. Не перезаписывайте существующую установку. Манифест храните отдельно от пакета.
Проверка ZIP не удостоверяет собственный bootstrap: Python/stdlib, entry scripts, `scripts/git_docs_source_loader.py` и `src/harness/git_docs_delivery.py` должны быть доверенными заранее. Не запускайте непроверенную копию для подтверждения её же доверенности.
Runtime использует точные исходные байты, обходя затеняющие Python-пакеты и `.pyc`; обычный CLI и commit-hook сами по себе не закрепляют внешний манифест. Изменения распакованного дерева требуют повторной проверки.

Индекс: `python -I -B "<package>/scripts/git_docs_verify.py" --root "<target>" --mode index`.
Диапазон: `python -I -B "<package>/scripts/git_docs_verify.py" --root "<target>" --mode range --base <full-SHA> --head <full-SHA>`; код и документ могут быть в разных коммитах.
Результат — JSON v1: rc0 PASS, rc1 FAIL, rc2 UNKNOWN. Авторство `not_assessed`, качество текста требует ревью. Другой индекс задаётся явно: `--index-path "<absolute-path-inside-private-git-dir>"`.

Перед установкой сохраните байты и права активного `pre-commit`, его SHA256 и значение/источник `git config --show-origin --get core.hooksPath`; путь hook определите из целевого репозитория через `git rev-parse --git-path hooks/pre-commit`.
Шаблон `scripts/git_hooks/pre-commit.git-docs.example` рассчитан на расположение `<package>/scripts/git_hooks/pre-commit`. До копирования сравните разрешённые абсолютные пути: установочная копия и активный hook должны быть разными файлами; при совпадении выберите отдельный каталог распаковки. Не добавляйте вызов hook самого себя. Создайте установочную копию, предварительно сохранив существующий файл; Unix: `chmod +x "<package>/scripts/git_hooks/pre-commit"`.
В существующий активный `pre-commit` добавьте вызов этой абсолютной копии последним после обработчиков, меняющих индекс; ненулевой код передайте Git. Существующие обработчики и `core.hooksPath` сохраните.
Если активного hook нет, создайте только этот `pre-commit` с `#!/bin/sh` и строкой `exec "<package>/scripts/git_hooks/pre-commit"`; Unix: `chmod +x "<active-hooks>/pre-commit"`. Шаблон использует `PYTHON`, затем venv пакета, затем `python` из PATH.
Hook проверяет delta индекса относительно текущего HEAD; amend не доказывает корректность всего переписанного коммита. Включение hook в одном репозитории не подключает его в других.
CI запускается через `pull_request_target` только для PR в master: закреплённый checkout получает base SHA, права ограничены `contents: read`. Манифест описывает исходные файлы; объекты PR читаются как данные, код PR не исполняется. Другие целевые ветки не квалифицированы; проверка push/force-push остаётся открытой.

## P4. Явная проверка в Codex

Для ранней проверки до правок или проверки при ревью предусмотрен нативный навык
[git-docs-check](../.agents/skills/git-docs-check/SKILL.md). Пример запроса:
`$git-docs-check Проверь диапазон: package-root=<абсолютный путь принятого пакета>, root=<абсолютный путь репозитория>, base=<полный SHA>`.
Это явный вызов выбранной проверки; автоматическое выполнение на каждой задаче не заявлено.
Настройка навыка `allow_implicit_invocation: false` задаёт явное применение;
её распознавание целевым клиентом входит в отдельную приёмку.
Существующие UserPromptSubmit/Stop, включая прежние случаи UNKNOWN, этим дополнением не изменяются.

Прямой вызов адаптера:

```text
python -X utf8 -I -B "<adapter-repository>/scripts/git_docs_codex.py" --package-root "<accepted-package>" --root "<target>" --base <full-base-SHA> --format json
```

`--package-root` и `--root` обязательны и задаются абсолютными путями; `--base` обязателен
и содержит полный SHA из 40 или 64 шестнадцатеричных символов. Необязательный `--head`
принимает такой же SHA; без него адаптер один раз закрепляет фактический HEAD цели.
`--format human|json` выбирает вид вывода, по умолчанию `human`; `--timeout` по умолчанию 45 секунд.
Проверка охватывает весь объявленный диапазон зафиксированных изменений, без фильтра путей;
индекс и рабочее дерево она не оценивает.

Адаптер запускает принятый CLI только для чтения через `-I -B`, сохраняя смысл кодов
0 PASS, 1 FAIL, 2 UNKNOWN. Внешний результат добавляет контекст и ошибки адаптера,
сохраняя вложенный отчёт без изменений. PASS требует свежего проверенного контекста;
FAIL - подлинного связанного отчёта с нарушениями. Ошибки запуска, таймауты, недостающие
пути, неверная схема и несовпадение кода с отчётом дают UNKNOWN. Отсутствие запуска не даёт PASS.
Поля вложенного отчёта `author: not_assessed` и `adapter_status: not_used` остаются прежними;
принадлежность изменений исполнителю не устанавливается.

Вызывающий отвечает за доверенный Python/stdlib, начальный запускаемый код адаптера
и заранее принятую установку пакета. Нельзя выбирать проверяющий код из целевого
репозитория, выводить его путь из текущего каталога или подтверждать доверие запуском
непроверенной скачанной копии. Это граница конкретного вызова, а не гарантия безопасности всей файловой системы.
Новые адаптер и навык не объявляются частью ранее принятого ZIP из 22 файлов;
адаптер размещается с репозиторием либо отдельно, а принятый пакет задаётся явно.
Удаление этого навыка и адаптера не требует изменения прямой команды проверяющего CLI.

[Официальная инструкция Codex](https://learn.chatgpt.com/docs/build-skills) описывает
обнаружение `.agents/skills` и явный вызов через `$`. Общий каталог Claude Code и его
поисковый индекс здесь не изменяются, регистрации в них нет.

Живая приёмка 15.11.2026 в свежем Codex CLI 0.169 подтвердила явный вызов
`$git-docs-check`: инструкция прочитана целиком в UTF-8 с точным совпадением содержимого,
после чего адаптер дал FAIL (rc1) для изменения кода без документа и PASS (rc0)
для диапазона с соответствующим документом. Проверка выполнена на отдельном
Git-репозитории, принадлежащем учётной записи песочницы; в ходе проверки изменений
файлов не зафиксировано. В отдельном пустом проекте без навыка получен NOT_INVOKED,
без запуска команд и изменений файлов; это не PASS проверяющего кода.

в изолированном окружении без сети; это не подтверждает запуск CI на сервере.

дала UNKNOWN из-за проверки Git `dubious ownership`. Настройки `safe.directory`
при приёмке не менялись. Доступность произвольного пользовательского репозитория
из такой песочницы не подтверждена; отказ Git сохраняется как UNKNOWN.
Автоматический вызов и применение `allow_implicit_invocation: false` независимо
не доказаны. Версия серверной части текущего Desktop и фактическая модель исполнения
не установлены; результат CLI 0.169 на них не распространяется.
