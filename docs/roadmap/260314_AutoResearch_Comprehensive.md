# AutoResearch: комплексный подход к улучшению работы Claude Code

**Дата:** 2026-03-14
**Основа:** [AutoResearch для Python](260314_AutoResearch%20для%20Python%20от%20нуля%20до%20автономного%20цикла%20качества%20кода.md) — конкретный пример для одного направления
**Суть:** применение цикла "измерил → изменил → проверил → сохранил/откатил" ко ВСЕЙ работе Claude Code

---

## Концепция

Оригинальный AutoResearch (Karpathy → Goenka) оптимизирует одну числовую метрику Python-кода. Это узкий инструмент для узкой задачи.

**Комплексный AutoResearch** — это тот же принцип, но применённый к каждому аспекту работы:

```
Для КАЖДОГО направления работы:
  1. Определить измеримую метрику
  2. Замерить текущий уровень (baseline)
  3. Итерация: действие → замер → keep/revert
  4. Кэшировать результаты между сессиями
  5. Повторять до целевого уровня
```

Ключевое отличие от оригинала: не все метрики — числа. Некоторые — покрытие знаниями, некоторые — частота ошибок, некоторые — качественные оценки.

## 10 направлений

### Направление 1: Знание конфигурации 1С

**Проблема:** Claude не понимает архитектуру конфигурации — какие документы в какие регистры пишут, как работает проведение, какие бизнес-процессы реализованы. Каждую сессию "открывает" заново.

**Метрика:** процент изученных объектов конфигурации
- Документы изучены / всего документов (27)
- Регистры описаны / всего регистров (190+)
- Связи документ→регистр задокументированы
- Бизнес-процессы реконструированы

**Цикл итерации:**
```
1. REVIEW   — что уже в кэше? (cache/documents_map.md)
2. SELECT   — выбрать следующий неизученный объект
3. QUERY    — get_metadata() + find_references() + execute_query()
4. ANALYZE  — разобрать структуру, связи, модуль проведения
5. VERIFY   — проверить на реальных данных: "в регистре X есть движения от документа Y?"
6. CACHE    — записать в структурированный кэш
7. REPEAT   — следующий объект
```

**Инструменты MCP:**
- `get_metadata(type, name)` — структура объекта
- `find_references_to_object(object, scope)` — связанные объекты
- `execute_query(query)` — проверка на данных
- `bsl_object_info(module)` — код модуля объекта
- `bsl_call_graph(symbol)` — граф вызовов

**Кэш:**
```
.claude/skills/1c-config-knowledge/cache/
├── _index.json              # что изучено, когда, coverage %
├── config_overview.md       # общая структура, подсистемы
├── documents/
│   ├── ЗаказНаПеревозку.md  # реквизиты, ТЧ, проведение, движения
│   ├── ПутевойЛист.md
│   └── ...
├── registers/
│   ├── accumulation.md      # все регистры накопления
│   └── information.md       # все регистры сведений
├── document_register_map.md # ГЛАВНЫЙ ФАЙЛ: какой документ куда пишет
├── business_processes.md    # цепочки: заказ → рейс → ТТН → акт
└── posting_patterns.md      # паттерны проведения
```

**Уровни:**
| Уровень | Coverage | Значение |
|---------|----------|----------|
| 0 — Слепой | 0-10% | Знаю только что база существует |
| 1 — Турист | 10-30% | Знаю основные документы и регистры |
| 2 — Стажёр | 30-60% | Понимаю связи, могу предсказать движения |
| 3 — Разработчик | 60-85% | Понимаю бизнес-процессы |
| 4 — Эксперт | 85-100% | Предсказываю последствия изменений |

**Текущий уровень:** 0
**Цель:** 2-3

**Цель:** ruff 0, mypy 0

### Направление 3: Качество выполнения задач

**Проблема:** Claude часто выполняет задачу не так, как ожидает пользователь. Пользователь поправляет, уточняет, повторяет.

**Метрика:** количество коррекций на задачу
- Пользователь сказал "нет, не так" → correction +1
- Пользователь переформулировал запрос → misunderstanding +1
- Задача выполнена с первого раза → perfect +1

**Цикл итерации:**
```
1. REVIEW   — какие типы задач вызывают больше коррекций?
2. ANALYZE  — почему ошибся? (не понял контекст / не знал API / не прочитал файл)
3. PATTERN  — это повторяющаяся ошибка? (да → нужен guard)
4. FIX      — создать hook/skill/cache чтобы не повторять
5. VERIFY   — в следующих задачах этого типа ошибок меньше?
6. LOG      — записать паттерн ошибки и решение
```

**Кэш:** `data/task-quality-log.tsv`
```
date    task_type       corrections     root_cause              fix_applied
...     1c-document     3               не знал проведение      cache/posting_patterns.md
...     bsl-code        1               неверный синтаксис      bsl-platform-context lookup
...     feature-file    0               -                       -
```

**Текущий уровень:** не измерен (субъективно: 2-3 коррекции на среднюю задачу)
**Цель:** < 1 коррекция на задачу

### Направление 4: Понимание запросов пользователя

**Проблема:** пользователь говорит одно, Claude делает другое. Особенно с короткими и неявными запросами.

**Метрика:** процент верно интерпретированных запросов

**Паттерны ошибок:**
- Пользователь просит X, Claude делает X + Y + Z (over-engineering)
- Пользователь имеет в виду конкретное, Claude понимает общее
- Пользователь ссылается на предыдущий контекст, Claude теряет нить
- Пользователь фрустрирован — Claude не считывает это вовремя

**Цикл:**
```
1. REVIEW   — в каких случаях пользователь говорил "не то" / "не так"?
2. PATTERN  — есть ли паттерн? (короткие запросы, 1С контекст, неявные ссылки)
3. RULE     — сформулировать правило: "когда видишь X — спроси Y"
4. CACHE    — записать в user-preferences
5. VERIFY   — в следующей подобной ситуации правило сработало?
```

**Кэш:** `.claude/skills/user-preferences/cache/`
```
communication_patterns.md   # как пользователь формулирует запросы
common_misunderstandings.md  # типичные ошибки интерпретации
clarification_triggers.md    # когда ОБЯЗАТЕЛЬНО уточнить
```

**Текущий уровень:** ~70% (субъективно)
**Цель:** >90%

### Направление 5: Эффективность MCP-вызовов

**Проблема:** лишние вызовы MCP, неправильные параметры, таймауты. Особенно с `1c-mcp-toolkit` и `bsl-semantic-search`.

**Метрика:** полезных результатов / всего вызовов

**Паттерны ошибок:**
- Вызвал `get_metadata` без указания `name` — получил огромный ответ
- Вызвал `find_references_to_object` с неправильным `search_scope`
- Вызвал `execute_query` с синтаксической ошибкой в запросе
- Не знал что инструмент существует — делал вручную

**Цикл:**
```
1. REVIEW   — какие MCP-вызовы failed / timeout / бесполезны?
2. PATTERN  — повторяющиеся ошибки? (неверные параметры, scope)
3. CACHE    — записать правильный формат вызова с примером
4. VERIFY   — следующий аналогичный вызов прошёл с первого раза?
```

**Кэш:** уже частично есть в MEMORY.md (`API gotchas`). Расширить до полного справочника.

**Текущий уровень:** ~60% (много промахов с 1c-mcp-toolkit)
**Цель:** >90%

### Направление 6: Сохранение знаний между сессиями

**Проблема:** каждая новая сессия — почти с нуля. MEMORY.md помогает, но содержит разрозненные факты, а не структурированные знания.

**Метрика:** процент задач где знания из кэша реально использовались vs заново запрошены

**Цикл:**
```
1. REVIEW   — что я спрашивал/искал в этой сессии?
2. CHECK    — было ли это уже в кэше? (если да — почему не использовал?)
3. SAVE     — если нет в кэше — записать
4. ORGANIZE — если кэш неструктурирован — реорганизовать
5. VERIFY   — в следующей сессии загрузилось автоматически?
```

**Текущий уровень:** ~30% (MEMORY.md загружается, но специализированные кэши — нет)
**Цель:** >70%

### Направление 7: Качество BSL-кода

**Проблема:** когда Claude пишет BSL-код, часто ошибается в синтаксисе, не знает актуальные методы API, путает русские/английские названия.

**Метрика:** ошибок при проверке BSL-кода / строк написанного кода

**Цикл:**
```
1. WRITE    — написать BSL-код
2. ANALYZE  — bsl_analyze() → список ошибок
3. FIX      — исправить
4. PATTERN  — это повторяющаяся ошибка? (записать в кэш типичных ошибок)
5. PREVENT  — добавить проверку ДО написания (bsl-platform-context lookup)
```

**Кэш:** `bsl-development/cache/common_mistakes.md`
```
# Типичные ошибки при написании BSL
- НЕ "СправочникМенеджер.НайтиПоКоду" → правильно "Справочники.ИмяСправочника.НайтиПоКоду"
- НЕ "Запрос.Текст = ..." → правильно "Запрос = Новый Запрос; Запрос.Текст = ..."
- ...
```

**Текущий уровень:** не измерен
**Цель:** < 1 ошибка на 50 строк

### Направление 8: Качество архитектурных решений

**Проблема:** предложенные решения иногда не работают на практике. Нет обратной связи: решение принято → сработало?

**Метрика:** accepted ADR / total ADR, reverted decisions count

**Цикл:**
```
1. PROPOSE  — предложить решение (ADR format)
2. IMPLEMENT — реализовать
3. VERIFY   — через N сессий проверить: решение работает? Есть жалобы?
4. ADJUST   — скорректировать или supersede ADR
5. LEARN    — какие типы решений срабатывают чаще
```

**Текущий уровень:** не измерен
**Цель:** >80% accepted, <10% reverted

### Направление 10: Скорость работы

**Проблема:** слишком много итераций на задачу. Чтение лишних файлов, избыточные проверки, повторные попытки.

**Метрика:** tool calls per completed task, time per task

```
3. OPTIMIZE — убрать лишние шаги

```

**Текущий уровень:** не измерен
**Цель:** -30% tool calls для типовых задач

## Роль LLM в каждом направлении

В оригинальном AutoResearch **LLM — это агент**, который думает, действует и принимает решения. Не скрипт запускает ruff — LLM решает КАКУЮ категорию ошибок исправить, КАК исправить, и ОЦЕНИВАЕТ результат. Без LLM-reasoning цикл превращается в тупой скрипт.

### Таблица: что делает LLM vs что делает автоматика

| Направление | Автоматика (скрипт/MCP) | LLM (рассуждение) |
|---|---|---|
| **1. Конфигурация 1С** | `get_metadata()`, `find_references()`, `execute_query()` — сбор сырых данных | **Понять** зачем этот регистр, **связать** документ с бизнес-процессом, **сформулировать** объяснение "документ X создаётся когда клиент заказывает перевозку, при проведении резервирует ТС в регистре Y" |
| **2. Python quality** | `ruff check`, `mypy` — числовые метрики | **Выбрать** самую частую категорию ошибок, **придумать** способ исправления (не шаблонный), **оценить** не сломает ли runtime |
| **3. Качество задач** | Подсчёт коррекций в логе | **Проанализировать** ПОЧЕМУ пользователь поправил — не учёл контекст? не знал API? over-engineering? **Сформулировать** правило на будущее |
| **4. Понимание запросов** | Логирование "пользователь переформулировал" | **Распознать** паттерн коммуникации: "когда пользователь пишет коротко — он ожидает что я знаю контекст". **Выработать** стратегию уточнения |
| **5. MCP-эффективность** | Логирование failed/timeout вызовов | **Понять** почему вызов не сработал — неправильный параметр? не тот инструмент? **Запомнить** правильный формат |
| **6. Сохранение знаний** | Проверка "было ли в кэше?" | **Реорганизовать** кэш — объединить дублирующиеся записи, **структурировать** по доменам, **оценить** что устарело |
| **7. BSL-код** | `bsl_analyze()` — список ошибок | **Понять** почему ошибся — не знал метод API? перепутал синтаксис? **Обратиться** к `bsl-platform-context` ДО написания кода |
| **8. Архитектура** | Подсчёт accepted/reverted ADR | **Проанализировать** почему решение не сработало — неверные предпосылки? изменился контекст? **Скорректировать** подход |
| **9. Документация** | `audit-docs` — score покрытия | **Написать** документацию, **выбрать** что важнее задокументировать, **оценить** понятность |
| **10. Скорость** | Подсчёт tool calls | **Определить** какие вызовы были лишними — можно было взять из кэша? параллельно? **Оптимизировать** workflow |

### Ключевой принцип: LLM reasoning в каждой итерации

Без LLM цикл AutoResearch — это `while true: run script; check metric; if worse: revert`.
С LLM каждая итерация включает:

```
1. ANALYZE  — LLM читает текущее состояние и ПОНИМАЕТ что не так
2. HYPOTHESIZE — LLM формулирует гипотезу: "если исправить X, метрика улучшится потому что Y"
3. ACT      — LLM делает изменение (не по шаблону, а осмысленно)
4. EVALUATE — LLM оценивает результат: "метрика улучшилась, но Z стало хуже"
5. LEARN    — LLM формулирует вывод: "в будущем при похожей ситуации делать A, не B"
```

Это принципиально отличается от скрипта — LLM **учится** на каждой итерации, а не просто повторяет.

## Двойная LLM: Opus + локальная модель

### Архитектура

```
                    ┌──────────────────────────────────┐
                    │         Claude Opus (облако)       │
                    │  - Сложное рассуждение             │
                    │  - Архитектурные решения            │
                    │  - Анализ "почему ошибся"           │
                    │  - Написание нового кода            │
                    │  - $5-25/1M токенов                 │
                    └──────────┬───────────────────────────┘
                               │ делегирует рутину
                               ▼
┌──────────────────────────────────────────────────────────┐
│                Локальная LLM (Ollama)                     │
│  Модель: qwen2.5:7b / qwen3 / deepseek-coder-v2          │
│  - Классификация и маршрутизация                          │
│  - Извлечение фактов из MCP-ответов                       │
│  - Генерация описаний объектов по шаблону                  │
│  - Ответы на вопросы по КЭШУ (RAG)                        │
│  - Предварительный анализ перед Opus                       │
│  - $0 (локальная)                                         │
└──────────────────────────────────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────┐
│              Кэш знаний (файлы + векторы)                 │
│  .claude/skills/*/cache/   — структурированные MD          │
│  Qdrant: bsl_code_v2       — семантический поиск           │
│  SQLite: hybrid_search.db  — FTS5 полнотекстовый           │
└──────────────────────────────────────────────────────────┘
```

### Распределение задач

| Задача | Opus (облако) | Локальная LLM | Почему |
|--------|--------------|---------------|--------|
| **Изучение объекта 1С** | Формулирует вопросы, строит связи, пишет объяснение | Извлекает факты из JSON-ответа `get_metadata`, форматирует в MD | Opus дорогой для парсинга JSON |
| **Проверка BSL-кода** | Оценивает архитектуру, выбирает паттерн | Прогоняет через шаблон проверки, сравнивает с кэшем ошибок | Шаблонная работа |
| **Ответ на вопрос о конфигурации** | Если вопрос сложный (связи, бизнес-логика) | Если ответ есть в кэше — RAG по накопленным знаниям | 80% вопросов — из кэша |
| **Генерация документации** | Ревью и финальная правка | Черновик по шаблону из данных кэша | Z.AI delegation |
| **Классификация задачи** | Нет | Определить тип задачи, подобрать скилл | Быстро, не тратить Opus |
| **Анализ ошибки** | Почему ошибся, как предотвратить | Нет — тут нужно рассуждение | Только Opus |

### Как локальная LLM "учится параллельно"

Локальная модель не дообучается (fine-tuning). Она "учится" через **RAG над растущим кэшем**:

```
Сессия 1: Opus изучил ЗаказНаПеревозку → записал в cache/documents/
Сессия 2: Opus изучил ПутевойЛист → записал в cache/documents/
...
Сессия N: Пользователь спрашивает "какие регистры у ЗаказНаПеревозку?"
          → Локальная LLM ищет в кэше → находит → отвечает БЕЗ Opus
          → Opus экономит токены для сложных задач
```

**Три способа "обучения" локальной LLM:**

| Способ | Как работает | Сложность | Эффект |
|--------|-------------|-----------|--------|
| **RAG (сейчас)** | Кэш-файлы индексируются в Qdrant, локальная LLM ищет по ним | Низкая | Отвечает на вопросы по изученным объектам |
| **Few-shot prompting** | В промпт локальной LLM добавляются примеры из кэша | Низкая | Генерирует описания по шаблону |
| **Fine-tuning (будущее)** | Накопить 500+ пар вопрос-ответ → дообучить qwen2.5 на нашем домене | Высокая | Отвечает без RAG, быстрее, точнее |

### Конкретная реализация через LLM Rotation

У нас уже есть `mcp__llm-rotation__llm_complete`. Сейчас провайдеры: zai-glm5, gemini, ollama-local.

**Новый провайдер:** `ollama-1c-expert` — та же Ollama, но с системным промптом, содержащим накопленный кэш знаний о конфигурации:

```python
# В конфиге LLM Rotation добавить:
{
    "name": "ollama-1c-expert",
    "type": "ollama",
    "model": "qwen2.5:7b",
    "system_prompt_file": ".claude/skills/1c-config-knowledge/cache/system_prompt.md",
    "priority": 1,  # пробовать первым для 1С-вопросов
    "tags": ["1c", "config", "metadata"]
}
```

**system_prompt.md** — автоматически генерируется из кэша:
```markdown
Ты — эксперт по конфигурации УправлениеТранспортомНаПЛК v2026.1.1.0.

## Документы и их регистры:
- ЗаказНаПеревозку → РегистрНакопления.ЗаказыНаПеревозку (Приход), ...
- ПутевойЛист → РегистрНакопления.ВыработкаТС, ...
...

## Бизнес-процессы:
- Заказ перевозки: Заявка → ЗаказНаПеревозку → ПутевойЛист → ТТН → Акт
...
```

По мере изучения конфигурации через AutoResearch-цикл, этот системный промпт **растёт автоматически**.

### Цикл параллельного обучения

```
┌─────────────────────────────────────────────────────────┐
│  AutoResearch итерация (Opus)                            │
│                                                          │
│  1. Выбрать неизученный документ                         │
│  2. get_metadata() + find_references() → сырые данные    │
│  3. Opus: ПОНЯТЬ связи, СФОРМУЛИРОВАТЬ объяснение        │
│  4. Записать в cache/documents/ИмяДокумента.md           │
│  5. execute_query() → ПРОВЕРИТЬ на реальных данных       │
│  6. Обновить cache/document_register_map.md              │
│                                                          │
│  ──── ПАРАЛЛЕЛЬНО ────                                   │
│                                                          │
│  7. Пересобрать system_prompt.md из всего кэша           │
│  8. Локальная LLM теперь знает этот документ             │
│  9. Тест: llm_complete("Какие регистры у ДокументX?")    │
│     → Локальная ответила правильно? → coverage +1        │
│     → Ответила неправильно? → уточнить кэш              │
└─────────────────────────────────────────────────────────┘
```

### Экономика

| Сценарий | Только Opus | Opus + локальная |
|----------|------------|-----------------|
| 100 вопросов о конфигурации | ~$5-10 | ~$1-2 (80% отвечает локальная) |
| Изучение 27 документов | ~$15-20 | ~$15-20 (изучение = Opus) |

Локальная LLM не экономит на ОБУЧЕНИИ (это Opus), но экономит на ИСПОЛЬЗОВАНИИ накопленных знаний.

## Отличия от оригинального AutoResearch

| Аспект | Оригинал (Python lint) | Комплексный подход |
|--------|----------------------|-------------------|
| **Направлений** | 1 (ruff errors) | 10 |
| **Тип метрик** | Только число (errors count) | Числа + покрытие + качественные оценки |
| **Цикл** | fix → check → keep/revert | query → learn → verify → cache |
| **Откат** | git revert | Исправление кэша |
| **Персистентность** | Только TSV-лог | Структурированный кэш знаний |
| **Обратная связь** | Автоматическая (ruff) | Человек + автоматика |
| **Scope** | src/*.py | Вся работа Claude Code |
| **Время** | Бесконечный цикл за ночь | Постепенное накопление между сессиями |

## Связь с существующей инфраструктурой

Комплексный AutoResearch не заменяет, а усиливает то что уже есть:

| Существующее | Как усиливается AutoResearch |
|-------------|------------------------------|
| Ralph Wiggum (автономный цикл) | Новые templates: `1c-study`, `bsl-quality` |

| Task Protocol (протокол задач) | Добавляется замер качества выполнения |
| Code Review Enforcer (ревью) | Добавляется замер повторяющихся ошибок |
| Hooks (автоматизация) | Hook для записи task-quality-log |
