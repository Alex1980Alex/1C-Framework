## Цикл изучения одного объекта (6 фаз)

### Фаза 1: МЕТАДАННЫЕ (1c-mcp-toolkit, read-only)

```
get_metadata("Документ.ЗаказНаПеревозку")
  → реквизиты, табличные части, типы данных

find_references_to_object("Документ.ЗаказНаПеревозку")
  → какие регистры связаны, какие справочники используются

execute_query("ВЫБРАТЬ ПЕРВЫЕ 3 * ИЗ Документ.ЗаказНаПеревозку")
  → как выглядят реальные данные (образец)

get_access_rights("Документ.ЗаказНаПеревозку")
  → кто может создавать/проводить
```

### Фаза 2: ИСХОДНЫЙ КОД (EDT-MCP, read-only)

```
list_modules("Документ.ЗаказНаПеревозку")
  → МодульОбъекта, МодульМенеджера, МодульФормы

get_symbol_info("ОбработкаПроведения")
  → полный код процедуры проведения
  → какие запросы, какие регистры, какие условия

get_symbol_info("ПередЗаписью")
  → валидации перед записью (обязательные поля)

get_symbol_info("ОбработкаЗаполнения")
  → значения по умолчанию, ввод на основании

get_problems()
  → ошибки в коде модуля (если есть)
```

### Фаза 3: ГИПОТЕЗА (LLM reasoning)

На основе метаданных + кода Opus формулирует:
- Какие реквизиты обязательны (из кода ПередЗаписью)
- Какие движения создаёт проведение (из кода ОбработкаПроведения)
- Какие зависимости нужны (справочники, другие документы)
- Бизнес-смысл документа

### Фаза 4: ПРОВЕРКА НА РЕАЛЬНОЙ БАЗЕ (1c-mcp-toolkit, write)

```
// Подготовка зависимостей
execute_code → Найти существующие элементы справочников
  или создать тестовые с префиксом "ТЕСТ_AR_"

// Создание документа
execute_code → Создать документ, заполнить реквизиты

// Проведение
execute_code → Попытка провести
  ЕСЛИ ОШИБКА → записать текст ошибки, понять причину, исправить
  ЕСЛИ УСПЕХ → перейти к проверке движений

// Проверка движений
execute_query → "ВЫБРАТЬ * ИЗ РегистрНакопления.X ГДЕ Регистратор = &Ссылка"
  → Совпадает с гипотезой из Фазы 3?
  → ДА: знание подтверждено
  → НЕТ: обновить понимание
```

### Фаза 5: ГРАНИЧНЫЕ СЛУЧАИ

```
// Попробовать без обязательного поля
execute_code → Создать документ без Организации → какая ошибка?

// Попробовать отмену проведения
execute_code → Отменить проведение → движения удалились?

// Попробовать ввод на основании
execute_code → СоздатьНаОсновании(СсылкаНаДругойДок) → что заполнилось?
```

### Фаза 6: CLEANUP + ЗАПИСЬ В КЭШ

```
// Удалить тестовые данные
execute_code → Найти все объекты с префиксом "ТЕСТ_AR_"
  → Отменить проведение (если документы)
  → Пометить на удаление
  → Удалить непосредственно

// Записать в кэш
Write → cache/documents/ИмяДокумента.md
Edit  → cache/_index.json (обновить coverage)
Edit  → cache/document_register_map.md (добавить строку)
```

## Ralph Template: `1c-study`

**Файл:** `scripts/ralph.sh`, `scripts/ralph.bat`
**Команда:** `scripts\ralph.bat --template 1c-study --max-iterations 27`

### Алгоритм выбора темы (автоматический)

```
1. Прочитать cache/_index.json → список изученных объектов
2. Получить полный список: get_metadata(type="documents") → 27 документов
3. Найти первый НЕизученный документ
4. Если все документы изучены → перейти к регистрам
5. Если все регистры изучены → перейти к справочникам
6. Если всё изучено → RALPH_DONE
```

### Приоритет изучения

| Очередь | Тип объекта | Количество | Почему |
|---------|------------|-----------|--------|
| 1 | Документы | 27 | Ядро бизнес-логики: проведение, движения |
| 2 | Регистры накопления | ~30-50 | Связаны с документами, хранят остатки/обороты |
| 3 | Регистры сведений | ~140 | Настройки, статусы, периодические данные |
| 4 | Справочники (ключевые) | ~20-30 | Только те, что используются в документах |

### Критерии завершения итерации

- Файл `cache/documents/ИмяДокумента.md` создан
- `cache/_index.json` обновлён
- `cache/document_register_map.md` обновлён (если документ)
- Тестовые данные `ТЕСТ_AR_*` удалены из базы
- Нет ошибок в процессе

### Критерии завершения всего цикла (RALPH_DONE)

- Все 27 документов изучены и записаны в кэш
- `document_register_map.md` содержит полную карту
- `business_processes.md` содержит основные цепочки
- `system_prompt.md` сгенерирован из всего кэша
- Coverage >= 80% по eval-вопросам

## Безопасность

| Правило | Реализация |
|---------|-----------|
| Только тестовая база | 1c-mcp-toolkit подключён к `testdb1c_research` |
| Префикс тестовых данных | `ТЕСТ_AR_` для всех создаваемых объектов |
| Cleanup каждой итерации | Удаление всех `ТЕСТ_AR_*` в конце фазы 6 |
| Не трогать реальные данные | Только чтение существующих, создание только тестовых |
| Откат при ошибке | Если cleanup не сработал — логировать, не продолжать |

## Метрики

| Метрика | Как измерять | Цель |
|---------|------------|------|
| **Coverage** | Изученные объекты / Все объекты | >= 80% документов |
| **Accuracy** | Правильные ответы на eval / Все вопросы eval | >= 80% |
| **Errors caught** | Пойманные ошибки проведения | Информативно |
| **Cache size** | Количество файлов в cache/ | Информативно |

**Eval-датасет:** `data/eval/1c_config_eval.json` — 50+ вопросов о конфигурации.
