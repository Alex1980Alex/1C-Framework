# Что остаётся после ночной работы AutoResearch

Автономный цикл AutoResearch производит чёткий набор артефактов: файл-лог экспериментов в формате TSV, ветку Git с историей «победивших» коммитов, изменённый код модели и (опционально) отчёт-дискуссию на GitHub. За одну ночь система способна провести **~100 экспериментов**, из которых ~18–20% оказываются успешными. Реальный результат Karpathy — снижение val_bpb с **0.9979 до 0.9697** за 126 экспериментов (~10.5 часов на H100). Обобщённый skill uditgoenka работает с любой числовой метрикой, но на момент исследования не имеет подтверждённых публичных результатов.

## Пять ключевых артефактов оригинального Karpathy autoresearch

### 1. `results.tsv` — журнал всех экспериментов

Главный артефакт — **табулированный файл** (TSV, не CSV — «запятые ломаются в описаниях»). Содержит пять столбцов и растёт с каждой итерацией:

```tsv
commit	val_bpb	memory_gb	status	description
a1b2c3d	0.997900	44.0	keep	baseline
b2c3d4e	0.993200	44.2	keep	increase LR to 0.04
c3d4e5f	1.005000	44.0	discard	switch to GeLU activation
d4e5f6g	0.000000	0.0	crash	double model width (OOM)
```

Статус принимает три значения: **keep** (метрика улучшилась), **discard** (равна или хуже) и **crash** (OOM, баг, таймаут). Аварийные запуски записываются с `val_bpb=0.000000` и `memory_gb=0.0`. Файл **не коммитится** в Git — он остаётся рабочим документом агента и рекомендуется к добавлению в `.gitignore`.

### 2. `run.log` — вывод каждого 5-минутного запуска

При каждой итерации создаётся `run.log` командой `uv run train.py > run.log 2>&1`. Лог содержит пошаговый вывод обучения и финальный блок метрик:

```
step 0: loss=10.8234 lr=0.0000 norm=12.34 dt=145ms mfu=0.0%
step 1: loss=10.2341 lr=0.0001 norm=11.98 dt=312ms mfu=18.2%
...
step 953: loss=3.1234 lr=0.0000 norm=0.98 dt=314ms mfu=39.8%
---
val_bpb: 0.997900
training_seconds: 300.1
total_seconds: 325.9
peak_vram_mb: 45060.2
mfu_percent: 39.80
total_tokens_M: 499.6
num_steps: 953
num_params_M: 50.3
depth: 8
```

Агент извлекает ключевые числа через `grep "^val_bpb:\|^peak_vram_mb:" run.log`. Если grep возвращает пустоту — запуск считается crashed, и агент анализирует стек-трейс через `tail -n 50 run.log`.

### 3. Git-ветка с историей «победивших» изменений

Каждая сессия работает на выделенной ветке формата `autoresearch/<tag>` (например, `autoresearch/mar8` или `exp/H100/mar8`). Механика простая: перед запуском эксперимента агент **коммитит** изменение в `train.py`. Если val_bpb улучшился — коммит остаётся. Если нет — выполняется `git reset` к предыдущему лучшему состоянию. В итоге ветка содержит **чистую линию** только успешных улучшений, а полная история (включая неудачи) сохраняется в `results.tsv`.

Результаты публикуются как **Pull Request**, где diff показывает финальную лучшую конфигурацию, а история коммитов — последовательность шагов к ней.

### 4. `analysis.ipynb` и `progress.png` — визуализация прогресса

В репозитории есть Jupyter-ноутбук, который загружает `results.tsv` и строит график прогресса:

```python
df = pd.read_csv("results.tsv", sep="\t")
# Зелёные точки — kept, красные — discard, фронтир — running minimum
```

Заголовок графика: `"Autoresearch Progress: {n_total} Experiments, {n_kept} Kept Improvements"`. Фронтирная линия показывает монотонное снижение лучшего val_bpb. Результат сохраняется как `progress.png`.

### 5. Session report — автоматический отчёт в GitHub Discussions

Агент может автоматически генерировать отчёт и публиковать его через GraphQL API GitHub. Формат включает таблицу всех экспериментов с дельтами, список ключевых находок и финальную конфигурацию. Это ближайший аналог «итогового отчёта» — по сути, лабораторный журнал сессии.

## Конкретные числа из реальных запусков Karpathy

### Сессия Discussion #32 — первый ночной прогон

**89 экспериментов** на NVIDIA H100 80GB за ~7.5 часов. Результат: val_bpb снизился с **0.9979 до 0.9773** (улучшение на 0.0207). Ключевые находки: уменьшение batch size вдвое (больше шагов за 5 минут), увеличение глубины до 9, настройка sliding window, повышение RoPE base frequency до 200K.

### Сессия Discussion #43 — 126 экспериментов, 10.5 часов

Самая подробно задокументированная сессия. Статистика итераций: **23 keep, 102 discard, 1 crash**. Итог: val_bpb с **0.9979 до 0.9697** (улучшение 0.0282). Семь крупнейших улучшений:

| Дельта val_bpb | Что сделал агент |
|---|---|
| **−0.0119** | Уменьшил batch 524K→262K (больше шагов за 5 мин) |
| −0.0043 | Depth 9 + aspect_ratio 57 (доп. слой, dim ~512) |
| −0.0033 | Embedding LR 0.6→0.8 |
| −0.0012 | RoPE base frequency 10K→200K |
| −0.0010 | Unembedding LR 0.004→0.006 |
| −0.0010 | Tiny VE weight decay 0.001 |
| −0.0009 | Short window 1/8 контекста (256 токенов) |

Лучшая находка сессии — **weight decay на эмбеддингах** (0.001 для embeddings, до 0.003 для value embeddings): суммарно ~0.0028 улучшения. Но WD 0.005 уже ухудшал метрику. Агент также нашёл оптимальный init scale **0.68x** — через последовательное тестирование 0.8→0.7→0.68 (0.66 и 0.65 уже регрессировали).

Тупиковые направления, обнаруженные агентом: **weight tying** (shared embed/unembed) — катастрофа на +2.24 BPB; parallel attn+MLP — +0.011; MQA с n_kv_head=1 — +0.008. Эти «антирезультаты» сами по себе ценны — человеку потребовались бы дни на те же эксперименты.

### Масштабный прогон — ~700 экспериментов за 2 дня

Karpathy запустил цикл на модели глубиной 12 для проекта nanochat. Из **~700 изменений** выжили **~20 улучшений**, которые стекировались и перенеслись на модель глубиной 24. Итог: время обучения до уровня GPT-2 снизилось с **2.02 до 1.80 часов** — ускорение на **11%**. Агент обнаружил забытый scaler multiplier в QKNorm, отсутствие регуляризации Value Embeddings, слишком консервативное окно banded attention и субоптимальные бету/WD в AdamW.

Karpathy написал: *«This is a first for me because I am very used to doing the iterative optimization of neural network training manually... Seeing the agent do this entire workflow end-to-end is wild.»*

### Сторонние результаты

**Tobi Lütke (CEO Shopify)** адаптировал паттерн для query-expansion модели QMD: **37 экспериментов за 8 часов** — модель 0.8B стала на **19% лучше** предыдущей 1.6B. **Hyperspace AI** запустил 35 агентов одновременно: **333 эксперимента** полностью автономно; когда один агент обнаружил, что Kaiming init снижает loss на 21%, находка распространилась через GossipSub-протокол и 23 других агента подхватили её за часы.

## Обобщённый skill uditgoenka/autoresearch для Claude Code

### Архитектурное отличие от оригинала

Ключевое различие: Karpathy создал **исполняемую инфраструктуру** (Python-код для обучения моделей), а uditgoenka — **чисто промпт-инженерный skill** (набор markdown-файлов, управляющих поведением Claude Code). В репозитории нет исполняемого кода — только четыре файла в `skills/autoresearch/`: `SKILL.md`, `autonomous-loop-protocol.md`, `core-principles.md` и `results-logging.md`.

### Артефакт: `autoresearch-results.tsv` — расширенный формат

Шесть столбцов вместо пяти — добавлены номер итерации и дельта:

```tsv
iteration	commit	metric	delta	status	description
0	a1b2c3d	85.2	0.0	baseline	initial state — test coverage 85.2%
1	b2c3d4e	87.1	+1.9	keep	add tests for auth middleware edge cases
2	-	86.5	-0.6	discard	refactor test helpers (broke 2 tests)
3	-	0.0	0.0	crash	add integration tests (DB connection failed)
4	c3d4e5f	88.3	+1.2	keep	add tests for error handling in API routes
5	d4e5f6g	89.0	+0.7	keep	add boundary value tests for validators
```

Для «crashed» и «discard» записей вместо хеша коммита стоит прочерк (`-`), поскольку коммит ревёртится. Файл, как и у Karpathy, **не коммитится в git**.

### Встроенный progress report каждые 10 итераций

В отличие от оригинала, skill печатает inline-сводку в терминал:

```
=== Autoresearch Progress (iteration 20) ===
Baseline: 85.2% → Current best: 92.1% (+6.9%)
Keeps: 8 | Discards: 10 | Crashes: 2
Last 5: keep, discard, discard, keep, keep
```

Отдельного файла-отчёта система **не генерирует** — TSV-лог и git-история являются исчерпывающей документацией.

### Метрики для любого домена

Система работает с **любой числовой метрикой**, извлекаемой shell-командой. Примеры из документации:

- **Test coverage**: `npm test -- --coverage | grep "All files"` (higher is better)
- **Bundle size**: `npm run build 2>&1 | grep "First Load JS"` (lower is better)
- **TypeScript `any` count**: `grep -r ":\s*any" src/ --include="*.ts" | wc -l` (lower)
- **Docker image size**: `docker build -t bench . && docker images bench --format "{{.Size}}"` (lower)
- **Lighthouse score**: `node scripts/lighthouse-score.js` (higher)
- **API p95 latency**: `npm run bench:api | grep "p95"` (lower)

При цикле верификации ~10 секунд теоретическая пропускная способность достигает **~360 экспериментов в час** — на порядок больше, чем у оригинала с его 5-минутными тренировками.

### Что видит разработчик утром

Если skill запущен на ночь с целью повышения test coverage:

- **`autoresearch-results.tsv`** — полный лог, например, 200+ итераций с финальной строкой типа `iteration 214, metric 93.7, status keep`
- **`git log --oneline`** — чистая серия коммитов только с успешными изменениями, каждый с описательным сообщением
- **Терминал** (если сессия ещё активна) — последний progress report вида «Baseline: 72.3% → Current best: 93.7%»
- **Улучшенный код** — все файлы в scope содержат стекированные улучшения, а неудачные попытки автоматически ревёртнуты

**Важная оговорка**: репозиторий uditgoenka выпущен **13 марта 2026** (за день до этого исследования), имеет 6 звёзд и 4 коммита. Все примеры в README — **иллюстративные**, а не из реальных прогонов. Подтверждённых публичных результатов пока нет. Реальные доказательства работоспособности паттерна идут от Karpathy (700 экспериментов, 11% ускорение) и Tobi Lütke (37 экспериментов, 19% улучшение).

## 8-фазный цикл и механика обработки ошибок

Каждая итерация у обоих систем проходит строгий протокол: **Review → Ideate → Modify → Commit → Verify → Decide → Log → Repeat**. Коммит происходит **до** верификации — это обеспечивает чистый rollback через `git reset`. Решение принимается механически: метрика улучшилась → keep, ухудшилась → revert, аварийный выход → попытка починки (до 3 раз), затем revert.

У uditgoenka добавлена **stuck detection**: после 5+ последовательных discard агент перечитывает все файлы и переключается на радикально другие подходы. Оригинал Karpathy полагается на инструкции в `program.md`, где прописаны подсказки типа «simpler is better» и «0.001 improvement from deleting code? Definitely keep.»

## Заключение: паттерн работает, но с нюансами

AutoResearch — не чёрный ящик, а **полностью прозрачная система** с детерминированными артефактами. Главные выводы, которые не повторяют изложенное выше:

**Соотношение сигнал/шум стабильно низкое.** Из 126 экспериментов Discussion #43 только 23 (~18%) дали улучшение — остальные 82% были осознанными неудачами. Это не баг, а фича: система исследует пространство решений шире, чем человек.

**«Антирезультаты» — скрытая ценность.** Обнаружение того, что weight tying катастрофически вредит (+2.24 BPB) или что parallel attn+MLP не работает, экономит недели ручных экспериментов.

**Стоимость вопроса.** По оценкам сообщества, ночной прогон обходится в **$50–200** за API-токены LLM. Для корпоративных задач (Shopify) — тривиальная сумма за 19% улучшение модели.

**Валидация под вопросом.** На GitHub поднимался обоснованный вопрос об overfitting на validation set после сотен экспериментов. Karpathy парировал, что оптимизируется «performance per compute», но проблема остаётся открытой для длительных прогонов.

**Академическое расширение AutoResearch-RL** (arXiv 2603.07300) формализовало цикл как задачу RL с PPO, добавив self-evaluation модуль, который досрочно прекращает **54.3% экспериментов**, увеличивая пропускную способность в 1.35× и sample efficiency в 2.4×.
