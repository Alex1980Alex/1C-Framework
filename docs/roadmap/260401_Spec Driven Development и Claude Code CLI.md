1. Постановка проблемы: почему вайб-кодинг не работает в 1С
Три метода работы с нейросетями для кода (из видео)
Автор выделяет три уровня зрелости работы с AI для программирования:

Промтинг — искусство правильно формулировать запросы. Полезно, но ограничено.
Банк памяти (Memory Bank) — файлы с описанием проекта, которые нейросеть загружает в начале каждой сессии. Даёт долговременный контекст.
Spec Driven Development (SDD) — разработка через спецификации. Самый мощный подход, который автор считает переломным.

Фундаментальные проблемы вайб-кодинга
Контекстное окно — главное техническое ограничение. На маленькой задаче (одна обработка) всё работает, но на проекте из 20–30 итераций с десятками файлов нейросеть теряет нить рассуждений. Агенты в Cursor пытаются компенсировать это, сканируя файлы конфигурации, но это сжигает токены (реальные деньги) и работает непроизводительно.
Код как конечный продукт, а не отправная точка. На большом проекте нейросеть генерирует 5 000+ строк кода в разных модулях (модуль формы, модуль объекта, общий модуль, модуль менеджера). Архитектурная ошибка в таком объёме — задача на день поиска и ещё день исправления. Спецификацию подправить — 3 минуты.
Пример из практики (из видео). Разработчик на внедрении конфигурации с 1 000 объектов метаданных дал нейросети задачу доработать механизм резервирования товаров. Нейросеть работала 2 часа, сгенерировала 3 000 строк в семи модулях — и создала собственную систему резервирования с нуля (новый регистр, новый документ, новую подсистему), хотя в конфигурации уже был встроенный типовой механизм. После написания спецификации из трёх абзацев (контекст, что доработать, ограничения) нейросеть за 10 минут выдала точную доработку.
Подтверждение из исследований

По данным GitClear (2020–2024), дублирование AI-генерированного кода выросло в ~4 раза, а доля рефакторинга упала с 25% до менее 10%.
Рандомизированное исследование METR (июль 2025) показало, что разработчики тратят на отладку AI-кода больше времени, а не меньше.
Сам Андрей Карпати (автор термина «vibe coding», февраль 2025) через год, в феврале 2026, назвал вайб-кодинг «passé» и признал, что его проект Nanochat был написан вручную.


2. SDD: суть методологии
Принцип
Ты не пишешь код. Твоя задача — написать документ-спецификацию настолько точную, чтобы нейросеть сама написала весь код от первой до последней строки. Спецификация описывает: что хочешь получить, зачем, какие ограничения, какие данные на входе, какой результат на выходе. Формат — Markdown.
Пять принципов SDD для 1С (из видео)

Spec first — сначала спецификация, потом код. Документы: proposal → specs → design → tasks.
Конкретность — чем конкретнее спецификация, тем точнее результат. Тип данных каждого реквизита, поведение при пустых полях, граничные условия.
Контекст — нейросеть должна видеть структуру конфигурации: какие объекты, реквизиты, регистры существуют. Решается через выгрузку конфигурации в файлы и MCP-серверы.
Правь спецификацию, а не код — код расходный материал, спецификация единственный источник правды.
Инкрементальность — одна задача, одна спецификация, один результат. От простого к сложному.

Три уровня SDD (Martin Fowler / Thoughtworks)

Spec-first — спецификация пишется первой, но код остаётся основным артефактом.
Spec-anchored — спецификация живёт рядом с кодом как якорь.
Spec-as-source — спецификация единственный источник истины, код одноразовый побочный продукт (подход Tessl).


3. OpenSpec: архитектура и команды
Общие сведения

Репозиторий: github.com/Fission-AI/OpenSpec
Звёзды GitHub: ~28 000 (быстро растёт)
Лицензия: MIT, бесплатен
Язык: TypeScript, устанавливается через npm
Требования: Node.js 20.19.0+
Последняя версия: v1.2.0 (февраль 2026)
Поддерживает: 20+ AI-инструментов, включая Claude Code и Cursor

Ключевое отличие — brownfield-first
OpenSpec спроектирован для существующих кодовых баз (brownfield), а не для новых проектов. Использует дельта-подход: текущее состояние системы — в specs/, предлагаемые изменения — в changes/. Каждое изменение описывает только добавленное, изменённое или удалённое — не переписывает всю спецификацию. Это критически важно для 1С, где большинство задач — доработка типовых конфигураций.
Четыре ступени (артефакта) изменения
Ступень 1 — Proposal (Предложение). Описание задачи по-человечески: зачем, какую проблему решаем, что хотим получить. Пример: «Добавить табличную часть "Прошлые места работы" в справочник "Сотрудники". Реквизиты: Организация, ДатаНачала, ДатаОкончания, Должность. Вывести на форму. Проверить что ДатаОкончания > ДатаНачала.»
Ступень 2 — Specs (Спецификации). Инженерная конкретика: типы данных (Дата vs ДатаВремя), ограничения (ДатаОкончания строго > ДатаНачала), поведение при пустых полях. Формат — Given/When/Then для сценариев, ключевые слова RFC 2119 (MUST/SHALL/SHOULD/MAY).
Ступень 3 — Design (Архитектура). Какие конкретно файлы будут затронуты. Пример: «Будет изменён файл Сотрудник.xml — добавлена табличная часть». Здесь ловятся ошибки, которые при вайб-кодинге обнаружились бы через неделю.
Ступень 4 — Tasks (Задачи). Чек-лист атомарных шагов с галочками: «Изменить файл → добавить узел табличной части → добавить 4 реквизита → провести проверку XML».

4. Интеграция с Claude Code CLI — детальный разбор
Как OpenSpec подключается к Claude Code
При инициализации OpenSpec автоматически определяет установленные инструменты (по наличию .claude/, .cursor/ и других директорий) и генерирует соответствующие конфигурации.
bash# Установка OpenSpec
npm install -g @fission-ai/openspec

# Инициализация для Claude Code + Cursor
openspec init --tools claude,cursor

# Только для Claude Code
openspec init --tools claude

# Для всех поддерживаемых инструментов
openspec init --tools all
После инициализации для Claude Code создаются:
.claude/

    ├── opsx-propose/
    │   └── SKILL.md
    ├── opsx-apply/
    │   └── SKILL.md
    ├── opsx-explore/
    │   └── SKILL.md
    └── opsx-archive/
        └── SKILL.md
Механизм интеграции через Skills
Claude Code (начиная с v2.0+) использует систему Skills — markdown-файлы с YAML-frontmatter, которые определяют slash-команды. OpenSpec генерирует навыки, которые Claude Code распознаёт как команды /opsx:propose, /opsx:apply и т.д.
Каждый SKILL.md содержит:

Frontmatter (name, description) — для автоматического распознавания
Инструкции — детальный промпт, который Claude следует при вызове команды
$ARGUMENTS — параметры, переданные пользователем после команды

Ключевая конфигурация: CLAUDE.md
Файл CLAUDE.md в корне проекта — «мировоззрение» Claude для данного проекта. Для SDD-workflow рекомендуется добавить:
markdown## Правила проекта
- Мы следуем Spec-Driven Development (OpenSpec)
- Спецификация — единственный источник правды
- Перед любым изменением кода — обновить спецификацию
- Не создавать новых объектов метаданных без явного указания в specs
- Использовать существующие регистры и справочники конфигурации
- Язык кода: русский (1С:Предприятие BSL)
- Формат файлов конфигурации: XML (выгрузка из Конфигуратора)
Рабочий цикл Claude Code + OpenSpec
1. claude                          # Запускаем Claude Code CLI
2. /opsx:explore                   # Исследуем конфигурацию
   → Claude сканирует файлы, анализирует структуру
3. /opsx:propose add-print-form    # Создаём изменение
   → Генерируются proposal.md, specs/, design.md, tasks.md
4. [Проверяем и корректируем артефакты]
5. /opsx:apply                     # AI реализует задачи по чек-листу
   → Claude вносит изменения в файлы конфигурации
6. /opsx:verify                    # Проверяем соответствие спецификации
7. /opsx:archive                   # Архивируем, чистим контекст

7. Ключевые выводы

SDD — не бюрократия, а инженерия. Спецификация сжимает контекст, задаёт границы, создаёт проверяемый контракт между разработчиком и AI. Для 1С это особенно критично из-за сложности типовых конфигураций.
OpenSpec — оптимальный выбор для 1С. Его brownfield-подход (дельта-спеки) идеально ложится на задачу доработки существующих конфигураций. Brownfield — это 90% реальной работы 1С-разработчика.
Claude Code CLI > Cursor для SDD-workflow. Полный контроль контекста через CLAUDE.md, нативные skills и hooks, субагенты, мгновенная компактизация. Claude Opus 4.6 с thinking mode обеспечивает лучшее качество рассуждений для сложных архитектурных решений.
Кроссплатформенность артефактов — страховка. Спецификации в Markdown не привязаны к конкретному AI. Можно начать в Claude Code, продолжить в Cursor, передать коллеге с Copilot.
MCP-серверы — необходимое дополнение. Без контекста конфигурации (метаданные, синтаксис BSL, структура регистров) AI генерирует неработающий код. MCP-серверы для 1С решают эту проблему.
Роль разработчика меняется. Из кодера — в архитектора требований. 15 минут на спецификацию → рабочий код, который не стыдно показать коллегам. Нейросеть — не волшебная палочка, а послушный исполнитель по чётким чертежам.

Анализ ведущих репозиториев показывает консолидацию паттернов взаимодействия между IDE, AI-агентами и системами контроля версий. #### Детализация по фреймворкам

**1. OpenSpec (Fission-AI)**
Текущий лидер экосистемы. Реализует концепцию "Delta-specs" (ориентация на изменение существующего кода — brownfield-first, а не разработку с нуля). Жизненный цикл задачи разбит на 4 строгих артефакта: `proposal` → `specs` → `design` → `tasks`.
Для интеграции с Claude Code использует механизм skills в директории `.claude/`. Внедрен концептуальный стандарт `AGENTS.md` — файл, выступающий в роли "README для роботов", содержащий машинно-читаемые инструкции по работе с репозиторием. Конфигурация вынесена в `config.yaml`. Поставляется с выделенным MCP-сервером `openspec-mcp` (v0.4.2), предоставляющим веб-дашборд, Kanban-доску, approval workflow и двустороннюю связь через WebSocket.

**2. cc-sdd (gotalab)**
Фреймворк, вдохновленный подходом Amazon Kiro. Специализируется на глубокой интеграции с Claude Code CLI через 12 пользовательских команд и 9 специализированных субагентов. Главная сильная сторона — встроенный **Brownfield Validation Suite**, проверяющий дрифт спецификаций на трех уровнях (gap, design, impl). Поддерживает 8 AI-инструментов и 13 языков программирования.

**3. spec-workflow-mcp (Pimzino)**
Полностью MCP-native решение. Включает в себя не только CLI-инструментарий, но и полноценный веб-дашборд в связке с расширением для VSCode. Ориентирован на строгий цикл: Steering → Specs → Implementation → Verification. Имеет встроенную систему утверждения спецификаций (approval workflow) с поддержкой исторических ревизий.

**4. GSD (Get Stuff Done)**
Популярный фреймворк (около 23 000 stars), базирующийся на концепции Meta-prompting. Обеспечивает чистое разделение контекста (clean context phases: plan → execute → review). Состоит из 29 навыков (skills), 12 субагентов и 2 хуков (hooks) для перехвата операций.

### 8.2 Пять ключевых паттернов SDD

Анализ экосистемы позволил выделить 5 фундаментальных архитектурных паттернов, которые стали стандартом де-факто для SDD-инструментов:

1. **Artifact-guided workflow (Управление на основе артефактов)**
   Спецификации больше не являются простым текстовым чеклистом. Они представляют собой конечный автомат (state machine). Переход между фазами (например, от проектирования к задачам) возможен только при заполнении обязательных слотов данных в текущем артефакте.
2. **Delta-specs (Дельта-спецификации)**
   Смещение парадигмы с greenfield на brownfield-first. Спецификации содержат маркеры `ADDED` и `MODIFIED`. При завершении работы (фаза archive) дельта-спецификации мержатся в общую базу знаний проекта, поддерживая её в актуальном состоянии без полного переписывания.
3. **AGENTS.md (Разделение контекста)**
   Выделение инструкций для AI-агентов в отдельный файл `AGENTS.md`. Это решает проблему загрязнения человеческой документации (README.md) техническими промптами, лимитами токенов и машинно-читаемыми структурами.
4. **Approval workflow (Процесс утверждения)**
   Внедрение жестких гейтов (gate) перед генерацией кода. Жизненный цикл: `draft` → `pending` → `approved` → `implementing` → `completed` → `archived`. Технически реализуется преимущественно через MCP-серверы, блокирующие запуск команд генерации кода без статуса `approved`.
5. **Brownfield Validation Suite (Валидация существующего кода)**
   Трехуровневая система проверки дрифта между спецификацией и реальным кодом:
   * *Gap validation*: проверка полноты покрытия.
   * *Design validation*: соответствие архитектурным правилам.
   * *Impl validation*: проверка фактической реализации на уровне кода.

### 8.3 Сравнение с 1С-Framework (текущий ландшафт)

Сопоставление выявленных паттернов с текущими практиками 1С-разработки с использованием Claude Code показывает зоны роста.

| Паттерн SDD | Реализация в 1С-Framework | Вывод / Зона роста |
| :--- | :--- | :--- |
| **Artifact-guided workflow** | `analyze-1c-task-v2` (5 фаз) | Аналог существует, но спеки одноразовые. Необходимо внедрение state machine. |
| **AGENTS.md** | `CLAUDE.md` | Совмещает роли README для разработчика и инструкций для AI. **Требуется разделение.** |
| **Brownfield Validation** | `code-verify` | Работает post-factum. Отсутствует pre-impl validation (проверка до написания кода). |
| **Approval workflow** | Отсутствует | AI переходит к написанию кода сразу после генерации плана. Нет approval gate. |
| **MCP-серверы** | `1c-mcp-crud`, `bsl-semantic-search`, `METR` | Мощная база уже существует, готова к интеграции с SDD-фреймворками. |

Текущий процесс в 1С опирается на `analyze-1c-task-v2`, который успешно декомпозирует задачи, однако результат является одноразовым, если человек не контролирует каждый шаг. Файл `CLAUDE.md` перегружен — AI вынужден парсить человеческую документацию вперемешку со своими системными промптами. Инструмент `code-verify` реагирует на ошибки постфактум, в то время как экосистема SDD уже перешла к превентивной валидации архитектуры (pre-impl validation). При этом наличие зрелых 1С-специфичных MCP-серверов (`1c-mcp-crud` и др.) обеспечивает готовую инфраструктуру для внедрения паттернов SDD.

### 8.4 Рекомендации по интеграции OpenSpec в 1С-workflow

На основе анализа, наилучшим кандидатом для адаптации в 1С-разработке является фреймворк **OpenSpec** благодаря поддержке delta-specs (идеально для типовых конфигураций 1С) и тесной интеграции с Claude Code.

**Предлагаемый план интеграции:**

1. **Разделение контекста (AGENTS.md)**
   Вынести машинно-читаемые инструкции по работе с метаданными 1С, синтаксисом BSL и правилами платформы из `CLAUDE.md` в `AGENTS.md`. Оставить в `CLAUDE.md` только описание бизнес-логики проекта для человека.

2. **Адаптация 4 артефактов под 1С**
   Модифицировать пайплайн `proposal→specs→design→tasks` под реалии 1С:
   * *Proposal*: Описание бизнес-процесса.
   * *Specs*: Карта метаданных (документы, регистры, справочники).
   * *Design*: Архитектура модулей и взаимодействий (включая подписки на события и расширения).
   * *Tasks*: Конкретные шаги для Claude Code (создать объект, написать код модуля).

3. **Внедрение Approval Gate**
   Использовать `openspec-mcp` для добавления обязательного шага утверждения спеки (статус `approved`) перед тем, как Claude Code получит доступ к командам изменения конфигурации через `1c-mcp-crud`.

4. **Переход к Delta-specs**
   Внедрить маркеры `ADDED`/`MODIFIED` для работы с расширениями конфигурации. Это позволит AI корректно понимать, что он модифицирует существующий объект типовой конфигурации (brownfield), а не создает новый с нуля, что критично для обновлений 1С.

5. **Модернизация code-verify**
   Дополнить существующий `code-verify` функционалом `Brownfield Validation Suite` из cc-sdd. Добавить проверку дрифта между утвержденной спецификацией дизайна и генерируемым кодом до фактической выгрузки конфигурации.

### 9.9. Когда НЕ использовать SDD

Полный цикл SDD нецелесообразен для тривиальных задач:

- Косметические исправления UI (видимость, группировки)
- Исправление мелких багов (опечатки, замена знака `>` на `>=`)
- Рефакторинг формата кода (пробелы, переносы)
- Простые отчеты на СКД или обработки загрузки/выгрузки
- Обновление комментариев и документации

**Правило:** Если задача не требует создания новых объектов метаданных или изменения существующей бизнес-логики — SDD-конвейер можно безопасно обойти.
