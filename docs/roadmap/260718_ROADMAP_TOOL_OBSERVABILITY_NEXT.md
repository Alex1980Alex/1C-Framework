## §2 Найденные дефекты (NB — new bugs, по живым данным)

### NB1 🔴 CRITICAL — error-детект built-in мёртв на живом payload → success_rate=1.0 везде

**Эмпирически доказано зондом 2026-07-18:** Bash-команда `exit 42` → canonical строка
`outcome=allow success=True error_type=''`. На всём окне: **164/164 Bash Post = success**, включая
реальные фейлы (jq exit 127, UnicodeEncodeError). Все 1526 built-in вызовов — 0 ошибок; все server
rollups — error_rate 0.0.

- Код `_classify_outcome` ([tool-invocation-logger.py:127-165](../../.claude/hooks/tool-invocation-logger.py))
  ждёт `exit_code`/`exitCode` int в dict `tool_response` — живой payload Claude Code этой формы
  **не несёт** (юнит-тест кормит фикстуру нужной формы → зелёный, live — мимо).
- **Каскад:** error_rate≡0 → вердикты `broken` (success-rate<50%) и `ineffective` (abandonment
  error-based) **недостижимы в принципе** → авто-эскалация broken никогда не сработает →
  decision layer слеп к реальным отказам. Держится только `degraded` по латентности (см. NB2 — и тот FP).
- Урок класса [[feedback-deterministic-test-robustness]]: форма hook-payload — контракт ПЛАТФОРМЫ,
  юнит-фикстура его не пинит; нужен live-контракт-тест.

### NB2 🟠 HIGH — degraded по p95×2-baseline = FP-фабрика на content-variable инструментах

Живой прогон: **все 6 degraded** — чисто латентностные при success_rate=1.0:
`Bash p95 65901ms > 2× baseline 1236ms`, `Grep 3996 vs 230`, `Read 408 vs 189`, `Skill`, `TaskUpdate`,
`execute_code 4956 vs 1876`. Длительность Bash/Grep/Read/execute_code определяется СОДЕРЖИМЫМ вызова
(pytest-прогон ≠ echo), а не здоровьем инструмента — baseline, пойманный на «лёгком» окне, красит
любое рабочее окно в degraded. Баннер кричит волк → alert fatigue, реальный сигнал утонет.

### NB3 🟠 HIGH — «окно 14 дней» фактически ~1 день: ротация съедает данные, аналайзер архив не читает

Живой лог `hook-invocations.jsonl` начинается `2026-07-17T17:28` (~12ч истории на момент аудита);
скорость записи ~8МБ/день при cap ротации 10МБ; `hook-invocations.1.jsonl` (10.4МБ) аналайзером
**не читается**. `window_incomplete=True` честно проставлен, но вердикты (особенно **unused=18**,
вкл. WebSearch) посчитаны на сутках данных → unused-вердикты в основном FP, TTL-prune и будущий
месячный отчёт «кандидаты на отключение» дадут мусор.

### N-P4 — слепая зона app-level ошибок MCP (найдено 2026-07-25 при разборе 2 broken)

Класс NB1, но с другой стороны: у части MCP-серверов ошибка приходит **успешным ответом с текстом**,
а не протокольной ошибкой — тогда пара Pre→Post полная, `success=True`, и провал **не виден метрикам вообще**.
Доказано экспериментом (по одному заведомо ошибочному вызову на сервер + сверка `tool_call_id`):
`edt-mcp` → протокольная ошибка → непарный Pre (виден); `1c-mcp-crud` → `«Ошибка выполнения инструмента …»`
+ стек BSL в теле успешного ответа → PAIRED (невидим). Следствие: error-rate всего семейства
`1c-mcp-crud-*` структурно ≡ 0, вердикты `broken/degraded` для него достижимы только через транспортные сбои.

- **N-P4.1 Детект app-level ошибки в теле ответа.** *~2-3ч.* Post-payload содержит текст ответа →
  сигнатуры (`Ошибка выполнения инструмента`, `ВызватьИсключение`, `{МодульМенеджера(`) → `outcome=error`
  для `mcp_call`. Осторожно: сигнатуры серверо-специфичны, нужен allow-list per-server + тест на FP
  (легитимный ответ, обсуждающий ошибку, не должен краснить). Acceptance: синтетический ошибочный вызов
  `1c-mcp-crud` → `outcome=error` в логе; успешный — без изменений.
- **N-P4.2 Порог `MIN_CALLS_FOR_BROKEN` для малых выборок.** *~1ч.* Сейчас 5 вызовов: две неудачи подряд
  (типично — подбор аргументов) роняют тул в `broken` и заводят mandatory-задачу. Варианты: поднять минимум
  для MCP-тулов, либо требовать непарность **выше фона** (замер 2026-07-25: фон по MCP ≈7% на 1047 Pre).
  Acceptance: разобранные кейсы (`modify_metadata` 4/5, `get_metadata_structure` 6/8) классифицируются
  без ложного «инструмент сломан», реальный отказ сервера — по-прежнему `broken`.

**Порядок:** N-P0.1 → N-P0.2 → N-P0.3 → N-P1.1 → N-P1.2 → N-P1.4 → N-P2.3 → N-P4.1 → N-P4.2 → остальное
по мере касания/потребности. N-P0 — один спринт (~1 день с тестами и code-verify), N-P1 — второй.

### 2026-07-25 (вечер) — Снята опровергнутая known-issue запись `update_database`

Запись подавляла вердикт формулировкой «непарный Pre при **фактическом успехе**: EDT дописывает
обновление БД после отвала клиента по 60с MCP-таймауту; 0 записей с ошибкой; результат проверяется
повторным вызовом». Сверка с native OTel по `tool_use_id` (возможная после фикса архивов — запись ниже)
опровергла все три утверждения: у **всех 20** непарных Pre native даёт `success=false`; «0 ошибок» —
артефакт чтения только hook-лога (там `error_type` = пустая строка ⇒ предикат `IS NOT NULL` истинен
на всех 14 673 строках); повтор с теми же аргументами падал снова в **15 из 20** случаев при том, что
успешный вызов длится 4.3-16.5с. Кластеры: 5 × `TelemetrySafeError` @ 60 004-60 012мс + 15 ×
`McpToolCallError`. «MCP-таймаут» неверен и по источнику: у `edt-mcp` таймаут 180 000мс при
`MCP_TOOL_TIMEOUT=240000` ⇒ 60с приходят изнутри цепочки.

**Снято, а не переписано:** ADR-055 требует ИЗВЕСТНЫЙ корень, здесь корней два и ни один не установлен.
Подавлять неизвестный воспроизводимый отказ **деструктивного** тула опасно инверсией — тихий провал
`update_database` означает «разработчик считает БД обновлённой, когда она не обновлена». Вердикт после
снятия `degraded` (success 57% ⇒ не broken), а `degraded` по §6.1 mandatory-задачу не плодит.
Подавлены теперь только `qa_run`/`qa_generate` (W13, корень внешний и известный).

Следующий шаг диагностики: текста ошибки нет ни в native (`tool_name` у MCP обобщён до `mcp_tool`),
ни в hook-логе; `mcp_call_log` к edt-mcp неприменим (внешний Eclipse-плагин через `mcp-remote`) ⇒
журнал самого EDT. Гипотеза, согласная с данными: реструктуризация ждёт неавто-принимаемого
подтверждения (`stateAfter≠UPDATED` → `fullUpdate=true`), что объясняет и 60с-потолок, и мгновенные
отказы следующих вызовов, и кластеризацию во времени. Полный разбор —
[гл. 50.3 §«Опровергнутая запись `update_database`»](../framework%20documentation/7_ПРОВЕРКА/7.11_ЛОГИРОВАНИЕ_ИНСТРУМЕНТОВ/50.3_Анализ_вердикты_действия.md).
