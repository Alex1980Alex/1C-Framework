# Feature: GKSTCPLK-2507 — Автоматическая установка вида допуска в РМ Приёмка/отгрузка по номенклатуре

> Source ANALYSIS-REPORT: `configuration/260304_GKSTCPLK-2182…/docs/260519_GKSTCPLK-2501 Дополнить АРМ детали. Блок лаб анали/ANALYSIS-REPORT.md`
> Task ID: **GKSTCPLK-2507** (комментарии к коду: `// GKSTCPLK-2507`)

## Summary

Добавить механизм автоматической установки запрета вскрытия по виду допуска при проведении документа `гкс_РегистрацияНаПЛК`. Правила настраиваются оператором через новый регистр сведений «Настройки запрета вскрытия по номенклатуре» — для пары `(Номенклатура, ДопускКВскрытию)` указывается, что соответствующий допуск должен блокироваться автоматически (`ВскрытиеЗапрещено = Истина`) при создании регистрации. Механизм работает по аналогии с «зелёным коридором» (`гкс_НастройкиОтключенияВходногоКонтроляКачества`) и распространяется и на ЖД, и на Авто-приёмку.

## Motivation

Сейчас при проведении `гкс_РегистрацияНаПЛК` (только для ЖД-приёмки) функция `ТекстЗапросаТаблицаСтатусыДопускаВагоновКВскрытию` ([ManagerModule.bsl:615-679](../../../ИБTransportManagementDevelop/Конфигурация/src/Documents/гкс_РегистрацияНаПЛК/ManagerModule.bsl#L615)) формирует по 4 записи на каждый вагон в регистре `гкс_СтатусыДопускаВагоновКВскрытию` (по одной на каждое значение перечисления `гкс_ДопускиКВскрытиюВагонов`: Фитосанитарный/Фумигационный/Претензионный/Ветеринарный). Из коробки `ВскрытиеЗапрещено=Истина` ставится **только** для Претензионного, остальные — `Ложь`. Переключение запретов делается **вручную** через АРМ «Приёмка и отгрузка на ПЛК». Бизнес-требование — для рискованных номенклатур ставить запреты автоматически без ручного вмешательства оператора, чтобы (a) сократить время оформления регистрации, (b) убрать риск пропуска ручной операции на критичной номенклатуре, (c) дать оператору единый узел настройки в АРМ Приёмки По Качеству рядом с уже существующими «Усиленный контроль» и «Отключение входного контроля».

## Proposed Solution

**1. Новый регистр сведений настроек** `РегистрСведений.гкс_НастройкиЗапретаВскрытияПоНоменклатуре`:
- Измерения (минимальный набор): `Номенклатура` (`CatalogRef.Номенклатура`), `ДопускКВскрытию` (`EnumRef.гкс_ДопускиКВскрытиюВагонов`), `ДатаНачала` (`Date`).
- Ресурс `Активен` (`Boolean`). Реквизиты `ДатаОкончания`, `Комментарий (String 150)`, `ДатаВремяИзменения`, `Пользователь`.
- RLS: `РазрешитьЧтениеИзменение ГДЕ ЗначениеРазрешено(Номенклатура)` (паттерн зелёного коридора).
- Формы записи и списка по образцу [`гкс_НастройкиОтключенияВходногоКонтроляКачества`](../../../ИБTransportManagementDevelop/Конфигурация/src/InformationRegisters/гкс_НастройкиОтключенияВходногоКонтроляКачества/гкс_НастройкиОтключенияВходногоКонтроляКачества.mdo).

**2. Расширение SQL в `ТекстЗапросаТаблицаСтатусыДопускаВагоновКВскрытию`**: `ЛЕВОЕ СОЕДИНЕНИЕ` с новым РС по ключу `(Номенклатура, ДопускКВскрытию)` + фильтр `Активен`. Финальный `ВЫБОР` для `ВскрытиеЗапрещено`: при `Настройки.Номенклатура ЕСТЬ NULL` — старая логика (Истина только для Претензионного); иначе — Истина. `Комментарий` — «Автоматически по настройкам запрета вскрытия по номенклатуре» при срабатывании. Условие вызова на стр. 51 расширяется с «только ЖД» на «ЖД + Авто» (измерение `Вагон` — `CatalogRef.ТранспортныеСредства`, универсально).

**3. UI в `Обработка.гкс_АРМПриемкаПоКачеству.Форма.Форма`**: третья страница в `ГруппаНастройки` рядом с «Усиленный контроль» и «Отключение входного контроля» — динсписок нового РС + команды CRUD + фильтр активности по образцу зелёного коридора ([Module.bsl:78-200](../../../ИБTransportManagementDevelop/Конфигурация/src/DataProcessors/гкс_АРМПриемкаПоКачеству/Forms/Форма/Module.bsl#L78)).

**4. Защита и доступ**: новая ФО `гкс_ИспользоватьАвтоустановкуЗапретаВскрытия` (+ константа) управляет видимостью вкладки и опционально оборачивает LEFT JOIN. Новая роль `гкс_НастройкаЗапретаВскрытияПоНоменклатуре` даёт право редактирования; проверка через `Пользователи.РолиДоступны(...)` в `УстановитьВидимостьДоступность`.

## Alternatives Considered

- **Расширенный набор измерений** (Поставщик + ВидПеревозки + ТочкаМаршрута + ПунктПогрузки + Транспорт + ЖДСтанция, как в зелёном коридоре): отклонено заказчиком в пользу минимального набора. Расширение возможно потом через `add_metadata_attribute` без переписывания SQL.
- **Отдельный регистр для Авто** (`гкс_СтатусыДопускаАвтоКВскрытию`): отклонено. Тип `Вагон = CatalogRef.ТранспортныеСредства` универсален, переиспользование проще; open-issue про синоним «Статусы допуска **вагонов**» обсуждается на approve.
- **Хук на `ПередЗаписью` документа** вместо SQL-расширения: отклонено. Логика движений централизована в `ТекстЗапросаТаблицаСтатусыДопускаВагоновКВскрытию`, overlay через LEFT JOIN — изоморфное расширение без дублирования транзакционной логики.
- **Прямая `/implement-1c-task` без SDD**: отклонено. 3 `[ADDED]` объекта метаданных (РС + ФО + Роль) попадают под правило skill `analyze-1c-task-v2` — рекомендован SDD-маршрут с approval gate.

## Impact

- [x] **Breaking changes** — добавляются новые метаданные (РС / ФО / Роль), требуется обновление конфигурации БД (`mcp__edt-mcp__update_database`). Существующее поведение НЕ ломается: при пустом новом РС движения по `гкс_СтатусыДопускаВагоновКВскрытию` идентичны текущим (LEFT JOIN не находит совпадения → срабатывает ветка дефолта).
- [x] **Database migrations** — создание физических таблиц нового РС при первом deployment (`update_database(fullUpdate=true, autoRestructure=true)`). Существующие данные `гкс_СтатусыДопускаВагоновКВскрытию` НЕ модифицируются.
- [ ] **API changes** — нет (внутренняя бизнес-логика, новых публичных API нет).
- [x] **Operational impact** — единая точка контроля для оператора в АРМ Приёмки По Качеству; перепроведение существующих регистраций будет применять новые правила (документировано как ожидаемое поведение).

## Security & Authorization

Безопасность реализуется на трёх уровнях:

1. **Аутентификация** — стандартная 1С-сессия (пользователь авторизован при старте Конфигуратора/тонкого клиента). Дополнительной auth-логики не вводится.
2. **Авторизация (RBAC)** — новая роль `гкс_НастройкаЗапретаВскрытияПоНоменклатуре` даёт R/W/Add/Edit/Delete на новый РС. Пользователи без роли видят список read-only (через `Элементы.НастройкиЗапретаВскрытияПоНоменклатуре.ТолькоПросмотр = Истина`). Команды «Создать»/«Удалить» в АРМ Приёмки По Качеству скрываются через `Пользователи.РолиДоступны("гкс_НастройкаЗапретаВскрытияПоНоменклатуре")` в `УстановитьВидимостьДоступность`.
3. **RLS** — `ПриЗаполненииОграниченияДоступа` в `ManagerModule` нового РС: `РазрешитьЧтениеИзменение ГДЕ ЗначениеРазрешено(Номенклатура)`. Ограничивает чтение/запись правил по номенклатурам, доступным текущему пользователю (стандартный паттерн БСП «Управление доступом»).

Read-доступ дополнительно предоставляется существующим read-only ролям `гкс_БазовыеПраваУправлениеТранспортомНаПЛК` и `гкс_ТолькоПросмотрБезРЛС` — чтобы операторы видели правила, не имея права их менять.

## Error Handling

Сценарии ошибок и их обработка:

- **Конфликт уникальности измерений** — две активные записи `(Номенклатура × ДопускКВскрытию)` с одинаковым `ДатаНачала` отклоняются платформой (`Конфликт уникальности`). Форма записи перехватывает через стандартный `ОбработкаПроверкиЗаполнения` БСП, оператор видит «Запись с такой парой уже существует».
- **Удалённая Номенклатура** (на которую ссылается активное правило) — в SQL-overlay LEFT JOIN вернёт NULL (битая ссылка), сработает дефолтная ветка `ВЫБОР КОГДА NULL ТОГДА <старая логика>`. Правило перестаёт работать (graceful degradation), без падения проведения.
- **Ошибка в `ПриЗаполненииОграниченияДоступа`** — стандартный механизм RLS падает только при некорректной формулировке условия; условие верифицируется при компиляции конфигурации EDT.
- **Перепроведение с уже существующими движениями** — стандартное поведение проведения 1С: старые движения по регистратору удаляются, формируются новые согласно текущему состоянию правил. Не требуется специальной обработки.
- **Отказ при обновлении БД** (`update_database`) — если другие пользователи держат блокировки конфигурации, EDT-MCP вернёт ошибку. Обработка — программный gate `get_applications() len ≤ 1` перед вызовом (см. tasks.md §9.1).

## Concurrency

Параллельные сценарии и их семантика:

- **Параллельные проведения двух Регистраций на ПЛК** с одной номенклатурой — каждый документ имеет свой `Регистратор` в `гкс_СтатусыДопускаВагоновКВскрытию`, конфликта измерений нет. Оба проведения корректно применяют overlay из одних и тех же правил РС (SELECT-only обращение).
- **Изменение правила во время проведения** — правило читается через `SELECT` внутри запроса проведения; платформа 1С использует управляемые блокировки (`Managed`). Если в момент проведения параллельно идёт запись в РС-настройку — одно из двух будет ждать (зависит от уровня изоляции). Стандартное поведение для всех РС в конфигурации.
- **Перепроведение пакетом нескольких документов** — последовательная транзакционная обработка (стандартная для 1С). Каждый документ независимо читает текущее состояние правил.
- **Concurrent edit правила двумя операторами** — `ФормаЗаписи` блокирует объект на чтении (`InDialog` + optimistic locking), второй оператор получит «Запись изменена другим пользователем» и должен перечитать. Стандарт БСП.

Транзакционных гарантий поверх стандартного 1С не добавляется — overlay изоморфен текущей логике движений.

## Glossary

Сокращения и термины, используемые в документе:

- **АРМ** — Автоматизированное Рабочее Место (форма 1С с UI для оператора).
- **БСП** — Библиотека Стандартных Подсистем 1С.
- **BSL** — Built-in Scripting Language (язык 1С).
- **EDT** — Eclipse Development Tools для 1С (IDE для BSL/XML конфигураций).
- **ЖД** — железнодорожный (тип перевозки в `Перечисление.гкс_ТипыТранспортныхСредствДоставки`).
- **MCP** — Model Context Protocol (протокол интеграции AI-агентов с инструментами).
- **NULL** — отсутствие значения в результате SQL-запроса (для LEFT JOIN — нет совпадения по ключу).
- **ПЛК** — пункт логистического контроля Сморгонь (бизнес-локация).
- **RBAC** — Role-Based Access Control (ролевая модель доступа).
- **REQ-N** — нумерованное требование в spec.md (delta-spec).
- **RFC 2119** — стандарт ключевых слов формулировки требований (MUST, SHOULD, MAY, MUST NOT, etc.).
- **RLS** — Record-Level Security (ограничение доступа на уровне записей через `ЗначениеРазрешено`).
- **РС** — регистр сведений (тип объекта 1С: периодический/непериодический срез по измерениям).
- **SDD** — Spec-Driven Development (OpenSpec workflow: propose → approve → apply → archive).
- **SQL** — Structured Query Language (запросы к базе данных; в 1С — наследник, с русскоязычным синтаксисом ВЫБРАТЬ/ИЗ/ГДЕ).
- **ТС** — транспортное средство (вагон или автомобиль, `CatalogRef.ТранспортныеСредства`).
- **ФО** — функциональная опция (объект 1С: feature flag на уровне конфигурации).
