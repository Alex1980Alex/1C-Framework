# Spec: disallow-by-nomenclature-overlay

**Change:** gkstcplk-2507-auto-disallow-by-nomenclature
**JIRA:** GKSTCPLK-2507

См. proposal.md и design.md для контекста.

## ADDED Requirements

### Requirement: РегистрСведений `гкс_НастройкиЗапретаВскрытияПоНоменклатуре`

Конфигурация **MUST** содержать новый периодический независимый РегистрСведений с тремя измерениями (Номенклатура, ДопускКВскрытию, ДатаНачала), ресурсом Активен и реквизитами для аудита и срока действия (ДатаОкончания, Комментарий, ДатаВремяИзменения, Пользователь). RLS-условие `ПриЗаполненииОграниченияДоступа` **MUST** содержать `РазрешитьЧтениеИзменение ГДЕ ЗначениеРазрешено(Номенклатура)`. Формы записи и списка **MUST** быть созданы по образцу `гкс_НастройкиОтключенияВходногоКонтроляКачества`.

#### Scenario: создание правила автоустановки запрета

- **WHEN** оператор открывает форму записи нового РС и заполняет Номенклатура + ДопускКВскрытию + ДатаНачала + Активен=Истина
- **THEN** запись сохранена, `ДатаВремяИзменения = ТекущаяДата()`, `Пользователь = ПараметрыСеанса.ТекущийПользователь`

#### Scenario: попытка дубликата

- **WHEN** оператор сохраняет вторую активную запись с одинаковой парой (Номенклатура × ДопускКВскрытию × ДатаНачала)
- **THEN** платформа возвращает «Конфликт уникальности», запись не сохранена

### Requirement: ФункциональнаяОпция `гкс_ИспользоватьАвтоустановкуЗапретаВскрытия`

Конфигурация **MUST** содержать новую функциональную опцию типа Boolean со связью на одноимённую константу `Constants.гкс_ИспользоватьАвтоустановкуЗапретаВскрытия`. Опция используется как kill-switch для механизма автоустановки запретов.

#### Scenario: видимость UI-вкладки

- **WHEN** константа = Ложь
- **THEN** третья страница `ГруппаЗапретаВскрытияПоНоменклатуре` в АРМ Приёмки По Качеству скрыта

#### Scenario: гарда SQL-overlay

- **WHEN** константа = Ложь и SQL-overlay обёрнут гардой `Если ПолучитьФункциональнуюОпцию(...)`
- **THEN** при проведении регистрации overlay не применяется, движения формируются по дефолтной логике

### Requirement: Role `гкс_НастройкаЗапретаВскрытияПоНоменклатуре`

Конфигурация **MUST** содержать новую роль с правами R/W/Add/Edit/Delete на РегистрСведений `гкс_НастройкиЗапретаВскрытияПоНоменклатуре`. Роль **MUST** быть создана по образцу `гкс_НастройкаУсиленногоКонтроля`.

#### Scenario: пользователь с ролью

- **WHEN** пользователь имеет роль и открывает третью вкладку АРМ Приёмки По Качеству
- **THEN** команды «Создать»/«Удалить» доступны

#### Scenario: пользователь без роли

- **WHEN** пользователь не имеет роли и открывает третью вкладку
- **THEN** список read-only, команды CRUD заблокированы

### Requirement: UI — третья страница в `ГруппаНастройки` АРМ Приёмки По Качеству

Форма `DataProcessor.гкс_АРМПриемкаПоКачеству.Form.Форма` **MUST** содержать третью страницу `ГруппаЗапретаВскрытияПоНоменклатуре` в существующем pages-контейнере `ГруппаНастройки` (рядом с «Усиленный контроль» и «Отключение входного контроля»). Top-level реквизит формы `НастройкиЗапретаВскрытияПоНоменклатуре` типа `DynamicList(РегистрСведений.<новый>)` **MUST** быть добавлен. Видимость управляется ФО `гкс_ИспользоватьАвтоустановкуЗапретаВскрытия`.

#### Scenario: открытие вкладки при включённой ФО

- **WHEN** ФО = Истина, оператор открывает АРМ
- **THEN** видна третья вкладка с динсписком нового РС и колонками Номенклатура/ДопускКВскрытию/Активен/ДатаНачала/ДатаОкончания/Комментарий

#### Scenario: команда «Создать»

- **WHEN** оператор с ролью нажимает «Создать» на третьей вкладке
- **THEN** открывается ФормаЗаписи нового РС

## MODIFIED Requirements

### Requirement: SQL-overlay движений по `гкс_СтатусыДопускаВагоновКВскрытию`

Функция `Документ.гкс_РегистрацияНаПЛК.МодульМенеджера.ТекстЗапросаТаблицаСтатусыДопускаВагоновКВскрытию` **MUST** быть расширена: в `ВТ_НачальныеДопуски` SELECT добавляется `Регистрация.Номенклатура`, финальный SELECT делает `ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.гкс_НастройкиЗапретаВскрытияПоНоменклатуре` по ключу `(Номенклатура × ДопускКВскрытию)` с фильтром `Активен`. `ВЫБОР` для `ВскрытиеЗапрещено`: `КОГДА Настройки.Номенклатура ЕСТЬ NULL ТОГДА <старая логика> ИНАЧЕ ИСТИНА`. `Комментарий` аналогично через `ВЫБОР`.

#### Scenario: правило сработало (Фумигационный)

- **WHEN** активная запись (Номенклатура=Лен, Допуск=Фумигационный) существует, провели Регистрацию
- **THEN** в `гкс_СтатусыДопускаВагоновКВскрытию` запись Фумигационный имеет `ВскрытиеЗапрещено = Истина`, Комментарий = «Автоматически по настройкам запрета вскрытия по номенклатуре»

#### Scenario: правил нет (регрессия)

- **WHEN** для пары (Номенклатура × Допуск) активных записей в новом РС нет
- **THEN** поведение полностью идентично текущему: 4 записи на ТС, `ВскрытиеЗапрещено = Истина` только для Претензионного

#### Scenario: правило деактивировано

- **WHEN** запись в РС переведена в `Активен = Ложь`, регистрация перепроведена
- **THEN** соответствующий допуск возвращается к дефолтной логике

### Requirement: Распространение проведения движений на Авто-приёмку

Условие вызова `ТекстЗапросаТаблицаСтатусыДопускаВагоновКВскрытию` в общей логике формирования движений документа `гкс_РегистрацияНаПЛК` **MUST** быть расширено с «только ЖД» (`ЭтоПриемкаЖДТранспорта(Документ)`) на «ЖД И Авто» (`Или ЭтоПриемкаАвтоТранспорта(Документ)` либо эквивалентное условие).

#### Scenario: ЖД-регистрация

- **WHEN** документ с `ВидПеревозки = ЖДТранспорт` проведён
- **THEN** движения по `гкс_СтатусыДопускаВагоновКВскрытию` сформированы (как и было)

#### Scenario: Авто-регистрация

- **WHEN** документ с `ВидПеревозки = Автомобиль` проведён
- **THEN** движения тоже сформированы (новое поведение)
