Компактная форма (ADR-018, trivial-трек): задача read-only, продуктовый код не менялся.
Артефакты разбора - скрипты в scratchpad сессии, выводы ниже.

Баннер SessionStart выдал ~20 сигналов (tool-health 4 broken + 10 degraded, 50 непрочитанных
ci-fail, 4 сабмодуля с 524 несохранёнными файлами, 3 замолчавших memory-синка,

Два инварианта опровергнуты фактами:

- **Блоки гардов ПОПАДАЮТ в непарные Pre.** CLAUDE.md (N-P0.1) утверждает
  «Write unpaired=0 при живом блоке». В этой сессии `code-skill-enforcer` заблокировал
  `Write` (FP на строковых именах MCP-тулов внутри скрипта) → в логе за 25.07 ровно
  1 непарный `Write` при 9 вызовах. Часть 47 непарных Write - активность энфорсеров.
- **`error_type` пишется пустой строкой, а не отсутствует** → предикат `error_type IS NOT NULL`
  ложно-положителен на **всех** 14 673 канонических записях. Реальное значение
  (`mcp_tool_error` + `success=false` + `outcome=error` + зашифрованное тело `error` вида
  `enc::…`) несут ровно **3** записи (0.02%). То есть провал практически всегда виден только
  как непарный Pre - это соответствует NB1, но делает поле `error_type` непригодным для
  фильтрации «есть ошибка».

Для shell-тулов непарный Pre честен, но измеряет качество команд вызывающего, а не
здоровье инструмента - порог error-rate 10% для `Bash`/`PowerShell` бессмыслен по той же
причине, по которой для них отключили p95-порог.

### 4. OTel крос-чек молча теряет данные при ротации

Отчёт 10:53 - native 1485 событий, FP 18 / TP 17. Прогон 11:13 - native **17**, FP 0 / TP 2.
Причина: `otel_crosscheck.py:43` читает только живой `data/otel/claude-otel-logs.jsonl`,
а file-exporter ротирует по 20 МБ в `claude-otel-logs-<ts>-size.jsonl` (ротация была 11:06;
4 архива по ~1700 строк игнорируются). Это тот же дефект single-retention, который для
hook-лога закрыли каскадной ротацией в N-P0.2, - на OTel-сторону не перенесён.
Вывод «детектор согласован с native» непроверяем до фикса.

### 5. Окно 14д = 8.5д, самозаполнится

Лог 16.07 23:25 → 25.07 11:13, 7 файлов. Каскадная ротация заведена 17.07, архивов 6 из 12;
при ~10 МБ / 1.5 дня набор дойдёт до ~18 дней к концу месяца. Отчёт помечает
`window_incomplete` честно. Существенно то, что 3 из 4 broken стоят на N=2..10 вызовов
внутри усечённого окна.

**Этап 1.** Отдано 131 коммит: MFM 4, SVETLY 19, ИБ 25, 260416 1, 260304 77,

**260304 — записи встреч через git LFS** (решение пользователя; коммит `6216924c1`).
19 коммитов упирались в `.webm` 131.55МБ при лимите GitHub 100МБ. Штатный
`git lfs migrate import` переписывает **все 447 коммитов** (кладёт `.gitattributes`
в первый) → force-push поверх ~389 опубликованных и сломанные гитлинки в прошлых
коммитах парента. Сделано без force-push: `.gitattributes` (`*.webm filter=lfs`)
закоммичен поверх уже отданного `0af2188f`, 19 коммитов перенесены cherry-pick'ом.
⚠ **Ловушка:** cherry-pick переносит готовые git-объекты и clean-фильтр НЕ запускает —
блоб остался сырым (поймано проверкой, не предположением). Единственный коммит,
добавляющий запись (`eaf55fc6`), пересобран через рабочее дерево
(`cherry-pick -n` → `reset` → `add -A` → `commit -C`); остальные 18 запись не трогают
и подхватили указатель трёхсторонним слиянием.
Перезапись шла в клоне на **коротком пути** (`%TEMP%\lm`, `core.longpaths=true`) — первый
клон в scratchpad упал в MAX_PATH и не выгрузил 41 файл, на таком дереве cherry-pick
дал бы ложные удаления. Рабочее дерево сабмодуля не тронуто: 79 несохранённых файлов
(18 M / 4 D / 57 untracked) до и после идентичны. Страховка — ref
`backup/pre-lfs-260725` (держит прежний хвост `20e7cce2`).
Проверено перед пушем: `0af2188f` остался предком (fast-forward), блобов >50МБ в
диапазоне нет, LFS-объект 138МБ загружен, дерево нового хвоста отличается от исходного
**ровно двумя** файлами. Гитлинки на remote: **9 из 9**, `clone --recursive` собирается
(для записей нужен `git lfs pull`).

**Этап 4 — посылка опровергнута.** Проверял корень перед мьютом, как требует ADR-055.
Native OTel по `tool_use_id`: **все 30 непарных Pre = `success=false`**, ни одного
мнимого провала, и корней ДВА, а не один:
`TelemetrySafeError` при `duration_ms` 60 004-60 016 (ровно 60с = таймаут MCP-клиента)
и `McpToolCallError` при 5-28мс (мгновенный отказ сервера). Разбивка непарных:
`modify_metadata` 4 мгновенных + 1 таймаут, `delete_project` 2 таймаута + 1 мгновенный,
`create_project` 2 таймаута, `update_database` 12 мгновенных + 8 таймаутов.
Регистрация «одним корнем» замьютила бы реальные отказы → не делал.
Дополнительно: **действующая запись `update_database` в `known_issues.json` опирается на
опровергнутое утверждение** («непарный Pre при ФАКТИЧЕСКОМ успехе», «0 записей с
ошибкой») — цифра «0 ошибок» была артефактом чтения только hook-лога, где `error_type`
пишется пустой строкой. Решение по ней — за пользователем (ADR-055 отдаёт мьют человеку).

**Известное ограничение этапа 5.** Вычет блоков сделан в per-tool разрезе;
`agent_rollup` (разрез по `agent_id`) блоки не вычитает — там они по-прежнему в errors.
Влияние <1% на `(main)`, вердиктов по агентам нет, поэтому не расширял скоуп.
