# 01 · Планирование — гейт «действие не названо» в `route_1c_task`

## Проблема (найдена живым прогоном на реальном примере)
Вход из чата: путь к `ManagerModule` обработки с `гкс_`-префиксом + строка инициализации
структуры (BSL) + предупреждение анализатора + вопрос «Это 1С задача?».

Фактический вывод `route_1c_task` (прогон пробника):
- детект «это 1С» — **верен**: `гкс_` (definitive) + литеральный BSL (`_1C_CODE`) → `confidence=0.9`,
  `confident_1c=true`;
- маршрут — **баг**: `flow="auto"` → запустил бы `/run-1c-task` (AUTO analyze→implement→test),
  хотя `_TASK_VERB=False` и `signals=[]` (ноль улик о scope). `simple` достигнут лишь из
  `base(1)+ttype_T1(1)`.

## Корень
Детектор смешивает **«в тексте есть 1С-код/маркер»** с **«дана 1С-задача к исполнению»**.
`code=True` форсит `confident`, а `estimate_effort` без сигналов работы даёт `simple` → ветка `auto`.
Дорогой класс FP: code-путь короткозамыкает на авто-прогон (см. memory
[[feedback-1c-code-presence-key-signal]]).

## Цель
Confident-1С **без названного действия** (нет таск-глагола И нет work-сигналов) → НЕ запускать
AUTO в пустоту, а спросить «что именно сделать?». Согласуется с инвариантом пользователя
«сомнение → спросить» ([[feedback-1c-detection-judgment-mine]]).

## Не-цель
- Не трогаем детект «это 1С» (он верен) — только ветку маршрута.
- Не расширяем `_TASK_VERB` (отдельная задача); гейт работает на отсутствии ЛЮБОГО из словаря.
- Не вводим новый `flow`-литерал (минимизируем blast-radius на потребителя `onec-task-input.py`).
