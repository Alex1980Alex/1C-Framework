# Клиентский потолок ожидания ≠ провал инструмента (tool-health)

**Задача.** Метрика считала провалом непарный Pre, включая случаи, когда клиент оборвал
ожидание (~60с), а сервер довёл операцию до успеха → ложные `broken`/`degraded`
(`delete_project` «0 успешных из 3 попыток» при двух удавшихся удалениях).

## Этап 1-2. Анализ и дизайн (замер до кода)

Проверены три кандидата в источник истины:

| Источник | Что даёт | Вывод |
|---|---|---|
| hook-лог `data/hook-invocations*.jsonl` | парность Pre/Post | причину не знает |
| native OTel `claude_code.tool_result` | `success`/`duration_ms` | смотрит **глазами клиента**: при обрыве `success=false` даже при серверном успехе |
| **журнал EDT** `<ws>/.metadata/.log` | `Completed tools/call: <t> in Nms, outcome=` + `Failed … - <текст>` | **арбитр исхода** (+ единственный носитель текста отказа) |
| per-call лог `.claude/cache/mcp-*-calls.jsonl` | серверные вызовы 1c-mcp-crud | покрывает только обёрнутые серверы |

Замеры, задавшие константы:
- Δ(journal.start − Pre.ts) на 22 живых записях = **+0.065…+0.548с** → допуск `SERVER_OK_MATCH_SEC=2`.
- Максимум **парного** (успешно вернувшегося) вызова **13.4с**; минимум оборванного при
  серверном `ok` — **60.3с** → `CLIENT_CAP_MS=55_000` в пустой полосе между ними.

Решения дизайна: (1) вычитать только доказанное (`outcome=ok` ∧ `ms ≥ порог`), иначе провал
остаётся провалом (fail-closed); (2) повторить механику `blocked` (расходуемое сопоставление 1:1),
не изобретать вторую; (3) НЕ классифицировать эвристиками ошибки вызывающего/транзиенты —
их тексты **сюрфейсить** в отчёт, решение за человеком; (4) вычтенное показывать (`no silent caps`).

## Этап 3. Кодирование

- `scripts/edt_journal.py` — новый stdlib-парсер (read-only, fail-soft; пропуск битой строки
  и абсурдной длительности вместо падения — класс tz-крэша `iter_window_rows`).
- `scripts/tool_effectiveness.py` — `completion_stats(server_ok=, server_ok_ids=)`,
  `_take_server_ok`, счётчик `client_timeout`; **парный Pre забирает свою запись первым**.
- `scripts/analyze_tool_health.py` — `CLIENT_CAP_MS`/`EDT_JOURNAL_SERVER`, `server_ok_by_tool`,
  `journal_failures_for`, проводка в `aggregate_tools`/`agent_rollup`/`compute_health`/`run`,
  секция отчёта «Серверные исходы (журнал EDT)», поля sidecar.

Аддитивность: без журнала (`server_ok=None`) поведение бит-в-бит прежнее.

## Этап 4. Тестирование

- 22 unit `tests/unit/test_tool_health_client_timeout.py` (парсер, вычет, обе стороны инварианта,
  graceful, согласованность разрезов).
- **Саботаж 5/5**: вычет выключен → 7 красных; парный Pre не забирает запись → 1; сопоставление
  не расходуется → 1; `CLIENT_CAP_MS=0` → 1; счётчик возвращён в провалы → 2. Восстановление зелёное.
- Полный `-m unit`: **2725 passed, 2 skipped**. ruff + compileall чистые.
- Живой прогон: вычтено **7** вызовов (`update_database` 3, `delete_project` 2, `delete_metadata` 1,
  `create_project` 1); **broken 4 → 3**; `update_database` 43% → 40%; суммы вычета per-tool ==
  per-agent (`client_timeout` 7/7, `blocked` 81/81).
