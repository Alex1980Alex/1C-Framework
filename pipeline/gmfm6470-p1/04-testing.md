## Отгруженная строка не убирается из заказа (решение постановщика 2026-07-16)

**Находка постановщика при ручном прогоне:** в S5 строка `A` из заказа **исчезала**, хотя по ней есть
проведённый транспортный документ. Загрузка делает `ГрафикОтгрузки.Загрузить()` — полное замещение
табличной части, поэтому строки, которой CRM не прислала, в заказе не остаётся. Ничто её не защищало:
`СтрокаЗакрыта` в регистре ставит **вручную логист** из АРМ ОСПГ, автоматически по факту отгрузки не
выставляется.

**Решение:** отгруженную строку возвращаем в заказ — новая `гкс_ЗаявкаНаОтгрузку.ВернутьОтгруженныеСтроки`,
вызывается из `ЗаполнениеГрафикаОтгрузки` **до** заполнения номеров. Работает потому, что
`ЗаполнениеГрафикаОтгрузки` живёт в `ПередЗаписью` — прежняя табличная часть ещё в базе, из неё и
восстанавливаем. Отличаем «строку убрали» от «строка на месте» по `ИдентификаторСтроки`: после
`Загрузить()` `ИндЗаказа` обнулён у всех. Возвращённая строка приходит со своим номером, поэтому
`ЗаполнениеИндЗаказаПоДокументу` сразу считает его занятым, а правило про номера становится
подстраховкой. Строки дописываются в конец: порядок остальных задаёт CRM.

Прежнюю версию строк читаем через БСП — `ОбщегоНазначения.ЗначениеРеквизитаОбъекта(Ссылка, "ГрафикОтгрузки").Выгрузить()`
(идиома этого же модуля, `ЗаполнитьНаОснованииЗаявкиНаОтгрузку`). Первая редакция собирала запрос
руками с динамическим списком полей по метаданным — замечание постановщика «почему через запрос, а не
к табличной части?»; процедура ужалась с 50 строк до 22. К `ГрафикОтгрузки` в памяти обратиться нельзя:
он уже замещён данными CRM, убранной строки там физически нет.

⚠ **Расширение рамок ТЗ, принято осознанно.** ТЗ (строка 76) относит «блокировать отгруженные строки»
к **пункту 2** (документ-корректировка), а строка 86 говорит «доработка пути загрузки не нужна».
Реакция выбрана «вернуть строку», а не «отказать в записи» — по указанию постановщика.

⚠ **Известный предел (пункт 2).** Признак «была отгрузка» — движения проведённого ТД. По процессу
(ТЗ, строка 21) логисты **распроводят подчинённые документы** перед переобменом; после распроведения
движений нет, и защита не сработает. Постановщик решил оставить так: полное решение — пункт 2.

## «Второй момент» встречи (проверка «изменился ли заказ») — разобрано 2026-07-16

Требование (транскрипт 13.07, Задача 1 п.3): *«при перепроведении добавить проверку "изменился ли заказ":
не изменился → ничего не переприсваивать; изменился → переприсваивать только для новых строк,
отгруженные не трогать»*.

**Выполнено, явная проверка не нужна и была бы хуже.** Проверено live: ручное перепроведение заказа
(экспедитор ставит «Утверждён») — было `A=1,B=2`, стало `A=1,B=2`, номера не шевельнулись. Механика: при
ручном перепроведении ТЧ не замещается, `ИндЗаказа` ненулевой → проход 1 помечает занятым и пропускает;
запись в регистр идёт только для новых пар (`ИдентификаторыСтрокЗаказов.ИндЗаказа ЕСТЬ NULL`).
Ре-обмен без изменений — сценарий S1, PASS.

Постановщик назвал механизм (проверка на уровне документа), но нужен результат. Документная проверка
бинарна: «изменился → переприсвоить» сдвинуло бы и нетронутые строки = исходный баг. Сопоставление по
`ИдентификаторСтроки` даёт «не изменилась → не трогаем» для КАЖДОЙ строки, включая частично изменённый
заказ, — строго сильнее требования.

### ⚠ Найденный дефект: возврат удалённой строки ломает обмен (допущение принято)

Правило встречи «прыгаем от единицы» конфликтует с тем, что регистр append-only. Воспроизведено live:

| Шаг | CRM шлёт | Результат | Регистр после |
|---|---|---|---|
| 1 | A,B | A=1, B=2 | A→1, B→2 |
| 2 | C,B (A убрали) | C=**1**, B=2 | A→1, **C→1**, B→2 |
| 3 | A,C,B (A вернулась) | **«Не удалось провести»** | — |

Номер удалённой строки переиспользуется (п.2 встречи), но пара `A→1` в регистре остаётся навсегда
(п.1 встречи: «идентификатор не должен менять номер»). Две записи с номером 1. Возврат A → проход 1
восстанавливает `A→1` и `C→1` → дубль → `ПроверитьУникальностьИндексовЗаказа` ставит `Отказ`.
Со старым правилом `Макс + 1` коллизия была невозможна — дефект внесён правилом встречи.

**Решение постановщика 2026-07-16: принять как недостижимый сценарий.** Обоснование — CRM при повторном
заведении строки выдаёт новый ID. ⚠ Оговорка: уникальность ID сама по себе этого НЕ гарантирует
(отмена удаления вернула бы ту же строку с тем же ID, не нарушая уникальности); допущение опирается
именно на «CRM не откатывает удаление», это стоит подтвердить у владельца CRM.

Защита не строится: дешёвой нет — пришлось бы пожертвовать либо «мин. свободным», либо «номер за
идентификатором навсегда». Цена допущения приемлема: отказ громкий и диагностируемый («Обнаружены
неуникальные значения ИндЗаказа: 1»), порчи данных нет, обмен по заказу просто встаёт.
Отгруженных строк не касается — их теперь нельзя убрать, номер занят самой строкой в ТЧ.

   это обратное решение, вернуть условие `ФактПеревозки <> 0` (одна строка в `НомераЗанятыеТранспортнымиДокументами`).
