# LLM Rotation — максимальное использование

Мандат: «LLM Rotation настроить на максимальное использование». Рычаги выбраны
пользователем: пропускная способность + параллельная делегация + покрытие фреймворка.
Энфорсмент (жёсткие пороги хуков) намеренно НЕ трогали.

## Диагноз

Ротация исполняла 1-5 вызовов в день. Потолки оказались не в политике, а в конфиге:

| Находка | Факт |
|---|---|
| `.mcp.json` → `LLM_ROTATION_TIMEOUT=60` | перебивал `.env`(90); живой максимум успешного claude-cli — 66с ⇒ вызовы рвались |
| `batch_complete` не экспортирован | параллельная делегация оркестратору недоступна вовсе |
| `batch_complete` без `model` | строгий тир и весь explicit_only-путь (opus) из батча недостижимы |
| `total_budget_seconds=240` при окне 300с | 60с бюджета простаивало |
| Category 2 «opt-in через env» | мёртвая настройка: env читается сырым `os.environ`, `load_dotenv()` во фреймворке только в `zai_proxy.py` |

## Сделано

1. **Пропускная способность.** Снят `LLM_ROTATION_TIMEOUT` из `.mcp.json`, вычищен мёртвый
   `ZAI_API_KEY`; `total_budget_seconds` 240→270, `max_retries` 3→5.
2. **Параллельная делегация.** MCP-тул `llm_complete_batch` (index-aligned результаты,
   провал одного промпта не рвёт батч, честная телеметрия, структурный конверт на
   невалидном входе). `batch_complete` получил `model`.
3. **Безопасность спавнов.** Семафор `batch_cli_concurrency=3` в ТОЧКЕ СПАВНА
   (`_cli_spawn_gate`), не на уровне батча — на уровне батча известен лишь
   предпочитаемый провайдер, а исполнителя выбирает ротация (fail-open, находка ревью).
4. **Агрегатный дедлайн батча** `batch_budget_seconds=250` — частичный результат вместо
   потери всей работы при обрыве клиентом.
5. **Покрытие.** Category 2 включена дефолтом в коде; страховка (пустой ответ → Claude)
   не тронута.
