# 01 — Анализ: почему закрытие Sonar-гейта GKSTCPLK-2637 заняло часы

Дата: 2026-07-03. Вход: вопрос пользователя «почему так долго, как улучшить процесс».

Серийная цепочка из 4 независимых проблем (каждая = полная итерация, итерация = скан на минуты):

1. **Вырожденный new-code baseline SonarQube** (главная потеря). Проект впервые просканирован
   2026-07-01 → все 132k легаси-issue получили creationDate дня скана; период `PREVIOUS_VERSION`
   унаследован от анализа с VERSION-тегом → new≈total (71k «новых»). Гейт ADR-037 запрашивал
   `inNewCodePeriod=true` → 5 легаси-CRITICAL посчитаны новыми → ложный FAIL → расследование
   (3 скрипта, разбор истории анализов). `SPECIFIC_ANALYSIS` на project-level тихо не применяется.
2. **bsl-format хук (ADR-036) переформатировал весь файл** после каждого Edit: гонка Edit-серии
   (2 упавших Edit), ~277 строк легаси-whitespace-churn, CRLF→LF флип → дифф 591 строка →
   потенциальная порча SCM-атрибуции new-code (хук подкармливал проблему №1).
3. **Свои MAJOR на втором скане** — извлечённые хелперы без док-комментариев
   (MissingReturnedValueDescription/MissingParameterDescription) → итерация правка→скан.
4. **Дизайн гейта**: любая правка после скана = stale → полный ре-скан (12g heap, минуты).

Побочные находки в ходе работ: stale `.git/index.lock` от конкурирующих auto-save хуков;
`gate_policy.log_decision` писал `data/gate-decisions.jsonl` относительно cwd → мусор внутри
сабмодулей конфигураций (4 файла).
