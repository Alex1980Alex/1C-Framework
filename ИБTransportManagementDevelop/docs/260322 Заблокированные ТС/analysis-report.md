## 1. Общее описание

Функционал «Заблокированные ТС» реализует механизм усиленного контроля качества на приёмных лабораторно-контрольных комплексах (ПЛК). Суть: при получении неудовлетворительных результатов лабораторных анализов по одному ТС, система автоматически блокирует последующие ТС этого же поставщика/номенклатуры для принудительного прохождения дополнительных проверок перед разгрузкой.

**Архитектура**: Mediator-паттерн — единый серверный общий модуль `гкс_ВходнойКонтрольКачества` (~2 900 строк, 40+ методов) координирует всю бизнес-логику. РС `гкс_ЗаблокированныеРегистрацииУсиленныйКонтроль` выступает тонким CRUD-слоем с 3 экспортными методами в модуле менеджера.

**Функциональная опция**: `гкс_ИспользоватьУсиленныйКонтрольКачества` (хранение в константе). Управляет видимостью всех объектов подсистемы.

- **Код КачествоПринято**: `ОбновитьБлокировкуДляТС()` (строки 1981-2026) — для каждого показателя вызывает `ОбновитьСостояниеБлокировки()` с новым состоянием. При КачествоПринято → `Разблокировано = Истина`, затем `ЗаписатьСостоянияРегистрацииЗаблокированныхТС()` меняет состояние регистрации на КачествоПринято [VERIFIED: MCP read_method_source]

  3. Иначе → `ДобавитьПоказателиУКДляЗаблокированногоТС()` — создаёт `Единичная/ПромежуточныйКомпозит` показатели с данными первого ТС (Мин, Макс, Базис) [VERIFIED]

#### Ключевой механизм: Эскалация правил (НеПринято → КаждоеТС)

При отклонении качества (НеПринято) на Первом ТС или в Группе, метод `ОбработкаОтклоненияПоКачествуУсиленногоКонтроля()` (строки 299-342) выполняет:

1. Получает показатели с `ОтклонятьКачество = Истина`
2. Ищет правила типа `ПервоеТС` для документов регистрации ЛА
3. Ищет правила типа `ГруппыТС` через `Справочники.гкс_ГруппыТС.СоставГруппыПоРегистрации()`
4. **Меняет тип правила на `КаждоеТС`** через `УстановитьТипВНастройкахУсиленногоКонтроля()`
5. Устанавливает `ДатаОкончания` = ТекущаяДата + `гкс_СрокУстановкиПравилКаждоеТС` (константа, в днях)

Это значит: если первое ТС или группа не прошли контроль, ВСЕ последующие ТС этого поставщика/номенклатуры будут проверяться индивидуально в течение N дней.

#### Логика `ПроверитьБлокировкуДляСозданияНнР()` (строки 2424-2536)

```
Проверка: есть ли активные записи в РС ЗаблокированныеРегистрацииУК?
  │
  ├─ Нет записей → Результат.ЕстьБлокировка = Ложь → OK
  │
  ├─ Есть записи с КачествоНеПринято БЕЗ промежуточного композита:
  │   → ЕстьБлокировка = Истина
  │   → "ТС заблокировано. Качество не принято. Создание НнР запрещено."
  │   → СТОП (Block)
  │
  └─ Есть записи с КачествоНеПринято/РПП С промежуточным композитом:
      → ЕстьПредупреждение = Истина
      → "ТС заблокировано. Продолжить создание НнР?"
      → Вопрос Да/Нет (Warn)
```

Промежуточный композит определяется через `РС гкс_ПоказателиУсиленногоКонтроляПоРегистрации` с `НазначениеИспользования = ПромежуточныйКомпозит`.

## 3. Принципы формирования записей (REQ-2) [VERIFIED: PASS]

### 3.1 Когда создаются записи

Записи в РС `гкс_ЗаблокированныеРегистрацииУсиленныйКонтроль` создаются **при проведении документа «Лабораторный анализ»** (`гкс_ЛабораторныйАнализ`), если результаты анализа показывают отклонение от допустимых значений показателей, определённых в настройках усиленного контроля.

### 3.2 Двухканальная запись

Реализована **двухканальная модель** создания записей (строки 252-278 модуля `гкс_ВходнойКонтрольКачества`):

1. **Канал «Первое ТС»** (`ДокументРегистрации`) — блокировка привязывается к конкретному документу регистрации на ПЛК.
2. **Канал «Группа ТС»** (`БлокирующаяГруппаТС`) — блокировка привязывается к группе ТС (справочник `гкс_ГруппыТС`), что позволяет блокировать все последующие ТС в группе поставщика.

### 3.3 Структура записи

Каждая запись фиксирует:
- **Что заблокировано**: `ДокументРегистрации` — регистрация ТС, которую нельзя направить на разгрузку
- **Чем заблокировано**: `БлокирующаяРегистрация` + `БлокирующаяГруппаТС` — источник блокировки
- **По какому показателю**: `Показатель` — конкретный показатель анализа
- **С каким состоянием**: `БлокирующееСостояниеКачества` — текущее состояние качества блокирующего ТС
- **Снята ли блокировка**: `Разблокировано` (Boolean)

### 3.4 Принцип Optimistic Read-Modify-Write

Метод `ОбновитьСостояниеБлокировки` реализует паттерн оптимистичного обновления:
1. Читает текущий набор записей по фильтру измерений
2. Модифицирует ресурсы (состояние, флаг разблокировки)
3. Записывает обратно

### 3.5 Пакетная предзагрузка

Метод `ЗаполнитьЗаблокированныеРегистрации` использует пакетную предзагрузку с дедупликацией через `Соответствие` для минимизации обращений к БД при массовых операциях (АРМ отображает список всех ТС).

## 4. Принципы проверок и валидаций (REQ-3) [VERIFIED: PASS]

### 4.1 Трёхуровневая система проверки блокировки

Метод `ПроверитьБлокировкуДляСозданияНнР` (проверка перед созданием «Направления на разгрузку») реализует **3 уровня**:

| Уровень | Результат | Действие |
|---------|-----------|----------|
| **Block** (Блокировка) | Есть активные незакрытые блокировки | Создание НнР запрещено. Пользователь видит ошибку. |
| **Warn** (Предупреждение) | Есть блокировки, но они допускают продолжение с подтверждением | Пользователю выводится предупреждение, может продолжить. |
| **OK** | Блокировок нет или все разблокированы (`Разблокировано = Истина`) | Создание НнР разрешено без ограничений. |

Подробная матрица решений с учётом наличия единичного анализа — см. раздел 17.

### 4.2 Проверки при проведении документов

1. **Лабораторный анализ (проведение)**: проверяется, попадают ли результаты анализа в диапазоны настроек усиленного контроля (`ЗначениеПоказателяМин`..`ЗначениеПоказателяМакс`). Если да — создаются/обновляются записи блокировки для всех ТС, подпадающих под правило.

2. **Направление на разгрузку (проведение)**: проверяется наличие активных блокировок для данной регистрации. При принятии качества — записи разблокируются (`Разблокировано = Истина`).

3. **Регистрация на ПЛК (проведение)**: проверяется, не попадает ли ТС под действующие правила усиленного контроля.

### 4.3 Валидация настроек

Настройки усиленного контроля (`гкс_НастройкиУсиленногоКонтроляКачества`) валидируются:
- Обязательность заполнения ключевых измерений (вид перевозки, точка маршрута, номенклатура, показатель)
- Корректность диапазона (Мин <= Макс)
- Непересечение периодов действия правил
- Корректность количества ТС (> 0)

## 7. АРМ гкс_ПриемкаТранспорта — центральный пульт управления (REQ-6) [VERIFIED: PASS]

### 7.1 Общая характеристика

- **Обработка:** `гкс_ПриемкаТранспорта` (АРМ "Приёмка и отгрузка на ПЛК")
- **ОсновнаяФорма:** 4002 строки, 199 методов, 7 дополнительных форм
- **Роль:** Единая точка входа для оператора ПЛК — весь жизненный цикл ТС от въезда до приёмки проходит через этот АРМ

### 7.2 Жизненный цикл ТС в АРМ (State Machine)

АРМ реализует **state machine с 13 состояниями**. Правая панель кнопок соответствует этапам процесса. Метод `ОбновитьКнопки` (строки 2280-2343) переключает доступность кнопок по текущему состоянию регистрации:

```
  КНОПКА АРМ              СОСТОЯНИЕ              БЛОКИРОВКА ВЛИЯЕТ?
  ─────────               ─────────              ──────────────────
  1. Редактировать        (любое)                Нет
  2. Въезд                Прибыл                 Нет
  3. Номер пробы          ГотовКОтборуПроб       Нет
  4. Принять пробы        ВзятыПробы             Нет
  5. Анализ               ПринятыПробы /         Нет (создание ЛА)
                          РезультатыПробПолучены  Но ЛА ТРИГГЕРИТ блокировку!
  6. На разгрузку         КачествоПринято /       ДА — КЛЮЧЕВАЯ ТОЧКА
                          КачествоНеПринято       Block/Warn/OK проверка
  7. Разгрузка            ВыгрузкаРазрешена      Нет (уже прошёл проверку)
  8. Отменить разрешение  ВыгрузкаРазрешена      Нет
  9. Выезд                Погружен/Выгружен      Нет
  10. Приемка             (финальное)             Нет
```

### 7.3 Точки влияния блокировки в жизненном цикле

#### Точка 1: Результаты анализа — ТРИГГЕР блокировки (этап 5 "Анализ")

Когда оператор создаёт и проводит `гкс_ЛабораторныйАнализ` из АРМ:
- Если результаты отклоняются от настроек усиленного контроля → создаются записи блокировки
- В колонке **"УК"** (усиленный контроль) появляется иконка ⚠ у заблокированных ТС
- Блокируется не только текущее ТС, но и все последующие ТС в группе поставщика

#### Точка 2: Направление на разгрузку — GATE (этап 6 "На разгрузку")

Метод `РедактироватьНаправлениеНаРазгрузку` (строки 374-413):

```
Пользователь нажимает "На разгрузку"
  │
  ├─ Одиночная регистрация:
  │     РезультатБлокировки = ПроверитьБлокировкуДляСозданияНнР()
  │       │
  │       ├─ ЕстьБлокировка = Истина → СТОП: сообщение, кнопка заблокирована
  │       ├─ ЕстьПредупреждение = Истина → Вопрос "Да/Нет"
  │       │     ├─ Да → ОткрытьФормуНаправленияНаРазгрузку()
  │       │     └─ Нет → отмена
  │       └─ Нет блокировок → ОткрытьФормуНаправленияНаРазгрузку()
  │
  └─ Групповая обработка:
        КонтрольВыбранныхПоСостоянию(ВалидныеСостояния) → проверка
        Форма "ГрупповоеНаправлениеНаРазгрузку"
```

#### Точка 3: Отображение причины блокировки (панель "Детали")

Регион `ИнформацияОБлокировке` (строки 3899-4001) — **программно** создаётся при `ПриСозданииНаСервере`:

- `СоздатьЭлементыБлокировкиНаСервере()` — создаёт группу, декорацию (красный текст), гиперссылку на блокирующий ЛА
- Управляется ФО `гкс_ИспользоватьЗаблокированныеТС` — если выключена, элементы не создаются
- `ЗаполнитьИнформациюОБлокировке(ДокументРегистрации)` — при выборе строки в таблице вызывает `гкс_ВходнойКонтрольКачества.ПолучитьПричинуБлокировкиДляДеталей()` и показывает:
  - Текст причины блокировки (красный цвет)
  - Гиперссылка на блокирующий `гкс_ЛабораторныйАнализ` (клик открывает документ)

#### Точка 4: Пропуск контроля качества

Кнопка `ПропуститьКонтрольКачества` (строки 838-873):
- Видимость: только ЖД перевозка + ФО `гкс_ИспользоватьОтключениеВходногоКонтроляКачества`
- Доступность: роль `гкс_ПриемкаТранспортаБезВходногоКонтроля_ДобавлениеИзменение`
- Только для состояния `ГотовКОтборуПроб`
- Создаёт запись в РС `гкс_ПриемкаТранспортаБезВходногоКонтроля` и НнР

#### Точка 5: Доступность кнопки "На разгрузку" по состоянию

Для состояния `КачествоНеПринято` (строки 2121-2141):
```
Элементы.РедактироватьНаправлениеНаРазгрузку.Доступность =
    ДоступностьКнопкиНаправлениеНаРазгрузку(Регистрация, СтруктураДоступов)
```
Вызывает `НаправлятьНаРазгрузкуРазрешение` на сервере — проверяет наличие блокировок.

### 7.4 Архитектура взаимодействия АРМ с блокировками

```
  АРМ гкс_ПриемкаТранспорта (ОсновнаяФорма, 4002 строки)
  ════════════════════════════════════════════════════════
  │
  │ ИНИЦИИРУЕТ (кнопки правой панели)
  ├─► "На разгрузку" → РедактироватьНаправлениеНаРазгрузку()
  │     └─► гкс_ПриемкаТранспортаВызовСервера.ПроверитьБлокировкуДляСозданияНнР()
  │           └─► гкс_ВходнойКонтрольКачества.ПроверитьБлокировкуДляСозданияНнР()
  │                 └─► РС гкс_ЗаблокированныеРегистрацииУсиленныйКонтроль (чтение)
  │
  ├─► "Пропустить контроль" → ПропуститьКонтрольКачества()
  │     └─► гкс_ПриемкаТранспорта.ЗаписатьРегистрПриемкиБезВходногоКонтроля()
  │           └─► РС гкс_ПриемкаТранспортаБезВходногоКонтроля (запись)
  │
  │ ОТОБРАЖАЕТ (панель деталей)
  ├─► При выборе строки → ЗаполнитьИнформациюОБлокировке()
  │     └─► гкс_ВходнойКонтрольКачества.ПолучитьПричинуБлокировкиДляДеталей()
  │           ├─► Красный текст: причина блокировки
  │           └─► Гиперссылка: блокирующий ЛабораторныйАнализ
  │
  │ УПРАВЛЯЕТ (state machine, 13 состояний)
  └─► ОбновитьКнопки() → по текущему состоянию регистрации:
        ├─► КачествоНеПринято → кнопка "На разгрузку" доступна условно
        ├─► КачествоПринято → кнопка "На разгрузку" доступна
        └─► ВыгрузкаРазрешена → кнопка "Разгрузка" доступна (блокировка пройдена)
```

## 11. Две цепочки обработки качества: Приёмка и Заблокированные ТС

Функционал усиленного контроля работает в **двух принципиально разных цепочках**, каждая из которых оперирует своим набором показателей из лабораторного анализа.

### 11.1 Описание цепочек

| # | Цепочка | Когда срабатывает | Какие показатели анализируются | Результат |
|---|---------|-------------------|-------------------------------|-----------|
| **1** | **Приёмка** | ЛА с назначением «Приёмка» завершён для текущего ТС | **Все** показатели качества ЛА (без фильтра по `УсиленныйКонтроль`) | Определяет общий статус качества; если все показатели не приняты → `ПробыНеТребуются`, композит не нужен |
| **2** | **Заблокированные ТС** | Работа с ТС, заблокированными по результатам первого ТС или группы | **Только** показатели усиленного контроля (`УсиленныйКонтроль = Истина`) | Разблокировка конкретного показателя ИЛИ создание индивидуальных показателей для заблокированного ТС |

### 11.2 Принцип разделения

**Цепочка 1 (Приёмка)** — система оценивает ЛА в целом. Если входной контроль (все обычные показатели) не пройден, то усиленный контроль не имеет смысла — ТС разворачивается на этапе приёмки.

**Цепочка 2 (Заблокированные)** — система работает адресно с конкретным показателем усиленного контроля. Здесь анализируются только те показатели, которые помечены как `УсиленныйКонтроль = Истина`, потому что задача — разблокировать конкретный показатель или назначить дополнительные пробы.

### 11.3 Реализация разделения в коде

| Метод | Фильтр | Цепочка | Назначение |
|-------|--------|---------|------------|
| `СтатусКачестваЛабораторногоАнализа()` (строка 472) | Динамический через параметр `ТипКонтроляКачества` | Обе | Поддерживает оба режима: передаётся `УсиленныйКонтроль` → фильтр по УК; не передаётся → все показатели |
| `РезультатУсиленногоКонтроляЛабораторногоАнализаПострочно()` (строка 546) | Фиксированный: `И КП.УсиленныйКонтроль` (строка 566) | Только цепочка 2 | Используется исключительно для заполнения показателей УК (строка 78) и эскалации правил (строка 310) |
| Запрос определения `СоответствуетНормативу` (строка 840) | `И НЕ КП.УсиленныйКонтроль` | Цепочка 1 | Оценивает общий результат приёмки: смотрит только обычные показатели |
| Пакет 9 «ТС не прошедшие входной контроль» (строки 1748, 1762) | `КП.УсиленныйКонтроль = ЛОЖЬ И КП.СоответствуетНормативу = ЛОЖЬ` | Цепочка 1 | Определяет ТС, у которых обычный входной контроль не пройден — для таких ТС индивидуальные показатели УК не создаются |
| Пакет 1 «Причина блокировки» (строка 2168) | `И (НЕ КП.УсиленныйКонтроль)` | Цепочка 1 | Отображение причины блокировки в деталях АРМ — по обычным показателям |

### 11.4 Поведение при комбинации правил ГруппыТС + КаждоеТС

Когда для одного поставщика/номенклатуры одновременно действуют правила **ГруппыТС** и **КаждоеТС**, в ЛА формируются показатели обоих типов. Важно, чтобы в цепочке 1 (Приёмка) запрос видел **все** показатели, а не только показатели одного типа.

**Пример.** Поставщик «Альфа», номенклатура «Продукт А», показатели: ГМО (правило ГруппыТС) + Влажность (правило КаждоеТС).

- При проведении ЛА приёмки для ТС поставщика «Альфа» в ТЧ `КачественныеПоказатели` окажутся строки и с флагом `УсиленныйКонтроль = Истина` (для ГМО), и без флага (для Влажности, если это обычный показатель).
- Цепочка 1 должна оценить общий статус приёмки по **всем** строкам — независимо от флага `УсиленныйКонтроль`.
- Цепочка 2 (если ТС заблокировано) будет работать адресно только с показателями усиленного контроля.

### 11.5 Метод `РезультатУсиленногоКонтроляЛабораторногоАнализаПострочно` (строка 546)

Метод возвращает построчные результаты показателей усиленного контроля. Фильтр `УсиленныйКонтроль` на строке 566 — фиксированный. Вызывается из двух мест:

| Вызов | Метод | Контекст |
|-------|-------|----------|
| Строка 78 | `ЗаполнитьРегистрПоказателейУсиленногоКонтроляЛабАнализом` | Заполнение РС показателей УК при проведении ЛА — работает только с данными усиленного контроля |
| Строка 310 | `ОбработкаОтклоненияПоКачествуУсиленногоКонтроля` | Эскалация: получает показатели с `ОтклонятьКачество = Истина` для изменения правил на КаждоеТС |

Оба вызова относятся к цепочке 2 (работа с усиленным контролем), поэтому фиксированный фильтр оправдан.

## 12. Сценарии работы при комбинации правил ГруппыТС + КаждоеТС

### 12.1 Исходные условия (гипотетический пример)

Типы правил усиленного контроля описаны в разделе 2.8.3. Для сценариев ниже используется следующая конфигурация:

- Поставщик: «Альфа»
- Номенклатура: «Продукт А»
- Показатель: Показатель_1 (например, ГМО)
- Настройки усиленного контроля — **два правила одновременно**:
  - Правило А: `ТипКонтроля = ГруппыТС`, `КоличествоТС = 2`
  - Правило Б: `ТипКонтроля = КаждоеТС`

### 12.2 Сценарий 1: Приёмка, качество не принято у первого ТС

| Шаг | Действие | Что происходит в системе |
|-----|---------|--------------------------|
| 1 | Регистрация **ТС-А** (первое ТС поставщика «Альфа» за сутки) | РС `ТранспортныеСредстваПоставщикаУК`: ЭтоПервоеТС = Истина. РС `ПоказателиУК`: по 2 записи на Показатель_1 (от правила А и правила Б) |
| 2 | ФНП + ЛА(Приёмка) для **ТС-А**: результат **КачествоНеПринято** | Эскалация: оба правила (А и Б) переключаются на `КаждоеТС`. Для композитных показателей устанавливается `ПробыНеТребуются` |
| 3 | Регистрация **ТС-Б** (второе ТС поставщика «Альфа») | Группа создаётся (Справочник `гкс_ГруппыТС`), **ТС-Б** привязывается к группе. Показатели: единичный + промежуточный композит |
| 4 | ФНП + ЛА(Приёмка) для **ТС-Б**: результат **КачествоНеПринято** | **ТС-Б** НЕ блокируется (блокировка не формируется, т.к. правила уже эскалированы на КаждоеТС на шаге 2). Для композитных показателей ТС-Б устанавливается `ПробыНеТребуются`. НнР НЕ формируется |

### 12.3 Сценарий 2: Приёмка, качество принято у первого ТС

| Шаг | Действие | Что происходит в системе |
|-----|---------|--------------------------|
| 1 | Регистрация **ТС-А** | Аналогично сценарию 1, шаг 1 |
| 2 | ЛА(Приёмка) для **ТС-А**: результат **КачествоПринято** | НнР формируется автоматически. Правила НЕ эскалируются — оба правила остаются (ГруппыТС + КаждоеТС) |
| 3 | Регистрация **ТС-Б** | Группа создаётся, **ТС-Б** привязывается |
| 4 | ЛА(Приёмка) для **ТС-Б**: результат **КачествоПринято** | НнР формируется, блокировки нет |

### 12.4 Сценарий 3: Заблокированное ТС — разблокировка по усиленному контролю

| Шаг | Действие | Что происходит в системе |
|-----|---------|--------------------------|
| 1-3 | Как в сценарии 1: **ТС-А** не принято, **ТС-Б** заблокировано | РС `ЗаблокированныеРегистрацииУК`: запись для ТС-Б (Разблокировано = Ложь) |

### 12.5 Сценарий 4: Заблокированное ТС — качество не принято, создание индивидуальных показателей

| Шаг | Действие | Что происходит в системе |
|-----|---------|--------------------------|
| 1-3 | Как в сценарии 1: **ТС-А** не принято, **ТС-Б** заблокировано | — |
| 4 | ЛА(УсиленныйКонтроль) для **ТС-Б**: результат **КачествоНеПринято** | `ПробыНеТребуются` для композитных показателей. Если ТС-Б прошёл обычный входной контроль → создаются индивидуальные показатели (`Единичная` / `ПромежуточныйКомпозит`) с данными первого ТС (Мин, Макс, Базис). Если обычный входной контроль НЕ пройден → индивидуальные показатели НЕ создаются |

### 12.6 Ключевые различия между цепочками в сценариях

| Аспект | Цепочка «Приёмка» (сценарии 1-2) | Цепочка «Заблокированные» (сценарии 3-4) |
|--------|----------------------------------|------------------------------------------|
| Какие показатели анализируются | Все (обычные + усиленный контроль) | Только `УсиленныйКонтроль = Истина` |

## 17. Уточнение логики блокировки: Block только при отсутствии единичного анализа

> Источник: совещание 2026-03-12

### 17.1 Принцип

Метод `ПроверитьБлокировкуДляСозданияНнР` (раздел 4.1) реализует трёхуровневую проверку. Из разговора уточнены **точные условия** каждого уровня для заблокированных ТС:

| Уровень | Условие | Действие |
|---------|---------|----------|
| **Block** (полная блокировка) | `БлокирующееСостояниеКачества = КачествоНеПринято` **И** единичный анализ по усиленному контролю (`ПромежуточныйКомпозит` / `Единичная`) **НЕ выполнен** (состояние пустое или `ОтборПроб`) | НнР запрещено. Пользователю выводится сообщение: необходимо выполнить анализ по усиленному контролю |
| **Warn** (предупреждение) | Любое из: (1) `БлокирующееСостояниеКачества = РезультатыПробПолучены`; (2) `КачествоНеПринято`, но единичный анализ **выполнен** (с любым результатом — даже НеПринято) | НнР разрешено после подтверждения пользователем (вопрос Да/Нет) |
| **OK** | Нет активных блокировок ИЛИ все разблокированы | НнР формируется без ограничений |

### 17.2 Ключевое уточнение

Критерий перехода от Block к Warn — **наличие** единичного анализа, а **не его результат**. Даже если единичный анализ показал `КачествоНеПринято`, пользователю разрешается создать НнР с предупреждением. Логика:

- Пользователям необходимо оставить возможность принять качество вручную через НнР (аналогично тому, как при непринятом входном контроле НнР всё равно доступно)
- Полная блокировка нужна только чтобы направить пользователя выполнить обязательный анализ по усиленному контролю

### 17.3 Определение «единичный анализ выполнен»

Анализ считается **выполненным**, если в РС `гкс_ПоказателиУсиленногоКонтроляПоРегистрации` для данной регистрации есть запись с:
- `НазначениеИспользования = ПромежуточныйКомпозит`
- `ТипПробы = Единичная`
- `СостояниеКачества` содержит **финальное** значение

Три **финальных** состояния качества:
- `КачествоПринято`
- `КачествоНеПринято`
- `РезультатыПробПолучены`

Состояния, при которых анализ считается **НЕ выполненным** (Block):
- Пустое значение (запись создана, но анализ не проведён)
- `ОтборПроб` (пробы отобраны, результаты ожидаются)

### 17.4 Гипотетический пример

Поставщик «Дельта», три ТС заблокированы первым ТС. У первого ТС качество по усиленному контролю `КачествоНеПринято`. Система создала индивидуальные показатели для каждого заблокированного ТС:

| Заблокированное ТС | Единичный анализ | Состояние | Уровень проверки | Доступность НнР |
|---------------------|------------------|-----------|-----------------|-----------------|
| **ТС-А** | Не выполнен | Пустое | **Block** | Запрещено. Сообщение: «Необходимо выполнить анализ по усиленному контролю» |
| **ТС-Б** | Выполнен | КачествоНеПринято | **Warn** | Вопрос «ТС заблокировано. Продолжить создание НнР?» |
| **ТС-В** | Выполнен | КачествоПринято | **Warn** | Вопрос (т.к. блокирующее состояние ещё активно). После разблокировки → OK |

### 17.5 Информационные сообщения

| Ситуация | Сообщение пользователю | Цель |
|----------|----------------------|------|
| Block (нет анализа) | «ТС заблокировано. Необходимо выполнить анализ по усиленному контролю для продолжения» | Направить пользователя на создание ЛА |
| Warn (анализ есть) | «ТС заблокировано. Продолжить создание направления на разгрузку?» | Дать возможность принять качество вручную |

## 18. Разделение состояния регистрации и состояния качества

> Источник: совещание 2026-03-12

### 18.1 Принцип

Состояние регистрации ТС (`гкс_СостоянияРегистрации`) и состояние качества показателя (`гкс_СостоянияКачества`) — это **два разных атрибута**, которые могут изменяться независимо:

- **Состояние регистрации** — отражает позицию ТС в жизненном цикле АРМ (от въезда до приёмки)
- **Состояние качества** — отражает результат лабораторного анализа по конкретному показателю

### 18.2 Проблема пересечения

При работе с заблокированными ТС состояние регистрации может меняться несколько раз:

1. Входной контроль принят → состояние регистрации = `КачествоПринято`
2. ТС заблокировано (блокирующий ЛА не пройден) → состояние регистрации переписывается на `КачествоНеПринято`
3. Блокирующий ЛА принят → состояние возвращается к `КачествоПринято`

Это создаёт путаницу: состояние `КачествоНеПринято` в регистрации может означать как «входной контроль не принят», так и «заблокировано по усиленному контролю».

### 18.3 Решение: использование `ПробыНеТребуются`

Для разделения этих ситуаций используется состояние качества `ПробыНеТребуются` в РС `гкс_ПоказателиУсиленногоКонтроляПоРегистрации`:

| Ситуация | Состояние качества в показателях | Значение |
|----------|--------------------------------|----------|
| Приёмка не выполнена | Пустое | Анализ ещё не проводился |
| Входной контроль не принят | `ПробыНеТребуются` | Усиленный контроль не нужен — ТС отклоняется на этапе приёмки |
| Входной контроль принят, но заблокировано | Показатели записаны с актуальным состоянием | Ожидание результата блокирующего анализа |
| Композитный анализ не нужен (эскалация) | `ПробыНеТребуются` | Правила сменились на КаждоеТС, групповой композит больше не требуется |

Это позволяет отсечь ТС с `ПробыНеТребуются` при формировании композитных анализов — они не должны попадать в групповые пробы.

## 14. Последовательная зависимость групп (принцип каскадной разблокировки)

> Источник: совещание 2026-03-20 (GKSTCPLK-2257)

### 14.1 Принцип

Группы ТС связаны **последовательно** через реквизит `ПредыдущаяГруппа` справочника `гкс_ГруппыТС`. Разблокировка передаётся **строго по цепочке** — каждая группа может быть разблокирована только результатом анализа **непосредственно предыдущей** группы или первого ТС.

```
Первое ТС поставщика
  │
  │ результат ЛА первого ТС
  ▼
Группа 1 (ПредыдущаяГруппа = пусто)
  │
  │ композитный анализ группы 1
  ▼
Группа 2 (ПредыдущаяГруппа = Группа 1)
  │
  │ композитный анализ группы 2
  ▼
Группа 3 (ПредыдущаяГруппа = Группа 2)
  │
  ...
```

**Важно**: Первое ТС НЕ может напрямую разблокировать группу 2 или группу 3. Каждое звено цепочки зависит только от непосредственно предшествующего.

### 14.2 Гипотетический пример

Поставщик «Бета», номенклатура «Продукт Б», правило «ГруппыТС» с КоличествоТС = 2.

За производственные сутки поступает 7 ТС:

| ТС | Роль | Группа | Зависит от |
|----|------|--------|-----------|
| ТС-1 | Первое ТС поставщика | — | — |
| ТС-2 | В группе 1 | Группа 1 | Первое ТС (ТС-1) |
| ТС-3 | В группе 1 | Группа 1 | Первое ТС (ТС-1) |
| ТС-4 | В группе 2 | Группа 2 | Группа 1 |
| ТС-5 | В группе 2 | Группа 2 | Группа 1 |
| ТС-6 | В группе 3 | Группа 3 | Группа 2 |
| ТС-7 | В группе 3 | Группа 3 | Группа 2 |

**Цепочка разблокировки:**

1. ЛА(Приёмка) первого ТС завершён → **ТС-2 и ТС-3** могут быть разблокированы (если качество принято)
2. Композитный ЛА группы 1 завершён → **ТС-4 и ТС-5** могут быть разблокированы
3. Композитный ЛА группы 2 завершён → **ТС-6 и ТС-7** могут быть разблокированы

ТС-1 НЕ может разблокировать ТС-4..ТС-7 напрямую. Группа 1 НЕ может разблокировать ТС-6, ТС-7.

### 14.3 Верификация в базе TestDB

Верификация: в базе TestDB подтверждена цепочка группа:1→группа:2→группа:3 (см. раздел 13).

## 15. Два независимых механизма при проведении лабораторного анализа

> Источник: совещание 2026-03-20 (GKSTCPLK-2257)

### 15.1 Описание

При проведении документа `гкс_ЛабораторныйАнализ` срабатывают **два независимых механизма**:

| # | Механизм | Что делает | Условие срабатывания |
|---|----------|-----------|---------------------|
| **1** | Обработка текущей регистрации | Оценивает качество текущего ТС, определяет статус (Принято / НеПринято / РПП), формирует НнР при положительном результате | Всегда при проведении ЛА с назначением «Приёмка» или «Единичный композит» |
| **2** | Обработка заблокированных ТС | Ищет, какие ТС были заблокированы текущим документом (как первым ТС или как группой). Если находит — обновляет состояние блокировки | Только если текущий ЛА является блокирующим для других ТС (первое ТС поставщика или композит группы) |

### 15.2 Независимость механизмов

Механизмы работают **последовательно, но независимо**:

1. Сначала выполняется механизм 1 — записываются показатели, определяется качество
2. Затем выполняется механизм 2 — проверяется, заблокировал ли этот ЛА что-то, и если да — обновляет состояние заблокированных ТС

Результат механизма 1 (качество текущего ТС) влияет на механизм 2 (какое состояние записать заблокированным ТС), но сам механизм 2 не влияет на текущую регистрацию.

### 15.3 Гипотетический пример

Поставщик «Гамма», первое ТС-1, заблокировано ТС-2:

1. **Механизм 1**: Проводится ЛА(Приёмка) для ТС-1 → качество НеПринято → НнР НЕ формируется, состояние ТС-1 = КачествоНеПринято
2. **Механизм 2**: Система проверяет: «Заблокировал ли ТС-1 кого-то?» → Да, ТС-2. Состояние качества ТС-1 = НеПринято → записывает в РС `ЗаблокированныеРегистрацииУК` для ТС-2: `БлокирующееСостояниеКачества = НеПринятоВходнойКонтроль`. Создаёт индивидуальные показатели для ТС-2.

Если бы качество ТС-1 было КачествоПринято:
- Механизм 2 записал бы `Разблокировано = Истина` для ТС-2
- Состояние регистрации ТС-2 обновилось бы на КачествоПринято
- НнР для ТС-2 сформировалось бы автоматически

## 16. Обработка смешанных результатов в группе

> Источник: совещание 2026-03-20 (GKSTCPLK-2257)

### 16.1 Принцип

Когда группа ТС заблокирована и анализ первого ТС (или предыдущей группы) завершён, каждое заблокированное ТС в группе обрабатывается **индивидуально** в зависимости от комбинации двух факторов:
- Состояние качества по **усиленному контролю** (из результата блокирующего ЛА)
- Состояние **входного контроля** самого заблокированного ТС (если ЛА приёмки уже был выполнен)

### 16.2 Матрица решений для заблокированного ТС

| Состояние УК блокирующего ЛА | Входной контроль заблокированного ТС | Результат |
|------------------------------|--------------------------------------|-----------|
| **КачествоПринято** | Принят | Разблокировка + НнР формируется автоматически |
| **КачествоПринято** | НеПринят | Разблокировка + НнР НЕ формируется (качество не принято по входному контролю) |
| **КачествоПринято** | Не выполнен | Разблокировка + НнР НЕ формируется (ожидание ЛА приёмки) |
| **КачествоНеПринято** | Принят | Остаётся заблокировано. `ПробыНеТребуются` для композита. Создаются индивидуальные показатели (Единичная / ПромежуточныйКомпозит) |
| **КачествоНеПринято** | НеПринят | Остаётся заблокировано. `ПробыНеТребуются` для композита. Индивидуальные показатели **НЕ создаются** (входной контроль уже не пройден) |
| **РезультатыПробПолучены** | Любой | Остаётся заблокировано. Требуется ручное решение (ДопАнализ или ручная приёмка через НнР) |

### 16.3 Гипотетический пример

Группа из 3 ТС (ТС-А, ТС-Б, ТС-В), заблокированных первым ТС поставщика. ЛА приёмки для каждого из трёх уже выполнен:

| ТС | Входной контроль | Что произойдёт при разблокировке (КачествоПринято по УК) | Что произойдёт при НеПринято по УК |
|----|-----------------|-------------------------------------------------------|----------------------------------|
| **ТС-А** | Принят | Разблокировка → НнР формируется | Остаётся заблокировано → индивидуальные показатели |
| **ТС-Б** | НеПринят | Разблокировка → НнР НЕ формируется | Остаётся заблокировано → индивидуальные показатели НЕ создаются |
| **ТС-В** | РезультатыПробПолучены | Разблокировка → НнР НЕ формируется | Остаётся заблокировано → ручное решение |

Каждое ТС обрабатывается **отдельно** — даже если группа целиком разблокируется, НнР формируется только для тех ТС, у которых входной контроль принят.

### 16.4 Цепочка после создания индивидуальных показателей

Когда для заблокированного ТС создан **единичный анализ по усиленному контролю** (ТипПробы = Единичная, Назначение = ПромежуточныйКомпозит):

```
ТС заблокировано, КачествоНеПринято по УК
  │
  │ Создаются индивидуальные показатели
  ▼
ЛА(УсиленныйКонтроль) для заблокированного ТС
  │
  ├── КачествоПринято + ВходнойКонтроль принят → НнР
  ├── КачествоПринято + ВходнойКонтроль НЕ принят → НнР НЕ формируется
  ├── КачествоНеПринято → Ручная приёмка через НнР
  └── РезультатыПробПолучены → Ожидание / ДопАнализ
```

### 16.5 Верификация в базе TestDB

Верификация данных — см. раздел 13.

Блокировки по каналу «Группа ТС»: 5 записей (группы 1 и 2), из них 2 разблокированы, 3 активные.

## 19. Условие блокировки: только факт выполнения анализа, не качество

> Источник: совещание 2026-03-12 (15:18)

### 19.1 Принцип

При проведении регистрации ТС система определяет, нужно ли блокировать это ТС. Решение принимается на основании **факта выполнения** лабораторного анализа первого ТС (или предыдущей группы), а **не на основании качества** этого анализа.

| Состояние ЛА первого ТС | Статус в показателях | Блокировать последующие ТС? | Почему |
|--------------------------|---------------------|-----------------------------|--------|
| Не проведён | Пустое | **Да** | Результат неизвестен — последующие ТС ждут |
| Пробы отобраны, результат ожидается | `ОтборПроб` | **Да** | Результат ещё не готов |
| Выполнен, качество принято | `КачествоПринято` | **Нет** | Результат получен — блокировка не нужна |
| Выполнен, качество не принято | `КачествоНеПринято` | **Нет** | Результат получен, правила эскалируются на «КаждоеТС» → последующие ТС пойдут по индивидуальному правилу |
| Выполнен, результаты получены | `РезультатыПробПолучены` | **Нет** | Результат получен — решение по качеству принимается отдельно |

### 19.2 Реализация в коде

Метод `ТребуетсяБлокировкаПервоеТС()` (строки 2480-2486):

```bsl
Функция ТребуетсяБлокировкаПервоеТС(ЕстьПервоеТСДругойРегистрации, СостояниеКачества)
    Возврат ЕстьПервоеТСДругойРегистрации
        И (СостояниеКачества = Перечисления.гкс_СостоянияКачества.ОтборПроб
            ИЛИ СостояниеКачества = Перечисления.гкс_СостоянияКачества.ПустаяСсылка());
КонецФункции
```

Два условия:
1. Существует первое ТС другой регистрации (текущее ТС — не первое)
2. Состояние качества первого ТС — `ОтборПроб` или пустое (анализ не завершён)

### 19.3 Связь с эскалацией правил

Почему качество `КачествоНеПринято` у первого ТС **не приводит** к блокировке последующих:

1. ЛА первого ТС завершается с `КачествоНеПринято`
2. Метод `ОбработкаОтклоненияПоКачествуУсиленногоКонтроля()` переключает правила с `ПервоеТС` / `ГруппыТС` на `КаждоеТС`
3. Следующее ТС при регистрации обнаруживает правило `КаждоеТС` → пропускается на строке 242 (`Продолжить`) → блокировка не создаётся
4. Это ТС проходит индивидуальный анализ по усиленному контролю

### 19.4 Та же логика для групп

Аналогичный принцип применяется для блокировки по группам — группа блокируется, только если:
- Композитный анализ предыдущей группы **не выполнен** (статус пустой или `ОтборПроб`)
- ИЛИ ЛА первого ТС **не выполнен** (для первой группы)

Если анализ выполнен (с любым качеством) — группа не блокируется.

### 19.5 Гипотетический пример: последовательная обработка

Поставщик «Эпсилон», показатель ГМО, правило `ПервоеТС`.

**Ситуация А — анализ первого ТС ещё не готов:**

| Событие | Действие системы |
|---------|-----------------|
| ТС-1 зарегистрировано, ЛА не проведён | РС ПоказателиУК: СостояниеКачества = пустое |
| ТС-2 зарегистрировано | `ТребуетсяБлокировкаПервоеТС(Истина, ПустаяСсылка)` → **Истина** → ТС-2 заблокировано |
| ТС-3 зарегистрировано | Аналогично → ТС-3 заблокировано |

**Ситуация Б — анализ первого ТС выполнен (КачествоНеПринято):**

| Событие | Действие системы |
|---------|-----------------|
| ЛА для ТС-1 выполнен, КачествоНеПринято | Эскалация: правило → `КаждоеТС` |
| ТС-4 зарегистрировано | Правило = `КаждоеТС` → строка 242 `Продолжить` → блокировка **не создаётся** |
| ТС-4 проходит индивидуальный ЛА по УК | Показатели записываются с типом `Единичная` |

**Ситуация В — анализ первого ТС выполнен (КачествоПринято):**

| Событие | Действие системы |
|---------|-----------------|
| ЛА для ТС-1 выполнен, КачествоПринято | ТС-2 и ТС-3: `Разблокировано = Истина`, НнР формируется |
| ТС-4 зарегистрировано | `ТребуетсяБлокировкаПервоеТС(Истина, КачествоПринято)` → **Ложь** → не блокируется |

### 19.6 Верификация в коде

Метод `ТребуетсяБлокировкаПервоеТС` (строки 2480-2486) содержит только два допустимых состояния для блокировки: `ОтборПроб` и `ПустаяСсылка()`. Состояния `КачествоНеПринято` и `РезультатыПробПолучены` **отсутствуют** в условии — блокировка при них не срабатывает. Это соответствует описанному принципу.

## 20. Раннее отсечение композитных анализов при непройденном входном контроле

> Источник: совещание 2026-03-16 (11:52)

### 20.1 Принцип

Если ТС в группе не прошло входной контроль (ЛА приёмки не принят), то групповой композитный анализ для этого ТС **не имеет смысла**. Система устанавливает `ПробыНеТребуются` для композитного показателя **на этапе завершения ЛА приёмки**, а не позже при формировании композита.

Это раннее отсечение: вместо того чтобы ждать формирования группового композита и исключать ТС в момент нажатия кнопки «Сформировать», решение принимается при проведении ЛА приёмки.

### 20.2 Гипотетический пример

Поставщик «Зета», правило `ГруппыТС`, группа из 3 ТС:

| ТС | Результат приёмки | Показатель ПромежуточныйКомпозит | Попадёт в групповой композит? |
|----|-------------------|----------------------------------|------------------------------|
| **ТС-А** | КачествоПринято | Состояние сохраняется | **Да** |
| **ТС-Б** | КачествоНеПринято (входной контроль не пройден) | → `ПробыНеТребуются` | **Нет** — отсечён на этапе приёмки |
| **ТС-В** | РезультатыПробПолучены | Состояние сохраняется | **Да** |

При формировании группового композита система учтёт только ТС-А и ТС-В. ТС-Б исключено, потому что его показатель уже в состоянии `ПробыНеТребуются`.

### 20.3 Реализация в коде

Метод `ЗаполнитьРегистрПоказателейУсиленногоКонтроляЛабАнализом` (строки 195-213):

```
Если КоличествоНеПринято > 0 И ЛАНеСоответствуетНормативу:
    → УстановитьПробыНеТребуютсяДляКомпозитных(Регистрация, ПоказателиНеПринято, Композитная, ПромежуточныйКомпозит)

ИначеЕсли КоличествоНеПринято > 0 И ЛАСоответствуетНормативу:
    → ОчиститьСостояниеКачестваДляКомпозитных(Регистрация, ПоказателиНеПринято, Композитная, ПромежуточныйКомпозит)
```

Два сценария:
- Входной контроль **не пройден** (`ЛАНеСоответствуетНормативу`) → ставится `ПробыНеТребуются`
- Входной контроль **пройден** (`ЛАСоответствуетНормативу`), но были отклонения → очищается состояние (анализ нужен)

### 20.4 Независимость от функциональной опции «Заблокированные ТС»

Описанная логика (пункт 1 из разговора) работает **всегда**, независимо от значения ФО `гкс_ИспользоватьЗаблокированныеТС`. Это базовый механизм формирования показателей при проведении ЛА приёмки.

Функциональная опция `гкс_ИспользоватьЗаблокированныеТС` влияет только на:
- Проверку блокировок при создании НнР (строка 2589: выход из метода, если ФО выключена)
- Программное создание элементов блокировки в деталях АРМ

| Функционал | Зависит от ФО `ЗаблокированныеТС`? |
|-----------|-----------------------------------|
| Раннее отсечение: `ПробыНеТребуются` при непройденном входном контроле | **Нет** — работает всегда |
| Запись блокировок в РС `ЗаблокированныеРегистрацииУК` | **Нет** — работает при включённом УК |
| Проверка Block/Warn/OK при создании НнР | **Да** — только при включённой ФО |
| Отображение причин блокировки в деталях АРМ | **Да** — только при включённой ФО |
| Создание индивидуальных показателей для заблокированных ТС | **Да** — только при включённой ФО |

### 20.5 Связь с обработкой заблокированных ТС (пункт 2)

При обработке заблокированных ТС (раздел 16, `ОбновитьБлокировкуДляТС`) аналогичная логика: если заблокированное ТС не прошло входной контроль (определяется через Пакет 9 запроса), индивидуальные показатели для него **не создаются** (строки 2022-2031):

```
НеПрошелВходнойКонтроль = ТСНеПрошедшиеВходнойКонтроль <> Неопределено
    → УстановитьПробыНеТребуютсяДляКомпозитных(...)
    Если НЕ НеПрошелВходнойКонтроль Тогда
        → ДобавитьПоказателиУКДляЗаблокированногоТС(...)
    КонецЕсли
```

Оба пункта используют единый принцип: если входной контроль не пройден — дальнейшие анализы по усиленному контролю для этого ТС не нужны.

## 21. Обратимость раннего отсечения: правило «точки невозврата»

> Источник: совещание 2026-03-16 (14:16)

### 21.1 Ситуация

Оператор провёл ЛА приёмки для ТС в группе, входной контроль не принят → система записала `ПробыНеТребуются` для композитного показателя. Затем оператор исправляет ЛА (пересматривает результаты, ставит галочки обратно) и проводит повторно — входной контроль теперь принят.

**Вопрос**: Нужно ли откатить `ПробыНеТребуются` обратно в обычное состояние?

### 21.2 Правило «точки невозврата»

Откат допустим **только до** создания индивидуального анализа. Три типа анализа для регистрации образуют последовательность:

```
1. Входной контроль (Приёмка / Единичная)
    │
    ├── НеПринят → ПробыНеТребуются для п.2
    │                 │
    │                 └── ОТКАТ возможен ← если п.3 ещё НЕ существует
    │
    ▼
2. Промежуточный композит / Композитная (групповой анализ)
    │
    ├── НеПринят → создаётся п.3
    │
    ▼
3. Промежуточный композит / Единичная (индивидуальный анализ)
    │
    └── ТОЧКА НЕВОЗВРАТА: если п.3 существует,
        откат п.2 в обычное состояние НЕ допускается
```

### 21.3 Матрица решений при повторном проведении ЛА

| `ПробыНеТребуются` для композитной | Единичный анализ существует? | Действие при повторном ЛА (контроль принят) |
|-------------------------------------|-----------------------------|--------------------------------------------|
| Да | **Нет** | Очистить `ПробыНеТребуются` → вернуть пустое состояние. Композитный анализ снова нужен |
| Да | **Да** (любое качество) | **Не менять**. Процесс перешёл к индивидуальному анализу, возврат к групповому композиту не имеет смысла |

### 21.4 Обоснование

Если индивидуальный анализ уже создан, это означает:
1. Композитный анализ группы был выполнен (или признан не нужным)
2. По результатам было принято решение о необходимости индивидуальной проверки
3. Возможно, индивидуальный анализ уже выполнен с каким-то результатом

Откат к групповому композиту в этой ситуации:
- Создаёт противоречие между двумя параллельными ветками анализа
- Может привести к дублированию проверок
- Не имеет практического смысла — результат индивидуального анализа уже определяет дальнейшие действия

### 21.5 Реализация в коде

Метод `ОчиститьСостояниеКачестваДляКомпозитных` (строки 188-204 менеджера РС `гкс_ПоказателиУсиленногоКонтроляПоРегистрации`):

```bsl
Для Каждого Запись Из НаборЗаписей Цикл
    Если ПоказателиНеПринято.Найти(Запись.Показатель) <> Неопределено
        И Запись.СостояниеКачества = ПробыНеТребуются Тогда
        Запись.СостояниеКачества = ПустаяСсылка();
    КонецЕсли;
КонецЦикла;
```

Вызывается из `ЗаполнитьРегистрПоказателейУсиленногоКонтроляСостояниемКачества` (строка 208) при повторном проведении ЛА, если входной контроль теперь пройден. Проверка наличия индивидуального анализа (`ПромежуточныйКомпозит` / `Единичная`) должна выполняться перед вызовом этого метода.

### 21.6 Гипотетический пример

Поставщик «Тета», ТС-А в группе 1:

**Сценарий А — откат допустим:**

| Шаг | Событие | Состояние композитного показателя |
|-----|---------|----------------------------------|
| 1 | ЛА приёмки: входной контроль НеПринят | → `ПробыНеТребуются` |
| 2 | Оператор исправляет ЛА, повторно проводит: входной контроль Принят | Единичного анализа нет → `ПробыНеТребуются` очищается → пустое |
| 3 | Групповой композит формируется | ТС-А включается в композит |

**Сценарий Б — откат заблокирован:**

| Шаг | Событие | Состояние композитного показателя |
|-----|---------|----------------------------------|
| 1 | ЛА приёмки: входной контроль НеПринят | → `ПробыНеТребуются` |
| 2 | Система создала индивидуальный анализ | Единичная запись появилась |
| 3 | Оператор исправляет ЛА, повторно проводит | Единичный анализ существует → `ПробыНеТребуются` **не меняется** |

## 22. Привязка индивидуальных анализов к производственным суткам блокировки

> Источник: совещание 2026-02-20 (15:25)

### 22.1 Принцип

Когда система создаёт запись о необходимости индивидуального анализа (`ПромежуточныйКомпозит` / `Единичная`) для заблокированного ТС, **производственные сутки** в этой записи должны соответствовать дню, когда проблема была **зафиксирована** (когда ТС встало на блокировку), а не текущей дате создания записи.

### 22.2 Обоснование

Каждое ТС «живёт» в рамках своих производственных суток:

- ТС заехало на ПЛК в определённые производственные сутки
- Входной контроль (ФНП, ЛА приёмки) — в те же сутки
- Блокировка — фиксируется в те же сутки
- Индивидуальный анализ по усиленному контролю — должен быть привязан к тем же суткам

Если индивидуальный анализ записать с текущими сутками (например, 20-е), а ТС было зарегистрировано 10-го:
- Оператор, работающий с 11-м днём, увидит «чужое» ТС
- Нарушается принцип завершения производственных суток (аналогия с закрытием кассовой смены)
- Статистика по количеству обработанных ТС за сутки будет искажена

### 22.3 Реализация в коде

Метод `ДобавитьПоказателиУКДляЗаблокированногоТС` (менеджер РС `гкс_ПоказателиУсиленногоКонтроляПоРегистрации`, строки 128-152):

```bsl
НоваяЗапись.ДокументРегистрации = ДокументРегистрации;
НоваяЗапись.ТипПробы = Единичная;
НоваяЗапись.НазначениеИспользования = ПромежуточныйКомпозит;

// Производственные сутки определяются через точку маршрута
МестнаяДата = Справочники.гкс_ТочкиМаршрута.ПолучитьМестнуюДатуПоТочкеМаршрута(ТочкаМаршрута);
НоваяЗапись.МестнаяДата = МестнаяДата;
НоваяЗапись.ПроизводственныеСутки = гкс_ПриемкаТранспорта.ПроизводственныеСуткиПоДата(МестнаяДата);
```

Метод `ПолучитьМестнуюДатуПоТочкеМаршрута` возвращает текущую дату с учётом часового пояса точки маршрута. Затем `ПроизводственныеСуткиПоДата` преобразует её в производственные сутки (учитывая границу суток — обычно 08:00).

### 22.4 Гипотетический пример

Поставщик «Йота», ТС-А зарегистрировано **10 марта** (производственные сутки = 10.03):

| День | Событие | Производственные сутки записи |
|------|---------|------------------------------|
| 10.03 | ТС-А зарегистрировано, ФНП, ЛА приёмки | 10.03 |
| 10.03 | ТС-Б заезжает, блокируется первым ТС | 10.03 |
| 10.03 | ЛА первого ТС: КачествоНеПринято | 10.03 |
| 10.03 | Создаётся запись «нужен единичный анализ» для ТС-Б | **10.03** (дата фиксации проблемы) |
| 12.03 | Оператор выполняет единичный анализ для ТС-Б | Анализ проводится 12.03, но показатель привязан к **10.03** |

Оператор, работающий с производственными сутками 11.03, **не увидит** ТС-Б в своём списке — оно принадлежит суткам 10.03.

### 22.5 Граница производственных суток

Производственные сутки на ПЛК обычно начинаются в 08:00 утра. Метод `ПроизводственныеСуткиПоДата` учитывает эту границу:

- ЛА выполнен **10.03 в 07:55** → производственные сутки = **09.03** (ещё «вчера»)
- ЛА выполнен **10.03 в 08:01** → производственные сутки = **10.03**

На практике ситуация, когда индивидуальный анализ выполняется через несколько дней после блокировки, крайне редка — обычно всё укладывается в одни производственные сутки с небольшим лагом на границе.

### 22.6 Принцип: данные формируются только через документы

Из разговора также зафиксировано важное правило тестирования: записи в регистрах сведений должны создаваться **только через проведение документов** (ЛА, ФНП, Регистрация), а не напрямую через формы регистров. Прямая запись в регистры может:
- Нарушить целостность связей между документами и записями
- Скрыть ошибки в логике проведения документов
- Создать записи с некорректными реквизитами (например, неправильные производственные сутки)

## 23. Приоритет собственных результатов над разблокировкой предыдущей группы

> Источник: совещание 2026-03-20 (10:13)

### 23.1 Принцип «врачебной аналогии»

Разблокировка ТС происходит по результатам **предыдущего** анализа (первого ТС или предыдущей группы). Это аналогично ситуации, когда врач ставит диагноз «здоров» не по вашим анализам, а по анализам предыдущего пациента.

Однако если **собственные** результаты ТС (промежуточный композит текущей группы) уже получены и показали отклонение — они имеют **приоритет** над разблокировкой. Даже если предыдущая группа дала «добро», собственный плохой результат отменяет разрешение на разгрузку.

### 23.2 Матрица решений

| Результат предыдущей группы/первого ТС | Собственный композит текущей группы | НнР формируется? |
|----------------------------------------|-------------------------------------|-----------------|
| КачествоПринято | Не выполнен | **Да** — разблокировка по предыдущему |
| КачествоПринято | КачествоПринято | **Да** — подтверждено обоими |
| КачествоПринято | КачествоНеПринято | **Нет** — собственный результат приоритетнее |
| КачествоНеПринято | Любой | **Нет** — предыдущий не дал добро |

### 23.3 Гипотетический пример

Поставщик «Каппа», правило `ГруппыТС`, группа из 2 ТС:

| ТС | Группа | Роль |
|----|--------|------|
| ТС-1 | — | Первое ТС |
| ТС-2 | Группа 1 | Заблокировано первым ТС |
| ТС-3 | Группа 2 | Заблокировано группой 1 |

**Сценарий: разблокировка с последующей отменой**

| Шаг | Событие | Результат |
|-----|---------|-----------|
| 1 | ЛА приёмки для ТС-1, ТС-2, ТС-3: все КачествоПринято по входному | — |
| 2 | ЛА ТС-1 выполнен: КачествоПринято по УК | ТС-2 разблокировано → НнР для ТС-2 формируется автоматически |
| 3 | Промежуточный композит группы 1 выполнен: КачествоПринято | ТС-3 разблокировано → НнР для ТС-3 формируется |
| **3'** | *(альтернативный)* Промежуточный композит группы 1 выполнен: **КачествоНеПринято** | ТС-3 **НЕ** разблокировано. Даже если бы ТС-1 дал добро, собственный результат группы 1 перекрывает |

### 23.4 Значение для реализации

При проведении ЛА, который разблокирует заблокированные ТС, система должна проверять не только блокирующий статус, но и наличие собственного промежуточного композита у заблокированного ТС. Если собственный композит уже выполнен с отрицательным результатом — разблокировка не приводит к формированию НнР.

## 24. Сохранение структуры блокировок при каскадной блокировке

> Источник: совещание 2026-03-20 (10:13)

### 24.1 Принцип

Когда первое ТС не проходит усиленный контроль и блокирует все последующие группы, структура записей в РС `ЗаблокированныеРегистрацииУсиленныйКонтроль` **не переписывается**:

- Первая группа остаётся заблокированной **первым ТС** (через `БлокирующаяРегистрация`)
- Вторая группа остаётся заблокированной **первой группой** (через `БлокирующаяГруппаТС`)

Даже если первопричина блокировки — первое ТС, цепочка зависимостей сохраняется в исходном виде.

### 24.2 Обоснование

- Структура отражает **фактическую** цепочку зависимостей
- При разблокировке каждое звено цепочки разблокируется через свой индивидуальный анализ
- Переписывание `БлокирующаяГруппаТС` с «группа 1» на «первое ТС» исказило бы реальную картину зависимостей
- Для аудита важно сохранять, кто именно заблокировал каждое ТС

### 24.3 Гипотетический пример

Первое ТС не прошло УК → все три группы заблокированы:

| Запись в РС | ДокументРегистрации | БлокирующаяРегистрация | БлокирующаяГруппаТС |
|-------------|--------------------|-----------------------|--------------------|
| 1 | ТС-2 (группа 1) | Первое ТС | — |
| 2 | ТС-3 (группа 2) | — | Группа 1 |
| 3 | ТС-4 (группа 3) | — | Группа 2 |

Запись 2 **не переписывается** на `БлокирующаяРегистрация = Первое ТС`. Каждое ТС разблокирует себя через собственный единичный анализ. Композитные показатели всех групп переходят в `ПробыНеТребуются`, и для каждого заблокированного ТС создаётся индивидуальный показатель (`Единичная` / `ПромежуточныйКомпозит`).

## 25. Переориентация блока анализов в деталях АРМ на РС «Фактические показатели качества»

> Источник: совещание 2026-03-20 (10:13)

### 25.1 Текущее состояние

Блок «Анализы» в панели деталей АРМ `гкс_ПриемкаТранспорта` отображает данные из **табличной части документа** `гкс_ЛабораторныйАнализ.КачественныеПоказатели` (только входной контроль / приёмка).

### 25.2 Целевое состояние

Переориентировать источник данных на **РС** `ФактическиеПоказателиКачества`, который содержит **полную картину** по всем типам анализов:

| Тип анализа | Сейчас отображается? | После переориентации |
|-------------|---------------------|---------------------|
| Входной контроль (Приёмка / Единичная) | **Да** | Да |
| Промежуточный композит (Композитная) | **Нет** | **Да** |
| Единичный анализ после перепроверки | **Нет** | **Да** |
| Признак «Внешняя проба» | **Нет** | **Да** (при дообогащении РС) |

### 25.3 Дообогащение РС «ФактическиеПоказателиКачества»

Предложено добавить реквизит `ВнешняяПроба` (Булево) в РС, аналогично тому, как ранее был добавлен реквизит `УсиленныйКонтроль`. Источник значения — ТЧ `ЛабораторныйАнализ.КачественныеПоказатели.ВнешняяПроба`.

Цель: отображать пользователю, что конкретный показатель — результат внешней пробы (не собственная лаборатория ПЛК).

### 25.4 Ожидаемый результат

Оператор в деталях АРМ видит **все** этапы проверки качества ТС в одном блоке:
- Входной контроль с результатами
- Промежуточный композит (если применимо)
- Единичный анализ (если был создан после непринятия композита)
- Пометку «внешняя проба» для показателей из внешних лабораторий
