# GKSTCPLK-2292 Исправить ошибки: запись в РС "Заблокированные регистрации усиленный контроль"

## 1. Описание задачи

### 1.1 Требования

[REQ-1] При проведении ЛА промежуточный композит, если он **НЕ выполнен**, делать запись в РС `гкс_ЗаблокированныеРегистрацииУсиленныйКонтроль` для регистраций, заблокированных **группой** регистраций ЛА.

[REQ-2] Рефакторинг запроса `ТекстЗапросаЗаблокированныхРегистрацийУК()` — разделить логику блокировки по "Первое ТС" и "Группа ТС".

[REQ-3] Дополнительный анализ запроса `ПолучитьДанныеБлокировкиДляРегистраций()` при необходимости.

[REQ-4] Тестирование блокировки ТС по различным цепочкам.

### 1.2 Суть проблемы (подробно)

#### Бизнес-контекст

Система усиленного контроля качества работает по каскадному принципу: ТС поставщика группируются, и каждая следующая группа **заблокирована** до тех пор, пока промежуточный композит предыдущей группы не будет проанализирован. Это нужно, чтобы не допустить на разгрузку потенциально некачественное сырьё, пока не получены результаты анализа предшествующей партии.

#### Пример на реальных данных (TestDB)

Поставщик **ТЕРРА АЛЬЯНС**, 18.03.2026, Рапс. Правило: **ГруппыТС** (по 2 ТС в группе).

```
ТМУТ-0000005 (ПервоеТС поставщика)
    │
    ▼
группа:1 ──── ТМУТ-0000007  (заблокировано первым ТС ✓)
    │
    ▼
группа:2 ──── ТМУТ-0000006  (заблокировано группой:1 ✓)
    │
    ▼
группа:3 ──── (будущие ТС)  ← должны блокироваться группой:2
```

**Сценарий ошибки**: Оператор создаёт ЛА промежуточного композита для группы:2 (ТМУТ-0000006). Проводит документ, но статус ещё **НЕ "Выполнен"** — пробы отобраны, но лаборатория ещё не завершила анализ. В этот момент ТС из группы:3 **должны быть заблокированы** (результат группы:2 не известен), но **НЕ блокируются** — их можно направить на разгрузку без контроля.

#### Техническая причина: один guard на два разных бизнес-правила

При проведении ЛА вызывается цепочка проверок:

```
ОбработкаПроведения (ObjectModule.bsl:139)
  └─ СформироватьВспомогательныеДанныеДляЗаблокированныхТС(Отказ) :153
       └─ guard: ТребуетсяЗаблокированныеТСЛабАнализа() :685
            └─ ТребуетсяУсиленныйКонтрольЛабАнализа() :671
                 │
                 │  Возврат
                 │    ФО("гкс_ИспользоватьУсиленныйКонтрольКачества")  ← OK
                 │    И Статус = Выполнен  ← ❌ БЛОКИРУЕТ ВЕСЬ ПУТЬ
                 │    И ЭтоПриемкаПромежуточныйКомпозит()              ← OK
```

Проверка `Статус = Выполнен` (строка 675) **правильна** для одного сценария, но **ошибочна** для другого:

| Сценарий | Нужен `Статус = Выполнен`? | Почему |
|----------|---------------------------|--------|
| **"Первое ТС"** — запись блокировки на основании РЕЗУЛЬТАТА анализа первого ТС | **Да** — нужен конкретный результат (Принято/НеПринято) | Блокировка создаётся по РЕЗУЛЬТАТУ анализа: если первое ТС не прошло — блокируем последующие |
| **"Группа ТС"** — запись блокировки следующей группы, потому что текущая ещё не проанализирована | **Нет** — блокировка нужна ДО результата | Блокировка создаётся по ФАКТУ существования незавершённого анализа: сам факт, что группа ещё анализируется, блокирует следующую |

Один guard `Статус = Выполнен` обслуживает оба сценария, но подходит только первому. Для второго он является чрезмерно строгим — отсекает запись блокировки по группе, когда она как раз больше всего нужна.

#### Что происходит при `Статус ≠ Выполнен`

Когда guard возвращает `ЛОЖЬ`, **вся ветвь пропускается целиком**:

```
Если Не ТребуетсяЗаблокированныеТСЛабАнализа() Тогда  ← Ложь при Статус ≠ Выполнен
    Возврат;  ← ❌ ВЫХОД — ничего не делаем
КонецЕсли;

// Весь код ниже НЕ выполняется:
// - ЗаписатьБлокировкуГруппыТС() — НЕ вызывается
// - ОбновитьЗаблокированныеТСПриЗавершенииЛА() — НЕ вызывается
// - ЗаписатьБлокировкуТС() — НЕ вызывается
```

Записи блокировки для следующей группы не создаются. ТС из следующей группы выглядят "свободными" в АРМ Приёмки и могут быть направлены на разгрузку.

#### Суть исправления

Разделить единый путь на два **независимых**, каждый со своим guard:

```
ОбработкаПроведения
  │
  ├─ ПУТЬ 1: "Первое ТС" + обновление существующих блокировок
  │   guard: Статус = Выполнен (оставляем как есть)
  │   → результат анализа известен → записываем/обновляем блокировки
  │
  └─ ПУТЬ 2: "Группа ТС" — НОВЫЙ
      guard: ЭтоПромежуточныйКомпозит() БЕЗ проверки Статус
      → факт проведения ЛА → блокируем следующую группу
```

При `Статус = Выполнен` работают ОБА пути (Путь 1 для результата + Путь 2 для группы). При `Статус ≠ Выполнен` работает ТОЛЬКО Путь 2 (группа блокируется, результат ещё не записывается). Дубликатов не будет — `ДобавитьЗаписьБлокировки` использует набор записей с отбором по всем измерениям и перезаписывает существующую запись.

#### Дополнительно обнаруженные ошибки

- **Логическая ошибка** в `ГруппаТСТребуетБлокировки()` — условие `Или` вместо `И` делает проверку состояния качества группы **всегда истинной** (тавтология `X<>A Или X<>B`). Из-за этого блокировка атрибутируется группе даже когда результат группы уже известен (КачествоНеПринято), вместо того чтобы перейти к проверке "Первое ТС".
- **Ошибка дедупликации** в `ДобавитьЗаблокированноеВГруппыРегистрации()` — при N существующих записях добавляется N дубликатов новой записи вместо одной (добавление внутри цикла проверки).

### 3.3 Ошибка 1 (основная): guard слишком строгий [REQ-1]

**Файл**: `CommonModules/гкс_ВходнойКонтрольКачества/Ext/Module.bsl`

#### Цепочка guard-условий (строки 671-693)

```bsl
// ObjectModule.bsl:671
Функция ТребуетсяУсиленныйКонтрольЛабАнализа()
    Возврат
        ПолучитьФункциональнуюОпцию("гкс_ИспользоватьУсиленныйКонтрольКачества")
        И Статус = Перечисления.гкс_СтатусыЛабораторногоАнализа.Выполнен  // ← ПРОБЛЕМА
        И ЭтоПриемкаПромежуточныйКомпозит();

// ObjectModule.bsl:685
Функция ТребуетсяЗаблокированныеТСЛабАнализа()
    Если Не ПолучитьФункциональнуюОпцию("гкс_ИспользоватьЗаблокированныеТС") Тогда
        Возврат Ложь;
    КонецЕсли;
```

#### Кто использует guard

Три процедуры зависят от этого guard-условия, и ВСЕ три полностью пропускаются при `Статус ≠ Выполнен`:

| Процедура (ObjectModule.bsl) | Строка | Что делает | Нужен ли Статус=Выполнен? |
|------------------------------|--------|------------|--------------------------|
| `ЗаполнитьРегистрПоказателейУсиленногоКонтроля()` | 145 | Записывает показатели из результатов ЛА | **Да** — нужен результат |
| `ЗаполнитьРегистрЗаблокированныеРегистрацииПЛК()` | 150 | Обновляет блокировку текущей регистрации | **Да** — нужен результат |
| `СформироватьВспомогательныеДанныеДляЗаблокированныхТС()` | 153 | Создаёт блокировки для ДРУГИХ ТС (по группе) | **Нет для группы** — нужен сам факт проведения |

Третья процедура содержит вызов `ЗаполнитьЗаблокированныеРегистрацииУсиленныйКонтроль()` — это ЕДИНСТВЕННОЕ место, где создаются записи блокировки по "Группа ТС". Guard отсекает её при Статус ≠ Выполнен.

#### Что видит пользователь при ошибке

1. Оператор регистрирует ТС из группы:3 в АРМ Приёмки
2. Промежуточный композит группы:2 ещё не завершён (ЛА создан, но не "Выполнен")
3. В колонке "УК" АРМа **нет иконки блокировки** у ТС группы:3
4. Оператор нажимает "На разгрузку" → `ПроверитьБлокировкуДляСозданияНнР()` → **нет записей блокировки в РС** → проверка OK
5. ТС направляется на разгрузку **без ожидания результатов предыдущей группы**

#### Корректное поведение (после исправления)

Шаги 1-2 те же, но:
3. В колонке "УК" **есть иконка блокировки** — запись в РС создана при проведении ЛА группы:2
4. "На разгрузку" → `ПроверитьБлокировкуДляСозданияНнР()` → **Block** → "Направление на разгрузку не сформировано: регистрация заблокирована по усиленному контролю"
5. ТС ждёт завершения анализа группы:2

### 3.4 Ошибка 2: `ГруппаТСТребуетБлокировки` — логическая ошибка

**Файл**: `InformationRegisters/гкс_ЗаблокированныеРегистрацииУсиленныйКонтроль/Ext/ManagerModule.bsl:138-145`

#### Контекст вызова

Функция вызывается из `ЗаписатьБлокировкуГруппыТС()` (ManagerModule.bsl:36-50), которая решает: записать блокировку **по группе** или **по первому ТС**:

```bsl
// ManagerModule.bsl:36
Процедура ЗаписатьБлокировкуГруппыТС(...) Экспорт
    Если ГруппаТСТребуетБлокировки(БлокирующаяГруппаТС, АнализГруппыЗавершен, СостояниеКачестваГруппы) Тогда
        // Канал "Группа ТС": блокировка привязана к ГРУППЕ
        ДобавитьЗаписьБлокировки(... БлокирующаяГруппаТС ...);
    ИначеЕсли ПервоеТСТребуетБлокировки(СостояниеКачестваПервоеТС) Тогда
        // Канал "Первое ТС": блокировка привязана к РЕГИСТРАЦИИ первого ТС
        ДобавитьЗаписьБлокировки(... БлокирующаяРегистрация ...);
    КонецЕсли;
КонецПроцедуры
```

Выбор канала важен: от него зависит, как система потом найдёт и обновит запись при завершении анализа (`ОбновитьБлокировкуДляТС` vs `ОбновитьБлокировкуГруппаТС`), и какую причину блокировки покажет пользователю в АРМ (`ПолучитьПричинуБлокировкиДляДеталей`).

#### Ошибка в коде

```bsl
// ТЕКУЩИЙ КОД (ОШИБКА):
Функция ГруппаТСТребуетБлокировки(БлокирующаяГруппаТС, АнализГруппыЗавершен, СостояниеКачестваГруппы)
    Возврат ЗначениеЗаполнено(БлокирующаяГруппаТС)       // 1. Есть блокирующая группа?
        И Не АнализГруппыЗавершен                          // 2. Анализ группы ещё НЕ завершён?
        И (СостояниеКачестваГруппы <> КачествоНеПринято
        Или СостояниеКачестваГруппы <> РезультатыПробПолучены);  // 3. ← ВСЕГДА ИСТИНА!
КонецФункции
```

**Логическая тавтология**: `(X <> A Или X <> B)` = `НЕ (X = A И X = B)`. Переменная X не может быть одновременно равна A и B, поэтому `НЕ (ЛОЖЬ)` = `ИСТИНА` всегда. Проверка строки 3 фактически **не работает**.

Таблица истинности:

| `СостояниеКачестваГруппы` | `<> КачествоНеПринято` | `<> РезультатыПробПолучены` | `Или` (текущий) | `И` (правильный) |
|--------------------------|----------------------|---------------------------|-----------------|-----------------|
| ПустаяСсылка | Истина | Истина | **Истина** | **Истина** |
| ОтборПроб | Истина | Истина | **Истина** | **Истина** |
| КачествоПринято | Истина | Истина | **Истина** | **Истина** |
| **КачествоНеПринято** | **Ложь** | Истина | **Истина** ← ОШИБКА | **Ложь** ← ПРАВИЛЬНО |
| **РезультатыПробПолучены** | Истина | **Ложь** | **Истина** ← ОШИБКА | **Ложь** ← ПРАВИЛЬНО |

#### Последствие ошибки

При `СостояниеКачестваГруппы = КачествоНеПринято` (результат группы уже известен — качество не принято):

- **Текущее поведение** (с `Или`): `ГруппаТСТребуетБлокировки = Истина` → запись создаётся с `БлокирующаяГруппаТС`. Блокировка атрибутируется **группе**, хотя результат группы уже известен.
- **Правильное поведение** (с `И`): `ГруппаТСТребуетБлокировки = Ложь` → переходим к `ПервоеТСТребуетБлокировки` → запись создаётся с `БлокирующаяРегистрация`. Блокировка атрибутируется **первому ТС**, т.к. нужен индивидуальный анализ.

Ошибка проявляется в **edge case**: группа с частично завершённым анализом (один ТС в группе — КачествоНеПринято, другой ещё не проанализирован). В этом случае `АнализГруппыЗавершен = Ложь` (не все завершены), но `СостояниеКачестваГруппы` уже содержит промежуточный результат.

**Должно быть `И`**:

### 3.5 Ошибка 3: дубликаты в `ДобавитьЗаблокированноеВГруппыРегистрации`

**Файл**: `CommonModules/гкс_ВходнойКонтрольКачества/Ext/Module.bsl:1846-1859`

#### Контекст

Функция заполняет in-memory кэш `Результат.ГруппыПоРегистрациям` — Соответствие, где ключ = блокирующая регистрация, значение = массив пар `{БлокирующаяГруппаТС, ЗаблокированноеТС}`. Этот кэш используется в `ОбновитьЗаблокированныеТСПриЗавершенииЛА()` для пакетного обновления записей блокировки без повторных запросов к БД.

#### Ошибка в логике

```bsl
// ТЕКУЩИЙ КОД (ОШИБКА):
Для Каждого БлокируюшаяГруппы Из БлокируюшааяГруппы Цикл
    Если БлокируюшаяГруппы["БлокирующаяГруппаТС"] <> БлокирующаяГруппаТС
        И БлокируюшаяГруппы["ЗаблокированноеТС"] <> ЗаблокированноеТС Тогда
        БлокируюшааяГруппы.Добавить(...);  // ← ДОБАВЛЯЕТ НА КАЖДОЙ ИТЕРАЦИИ ЦИКЛА!
    КонецЕсли;
КонецЦикла;
```

Намерение разработчика: "если такой пары ещё нет — добавить". Реализация: "для КАЖДОЙ существующей пары, которая ОТЛИЧАЕТСЯ от новой — добавить новую".

Пример: в массиве уже 3 записи (А, Б, В), добавляем Г:
- Итерация 1 (А): А ≠ Г → **Добавить Г** → массив: А, Б, В, **Г**
- Итерация 2 (Б): Б ≠ Г → **Добавить Г** → массив: А, Б, В, Г, **Г**
- Итерация 3 (В): В ≠ Г → **Добавить Г** → массив: А, Б, В, Г, Г, **Г**

**Результат**: вместо 1 добавления — 3 дубля. При N записях → N дубликатов.

#### Последствие

Дубликаты в кэше приводят к многократному вызову `ОбновитьБлокировкуГруппаТС()` для одних и тех же ТС. Это:
- Лишние операции записи в РС (производительность)
- Потенциально некорректная логика при `ДобавитьПоказателиУКДляЗаблокированногоТС` (дублирование показателей)

В текущей TestDB не проявляется — каждая группа содержит 1-2 ТС с 1 записью в кэше.

#### Исправление

Сначала проверить наличие, потом добавить один раз:
```bsl
// GKSTCPLK-2292: Исправление дедупликации
Для Каждого БлокируюшаяГруппы Из БлокируюшааяГруппы Цикл
    Если БлокируюшаяГруппы["БлокирующаяГруппаТС"] = БлокирующаяГруппаТС  // = вместо <>
        И БлокируюшаяГруппы["ЗаблокированноеТС"] = ЗаблокированноеТС Тогда
        Возврат;  // Уже есть — выходим
    КонецЕсли;
КонецЦикла;
// Не нашли — добавляем один раз ПОСЛЕ цикла
БлокируюшааяГруппы.Добавить(ЗаполнитьЗаблокированное(БлокирующаяГруппаТС, ЗаблокированноеТС));
```

2. **Дублирование записей блокировки** — при добавлении вызова `ЗаполнитьБлокировкиПоГруппеТС` (ТМ-5) для не-Выполнен, а потом проведении того же ЛА со статусом Выполнен, вызовется и старая процедура `ЗаполнитьЗаблокированныеРегистрацииУсиленныйКонтроль`. Нужно убедиться, что `ДобавитьЗаписьБлокировки` в модуле менеджера РС не создаёт дубли (текущая реализация: `НаборЗаписейСОтбором` → `Добавить` → `Записать()` с отбором — перезаписывает, не дублирует).

3. **Исправление `ГруппаТСТребуетБлокировки` (ТМ-1)** может изменить текущее поведение — при `СостояниеКачестваГруппы = КачествоНеПринято` текущий код создаёт запись с `БлокирующаяГруппаТС`, а после исправления будет создаваться с `БлокирующаяРегистрация`. Нужно проверить, что это не ломает отображение в АРМ Приёмки (`ПолучитьПричинуБлокировкиДляДеталей`).

### Открытые вопросы

1. **Нужно ли при ТМ-5 также вызывать `ОбновитьЗаблокированныеТСПриЗавершенииЛА` для групп?** — Предварительно: нет, т.к. обновление применяется к уже существующим записям при ЗАВЕРШЕНИИ анализа, а ТМ-5 работает при начальном проведении.

2. **Функция `ЭтоПриемкаПромежуточныйКомпозит()`** — приватная в модуле документа. Нужно убедиться, что она доступна в контексте, где будет вызываться (ObjectModule — OK).
