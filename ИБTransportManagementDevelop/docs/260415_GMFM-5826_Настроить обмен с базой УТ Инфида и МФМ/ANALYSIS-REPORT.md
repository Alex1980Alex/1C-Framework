# GMFM-5826 Настроить обмен с базой УТ Инфида и МФМ

> Дата анализа: 2026-04-16
> База-приёмник: `Srvr="by-s-app1c03";Ref="tm_infeeda"`
> База-партнёр (мастер справочников): `Srvr="ys-app1c01";Ref="MFM"`
> База-образец: `Srvr="by-s-app1c01";Ref="tm_bat"` (Светлый)
> Анализ выполнен через MCP `1c-mcp-crud-infeeda` — подключение к живой infeeda подтверждено

---

## 1. Описание задачи

### 1.1 Требования

**[REQ-1]** Настроить RMQ-обмен между новой базой `tm_infeeda` (УТ Инфида) и базой МФМ по полной аналогии с действующим обменом базы `tm_bat` (Светлый) ↔ МФМ.

**[REQ-2]** Мастером справочной НСИ является база МФМ. Первоначально должны синхронизироваться из МФМ в infeeda:
- Показатели качества / показатели анализов номенклатуры
- Алгоритмы расчёта показателей качества
- Номенклатура
- Точки маршрута
- Транспортные документы (реквизит «Алгоритмы расчёта» в транспортном документе — особый кейс)

**[REQ-3]** (Инфра-требование, выполняется не в 1С) Виктор должен создать на RMQ-сервере **две новые очереди** для базы infeeda — одна под выгрузку (исходящие), одна под загрузку (входящие).

**[REQ-4]** Задача разбивается на 2 этапа. Текущий анализ покрывает **только Этап 1 — подготовка инфраструктуры обмена**. Этап 2 (регистрация конкретных справочников на выгрузку из МФМ + первичная прогрузка) будет отдельно уточнён после созвона после KPI.

### 1.2 Суть проблемы

База `tm_infeeda` только что поднята и **полностью изолирована** от контура обмена:

- 0 контрагентов, 0 номенклатуры, 0 показателей качества, 0 алгоритмов расчёта, 0 точек маршрута, 0 ТС (проверено через `execute_query` — см. секция 8)
- В механизме ИАС (Интеграционный адаптер «Содружество») сидит **единственный stub-сервер очередей** «Основной» со всеми пустыми реквизитами (адрес/порт/логин/пароль пустые)
- 0 точек обмена, 0 получателей данных, 0 обработчиков событий, 0 подписок, 0 участников обмена

При этом сам механизм ИАС в конфигурации **полностью развёрнут**: все нужные справочники, модули, предопределённые форматы и потоки событий на месте (см. секция 2). Задача сводится не к разработке кода, а к **заполнению справочников ИАС данными** по образцу из Светлого.

## 3. Детальный анализ механизма

### 3.1 Архитектура ИАС «Содружество» (по изученному коду и скриншотам)

RMQ-обмен в конфигурации устроен как классический publish/subscribe через RabbitMQ:

```
┌────────────────┐    publish     ┌──────────┐     consume    ┌───────────────┐
│ Исходящие сооб.│ ─────────────► │ RabbitMQ │ ─────────────► │ Входящие сооб.│
│ (Светлый / МФМ)│                │  broker  │                │   (infeeda)   │
└────────────────┘                └──────────┘                └───────────────┘
        ▲                              ▲                              │
        │                              │                              ▼
    Получатель                      Точка обмена                  Подписка →
    данных RMQ                      (exchange, type               Обработчик
    (producer)                       = Topic)                      событий
```

Ключевые сущности в конфигурации:
- **Сервер очередей** = соединение с конкретным RabbitMQ-узлом (host + port + vhost + login + pwd + TLS)
- **Точка обмена** = RMQ exchange, подчинена серверу (справочник иерархический через Владельца)
- **Получатель данных** = producer-конфигурация (что, в каком формате и с каким routing key выгружать)
- **Подписка на очередь** = consumer-конфигурация (на какой очереди слушать, какой обработчик вызывать)
- **Обработчик событий** = BSL-код, который вызывается при получении сообщения

### 3.4 Ключевое предупреждение по инфре RMQ

В Светлом используется vhost `/onec-apps` и сервер `onec-apps`. **Для infeeda очереди будут отдельные** (согласно диалогу: «нужно будет к Виктору сходить, попросить, чтобы он создал две очереди. Одна для выгрузки, вторая для загрузки»). Имя сервера/vhost/очередей для infeeda **нужно уточнить у Виктора до начала ввода данных** (см. секция 6, OQ-1/OQ-2).

Возможные варианты (на уточнение):
- Сервер `onec-apps` + те же vhost/login, новые очереди внутри vhost `/onec-apps` — если инфраструктурно всё живёт в одном кластере
- Отдельный vhost `/infeeda-apps` с новыми credentials — если изоляция по базам

## 6. Риски и открытые вопросы

### Открытые вопросы (OQ) — требуют уточнения перед реализацией

**OQ-1.** Имена очередей, которые создаст Виктор (для выгрузки и загрузки). Без них точка 6 (Подписка) не заполняется.

**OQ-2.** Общие ли credentials RabbitMQ для Светлого и infeeda, или Виктор заведёт отдельный vhost/login для infeeda. От этого зависит псевдоним сервера в точке 1 и значение `ВиртуальныйХост`.

**OQ-3.** Используется ли одна и та же точка обмена `onec-main-topic` для всех баз (Светлый + infeeda + будущие), или для infeeda создаётся своя, например `infeeda-main-topic`? Зависит от того, как Виктор настроит routing на broker-уровне.

**OQ-4.** В Светлом 4 получателя (МФМ, СРПВ, Электронная очередь, Электронные табло). Для infeeda на Этапе 1 создаётся **только МФМ**. Подтвердить, что остальные три (СРПВ, Электронная очередь, Электронные табло) для базы infeeda **не нужны** (по диалогу явно не сказано, но из контекста — да: infeeda — отдельный проект под УТ Инфида).

**OQ-5.** Нужен ли обработчик событий входящих сообщений отдельной записью, или используется типовой из `гкс_ОбработкаОчередиВходящихСообщенийRMQ`. Проверить по образцу Светлого.

**OQ-6.** (Для Этапа 2) Полный список справочников для первичной выгрузки из МФМ. В диалоге упомянуты: показатели качества, показатели анализов, алгоритмы расчёта, номенклатура, точки маршрута, транспортные документы. Возможно, в ходе реализации выявятся связанные зависимости (единицы измерения, классификаторы и т.д.).

### Риски (R)

**R-1.** Сетевая доступность: кластер infeeda (`by-s-app1c03`) может не иметь сетевого доступа до `ms-s-rabbitmq-cls01`. Проявление — точка 1 не пройдёт «Проверить соединение». Митигация — до начала работы попросить у админов проверку доступности порта 5672 с `by-s-app1c03`. Цитата из диалога: «могут быть подводные камни, типа, если с кластера, на котором она опубликована, не сможет до ребята достучаться».

**R-2.** Stub-запись «Основной» в `СерверыОчередейRMQ` имеет UUID — не факт, что она предопределённая платформой. Если её удалить, могут отвалиться миграционные ссылки. Рекомендация — **не удалять**, а либо заполнить, либо создать параллельно новую и пометить «Основной» на удаление после проверки.

**R-3.** Реквизит `ВиртуальныйХост` в Светлом пишется как `/onec-apps` (с ведущим слэшем). Без слэша RabbitMQ вернёт auth error. При копировании проверить точно.

**R-4.** Пароль в справочнике `СерверыОчередейRMQ` хранится **в открытом виде** (реквизит типа Строка, не Хранилище значения — по структуре `✓ get_metadata_structure`). Из диалога: «он тут по-моему не шифруется в открытом виде хранится… можно консолью запросов вытащить». Это security-aware момент, но вне scope текущей задачи — просто отметить.

**R-5.** Кастомный обработчик (точка 5) может быть нетривиальным — если в Светлом есть отдельная запись с BSL-кодом, то её нужно копировать полностью через консоль. В рамках текущего анализа на это уйдёт отдельная проверка.

**R-6.** Реквизит справочника `гкс_ПолучателиДанныхRMQ.ТЧ.ВыгружаемыеДанные.Условие` имеет тип `ХранилищеЗначения` — при ручном переносе через форму это просто выбор, но через автоматизированный import/export нужен специальный код.

**R-7.** Опечатка в метаданных: `ИдентифкаторСтроки` (должно быть `Идентификатор`). Не влияет на работу, но при написании скриптов копировать точно.
