# GKSTCPLK-2407 — Добавить вид допуска «Ветеринарный» в РМ «Приёмка и отгрузка на ПЛК»

> Выход скилла `/analyze-1c-task-v2` v4.1. Базовый путь: `src/projects/configuration/260304_GKSTCPLK-2182 Доработать создание Направление на разгрузку для заблокированных ТС/`.
> Все пути ниже относительны корня этой подконфигурации (submodule).

## 1. Описание задачи

### 1.1 Требования

- **[REQ-1]** Добавить в обработку `Обработка.гкс_ПриемкаТранспорта` четвёртый вид допуска **«Ветеринарный»** по аналогии с тремя существующими: `Фумигационный`, `Фитосанитарный`, `Претензионный`. Объём — весь цикл: значение перечисления, роль, ключ доступа, команда, кнопка в подменю «Допуски», колонка-индикатор «треугольник», запросы динамического списка и серверные запросы по регистру.
- **[REQ-2]** Проверить корректность логики видимости реквизитов/колонок допусков на форме обработки. Пользователь в диалоге `Диалог по задаче_1.md` сообщает: в настройках формы галка «Видимость» у колонок-индикаторов снята, но колонки всё равно отображаются. Нужно разобраться, почему пользовательская настройка перекрывается, и починить (либо обосновать, что так и задумано). См. [§3.3 Гипотеза бага REQ-2](#33-гипотеза-бага-req-2).

### 1.2 Суть проблемы

В обработке «Приёмка/Отгрузка на ПЛК» (скриншот `Скриншот-20260421-114532.jpg`) рядом с кнопками `Допуски ▾` у каждой строки регистрации ЖД-перевозки отображается три PictureField-индикатора (красные/зелёные треугольники) — по одному на каждый вид допуска. В регистре сведений `гкс_СтатусыДопускаВагоновКВскрытию` хранится статус (разрешено/запрещено). Кнопки изменения допуска скрываются при отсутствии соответствующей роли, но сами колонки-индикаторы — нет: их видимость явно выставляется кодом формы каждый раз при пересчёте ([ОсновнаяФорма/Module.bsl:1198-1200](src/DataProcessors/гкс_ПриемкаТранспорта/Forms/ОсновнаяФорма/Ext/Form/Module.bsl#L1198)), что перекрывает пользовательскую настройку «Видимость» через стандартное меню «Настройки формы».

По задаче нужно добавить четвёртый допуск «Ветеринарный» и исследовать описанный пользователем баг с видимостью.

### 3.3 Гипотеза бага REQ-2

**Код**: [ОсновнаяФорма/Module.bsl:1191-1214](src/DataProcessors/гкс_ПриемкаТранспорта/Forms/ОсновнаяФорма/Ext/Form/Module.bsl#L1191) — процедура `УстановитьВидимостьЭлементовСпискаРегистрации()` при каждом пересчёте безусловно перезаписывает:

```bsl
Элементы.СписокРегистрацииФумигационный.Видимость 	= ЭтоЖДПеревозка;
Элементы.СписокРегистрацииФитосанитарный.Видимость 	= ЭтоЖДПеревозка;
Элементы.СписокРегистрацииПретензионный.Видимость 	= ЭтоЖДПеревозка;
```

Для **кнопок** (СписокРегистрацииДопускХ, [:1115-1117](src/DataProcessors/гкс_ПриемкаТранспорта/Forms/ОсновнаяФорма/Ext/Form/Module.bsl#L1115)) видимость правильно прокинута через `СтруктураДоступов.ДоступенДопускХ` (роли). Для **колонок-индикаторов** — просто `= ЭтоЖДПеревозка`. Это перекрывает пользовательскую настройку «Видимость колонок», которую мог снять пользователь через меню «Настройки формы» — именно это описано в диалоге:

> «видимости галка не стоит, галка не стоит, но они всё равно показываются» (`Диалог по задаче_1.md` строка 3)

**Рекомендация**: согласовать видимость колонок с видимостью кнопок — gate по роли. Тогда у пользователя без роли колонка сразу скрыта, а у пользователя с ролью — решает стандартный механизм настроек формы (пользовательская видимость перестаёт перетираться). Формально:

```bsl
Элементы.СписокРегистрацииФумигационный.Видимость   = ЭтоЖДПеревозка И СтруктураДоступов.ДоступенДопускФумигационный;
Элементы.СписокРегистрацииФитосанитарный.Видимость  = ЭтоЖДПеревозка И СтруктураДоступов.ДоступенДопускФитосанитарный;
Элементы.СписокРегистрацииПретензионный.Видимость   = ЭтоЖДПеревозка И СтруктураДоступов.ДоступенДопускПретензионный;
Элементы.СписокРегистрацииВетеринарный.Видимость    = ЭтоЖДПеревозка И СтруктураДоступов.ДоступенДопускВетеринарный;
```

**Альтернатива (более мягкая)** — полностью убрать принудительное назначение видимости колонок, оставив только правила визуализации (вагон/ЖД) через ФункциональныеОпции или условное оформление. Но это затрагивает форму сильнее и требует переноса в настройки — вне scope задачи.

**Открытый вопрос [OQ-1]**: пользователь прислал копию БелАгроТерминал (`Диалог по задаче_1.md` строка 4, `Диалог по задаче_2.md` строки 6-8), где якобы колонки не пропадают даже при снятой галке. Нужна ручная проверка на её копии, либо на локально восстановленном dt — **перед** финализацией REQ-2 подтвердить, что предложенная правка решает то, что видит пользователь (не другой баг).

## 6. Риски и открытые вопросы

- **[OQ-1]** Пользователь утверждает, что на копии БелАгроТерминал колонки-индикаторы не пропадают при снятой пользовательской галке «Видимость». **Нужна проверка на её копии** перед релизом REQ-2 — возможно, дело не только в строках :1198-1200, но и в условном оформлении / функциональной опции, которую я не проверил. Запросить dt-копию у аналитика (в диалоге #2 упоминается серверная копия + просьба выгрузить dt).
- **[OQ-2]** Согласовать семантику REQ-2-фикса: *скрывать ли колонку у пользователя без роли?* В текущем коде колонка видна всем (`= ЭтоЖДПеревозка`), то есть пользователь без роли «менять допуск» всё равно видит статус. Если аналитика устраивает — можно оставить колонку, но перестать перетирать пользовательскую настройку (удалить или вынести в условное оформление). Если ок скрывать — как в Точке 12.
- **[OQ-3]** Нужна ли специфичная логика при ветеринарном допуске в `Документ.гкс_РегистрацияНаПЛК.ManagerModule` по аналогии со строками 655-659 (Претензионный)? И в `Документ.гкс_Взвешивание.ManagerModule` (строки 374, 498) — `ВыполнитьПроверкуОтклоненияБрутто` использует только Претензионный. Если ветеринарный запрет должен влиять на отклонение брутто / блокировку приёмки — нужна доработка. Уточнить у постановщика.
- **[OQ-4]** Название роли — `гкс_ВозможностьМенятьДопускВетеринарныйВАРМеПриемкиНаПЛК` (по шаблону трёх существующих). Подтвердить у ответственного за роли (есть договорённость, может ли отличаться).
- **[OQ-5]** Значения `uuid` для нового EnumValue, Button, PictureField, Command — сгенерировать при реализации в Конфигураторе/EDT, не вписывать вручную.
- **[Риск R-1]** Повторное индексирование dynamic list (тяжёлый запрос в Form.xml) — после правки SQL убедиться, что план запроса не деградировал. Проверить на объёмной базе (>10k регистраций).
- **[Риск R-2]** Обратная совместимость существующих записей в `гкс_СтатусыДопускаВагоновКВскрытию` — их структура не меняется, все существующие записи с `Фумигационный/Фитосанитарный/Претензионный` остаются валидными.
- **[Риск R-3]** `ДополнитьПрофильРолямиУправленияПретензионнымДопускомКВагонам` вызывается при стандартной поставке профилей — добавление роли в этот список даст роль всем пользователям, уже имеющим другие «допуск»-роли. Уточнить, допустимо ли это по умолчанию, или новая роль должна выдаваться отдельно.
