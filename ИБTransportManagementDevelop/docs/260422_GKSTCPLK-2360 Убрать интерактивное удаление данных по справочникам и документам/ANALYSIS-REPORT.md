# GKSTCPLK-2360 Убрать интерактивное удаление данных по справочникам и документам

## 1. Описание задачи

### 1.1 Требования

- **[REQ-1]** У роли полноправного пользователя (`ПолныеПрава`) запретить интерактивное удаление объектов метаданных `Справочник.гкс_*` и `Документ.гкс_*`.
- **[REQ-2]** Проверить все остальные роли конфигурации и убрать интерактивное удаление на `Справочник.гкс_*` / `Документ.гкс_*`, если оно где-либо явно разрешено.

### 1.2 Суть проблемы

В текущем состоянии роль `ПолныеПрава` имеет `setForNewObjects=true`, поэтому для любого объекта `Справочник.гкс_*` / `Документ.гкс_*`, не перечисленного в её `Rights.xml`, по умолчанию разрешены все права, включая `InteractiveDelete` и `InteractiveDeleteMarked`. Полноправный пользователь может случайно удалить данные через Shift+Del или команду "Удалить помеченные" в интерфейсе. Часть роли `гкс_*` с именем вида `_ДобавлениеИзменение` и `гкс_БазовыеПраваАналитика` / `гкс_НастройкаУсиленногоКонтроля` также явно предоставляют права `InteractiveDelete*=true` на объекты `гкс_*` — это тоже требуется убрать.

## 3. Детальный анализ механизма

### 3.1 Структура `Rights.xml` (платформенная модель прав 1С)

Файл `<Role>/Ext/Rights.xml` содержит:

- Корневые флаги:
  - `<setForNewObjects>` — значение прав для объектов, не перечисленных явно. Для `ПолныеПрава` = `true` (всё разрешено по умолчанию), для остальных = `false`.
  - `<setForAttributesByDefault>`, `<independentRightsOfChildObjects>`.
- Список `<object>` с именем (`Catalog.<ИмяОбъекта>` / `Document.<ИмяОбъекта>`) и набором `<right>` (имя + `true`/`false`).
- Права, относящиеся к **интерактивному удалению** (права вида `Interactive*Delete*`):
  | Право | Применимо к | Смысл |
  |-------|-------------|-------|
  | `InteractiveDelete` | Справочник, Документ | Непосредственное удаление (Shift+Del) |
  | `InteractiveDeleteMarked` | Справочник, Документ | Удаление помеченных на удаление |
  | `InteractiveDeletePredefinedData` | Справочник | Интерактивное удаление предопределённых элементов |
  | `InteractiveDeleteMarkedPredefinedData` | Справочник | Удаление помеченных предопределённых |
  
  Права на установку/снятие пометки (`InteractiveSetDeletionMark`, `InteractiveClearDeletionMark`) **не трогаем** — это не удаление, а только пометка.

### 3.2 Найденные паттерны в конфигурации ✓ pattern

**Паттерн А — запись в `Rights.xml` `ПолныеПрава` для частичного запрета.** Уже применён к 4 объектам:

- `Catalog.гкс_СтатусыСудов` (line 2631-2641): `InteractiveDelete=false` + `InteractiveDeletePredefinedData=false`.
- `Catalog.гкс_ПоказателиАнализовНоменклатуры` (line 3621-3631): `InteractiveDelete=false` + `InteractiveDeletePredefinedData=false`.
- `Document.гкс_ЗаявкаНаПеревозку` (line 1614-1620): только `InteractiveDelete=false` (частично — нужно дополнить `InteractiveDeleteMarked`).
- `Document.гкс_РеестрНакладныхЗПП3` (line 2918-2928): `InteractiveDelete=false` + `InteractiveDeleteMarked=false` — **эталонный паттерн для документов**.

**Паттерн Б — BSP-роли.** Аналогичный приём применён BSP для `Catalog.ВариантыОтчетов` (lines 108-130 `ПолныеПрава`), `Catalog.ГруппыВнешнихПользователей` (line 2929-2941 `ПолныеПрава`). В качестве образца стиля XML-вставки используется именно существующий элемент для `Document.гкс_РеестрНакладныхЗПП3`.

### 3.3 Производный набор прав для отключения

Итоговый набор прав, устанавливаемых в `false` (по паттерну Б + документация 1С):

- **Справочник**: 4 права — `InteractiveDelete`, `InteractiveDeleteMarked`, `InteractiveDeletePredefinedData`, `InteractiveDeleteMarkedPredefinedData`.
- **Документ**: 2 права — `InteractiveDelete`, `InteractiveDeleteMarked`.

Существующие частичные записи для 4 объектов будут дополнены до полного набора (унификация стиля).

### 3.4 Алгоритм применения (общий для всех точек)

Для **ПолныеПрава** (объект отсутствует):

```xml
<object>
    <name>Catalog.гкс_&lt;Имя&gt;</name>
    <right>
        <name>InteractiveDelete</name>
        <value>false</value>
    </right>
    <right>
        <name>InteractiveDeleteMarked</name>
        <value>false</value>
    </right>
    <right>
        <name>InteractiveDeletePredefinedData</name>
        <value>false</value>
    </right>
    <right>
        <name>InteractiveDeleteMarkedPredefinedData</name>
        <value>false</value>
    </right>
</object>
```

Для документов — аналогично, без `*PredefinedData`. Блок вставляется перед закрывающим `</Rights>` (в конец файла, до последней строки).

Для **других ролей** — замена значения `<value>true</value>` на `<value>false</value>` внутри уже существующих блоков (точечный патч без вставки новых `<object>`).

## 5. Чек-лист верификации

- [ ] `Rights.xml` остаётся валидным XML (schema `http://v8.1c.ru/8.2/roles`).
- [ ] В роли `ПолныеПрава` для каждого из 66 объектов `Catalog.гкс_*` / `Document.гкс_*` присутствует `<object>` с `InteractiveDelete=false` (+ дополнительные права по шаблону §3.3).
- [ ] В 7 «других» ролях не осталось ни одного `<value>true</value>` под `Interactive*Delete*` для `Catalog.гкс_*` / `Document.гкс_*` — проверить скриптом §5.1.
- [ ] Конфигурация собирается в EDT/Конфигураторе без ошибок (проверка прав — не битые имена объектов).
- [ ] Остальные права ролей (чтение, добавление, изменение, проведение) — не меняются.

### 5.1 Проверочный скрипт (Python) ✓ execute_query — запускается на `src/Roles/**/Rights.xml`

```python
# Сканирует Rights.xml и сообщает любую оставшуюся запись Interactive*Delete*=true для гкс_.
import re, glob, os
base = r'src/projects/configuration/260304_GKSTCPLK-2182 .../src/Roles'
leftover = []
for fp in glob.glob(os.path.join(base, '*/Ext/Rights.xml')):
    t = open(fp, encoding='utf-8').read()
    for m in re.finditer(r'<object>(.*?)</object>', t, re.DOTALL):
        b = m.group(1)
        n = re.search(r'<name>([^<]+)</name>', b)
        if not n or not n.group(1).startswith(('Catalog.гкс_', 'Document.гкс_')):
            continue
        for rm in re.finditer(r'<right>\s*<name>(Interactive\w*Delete\w*)</name>\s*<value>true</value>', b):
            leftover.append((fp, n.group(1), rm.group(1)))
assert not leftover, leftover
```

## 6. Риски и открытые вопросы

Структурировано по вероятности × влиянию.

### 6.1 🔴 Критичные (high impact)

**R1. Регрессия сценариев, использующих БСП «Удаление помеченных объектов»**
- **Уточнение механизма** (верифицировано по ИТС + [infostart.ru/topic258038](https://forum.infostart.ru/forum9/topic258038/), [1s-up.ru](https://www.1s-up.ru/udalenie-v-1s/); детали закешированы в `.claude/skills/1c-doc-research/cache/interactive-delete-rights.md`):
  - Платформа различает **5 прав на удаление**: `Delete` (программное), `InteractiveDelete` (Shift+Del), `InteractiveSetDeletionMark` (установка пометки), `InteractiveClearDeletionMark` (снятие пометки), `InteractiveDeleteMarked` (удаление помеченных).
  - Стандартная БСП-обработка `УдалениеПомеченныхОбъектов` (и её регламентное задание) проверяет **именно `InteractiveDeleteMarked`** через `ПравоДоступа("InteractiveDeleteMarked", МетаданныеОбъекта)` — НЕ `Delete` и НЕ `InteractiveDelete`.
  - Программное удаление через `Object.Удалить()` / `УдалитьНепосредственно()` требует **только `Delete`**. Задача **не трогает** `Delete` — программное удаление в коде (РИБ, сервисные задания, миграции через `НайтиПоСсылке().ПолучитьОбъект().Удалить()`) продолжит работать.
- **Следствия запрета `InteractiveDeleteMarked=false`:**
  - Пользователи `ПолныеПрава` **не смогут** запустить «Функции для технического специалиста → Стандартные → Удаление помеченных объектов» для `гкс_*`-объектов.
  - Регламентное задание `УдалениеПомеченныхОбъектов` **пропустит** эти объекты (не удалит помеченные автоматически по расписанию).
  - «Очередь мусора» из помеченных `гкс_*`-объектов будет копиться до ручной очистки (через Конфигуратор или отдельную роль).
- **Mitigation:**
  1. Аудит `src/**/*.bsl` на вызовы `УдалитьПомеченные*|НачатьУдалениеПомеченных|УдалениеПомеченныхОбъектов.*` через Grep.
  2. Если найдено — либо оставить отдельную роль-исключение для сервисного аккаунта, либо переписать через программное `Удалить()` (требует только `Delete`).
  3. Проверить настройку регламентного задания `УдалениеПомеченныхОбъектов` в БСП — возможно, потребуется исключить `гкс_*`-объекты из списка обрабатываемых.

**R2. Авто-разрешение `InteractiveDelete` для будущих `гкс_*`-объектов через `setForNewObjects=true`**

**Уточнённая механика** (верифицировано по [its.1c.ru/v8std/600/i8100532.htm](https://its.1c.ru/db/content/v8std/src/600/i8100532.htm), [koderline.ru](https://www.koderline.ru/expert/programming/article-roli-polzovateley-v-sisteme-1s/), [infostart/topic239622](https://forum.infostart.ru/forum9/topic239622/); в кеше `.claude/skills/1c-doc-research/cache/interactive-delete-rights.md`):

- Флаг срабатывает **в момент ДОБАВЛЕНИЯ нового объекта метаданных**, НЕ при каждом open/save конфигурации.
- При добавлении нового `Catalog.гкс_НовыйСправочник` / `Document.гкс_НовыйДокумент` в роль `ПолныеПрава` автоматически добавляется запись со **всеми правами = true** (включая `InteractiveDelete`, `InteractiveDeleteMarked`, `Delete`, `Read`, `Insert`, `Update`, `View`, `Edit` и т. д.).
- **Ретроактивного перезаписывания `Rights.xml` нет** — существующие записи не меняются. Для объектов, которых нет в `Rights.xml` при `setForNewObjects=true`, платформа runtime трактует их как «разрешено всё» (неявно).
- **Следствие для задачи:** 62 новых `<object>`-блока для 66 существующих `гкс_*`-объектов безопасны — их платформа не перезапишет. Риск R2 **касается будущих объектов**, добавляемых после merge.

**Критичное уточнение для этого проекта:**
- ✅ Расширений конфигурации в проекте **нет** (проверено: отсутствует папка `ConfigurationExt` в `src/`) → риск авто-назначения прав на объекты расширений (появился в 8.3.14+) НЕ применим.
- ⚠️ Но для **будущих** `гкс_*`-объектов, которые разработчики добавят после внедрения задачи, **ПолныеПрава автоматически получит `InteractiveDelete=true`** — круг вернётся.

**Стандарт ИТС** ([v8std/700/i8100689.htm](https://its.1c.ru/db/content/v8std/src/700/i8100689.htm)):

> Только для роли `ПолныеПрава` должен быть установлен флаг «Устанавливать права для новых объектов». Для всех остальных ролей этот флаг должен быть снят.

→ Наша конфигурация уже соответствует (проверено скриптом: `setForNewObjects=true` только у `ПолныеПрава` из 376 ролей).

**Mitigation (расширенное):**

1. **Проверочный скрипт §5.1 в pre-commit / CI** — при добавлении нового `Catalog.гкс_*` / `Document.гкс_*` без явного `InteractiveDelete=false` в `ПолныеПрава/Rights.xml` → fail сборки.
2. **Документальный standard для команды** — добавить в `CLAUDE.md` / onboarding: «при добавлении нового `гкс_*`-объекта обязательно добавить 4 (для каталога) или 2 (для документа) записи `Interactive*Delete*=false` в `ПолныеПрава/Rights.xml`».
3. **Паттерн "шаблон объекта"** — создать template-сниппет в EDT, который автоматически добавляет правильный блок в `Rights.xml` при создании нового `гкс_*`-объекта.
4. **Альтернативный архитектурный паттерн** ([infostart/1128549](https://infostart.ru/1c/articles/1128549/), [607206](https://infostart.ru/1c/articles/607206/)): создать отдельную базовую роль с `setForNewObjects=true` как "insurance" (собирает права на новые объекты), снять флаг с `ПолныеПрава`. **Требует крупного рефакторинга — за рамками GKSTCPLK-2360.**

**R3. Обновление конфигурации поставщика (БСП/ERP/УТ) — возможный откат правок**

**Уточнённый анализ** (верифицировано по [its.1c.ru/v8std/600/i8100488.htm](https://its.1c.ru/db/content/v8std/src/600/i8100488.htm), [its.1c.ru/bsp/3.1/updatessl_3.1.html](https://its.1c.ru/db/content/updlib/src/bsp/3.1/updatessl_3.1.html), [infostart/300363](https://infostart.ru/1c/articles/300363/); детали в `.claude/skills/1c-doc-research/cache/interactive-delete-rights.md#28`):

**Коррекция исходной формулировки:** БСП-подсистема `Справочник.ПрофилиГруппДоступа` **НЕ переопределяет `Rights.xml`**. Профили управляют связью «профиль ↔ набор ролей» и «пользователь ↔ профиль», а не содержимым прав внутри роли.

**Проверка проекта:** `Справочник.ПрофилиГруппДоступа` + `Справочник.ГруппыДоступа` **присутствуют** (Grep: 8 файлов в `src/Catalogs/`). Подсистема «Управление доступом» БСП подключена.

**Что делают ПрофилиГруппДоступа:**
- Хранят наборы ролей (поставляемый «Администратор» включает `ПолныеПрава` + `АдминистраторСистемы` + `ИнтерактивноеОткрытиеВнешнихОтчетовИОбработок`).
- При обновлении типовой поставки БСП автоматически **добавляют/убирают роли** в составе профилей (changelog БСП 3.1: «В профили, кроме поставляемых, содержащие роль X, будет добавлена роль Y»).

**Что НЕ делают:**
- Не трогают `Rights.xml` ролей. Наш запрет `InteractiveDelete=false` для `ПолныеПрава` **не может быть возвращён через механизм профилей** — ни при обновлении типовой конфигурации, ни при автосинхронизации профилей БСП.

**Реальный риск R3 — cf-обновление конфигурации поставщика:**
- При выполнении «Конфигурация → Сравнить и объединить с конфигурацией поставщика» (ручная админ-операция при апдейте типовой БСП/ERP/УТ), в диалоге слияния `Rights.xml` роли `ПолныеПрава` попадёт в конфликт (у поставщика — дефолтные права включая `InteractiveDelete=true`, у нас — `false`).
- Если админ выберет «взять из поставщика» (по умолчанию, при нажатии «ОК» без детального разбора) → наши 62 блока `Interactive*Delete*=false` будут удалены.
- Это **не автоматический** процесс — только при ручном обновлении cf-файла.

**Mitigation (уточнённое):**
1. **Процедура обновления БСП/ERP/УТ** — чек-лист для админа: при слиянии `Rights.xml` роли `ПолныеПрава` всегда выбирать «взять из текущей конфигурации» или «объединить», **никогда не «взять из поставщика»**.
2. **Маркер в коде** — добавить XML-комментарий `<!-- GKSTCPLK-2360: custom, preserve on supplier merge -->` в каждый вставленный `<object>` (уже заложено в §4 плана). При слиянии админ увидит маркер.
3. **Пост-обновление проверка** — после любого cf-обновления выполнить проверочный скрипт §5.1 → `leftover == []`. Если не пусто — восстановить правки.
4. **Автопроверка в CI** — проверочный скрипт §5.1 прогонять на каждом PR к основной ветке.

### 6.2 🟡 Средние (medium impact)

**R4. UX-регрессия**
- Пользователи `ПолныеПрава` привыкли к Shift+Del / «Удалить помеченные» на формах списков `гкс_`-объектов. После правки команды исчезнут без предупреждения → поток обращений в поддержку.
- *Mitigation:* уведомление пользователей + инструкция «удаление теперь через Конфигуратор / обработку».

**R5. Удаление предопределённых элементов**
- `InteractiveDeletePredefinedData=false` заблокирует удаление предопределённых элементов справочников (например, `гкс_СтатусыСудов`: «Зарегистрирован», «В пути»). Обычно правильно, но если есть процедура смены предопределённых при обновлении конфигурации — сломается.
- *Mitigation:* grep по `УдалитьПредопределённый`, проверить обработчики `ПриПолученииДанныхНаСервере`.

**R6. YaXUnit-тесты, использующие интерактивное удаление**
- Тесты, проверяющие сценарий «создал → удалил через интерфейс», упадут.
- *Mitigation:* прогон `tools/yaxunit.json` на TestDB **до** merge; фикс тестов с переходом на программное удаление.

**R7. Merge conflicts на `ПолныеПрава/Rights.xml`**
- Файл 3744 строк + 62 новых `<object>`-блока. Параллельные PR, меняющие тот же файл (любое добавление объекта), дадут тяжёлый merge.
- *Mitigation:* мержить первым после аппрува; вставлять блоки в конце файла перед `</Rights>` (меньше конфликтов), а не в алфавитный порядок.

### 6.3 🟢 Низкие (low impact)

**R8. Конфигуратор переупорядочивает XML при save**
- Конфигуратор может отсортировать `<object>` по имени при сохранении → шумный diff в последующем коммите. Не ломает логику, но затрудняет code review.
- *Mitigation:* один коммит — «добавление блоков», второй (если понадобится) — «reorder by platform»; либо редактировать только через EDT/Конфигуратор, не руками.

**R9. Валидация XML schema**
- Неверное место вставки блока / лишний пробел → ошибка загрузки конфигурации. Ошибка ловится на первом же «Проверка конфигурации».
- *Mitigation:* `xmllint --noout` на каждый изменённый `Rights.xml` в pre-commit.

**R10. Конфликт ролей при множественном назначении**
- В 1С если пользователю назначено несколько ролей, права **складываются по принципу OR**. Если у пользователя есть `ПолныеПрава` **и** дополнительная роль с `InteractiveDelete=true` на `гкс_*`, запрет не сработает.
- *Mitigation:* после правок запустить запрос к `ИнформацияПравДоступа` через `mcp__1c-mcp-crud__get_access_rights` по нескольким реальным пользователям и проверить effective-права.

### 6.4 🔍 Неочевидные

**R11. Обмен данными / РИБ**
- Если в распределённой информационной базе подчинённый узел получает данные с flag «удалить», делает это через программное `Delete` — **НЕ затронуто**. Но типовая «Очередь отложенного проведения» / выгрузка через `СтандартныеПодсистемы.ОбменДанными` может вызывать интерактивный сценарий — проверить.

**R12. Inconsistency с не-`гкс_` объектами**
- После правок `ПолныеПрава` будет разрешать `InteractiveDelete` для BSP-объектов (`Catalog.Номенклатура`, `Document.ЗаказПокупателя`), но запрещать для `гкс_*`. Это может показаться странным аудитору безопасности.
- *Mitigation:* документально зафиксировать решение в ADR или в `docs/architecture/` — «почему защита только на гкс_».

### 6.5 Открытые вопросы автору задачи

1. **Трактовка «у других прав».** Фраза ТЗ «проверить и убрать интерактивного удаления у других прав» интерпретирована как «у других ролей конфигурации». Если автор задачи имел в виду также права семейства `InteractiveSetDeletionMark` / `InteractiveClearDeletionMark` (установка/снятие пометки удаления), объём вырастает в ~2 раза.
2. **Не затрагиваются подчинённые объекты.** Команды (`Command.*`), реквизиты (`Attribute.*`), формы — их права не меняются, только «корневые» объекты каталогов/документов. Подтвердить, что это ожидаемо.
3. **Inconsistency с BSP-объектами (см. R12).** Подтвердить, что защита ограничена только префиксом `гкс_` осознанно.

### 6.7 ✅ Alignment с стандартом ИТС (снижение риска архитектурной критики)

Проведена дополнительная верификация через [its.1c.ru](https://its.1c.ru/db/content/v8std/src/700/i8100689.htm) (детали в кеше `.claude/skills/1c-doc-research/cache/interactive-delete-rights.md`):

> **ИТС, «Настройка ролей и прав доступа»:** «**Ни одна роль (в т.ч. `ПолныеПрава` и `АдминистраторСистемы`) не должна давать право на интерактивное удаление ссылочных объектов.** После создания нового объекта нужно зайти в роль `ПолныеПрава` и отключить право интерактивного удаления у ссылочных объектов. Только для роли `ПолныеПрава` должен быть установлен флаг «Устанавливать права для новых объектов».»

> **ИТС, «Стандартные роли»:** «Роль `ПолныеПрава` должна предоставлять неограниченный доступ ко всем данным области (к разделенным данным), **кроме права интерактивного удаления**.»

**Следствие:** задача GKSTCPLK-2360 **буквально следует стандарту ИТС**. Это снижает риски:
- R12 (inconsistency с BSP-объектами) ослаблен — стандарт ИТС не требует разрешать interactive delete на BSP-объектах, просто не было задачи отключать их. Для полного соответствия стандарту можно запланировать отдельную задачу на отключение `InteractiveDelete` у всех ссылочных BSP-объектов в `ПолныеПрава`.
- Аудитору безопасности можно ссылаться на стандарт ИТС как на обоснование.
