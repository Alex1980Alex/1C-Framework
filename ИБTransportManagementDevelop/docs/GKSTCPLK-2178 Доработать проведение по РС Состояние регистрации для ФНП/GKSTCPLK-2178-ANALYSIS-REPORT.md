# GKSTCPLK-2178 Доработать проведение по РС Состояние регистрации для ФНП

## Детальный аналитический отчёт

**Дата:** 2026-03-05
**Проект:** 260304_GKSTCPLK-2182 Доработать создание Направление на разгрузку для заблокированных ТС
**Статус:** Анализ завершён

---

## 1. Описание задачи

### 1.1 Требования

1. При проведении документа "Формирование номера пробы" (ФНП), созданного из АРМ "Композитные пробы" для единичного ТС по УК (усиленный контроль) — **НЕ делать** движения по РС `гкс_СостоянияРегистрации`
2. Для остальных сценариев (обычная единичная проба, не связанная с композитной) — поведение НЕ менять

### 1.2 Суть проблемы

**Как сейчас:**
Документ ФНП с `ТипПробы = Единичная` при проведении **всегда** записывает в РС `гкс_СостоянияРегистрации` состояние `ВзятыПробы`. Это происходит и для единичных проб, созданных из АРМ "Композитные пробы" для ТС под усиленным контролем.

**Что должно быть:**
Если `ДокументРегистрации` из табличной части ФНП уже участвует в композитной пробе (есть запись в РС `гкс_КомпозитныеПробы`), то движение по РС `гкс_СостоянияРегистрации` **НЕ формировать**.

**Причина ошибки:**
В функции `ДанныеДокументаДляПроведения` (ManagerModule.bsl, строка 49-54) разветвление идёт только по `ТипПробы`:
- `Композитная` → движения по `гкс_КомпозитныеПробы` (БЕЗ СостоянияРегистрации)
- `Единичная` (все остальные) → движения по `гкс_СостоянияРегистрации` с состоянием "ВзятыПробы"

Нет проверки: является ли ДокументРегистрации частью композитной пробы.

## 3. Детальный анализ механизма

### 3.1 Документ гкс_ФормированиеНомераПробы — МодульМенеджера

#### Текущий алгоритм (функция ДанныеДокументаДляПроведения, строки 31-63)

```
1. Получает ДопПараметры.ДополнительныеСвойства.ТипПробы
2. ЕСЛИ ТипПробы = Композитная:
   → Вызывает ТекстЗапросаТаблицагкс_КомпозитныеПробы()
   → Записывает движения ТОЛЬКО в РС гкс_КомпозитныеПробы
3. ИНАЧЕ (ТипПробы = Единичная):
   → Вызывает ТекстЗапросаТаблицаСостояниеРегистрации()
   → Записывает движения в РС гкс_СостоянияРегистрации с состоянием "ВзятыПробы"
```

**Ключевые строки:**
- Строка 49-54: ветвление по ТипПробы
- Строка 1025-1060: функция `ТекстЗапросаТаблицаСостояниеРегистрации` — формирует запрос

#### Функция ТекстЗапросаТаблицаСостояниеРегистрации (строки 1025-1060)

Текущий запрос:
```sql
ВЫБРАТЬ
    ФормированиеНомераПробы.Дата КАК Период,
    ФормированиеНомераПробы.ТочкаМаршрута КАК ТочкаМаршрута,
    ФормированиеНомераПробы.Ссылка КАК Регистратор,
    ФормированиеНомераПробыТЧ.ДокументРегистрации КАК ДокументРегистрации,
    &Пользователь КАК Пользователь,
    Регистрация.ТранспортноеСредство КАК ТранспортноеСредство,
    ЗНАЧЕНИЕ(Перечисление.гкс_СостоянияРегистрации.ВзятыПробы) КАК Состояние,
    Регистрация.ТипРегистрации КАК ТипРегистрации,
    Регистрация.ВидПеревозки КАК ВидПеревозки,
    ФормированиеНомераПробы.МестнаяДата КАК МестнаяДата
ИЗ
    Документ.гкс_ФормированиеНомераПробы.СписокРегистраций КАК ФормированиеНомераПробыТЧ
        ВНУТРЕННЕЕ СОЕДИНЕНИЕ Документ.гкс_ФормированиеНомераПробы КАК ФормированиеНомераПробы
        ПО ФормированиеНомераПробыТЧ.Ссылка = ФормированиеНомераПробы.Ссылка
        ВНУТРЕННЕЕ СОЕДИНЕНИЕ Документ.гкс_РегистрацияНаПЛК КАК Регистрация
        ПО ФормированиеНомераПробыТЧ.ДокументРегистрации = Регистрация.Ссылка
ГДЕ
    ФормированиеНомераПробыТЧ.Ссылка = &Ссылка
    И ФормированиеНомераПробыТЧ.ДокументРегистрации ССЫЛКА Документ.гкс_РегистрацияНаПЛК
```

**Проблема:** Запрос не проверяет, есть ли ДокументРегистрации в РС `гкс_КомпозитныеПробы`. Все единичные пробы безусловно пишут "ВзятыПробы".

### 3.2 Документ гкс_ФормированиеНомераПробы — МодульОбъекта

#### Цепочка вызовов при проведении (ОбработкаПроведения, строки 29-56)

```
1. ОбработкаПроведения()
2. → гкс_ПроведениеДокументов.ОбработкаПроведенияДокумента()
3.   → ДанныеДокументаДляПроведения() [ManagerModule]
4.     → ТекстЗапросаТаблицаСостояниеРегистрации() ← ТОЧКА МОДИФИКАЦИИ
5. → СформироватьЛабораторныйАнализПоНеобходимости()
6. → ЗаписатьСопоставлениеФНПИЛабАнализа()
```

#### Связь с требованием
Движения по РС `гкс_СостоянияРегистрации` формируются на шаге 4. Именно здесь нужно добавить условие-исключение.

**Когда использовать:** Если нужно убрать движения ТОЛЬКО для единичных проб, созданных по усиленному контролю, а остальные единичные пробы в композитных должны по-прежнему менять состояние.

**Суть:** LEFT JOIN к `гкс_КомпозитныеПробы` + LEFT JOIN к `гкс_СопоставлениеФНПЛабАнализа` (поле `УсиленныйКонтроль = Истина`) + условие-исключение.

**Минусы:** Сложнее, 2 LEFT JOIN, зависит от наличия записи в `гкс_СопоставлениеФНПЛабАнализа` (которая может быть создана позже при формировании ЛабАнализа).

**Важное замечание к Варианту Б:** Запись в `гкс_СопоставлениеФНПЛабАнализа` создаётся в `ОбработкаПроведения` (ObjectModule.bsl:52) ПОСЛЕ формирования движений. То есть на момент проведения запись может ещё не существовать. В этом случае JOIN не найдёт совпадения и движение всё равно сформируется. Для корректной работы Варианта Б нужно переместить вызов `ЗаписатьСопоставлениеФНПИЛабАнализа` ДО формирования движений, что потребует рефакторинга `ОбработкаПроведения`. Поэтому **Вариант А предпочтительнее**.

## 5. Чек-лист верификации

- [ ] Требование 1 → Точка модификации 1: LEFT JOIN к `гкс_КомпозитныеПробы` + условие `ЕСТЬ NULL` исключает регистрации из композитных проб
- [ ] Требование 2 → Обратная совместимость: для обычных единичных проб (не входящих в композитные) LEFT JOIN даст NULL, условие `ЕСТЬ NULL` будет истинным → поведение не изменится
- [ ] Побочные эффекты проверены: `find_referencing_symbols` показал, что `ТекстЗапросаТаблицаСостояниеРегистрации` вызывается только из `ДанныеДокументаДляПроведения` того же модуля
- [ ] LEFT JOIN не потеряет строки: используется LEFT (не INNER), поэтому строки без записей в КомпозитныеПробы сохраняются
- [ ] Условие `ЕСТЬ NULL` корректно: отфильтровывает только строки, где есть совпадение (т.е. регистрация входит в композитную пробу)

## 6. Риски и открытые вопросы

### Риски
1. **Множественные записи в гкс_КомпозитныеПробы:** Если для одной ДокументРегистрации есть несколько записей в РС КомпозитныеПробы, LEFT JOIN может дать дубликаты. Для исключения достаточно добавить `РАЗЛИЧНЫЕ` в выборку или подзапрос с `В (ВЫБРАТЬ...)` вместо LEFT JOIN. Рекомендуется проверить уникальность ДокументРегистрации в РС.

### Открытые вопросы
1. **Перепроведение:** Если ФНП уже был проведён (до исправления) и записал "ВзятыПробы" — нужно ли перепроведение таких документов для удаления ошибочных записей из РС?
2. **Выбор варианта:** ТЗ говорит "для единичного ТС по УК". Подготовлено два варианта реализации (см. раздел 4):
   - **Вариант А** — исключить ВСЕ единичные ФНП в композитных пробах (рекомендуется, проще и надёжнее)
   - **Вариант Б** — исключить только единичные ФНП по УК (точнее, но сложнее и требует рефакторинга)
