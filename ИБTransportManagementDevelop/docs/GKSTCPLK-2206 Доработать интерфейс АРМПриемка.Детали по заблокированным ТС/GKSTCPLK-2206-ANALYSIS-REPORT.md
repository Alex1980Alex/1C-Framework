## 1. Описание задачи

### 1.1 Требования

**Контекст:** АРМ Приемки -> правая панель "Детали" -> секция "Анализы". При включённой ФО `гкс_ИспользоватьЗаблокированныеТС`.

**Требование 1:** Вывести на форму причину блокировки для заблокированных ТС. Необходимо различать 5 типов причин:

1. Заблокировано, т.к. ждём результата по входному контролю
2. Заблокировано, потому что ждём результат по первому ТС *(ссылка на ЛА)*
3. Заблокировано, потому что анализ по первому ТС не прошёл *(ссылка на ЛА)*, ждём результата проверки на усиленный контроль текущей записи
4. Заблокировано, потому что ждём результат на промежуточный композит предыдущей группы
5. Заблокировано, потому что не прошёл анализ на промежуточный композит предыдущей группы *(ссылка на ЛА)*, ждём результата проверки на усиленный контроль текущей записи

### 1.2 Суть проблемы

**Что сейчас:** В списке регистраций АРМ Приемки есть колонка-иконка "Заблокировано" (Булево), но при выборе строки в панели "Детали" не отображается **причина** блокировки. Пользователь видит только факт блокировки, но не понимает почему ТС заблокировано и какой ЛА блокирует.

**Что должно быть:** В секции "Анализы" (правая панель "Детали") должен отображаться текст причины блокировки и гиперссылка на блокирующий лабораторный анализ (если применимо).

#### Текущий SQL (ObjectModule.bsl, строка 279-325)

2-пакетный запрос:

#### Логика заполнения (ManagerModule.bsl) — ВЕРИФИЦИРОВАНО

- `ЗаписатьБлокировкуТС()` (строка 14) — блокировка по правилу "Первое ТС": `БлокирующаяРегистрация` = первое ТС, `БлокирующаяГруппаТС` = пусто
- `ЗаписатьБлокировкуГруппыТС()` (строка 36) — блокировка по правилу "Группа ТС": `БлокирующаяГруппаТС` = предыдущая группа, `БлокирующаяРегистрация` = пусто
- `ОбновитьСостояниеБлокировки()` (строка 64) — обновляет при завершении ЛА: КачествоПринято -> Разблокировано; КачествоНеПринято/РПП -> БлокирующееСостояниеКачества

### 3.3 Маппинг причин блокировки на данные регистра

| # | Причина | Условие в регистре | Ссылка на ЛА |
|---|---------|-------------------|--------------|
| 1 | Ждём результата по входному контролю | `БлокирующаяРегистрация` != Пусто, `БлокирующаяГруппаТС` = Пусто, `БлокирующееСостояниеКачества` = Пусто, у `БлокирующаяРегистрация` нет связанного ЛА (Приемка) | Нет |
| 2 | Ждём результат по первому ТС | То же, но у `БлокирующаяРегистрация` ЕСТЬ связанный ЛА (Приемка) | ЛА блокирующей регистрации |
| 3 | Первое ТС не прошло, ждём УК | `БлокирующаяРегистрация` != Пусто, `БлокирующееСостояниеКачества` IN {КачествоНеПринято, РезультатыПробПолучены} | ЛА блокирующей регистрации |
| 4 | Ждём промежуточный композит группы | `БлокирующаяГруппаТС` != Пусто, `БлокирующееСостояниеКачества` = Пусто | Нет |
| 5 | Группа не прошла, ждём УК | `БлокирующаяГруппаТС` != Пусто, `БлокирующееСостояниеКачества` IN {КачествоНеПринято, РезультатыПробПолучены} | ЛА группы (через СопоставлениеФНП) |

- Запрос к `гкс_ЗаблокированныеРегистрацииУсиленныйКонтроль` с `Разблокировано = Ложь`

- Возвращает структуру:
  ```
  { ЕстьБлокировка: Булево,
    ТекстПричины: Строка,
    ЛабораторныйАнализ: ДокументСсылка.гкс_ЛабораторныйАнализ }
  ```

SQL запроса (**ИСПРАВЛЕН** — см. раздел 10.2 для полной верифицированной версии с двумя JOIN-цепочками):
```sql
-- Нужны ДВЕ отдельные цепочки LEFT JOIN:
-- Цепочка 1: БлокирующаяРегистрация → ФНП → Сопоставление(Приемка) → ЛА (причины 1-3)
-- Цепочка 2: БлокирующаяГруппаТС → СоставГруппТранспорта → ФНП → Сопоставление(ПромежуточныйКомпозит) → ЛА (причины 4-5)

-- См. полный верифицированный SQL в разделе 10.2
```

Логика определения причины (5 веток, 2 поля ЛА):
```
Если БлокирующаяРегистрация != Пусто:
    Если БлокирующееСостояниеКачества = Пусто:

    Если БлокирующееСостояниеКачества = Пусто -> Причина 4 (ждём композит группы)
    Иначе -> Причина 5 (группа не прошла, ждём УК), ссылка = ЛАГруппа
```

### 10.1 Ключевое открытие: нужны ДВА отдельных LEFT JOIN

Исходный SQL в Точке 1 использует одну цепочку LEFT JOIN через `БлокирующаяРегистрация`. Но реальные данные показали, что **для причин 4-5 (Группа ТС)** нужна отдельная цепочка через `БлокирующаяГруппаТС → СоставГруппТранспорта → ФНП → Сопоставление`.

#### Цепочка 1: "Первое ТС" (причины 1-3)
```
БлокирующаяРегистрация
  → ФНП.СписокРегистраций (ДокументРегистрации = БлокирующаяРегистрация)
    → гкс_СопоставлениеФНПЛабАнализа (НазначениеИспользования = Приемка, ТипПробы = Единичная)
      → ЛабораторныйАнализ
```

#### Цепочка 2: "Группа ТС" (причины 4-5)
```
БлокирующаяГруппаТС
  → гкс_СоставГруппТранспорта (ГруппаТС = БлокирующаяГруппаТС)
    → ФНП.СписокРегистраций (ДокументРегистрации = РегистрацияТранспорта)
      → гкс_СопоставлениеФНПЛабАнализа (НазначениеИспользования = ПромежуточныйКомпозит)
        → ЛабораторныйАнализ
```

**Важно:** Цепочка 2 даёт множественные строки (несколько регистраций в группе), нужна агрегация (МАКСИМУМ) или ПЕРВЫЕ 1.

### 10.2 Исправленный SQL

### 10.5 Замечания по имплементации

1. **Имя поля `НазначениеИспользования`:** В регистре `гкс_СопоставлениеФНПЛабАнализа` поле называется `гкс_НазначениеИспользованияКачества` (с префиксом `гкс_`). В исходном анализе было указано без префикса — исправлено.

2. **Имя поля `ДокументРегистрации` в `гкс_СоставГруппТранспорта`:** В регистре `гкс_СоставГруппТранспорта` поле для регистрации называется `РегистрацияТранспорта`, а НЕ `ДокументРегистрации`.

3. **Дубли в цепочке "Группа ТС":** Одна группа содержит несколько регистраций → JOIN даёт несколько строк на одну заблокированную регистрацию. Решение: `ВЫБРАТЬ РАЗЛИЧНЫЕ` или `ПЕРВЫЕ 1` в финальном запросе.

4. **Причина 1 ("входной контроль"):** В текущих тестовых данных нет примеров — все блокирующие регистрации уже имеют ЛА Приемка. Причина возникает только в начальном состоянии, когда блокирующая регистрация ещё не прошла анализ. Код ветки 1 протестировать можно, удалив ЛА Приемка у блокирующей регистрации.

5. **Причина 5 ("группа не прошла"):** Нет примеров в текущей базе. Возникает когда промежуточный композит группы показал КачествоНеПринято. Для теста нужно создать соответствующую запись в регистре.
