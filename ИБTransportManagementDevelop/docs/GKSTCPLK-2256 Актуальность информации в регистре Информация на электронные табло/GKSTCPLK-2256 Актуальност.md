## Описание задачи

Регистр сведений **"Информация на электронные табло"** (`гкс_ЭлектронныеТабло`) — промежуточный кэш для передачи данных на физические табло через RabbitMQ. Данные формируются внутри 1С и должны отображаться в реальном времени.

**Ключевое требование**: данные НЕ должны зависать в регистре. Записи за вчерашний день — быть не должно.

## Перечень проблем (из диалога)

### Проблема 1: Записи для ненастроенных видов табло

> "Он не смотрит на наличие настроенных табло. Генерит тупо сообщение... записи есть по тем видам табло, которые даже не настроены" (стр. 45-47, 67-69)

Настроено только 2 табло (оба НеПрошедшиеРегистрацию на Светлом), но в регистре появляются записи для НазначениеНаВесы, НазначениеНаВыгрузку, ОжиданияПроб и других видов — т.е. для табло, которых физически не существует на площадке.

**Вопрос заказчика**: "Зачем генерировать записи, если под них нет табло?"

### Проблема 2: Записи "зависают" — не уходят при прохождении по статусам

> "Из-за этого в этом регистре подвисают сообщения. По идее, сообщение за вчерашний день быть не должно" (стр. 49)
> "Машина уже приехала, она уже уехала, она до сих пор не откликается" (стр. 67)

ТС, прошедшие весь маршрут (статус Убыл), продолжают отображаться на табло. Записи висят месяцами.

### Проблема 3: Номенклатура в настройке есть, но фильтр в коде не реализован

> "Есть вид табло НеПрошедшиеРегистрацию. В настройках электронного табло есть номенклатура, но судя по куску кода, там нету отбора по номенклатуре" (стр. 85-87)
> "Либо лишнее поле, либо там не сделан фильтр" (стр. 89)

На форме настройки табло есть поле "Номенклатура" (см. скриншот `Не прошедшие регистрацию .jpg`), но в запросе `ТекстЗапросаОтображениеНаТаблоНепрошедшиеРегистраци()` условие `ГДЕ` содержит только ТочкаМаршрута и ВидТабло — номенклатура не учитывается.

### Проблема 4: Дублирующие записи с разной номенклатурой

Одно ТС с одним документом регистрации попадает в регистр несколько раз с разными номенклатурами:
- **Светлый**: разгрузка — 3 записи на одно ТС (Пшеница 3кл, 4кл, продовольственная) — см. `Разгрузка по три записи_1.jpg`
- **КАТ Погрузка**: дубли Шрот соевый / Оболочка соевая — см. `КАТ. Погрузка. дублирующие записи.jpg`
- **КАТ Разгрузка**: дубли Соевые бобы / Семена подсолнечника — см. `КАТ. Разгрузка. дублирующие записи.jpg`

### Проблема 5: Возможная потеря записей

> "Берёт нечто срез последних... последние три записи, что-то такое. Не мешало бы проверить, не теряем ли мы случайно записи" (стр. 64, 71)

В коде используется `ПЕРВЫЕ 10` (для запроса регистраций) и `ПЕРВЫЕ 4` (для отображения). Если одновременно на площадке более 10 активных регистраций — часть ТС может не попасть на табло.

### Проблема 6: Регистр неинформативен для расследования инцидентов

> "Когда тебе звонят и спрашивают, почему нет информации — очень сложно найти этот момент. С этим регистром разбираться... записи оттуда уходят" (стр. 99-101)

Регистр перезаписывается целиком (замена по фильтрам) — нет истории, что было на табло в конкретный момент.

## Указания заказчика

1. **"Сначала разобраться с механизмом записи в этот регистр"** (стр. 57, 75, 101-103) — понять, как формируется, прежде чем чинить
2. **"Светлый — один вид табло, КАТ — два других"** (стр. 73) — на КАТе случай интереснее
3. **"Может быть, стоит переписать как-то"** (стр. 101) — возможен рефакторинг, не просто фиксы
4. **"Машины, которые сегодня не записывались, завтра их быть не должно"** (стр. 75) — данные за прошлые сутки недопустимы
