# GKSTCPLK-2256 — Баги табло: было/стало

Регистр сведений `ИнформацияНаЭлектронныеТабло` — центральное звено системы отображения статусов ТС на физических табло. Обновляется через два пути: событийный (Путь А) и регламентный (Путь Б). В процессе эксплуатации выявлен букет проблем — от засирания регистра мусорными записями до потери валидных данных.

---

## 1. Зависание записей НазначениеНаВесы
**Критичность**: Критичный  |  **Статус**: Реализовано  |  **Точка исправления**: `гкс_ИнтеграцияСЭлектроннымТаблоСервер.ПолучитьСписокРегистрацийДляТабло()`

### Было
В процедуре `ПолучитьСписокРегистрацийДляТабло()` общего модуля `гкс_ИнтеграцияСЭлектроннымТаблоСервер` для видов табло `НазначениеНаВесы` и `НеПрошедшиеРегистрацию` тупо забыли поставить фильтр по состояниям. Для `ОжиданияПроб` и `НазначениеНаВыгрузку` фильтр `ГДЕ Состояние В(&СписокСостояний)` присутствует — ограничивает выборку нужными статусами. А вот весы и нерегистрированные тянут всё подряд.

Запрос дергает все 17 состояний из регистра за последние 24 часа (ТочкаОтсчета = ТекущаяДата - 86400). ТС со статусом "Убыл", "Отменён" и прочим мусором спокойно попадают в итоговый набор. Дальше при каждом триггере — любая смена состояния любого ТС на площадке — вызывается `ОбновитьТабло()`, который делает `НаборЗаписей.Записать(Истина)`. Этот набор пишется вслепую, с заменой, и зависшие записи снова оказываются в регистре.

Результат: из 64 записей НазначениеНаВесы в testdb1c только 6 валидных (9.4%). Остальные 58 — мусор, который висит на табло мёртвым грузом. 36 записей со статусом "Убыл" и прочий хлам.

### Стало
В запрос `ПолучитьСписокРегистрацийДляТабло()` добавлен параметр `СписокСостояний` со значением `Прибыл` и условие `ГДЕ Состояние В(&СписокСостояний)`. Теперь запрос не жрёт всё подряд, а забирает только ТС в состоянии "Прибыл". Мусорные записи с "Убыл" и прочими статусами отсекаются на уровне запроса, регистр не засирается, на табло весов попадают только реально нужные машины.

## 2. Номенклатура не учитывается в НеПрошедшиеРегистрацию
**Критичность**: Критичный  |  **Статус**: Реализовано  |  **Точка исправления**: `гкс_ИнтеграцияСЭлектроннымТаблоСервер.ПолучитьСписокРегистрацийДляТабло()`

### Было
Путь Б (регламентный) через `гкс_ОбновлениеТаблоЭлектроннойОчереди` → `гкс_ЭлектроннаяОчередь.ОбновлениеТаблоЭлектроннойОчереди()` → `гкс_ИнтеграцияСЭлектроннымТаблоСервер.ОбновитьТаблоДляЭлектроннойОчереди()` передаёт параметр `Номенклатура = Неопределено`. Это hardcoded значение — номенклатура тупо не передаётся.

Фильтры замены набора в Пути Б: `ТочкаМаршрута + ВидТабло`. Номенклатуры в фильтре нет, поэтому все номенклатуры сваливаются в одну кучу внутри одного набора. Для сравнения, Путь А использует фильтр `ТочкаМаршрута + ВидТабло + Номенклатура` — каждая номенклатура живёт в отдельном слоте. При замене набора одной номенклатуры записи с другими номенклатурами остаются нетронутыми, но в Пути Б это не работает — всё перемешано.

Фильтр по номенклатуре просто не стоит, и резать данные по номенклатуре невозможно. На табло "Не прошедшие регистрацию" всё идёт единым нефильтрованным потоком.

### Стало
В запрос `ПолучитьСписокРегистрацийДляТабло()` добавлен параметрический фильтр `&УсловиеНоменклатуры`. Логика: если параметр `Номенклатура` заполнен — подставляется условие `ДокРегистрацияНаПЛК.Номенклатура = &Номенклатура`. Если не заполнен — подставляется `ИСТИНА` (без фильтра, обратная совместимость). Теперь Путь Б может корректно фильтровать по номенклатуре, и записи не перемешиваются.

## 3. Зарегистрированные ТС на табло НеПрошедшиеРегистрацию
**Критичность**: Важный  |  **Статус**: Реализовано  |  **Точка исправления**: `гкс_СтатусыЗаписейВОчередиПриемкиПЛК.ПолучитьСписокЗаписейВОчередьДляТабло()`

### Было
Процедура `ПолучитьСписокЗаписейВОчередьДляТабло()` в модуле `гкс_СтатусыЗаписейВОчередиПриемкиПЛК` берёт `ПЕРВЫЕ 15` записей из электронной очереди. Запрос выбирает данные из очереди, но не делает JOIN с документом `гкс_РегистрацияНаПЛК`. Нет проверки — а зарегистрировано ли ТС вообще?

Если ТС прошло регистрацию и уже двигается по маршруту (взвешивание, пробы, выгрузка) — оно всё равно продолжает числиться в электронной очереди приёмки. И спокойно отображается на табло "Не прошедшие регистрацию". Запрос не отсекает зарегистрированные машины, фильтр не стоит, и на табло висят записи, которым там уже не место.

### Стало
В запрос добавлен `LEFT JOIN Документ.гкс_РегистрацияНаПЛК` через связку `ОчередьПриемкиПЛК.НомерТранспортногоСредства = ТранспортныеСредства.Наименование` (через справочник ТС) с дополнительными условиями по `ТочкаМаршрута` и `Проведен = ИСТИНА`. В секцию WHERE добавлено: `РегистрацияНаПЛК.Ссылка ЕСТЬ NULL` — теперь выбираются только те записи очереди, для которых нет проведённого документа регистрации. Зарегистрированные ТС отсекаются, на табло попадают только реально незарегистрированные.

## 4. Дублирование ТС с разной номенклатурой
**Критичность**: Средний  |  **Статус**: Реализовано  |  **Точка исправления**: `гкс_ИнтеграцияСЭлектроннымТаблоСервер.ПолучитьСписокРегистрацийДляТабло()` + RC-5

### Было
В Пути А номенклатура входит в фильтр замены набора: `НаборЗаписей.Отбор.Номенклатура.Установить(...)`. Если ТС связано с тремя номенклатурами (Пшеница 3кл, 4кл, продовольственная) — каждая образует отдельный "слот" в регистре. Замена по фильтру `ТочкаМаршрута + ВидТабло + Номенклатура` не трогает другие номенклатуры. Итог: одно ТС = 3 строки на табло. В testdb1c С111СС39 имел 8 дублей.

Вторая часть проблемы: `ПЕРВЫЕ 10` стоял в Пакете 1 запроса — до фильтрации по номенклатуре. Лимит резал сырые данные, и после применения фильтра по номенклатуре записей могло остаться 0. Получали пустой набор, хотя данные реально есть — просто не попали в первую десятку.

### Стало
Фильтр по номенклатуре добавлен прямо в запрос (Точка 4) — теперь номенклатура учитывается на этапе выборки, а не только при записи набора. Оператор `ПЕРВЫЕ 10` перенесён из Пакета 1 в Пакет 2 (после фильтрации). Теперь лимит применяется к уже отфильтрованным данным, и дублирование по номенклатурам устранено на корню.

## 5. Записи для ненастроенных видов табло
**Критичность**: Средний  |  **Статус**: Реализовано  |  **Точка исправления**: `гкс_ИнтеграцияСЭлектроннымТаблоСервер.ЗарегистрироватьОбъектКОбменуСТабло()`

### Было
В процедуре `ЗарегистрироватьОбъектКОбменуСТабло()` порядок шагов следующий: [1] `ОбновитьТабло()` — безусловная запись в регистр; [2] `СтруктураОтбораПоВидуТабло()` — формирование фильтров; [3] `ПолучитьНастройкиПоВидуТабло()` — проверка, есть ли физическое табло; [4] `ОтправитьДанныеНаЭлектронноеТабло()` — отправка в RabbitMQ.

Шаг [1] выполняется ДО шага [3]. Данные пишутся в регистр безусловно, а проверка "а есть ли вообще табло?" — потом. Если физического табло нет — RMQ не отправляется (это правильно), но записи уже лежат в регистре мёртвым грузом. Из 113 записей в testdb1c — 98 (86.7%) для ненастроенных видов. Регистр засирается данными, которые никто никогда не увидит.

### Стало
Проверка `ПолучитьНастройкиПоВидуТабло()` перенесена ПЕРЕД `ОбновитьТабло()`. Новый порядок: [3] → [1] → [4]. Если настроенных физических табло для данного вида нет — запись в регистр вообще не происходит. Регистр не засирается phantom-записями, пишутся только данные для реально существующих табло.

## 6. Потеря записей при ПЕРВЫЕ 10
**Критичность**: Низкий (переоценён)  |  **Статус**: Снят  |  **Точка исправления**: фактически решён исправлениями Точки 1 + Точки 4

### Было
В Пути А процедура `ПолучитьСписокРегистрацийДляТабло()` использует `ПЕРВЫЕ 10`. В Пути Б процедура `ПолучитьСписокЗаписейВОчередьДляТабло()` использует `ПЕРВЫЕ 15`. Теоретически, если на площадке одновременно больше 10 (или 15) активных регистраций — хвост не попадает в регистр.

### Почему это не проблема
После исправлений Точки 1 и Точки 4 выборка стала узкой. `ПЕРВЫЕ 10` теперь режет не "все регистрации за сутки", а "ТС на конкретной площадке, конкретный вид табло, конкретная номенклатура, в конкретном состоянии (например, только Прибыл), за последние 24 часа". Чтобы лимит сработал, нужно 10+ машин одновременно с одной номенклатурой в одном состоянии на одной площадке — практически нереальный сценарий. Физическое табло показывает максимум 3 строки, так что даже при 10 записях в регистре отображаются только первые 3.

## 7. Нет истории изменений регистра
**Критичность**: Низкий  |  **Статус**: В плане  |  **Точка исправления**: Регистр сведений `гкс_ИнформацияНаЭлектронныеТабло`

### Было
Регистр сведений `гкс_ИнформацияНаЭлектронныеТабло` — обычный РС без периодичности и без истории. Механизм `Записать(Истина)` полностью заменяет набор записей по фильтру при каждом обновлении. Предыдущее состояние безвозвратно теряется.

Нет возможности узнать: что было раньше, когда конкретное ТС появилось на табло, когда исчезло, кто инициировал обновление. При расследовании инцидентов — полный вакуум информации. Сказать, что происходило с табло час назад, невозможно — данные уже перезаписаны.

---

## Сообщение коммита

```
fix: Исправлена актуальность данных в регистре Информация на электронные табло

Как было/ошибочное поведение:
- Регистр сведений гкс_ИнформацияНаЭлектронныеТабло засорялся мусорными записями (86.7% от общего числа)
- НазначениеНаВесы: запрос тянул все 17 состояний за 24 часа без фильтра — ТС со статусом «Убыл» висели на табло (90.6% записей — мусор)
- НеПрошедшиеРегистрацию: зарегистрированные ТС продолжали отображаться на табло — не было JOIN с документом РегистрацияНаПЛК
- НеПрошедшиеРегистрацию: номенклатура не передавалась (hardcoded Неопределено) — все номенклатуры в одном нефильтрованном блоке
- Дубли: одно ТС с 3 номенклатурами = 3 строки на табло, т.к. номенклатура входила в фильтр замены набора
- Мусорные записи: данные писались в регистр безусловно ДО проверки наличия физического табло

Как стало/исправление:
- Точка 1: добавлен фильтр ГДЕ Состояние В(&СписокСостояний) для НазначениеНаВесы — только состояние «Прибыл»
- Точка 3: добавлен LEFT JOIN с гкс_РегистрацияНаПЛК + условие Ссылка ЕСТЬ NULL — зарегистрированные ТС отсекаются
- Точка 4: добавлен параметрический фильтр &УсловиеНоменклатуры в запрос ПолучитьСписокРегистрацийДляТабло
- RC-5: ПЕРВЫЕ 10 перенесён из Пакета 1 в Пакет 2 (после фильтра по номенклатуре)
- M-1: проверка ПолучитьНастройкиПоВидуТабло() перенесена ПЕРЕД записью в регистр — нет табло = нет записи

Изменённые объекты:
- Общий модуль гкс_ИнтеграцияСЭлектроннымТаблоСервер: процедура ПолучитьСписокРегистрацийДляТабло (Точка 1, 4, RC-5), процедура ЗарегистрироватьОбъектКОбменуСТабло (M-1)
- Регистр сведений гкс_СтатусыЗаписейВОчередиПриемкиПЛК: модуль менеджера, процедура ПолучитьСписокЗаписейВОчередьДляТабло (Точка 3)
- Регистр сведений гкс_СостоянияРегистрации: модуль набора записей, процедура ЗарегистрироватьОбъектКОбменуСТабло (M-1)

МЕТАДАННЫЕ: GKSTCPLK-2256
```

### Стало
В плане. Рассматриваются два варианта: [1] включить журнал регистрации с фильтром по метаданным регистра — даст минимальную историю кто и когда менял; [2] создать отдельный РС-лог, куда перед каждым `Записать(Истина)` будет сбрасываться предыдущее состояние набора. Второй вариант даёт полную историю, но требует доработки механизма записи.
