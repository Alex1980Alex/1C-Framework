## Executive Summary

В рамках задачи GKSTCPLK-2256 проведён анализ и устранение критических ошибок в механизме формирования данных для электронных табло на предприятиях ПЛК (Светлый, КАТ). Основная проблема заключалась в «зависании» устаревших записей в регистре сведений — транспортные средства (ТС) не удалялись с табло после прохождения маршрута. Корневой причиной является отсутствие фильтрации по актуальному состоянию регистрации в исходных запросах.

На 02.04.2026 реализованы исправления для 5 из 7 дефектов: два критических (фильтр по состоянию, фильтр по номенклатуре в отображении), два средних (дубли по номенклатуре при записи, мусорные записи для ненастроенных табло) и один важный (зарегистрированные ТС на табло очереди). Остаются нереализованными: лимит ПЕРВЫЕ 10 (RC-5, требует диагностики) и отсутствие истории (RC-6, архитектурный рефакторинг).

### Суть проблемы

Данные на физических электронных табло отображаются некорректно: записи о ТС «зависают» и не очищаются после того, как машина проходит точку маршрута. Причина кроется в логике формирования записей в регистре `РегистрСведений.гкс_ЭлектронныеТабло` — запросы игнорируют текущий статус регистрации ТС.

| **КАТ**     | НазначениеНаВыгрузку   | 4 шт. (диапазон `172.31.28.186-199`)         |       3        |

## 3. Корневые причины

**RC-1** — Записи для ненастроенных видов табло `ИСПРАВЛЕНО — M-1` → REQ-1
- **Файл:** `RecordSetModule.bsl`
- **Суть:** `СформироватьВариантыДляТабло` не проверяет наличие настроек. `ОбновитьТабло` пишет безусловно (стр.100), `ПолучитьНастройкиПоВидуТабло` вызывается после (стр.265)

**RC-2** — Нет фильтра по состоянию `ИСПРАВЛЕНО — Точка 1` → REQ-2
- **Файл:** `Module.bsl` стр.274-305
- **Суть:** Параметр `СписокСостояний` инициализируется (стр.272), но не используется в WHERE. В ОжиданияПроб (стр.328) и НазначениеНаВыгрузку (стр.403) такой фильтр есть

**RC-3** — Нет фильтра по номенклатуре при записи `ИСПРАВЛЕНО — Точка 4` → REQ-3, REQ-4
- **Файл:** `Module.bsl` стр.274-305
- **Суть:** Параметр `&Номенклатура` подготавливается (стр.277), но в запросе не участвует → одна регистрация = N записей с разной номенклатурой

**RC-4** — Нет фильтра по номенклатуре в отображении `ИСПРАВЛЕНО — Точка 2` → REQ-3
- **Файл:** `ManagerModule.bsl` стр.44-62
- **Суть:** WHERE только `ТочкаМаршрута + ВидТабло`, нет `Номенклатура`. У НазначениеНаВесы (стр.88) фильтр ЕСТЬ

**RC-5** — Жёсткие лимиты (хардкод) `НЕ ИСПРАВЛЕНО` → REQ-5
- **Файл:** `Module.bsl` / `ManagerModule.bsl`
- **Суть:** `ПЕРВЫЕ 10` при записи, `ПЕРВЫЕ 4` при отображении

**RC-6** — Деструктивная перезапись без истории `НЕ ИСПРАВЛЕНО` → REQ-6
- **Файл:** Архитектура регистра
- **Суть:** Непериодический регистр, `Записать(Истина)` полностью затирает предыдущие данные

> **ВозвратАвто** — значение перечисления `гкс_ВидыЭлектронныхТабло` без реализации в коде (Dead Code).

## 3а. Карточки дефектов: воспроизведение, примеры, тестирование

### RC-1: Записи для ненастроенных видов табло `ИСПРАВЛЕНО — M-1 (02.04.2026)`

**В чём проблема:** На площадке Светлый настроены только 2 физических табло вида "НеПрошедшиеРегистрацию". Табло "НазначениеНаВесы", "НазначениеНаВыгрузку" и "ОжиданияПроб" на Светлом **не существуют** (они есть только на КАТе). Но при каждой смене состояния ТС код генерирует записи для **ВСЕХ** видов табло и пишет их в регистр — даже если физического табло нет.

**Почему так происходит:** Процедура `ЗарегистрироватьОбъектКОбменуСТабло` (RecordSetModule.bsl, стр.239-276) выполняет два шага в **неправильном порядке**:
1. **Шаг 1** (стр.251): `ОбновитьТабло()` — записи уже в регистре (безусловно!)
2. **Шаг 2** (стр.265): `ПолучитьНастройкиПоВидуТабло()` — только здесь проверяется, есть ли физическое табло. Если нет — RabbitMQ-сообщение не отправляется, но **записи в регистре уже остались**.

**Правильный порядок:** сначала проверить настройки (шаг 2), и только если табло существует — писать в регистр (шаг 1).

**Масштаб:** из 113 записей в регистре **98 (86.7%) — мусор** для несуществующих табло. Эти записи не влияют на отображение (RabbitMQ не отправляется), но засоряют базу и затрудняют диагностику.

**Почему не исправлено:** Низкий приоритет — мусорные записи не видны пользователям. Исправление (M-1) требует перестановки вызовов в процедуре, что может повлиять на площадки, где настройки добавляются динамически.

| Компонент | Описание |
| :--- | :--- |
| **Воспроизведение** | Сравнение записей регистра по `ВидТабло` с настройками `гкс_НастройкаЭлектронногоТабло`. Выявляются записи, для которых не существует настроек (мусор). |
| **Результат ДО** | 98 записей (НазначениеНаВесы: 64, НазначениеНаВыгрузку: 29, ОжиданияПроб: 5). |
| **Ожидание ПОСЛЕ** | Записи по ненастроенным видам табло должны отсутствовать (0 записей). |

**SQL воспроизведения:**
```sql
ВЫБРАТЬ
    Табло.ВидТабло,
    КОЛИЧЕСТВО(*) КАК Записей
ИЗ
    РегистрСведений.гкс_ЭлектронныеТабло КАК Табло
    ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.гкс_НастройкаЭлектронногоТабло КАК Настройки
        ПО Табло.ВидТабло = Настройки.ВидТабло
        И Табло.ТочкаМаршрута = Настройки.ТочкаМаршрута
ГДЕ
    Настройки.ВидТабло ЕСТЬ NULL
СГРУППИРОВАТЬ ПО
    Табло.ВидТабло
```

**Тест после исправления:** Запустить SQL. Ожидание: пустой результат.

### RC-2: Нет фильтра по состоянию (НазначениеНаВесы) `ИСПРАВЛЕНО — Точка 1`

**В чём проблема:** При каждом обновлении табло "НазначениеНаВесы" запрос `ПолучитьСписокРегистрацийДляТабло` выбирал **все** регистрации за последние сутки — включая ТС со статусом "Убыл" (уехали), "Выгружен" (уже разгрузились), "ВзвешенТара" (прошли весы). Эти "фантомы" записывались в регистр и отображались на физическом табло. Водители видели машины, которых давно нет на площадке.

**Почему так случилось:** Параметр `СписокСостояний = [Прибыл]` заполнялся (стр.272 Module.bsl), но **не использовался** в WHERE-условии запроса для ветки НазначениеНаВесы (стр.274-305). При этом для двух других видов табло — ОжиданияПроб (стр.328) и НазначениеНаВыгрузку (стр.403) — фильтр `ГДЕ Состояние В(&СписокСостояний)` уже был. То есть просто забыли добавить.

**Что исправлено:** Добавлены 2 строки — `ГДЕ РССостоянияРегистрации.Состояние В(&СписокСостояний)` (стр.287-288). Теперь в регистр попадают только ТС со статусом "Прибыл" — те, что реально ждут назначения на весы.

**Масштаб:** из 64 записей в регистре только 6 были валидными (9.4%). Остальные 58 — мусор, включая записи возрастом до 12 месяцев.

| Компонент | Описание |
| :--- | :--- |
| **Воспроизведение** | Запрос к регистру `гкс_ЭлектронныеТабло` LEFT JOIN `гкс_СостоянияРегистрации.СрезПоследних` с фильтром `ВидТабло=НазначениеНаВесы`. |
| **Результат ДО** | 64 записи (36 «Убыл», 6 «Прибыл», остальные промежуточные). |
| **Ожидание ПОСЛЕ** | Только записи со `Состояние = Прибыл`. |

**SQL воспроизведения:**
```sql
ВЫБРАТЬ
    Табло.Авто,
    Состояния.Состояние,
    КОЛИЧЕСТВО(*) КАК Кол
ИЗ
    РегистрСведений.гкс_ЭлектронныеТабло КАК Табло
    ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.гкс_СостоянияРегистрации.СрезПоследних КАК Состояния
        ПО Табло.ДокументРегистрации = Состояния.ДокументРегистрации
ГДЕ
    Табло.ВидТабло = ЗНАЧЕНИЕ(Перечисление.гкс_ВидыЭлектронныхТабло.НазначениеНаВесы)
СГРУППИРОВАТЬ ПО
    Табло.Авто,
    Состояния.Состояние
```

**Примеры из базы (ДО):**
- О909РУ — ТМУТ-0000476 от 14.05.2025, статус «Убыл» (висит 11 месяцев)
- Н006АЕ46 — ТМУТ-0000001 от 26.03.2025, статус «НеПринято» (висит 12 месяцев)

**Тест после исправления:** Запустить тот же SQL. Ожидание: все записи со `Состояние = Прибыл`. Если есть другие — фикс не работает.

### RC-3: Дубли по номенклатуре `ИСПРАВЛЕНО — Точка 4 (02.04.2026)`

**В чём проблема:** Одно и то же ТС появляется на табло несколько раз — по строке на каждую номенклатуру из документа регистрации. Например, если регистрация содержит "Пшеница 3кл" и "Пшеница 4кл", то на табло ТС будет показано 2 раза.

**Почему так происходит:** Механизм записи работает так:
1. `СформироватьВариантыДляТабло` (RecordSetModule.bsl, стр.149-150) **сворачивает варианты по всем колонкам**, включая `Номенклатура`. Если в регистрации 2 номенклатуры — создаётся 2 варианта.
2. Для каждого варианта вызывается `ОбновитьТабло` (Module.bsl). Набор записей создаётся с фильтром по `Номенклатура` (стр.64): `НаборЗаписей.Отбор.Номенклатура.Установить(Номенклатура)`.
3. Но запрос `ПолучитьСписокРегистрацийДляТабло` (стр.274-305) **не фильтрует по `&Номенклатура`** — он берёт ВСЕ регистрации на площадке.
4. Результат: одна и та же регистрация записывается в регистр с `Номенклатура = Пшеница 3кл`, а потом ещё раз с `Номенклатура = Пшеница 4кл`.

**Визуально:**
```
Документ ТМУТ-0004362 (А117СО62RUS): Пшеница 3кл + Пшеница 4кл
    ↓
Вариант 1: Номенклатура = Пшеница 3кл → ОбновитьТабло → запись в регистр
Вариант 2: Номенклатура = Пшеница 4кл → ОбновитьТабло → запись в регистр
    ↓
Регистр: 2 записи для одного ТС с разной номенклатурой
    ↓
Табло: А117СО62RUS отображается 2 раза
```

**Почему не исправлено:** Точка 4 (добавить `&Номенклатура` в WHERE запроса) отложена — проблема частично решается через Точку 2 (фильтр по номенклатуре при отображении не даёт дублям "вылезти" на конкретное табло).

| Компонент | Описание |
| :--- | :--- |
| **Воспроизведение** | Выборка с группировкой по ТС и документу, где количество различных номенклатур > 1. |
| **Результат ДО** | 5 ТС с дублями номенклатур. |
| **Ожидание ПОСЛЕ** | На одно ТС и один документ регистрации — строго 1 номенклатура. |

**SQL воспроизведения:**
```sql
ВЫБРАТЬ
    Табло.Авто,
    ПРЕДСТАВЛЕНИЕ(Табло.ДокументРегистрации) КАК ДокументРегистрации,
    Табло.ВидТабло,
    КОЛИЧЕСТВО(РАЗЛИЧНЫЕ Табло.Номенклатура) КАК КолНоменклатур
ИЗ
    РегистрСведений.гкс_ЭлектронныеТабло КАК Табло
СГРУППИРОВАТЬ ПО
    Табло.Авто, Табло.ДокументРегистрации, Табло.ВидТабло
ИМЕЮЩИЕ
    КОЛИЧЕСТВО(РАЗЛИЧНЫЕ Табло.Номенклатура) > 1
```

**Примеры из базы:**
- А117СО62RUS (ТМУТ-0004362, НазначениеНаВесы, 2 номенклатуры)
- В008АН136RUS (ТМУТ-0000002, НазначениеНаВесы, 2 номенклатуры)

**Тест после исправления:** Выполнить запрос. Ожидание: пустой результат.

### RC-4: Нет фильтра по номенклатуре в отображении НеПрошедшиеРегистрацию `ИСПРАВЛЕНО — Точка 2`

**В чём проблема:** Каждое физическое табло привязано к настройке в регистре `гкс_НастройкаЭлектронногоТабло`, где можно указать конкретную номенклатуру (например, "Пшеница"). Когда система формирует данные для отправки на табло, она выполняет запрос `ТекстЗапросаОтображениеНаТаблоНепрошедшиеРегистраци` (стр.44-62 ManagerModule.bsl). Этот запрос фильтровал записи только по `ТочкаМаршрута + ВидТабло`, но **игнорировал** поле `Номенклатура` из настройки. В итоге табло, настроенное на "Пшеницу", показывало ТС со ВСЕМИ номенклатурами — Рапс, Ячмень и т.д.

**Почему так случилось:** Для трёх других видов табло фильтр по номенклатуре уже был реализован. Например, запрос для НазначениеНаВесы (стр.88) содержит `ЭлектронныеТабло.Номенклатура = &Номенклатура`. Для НеПрошедшиеРегистрацию — просто забыли добавить.

**Что исправлено:** Добавлено условие с проверкой на пустую ссылку (стр.58-59):
`И (Номенклатура = &Номенклатура ИЛИ &Номенклатура = ПустаяСсылка)`.
Условие `ИЛИ ПустаяСсылка` нужно для обратной совместимости: если в настройке табло номенклатура не указана (пустая) — табло показывает ВСЕ записи, как раньше.

**Дополнительный нюанс — дубли:** В testdb1c у С111СС39 — 8 одинаковых записей с «Рапс (Россия)». Это дубли по полю `ЗаписьВОчередь` (разное время записи в очередь — регламентное задание каждый раз добавляло новую запись, не проверяя дубли). Точка 2 не устраняет эти дубли, но фильтр по номенклатуре не даёт им "вылезть" на чужое табло.

| Компонент | Описание |
| :--- | :--- |
| **Воспроизведение** | Запрос отображения с конкретной номенклатурой возвращает ВСЕ записи вне зависимости от неё. |

### RC-5: Лимит ПЕРВЫЕ 10 `НЕ ИСПРАВЛЕНО — диагностика`

**В чём проблема:** В коде есть два жёстко заданных лимита, которые обрезают данные:

1. **При записи в регистр** (Путь А): запрос `ПолучитьСписокРегистрацийДляТабло` (Module.bsl, стр.278) содержит `ВЫБРАТЬ РАЗЛИЧНЫЕ ПЕРВЫЕ 10`. Если на площадке одновременно > 10 ТС в нужном состоянии — 11-е и далее **не попадут** в регистр вообще.
2. **При записи в регистр** (Путь Б): запрос `ПолучитьСписокЗаписейВОчередьДляТабло` (ManagerModule.bsl, стр.143) содержит `ВЫБРАТЬ ПЕРВЫЕ 15`. Аналогично — 16-я запись в очереди теряется.
3. **При отображении**: запросы содержат `ПЕРВЫЕ 4` (заменяется на `КоличествоСтрокТабло` из настройки, обычно 3). Это ограничение корректно — физическое табло вмещает 3 строки.

**Почему это может быть проблемой:** Если в пиковый час на площадке одновременно прибыло 15 машин (все в состоянии "Прибыл"), то на табло "НазначениеНаВесы" попадут только первые 10. Водители оставшихся 5 ТС не увидят себя на табло и не поймут, что они в очереди.

**Смягчающий фактор:** Физическое табло показывает максимум 3 строки. Даже если в регистре 10 записей — водитель видит только 3. Потеря 11-й записи критична только если важен сам факт нахождения в регистре (например, для RabbitMQ-сообщений).

**Почему не исправлено:** Средний приоритет. Нужна диагностика — бывает ли реально > 10 одновременных ТС на одной площадке. Если нет — лимит не активен и проблема теоретическая.

| Компонент | Описание |
| :--- | :--- |
| **Воспроизведение** | Подсчёт количества прибывших ТС на каждой точке маршрута. Если > 10 — часть ТС теряется. |
| **Результат ДО** | Если `КолРегистраций > 10` на площадке, часть ТС не попадает на табло. |
| **Ожидание ПОСЛЕ** | Все прибывшие ТС отображаются без обрезки. |

**SQL диагностики:**
```sql
ВЫБРАТЬ
    Состояния.ТочкаМаршрута.Наименование КАК ТочкаМаршрута,
    КОЛИЧЕСТВО(РАЗЛИЧНЫЕ Состояния.ДокументРегистрации) КАК КолРегистраций
ИЗ
    РегистрСведений.гкс_СостоянияРегистрации.СрезПоследних КАК Состояния
ГДЕ
    Состояния.Состояние = ЗНАЧЕНИЕ(Перечисление.гкс_СостоянияРегистрации.Прибыл)
СГРУППИРОВАТЬ ПО
    Состояния.ТочкаМаршрута
```

**Тест:** Если `КолРегистраций > 10` — лимит активен, часть ТС потеряна.

#### 1. Текущий код

#### 4. Нюансы реализации

1. **Строковая связь** — `НомерТранспортногоСредства` (Строка) vs `ТранспортноеСредство.Наименование` (через точку). Нет индекса на СУБД. Для 15 записей допустимо, но при большом объёме может тормозить.

## 7. Тест-план

**Сценарий 1:** НазначениеНаВесы — запись уходит при смене состояния
- **Шаги:** Зарегистрировать ТС (Прибыл) → проверить на табло → установить ВзвешенБрутто
- **Ожидание:** ТС пропало с табло

**Сценарий 2:** НеПрошедшиеРегистрацию — фильтр по номенклатуре
- **Шаги:** 2 ТС в очереди (Пшеница + Ячмень) → открыть с Номенклатура=Пшеница
- **Ожидание:** Только Пшеница

**Сценарий 3:** Обратная совместимость — пустая номенклатура
- **Шаги:** Вызвать с Номенклатура=ПустаяСсылка
- **Ожидание:** Все записи без фильтрации

**Сценарий 4:** Зарегистрированное ТС уходит с НеПрошедшиеРегистрацию
- **Шаги:** ТС в очереди → РегистрацияНаПЛК → дождаться рег. задания
- **Ожидание:** ТС пропало (покрывает Точку 3)

**Сценарий 5:** Полный цикл жизни ТС
- **Шаги:** Очередь → Прибыл → ВзвешенБрутто → ВыгрузкаРазрешена → Выгружен → Убыл
- **Ожидание:** На каждом шаге ТС на одном табло или ни на одном
