# GKSTCPLK-2256 — Как работает механизм записи в регистр "Информация на электронные табло"

> Объяснение механизма для быстрого погружения в контекст задачи.

---

## Что такое регистр `гкс_ЭлектронныеТабло`

Это **промежуточный кэш** — буфер между бизнес-логикой 1С и физическими LED-табло на площадках (Светлый, КАТ). Физические табло подключены через **RabbitMQ**: 1С пишет данные в регистр, затем отправляет их в очередь RMQ, откуда табло считывают и отображают строки.

Регистр не хранит историю. Он работает как "доска объявлений": текущее состояние стирается и перезаписывается целиком при каждом обновлении.

---

### Детали по каждому виду

**1. НеПрошедшиеРегистрацию** — единственный вид с **рабочими настройками**.
- Обновляется регламентным заданием (Путь Б)
- На Светлом: 2 физических табло (IP: 172.20.23.250, 172.20.22.202)
- Комментарий в XML: `ERP-2056` (добавлен позже остальных)

**2. НазначениеНаВесы** — генерируется кодом, но **физических табло нет** ни на одной известной площадке.
- Триггер: состояние `Прибыл` (Условие 1 в `СформироватьВариантыДляТабло`)
- `СписокСостояний = [Прибыл]`
- Записи в базе: все мусорные (testdb1c: 30 зависших, PROD: 10, все со статусом "Убыл")
- Комментарий в XML: пуст (создан изначально, без номера задачи)

**3. НазначениеНаВыгрузку** — генерируется кодом, **настройки предположительно на КАТе** (4 табло по данным инструкции заказчика, но в testdb1c и PROD Светлого — нет).
- Триггер: состояние `ВыгрузкаРазрешена` (Условие 2)
- `СписокСостояний = [ВыгрузкаРазрешена]`
- Фильтр в запросе отображения: `ТочкаМаршрута + ВидТабло + ЯмаРазгрузки + Номенклатура` — полный

**4. ОжиданияПроб** — генерируется кодом двумя путями, **настройки предположительно на КАТе** (4 табло по данным инструкции).
- Триггеры: `ВыгрузкаРазрешена` (Условие 2, внутри вызова НазначениеНаВыгрузку) + `КачествоНеПринято` (Условие 3)
- `СписокСостояний = [ВыгрузкаРазрешена, КачествоНеПринято]`
- Фильтр в запросе отображения: `ТочкаМаршрута + ВидТабло + Весы`
- Комментарий в XML: `ERP-1425`

**5. ВозвратАвто** — **мёртвое значение**. Существует только в перечислении.
- В `СформироватьВариантыДляТабло` — **нет условия**, которое генерирует этот вид
- В `ТекстЗапросаПоВидуТаблоДляОтображения` — падает в `Иначе` → возвращает пустую строку `""`
- В обеих базах (testdb1c + PROD) — **0 записей**
- Не упоминается ни в одном BSL-модуле, кроме XML-определения
- Вероятно, задумывался при проектировании (по описанию заказчика: "Авто, не подходящие по качеству"), но **не был реализован**

## Два независимых пути обновления

Данные попадают в регистр **двумя разными способами** — и это ключевое для понимания всей архитектуры.

### Путь А — Событийный (реактивный)

**Когда срабатывает**: каждый раз, когда у регистрации меняется состояние. Полный список **17 состояний** (перечисление `гкс_СостоянияРегистрации`, по порядку):

| --- | -------------------------------------- | ------------------------ |
| 0   | Прибыл                                 | Прибыл                   |
| 1   | ВзвешенБрутто                          | Взвешен брутто           |
| 2   | НеПринятоПоПревышениюМаксимальногоВеса | Не принято по весу       |
| 3   | Регистрация                            | Регистрация              |
| 4   | ГотовКОтборуПроб                       | Готов к отбору проб      |
| 5   | ВзятыПробы                             | Взяты пробы              |
| 6   | РезультатыПробПолучены                 | Результаты проб получены |
| 7   | КачествоПринято                        | Качество принято         |
| 8   | КачествоНеПринято                      | Качество не принято      |
| 9   | ВыгрузкаРазрешена                      | Выгрузка разрешена       |
| 10  | Выгружен                               | Выгружен                 |
| 11  | ВзвешенТара                            | Взвешен тара             |

| 14  | ПринятыПробы                           | Приняты пробы            |
| 15  | ПогрузкаРазрешена                      | Погрузка разрешена       |
| 16  | Погружен                               | Погружен                 |

**Какие виды табло обслуживает**: НазначениеНаВесы, НазначениеНаВыгрузку, ОжиданияПроб.

**Соответствие состояний и видов табло** (из `СформироватьВариантыДляТабло`):

- **Прибыл** → НазначениеНаВесы, фильтр `[Прибыл]` — Усл.1: ТС только приехало
- **ВыгрузкаРазрешена** → НазначениеНаВыгрузку, фильтр `[ВыгрузкаРазрешена]` — Усл.2: разрешена выгрузка
- **ВыгрузкаРазрешена** → ОжиданияПроб, фильтр `[ВыгрузкаРазрешена, КачествоНеПринято]` — Усл.2+3: вложенный вызов из НазначениеНаВыгрузку
- **КачествоНеПринято** → ОжиданияПроб, фильтр `[ВыгрузкаРазрешена, КачествоНеПринято]` — Усл.3: качество отклонено
- **ВозвратАвто** → **Не реализован**: нет кода генерации
- **Все остальные (13 шт.)** → Не порождают вариантов для табло

**Цепочка вызовов**:

```
1. Оператор меняет состояние регистрации
      ↓
2. гкс_СостоянияРегистрации.ПриЗаписи()
      ↓
3. СформироватьВариантыДляТабло()
   Генерирует варианты для ВСЕХ видов табло, не только для настроенных.
   Это значит: даже если на площадке нет физического табло "ОжиданияПроб",
   код всё равно подготовит данные для этого вида.
      ↓
4. ЗарегистрироватьОбъектКОбменуСТабло()
      ↓
5. ОбновитьТабло()
   Запрос: ПолучитьСписокРегистрацийДляТабло()
   — берёт ПЕРВЫЕ 10 регистраций из СрезПоследних за последние 24 часа
   — набор записей пишется с заменой: Записать(Истина)
      ↓
6. ПолучитьНастройкиПоВидуТабло()
   ТОЛЬКО ЗДЕСЬ проверяется, есть ли физическое табло для этого вида.
   Если нет — RMQ-сообщение НЕ отправляется.
   НО: записи в регистре УЖЕ ЕСТЬ (шаг 5 выполнен раньше).
      ↓
7. ОтправитьДанныеНаЭлектронноеТабло()
   Отправка в RabbitMQ (только если настройка найдена).
```

гкс_СостоянияРегистрации.RecordSetModule
  ├─ ПередЗаписью → СформироватьВариантыДляТабло()        [стр. 111-154]
  │    Прибыл → ДобавитьВариантНазначениеНаВесы            [стр. 131]
  │    ВыгрузкаРазрешена → ДобавитьВариантНазначениеНаВыгрузку [стр. 137]
  │                        └─ ДобавитьВариантОжиданияПроб  [стр. 180, вложенный!]
  │    КачествоНеПринято → ДобавитьВариантОжиданияПроб     [стр. 144]
  │
  └─ ПриЗаписи → ЗарегистрироватьОбъектКОбменуСТабло()    [стр. 239-276]
       Для каждого варианта:
       ├─ [1] ОбновитьТабло(ВидТабло, Параметры)           — запись в регистр (БЕЗУСЛОВНО!)
       │    └─ ПолучитьСписокРегистрацийДляТабло()          — ПЕРВЫЕ 10 из СрезПоследних
       │    └─ НаборЗаписей.Записать(Истина)                — замена по фильтрам
       ├─ [2] СтруктураОтбораПоВидуТабло()                  — фильтры для настроек
       ├─ [3] ПолучитьНастройкиПоВидуТабло()                — есть ли физическое табло?
       └─ [4] ОтправитьДанныеНаЭлектронноеТабло()           — RabbitMQ (только если [3] нашёл)

**Ключевой дефект Пути А**: шаги 5 и 6 идут в неправильном порядке. Данные пишутся в регистр безусловно, а проверка наличия табло — после. Из-за этого регистр засоряется "мусорными" записями для видов табло, которых физически не существует на площадке.

### Путь Б — Регламентный (по расписанию)

**Когда срабатывает**: двумя способами:
1. **Регламентное задание** `гкс_ОбновлениеТаблоЭлектроннойОчереди` (по расписанию, `Use = false` по умолчанию!)
2. **Событие** — запись в РС `гкс_СтатусыЗаписейВОчередиПриемкиПЛК` (при изменении статуса в очереди)

**Какой вид табло обслуживает**: НеПрошедшиеРегистрацию (ТС в электронной очереди, ещё не зарегистрированные).

**Hardcoded параметры** (из `ОбновлениеТаблоЭлектроннойОчереди`):

| Параметр | Значение | Примечание |
|---|---|---|
| ВидТабло | НеПрошедшиеРегистрацию | Жёстко задано в коде |
| ВидПеревозки | Автомобиль | Другие виды перевозки не обрабатываются |
| ТипРегистрации | Приемка | Только приёмка |
| Номенклатура | Неопределено | **Не передаётся** — все номенклатуры в одном блоке |

**Источник данных**: регистр `гкс_ОчередьПриемкиПЛК` (электронная очередь приёмки) через регистр `гкс_СтатусыЗаписейВОчередиПриемкиПЛК`.

**Фильтры при замене набора записей**:

| Фильтр | Установлен? | Следствие |
|---|---|---|
| ТочкаМаршрута | ✅ | Замена по площадке |
| ВидТабло | ✅ | Замена только НеПрошедшиеРегистрацию |
| Номенклатура | **❌ НЕТ** | Все номенклатуры перемешаны в одном наборе |

**Цепочка вызовов**:

```
1. Срабатывает регламентное задание / запись в РС СтатусыЗаписейВОчередиПриемкиПЛК
      ↓
2. гкс_ЭлектроннаяОчередь.ОбновлениеТаблоЭлектроннойОчереди()
      ↓
3. гкс_ИнтеграцияСЭлектроннымТаблоСервер.ОбновитьТаблоДляЭлектроннойОчереди()
      ↓
4. гкс_СтатусыЗаписейВОчередиПриемкиПЛК.ПолучитьСписокЗаписейВОчередьДляТабло()
   — берёт ПЕРВЫЕ 15 записей из электронной очереди за последние N минут
   — НЕ проверяет, прошло ли ТС регистрацию
   — Номенклатура = Неопределено (не передаётся)
      ↓
5. НаборЗаписей.Записать(Истина) — замена по фильтрам ТочкаМаршрута + ВидТабло
   (фильтр по Номенклатуре НЕ устанавливается)
      ↓
6. ОтправитьДанныеНаЭлектронноеТабло() — RabbitMQ
```

**Дерево вызовов BSL** (с номерами строк):

```
гкс_ОбновлениеТаблоЭлектроннойОчереди (регламентное задание)
  │  ИЛИ
гкс_СтатусыЗаписейВОчередиПриемкиПЛК.RecordSetModule
  └─ ОбновитьИнформациюНаЭлектронныхТабло()
  │
  └─ гкс_ЭлектроннаяОчередь.ОбновлениеТаблоЭлектроннойОчереди()  [стр. 101]
       └─ гкс_ИнтеграцияСЭлектроннымТаблоСервер
            .ОбновитьТаблоДляЭлектроннойОчереди()                [стр. 124-183]
            ├─ ПолучитьСписокЗаписейВОчередьДляТабло()           [стр. 143] — ПЕРВЫЕ 15
            ├─ НаборЗаписей.Записать(Истина)                     [стр. 164] — в транзакции!
            └─ ОтправитьДанныеНаЭлектронноеТабло()               — RabbitMQ
```

**Ключевые дефекты Пути Б**:

1. **Нет проверки регистрации**: запрос не проверяет, прошло ли ТС регистрацию. Если машина уже зарегистрирована и двигается по маршруту — она продолжает отображаться на табло "Не прошедшие регистрацию".
2. **Нет фильтра по Номенклатуре**: все номенклатуры записываются одним блоком → фильтрация при отображении невозможна.
3. **Дубли по ЗаписьВОчередь**: если одно ТС имеет несколько записей в очереди с разным временем — каждая попадает как отдельная запись (ЗаписьВОчередь — измерение регистра). Пример: С111СС39 — 8 дублей в testdb1c.

**Отличия от Пути А**:

| Аспект | Путь А (событийный) | Путь Б (регламентный) |
|---|---|---|
| Триггер | Смена состояния регистрации | Рег. задание / запись в очередь |
| Транзакция | **Нет** (только блокировка) | **Да** (`НачатьТранзакцию`) |
| Фильтр по Номенклатуре | ✅ (в наборе записей) | ❌ (не устанавливается) |
| Проверка настроек | После записи (дефект) | Не проверяется вообще |
| Лимит записей | ПЕРВЫЕ 10 | ПЕРВЫЕ 15 |

## Механизм замены набора записей

Это критически важный момент для понимания дублей.

`НаборЗаписей.Записать(Истина)` — параметр `Истина` означает **замену** (не добавление). Платформа 1С удаляет все записи, подходящие под установленные фильтры, и записывает новый набор.

### Путь А — фильтры при замене:

```
НаборЗаписей.Отбор.ТочкаМаршрута.Установить(...)
НаборЗаписей.Отбор.ВидТабло.Установить(...)
НаборЗаписей.Отбор.Номенклатура.Установить(...)   ← вот здесь ключ к дублям
```

Поскольку `Номенклатура` входит в фильтр, замена работает **атомарно по номенклатуре**. Если ТС связано с тремя номенклатурами (Пшеница 3кл, 4кл, продовольственная), то каждая номенклатура образует **отдельный набор записей**. При обновлении одной номенклатуры — записи с другими номенклатурами остаются нетронутыми. Отсюда дубли: одно ТС = 3 строки на табло.

### Путь Б — фильтры при замене:

```
НаборЗаписей.Отбор.ТочкаМаршрута.Установить(...)
НаборЗаписей.Отбор.ВидТабло.Установить(...)
// Номенклатура НЕ устанавливается — все записи заменяются одним блоком
```

Здесь замена захватывает ВСЕ записи по ТочкеМаршрута+ВидуТабло, без разделения по номенклатуре. Поэтому фильтрация по номенклатуре при отображении невозможна — все номенклатуры перемешаны.

## Встроенный "таймаут" — ТочкаОтсчета

В `ИнициализироватьСтруктуруПараметровТабло` задаётся:

```
ТочкаОтсчета = ТекущаяДата - 86400   // 1 сутки назад
```

Это значит, что при каждом НОВОМ запросе (шаг 5 обоих путей) берутся только регистрации за последние 24 часа. Но этот таймаут **не удаляет** старые записи из регистра — он просто не включает их в новый набор. Проблема: если механизм обновления "не дотянулся" до конкретного набора фильтров (например, ненастроенный вид табло), старые записи останутся в регистре навсегда.

## Лимиты и потеря записей

| Место                                            | Лимит                     | Что отсекается                         |
| ------------------------------------------------ | ------------------------- | -------------------------------------- |
| `ПолучитьСписокРегистрацийДляТабло` (Путь А)     | `ПЕРВЫЕ 10`               | 11-я+ регистрация не попадёт в регистр |
| `ПолучитьСписокЗаписейВОчередьДляТабло` (Путь Б) | `ПЕРВЫЕ 15`               | 16-я+ запись в очереди не попадёт      |
| Запросы отображения                              | `ПЕРВЫЕ 3` или `ПЕРВЫЕ 4` | Физическое табло показывает 3 строки   |

Для отображения потеря не критична — табло всё равно показывает максимум 3 строки. Но на уровне записи в регистр: если одновременно на площадке > 10 активных регистраций, часть ТС не попадёт в кэш.

## Запросы отображения (из регистра на физическое табло)

Для каждого вида табло есть отдельная функция запроса в `гкс_ЭлектронныеТабло.ManagerModule`:

| Вид табло              | Функция запроса                                       | Фильтр по Номенклатуре |
| ---------------------- | ----------------------------------------------------- | ---------------------- |
| НеПрошедшиеРегистрацию | `ТекстЗапросаОтображениеНаТаблоНепрошедшиеРегистраци` | **НЕТ** (дефект)       |
| НазначениеНаВесы       | `ТекстЗапросаОтображениеНаТаблоНазначениеНаВесы`      | ДА                     |
| НазначениеНаВыгрузку   | `ТекстЗапросаОтображениеНаТаблоНазначениеНаВыгрузку`  | ДА                     |
| ОжиданияПроб           | `ТекстЗапросаОтображениеНаТаблоОжиданияПроб`          | ДА                     |
| ВозвратАвто            | (не анализировался)                                   | —                      |

Видно паттерн: в трёх из четырёх функций фильтр по номенклатуре есть, а для `НеПрошедшиеРегистрацию` — пропущен. Скорее всего забыли добавить при разработке.

## Аналогия "Фильтр по состоянию"

Та же ситуация с фильтром по состоянию в `ПолучитьСписокРегистрацийДляТабло`:

| Вид табло                                 | Фильтр `ГДЕ Состояние В(&СписокСостояний)` | Какие состояния                      |
| ----------------------------------------- | ------------------------------------------ | ------------------------------------ |
| ОжиданияПроб                              | **ДА**                                     | ВыгрузкаРазрешена, КачествоНеПринято |
| НазначениеНаВыгрузку                      | **ДА**                                     | ВыгрузкаРазрешена                    |
| НеПрошедшиеРегистрацию / НазначениеНаВесы | **НЕТ** (дефект)                           | Должно быть: Прибыл                  |

Два рабочих примера (ОжиданияПроб, НазначениеНаВыгрузку) показывают, как задумывалось. Для НазначениеНаВесы — фильтр просто не добавили.

## Визуальная схема: жизненный цикл записи

```
ТС встало в электронную очередь
    ↓
[Путь Б] Регламентное задание → запись в регистр (ВидТабло = НеПрошедшиеРегистрацию)
    ↓
ТС прошло регистрацию → состояние = Прибыл
    ↓
[Путь А] ПриЗаписи() → запись в регистр (ВидТабло = НазначениеНаВесы)
    |                                      (ВидТабло = НазначениеНаВыгрузку)  ← мусор, если нет табло
    |                                      (ВидТабло = ОжиданияПроб)          ← мусор, если нет табло
    ↓
ТС взвешено → состояние = ВзвешенБрутто
    ↓
[Путь А] ПриЗаписи() → ОбновитьТабло()
    Для ОжиданияПроб/НазначениеНаВыгрузку: фильтр по состоянию → ТС УХОДИТ с табло ✅
    Для НазначениеНаВесы: фильтра НЕТ → ТС ОСТАЁТСЯ на табло ❌ (зависает)
    ↓
...
    ↓
ТС убыло → состояние = Убыл
    ↓
Запись всё ещё в регистре для НазначениеНаВесы ❌
Запись может быть в регистре для НеПрошедшиеРегистрацию ❌ (если Путь Б не перезаписал)
```

## Итог: почему записи зависают

1. **НазначениеНаВесы**: запрос берёт ВСЕ регистрации за последние сутки, без фильтра по состоянию. ТС со статусом "Убыл" попадает обратно при каждом обновлении.

2. **НеПрошедшиеРегистрацию**: регламентное задание берёт записи из электронной очереди, но не проверяет, прошла ли машина регистрацию. Зарегистрированное ТС продолжает отображаться.

3. **Мусорные записи**: данные пишутся в регистр ДО проверки, есть ли физическое табло. На площадках с 1-2 видами табло регистр засоряется записями для несуществующих видов.

4. **Дубли номенклатуры**: набор записей Пути А фильтруется по номенклатуре → каждая номенклатура = отдельный "слот" → одно ТС с 3 номенклатурами = 3 записи.

5. **Нет самоочистки**: `ТочкаОтсчета` ограничивает только новые запросы, но не удаляет старые записи. Если набор фильтров больше не обновляется — записи остаются навечно.
