# GKSTCPLK-2256 — Детальный план тестирования реализации

**Задача:** Актуальность информации в регистре "Информация на электронные табло"
**Статус реализации:** 5 из 7 дефектов закрыты (02.04.2026)
**Дата плана:** 05.04.2026

---

## Назначение документа

Исчерпывающий план тестирования реализации GKSTCPLK-2256. Для каждой из **5 точек модификации** (ТМ-1, ТМ-2, ТМ-3, ТМ-4, M-1) описаны **функциональные тесты (FN)**, **регрессионные тесты (RG)** и **граничные условия (EC)**. План разбит на **7 этапов** — от подготовки данных до UAT.

Документ дополняет [GKSTCPLK-2256-TEST-ROADMAP.md](GKSTCPLK-2256-TEST-ROADMAP.md) (базовый roadmap). Существующие тесты `T-1.1..T-5.2` **не дублируются**, а дополняются детальными шагами и верификационными SQL.

## Этап 1 — Unit-тесты для каждой точки

### 1.1 ТМ-1: Фильтр по состояниям для НазначениеНаВесы

**Код:** `CommonModules/гкс_ИнтеграцияСЭлектроннымТаблоСервер/Ext/Module.bsl`, функция `ПолучитьСписокРегистрацийДляТабло()` (стр. 274-313)
**Баг:** RC-2

#### FN-1.1.1 — Только состояние "Прибыл" попадает на табло

**Предусловие:** 3 регистрации в разных состояниях: Прибыл, ВзвешенБрутто, Убыл
**Шаги:**
1. Создать 3 документа `гкс_РегистрацияНаПЛК` для ТС С001АА39, С002АА39, С003АА39
2. Установить состояния через `гкс_СостоянияРегистрации.ПриЗаписи()`:
   - С001АА39 → Прибыл
   - С002АА39 → ВзвешенБрутто
   - С003АА39 → Убыл
3. Проверить результат запроса `ПолучитьСписокРегистрацийДляТабло()` для ВидТабло=НазначениеНаВесы

**Ожидаемый результат:**
- В результате ровно 1 запись: С001АА39 (Прибыл)
- С002АА39 и С003АА39 отсутствуют

**SQL верификация:**
```sql
ВЫБРАТЬ Авто, Состояния.Состояние
ИЗ РегистрСведений.гкс_ЭлектронныеТабло КАК Табло
    ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.гкс_СостоянияРегистрации.СрезПоследних КАК Состояния
    ПО Табло.ДокументРегистрации = Состояния.ДокументРегистрации
ГДЕ Табло.ВидТабло = ЗНАЧЕНИЕ(Перечисление.гкс_ВидыЭлектронныхТабло.НазначениеНаВесы)
```
Все Состояния должны быть = "Прибыл".

#### FN-1.1.2 — Смена состояния убирает ТС с табло

**Предусловие:** FN-1.1.1 выполнен, С001АА39 на табло
**Шаги:**
1. Сменить состояние С001АА39: Прибыл → ВзвешенБрутто
2. Триггер `ПриЗаписи()` → ОбновитьТабло

**Ожидаемый результат:** С001АА39 исчезает с табло НазначениеНаВесы

#### EC-1.1.1 — Пустой результат: очистка записей

**Предусловие:** На площадке Светлый все ТС в состоянии Убыл (никого в Прибыл)
**Шаги:** Вызов `ОбновитьТабло()` для ВидТабло=НазначениеНаВесы
**Ожидаемый результат:** набор записей пустой, `НаборЗаписей.Записать(Истина)` очищает старые записи → 0 записей на табло

#### RG-1.1.1 — Пути А и Б согласованы

**Предусловие:** Регистрация С001АА39 создана, состояние Прибыл
**Шаги:**
1. Путь А триггерится (событие ПриЗаписи)
2. Запустить регламент Пути Б (после Путь А)

**Ожидаемый результат:** С001АА39 не дублируется. В регистре 1 запись для НазначениеНаВесы.

| 6 | Сменить состояние на Убыл | ТС не появляется нигде |

### INT-2.2 — Параллельный вызов Путь А + Путь Б

**Предусловие:** регламент Пути Б запущен, одновременно — запись в `гкс_СостоянияРегистрации`
**Шаги:** искусственная гонка (запуск регламента + сразу запись состояния)
**Ожидаемый результат:** нет дублей в регистре, нет взаимоблокировок

### INT-2.3 — Цикл КАТ с табло НазначениеНаВыгрузку + ОжиданияПроб

**Предусловие:** площадка КАТ, 4×НазначениеНаВыгрузку + 4×ОжиданияПроб настроены
**Шаги:** провести регистрацию → выставить Прибыл → ВзвешенБрутто → ВыгрузкаРазрешена
**Ожидаемый результат:** на шаге "ВыгрузкаРазрешена" ТС появляется **только** на табло НазначениеНаВыгрузку и ОжиданияПроб (где настроены)

## Приложение D — Runbook ручного тестирования в 1С:Предприятие

Пошаговый сценарий для 1С-программиста. Действия в режиме Предприятия (не конфигуратор). Каждый шаг = конкретная команда меню/формы. Обозначения: **PASS** — ожидаемый результат, **FAIL** — признак бага.

### Этап 0 — Подготовка базы

1. Запустить 1С:Предприятие → выбрать базу **testdb1c** → Предприятие.
2. **Главное меню → Все функции → Включить**, если не включено (Сервис → Параметры → "Отображать команду Все функции").

#### E.9.1 Две цепочки бизнес-процесса

Система обслуживает два параллельных процесса через **один АРМ** (`гкс_ПриемкаТранспорта`), переключаемый радиокнопкой `ОтборТипРегистрации`:

| Аспект | Светлый (Приёмка) | КАТ (Отгрузка) |
|--------|-------------------|-----------------|
| Очередь | `гкс_ЗаписьВОчередьПриемкиПЛК` | `гкс_ЗаписьВОчередьОтгрузкиПЛК` |
| Въезд = | Брутто (груженый) | **Тара (пустой)** |
| Выезд = | Тара (пустой) | **Брутто (груженый)** |
| Лаборатория | 3 кнопки (пробы, анализ) | **Нет** — кнопки скрыты |
| НаправлениеНаРазгрузку | Кнопка в АРМ → `ВыгрузкаРазрешена` | **Скрыта** — создаётся внешне → `ПогрузкаРазрешена` |
| Подтверждение | "разгружен" → `Выгружен` | **"погружен"** → `Погружен` |
| Кнопок АРМ | 8 | **4** |
| Табло | НазначениеНаВесы (Светлый) | **НазначениеНаВыгрузку + ОжиданияПроб** (КАТ) |

#### E.9.2 Цепочка состояний отгрузки через АРМ

```
гкс_ЗаписьВОчередьОтгрузкиПЛК → [регламент] → табло НеПрошедшиеРегистрацию
       ↓
гкс_РегистрацияНаПЛК (ТипРегистрации=Отгрузка) → авто "Прибыл"
       ↓
АРМ (ОтборТипРегистрации = Отгрузка):
  Прибыл → [Въезд=Тара] → ВзвешенТара → [Погрузка подтв.] → Погружен →
  [Выезд=Брутто] → ВзвешенБрутто → [Убытие] → Убыл
```

### F.9 Известные ограничения

- Hardcoded testdb1c credentials (`a.terletskiy@sodru.com`) в скриптах дублируют то, что уже было в `run-bdd.ps1`. Для production deploy — вынести в env / Credential Manager.
