# GKSTCPLK-2256 — Дорожная карта тестирования

## Источники данных на электронные табло

Данные на электронные табло **НЕ приходят извне** — они формируются **внутри конфигурации 1С** и хранятся в промежуточном регистре-кэше `гкс_ЭлектронныеТабло`. Существуют **два независимых пути** наполнения:

### Путь А — Событийный (реальное время)

```
Изменение состояния регистрации ТС (документ гкс_РегистрацияНаПЛК)
  -> ПриЗаписи() регистра гкс_СостоянияРегистрации
    -> гкс_ИнтеграцияСЭлектроннымТаблоСервер.ОбновитьТабло()
      -> Запрос к регистру гкс_СостоянияРегистрации (срез последних)
      -> Запись набора в регистр гкс_ЭлектронныеТабло (замена по фильтрам)
      -> Отправка данных на физические табло через RabbitMQ
```

**Виды табло**: НазначениеНаВесы, НазначениеНаВыгрузку, ОжиданияПроб

### Путь Б — Регламентный (по расписанию)

```
Регламентное задание гкс_ОбновлениеТаблоЭлектроннойОчереди
  -> Запрос к регистру гкс_ОчередьПриемкиПЛК (записи за N минут)
  -> Запись в регистр гкс_ЭлектронныеТабло
  -> Отправка через RMQ
```

**Вид табло**: НеПрошедшиеРегистрацию

### Итого: источники данных

| Источник | Тип | Что содержит |
|----------|-----|-------------|
| `гкс_СостоянияРегистрации` | Регистр сведений (периодический) | Текущие статусы ТС на маршруте |
| `гкс_ОчередьПриемкиПЛК` | Регистр сведений | Электронная очередь приёмки |
| `гкс_ЭлектронныеТабло` | Регистр сведений (кэш) | Промежуточное хранение для отдачи на физические табло |

Физические табло (hardware) получают данные из регистра `гкс_ЭлектронныеТабло` через **RabbitMQ**.

## Этап 0: Подготовка данных (prerequisites)

| Что нужно | Где взять | Проверка |
|-----------|-----------|----------|
| Точка маршрута ПЛК (Светлый) | Справочник `гкс_ТочкиМаршрута` | Есть привязка к табло в `гкс_НастройкаЭлектронногоТабло` |
| Настройка табло (ВидТабло + Номенклатура + ТочкаМаршрута) | Регистр `гкс_НастройкаЭлектронногоТабло` | Есть записи для 3 видов табло |
| Номенклатуры (минимум 2: Пшеница, Ячмень) | Справочник `Номенклатура` | Существуют ссылки |
| Документ регистрации (тестовый) | `гкс_РегистрацияНаПЛК` | Можно создать новый |

**Диагностические запросы** (через `1c-mcp-toolkit` / консоль запросов):

```sql
-- Текущие настройки табло
ВЫБРАТЬ ПЕРВЫЕ 10 * ИЗ РегистрСведений.гкс_НастройкаЭлектронногоТабло

-- Текущее содержимое регистра табло
ВЫБРАТЬ ПЕРВЫЕ 20 * ИЗ РегистрСведений.гкс_ЭлектронныеТабло

-- Текущие состояния регистраций
ВЫБРАТЬ ПЕРВЫЕ 10
    Состояния.ДокументРегистрации,
    Состояния.Состояние,
    Состояния.ТочкаМаршрута
ИЗ
    РегистрСведений.гкс_СостоянияРегистрации.СрезПоследних КАК Состояния
```

## Этап 1: Baseline — зафиксировать текущее поведение (ДО исправлений)

Цель: документально подтвердить каждый баг до внесения изменений.

| # | Действие | Инструмент | Ожидание (подтверждение бага) |
|---|----------|------------|------------------------------|
| 1.1 | Снять дамп регистра `гкс_ЭлектронныеТабло` | `execute_query` | Увидим "зависшие" записи |
| 1.2 | Найти регистрации в состоянии > Прибыл, которые есть на табло НазначениеНаВесы | `execute_query` (JOIN) | Записи с ВзвешенБрутто/Выгружен на табло |
| 1.3 | Проверить дубликаты (одно ТС, разная Номенклатура) | `execute_query` с GROUP BY | Дублирование подтверждено |
| 1.4 | Проверить НеПрошедшиеРегистрацию — есть ли зарегистрированные ТС | `execute_query` | Зависание подтверждено |

### SQL для проверки 1.2 (зависшие записи НазначениеНаВесы)

```sql
ВЫБРАТЬ
    Табло.Авто,
    Табло.ДокументРегистрации,
    Состояния.Состояние
ИЗ
    РегистрСведений.гкс_ЭлектронныеТабло КАК Табло
        ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.гкс_СостоянияРегистрации.СрезПоследних КАК Состояния
        ПО Табло.ДокументРегистрации = Состояния.ДокументРегистрации
ГДЕ
    Табло.ВидТабло = ЗНАЧЕНИЕ(Перечисление.гкс_ВидыЭлектронныхТабло.НазначениеНаВесы)
    И Состояния.Состояние <> ЗНАЧЕНИЕ(Перечисление.гкс_СостоянияРегистрации.Прибыл)
```

### SQL для проверки 1.3 (дубликаты)

```sql
ВЫБРАТЬ
    Табло.Авто,
    Табло.ДокументРегистрации,
    Табло.ВидТабло,
    КОЛИЧЕСТВО(РАЗЛИЧНЫЕ Табло.Номенклатура) КАК КолНоменклатур
ИЗ
    РегистрСведений.гкс_ЭлектронныеТабло КАК Табло
СГРУППИРОВАТЬ ПО
    Табло.Авто, Табло.ДокументРегистрации, Табло.ВидТабло
ИМЕЮЩИЕ
    КОЛИЧЕСТВО(РАЗЛИЧНЫЕ Табло.Номенклатура) > 1
```

## Этап 2: Тестирование Точки 1 (фильтр по состояниям)

**Связанная точка модификации**: `гкс_ИнтеграцияСЭлектроннымТаблоСервер/Module.bsl`, строки 278-305

### Сценарий 2.1: Запись уходит при смене состояния

| Шаг | Действие | Кто выполняет |
|-----|----------|---------------|
| 1 | Создать/найти регистрацию ТС в состоянии **Прибыл** | Пользователь (интерфейс 1С) |
| 2 | Убедиться что ТС на табло НазначениеНаВесы | `execute_query` к регистру |
| 3 | Перевести состояние в **ВзвешенБрутто** | Пользователь (интерфейс 1С) |
| 4 | Проверить регистр | `execute_query` |
| **Ожидание** | Запись ТС **исчезла** с табло НазначениеНаВесы | |

### Сценарий 2.2: Только "Прибыл" на табло

```sql
-- После исправления: все записи НазначениеНаВесы должны иметь состояние = Прибыл
ВЫБРАТЬ
    Табло.Авто,
    Табло.ДокументРегистрации,
    Состояния.Состояние
ИЗ
    РегистрСведений.гкс_ЭлектронныеТабло КАК Табло
        ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.гкс_СостоянияРегистрации.СрезПоследних КАК Состояния
        ПО Табло.ДокументРегистрации = Состояния.ДокументРегистрации
ГДЕ
    Табло.ВидТабло = ЗНАЧЕНИЕ(Перечисление.гкс_ВидыЭлектронныхТабло.НазначениеНаВесы)
```

**Ожидание**: все записи имеют `Состояние = Прибыл`. Записей с другими состояниями быть не должно.

## Этап 3: Тестирование Точки 2 (фильтр по номенклатуре)

**Связанная точка модификации**: `гкс_ЭлектронныеТабло/ManagerModule.bsl`, строки 44-62

### Сценарий 3.1: Фильтрация по номенклатуре работает

| Шаг | Действие | Ожидание |
|-----|----------|----------|
| 1 | В регистре есть записи НеПрошедшиеРегистрацию с Пшеницей и Ячменём | Предусловие |
| 2 | Вызвать функцию отображения с Номенклатура = Пшеница | Только записи с Пшеницей |
| 3 | Вызвать с Номенклатура = Ячмень | Только записи с Ячменём |

### Сценарий 3.2: Пустая номенклатура = все записи (обратная совместимость)

| Шаг | Действие | Ожидание |
|-----|----------|----------|
| 1 | Вызвать с Номенклатура = ПустаяСсылка | Все записи без фильтрации |

Это гарантирует совместимость с табло, где нет отбора по номенклатуре.

## Этап 4: Тестирование Точки 3 (очередь vs регистрация)

**Связанная точка модификации**: `гкс_СтатусыЗаписейВОчередиПриемкиПЛК/ManagerModule.bsl`, строки 115-152

> **ВАЖНО**: Перед тестированием необходимо верифицировать связи между `гкс_ОчередьПриемкиПЛК` и `гкс_РегистрацияНаПЛК` (см. раздел "Открытые вопросы").

### Сценарий 4.1: Зарегистрированное ТС уходит с табло

| Шаг | Действие | Кто выполняет |
|-----|----------|---------------|
| 1 | ТС есть в электронной очереди и на табло НеПрошедшиеРегистрацию | Предусловие |
| 2 | Оформить документ РегистрацияНаПЛК для этого ТС | Пользователь (интерфейс 1С) |
| 3 | Дождаться цикла регламентного задания (или запустить вручную) | Пользователь / Администратор |
| 4 | Проверить регистр | `execute_query` |
| **Ожидание** | ТС **исчезло** с табло НеПрошедшиеРегистрацию | |

### Сценарий 4.2: Незарегистрированное ТС остаётся

| Шаг | Действие | Ожидание |
|-----|----------|----------|
| 1 | ТС в очереди, регистрация НЕ оформлена | Предусловие |
| 2 | Запуск цикла регламентного задания | ТС остаётся на табло |

## Этап 5: Интеграционное тестирование (все точки вместе)

### Сценарий 5.1: Полный цикл жизни ТС

```
Очередь -> Регистрация -> Взвешивание -> Выгрузка -> Убыл
```

| Статус ТС | НеПрошедшиеРегистрацию | НазначениеНаВесы | НазначениеНаВыгрузку | ОжиданияПроб |
|-----------|----------------------|-----------------|---------------------|-------------|
| В очереди (до регистрации) | ЕСТЬ | - | - | - |
| Прибыл | НЕТ | ЕСТЬ | - | - |
| ВзвешенБрутто | НЕТ | НЕТ | - | - |
| ВыгрузкаРазрешена | НЕТ | НЕТ | ЕСТЬ | ЕСТЬ |
| Выгружен | НЕТ | НЕТ | НЕТ | - |
| Убыл | НЕТ | НЕТ | НЕТ | НЕТ |

На каждом шаге ТС должно быть **ровно на одном** табло (или ни на одном на финальных этапах).

### Сценарий 5.2: Регрессия

| Табло | Что проверяем | Ожидание |
|-------|--------------|----------|
| НазначениеНаВыгрузку | Фильтры работают как раньше | Без изменений (фильтр по состоянию уже был) |
| ОжиданияПроб | Фильтры работают как раньше | Без изменений (фильтр по состоянию уже был) |

### Сценарий 5.3: RabbitMQ

Физические табло получают обновления при каждой смене состояния. Проверка: мониторинг очереди RMQ или визуальный контроль на табло.

## Этап 6: Очистка после деплоя

После выкатки исправлений в регистре останутся "зависшие" записи от старого кода.

### Вариант А: Автоочистка (рекомендуется)

1. Запустить регламентное задание `гкс_ОбновлениеТаблоЭлектроннойОчереди` — перезапишет НеПрошедшиеРегистрацию
2. Для НазначениеНаВесы — обновление произойдёт автоматически при следующей смене состояния любой регистрации на этой точке маршрута

### Вариант Б: Принудительная очистка

Обработка для удаления записей регистра `гкс_ЭлектронныеТабло`, у которых текущее состояние не соответствует виду табло.

## Сводка: порядок тестирования

```
Этап 0: Подготовка данных
  |
Этап 1: Baseline (зафиксировать баги ДО исправлений)
  |
  +-- Этап 2: Точка 1 (фильтр состояний) --+
  |                                          |-- параллельно, независимы
  +-- Этап 3: Точка 2 (фильтр номенклатуры)-+
  |
Этап 4: Точка 3 (очередь vs регистрация) -- после верификации связей
  |
Этап 5: Интеграционное тестирование (все точки вместе)
  |
Этап 6: Очистка после деплоя
```

**Общее время**: Этапы 0-1 — 1 сессия, Этапы 2-4 — по 1 сессии на каждую точку, Этап 5 — 1 сессия.
