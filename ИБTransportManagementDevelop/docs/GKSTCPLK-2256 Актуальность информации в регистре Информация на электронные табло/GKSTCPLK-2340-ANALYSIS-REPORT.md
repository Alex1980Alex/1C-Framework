### 3.2 Анализ пустых сообщений [REQ-2]

#### Как возникают пустые сообщения

Когда `ОбновитьТабло()` вызывается и запрос `ПолучитьСписокРегистрацийДляТабло()` не находит актуальных регистраций (машина уехала):

1. `СписокРегистраций.Количество() = 0` → цикл заполнения не выполняется (стр. 76-98)
2. `НаборЗаписей.Записать(Истина)` — **записывает пустой набор** → удаляет старые записи из регистра (стр. 100)
3. Далее `ОтправитьДанныеНаЭлектронноеТабло()` → `СформироватьСообщение()`:
   - `ПодготовитьЗапросПолученияДанныхДляЗаполненияТаблицыСтрок()` читает из теперь-пустого регистра (стр. 334-361)
   - `РезультатЗапроса.Пустой() → Возврат` (стр. 191-192) — DataTable не заполняется
   - XDTO-сообщение отправляется **без DataTable** → физическое табло **очищает экран**

#### Вывод анализа

**Пустые сообщения НУЖНЫ** — они выполняют функцию **очистки табло**. Без пустого сообщения табло продолжит показывать устаревшие данные (уехавшую машину).

**Оптимизация возможна, но не критична:**
- Можно пропускать повторную отправку пустого сообщения, если регистр уже был пуст для данного фильтра
- Экономия: ~1 RMQ-сообщение на каждую смену состояния не-табличного ТС
- Риск: если RMQ-сообщение потерялось → табло не очистится → без повторной отправки данные зависнут

**Рекомендация:** НЕ оптимизировать пустые сообщения в текущем релизе. Гарантия очистки табло важнее экономии трафика RMQ. Если потребуется — реализовать как отдельную задачу с флагом `ТаблоОчищено`.

### 3.3 Найденный паттерн: логирование внутри ОбновитьТабло ✓ pattern

В `ОбновитьТабло()` (стр. 76-100) уже есть цикл записи данных в `гкс_ЭлектронныеТабло`:
```bsl
Для Каждого Строка Из СписокРегистраций Цикл
    НоваяЗапись = НаборЗаписей.Добавить();
    // ... заполнение ...
    НоваяЗапись.Авто = Строка.ДокументРегистрации.ТранспортноеСредство.Наименование; // стр. 96
КонецЦикла;
НаборЗаписей.Записать(Истина); // стр. 100
```
**`Авто` (Строка, 50) = госномер ТС** — доступен только внутри этого цикла. Логирование per-машина возможно только здесь, после записи набора.

Почему НЕ в `гкс_НастройкаЭлектронногоТабло`: настройки = per-табло (ТочкаМаршрута+ВидТабло+Табло), нет измерения Авто. Каждая новая машина перезатирает timestamp предыдущей.
Почему НЕ в `гкс_ЭлектронныеТабло`: это кеш — записи удаляются при отъезде машины (пустой набор на стр. 100).

## 6. Риски и открытые вопросы

### 6.1 Производительность записи

**Риск:** `МенеджерЗаписи.Записать()` вызывается для каждой машины внутри цикла `ОбновитьТабло()`.

**Оценка:** Типично 1-3 машины на вариант → 1-3 записи → некритично. Операция внутри привилегированного режима (стр. 32). МенеджерЗаписи = upsert без предварительного чтения.

### 6.2 Электронная очередь

**Вопрос:** В `гкс_СтатусыЗаписейВОчередиПриемкиПЛК.RecordSetModule` (стр. 134) отправка на табло через другую цепочку. Логирование per-машина НЕ требует отдельной точки модификации — `ОбновитьТабло()` вызывается и из этого модуля, логирование сработает автоматически.

### 6.3 Рост регистра лога

**Вопрос:** `гкс_ЛогОтправкиНаТабло` — upsert по ключу (Авто+ВидТабло+ТочкаМаршрута), поэтому для одного ТС хранится только ПОСЛЕДНЯЯ отправка. Рост = O(уникальных ТС × видов табло × точек), а не O(отправок). Очистка исторических записей — отдельная задача при необходимости.

### 6.3 Пустые сообщения — решение

**Вывод:** Не оптимизировать в текущем релизе. Причина: пустое сообщение = команда очистки табло. Если RMQ потеряет единственное пустое сообщение, на табло останутся устаревшие данные. Повторная отправка пустого — дешёвая страховка.
