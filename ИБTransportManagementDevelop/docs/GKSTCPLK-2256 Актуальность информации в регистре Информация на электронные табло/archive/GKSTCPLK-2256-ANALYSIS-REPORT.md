# GKSTCPLK-2256 Актуальность информации в регистре Информация на электронные табло

## 1. Описание задачи

### 1.1 Требования

Данные на электронных табло ПЛК (Светлый) должны отображаться в реальном времени и автоматически очищаться при прохождении ТС по статусам маршрута. Текущая ситуация — записи "зависают" в регистре `гкс_ЭлектронныеТабло`.

### 1.2 Перечень проблем из ТЗ и диалога с заказчиком

| # | Проблема | Вид табло | Источник |
|---|---------|-----------|----------|
| 1 | Номенклатура не учтена в запросе отображения | НеПрошедшиеРегистрацию | ТЗ + диалог стр. 85-89 |
| 2 | Записи не уходят при прохождении статусов (зависают) | НазначениеНаВесы + НеПрошедшиеРегистрацию | ТЗ + диалог стр. 49-53, 67, 75 |
| 3 | Дублирующие записи с разной номенклатурой | НазначениеНаВесы (КАТ, погрузка + разгрузка) | ТЗ |
| 4 | Записи генерируются для ненастроенных видов табло | Все виды | Диалог стр. 45-47, 67-69 |
| 5 | Возможная потеря записей из-за `ПЕРВЫЕ 10` | Все виды | Диалог стр. 64, 71 |
| 6 | Регистр неинформативен — нет истории для расследования | Все виды | Диалог стр. 99-101 |

### 1.3 Суть проблемы

Регистр сведений `гкс_ЭлектронныеТабло` (синоним: "Информация на электронные табло") — промежуточный кэш данных для физических табло. Он перезаписывается целиком по набору фильтров при каждом изменении состояния регистрации. **Корневая проблема**: запросы, формирующие список регистраций для записи в регистр, не фильтруют по актуальному состоянию, поэтому "старые" регистрации (уже прошедшие этап) снова попадают в регистр.

### 1.4 Инфраструктура (из диалога и инструкции заказчика)

**Светлый** (ПЛК Светлый): 2 физических табло, оба НеПрошедшиеРегистрацию (IP: 172.20.23.250, 172.20.22.202), по 3 строки.

**КАТ** (ПЛК Курск): 4 табло "Назначение на выгрузку" (172.31.28.186-199) + 4 табло "Ожидания проб" (172.31.28.164-185), по 3 строки.

> Заказчик: "Светлый использует один вид табло, КАТ — два других. В КАТе может быть более интересный случай по поводу подвисших записей" (диалог стр. 73)

### 1.5 Указания заказчика

1. **"Сначала разобраться с механизмом записи"** — понять, как формируется регистр, прежде чем чинить (стр. 57, 75, 101-103)
2. **"Может быть, стоит переписать"** — возможен рефакторинг механизма, не просто точечные фиксы (стр. 101)
3. **"Записи за вчерашний день быть не должно"** — данные за прошлые сутки недопустимы (стр. 49, 75)
4. **"Очень сложно разбираться с этим регистром"** — при звонках пользователей невозможно понять, почему нет информации (стр. 99-101)

### 2.3 Триггеры обновления табло

Существуют **два независимых пути** обновления регистра `гкс_ЭлектронныеТабло`:

**Путь А** — При изменении состояния регистрации:
```
гкс_СостоянияРегистрации.ПриЗаписи()
  → СформироватьВариантыДляТабло()
  → ЗарегистрироватьОбъектКОбменуСТабло()
    → гкс_ИнтеграцияСЭлектроннымТаблоСервер.ОбновитьТабло()
      → ПолучитьСписокРегистрацийДляТабло()  ← ПРОБЛЕМА: нет фильтра по состоянию
      → НаборЗаписей.Записать(Истина)  // замена по фильтрам
    → ОтправитьДанныеНаЭлектронноеТабло()  // RMQ
```
Виды: НазначениеНаВесы, НазначениеНаВыгрузку, ОжиданияПроб

**Путь Б** — Регламентное задание `гкс_ОбновлениеТаблоЭлектроннойОчереди`:
```
гкс_ЭлектроннаяОчередь.ОбновлениеТаблоЭлектроннойОчереди()
  → гкс_ИнтеграцияСЭлектроннымТаблоСервер.ОбновитьТаблоДляЭлектроннойОчереди()
    → гкс_СтатусыЗаписейВОчередиПриемкиПЛК.ПолучитьСписокЗаписейВОчередьДляТабло()
      ← ПРОБЛЕМА: нет проверки факта регистрации
    → НаборЗаписей.Записать(Истина)
```
Виды: НеПрошедшиеРегистрацию

## 3. Детальный анализ механизма

### 3.1 Корневая причина 1: Запрос ПолучитьСписокРегистрацийДляТабло НЕ фильтрует по СписокСостояний для НазначениеНаВесы

**Файл**: `CommonModules/гкс_ИнтеграцияСЭлектроннымТаблоСервер/Module.bsl`, строки 274-305

Для видов `НеПрошедшиеРегистрацию` и `НазначениеНаВесы` запрос:

```sql
ВЫБРАТЬ РАЗЛИЧНЫЕ ПЕРВЫЕ 10
    РССостоянияРегистрации.ДокументРегистрации
ПОМЕСТИТЬ ВТ_СостоянияРегистрации
ИЗ
    РегистрСведений.гкс_СостоянияРегистрации.СрезПоследних(
        &ТекущаяДата,
        ТочкаМаршрута = &ТочкаМаршрута
        И ВидПеревозки = &ВидПеревозки
        И ТипРегистрации = &ТипРегистрации
        И Период >= &ТочкаОтсчета)
-- !!! НЕТ: ГДЕ РССостоянияРегистрации.Состояние В(&СписокСостояний)
```

**Сравнение с рабочими ветками**:
- `ОжиданияПроб` (строка 328): `ГДЕ СостоянияРегистрации.Состояние В(&СписокСостояний)` ✅
- `НазначениеНаВыгрузку` (строка 403): `ГДЕ СостоянияРегистрации.Состояние В(&СписокСостояний)` ✅
- `НеПрошедшиеРегистрацию / НазначениеНаВесы` (строка 278): **фильтр отсутствует** ❌

**СписокСостояний** формируется в `гкс_СостоянияРегистрации.RecordSetModule`:
- Для `НазначениеНаВесы` (строка 193): `[Прибыл]`
- Для `НазначениеНаВыгрузку` (строка 178): `[ВыгрузкаРазрешена]`
- Для `ОжиданияПроб` (строка 213): `[ВыгрузкаРазрешена, КачествоНеПринято]`

**Последствия**: Регистрации, уже прошедшие статус "Прибыл" (например, ВзвешенБрутто, Выгружен, Убыл), продолжают попадать в регистр табло для "НазначениеНаВесы". Отсюда "зависшие" записи на табло Светлый.

### 3.2 Корневая причина 2: Запрос отображения НеПрошедшиеРегистрацию не фильтрует по Номенклатуре

**Файл**: `InformationRegisters/гкс_ЭлектронныеТабло/ManagerModule.bsl`, строки 44-62

```sql
ВЫБРАТЬ РАЗРЕШЕННЫЕ ПЕРВЫЕ 4
    ЭлектронныеТабло.ЗаписьВОчередь,
    ЭлектронныеТабло.Авто,
    ЭлектронныеТабло.Номенклатура,
    ЭлектронныеТабло.ВидЗерна,
    ...
ИЗ
    РегистрСведений.гкс_ЭлектронныеТабло
ГДЕ
    ЭлектронныеТабло.ТочкаМаршрута = &ТочкаМаршрута
    И ЭлектронныеТабло.ВидТабло = &ВидТабло
-- !!! НЕТ: И ЭлектронныеТабло.Номенклатура = &Номенклатура
```

Параметр `Номенклатура` устанавливается в `ПодготовитьЗапросПолученияДанныхДляЗаполненияТаблицыСтрок` (строка 340), но **не используется** в WHERE-условии запроса. Табло, настроенное для конкретной номенклатуры, видит ВСЕ записи.

**Дополнительно**: В `ОбновитьТаблоДляЭлектроннойОчереди` (строка 118) `Номенклатура = Неопределено`, а набор записей (строки 148-149) не фильтрует по `Номенклатура`. Так что для НеПрошедшиеРегистрацию все номенклатуры перемешиваются в одном наборе записей.

### 3.3 Корневая причина 3: Запрос электронной очереди не проверяет факт прохождения регистрации

**Файл**: `InformationRegisters/гкс_СтатусыЗаписейВОчередиПриемкиПЛК/ManagerModule.bsl`, строки 89-156

Функция `ПолучитьСписокЗаписейВОчередьДляТабло` выбирает из `гкс_ОчередьПриемкиПЛК` записи за последние N минут, но **не исключает** записи, для которых уже существует документ регистрации с состоянием `>= Прибыл`. Это означает, что автомобиль, уже прошедший регистрацию и двигающийся по маршруту, продолжает отображаться на табло "Не прошедшие регистрацию".

### 3.4 Проблема из диалога: Записи для ненастроенных видов табло

> "Он не смотрит на наличие настроенных табло. Генерит тупо сообщение" (диалог стр. 45-47)

**Механизм по коду** (`гкс_СостоянияРегистрации.RecordSetModule`, процедура `ЗарегистрироватьОбъектКОбменуСТабло`):

1. `СформироватьВариантыДляТабло()` генерирует варианты для ВСЕХ видов табло (НазначениеНаВесы, НазначениеНаВыгрузку, ОжиданияПроб) при каждой смене состояния
2. **Строка 251**: вызывается `ОбновитьТабло()` — записи пишутся в регистр `гкс_ЭлектронныеТабло`
3. **Строка 265**: ТОЛЬКО ПОСЛЕ записи вызывается `ПолучитьНастройкиПоВидуТабло()` — проверка наличия физических табло
4. Если настройки не найдены — RMQ-сообщение просто не отправляется, но записи в регистре **уже остались**

Таким образом: данные пишутся в регистр БЕЗУСЛОВНО, а проверка настроек определяет только отправку в RMQ. Регистр засоряется записями для несуществующих табло.

**Следствие**: на Светлом, где настроены только табло НеПрошедшиеРегистрацию, в регистре `гкс_ЭлектронныеТабло` появляются записи для НазначениеНаВесы, НазначениеНаВыгрузку и ОжиданияПроб — "мусорные" данные, которые никуда не отправляются.

**Рекомендация**: Перенести вызов `ПолучитьНастройкиПоВидуТабло()` ПЕРЕД `ОбновитьТабло()` и пропускать запись, если настройки не найдены. Изменение должно быть аккуратным — возможно, что на некоторых площадках настройки добавляются динамически.

### 3.5 Проблема из диалога: Возможная потеря записей (лимиты ПЕРВЫЕ N)

> "Последние три записи... не мешало бы проверить, не теряем ли мы случайно записи" (диалог стр. 64, 71)

**Лимиты по коду**:
- `ПолучитьСписокРегистрацийДляТабло` (строка 278): `ВЫБРАТЬ РАЗЛИЧНЫЕ ПЕРВЫЕ 10` — запись в регистр для Пути А
- `ПолучитьСписокЗаписейВОчередьДляТабло` (строка 143 ManagerModule): `ВЫБРАТЬ ПЕРВЫЕ 15` — запись в регистр для Пути Б (электронная очередь)
- Запросы отображения: `ПЕРВЫЕ 4` (строка 44), `ПЕРВЫЕ 3` (строка 64) — ограничение количества строк для физического табло

Если на площадке одновременно более 10 (Путь А) или 15 (Путь Б) активных регистраций, часть ТС не попадёт в регистр табло. Однако с учётом того, что физические табло показывают по 3 строки, потеря 11-й записи не критична для отображения.

**Диагностический запрос** (оценка масштаба):
```sql
ВЫБРАТЬ
    Состояния.ТочкаМаршрута.Наименование КАК ТочкаМаршрута,
    Состояния.Состояние,
    КОЛИЧЕСТВО(РАЗЛИЧНЫЕ Состояния.ДокументРегистрации) КАК КолРегистраций
ИЗ
    РегистрСведений.гкс_СостоянияРегистрации.СрезПоследних КАК Состояния
ГДЕ
    Состояния.Состояние = ЗНАЧЕНИЕ(Перечисление.гкс_СостоянияРегистрации.Прибыл)
СГРУППИРОВАТЬ ПО
    Состояния.ТочкаМаршрута, Состояния.Состояние
```

### 3.6 Проблема из диалога: Отсутствие истории для расследования

> "Когда звонят и спрашивают, почему нет информации — очень сложно найти этот момент. Записи оттуда уходят" (диалог стр. 99-101)

Регистр `гкс_ЭлектронныеТабло` — транзитный кэш без истории. При каждом обновлении (`НаборЗаписей.Записать(Истина)`) старые записи заменяются новыми. Невозможно восстановить, что было на табло в конкретный момент времени.

**Рекомендация**: Рассмотреть добавление журнала изменений (отдельный регистр или запись в журнал регистрации) для расследования инцидентов. Приоритет: низкий, после основных фиксов.

### 3.7 Найденные паттерны в конфигурации

**Рабочий пример фильтрации по состоянию** — `НазначениеНаВыгрузку` (строки 390-451 `ПолучитьСписокРегистрацийДляТабло`):
```sql
ГДЕ
    СостоянияРегистрации.Состояние В(&СписокСостояний)
    И СостоянияРегистрации.ДокументРегистрации <> &ДокументРегистрации
```
Этот паттерн следует применить и для НеПрошедшиеРегистрацию/НазначениеНаВесы.

**Рабочий пример фильтрации по Номенклатуре** — `ТекстЗапросаОтображениеНаТаблоНазначениеНаВесы` (строки 64-95 ManagerModule):
```sql
ГДЕ
    ЭлектронныеТабло.Номенклатура = &Номенклатура
    И ЭлектронныеТабло.ТочкаМаршрута = &ТочкаМаршрута
    И ЭлектронныеТабло.ВидТабло = &ВидТабло
```
Этот паттерн следует применить и для НеПрошедшиеРегистрацию.

### 3.8 Механизм дублирования записей (уточнение по коду)

Дублирование записей с разной номенклатурой (Проблема 3) объясняется архитектурой замены набора записей.

**Как работает замена** (`ОбновитьТабло`, строка 87):
```
НаборЗаписей.Отбор.ТочкаМаршрута.Установить(ТочкаМаршрута)
НаборЗаписей.Отбор.ВидТабло.Установить(ВидТабло)
НаборЗаписей.Отбор.Номенклатура.Установить(Номенклатура)  ← !!!
...
НаборЗаписей.Записать(Истина)  // Замена = Истина
```

`Записать(Истина)` удаляет и перезаписывает записи **только в рамках установленных фильтров**. Поскольку `Номенклатура` входит в фильтр, замена затрагивает только записи с ЭТОЙ КОНКРЕТНОЙ номенклатурой. Если ТС связано с несколькими номенклатурами (документ регистрации содержит несколько позиций), каждая номенклатура образует **отдельный набор записей** — и при обновлении одной номенклатуры записи с другой остаются нетронутыми.

**Для Пути Б** (электронная очередь) ситуация хуже: в `ОбновитьТаблоДляЭлектроннойОчереди` (строка 118) `Номенклатура = Неопределено`, а фильтр на набор записей по номенклатуре **не устанавливается** (строки 148-149). Это означает, что все записи НеПрошедшиеРегистрацию перезаписываются одним общим блоком без разделения по номенклатуре — но из-за этого и невозможна фильтрация по номенклатуре при отображении.

## 8. Верификация по коду

Верификация выполнена через чтение BSL-модулей конфигурации:
- Модуль менеджера `гкс_ЭлектронныеТабло` — 172 строки, 4 функции запросов отображения
- Общий модуль `гкс_ИнтеграцияСЭлектроннымТаблоСервер` — 462 строки, 2 процедуры обновления + 1 функция получения списка
- Модуль набора записей `гкс_СостоянияРегистрации` — 304 строки, формирование вариантов для табло
- Общий модуль `гкс_ЭлектроннаяОчередь` — `ОбновлениеТаблоЭлектроннойОчереди()` (строка 101), запуск обновления Пути Б
- Модуль менеджера `гкс_СтатусыЗаписейВОчередиПриемкиПЛК` — 252 строки, запрос электронной очереди (`ПЕРВЫЕ 15`)
- Перечисление `гкс_СостоянияРегистрации` — 17 значений (Прибыл...Убыл)
- Перечисление `гкс_ВидыЭлектронныхТабло` — 5 значений

### Ключевые находки верификации:
1. **Порядок вызовов**: `ЗарегистрироватьОбъектКОбменуСТабло()` пишет в регистр (стр. 251) ДО проверки настроек (стр. 265) — мусорные записи
2. **Номенклатуро-зависимая замена**: `НаборЗаписей.Отбор.Номенклатура` делает замену атомарной по номенклатуре — причина дублей
3. **Путь Б без номенклатуры**: `Номенклатура = Неопределено` в регламентном задании, фильтр на набор записей не устанавливается
4. **Лимит электронной очереди**: `ПЕРВЫЕ 15` (не `ПЕРВЫЕ 10` как в диалоге), но `ПЕРВЫЕ 10` есть в `ПолучитьСписокРегистрацийДляТабло`
5. **ТочкаОтсчета**: `ТекущаяДата - 86400` (1 сутки) в `ИнициализироватьСтруктуруПараметровТабло` — записи старше 1 суток не попадут в новый запрос, но старые записи в регистре НЕ удаляются (из-за отсутствия фильтра по состоянию)
