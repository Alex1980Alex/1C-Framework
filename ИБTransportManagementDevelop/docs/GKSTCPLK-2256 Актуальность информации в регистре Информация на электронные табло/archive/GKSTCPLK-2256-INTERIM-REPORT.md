# GKSTCPLK-2256 — Промежуточный отчёт по реализации

**Дата подготовки:** 26.03.2026
**Задача:** Актуальность информации в регистре "Информация на электронные табло" (гкс_ЭлектронныеТабло)
**Статус:** Реализованы критические исправления (Точки 1-2 из 4)

---

## 1. Общая информация

В рамках задачи GKSTCPLK-2256 проведён анализ проблем с отображением данных на электронных табло ПЛК (Светлый, КАТ). Основная жалоба пользователей: информация о транспортных средствах (ТС) "зависает" на экранах и не исчезает после фактического прохождения этапа маршрута.

В ходе диагностики выявлено **7 корневых причин**. На текущий момент реализованы исправления по двум наиболее критичным проблемам, влияющим на актуальность информации прямо сейчас.

## 2. Результаты анализа (кратко)

Анализ показал, что система некорректно фильтрует данные при отборе в регистр. Часть запросов игнорирует текущий статус ТС, а часть — не учитывает фильтры по номенклатуре, из-за чего на табло попадают неактуальные или нерелевантные записи.

| # | Проблема | Влияние | Статус |
|---|---------|---------|--------|
| 1 | **Зависание записей "Назначение на весы"** | На табло отображаются ТС, которые уже уехали или прошли этап | **Реализовано** |
| 2 | **Номенклатура не учтена (Светлый)** | На табло "Не прошедшие регистрацию" попадают ТС с другой продукцией | **Реализовано** |
| 3 | Зарегистрированные ТС не уходят с табло очереди | Электронная очередь не исключает уже прошедших регистрацию | Отложено |
| 4 | Дубликаты с разной номенклатурой | Одно ТС дублируется в регистре с разными номенклатурами | Частично решено (Точка 2) |
| 5 | Записи для ненастроенных видов табло | Мусорные данные в регистре для несуществующих табло | Отложено |
| 6 | Возможная потеря записей (ПЕРВЫЕ 10) | При >10 одновременных ТС часть не попадёт на табло | Отложено |
| 7 | Нет истории для расследования инцидентов | Невозможно узнать, что было на табло в конкретный момент | Отложено |

## 3. Реализованные изменения

Внесены изменения в два серверных модуля конфигурации. Каждое изменение маркировано комментарием `// GKSTCPLK-2256`.

### 3.1. Исправление фильтрации по статусам (Точка 1)

*Проблема: На табло попадали все записи за последние сутки, включая ТС со статусом "Убыл", "Выгружен", "Взвешен брутто" и др.*

- **Файл:** `CommonModules/гкс_ИнтеграцияСЭлектроннымТаблоСервер/Module.bsl`
- **Суть:** В запрос добавлено условие `ГДЕ Состояние В(&СписокСостояний)` — аналогично тому, как уже реализовано для табло "ОжиданияПроб" и "НазначениеНаВыгрузку".
- **Результат:** Теперь запрос для табло "НазначениеНаВесы" отбирает только ТС со статусом "Прибыл", игнорируя записи с другими статусами.

### 3.2. Исправление фильтрации по номенклатуре (Точка 2)

*Проблема: Табло "Не прошедшие регистрацию" показывало ТС всех номенклатур, игнорируя настройку.*

- **Файл:** `InformationRegisters/гкс_ЭлектронныеТабло/ManagerModule.bsl`
- **Суть:** В запрос отображения добавлено условие по номенклатуре с проверкой на пустую ссылку (для совместимости с единым табло без отбора).
- **Результат:** Табло "НеПрошедшиеРегистрацию" показывает только записи, соответствующие номенклатуре из настройки табло.

## 5. Ожидаемый эффект

Для пользователей площадок ПЛК изменения принесут следующую пользу:

1. **Актуальность табло "Назначение на весы":** Исчезнут "фантомы" — машины, которые уже уехали или прошли взвешивание. Диспетчеры и водители будут видеть только реальную очередь.
2. **Точность табло "Не прошедшие регистрацию" (Светлый):** Табло перестанет показывать машины с нерелевантной номенклатурой, что исключит путаницу при распределении по постам.
3. **Снижение ручных операций:** Операторам ПЛК не придётся регулярно разбираться с "зависшими" записями или обращаться в техподдержку.

## 6. Нереализованные пункты и рекомендации

| ID | Проблема | Причина отложения | Рекомендация |
|----|----------|-------------------|-------------|
| **#3** | Зарегистрированные ТС не уходят с табло очереди | Высокий риск: связь `ОчередьПриемки` ↔ `РегистрацияНаПЛК` требует исследования полей и бизнес-логики | Вынести в отдельную задачу на исследование |
| **#4** | Дубликаты с разной номенклатурой | Частично решается Точкой 2 (фильтрация при чтении) | Наблюдение; если дубли мешают — решать отдельно |
| **M-1** | Мусорные записи для ненастроенных табло | Не влияет на отображение (записи просто не читаются), но засоряет БД | Задача на рефакторинг записи в регистр (низкий приоритет) |
| **M-5** | Периодическая очистка для всех видов табло | Требует расширения регламентного задания | Реализовать после основного деплоя |

## 7. Открытые вопросы

Для финализации задачи требуется согласование следующих моментов:

1. **Очистка "хвостов":** После деплоя старые зависшие записи (те 64 записи) останутся в базе до следующего обновления по триггеру. Нужна ли разовая обработка для их удаления?
2. **Тестирование на КАТ (Курск):** Проверка работы на других видах табло ("НазначениеНаВыгрузку", "ОжиданияПроб"). Тестовая база testdb1c покрывает только Светлый.
3. **Связь очереди и регистрации:** Как технически связаны регистры `гкс_ОчередьПриемкиПЛК` и `гкс_РегистрацияНаПЛК`? Это критично для реализации Точки #3.
4. **Лимит записей:** Бывает ли ситуация, когда на одной точке одновременно находится более 10 активных ТС? (Сейчас стоит лимит `ПЕРВЫЕ 10`.)
