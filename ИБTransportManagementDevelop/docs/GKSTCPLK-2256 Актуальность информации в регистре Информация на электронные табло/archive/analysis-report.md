# GKSTCPLK-2256: Анализ регистра "Информация на электронные табло"

## Executive Summary

- **Критическая проблема [RC-2]**: Запросы для видов табло `НеПрошедшиеРегистрацию` и `НазначениеНаВесы` не фильтруют по статусу — ТС со статусом `Убыл` остаются в регистре; механизм периодической очистки отсутствует для 3 из 4 видов табло [REQ-2]
- **Мусорные записи [RC-1]**: Данные пишутся в регистр безусловно (до проверки наличия настроенных физических табло), что создаёт записи для ненастроенных видов табло [REQ-1]
- **Дубли по номенклатуре [RC-3]**: Запрос `ПолучитьСписокРегистрацийДляТабло` не использует параметр `&Номенклатура` — одна регистрация записывается N раз с разными номенклатурами [REQ-3], [REQ-4]
- **Нереализованный вид табло**: `ВозвратАвто` описан в перечислении, но полностью отсутствует в коде (ни в одном из двух путей записи)
- **5 точек модификации (M-1..M-5)** выявлены в 3 файлах; рекомендованный порядок: RC-2 (критический) -> RC-1 -> RC-3 -> RC-4 -> RC-5 -> RC-6

## 3. Потоки данных: два пути записи в регистр

### Путь 1: Изменение статуса регистрации (event-driven)

**Триггер**: Запись в РС `гкс_СостоянияРегистрации` (при изменении статуса ТС на ПЛК)

**Цепочка вызовов** [VERIFIED: RecordSetModule.bsl]:
```
гкс_СостоянияРегистрации.RecordSetModule
  └─ ПередЗаписью → СформироватьВариантыДляТабло()  [строки 111-154]
      │  Проверяет: ВидПеревозки = Автомобиль И ИспользуетсяЭлектронноеТабло(ТочкаМаршрута)
      │  НЕ проверяет: наличие настроенных табло для конкретного ВидТабло  ← [REQ-1]
      │
      │  Для каждой записи в наборе:
      │    Прибыл → ДобавитьВариантНазначениеНаВесы [строка 131]
      │             (Номенклатура = ДокументРегистрации.Номенклатура) [строка 190]
      │    ВыгрузкаРазрешена → ДобавитьВариантНазначениеНаВыгрузку [строка 137]
      │                      + ДобавитьВариантОжиданияПроб [строка 180]
      │    КачествоНеПринято → ДобавитьВариантОжиданияПроб [строка 144]
      │
      │  Свернуть ВариантыДляТабло [строки 149-150]
      │
  └─ ПриЗаписи → ЗарегистрироватьОбъектКОбменуСТабло()  [строки 239-276]
      │
      └─ Для каждого варианта:
          ├─ [1] гкс_ИнтеграцияСЭлектроннымТаблоСервер.ОбновитьТабло(ВидТабло, Параметры, Отказ)
          │    └─ ПолучитьСписокРегистрацийДляТабло(Параметры) → ПЕРВЫЕ 10 записей
          │    └─ Записать в гкс_ЭлектронныеТабло (замена по фильтрам)
          │    └─ ЗАПИСЫВАЕТ БЕЗУСЛОВНО — до проверки наличия физических табло  ← [REQ-1]
          │
          ├─ [2] СтруктураОтбораПоВидуТабло(ВидТабло) [строки 278-296]
          │    └─ Если ВидТабло не в словаре → Возврат (ВЫХОД из всей процедуры!)
          │    └─ НеПрошедшиеРегистрацию ОТСУТСТВУЕТ в словаре [строки 283-285]
          │
          ├─ [3] ПолучитьНастройкиПоВидуТабло(ТочкаМаршрута, ВидТабло, СтруктураОтбора)
          │    └─ Запрос к гкс_НастройкаЭлектронногоТабло
          │
          └─ [4] Для каждого настроенного табло:
               └─ ОтправитьДанныеНаЭлектронноеТабло(Табло) → RabbitMQ
```

**Обработанные виды табло**: НазначениеНаВесы, НазначениеНаВыгрузку, ОжиданияПроб

**Необработанные виды табло**: НеПрошедшиеРегистрацию (обрабатывается только через Путь 2), **ВозвратАвто** (НЕ реализован ни в одном пути -- см. раздел 3.1)

**Критический факт**: Состояние `Убыл` (терминальное) НЕ порождает ни одного варианта для табло. Это значит, что при убытии ТС обновление регистра НЕ происходит. → [REQ-2]

**Вложенный вызов** [VERIFIED: RecordSetModule.bsl:180]: Процедура `ДобавитьВариантНазначениеНаВыгрузку` (строка 156) **внутри себя** вызывает `ДобавитьВариантОжиданияПроб` (строка 180). Это означает, что каждое событие `ВыгрузкаРазрешена` неявно создаёт ДВА варианта: НазначениеНаВыгрузку + ОжиданияПроб. В схеме выше это отображено как два отдельных действия, но важно понимать, что ОжиданияПроб порождается **изнутри** процедуры НазначениеНаВыгрузку, а не параллельно.

**Важная деталь** [VERIFIED: RecordSetModule.bsl:258-263]: В `ЗарегистрироватьОбъектКОбменуСТабло` при неизвестном `ВидТабло` (отсутствующем в `СтруктураОтбораПоВидуТабло`) используется `Возврат` (выход из всей процедуры), а не `Продолжить` (пропуск итерации). Для текущего набора видов табло это не влияет (все три вида присутствуют в словаре), но при добавлении новых видов может привести к неожиданному прерыванию обработки.

### 3.1. Нереализованный вид табло: ВозвратАвто

В задаче описаны 5 видов табло, включая `ВозвратАвто` -- авто, не подходящие по качеству. Однако этот вид **полностью отсутствует** в реализации:

|---------------------------------------------------------------|----------------------------------------------|
| `СформироватьВариантыДляТабло` (RecordSetModule:111-154)      | НЕТ -- нет ветки для ВозвратАвто             |
| `ПолучитьСписокРегистрацийДляТабло` (Module.bsl:264-452)      | НЕТ -- нет ветки `ИначеЕсли ВозвратАвто`    |
| `ТекстЗапросаПоВидуТаблоДляОтображения` (ManagerModule:15-36) | НЕТ -- возвращает пустую строку              |

| `ОбновитьТаблоДляЭлектроннойОчереди` (Module.bsl:124-183)     | НЕТ -- hardcoded НеПрошедшиеРегистрацию      |

**Вывод**: Если в перечислении `гкс_ВидыЭлектронныхТабло` значение `ВозвратАвто` существует, его обработка не реализована. Необходимо уточнить у заказчика -- это запланированная функциональность или отменённая.

```

  └─ ПолучитьДанныеДляЗаполненияЭлектронногоТабло(ОбъектТабло, Параметры)
       └─ ЗаполнитьТаблицуСтрокТабло(Таблица, ОбъектТабло, НастройкиТабло)
```

## 4. Корневые причины проблем

### [RC-1] Записи для ненастроенных видов табло → [REQ-1]

**Файл**: `InformationRegisters/гкс_СостоянияРегистрации/Ext/RecordSetModule.bsl`

**Проблема** [VERIFIED: RecordSetModule.bsl:111-119]: Процедура `СформироватьВариантыДляТабло` (строка 111) проверяет только:
- `ВидПеревозки = Автомобиль` (строка 115)
- `ИспользуетсяЭлектронноеТабло(ТочкаМаршрута)` (строка 116)

Но **НЕ проверяет**, есть ли в `гкс_НастройкаЭлектронногоТабло` хотя бы одна запись для данного `ВидТабло + ТочкаМаршрута`.

**Механизм записи** [VERIFIED: Module.bsl:25-116]: В `ОбновитьТабло` данные записываются в регистр **БЕЗУСЛОВНО** (строка 100: `НаборЗаписей.Записать(Истина)`) -- ДО того, как в вызывающем коде проверяется наличие настроенных физических табло (строки 265-270 RecordSetModule). Таким образом:
1. Шаг 1: `ОбновитьТабло` -- данные УЖЕ в регистре
2. Шаг 2: `ПолучитьНастройкиПоВидуТабло` -- если табло нет, RabbitMQ-сообщение не отправляется, но записи в регистре ОСТАЮТСЯ

**Масштаб**: На Светлом настроены только 2 табло вида НеПрошедшиеРегистрацию. Но в регистре появляются записи для НазначениеНаВесы, ОжиданияПроб, НазначениеНаВыгрузку -- для табло, которых нет.

**Рекомендация**: Перед вызовом `ОбновитьТабло` проверять наличие настроенных табло через `ПолучитьНастройкиПоВидуТабло`. Если настроек нет -- пропускать вариант.

### [RC-2] Отсутствие фильтра по статусу в запросах НеПрошедшиеРегистрацию и НазначениеНаВесы → [REQ-2]

**Файл**: `CommonModules/гкс_ИнтеграцияСЭлектроннымТаблоСервер/Ext/Module.bsl`

**Проблема** [VERIFIED: Module.bsl:264-305]: Функция `ПолучитьСписокРегистрацийДляТабло` (строка 264) для видов `НеПрошедшиеРегистрацию` и `НазначениеНаВесы` (строки 274-305) выполняет запрос к `гкс_СостоянияРегистрации.СрезПоследних` с фильтрами `ТочкаМаршрута`, `ВидПеревозки`, `ТипРегистрации`, `Период >= &ТочкаОтсчета` -- но **БЕЗ фильтра по `СписокСостояний`**.

Параметр `СписокСостояний` устанавливается (строка 272), но **не используется в тексте запроса** для этих двух видов табло.

Для сравнения [VERIFIED]:
- `ОжиданияПроб` (строка 328): `ГДЕ СостоянияРегистрации.Состояние В(&СписокСостояний)` -- фильтр ЕСТЬ
- `НазначениеНаВыгрузку` (строка 403): `ГДЕ СостоянияРегистрации.Состояние В(&СписокСостояний)` -- фильтр ЕСТЬ

**Следствие**: ТС со статусом `Убыл` (и любым другим терминальным) продолжают попадать в выборку `ПЕРВЫЕ 10` и записываются в регистр. Запись остаётся, пока `Период >= ТочкаОтсчета` (24 часа от `ТекущаяДатаСеанса() - ЧислоСекундВСутках()`, см. RecordSetModule строка 229).

**Дополнительная причина зависания "месяцами"**: Запись обновляется только при ТРИГГЕРЕ (изменении статуса). Если после убытия всех ТС новые регистрации не приходят, старые записи остаются в регистре навсегда -- нет механизма периодической очистки для видов НазначениеНаВесы, ОжиданияПроб, НазначениеНаВыгрузку (регламентное задание обрабатывает только НеПрошедшиеРегистрацию).

**Рекомендация**:
1. Добавить фильтр `Состояние В(&СписокСостояний)` в запросы для НеПрошедшиеРегистрацию и НазначениеНаВесы.
2. Реализовать механизм периодической очистки/обновления регистра для ВСЕХ видов табло (расширить регламентное задание или создать отдельное).

### [RC-3] Отсутствие фильтра по номенклатуре при записи -- причина дублей → [REQ-3], [REQ-4]

**Файл**: `CommonModules/гкс_ИнтеграцияСЭлектроннымТаблоСервер/Ext/Module.bsl`

**Проблема** [VERIFIED: Module.bsl:274-305]: В функции `ПолучитьСписокРегистрацийДляТабло` для видов НеПрошедшиеРегистрацию и НазначениеНаВесы (строки 274-305):

1. Параметр `&Номенклатура` устанавливается (строка 277)
2. Но **не используется в WHERE-условии** запроса -- запрос получает ВСЕ регистрации для ТочкаМаршрута

**Механизм дублирования** [VERIFIED]:
1. `СформироватьВариантыДляТабло` создаёт вариант с `Номенклатура = ДокументРегистрации.Номенклатура` (RecordSetModule строка 190)
2. Свёртка `ВариантыДляТабло` по всем колонкам включая Номенклатуру (строка 149) -- каждая уникальная Номенклатура даёт отдельный вариант
3. Для каждого варианта вызывается `ОбновитьТабло`:
   - Набор записей создаётся с фильтром по `Номенклатура` (Module.bsl строка 64)
   - Но запрос `ПолучитьСписокРегистрацийДляТабло` возвращает ВСЕ регистрации, без фильтра по номенклатуре
4. Одна и та же регистрация записывается в регистр N раз -- с каждой уникальной Номенклатурой из вариантов

При записи в регистр [VERIFIED: Module.bsl:76-81]:
```bsl
НоваяЗапись = НаборЗаписей.Добавить();
ЗаполнитьЗначенияСвойств(НоваяЗапись, СтруктураПараметров);  // Номенклатура из варианта
ЗаполнитьЗначенияСвойств(НоваяЗапись, Строка);               // ДокументРегистрации из запроса
```

**Пример**: На Светлом регистрация ТМУТ-001 (Пшеница 3кл). При статусе Прибыл, если есть активные регистрации с другими номенклатурами (Пшеница 4кл, Пшеница продовольственная), вариант создаётся для каждой, и одна и та же регистрация попадает в регистр 3 раза с разными номенклатурами.

**Рекомендация**: Добавить `И Номенклатура = &Номенклатура` в запрос для НеПрошедшиеРегистрацию и НазначениеНаВесы (или убрать Номенклатуру как измерение этих записей).

### [RC-4] Отсутствие фильтра по номенклатуре в запросе отображения НеПрошедшиеРегистрацию → [REQ-3]

**Файл**: `InformationRegisters/гкс_ЭлектронныеТабло/Ext/ManagerModule.bsl`

**Проблема** [VERIFIED: ManagerModule.bsl:44-62]: Функция `ТекстЗапросаОтображениеНаТаблоНепрошедшиеРегистраци()` содержит WHERE:

```bsl
  И ЭлектронныеТабло.ВидТабло = &ВидТабло
```

Нет условия `И ЭлектронныеТабло.Номенклатура = &Номенклатура`, хотя в настройках табло поле Номенклатура присутствует, и для НазначениеНаВесы аналогичный запрос [VERIFIED: ManagerModule.bsl:88] этот фильтр содержит: `ЭлектронныеТабло.Номенклатура = &Номенклатура`.

Также [VERIFIED: RecordSetModule.bsl:278-296]: `СтруктураОтбораПоВидуТабло` (строка 278) не включает `НеПрошедшиеРегистрацию` в свой словарь (строки 283-285) → при вызове `ПолучитьНастройкиПоВидуТабло` для этого вида передаётся `Неопределено` вместо структуры с полем Номенклатура. Более того, `Возврат` на строке 262 прерывает ВСЮ процедуру `ЗарегистрироватьОбъектКОбменуСТабло` -- но поскольку НеПрошедшиеРегистрацию обрабатывается только через Путь 2 (электронная очередь), а не через Путь 1, этот `Возврат` в текущей реализации недостижим.

**Рекомендация**: Добавить фильтр по номенклатуре в запрос отображения, либо, если для НеПрошедшиеРегистрацию номенклатура не нужна -- убрать поле из формы настройки.

## 5. Детали блокировки и записи в ОбновитьТабло

[VERIFIED: Module.bsl:36-100]

Процедура `ОбновитьТабло` использует исключительную блокировку (`РежимБлокировкиДанных.Исключительный`) с различными фильтрами в зависимости от `ВидТабло`:

| ВидТабло             | Фильтры блокировки и набора записей                        |
|----------------------|------------------------------------------------------------|
| НазначениеНаВесы     | ТочкаМаршрута + ВидТабло + Номенклатура                    |
| НазначениеНаВыгрузку | ТочкаМаршрута + ВидТабло + Номенклатура + ЯмаРазгрузки     |
| ОжиданияПроб         | ТочкаМаршрута + ВидТабло + Весы                            |

При записи `НаборЗаписей.Записать(Истина)` (строка 100) -- замещение по установленным фильтрам: старые записи по этим фильтрам удаляются и заменяются новыми.

Ключевой момент: запись происходит **вне транзакции** (нет `НачатьТранзакцию`/`ЗафиксироватьТранзакцию`), но с блокировкой. В случае ошибки -- `Отказ = Истина` + логирование + повторный вызов исключения (строки 102-111).

Для сравнения, `ОбновитьТаблоДляЭлектроннойОчереди` (Путь 2) [VERIFIED: Module.bsl:142-179] работает **в транзакции** (`НачатьТранзакцию`/`ЗафиксироватьТранзакцию`/`ОтменитьТранзакцию`).
